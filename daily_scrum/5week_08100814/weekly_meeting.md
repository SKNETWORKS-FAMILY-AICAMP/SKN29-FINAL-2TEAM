# 5주차 주간 진행 내역 (2026.08.10 ~ 08.14)

## 주간 요약

8/8 오프라인 멘토링에서 프로젝트 방향이 **업무 분배 서비스 → 프로젝트 운영 Agent Platform**으로 확장됐다. 이번 주는 그 전환을 설계·화면·코드에 반영하는 데 썼다.

핵심은 **팀이 직접 에이전트를 만들어 쓰는 구조**다. 우리가 만든 기능을 고르는 것이 아니라, 무슨 일을 하는지·무엇을 참고할지·어떤 도구를 쓸지 적으면 팀 전체가 쓰는 에이전트가 된다. Harness 오픈소스 셋을 나눠 분석해 구조를 잡고, 기존 `orchestration` 확장이 아니라 **신규 작성**으로 전제를 정정했다.

화면도 이 방향에 맞춰 전면 개편했다. 온보딩 3종·대시보드·업무 분배 계열 화면을 걷고 **Chat 을 정문으로** 삼았다. 사용자가 화면을 순서대로 밟는 대신, 대화로 요청하면 정문 에이전트가 필요한 도구와 에이전트를 부른다.

주 후반에는 **시연 환경을 실제로 열었다.** 도메인(`halil-ai.site`)을 확보하고 EC2 에 https 로 올렸으며, `main` 에 push 하면 자동 배포된다. 그동안 「로컬에서는 되는데」로 남아 있던 것들이 공개 주소에서 검증 가능해졌다.

주간 규모는 커밋 **160건**, 374개 파일에서 44,381줄 추가·25,649줄 삭제다. 삭제가 큰 것은 폐기된 기능의 잔해를 걷어냈기 때문이다.

**아직 문서 파싱·임베딩 E2E 는 한 번도 끝까지 돌지 않았다.** 이번 프로젝트의 와우팩터인데 경로 검증이 남아 있다.

## 세부 진행 내용

### 1. Harness 구조 조사 — 3인 분담

방향 전환의 핵심을 **Agent Harness 환경 구축**으로 보고, 오픈소스 셋을 나눠 분석했다.

| 담당 | 대상 | 본 것 |
|---|---|---|
| 임준억 | OpenCode | Agent 구조와 설계 요소 — 코드 재사용이 아니라 우리 플랫폼에 적용할 구조 중심 |
| 김지훈 | deep-agent | 동작 방식, Agent 를 어떤 방식으로 설계해야 하는지 |
| 성주연 | clawcode | Agent product 가 어떤 구조로 동작하는지. 이후 함수 호출 흐름까지 추적 |

세 사례 모두 「도구를 가진 하나의 루프」라는 뼈대는 같고 도구 정의·실행 계약·이벤트 표현에서 갈렸다.

**전제 하나를 정정했다.** 기존 `services/orchestration` 을 확장해 Harness 를 만들 계획이었으나, 실제로는 12줄짜리 함수 하나뿐이라 확장할 실체가 없었다. 신규 작성으로 바꿨고 그 판단이 맞았다 — 해당 모듈은 이후 정리에서 삭제됐다.

### 2. 화면 전면 개편 — Chat 이 정문이 된다

업무 분배 시절의 화면은 **사용자가 정해진 순서를 밟는 구조**였다. 온보딩 3단계 → 대시보드 → 문서 선택 → 업무 추출 → 결과 확인. Agent Platform 에서는 이 순서가 맞지 않는다.

**Chat 을 정문으로 삼고 화면을 걷었다.** 삭제된 것은 `/onboarding/{connectors,folders,jira-project}`, `/dashboard`, `/tasks/*` 계열, `/workspace` 다. 대시보드가 하던 부하·업무 현황은 화면이 아니라 Chat 에서 내장 도구(`workload_report` 등)를 불러 본다.

커넥터 연결은 온보딩에서 **설정 탭으로 옮겼다.** 반복적인 「팀 관리」 성격이지 한 번 밟고 끝나는 절차가 아니기 때문이다. 설정은 팀·Connector·MCP·Model 네 탭으로 재편했고, **팀원은 읽기 전용**이다.

### 3. 에이전트 빌더와 실행 기록

에이전트를 만들 때 쓰는 도구 카탈로그 선택 UI 를 붙이고, 생성·검증 흐름을 구체화했다. 만든 에이전트가 실제로 도는지 확인하는 경로가 있어야 한다는 점을 확인해 검증 단계와 테스트 실행을 넣었다.

실행 기록(`agent_run`·`tool_call`)을 적재하기 시작했다. **평가의 모수가 되는 자리라 Harness 개발 초반에 넣어야 했다** — 나중에 붙이면 발표 전 측정이 불가능하다.

업무 추출 결과도 실제로 적재된다. 그전에는 응답으로만 존재해 새로고침하면 사라졌고, 이제 `task`·`proj_know_model` 에 남는다.

### 4. MCP 서버 — 등록해서 실제로 쓴다

외부 MCP 서버를 화면에서 등록하고 도구를 가져와 에이전트가 쓰는 경로를 붙였다. 등록·수정·연결 확인까지 되고, 시연용 MCP 서버를 Docker 로 띄워 실제 호출을 검증했다.

`services/mcp/security.py` 가 **https 아닌 주소와 사설 IP·내부 이름을 거절**한다(SSRF 1차 방어선). 이 때문에 시연에도 공인 https 주소가 필요했고, 그것이 도메인 확보를 앞당긴 이유 중 하나다.

### 5. 운영자 콘솔 — 보기만 되던 것을 조치할 수 있게

운영자 콘솔에 **볼 수만 있고 하지는 못하던 조치 네 가지**를 열었다.

| 열린 것 | |
|---|---|
| 운영자 권한 부여·회수 | 화면이 아니라 스크립트로만 — 승격 경로를 API 표면에 두지 않는다 |
| 팀 소유자 이전 | |
| 팀 에이전트·실행 기록 조회 | |
| **커넥터 강제 해제** | 그동안 제품 어디에도 없어서 **토큰이 유출돼도 고객도 운영자도 끊을 수 없었다** |

멘토링 피드백대로 **모델 등록 방식을 뒤집었다.** 사용자가 직접 API 키를 붙이는 대신 회사가 요청하면 운영자가 등록하는 흐름으로 바꾸고 제공자를 셋으로 넓혔다.

권한 정책도 화면과 서버를 맞췄다. 「팀장 전용」이라고 화면이 말하던 것 중 서버가 실제로 막지 않던 경로가 있었고, 표가 약속한 규칙 넷 중 셋이 코드에 없던 것을 확인해 채웠다.

### 6. AWS 시연 환경 — 1단계에서 공개 서비스까지

**8/11 · 1단계.** 팀원마다 자기 노트북에 Postgres 를 띄우던 구조를 걷었다. 스키마를 바꾸면 각자 수동 `ALTER` 를 돌려야 했고, A 가 등록·색인한 문서를 B 는 못 봤다. RDS·S3·IAM 을 만들고 EC2 는 인스턴스만 준비해 뒀다.

**8/14 · 2단계.** 도메인 `halil-ai.site` 를 확보하고 https 로 올렸다.

| | |
|---|---|
| 화면 | **https://halil-ai.site** (apex 가 본 주소, `www`·`app` 은 301) |
| API | `https://api.halil-ai.site` |
| MCP 시연 서버 | `https://mcp.halil-ai.site` — 주소 고정 |
| 인증서 | Let's Encrypt 자동 발급·갱신 (Caddy) |
| 배포 | `main` push → GitHub Actions → EC2 |

**도메인이 세 가지를 한 번에 풀었다.** Google OAuth 는 공인 IP 의 `http` redirect URI 를 받지 않고, MCP 서버 등록은 https 를 요구하며, 화면이 https 인데 API 가 http 면 브라우저가 막는다.

덜 눈에 띄지만 값이 큰 것이 하나 더 있다. RunPod 워커가 원문을 받아 가는 주소(`PUBLIC_BACKEND_BASE_URL`)가 그동안 **재시작마다 바뀌는 임시 터널**이었다. 시연 중 파싱이 조용히 끊길 수 있는 실패 모드였는데 도메인으로 고정됐다.

**이전 중 네 가지를 잡았다.** Caddy 가 빈 환경변수 때문에 재시작만 반복하던 것(web·frontend 는 200 이라 안쪽만 보면 멀쩡해 보인다), swap 이 0 이라 프론트 빌드가 OOM 날 상태, `SECURE_PROXY_SSL_HEADER` 누락으로 무한 리다이렉트가 날 상태, 그리고 시연용 MCP 서버가 **인증 없는 요청 하나에 다음 정상 요청을 먹는** 버그다. 마지막 건은 공개 주소라 스캐너만으로도 재현된다.

### 7. 문서 전처리 고도화

**제목 판정 (최원빈).** Docling 의 제목 검출은 텍스트의 볼드 여부를 고려하지 않는다. 폰트 정보로 볼드를 판단해 제목 신호로 쓰는 후처리 로직을 시험했다. 제목 레벨 판정도 우리 기준으로 다시 매기는 방향으로 고도화 중이다.

**순서 보정 (임준억).** 문장이 완결되지 않은 자리에서 다음 섹션을 검출하는 방안을 검증 중이다. **범용성과 효율성** 두 지표를 놓고 로직을 비교하고 있다.

### 8. 코드·문서 정리

다중 에이전트로 저장소를 훑어 폐기된 기능의 잔해와 죽은 코드를 찾았다. 8/13 에 **1만 3천 줄**을 걷었고, 8/14 에 한 번 더 훑어 25건을 추가로 정리했다.

가장 값이 컸던 것은 `ProjectRepository.get()` 이다. 호출부가 0건인데 **팀 검증 없이 `proj_id` 하나로 아무 프로젝트나 꺼내는 함수**였다. 정상 경로인 `get_for_team` 보다 이름이 짧아, 남아 있었으면 누군가 무심코 골라 테넌트 격리를 깼을 자리다.

문서도 실제 코드와 대조했다. 화면 목록·API 목록·배포 구조가 개편 전 상태로 남아 있던 것을 맞췄고, 참조 없는 구버전·중복 문서 16개(19.7MB)를 걷었다. **지우려다 만 것도 둘 있었다** — 외부 참고자료로 보였던 `개발_기획서_샘플/` 은 파싱 평가 코퍼스였고, `_archive/기획서_v2` 는 아키텍처 문서가 인용 중이었다.

## 현재 제한 및 다음 주 우선 과제

**가장 큰 제한은 파싱·임베딩 E2E 가 아직 한 번도 끝까지 돌지 않았다는 점이다.** 문서를 등록하면 RunPod 이 파싱·청킹·임베딩을 하고 그 결과로 검색이 되는 경로인데, 실제 문서로 검증한 적이 없다. RunPod 워커가 모델을 이미지에 굽고 있지 않아 첫 실행은 콜드 스타트로 수 GB 를 받는다 — **시연 당일에 하면 늦는다.**

- **문서 1건으로 파싱·임베딩 E2E 를 태우고 워커를 깨워 둔다** (최우선)
- 평가 골든셋 착수 — G-DOC·G-QUERY. 현재 0건이고 문서 단위 Recall 을 한 번도 재지 않았다. A안(요약 임베딩)이 미달이면 A′(tsvector 하이브리드)로 넓혀야 하는데, **3주차 말에 알면 고칠 시간이 없다**
- `storage.py` S3 어댑터 — 버킷·IAM Role 은 준비됐고 코드만 남았다. 지금은 원문이 EC2 로컬 디스크에 있다
- 에이전트 빌더 검증·스캐폴드 마무리
- Google·Atlassian 실제 연동 확인 (redirect URI 등록 완료, 화면에서 눌러 검증 필요)
- 팀원 재가입·초대 흐름 확인 — **가입 이메일이 HR 에 등록된 주소와 같아야 한다**
- `jihun` 브랜치가 `main` 대비 44 커밋 뒤처져 있다. 이번 주 정리로 `apps/people`·`repositories.py`·CSS 를 건드려 병합 시점 조율이 필요하다

> 참고: 시연 중에는 `main` 에 푸시하지 않는다. 배포 때 `web` 컨테이너가 재생성돼 몇 초 끊긴다.
