# 3주차 주간 진행 내역 (2026.07.27 ~ 07.31)

## 주간 요약

이번 주에는 MVP의 입력 데이터 기반과 역할별 사용자 흐름을 구체화했다. People DB·계정·외부 커넥터·문서 선택 저장 경로를 보강했고, 일반 사용자·팀장·팀원·운영자 화면을 역할별로 정리했다. 문서 파싱은 Docling 기반 구현과 품질 검증 방식 재설계를 진행 중이다.

주 후반에는 **우리 플랫폼을 쓰는 단위가 무엇인가**를 다시 정의했다. 한 회사만을 위한 시스템처럼 만들어져 있던 것을, 회사 안의 **팀**이 사용 단위인 구조로 고쳤다.

기획·설계 중심이던 지난주와 달리 실제 구현에 착수한 첫 주로, **로그인 → 팀 생성·팀원 초대 → Drive·Jira 연결 → 읽을 폴더·문서 선택**까지가 실계정에서 끊기지 않고 동작한다.

아직 문서 파싱 결과에서 업무 추출, 업무량 계산, 담당자 추천, PM 승인·재검증까지 이어지는 종단 흐름은 완성되지 않았다.

## 세부 진행 내용

### 1. 업무 분배 준비 기준 및 데이터 모델 정리

업무 분배 전에 필요한 HR, Jira, 기획서 데이터의 필수 항목을 검토했다. 데이터가 부족할 때 결과를 임의로 만들지 않고 `PARTIAL_RESULT`, `BLOCKED` 등 상태와 사유를 반환하는 방향을 정리했다.

또한 사내 계정, Google 계정, Jira 계정의 연결 기준과 업무 분배 시점 데이터 Snapshot 관리 방향을 검토했다.

데이터 기반에서는 두 가지 구조 변경이 있었다. 첫째, **Django ORM·Migration을 제거하고 `schema.sql` 기반 직접 SQL 구조로 전환**했다. 테이블 정의가 ORM 모델과 데이터 모델 문서로 이원화되는 것을 막기 위한 결정이다. 둘째, **벡터 저장소를 ChromaDB에서 pgvector로 전환**해 별도 인스턴스 없이 PostgreSQL 단일 DB로 운영한다.

HR/People DB 목업 데이터는 조직 9 · 직원 57 · Skill 14 · 직원별 Skill 111 · 근무일정 57 · 부재 23건으로 입력을 마쳤다.

### 2. Drive·Jira 연동과 문서 입력 경로 구현

Google Drive와 Jira OAuth 커넥터를 추가하고, 연결된 Drive에서 폴더를 탐색하고 문서를 조회하는 기능을 구현했다. 선택한 폴더와 탐색 깊이, 문서 역할을 저장해 프로젝트 입력 문서 범위를 구성할 수 있게 했다.

구현 중 **화면 순서에 대한 판단을 바꿨다.** 테이블 의존 관계상 프로젝트가 먼저 있어야 폴더를 연결할 수 있어 프로젝트 생성 화면을 앞에 두려 했으나, 문서를 근거로 프로젝트를 만드는 것이 제품 목적이므로 순서가 거꾸로였다. **폴더를 고르는 행위 자체가 프로젝트를 생성하도록** 바꾸고, 프로젝트명은 기획서 파싱 후 갱신하기로 했다.

폴더 전체를 한 번에 조회하던 방식도 트리 탐색으로 바꿨다. 실계정에서 폴더가 473개 나와 조회 상한에 잘렸고 실제 작업 폴더가 묻혔으나, 직속 하위만 받으면 최상위가 3개로 정리된다.

폴더를 다시 저장할 때 기존 문서의 파싱 관련 정보(해시·리비전)가 사라지지 않도록 갱신 방식을 보완했다. 토큰 만료 시 갱신 처리, 입력값 검증도 함께 적용했다.

**보안 점검에서 4건을 발견해 조치했다.** 프로젝트 생성 API 무인증, 배정 실행 API 2건 무인증, 폴더 id 검색식 주입, 그리고 `.env.example`에 실제 OAuth 시크릿이 들어간 상태(커밋 직전 발견·복구).

실계정 기준으로 Drive 폴더·파일 조회, Jira 프로젝트 조회, 문서 재저장과 선택 해제 흐름을 확인했고 문서 17건 등록을 검증했다.

### 3. 문서 파싱 및 검증 레이어 설계

문서 파싱 기능 구현을 시작하고 여러 파싱 모델을 비교했다. 그 과정에서 Docling SDK를 검토했고, **단일 파싱 모델이 아니라 여러 처리 단계를 조합해 파싱 워크플로우를 구성하는 SDK**로 다양한 문서 형식과 처리 과정을 유연하게 다룰 수 있다고 판단해 도입 방향을 잡았다.

Docling 결과를 원본 문서와 비교해 내용 정확도, 텍스트·구성요소 누락, 구조 유지, 표 변환을 검증하는 레이어를 설계했다.

멘토링 피드백에 따라 별도 검증 로직을 확대하기 전 **Docling 내부 파라미터를 충분히 조정·테스트하는 방향으로 전환**했다. 설정 가능한 주요 파라미터와 역할·적용 범위를 조사하고 파라미터 변경에 따른 결과를 비교했다.

현재는 Docling 설정만으로 해결 가능한 문제와 별도 검증이 필요한 문제를 구분하고 있으며, 과도한 검증 구조를 피하는 경량 검증 레이어를 재설계 중이다.

### 4. 인증·계정·역할별 사용자 흐름 보완

People DB(HR) 연결 상태를 관리하고, 사용자 본인 확인 후 플랫폼 계정과 HR 직원을 연결하는 흐름을 추가했다. **가입 경로를 기준으로 초대 코드 가입은 팀원, 직접 가입은 팀장으로 판정**하도록 정책을 정리했다. 별도 role 컬럼이나 권한 테이블을 두지 않는 방식이다.

초대 가입의 계정–직원 매핑은 이메일 비교가 아니라 초대 코드가 특정 직원에 미리 연결되어 있고 그 코드를 아는 사람만 수락할 수 있다는 "링크 소유 = 신원 확인" 모델을 쓴다.

팀원 초대 범위는 조직과 하위 조직 기준으로 조정했고, 로그인 상태 표시·라우트 가드·401 자동 로그아웃·로그인 후 이동 경로·세션 보관 방식을 보완했다.

### 5. 테넌트 경계 재정의 — 사용 단위는 회사가 아니라 팀

주 후반에 "범용 플랫폼이라고 했는데 한 회사만을 위한 시스템이 된 것 같다"는 문제 제기가 나왔고, 확인 결과 맞았다. **회사 안의 팀이 우리 플랫폼을 쓰는 것이지 회사 전체가 쓰는 것이 아니다.**

조직도에서 경계를 유도하려는 시도는 양쪽 다 실패했다. 회사를 기준으로 잡으면 과다 노출이고(실측: 개발팀 팀장이 회사 전 직원 56명을 보고 있었다), 조직을 기준으로 잡으면 팀원 한 명만 놓고는 어디까지가 우리 그룹인지 알 수 없다.

해법은 **팀을 명시적으로 만들게 하는 것**이었다. 온보딩에서 팀장이 본인 확인을 마치고 팀원을 고를 때 팀명을 함께 적게 하고, 그 팀으로 팀장과 팀원을 묶어 저장한다. 유도값이 아니라 실체가 되므로 경계가 흔들리지 않는다. `team`·`team_member` 테이블과 `user_account.team_id`·`member_invite.team_id`를 추가했다.

함께 **HR 목업(`org`/`person`)을 어댑터 한 곳으로만 읽도록 분리**했다. HR 목업은 Workday API를 붙일 수 없어(결제한 기업 고객 전용) 같은 모양의 DB로 대신한 것이고, 설계상 남의 시스템인데 코드에서는 43곳이 우리 테이블처럼 직접 조인하고 있었다. 어댑터 도입 후 HR 직접 접근은 0곳이다.

작업 중 **미인증 노출 1건을 발견해 조치**했다. `GET /api/people/`와 `GET /api/organizations/`가 인증 없이 직원 56명의 실명·실제 이메일을 반환하고 있었다. 지금은 로그인이 필요하고 본인 팀 소속만 반환한다.

### 6. 일반 사용자·팀장·팀원 화면 구현

Figma 기반 화면을 React 화면으로 정리하고, 랜딩 페이지부터 프로젝트 선택, 문서 등록, 팀원 선택, 분석·추천 결과 확인으로 이어지는 화면 흐름을 보완했다.

커넥터 온보딩과 폴더 선택 흐름, 팀장·팀원 설정 페이지, 초대 코드 입력 화면, 대시보드와 문서 등록 화면도 추가·개선했다.

**온보딩 4개 화면(커넥터 연결 / 폴더 선택 / 폴더 역할 / Jira 프로젝트)은 실제 API 연동을 마쳤다.** 실제 분석·추천 결과가 없는 구간은 데모 또는 제한 상태로 명시했다.

### 7. 운영자 콘솔 설계·구현

운영자 콘솔은 팀장 설정 화면과 분리해 별도 `/ops` 흐름으로 설계했다. 보안 경계를 URL 노출 여부가 아니라 별도 로그인에 둔다.

운영 현황, 연결 조직, 계정 관리, 계정 연결·초대, 연결 서비스, 감사 로그, 전역 정책 **7개 화면**을 Figma 목업으로 설계하고 피드백을 반영한 뒤 React 화면·라우팅·공통 레이아웃을 구현했다. 계정·조직·연결 서비스·감사·정책 관련 API와 화면 연동 작업도 이어졌다.

주 후반의 테넌트 경계 변경(5절)에 맞춰 **`연결 조직`을 `팀 현황`으로 교체**했다. 조직도는 고객사 HR 내부 사정이라 운영자가 열람할 자리가 아니고, 운영자가 봐야 하는 것은 "플랫폼을 쓰는 팀이 몇이고 그 안이 어떤 상태인가"다. 팀 행을 클릭하면 그 팀의 계정 목록으로 이동한다.

또한 콘솔 전 화면에서 **고유 번호(계정 ID·직원 ID·조직 ID 등)를 표시에서 뺐다.** 운영자가 판단에 쓰는 값이 아니고 고객사 직원 번호를 노출할 이유도 없어서, 이름·이메일·시각 같은 사람이 읽는 값으로 대체했다. 식별자는 API 응답과 화면 이동에는 그대로 쓴다.

운영자 UI 설계·프론트 구현과 서버 API·DB 구현은 담당 범위를 구분해 관리했다.

### 8. 문서화·발표·운영 준비

AWS 이전 매뉴얼, DB 실행 가이드, 권한 정책, 데이터 모델·설계 문서, 중간발표 개요와 To-Do를 실제 구현 상태에 맞게 갱신했다. 특히 중간발표 To-Do는 코드와 DB를 직접 확인한 실측 기준으로 고쳐, 완료 항목과 부분 완료 항목을 구분했다.

또한 일별 스크럼과 기능별 작업기록을 남기기 시작했다. 커넥터 문서 선택·저장, 운영자 콘솔 UI 구현, 테넌트 경계 재정의는 판단 근거, 검증 결과, 제한 사항, 후속 인계 사항까지 별도 문서로 기록했다.

## 현재 제한 및 다음 주 우선 과제

**가장 큰 제한은 파싱과 플랫폼의 접점이 아직 없다는 점이다.** 플랫폼은 "어떤 문서를 읽을지"까지 저장하지만 원문을 내려받지 않고, 파싱은 이 문서를 입력으로 받지 않는다. 두 구간이 붙어야 그 뒤 전체가 열린다.

- Docling 파라미터 테스트 결과를 정리하고 문서 유형별 적절한 설정을 확정
- Drive 원문 다운로드와 로컬 저장소 저장 경로 구현 (해시·리비전 기록 포함)
