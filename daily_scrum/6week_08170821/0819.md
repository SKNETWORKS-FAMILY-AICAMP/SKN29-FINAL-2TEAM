### N. 홈페이지 고도화 (준)

어제 「채팅 복구 대기」로 끝냈던 것이 풀렸고, **배포본을 브라우저로 끝까지
밟았다.** QA 체크리스트 §B-0 14 항목을 전부 통과시켰고, 그 과정에서 나온 결함을
그 자리에서 고쳤다. **오늘 고친 것 중 단위 테스트가 미리 잡을 수 있었던 것은
거의 없다** — 대부분 화면을 눌러야만 나오는 종류였다.

---

**① 승인 게이트가 대화를 조용히 끊고 있었다.** 쓰기 도구(`task_register`)를
부르면 그래프는 멈추는데 **「멈췄다」는 이벤트를 아무도 안 보냈다.** 서버는 200
으로 응답을 닫고, 화면은 빈 채로 남는다. 승인 카드가 뜰 방법이 없었다.

LangGraph 는 인터럽트를 `{"__interrupt__": (…)}` 로 내보내는데 값이 dict 가
아니라 **tuple** 이라, `updates` 를 `node_name -> dict` 로 훑던 이벤트 변환기가
조용히 버리고 있었다. 멈추는 쪽(`interrupt_on`)만 배선돼 있고 알리는 쪽·재개하는
쪽이 없던 **반쪽 상태**였다.

이어 붙였다. 레거시와 **같은 이벤트 모양**으로 냈더니 화면의 확인 카드와 저장
코드는 한 줄도 안 고쳐도 됐다. 승인 → `task` 테이블 **0 행 → 15 행**까지 확인.
부분 선택(체크를 풀고 일부만 등록)도 밟았다 — 10 건 중 7 건만 고르니 정확히
7 건만 들어갔다.

**② 프로젝트 대화가 무관한 문서를 읽고 있었다.** 화면은 「〈프로젝트〉의 문서를
근거로 답합니다」라고 약속하는데 `document_search` 는 `proj_id` 를 **인자로 받지도
않았다.** ERP 재구축 프로젝트에서 물었더니 「테스트.pdf」를 후보로 올려 5MB 를
읽었다. 프로젝트 문서를 먼저 보고, 없을 때만 팀 전체로 넓힌다.

**③ 모든 프로젝트가 같은 기준 문서를 자기 것으로 보여줬다.** 팀원이 실제로 써
보다가 나왔다. AI Platform 에서 「기준 문서에서 업무를 뽑아줘」가 「기준 문서가
없다」로 끝나는데 **그 화면에는 기준 문서가 버젓이 있었다** — 내용은 전혀 다른
ERP 감리용역 제안서였다.

화면이 팀 문서 목록에서 `doc_role === 'PRIMARY'` 하나만 보고 골랐다. `proj_id`
를 안 본다. **서버는 사실을 말했고 화면이 잘못 읽었다.** 기준 문서가 팀에
하나뿐일 때는 우연히 맞아서 오래 안 드러났고, 오늘 프로젝트를 하나 더 만들면서
「있는 쪽과 없는 쪽」이 처음 생기자 나왔다. 「업무 추출」 버튼이 활성이라
**엉뚱한 문서로 업무를 뽑을 수 있었다.**

**④ 배포 관련 둘.** `index.html` 에 캐시 헤더가 없어서 배포 뒤 새로고침해도 옛
화면이 남았다(내가 QA 중에 실제로 속아서 코드를 다시 봤다). 그리고 없는 자산에
`index.html` 을 돌려주고 있어서, 배포로 이름이 바뀐 조각을 찾던 탭이 「모듈인 줄
알았는데 HTML」로 깨졌다. 둘 다 **시연 중에 나면 원인을 못 찾는 종류**다.

**⑤ 정직 표기 두 건.** 모델이 「투입공수를 0시간으로 등록했습니다」라고 했는데
DB 는 `NULL` 이었다 — 0 을 버리는 것은 맞고(0 시간짜리 업무는 없다) **버렸다고
말하지 않은 것**이 틀렸다. 날짜에만 있던 알림을 공수·역할·우선순위까지 넓혔다.
그리고 「추가로 등록해줘」에 새 판이 생겨 **앞서 등록한 15 건이 화면에서
사라졌다** — 데이터는 남아 있는데 안 보이는 것이라 더 나빴다.

**⑥ 기다리는 동안 영어 독백이 보이던 것.** 생각 과정이 도는 동안 자동으로
펼쳐져서, 기다리는 내내 모델의 내부 독백이 화면 한가운데 있었다. OpenAI 의
reasoning 요약은 우리가 언어를 통제할 수 없다. 접어 두고, 그 옆의 한국어
상태줄이 **레지스트리의 사람 이름**을 쓰게 했다 — 「`task_register` 실행 중」이
「업무 등록 실행 중」이 됐다.

### 요청받아 새로 만든 것

**운영자 콘솔에 팀·계정 완전 삭제.** 지금까지 운영자가 할 수 있는 것은 잠금과
소유자 변경뿐이라 지울 방법이 없었다.

⚠ **이 저장소에는 외래키 제약이 하나도 없다**(실측 0 개). `DELETE FROM team` 은
막히지도 딸려 지워지지도 않고, 그냥 지워지고 나머지가 **오류 없이 고아가 된다.**
그래서 지울 것을 표로 전부 적었다 — 팀 39 단계, 계정 14 단계. 체크포인트 3 종도
지운다(대화 id 가 곧 `thread_id` 라, 안 지우면 승인 대기가 유령으로 남는다).

| 정한 것 | |
|---|---|
| 팀을 지워도 | **계정은 무소속으로 남긴다** |
| 계정을 지워도 | 팀 자산(문서·프로젝트·에이전트)은 남고 **소유자만 팀장에게 넘어간다** |
| 감사 기록 | **지우지 않는다** |
| 확인 | 팀은 이름, 계정은 **이메일**을 그대로 입력 |

막는 것 — 본인 계정·본인이 속한 팀·팀 소유자·마지막 운영자. 화면과 서버 **양쪽**
에서 검사한다(화면만 막으면 API 직접 호출이 열린 채로 남는다).

실제로 「개발팀B」와 계정 하나를 지워 확인했다 — **481 건**이 함께 사라졌고
잔재·고아 0, 감사 기록은 남았다.

> 그 과정에서 **지워진 번호가 재사용되는 것**을 발견했다. `UA005` 를 지우니
> 재가입자가 같은 `UA005` 를 받았다. 그러면 감사 기록의 「UA005 를 삭제했다」와
> 살아 있는 `UA005` 가 다른 사람인데 id 로는 구별되지 않는다. 감사 기록의 삭제
> 이력까지 보고 번호를 매기게 고쳤다(새 표를 만들지 않아 팀원이 돌릴 ALTER 도
> 없다).

**문서를 왜 못 읽었는지 저장한다.** 지금까지 「실패했다」까지만 알았다. 그런데
「암호가 걸린 PDF」는 암호를 풀어 다시 올리면 되고 「스캔본」은 다시 올려도 같다
— 사람이 할 행동이 정반대인데 화면이 「본문 추출 실패」 하나로 뭉갰다.
**추출기는 이 문구들을 이미 만들고 있었고** 담을 칸이 없어 저장 직전에 버려지고
있었다. 칸을 만들어 이어 붙였다(새로 계산하는 값이 아니다).
