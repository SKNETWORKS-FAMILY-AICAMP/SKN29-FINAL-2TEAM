## 문서 목적

이 문서는 기존 청킹·임베딩 작업을 검토한 뒤, 다음 작업에서 집중할 문제와 임베딩 모델 변경 이유만 기록한다.

각 문제의 구체적인 해결 방법, 구현 방식, 파라미터와 평가 방법은 아직 확정하지 않는다. 이후 실험과 논의를 통해 하나씩 결정한다.

## 개선 대상으로 확정한 세 가지 문제

### 1. 제목 계층 및 문맥 복원

현재 파싱 결과에서는 제목의 계층 정보가 충분히 보존되지 않고, 제목이 `level=1`로 평탄화되어 들어오는 문제가 확인됐다.

이로 인해 HybridChunker 결과에는 `Features`, `Specifications`와 같은 마지막 제목만 남고, 해당 내용이 어느 제품군과 상위 섹션에 속하는지 구분하기 어려워진다. 불완전한 제목 문맥은 본문과 표에 전달되며, 서로 다른 제품이나 페이지의 내용이 같은 문맥으로 판단되는 원인이 될 수 있다.

다음 작업에서는 제목의 정확한 계층과 각 본문·표·이미지가 속한 문맥을 어떻게 복원할지 검토한다.

### 2. 표 구조 보존 청킹

기본 HybridChunker는 표를 텍스트로 직렬화한 뒤 토큰 제한에 맞춰 분할한다. 이 과정에서 표의 행과 열 관계가 약해지고, 긴 행이나 셀 값이 청크 경계에서 나뉘는 문제가 확인됐다.

Markdown 표 직렬화와 헤더 반복을 적용해 기본 Triplet 표현보다 구조와 토큰 제한 준수는 개선했지만, 한 행 자체가 긴 경우의 분할, 불완전한 Markdown 행, 원본 표 구조 오류와 잘못된 제목 연결은 여전히 남아 있다.

다음 작업에서는 표의 행·열 의미와 셀 값의 완전성을 유지하면서 청킹하는 방법을 검토한다.

### 3. 이미지 유형별 설명·문맥 결합·검색 고도화

현재 파싱 및 청킹 결과에는 `Logo`, `Icon`, `Engineering drawing` 같은 저정보 문자열과 부정확한 이미지 설명이 포함될 수 있다. 이미지 설명이 일반 본문과 섞여 검색 공간을 오염하는 문제도 확인됐다.

현재 파이프라인은 image-only 청크를 임베딩에서 제외하고 혼합 청크에서 이미지·캡션 내용을 제거해 검색 오염을 방지한다. 그러나 이는 유용한 이미지 정보를 활용하는 고도화가 아니라 제외 중심의 안전장치다.

다음 작업에서는 이미지 유형별 설명, 주변 제목·본문과의 문맥 결합, 이미지 정보를 활용한 검색 고도화 방법을 검토한다.

## 임베딩 모델 변경 이유

### 기존 모델의 제약

기존 모델은 다음과 같다.

```text
sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2
최대 입력 길이: 128토큰
출력 벡터 차원: 384차원
```

128토큰의 입력 길이는 제목 계층, 표 헤더, 긴 표 행, 이미지 설명과 주변 문맥을 함께 포함하는 청킹 개선을 실험하기에 제약이 크다. 384차원 역시 이후의 구조적·시각적 문맥을 표현하는 기준 모델로 사용하기에는 제한적이라고 판단했다.

### 변경 후보

다음 모델을 새로운 기준 모델 후보로 정한다.

```text
google/embeddinggemma-300m
모델 규모: 약 300M 파라미터
최대 입력 길이: 2,048토큰
최대 출력 벡터 차원: 768차원
```

### 선택 의도

EmbeddingGemma는 기존 MiniLM보다 입력 길이와 표현 차원을 확장하면서도, 수십억 파라미터 규모의 대형 모델은 아니다.

따라서 모델 크기를 과도하게 높여 성능을 확보하기보다, 약 300M 규모의 제한된 모델 리소스를 기준으로 고정한 뒤 제목·표·이미지 청킹 개선이 검색 성능에 어떤 영향을 주는지 확인하려는 목적에 적합하다고 판단했다.

모델 교체만으로 성능이 향상된다고 가정하지 않는다. 실제 청크 크기와 세부 파라미터는 아직 결정하지 않았으며, 모델 교체 후 별도 실험을 통해 정한다.

## 현재 확정 범위

현재 확정한 내용은 다음 네 가지뿐이다.

1. 제목 계층 및 문맥 복원을 개선 대상으로 삼는다.
2. 표 구조 보존 청킹을 개선 대상으로 삼는다.
3. 이미지 유형별 설명·문맥 결합·검색 고도화를 개선 대상으로 삼는다.
4. 기존 MiniLM의 128토큰·384차원 제약을 완화하기 위해 `google/embeddinggemma-300m`을 새로운 기준 모델 후보로 사용한다.

구체적인 해결 방법과 구현 순서는 이후 논의를 통해 결정한다.
