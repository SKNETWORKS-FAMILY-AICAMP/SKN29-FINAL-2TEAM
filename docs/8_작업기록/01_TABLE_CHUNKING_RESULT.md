# 표 구조 보존 청킹 1차 개선 결과

## 문서 목적

이 문서는 표 구조 보존 청킹의 기준선 문제, 개선 방향, 구현 결과와 현재 단계에서 남겨둘 한계를 기록한다.

현재 목표는 파서가 표를 완벽히 이해하도록 만드는 것이 아니다. 비정형 PDF에서 파싱된 표 구조를 이용해 검색에 적합한 논리 단위로 청킹하고, 셀 값과 제품·속성 관계의 훼손을 줄이는 것을 목표로 한다.

## 기준선에서 확인한 문제

Docling과 EasyOCR로 파싱한 문서를 EmbeddingGemma 토크나이저 기반 기본 HybridChunker에 입력했을 때 다음 문제가 확인됐다.

- 표가 일반 텍스트처럼 직렬화된 뒤 토큰 기준으로 분할됐다.
- 하나의 셀 값이 청크 경계에서 나뉘었다.
- 제품명, 속성명과 값의 행·열 관계가 약해졌다.
- 표 조각이 주변 본문이나 `Engineering drawing` 같은 이미지 문자열과 섞였다.
- 표를 포함한 일부 청크가 설정한 512토큰을 초과했다.

실제 기준선에서는 다음과 같은 분절이 확인됐다.

```text
Discharge | Pressure
50 ~ | 364
5,700 x | 2,800 x 2,950
```

이 문제는 MiniLM에서 EmbeddingGemma로 모델과 토크나이저를 변경한 뒤에도 동일하게 나타났다. 따라서 임베딩 모델 자체의 문제가 아니라, 표를 직렬화해 일반 HybridChunker에 전달하는 처리 방식의 한계로 판단했다.

## 검토한 접근 방식

Docling의 Markdown 출력 대신 JSON 표 구조를 사용하는 방법을 검토했다.

Docling JSON에는 각 표에 다음 정보가 포함되어 있다.

- `num_rows`, `num_cols`
- `table_cells`
- 셀 텍스트
- 행·열 시작 및 종료 위치
- `row_span`, `col_span`
- 행 머리글과 열 머리글 여부
- 페이지와 원본 위치 정보

HybridChunker에 JSON 문자열을 그대로 넣는 방식은 선택하지 않았다. JSON을 문자열로 직렬화하면 필드명이 토큰을 소비하고, HybridChunker가 토큰 경계에서 JSON이나 셀 값을 다시 분할할 수 있기 때문이다.

대신 처리 책임을 다음과 같이 분리하는 방식을 선택했다.

```text
일반 텍스트·목록 → HybridChunker
표               → 구조 보존 TableChunker
이미지           → 이후 별도 개선
```

현재 구현한 TableChunker는 Docling의 공식 내장 `TableChunker` 클래스를 사용한 것이 아니라, `table_cells`를 직접 읽어 표에 맞는 논리 단위로 재구성하는 전용 로직이다.

## 구현한 1차 방식

구현 파일은 `runpod/06_chunk_tables_structured.py`이다.

한화 PDF의 사양표는 첫 행에 제품명이 있고 각 열에 제품별 사양이 배치된 구조다. 따라서 표 하나를 단순 행 단위로 자르지 않고, 다음과 같이 제품 열 단위로 재구성했다.

```text
제품 모델
├── Capacity / m³/hr
├── Capacity / CFM
├── Power / kW
├── Power / HP
├── Discharge Pressure / bar A
├── Discharge Pressure / Psi A
└── Dimension
```

구현 원칙은 다음과 같다.

- 제품명과 해당 제품의 속성 전체를 하나의 논리 단위로 만든다.
- 여러 제품에 걸친 병합 셀의 공통값을 각 제품 청크에 전달한다.
- 하나의 셀은 원자 단위로 취급하여 셀 내부 텍스트를 임의로 나누지 않는다.
- 구조화 JSON을 원본 데이터로 보존한다.
- 임베딩에는 JSON 전체가 아니라 별도로 생성한 `embedding_text`를 사용한다.
- 제품 청크가 토큰 제한을 넘는 경우에만 셀 속성 단위로 분할한다.
- EmbeddingGemma 토크나이저와 512토큰 제한을 사용한다.

## 실행 결과

Docling + EasyOCR로 파싱한 6페이지 한화 PDF의 고정 JSON을 입력으로 실행했다.

```text
표 수: 5
제품별 표 청크 수: 13
최소 토큰: 147
평균 토큰: 167.15
최대 토큰: 179
512토큰 초과 청크: 0
구조 경고: 0
```

표별 결과는 다음과 같다.

| 표 | 행×열 | 제품 수 | 생성 청크 수 |
|---|---:|---:|---:|
| 0 | 9×7 | 5 | 5 |
| 1 | 9×6 | 4 | 4 |
| 2 | 9×3 | 1 | 1 |
| 3 | 8×3 | 1 | 1 |
| 4 | 9×5 | 2 | 2 |
| 합계 | - | 13 | 13 |

예를 들어 SM3100 Pro는 다음과 같이 하나의 청크로 재구성됐다.

```text
제품 모델: SM3100 Pro
Capacity / m 3 /hr: 3,300 ~ 5,690
Capacity / CFM: 1,950 ~ 3,240
kW: 250 ~ 600
HP: 270 ~ 800
Discharge Pressure / bar A: 3.0 ~ 13
Discharge Pressure / Psi A: 43 ~ 188
Dimension (L x W x H) / mm: 5,250 x 2,250 x 2,500
Dimension (L x W x H): 3,210 x 2,150 x 1,920
```

기본 HybridChunker에서 분리됐던 압력 범위와 치수 값이 완전한 셀 단위로 유지됐으며, 제품명과 해당 제품의 전체 사양도 같은 청크에 포함됐다.

## 달성한 개선 범위

이번 1차 개선에서 달성한 내용은 다음과 같다.

- 표 전체의 텍스트 직렬화 후 분할 방식을 제품 중심의 논리적 분할로 변경했다.
- 제품명과 속성값의 관계를 한 청크 안에 유지했다.
- 병합 셀의 값을 관련된 제품에 전달했다.
- 압력·치수 등의 셀 값이 중간에서 분절되는 문제를 방지했다.
- 구조화 데이터와 임베딩 입력을 분리했다.
- 모든 제품 청크를 512토큰 이내로 생성했다.
- SA 계열 표의 `Compressor`, `Cooler` 치수 구분을 보존했다.

따라서 기본 HybridChunker의 표 처리에서 나타난 핵심 문제인 **셀 값 분절**과 **제품·속성 문맥 훼손**은 1차적으로 개선됐다고 판단한다.

## 남은 한계

`warnings`가 없다는 것은 현재 로직이 탐지하는 빈 값이나 구조적 실패가 없다는 의미다. OCR과 파싱 결과의 의미가 모두 정확하다는 뜻은 아니다.

원본 PDF와 결과를 대조했을 때 다음 한계가 남아 있다.

### 파싱 단계에서 누락된 계층 라벨

원본 표의 `Power` 상위 항목이 일부 Docling `table_cells`에서 누락되어 다음처럼 표현된다.

```text
kW: 250 ~ 600
HP: 270 ~ 800
```

원래 의미는 다음과 같다.

```text
Power / kW: 250 ~ 600
Power / HP: 270 ~ 800
```

### P/S 치수 유형의 의미 유실

원본 표에서 두 치수 행은 다음 의미를 가진다.

- `P`: Package type
- `S`: Standard type

일부 파싱 결과에서는 `P`, `S` 셀이 누락되어 두 치수의 값은 보존되지만 유형을 구분하는 라벨이 사라진다.

### OCR 및 표기 정규화 문제

다음과 같은 표현이 남아 있다.

```text
m 3 /hr
SM7100 +
mm S
```

이는 각각 `m³/hr`, `SM7100+`, `mm / Standard type`으로 정규화할 수 있지만, 이번 단계에서는 특정 문서에 맞춘 하드코딩을 추가하지 않았다.

### 표 유형에 대한 일반화 범위

현재 방식은 제품이 열 방향으로 배치된 사양표에 적합하다. 다음 구조는 별도의 방향 판별과 논리 단위 설계가 필요하다.

- 제품이 행 방향으로 배치된 표
- 다단 헤더 표
- 재무제표
- 시간표
- 여러 페이지에 걸친 표
- 셀 병합이 매우 복잡한 표

## 현재 단계의 판단

현재 목표는 비정형 PDF에서 파싱된 표를 검색 가능한 단위로 안정적으로 청킹하는 것이다. 파서가 누락한 의미를 청킹 단계에서 임의로 추론해 완전하게 복원하는 것까지는 현재 범위에 포함하지 않는다.

다음 원칙으로 표 개선의 범위를 정한다.

> 청킹 단계는 파싱 결과에 존재하는 구조를 최대한 보존하고 재구성한다. 파싱 과정에서 사라진 의미는 임의로 생성하지 않으며, 해당 부분은 파싱 및 구조 복원의 한계로 기록한다.

따라서 표 구조 보존 청킹은 **1차 개선 완료**로 판단한다. 파싱 오류 보정, 표 유형 자동 판별, 도메인 의미 복원은 추후 개선 사항으로 남긴다.

## 파이프라인 통합 결과

`runpod/07_build_stable_chunks.py`에서 표가 제거된 문서에는 HybridChunker를,
원본 `tables[]`에는 구조 보존 TableChunker를 적용한 뒤 원문 순서로 통합했다.

EmbeddingGemma 토크나이저와 512토큰 제한으로 검증한 결과는 다음과 같다.

```text
전체 청크: 52
일반 청크: 39
표 청크: 13
최소 토큰: 4
평균 토큰: 126.77
최대 토큰: 440
HybridChunker 표 잔존: 0
빈 청크: 0
토큰 초과: 0
표 처리 실패: 0
필수 안정성 검증: 통과
```

따라서 표가 HybridChunker와 TableChunker에서 중복 생성되는 문제는 해결됐다.
통합 결과는 `runpod/output/05_stable_chunks_512`에 보존한다.

추가 검토 대상으로 20토큰 미만 청크 7개와 페이지 5·6을 함께 포함하는
다중 페이지 청크 1개가 탐지됐다. 이미지 요소는 아직 HybridChunker 처리에
포함되어 있으며, 제목 계층 및 이미지 의미 개선은 적용하지 않은 상태다.
