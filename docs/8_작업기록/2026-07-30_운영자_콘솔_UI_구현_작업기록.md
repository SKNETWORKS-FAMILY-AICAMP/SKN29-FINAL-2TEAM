## 3. 판단이 바뀐 지점

### 3.1 팀장 설정 화면과 운영자 콘솔을 합치지 않았다

초기 피드백 중에는 일반 제품 흐름을 팀장 중심으로 정리하자는 의견이 있었다. 하지만 `/ops`는 팀장이 자신의 팀을 설정하는 화면이 아니라 플랫폼 개발·운영자가 별도 로그인으로 전체 연결 상태와 운영 위험을 점검하는 화면이다.

역할별 권한 정책과 최신 구현을 다시 대조해, 팀장·팀원 설정은 기존 설정 화면에 두고 운영자 콘솔은 별도 진입·별도 레이아웃으로 유지했다. 같은 조직·계정 정보를 보더라도 팀장 화면은 소속 범위의 설정, 운영자 화면은 플랫폼에 적재·연결된 범위의 운영 점검이라는 목적이 다르다.

### 3.2 운영자는 HR 원본 조직을 편집하지 않는다

`org`와 `person`은 People DB에서 가져오는 원본 데이터이므로, 운영자 화면을 인사 조직 편집기로 만들지 않았다. 조직 현황은 계층·인원·동기화·오류를 확인하는 조회 화면으로 설계했다.

계정 상태, 오류 연결 해제, 이상 초대 폐기, 시스템 공지는 플랫폼이 소유하거나 운영 조치가 필요한 대상에만 제한적으로 배치했다. 감사 로그는 수정·삭제할 수 없는 조회 전용으로 표시했다.

### 3.3 정보 노출과 조치 권한을 분리했다

기본 목록에는 계정 이메일, 직원 ID, 연결 조직·상태를 우선 표시하고, 개인 이름·외부 연결 상세는 오류 조사처럼 필요한 선택 상세에서만 보이도록 설계했다. 초대 코드 원문은 서버에 해시만 남기는 정책과 맞지 않으므로 재표시하지 않았다.

이를 통해 화면이 데이터를 많이 보여주는 관리 화면이 아니라, 최소 정보로 문제를 찾고 허용된 조치를 선택하는 운영 화면이 되도록 했다.

### 3.4 정적 UI를 실제 운영 기능처럼 보이게 만들지 않았다

운영자 API와 실제 권한 계약이 확정되지 않은 상태에서 임시 API 호출을 만들면 실제 동작처럼 오해할 위험이 있다. 1차 구현은 정적 목업 데이터와 페이지 로컬 상태로 제한했다.

따라서 검색·필터·선택 상세·공지 편집·확인 모달은 화면 검토용 상호작용이며, 새로고침하면 초기화된다. 실제 보안이나 데이터 변경 기능으로 간주할 수 없다.

## 4. 설계·구현한 화면

Figma에서 공통 사이드바, 상태 배지, 색상·간격·텍스트 스타일을 먼저 정리한 뒤 React의 운영자 전용 공통 UI로 반영했다. 화면은 다음과 같이 구성했다.

| 화면 | UI에서 확인할 수 있는 범위 |
|---|---|
| 운영자 로그인 | 일반 사용자 로그인과 분리된 운영자 진입 화면과 목업 보호 흐름 |
| 운영 현황 | 계정·연결 상태 요약, 확인할 일, 최근 운영 활동, 관련 화면 이동 |
| 연결 조직 | 적재된 조직 계층과 동기화·오류 상태의 조회 |
| 계정 관리 | 계정 상태, 필터, 선택 상세, 중복 연결 오류에 한정한 조치 진입점 |
| 계정 연결·초대 | 초대·연결 상태 조회, 검색·필터, 오류·대기 상태 확인 |
| 연결 서비스 | 인사 정보·Google Drive·Jira 연결 현황, 상태 필터, 선택 상세 |
| 감사 로그 | 운영 조치 이력과 분석·결정 기록의 분리, 배정 실행·추천·검증·결정 기록 탭 |
| 전역 정책 | 초대 정책, 시스템 공지 목록·상세, 정책 변경 전후 비교 UI |

React 구현은 `App.tsx`, `routes.ts`, 운영자 공통 컴포넌트, 8개 화면 컴포넌트, 전용 CSS Module, 목업 데이터·세션 유틸을 포함한 20개 프론트엔드 파일로 구성했다. 기준 커밋에서는 3,251줄을 추가하고 2줄을 변경했다.

## 5. 피드백을 반영하며 개선한 부분

- 운영 현황을 단순 숫자·목록에서 상태 비교와 우선 조치가 보이는 화면으로 변경했다.
- 내부 영문 상태 코드와 용어를 사용자 관점의 한글 문구로 바꾸고, `Connector`를 `연결 서비스`로 정리했다.
- 계정 생성·삭제처럼 권한 범위가 불명확한 동작은 제거하고, 상태 정지·재활성 또는 오류 연결 조사처럼 정책상 검토 가능한 조치로 좁혔다.
- 감사 로그에서 운영 조치 이력과 분석·결정 결과 계보를 분리해, 각 화면이 조회하려는 목적이 섞이지 않도록 했다.
- 필터 후 선택한 상세가 남는 문제와 빈 결과 상태를 보완하고, 요약 수치·표 헤더·상세 정보의 대응을 점검했다.
- 시스템 공지는 목록에서 바로 수정·삭제를 병렬로 노출하지 않고, 상세 확인 후 수정·삭제로 이어지도록 흐름을 조정했다.

## 7. 잘된 점과 개선할 점

### 잘된 점

- Figma 목업 단계에서 역할·권한·데이터 소유 경계를 먼저 검토해, React 구현 뒤에 화면 목적을 크게 되돌리는 일을 줄였다.
- 일반 사용자 설정 화면과 운영자 콘솔의 책임을 분리해 기존 팀원 작업과 화면 소유가 겹치지 않도록 했다.
- 실제 API가 없는 상태를 감추지 않고 목업·로컬 상태임을 UI와 작업기록에서 명시했다.
- 최신 `main` 통합 중 공통 라우팅·export 충돌을 확인해 팀원의 로그인 보호 흐름을 보존했다.

### 개선할 점

- 운영자 화면에 필요한 최소 API 응답과 권한 실패 응답을 백엔드 담당자와 먼저 합의해야 정적 상태를 실제 상태로 안전하게 교체할 수 있다.
- 운영자 권한으로 가능한 계정 상태 변경·오류 연결 해제·초대 폐기의 세부 정책과 감사 필드를 확정해야 한다.
- 화면별 목업 수치와 상태는 디자인 검토용이므로, 실제 API 연결 전 회귀 기준이나 운영 현황으로 사용하면 안 된다.

## 8. 인계 사항과 남은 작업

실제 연동을 시작하기 전에 아래 계약이 필요하다.

| 영역 | 필요한 확인 |
|---|---|
| 운영자 인증·권한 | 별도 로그인 성공·실패 응답, allowlist 또는 역할 판정 방식, 세션·CSRF 처리, 권한 없음 처리 |
| 계정·연결·초대 | 목록·상세·필터 응답, 상태 변경·오류 연결 해제·초대 폐기 허용 조건과 감사 필드 |
| 조직·감사 | 읽기 전용 조직 범위, 동기화·오류 상태, 운영 감사와 분석·결정 기록의 조회 계약 |
| 전역 정책 | 공지와 초대 정책의 생성·수정·삭제 권한, 저장·검증·감사 로그 규칙 |

백엔드·API 담당자가 위 계약을 확정하기 전에는 화면의 목업 동작을 실제 기능으로 연결하거나 실제 보안 경계라고 표현하지 않는다.

이 문서는 공유 전 검토 요청 초안이다. 다음을 확인받은 뒤 `검토 요청 초안` 표기를 제거한다.
