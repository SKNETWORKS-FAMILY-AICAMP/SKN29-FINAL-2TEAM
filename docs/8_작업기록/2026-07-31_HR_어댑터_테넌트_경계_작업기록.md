# 작업기록 — HR 어댑터 분리와 테넌트 경계 (2026-07-31)

지금의 설계는 [[HR_어댑터와_테넌트_경계]]에 있다. 여기에는 **판단이 바뀐 지점, 검증 근거, 의도적으로 남긴 것**만 적는다.

## 1. 문제 제기와 첫 진단이 틀렸던 것

PM이 "범용 플랫폼이라고 했는데 한 회사만을 위한 운영자 콘솔이 된 것 같다"고 지적했다.

처음에 나는 **운영자 콘솔의 문제로 진단했다.** 틀렸다. 확인해보니 운영자 콘솔의 역할 정의(플랫폼 벤더용, 전역 조회)는 오히려 멀티테넌트에 맞았다. 진짜 문제는 플랫폼 전체에 "고객사"라는 개념이 없어서 콘솔이 그걸 반영할 수 없다는 것이었다.

두 번째로 틀린 것은 **부트스트랩을 순환 문제로 본 것**이다. "회사를 알려면 person이 필요한데 person을 찾으려면 회사를 알아야 한다"며 이메일 도메인 매칭 같은 선택지를 제시했다. PM이 정정했다 — 사용자가 **자기 회사 HR을 연결**하고, 본인 확인 후 하위 구성원을 불러오는 흐름이면 조직명이 자동으로 정해진다는 것. 이게 맞다. Drive를 연결하면 내 폴더만 보이는 것과 같은 원리이고, 순환 자체가 생기지 않는다.

## 2. 경계를 세우는 방식 — 스키마가 아니라 코드

원래 설계에는 `mock_hr` **스키마** 분리가 있었는데 1차 구현에서 생략됐다. 복구하려면 43곳의 SQL을 전부 고쳐야 해서, 대신 **코드 계층**으로 같은 목적을 달성했다.

결정적인 확인은 이것이었다.

```
HR 원천 테이블(org·level·skill·person·person_skill·person_link·sched·absence)에 대한
애플리케이션 쓰기: 0곳 — 전부 읽기 전용
```

쓰기가 없으므로 어댑터가 **커서를 받지 않아도 된다.** 호출자 트랜잭션에 얹히지 않고 자기 연결을 열어 dict만 돌려주는, 실제 외부 API 클라이언트와 같은 모양이 가능해졌다. 이 사실을 확인하기 전에는 커서를 넘기는 어댑터를 만들 뻔했는데, 그건 이름만 어댑터고 경계가 아니다.

대가는 SQL JOIN 포기다. `list_with_stats`의 3중 조인을 분해해 메모리 결합으로 바꿨다.

## 3. 테넌트를 저장하지 않으려던 판단 — 뒤집혔다

처음에는 `connector_conn`에 테넌트 컬럼을 넣으려다 뺐다. "회사는 `person`에서 유도하면 되니 컬럼을 늘려 팀원 전원에게 ALTER를 시킬 이유가 없다"는 논리였다.

> **이 판단은 §7에서 뒤집혔다.** 테넌트가 회사가 아니라 팀이 되면서, 유도로는 팀원의 소속을 알 수 없게 됐다. `team`·`team_member` 테이블과 `user_account.team_id`·`member_invite.team_id`를 추가했다.

## 4. 검증 근거

단위 테스트로는 격리를 재현할 수 없다(`DATABASES = {}`라 Django가 테스트 DB를 안 띄운다). 아래는 **회사 기준으로 만들었을 당시의** 확인 기록이다(§7에서 팀 기준으로 바뀌었다). 로컬 Postgres에 임시로 2번째 회사를 넣고 확인한 뒤 롤백했다.

```
B사 직원의 회사 : B001        A사 직원의 회사 : A001
A001 스코프: A001~A009 (9개)  B001 스코프: B001, B002
교집합     : set()            ← 격리 성립
DB 확인    : org 9, person 57 (롤백되어 그대로)
```

전환이 회귀를 만들지 않았다는 근거는 **기존 SQL과의 대조**로 잡았다. 테스트가 리포지토리를 모킹해서 전환 자체를 검증하지 못하기 때문이다.

| 대상 | 대조 결과 |
|---|---|
| `hr.list_persons` / `list_orgs` vs 기존 리포지토리 | person 56건·org 9건, 행·필드 모두 일치 |
| `list_with_stats` vs 기존 3중 조인 SQL | 9개 조직 전 행 일치, 불일치 0 |
| `people_db_summary` vs 직접 SQL | 9 / 56 / 5 / 18 일치 |
| ops 엔드포인트 12개 | 전부 HTTP 200, 이름 붙이기 정상 |

## 5. 작업 중 발견해서 같이 고친 것

**미인증 노출.** `GET /api/people/`와 `GET /api/organizations/`가 인증 없이 직원 56명의 실명·실제 이메일을 반환하고 있었다. `team_overrides.sql`로 실제 팀원 정보가 들어간 데이터라 가정이 아니라 실제 노출이었다. 프론트·테스트 어디서도 호출하지 않아 잠가도 깨지는 곳이 없었다.

**퇴사자 이름 소실 위험.** 기존 `LEFT JOIN person`에는 재직 상태 조건이 없어 퇴사자도 이름이 나왔다. 어댑터의 `list_persons`는 `ACTIVE`만 주므로 그대로 쓰면 퇴사자에 연결된 계정이 "이름 없는 계정"이 될 뻔했다. 표시용 `lookup_persons`를 따로 두어 상태를 가리지 않게 했다. 현재 DB에 퇴사자가 1명 있어 실제로 걸렸을 케이스다.

**죽은 코드 제거.** `OrganizationRepository`·`PersonRepository`(57줄)와 `_scope_org_ids`·`_company_org_id`(100줄). 전부 이번 변경으로 호출처가 사라진 것이다.

## 6. 세 번째로 틀렸던 것 — 어댑터의 근거

작업을 마친 뒤 PM이 정정했다. **Workday API는 결제한 기업 고객만 쓸 수 있어 이 프로젝트에서는 애초에 붙일 수 없다.** 목업 DB는 그래서 만든 대역이고, 조직도가 HR 안에 있는 것이 맞으니 Workday 문서를 보고 같은 모양으로 설계한 것이다.

나는 어댑터의 근거를 "나중에 실제 HR API로 갈아끼우기 위해"라고 적었다. **틀렸다.** 갈아끼울 일이 없다.

다만 어댑터 자체가 무의미해지는 것은 아니고, **근거가 바뀐다.**

| 내가 적었던 근거 | 실제 근거 |
|---|---|
| 나중에 Workday로 교체하려고 | 목업이 **남의 시스템(HR)의 대역**이므로 코드도 그렇게 다뤄야 한다 |
| — | 회사 스코프는 "회사마다 자기 HR이 있다"를 목업 한 벌 안에서 **재현**하는 장치 |
| — | 테넌트 규칙을 43곳이 아니라 1곳에서만 지키면 된다 |

설계 의도(외부 HR 대역)와 코드(우리 테이블처럼 43곳에서 직접 조인)가 어긋나 있었고, 어댑터는 그 어긋남을 없앤 것이다. 미래를 위한 것이 아니라 **현재의 정합성**을 위한 것이었다.

## 7. 네 번째로 틀렸던 것 — 테넌트 단위

PM이 다시 정정했다. **"HR에서는 한 회사지만 우리 측에서는 하나의 그룹으로 봐야 한다. 회사 안의 그룹이 우리 플랫폼을 쓰는 것이지 회사 전체가 쓰는 것이 아니다."**

내가 만든 회사(`org_type='COMPANY'`) 기반 스코프는 **과다 노출이었다.** 실측하니 개발팀 팀장이 회사 전 직원 56명을 보고 있었다. 그룹 기준이면 18명이다. 초대 범위(`scope_org_ids`)는 처음부터 A002·A003·A004로 맞았는데, 내가 그 위에 더 넓은 층을 얹으면서 어긋난 것이다.

조직도에서 경계를 유도하려는 시도는 둘 다 실패한다.

| 시도 | 실패 이유 |
|---|---|
| 회사를 테넌트로 | 과다 — 팀장이 다른 부서까지 본다 |
| 조직을 테넌트로 | 불가 — 팀원 한 명만 놓고는 어디까지가 우리 그룹인지 알 수 없다 |

PM의 해법이 이 교착을 풀었다. **팀명을 적게 하면** 그룹이 유도값이 아니라 명시적 실체가 된다. 그래서 `team`·`team_member`를 만들고 온보딩의 팀원 선택 단계에 팀명 입력을 붙였다.

이 결정으로 앞서 "스키마를 늘리지 않겠다"고 한 판단도 뒤집혔다. 유도로는 팀원의 소속을 알 수 없어서 저장이 필수다.

## 8. 의도적으로 남긴 것

**`discover_person_by_email()`의 전역 검색.** 본인 확인 전 단계라 좁힐 근거가 없다.

처음에 "실제 HR을 붙이면 자동으로 닫힌다"고 적었는데 §6의 정정에 따라 그것도 틀렸다. 붙일 일이 없으므로 저절로 닫히지 않는다. 다만 영향은 제한적이다 — 잘못된 사람을 찾아도 사용자가 "본인이 맞습니까"에 아니오를 누르면 진행되지 않고, 확인 이후는 전부 팀 기준이다. 동명이인이 실제로 생기기 전까지 열어 둔다.

**~~`mock_hr` 스키마 분리~~ — 다섯 번째로 틀렸던 것.** "코드 경계를 세웠으니 DB 네임스페이스는 보기 좋게 정리하는 것뿐"이라며 우선순위 낮음으로 미뤘다. PM이 "네임스페이스 나누기로 하지 않았나"라고 물어 되짚어보니 틀렸다.

코드 경계는 **지금 있는 코드**만 지킨다. `public`에 `person`이 `proj`·`doc`과 나란히 있으면 다음 사람이 `JOIN person`을 쓰는 걸 막을 방법이 없다 — 되니까. 애초에 43곳이 직접 조인하게 된 경위가 정확히 그것이었는데, 나는 그 원인을 그대로 두고 결과만 고쳐 놓고 끝났다고 본 것이다.

8개 테이블(`org`·`level`·`skill`·`person`·`person_skill`·`person_link`·`sched`·`absence`)을 `mock_hr`로 옮겼다. `person_snap`·`assign_run` 같은 분석 결과는 FigJam에서 같은 "People DB" 페이지에 있어도 `public`에 남긴다 — 기준은 "누가 만드는 데이터인가"이지 다이어그램의 페이지가 아니다.

## 9. 운영자 콘솔 반영 — "연결 조직"을 없앤 이유

백엔드를 팀 기준으로 바꾼 뒤에도 콘솔에는 `연결 조직 현황`(조직 트리)이 남아 있었다. 나는 "운영자는 팀을 가로질러 보는 자리"라며 그대로 두려 했는데, PM이 정정했다 — **어차피 팀 리스트로 바꿀 것이므로 연결 조직은 필요 없다.**

맞는 지적이다. 조직도는 **고객사 내부 사정**이고, 운영자가 알아야 하는 것은 "우리 플랫폼을 쓰는 팀이 몇이고 그 안이 어떤 상태인가"다. 조직 트리를 남겨두면 운영자가 남의 회사 조직도를 열람하는 화면이 된다.

`OpsOrganizationsPage`(317줄)·`GET /api/ops/organizations/`·`opsOrganizations.ts`를 지우고 `팀 현황`으로 대체했다. 행을 클릭하면 `/ops/accounts?team=…`으로 넘어가 그 팀의 계정만 걸러 보여준다 — 팀에서 계정으로 내려가는 동선을 PM이 제안했고, 두 화면이 같은 목록을 중복해서 갖지 않게 된다.

**고유 번호 제거.** 콘솔 전 화면에서 내부 식별자(`account_id`·`person_id`·`org_id`·`conn_id`·`invite_id`·`snapshot_id` 등)를 화면에서 뺐다. 운영자가 판단에 쓰는 값이 아니고, 남의 회사 직원 번호를 노출할 이유도 없다. 식별자는 API 응답과 라우팅에는 그대로 남아 있다 — 지운 것은 표시뿐이다.

**내가 낸 버그.** 이 제거를 문자열 치환으로 하다가 `OpsAuditPage.tsx`에서 본문과 닫는 `</p>`를 함께 지우고 여는 `<p>`를 남겼다. Vite가 JSX 오류로 막았고 PM이 발견했다.

내가 못 잡은 이유가 더 문제다. 타입 검사를 `tsc --noEmit | head -20; echo $?`로 돌렸는데 **`$?`가 `tsc`가 아니라 `head`의 종료 코드**여서 언제나 0이었다. 이 세션에서 여러 번 "tsc 통과"라고 보고한 것 중 파이프를 거친 것은 근거가 없었다. 파이프 없이 다시 돌려 종료코드 0을 확인했고, 앞으로 파이프를 태우지 않는다.
