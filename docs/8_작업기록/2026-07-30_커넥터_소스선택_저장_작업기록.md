# 작업기록 — Drive·Jira 커넥터로 읽을 폴더·문서 선택·저장 (2026-07-30)

> 커밋 `386f0c3` (`june` → `main`). 설계 문서에는 **지금의 설계**만 남는다. 이 문서는 **왜 그렇게 됐는지와 무엇으로 확인했는지**를 남긴다.
> 범위: 커넥터 연결 이후 "무엇을 읽을지" 고르고 저장하는 구간까지. 본문 파싱은 WBS 2.4.1~2.4.3(성주연·최원빈)로 별도 진행 중이라 다루지 않았다.

## 1. 무엇이 없었고 무엇을 채웠나

작업 전 상태: `connector_conn`에 `PEOPLE_DB`만 있었고, Drive·Jira 카드는 데모 배지를 달고 `?mode=demo` 목업으로 연결돼 있었다. 인가 흐름은 팀원이 만들어 둔 상태였다.

| 구간 | 작업 전 | 작업 후 |
|---|---|---|
| 토큰 갱신 | 없음 | 호출 직전 lazy 갱신. 실패 시 `EXPIRED` 전이 |
| Drive 폴더 조회 | 없음 | 한 단계씩 트리 탐색 |
| Drive 파일 조회 | 없음 | `max_depth`만큼 하위 폴더 탐색 |
| Jira 프로젝트 조회 | 없음 | 연결된 사이트의 프로젝트 목록 |
| 선택 결과 저장 | 없음 | `proj(DRAFT)` + `proj_source` + `doc` |
| 폴더 역할 지정 | 데모 화면 | `proj_source.default_doc_role` → `doc.doc_role` 상속 |

## 2. 판단이 바뀐 지점 (가장 중요)

### 2.1 "프로젝트가 먼저다"는 틀렸다

[[Jira_Drive_커넥터_연결_설계]] §4가 "`proj_source.proj_id`가 NOT NULL이므로 **프로젝트 생성 흐름이 선행되어야 한다**"고 적고 있었고, 그대로 따라 "폴더·Jira 선택 화면을 실연결하려면 프로젝트 생성 UI가 먼저 필요하다"고 보고했다.

PM 지적: **"Drive의 기획서를 토대로 프로젝트를 생성하고 업무를 추출하는 게 우리 프로젝트의 목적인데 어떻게 프로젝트가 먼저 앞으로 와."**

맞는 지적이었다. 테이블 의존 순서로는 맞지만 그것을 **화면 순서**로 옮기면 제품 목적과 거꾸로 간다. 사람이 프로젝트를 먼저 정의해야 한다면 자동화할 것이 없다.

해결: **폴더를 고르는 행위가 프로젝트를 만드는 행위다.** `proj.status`에 이미 `DRAFT`가 있었고 `ProjectCreateSerializer`의 기본값이기도 했다 — 원래 설계도 "내용이 채워지기 전의 프로젝트"를 상정하고 있었다. 별도 생성 화면을 두지 않고, 이름은 임시로 폴더명을 쓰고 기획서를 파싱한 뒤 갱신한다.

**교훈: 설계 문서의 서술도 제품 목적과 충돌하면 문서가 틀린 것이다.** 문서를 근거로 삼기 전에 목적과 맞는지 봐야 한다.

### 2.2 Drive 폴더 전체 조회 → 트리 탐색

처음엔 폴더 전체를 한 번에 받았다. 실계정에서 **473개**가 나왔고 `pageSize` 상한 **200개에서 잘렸다.** PPT 템플릿 폴더 대량에 실제 작업 폴더가 묻혔다.

`parent`의 직속 자식만 받으면 최상위가 **3개**(`Colab Notebooks` / `PPT 템플릿` / `SKN29`)다. 공유 드라이브는 `drives.list`가 빈 배열이라 지원을 넣지 않았다.

### 2.3 폴더 역할을 담을 컬럼: 두 개가 아니라 하나

"하위 폴더 포함" 토글과 "탐색 깊이" 선택이 화면에 따로 있어 컬럼 두 개(`include_subfolders BOOLEAN` + `max_depth INT`)를 만들 뻔했다.

그러면 **"off인데 깊이가 3이면 어느 쪽이 이기나"가 아무도 강제하지 않는 규칙으로 남는다.** 토글을 끄는 것이 곧 `max_depth = 1`이므로 컬럼 하나로 접었다. 화면에서만 두 컨트롤로 풀어 쓴다(`toMaxDepth`/`fromMaxDepth`).

### 2.4 `doc`을 지우고 다시 만들지 않는다

처음 구현은 저장할 때 `DELETE` 후 `INSERT`였다. 파싱이 채울 `content_hash`·`cur_revision`을 **역할만 바꿨다고 날리게 된다.** `src_file_id`로 갱신하고, 목록에서 빠진 문서는 `deleted = true`로 표시한다(스키마가 이를 위해 둔 컬럼이다).

같은 문제를 `proj_source`에서도 발견했다. `PUT /sources/`가 DELETE+INSERT라서 **폴더를 다시 저장하면 `default_doc_role`이 날아갔다.** 계속 선택된 폴더의 값은 넘겨받도록 고쳤다.

### 2.5 저장 API가 파일 목록을 받지 않는 이유

`PUT /documents/`가 클라이언트에서 파일 id·이름·mime을 받는 설계가 자연스러워 보였다(화면이 이미 갖고 있으니까). 그러면 **실재하지 않는 문서가 `doc`에 들어갈 수 있다.** 서버가 저장된 `proj_source`의 폴더를 Drive에서 다시 읽는다. 탐색 깊이도 요청에서 받지 않고 `proj_source.max_depth`를 쓴다 — 화면이 보여준 것과 저장되는 것이 어긋나면 안 된다.

## 3. 발견해서 고친 보안 문제

| 문제 | 영향 |
|---|---|
| `POST /api/projects/`가 무인증이고 `owner_account_id`를 요청 본문에서 받았다 | 누구나 아무 계정 소유의 프로젝트를 만들 수 있었다 |
| 배정 실행 엔드포인트 2건 무인증 | 누구나 아무 프로젝트에 배정 실행을 만들 수 있었다 |
| Drive 폴더 id가 검색식에 그대로 들어감 | 따옴표·백슬래시 주입. 400으로 막음 |
| **`.env.example`에 실제 OAuth 시크릿** | 추적되는 파일이라 커밋되면 공개 저장소에 Google·Atlassian 시크릿 노출. 커밋 직전에 발견해 되돌림 |

마지막 항목은 값을 넣을 때 `.env`가 아니라 `.env.example`을 편집해서 생긴 것으로 보인다. **`.env.example`은 항상 빈 플레이스홀더로 둬야 한다.**

공유 드라이브           없음   drives.list → []

깊이 1                 16개   folder_path ['']
깊이 2                 21개   folder_path ['', '산출물']
제한 없음               21개   (더 깊은 폴더가 없어 동일)

Jira 프로젝트            2개   KAN SKN29_Final_2Team / SAM1 (Example) Billing System Dev
                              lead_name '임준' (expand=description,lead 필요)

**토큰 갱신은 우연히 확인됐다.** 저장된 토큰이 이미 만료된 상태였는데 두 API 호출이 200을 돌려줬다 — 갱신 경로가 동작했다는 뜻이다. 이후 단위 테스트로 고정했다.

## 5. 팀원이 해야 할 것

**스키마 변경.** 안 돌리면 폴더 선택 저장에서 에러가 난다. 세 줄 다 멱등이다.

```sql
ALTER TABLE connector_conn ALTER COLUMN encrypted_credential_ref TYPE TEXT;
ALTER TABLE proj_source ADD COLUMN IF NOT EXISTS default_doc_role VARCHAR(30);
ALTER TABLE proj_source ADD COLUMN IF NOT EXISTS max_depth INT;
```

정본은 [[DB_시작_가이드]] §4.3. 앞으로 스키마를 바꾸면 거기에 한 줄 추가한다.

**Drive·Jira를 직접 쓰려면** `.env`(`.env.example` 아님)에 각자 콘솔의 `client_id`/`client_secret`이 필요하다. `.env`를 바꾼 뒤에는 재시작이 아니라 **재생성**해야 반영된다.

```bash
docker compose -f infra/docker/docker-compose.yml up -d --force-recreate web
```

**Google은 테스트 모드라 `refresh_token`이 7일 후 만료된다.** 연결해두고 일주일 뒤 시연하면 끊겨 있다. 시연 직전에 재연결하면 되지만 모르면 당황한다.

**`SECRET_KEY`를 바꾸면 저장된 모든 자격증명을 복호화할 수 없다.** 암호화 키가 `SECRET_KEY`에서 파생되기 때문이다. 전원 재연결이 필요하다.

## 6. 파싱 담당자에게 넘기는 것

경계는 [[Jira_Drive_커넥터_연결_설계]] §6에 정리했다.

```
넘겨받는 것    doc.src_file_id      Drive 파일 id (내려받을 키)
              doc.mime_type        어떤 파서를 태울지
              doc.doc_role         파싱 규칙 분기·Vector 검색 필터
              doc.file_name        Citation 표기
              doc.deleted = false  아직 읽어야 하는 문서

채울 것        doc.cur_revision / content_hash / acl_principals
              doc_sync (chg_type, parse_status, parser_ver, embed_ver)
              doc_block → chunk → know_item → task
```

`doc` 행은 지우지 않으므로 채워 둔 값이 폴더·역할 재저장에도 남는다. 반대로 **`deleted = true`인 행은 걸러야 한다.**

`doc_role` 코드는 `PLAN` / `MEETING_NOTE` / `DAILY_REPORT` / `OTHER` 네 개다. [[비정형_문서_DB_설계]]가 예시로 적었던 `RFP`는 화면에 선택지가 없어 넣지 않았다.

## 7. 남은 것

- **폴더별 탐색 깊이** — `max_depth`는 폴더 단위 컬럼인데 화면 컨트롤이 하나라 모든 폴더에 같은 값이 들어간다. 폴더마다 다르게 하려면 화면만 바꾸면 된다. 필요한지는 미결
- **`proj.name` 자동 갱신** — 지금은 최상위 선택 폴더명이다. 기획서를 파싱한 뒤 갱신하는 시점과 `DRAFT → ACTIVE` 전이를 정해야 한다
- **프로젝트 조회가 소유자 기준** — `GET /api/projects/`가 `owner_account_id`로만 필터하고 `proj_member`를 보지 않는다. 팀장 온보딩에는 충분하지만 **팀원 대시보드를 붙일 때 `proj_member`를 함께 봐야 한다**
- **팀원 Jira 셀프 연동** — 팀원 Jira 이메일이 HR 이메일과 다를 수 있는 문제가 미해결이라 미룬 상태
- **랜딩 페이지 Jira 버튼** — `disabled` + "실제 Jira 연동 전 데모 버튼입니다". 랜딩은 로그인 전이고 Jira 연결은 로그인 + 팀장 권한이 필요하니 이 버튼이 연결을 수행할 수는 없다. 회원가입으로 보내는 편이 맞아 보이는데 화면 문구라 손대지 않았다
- **`GET /api/connectors/people-db/summary/`** — 호출처가 없다. 유지·삭제 미결
- **설계 문서와 실제 스키마 차이** — `connector_conn`·`proj_source`에 문서에만 있는 컬럼이 여럿이다. [[플랫폼_운영_권한_DB_설계]]에 실제 컬럼과 없어도 되는 이유를 적어 뒀지만, 다른 테이블도 같은 차이가 있을 수 있다
