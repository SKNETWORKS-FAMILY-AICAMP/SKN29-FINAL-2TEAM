# 업무량을 계산하는 방식 조사

> 조사일: 2026-07-31
> 전제: 현재 **HR DB, JIRA 데이터만**을 가지고 직원의 현재 업무량을 계산해야 한다.

### 용어 정의

| 용어 | 뜻 |
|---|---|
| **업무량** | 지금 맡고 있는 업무의 크기. 시간(`remaining`)으로 잰다 |
| **가용용량** | 실제로 일할 수 있는 양. 근무시간에서 휴가·회의를 뺀 값 |
| **부하율** | `업무량 / 가용용량`. 1을 넘으면 과부하 |

## Q2. 실제 서비스·논문에서는 업무량을 어떻게 계산하는가?

### Q2-1. 우리 데이터 유무와 상관없이 — 방식별 수식 전체 목록

**개인 업무량 계산과 직접 관련 없는 항목은 제외했다** — Kanban Little's Law·Resource Leveling(개인이 아니라 전체 흐름을 다루는 배분·재배치 기법), COCOMO II·LEMFEA(개인이 아니라 프로젝트 전체 공수 추정 모델), Wang & Chiou·신뢰도 기반 라우팅·Span of Control·Brooks' Law(업무량이 아니라 마감 심리·데이터 신뢰도·관리 조직 구조를 다루는 배경 지식)는 전부 뺐다.

아래는 두 종류가 섞여 있다: **수식이 실제로 공개된 것**과 **방법론만 있고 닫힌 수식은 없는 것**. 항목마다 "수식 없음"을 명시했으니 표로 다시 안 나누고 그대로 둔다.

#### 한눈에 보기

| 분류 | 이름 | 필요 값 | 계산 방법 | 비고 |
|---|---|---|---|---|
| 시간추정치 | Jira | Original Estimate, Time Spent | `Remaining = Original Estimate − Time Spent`(최초), 이후 이전 값에서 추가 소요시간만 차감 | |
| 시간추정치 | Tempo | Working Hours, Holiday, Planned Time | `Capacity = Working Hours − Holiday − Planned Time` | |
| 시간추정치 | Monday.com | Effort, Capacity | `Σ Effort > Capacity`면 초과 표시 | Effort 컬럼 없으면 작업 1건=1로 자동 계산 |
| 시간추정치 | Wrike | 그날 배정 시간, 일일 Capacity | `FTE = 배정시간 / 일일Capacity` | |
| 시간추정치 | Smartsheet | Allocation%(사람이 직접 입력) | `Σ Allocation%(같은 사람·날) > 100%`면 초과 | 자동 계산이 아니라 수동 입력값 |
| 시간추정치 | Harvest | Actual Hours, Capacity Hours | `Utilization = Actual Hours / Capacity Hours` | Remaining Estimate 개념 없음 |
| 시간추정치 | Asana | Task Effort, Capacity | `Σ Effort > Capacity` | 나눗셈 형태 명시 공식은 비공개 |
| 시간추정치 | ClickUp | 총 시간추정치, 근무일수 | `하루 배분시간 = 총추정치 / 근무일수` | 분배 공식이지 산출 공식 아님 |
| 시간추정치 | Linear | 직전 3 Cycle의 Velocity | `Cycle Capacity = avg(직전 3 Cycle)` | 개인 아닌 팀 단위 |
| 시간추정치 | BigPicture / Motion | — | 공개된 수식 없음 | |
| 시간추정치 | Jira Work Ratio(공식 기능) | Time Spent, Original Estimate | `Work Ratio = Time Spent / Original Estimate × 100` | Atlassian 공식 API로 확인됨. Original Estimate가 필요해서 R2M과 같은 문제를 가짐 — Q3-1에서 재확인 |
| 가용성 | GitLab | 개인별 가용 인원-일, 전체 인원-일 | `가용비율 = Σ가용 / Σ전체` | |
| 가용성 | MS Project | Resource Capacity, Assignment, Calendar Exceptions | `Availability ≈ Capacity − (Assignment + Exceptions)` | 공식 문서에 못박힌 수식은 아님 |
| 가용성 | Actonic Timesheet Builder | Defined Capacity, Logged Hours | `Utilization% = Logged/Defined × 100`, `Buffer = Defined × 0.8`(20% 제외 권장) | 100% 꽉 채워 계획하지 말라는 실무 권장치 |
| 보정계수 | R2M | 계획 시간, 실제 소요 시간 | `생산성계수 = 평균(계획시간/실제시간)` | 개인 단위로도 성립하는 방법론(데이터 유무는 Q3에서 확인) |
| 보정계수 | 다기준 가중합 | 기준별 점수, 가중치 | `최종점수 = Σ(가중치×점수)` | 신호가 아니라 방법론 — 가중치는 우리가 정해야 함 |
| 보정계수 | Focus Factor | 근무일수, 인원수 | `순가용시간 = 근무일수×인원수×FF(0.6~0.8)` | 실시간 신호가 아니라 정책 상수 |
| 보정계수 | Gloria Mark | 전환 횟수 | 전환 1회당 23분 15초 손실(실측값) | Weinberg 배율표의 실증 배경 |
| 보정계수 | Weinberg 손실표 | 동시 진행 프로젝트 수 | `조정값 = remaining × (1+손실률)`, 1개 0%~5개 75% | 경험칙(엄밀한 실험 아님) |
| 보정계수 | Kanban Work Item Age | 시작일(`start_at`) | `Age = 오늘 − start_at + 1` | 정체 신호 |

#### 시간추정치 기반 (SaaS)

Monday.com·Wrike·Smartsheet 세 개는 엄밀히는 "업무량 계산 공식"이 아니라 **표시 방식(Display Logic)** 이다 — 이미 있는 추정치와 용량을 비교해서 색으로 보여주는 로직이지, 새로운 값을 계산해내는 공식은 아니다.

**Jira**
```
Remaining Estimate = Original Estimate − Time Spent            (최초 1회)
Remaining Estimate(갱신) = Remaining Estimate(이전) − 추가 Time Spent
```

Jira는 **Work Ratio**라는 이름의 공식 필드도 제공한다. Atlassian 공식 API(`WorkRatio.getWorkRatio(originalEstimate, timespent)`)로 직접 확인한 정의는 다음과 같다 — 처음에 우리가 "`spent/(spent+remaining)`과 같은 식"이라고 적었던 건 **정정이 필요한 오류**였다.
```
Work Ratio = Time Spent / Original Estimate × 100     (정정 전: Spent/(Spent+Remaining)로 잘못 기재)
```
분모가 Original Estimate라서, 이 공식도 R2M과 똑같은 문제를 가진다 — 우리 `exist_task`에는 Original Estimate에 해당하는 컬럼이 없다(Q3-1에서 재확인). 우리가 실제로 쓸 수 있는 건 이것과 이름만 비슷한 **별도의 자체 지표**(`진행률 = spent/(spent+remaining)`)이고, 이걸 "Jira가 쓰는 공식과 같다"고 주장할 근거는 없다.

**Tempo**
```
Capacity = Working Hours − Holiday − Planned Time
FTE = (휴일 제외 가용시간) / (기본 Workload Scheme의 주간 정규 시간)
```

**Monday.com**
```
초과 여부 = Σ Effort > Capacity
Capacity(하루) = Capacity(주간) / 5
Capacity(한달) = Capacity(주간) × 4
```
(Effort 컬럼을 안 만들면 작업 1건 = 1 단위로 자동 계산)

**Wrike**
```
FTE = 그 날 배정된 시간 / 기본 일일 Capacity     (예: 4h / 8h = 0.5)
초과 여부 = 배정된 Effort > Custom Capacity
```

**Smartsheet**
```
Allocation% (사람이 직접 입력, 기본값 100%)
초과 여부 = Σ Allocation% (같은 사람, 같은 날) > 100%
```
자동 계산 공식이 아니라 사람이 넣는 값이라는 점이 다른 도구와 다르다.

**Harvest**
```
Utilization = Actual Hours(기록된 실제 시간) / Capacity Hours
Budget Remaining = Budget − Actual Hours
```
Remaining Estimate 개념이 없고 실제 기록 시간이 기준이다.

**Asana**
```
Load 초과 여부 = Σ Task Effort(시간/포인트/커스텀필드) > Capacity
```
공식 문서에 나눗셈 형태의 명시적 공식은 공개돼 있지 않다 — "초과하면 빨간 선" 정도로만 서술돼 있다.

**ClickUp**
```
하루 배분시간 = Task 총 시간추정치 / (마감일 − 시작일의 근무일 수)
```
남은 크기 자체를 계산하는 공식이 아니라 이미 있는 추정치를 근무일에 나눠 보여주는 분배 공식이다.

**Linear**
```
Cycle Capacity = avg(직전 3개 Cycle의 Velocity)     (이슈 수 또는 포인트 기준)
```
과거 실적이 없으면 팀원 수로 대략 추정한다. 개인이 아니라 팀 단위 지표다.

**BigPicture / Motion**: 수식 없음. 각각 "Original/Remaining Estimate를 겹쳐 보여줌", "AI가 다변수를 종합해 배치"라고만 돼 있고 닫힌 형태 수식은 공개돼 있지 않다.

#### 가용성 기반

**GitLab** (수식이 명시된 건 아니고 예시로 역산)
```
가용 비율 = Σ(개인별 가용 인원-일) / Σ(전체 인원-일)
```
예시: 4명 중 1명이 이번 달의 절반을 휴가로 쓰면 → (3×1 + 1×0.5) / 4 = 87.5%

**Microsoft Project**: Microsoft가 이 식을 문서에 "공식"이라고 못박아 공개한 건 아니다 — 리소스 캘린더(Resource Calendar)와 배정량(Assignment)을 비교해서 초과 여부(Overallocated)를 판단한다는 동작 방식이 알려져 있고, 이를 수식으로 풀어 쓰면 다음과 같다.
```
Resource Availability ≈ Resource Capacity − (Summary Resource Assignment + Calendar Exceptions)
Overallocated = Yes,  if 배정된 Work > Work Capacity
```

**Actonic Timesheet Builder (Jira 용량관리 앱)**
```
Utilization% = Logged Hours / Defined Capacity × 100
Buffer = Defined Capacity × 0.8     (20% 여유를 남기고 계획)
```
2026년 가이드에서 "정의된 용량을 100% 꽉 채워 계획하지 말고 회의·기술부채·돌발업무를 위해 15~20% 버퍼를 남기라"고 권장한다 — Utilization 자체는 Harvest와 같은 구조지만, 이 **버퍼 권장치는 새로 확인한 내용**이다.

#### 보조 지표 및 보정 계수

아래는 "부하율 = 업무량/용량" 자체를 계산하는 공식이 아니라, 그 계산에 넣거나 곁들이는 **보정값·방법론·정책 상수**다. 성격이 셋으로 갈린다: **실측 배율표**(Weinberg), **정책으로 정하는 상수**(Focus Factor), **우리가 기준·가중치를 직접 정해야 하는 방법론**(다기준 가중합, R2M).

**R2M(실적 기반 생산성 역산)**: 닫힌 형태 수식 없음 — 과거 데이터에서 회귀분석으로 동적으로 학습하는 방식이라 프로젝트마다 계수가 달라진다. **개인 단위로도 성립하는 방법론**이다 — 다만 필요한 필드가 우리한테 있는지는 Q3에서 따로 확인한다. 굳이 근사식으로 쓰면:
```
개인 생산성 계수 = 그 사람의 과거 완료 업무들의 평균(계획 시간 / 실제 소요 시간)
```

**다기준 가중합 (스케줄링 연구)**
```
최종 점수 = Σ (가중치i × 기준 점수i)
```
마감기한의 가중치가 가장 높다는 게 관측된 결과다. 신호가 아니라 방법론이다 — 기준과 가중치를 우리가 정해야 값이 나온다.

**Focus Factor (애자일 스프린트 용량)**
```
순가용시간 = 총 근무일수 × 인원 수 × Focus Factor
Focus Factor 범위 = 0.6 ~ 0.8 (보통 0.7~0.8)
```
실시간으로 관측되는 신호가 아니라 **정책적으로 정해서 곱하는 상수**다.

**Gloria Mark (컨텍스트 스위칭)**: 수식이 아니라 실측값 — 작업 전환 1회당 원래 업무로 완전히 복귀하기까지 평균 **23분 15초**. Weinberg 손실표를 "왜 쓰는지"에 대한 실증 배경이다.

> **2026-08-03 정정 — [실측/공식]이 아니라 [미검증]이다.** 인용한 CHI 2008 논문(*The Cost of Interrupted Work*) 원문에 이 수치가 없다. 논문의 실제 결과는 오히려 반대에 가깝다 — 중단된 작업을 **더 빨리** 끝냈고(약 20분 vs baseline 22.77분) 대신 스트레스·시간압박이 유의하게 늘었다. 23분 15초는 언론 인터뷰에서 유래한 것으로 보이며 1차 인쇄 출처가 확인되지 않는다. 수식에 직접 안 들어가 계산 영향은 없지만, **이 값이 맡은 역할이 Weinberg 배율의 실증 배경이라 그 배경이 사라진다.** 확장형을 기본형에서 분리해 둔 판단이 결과적으로 옳았다.

**Weinberg 컨텍스트 스위칭 손실표 (Quality Software Management)**: 동시 진행 프로젝트 수에 따른 손실률을 구체적 수치로 제시한다.
```
동시 진행 1개 → 손실 0%   (가용시간 100% 그대로 활용)
동시 진행 2개 → 손실 20%  (프로젝트당 40%씩만 배분)
동시 진행 3개 → 손실 40%  (프로젝트당 20%씩만 배분)
동시 진행 4개 → 손실 60%  (프로젝트당 10%씩만 배분)
동시 진행 5개 → 손실 75%  (프로젝트당 5%씩만 배분)
```
`remaining`에 곱하는 형태로 바로 쓸 수 있는 몇 안 되는 명시적 배율표다: `조정된 remaining = remaining × (1 + 손실률)`. 다만 저자 스스로 "엄밀한 실험이 아니라 엔지니어링 경험칙"이라고 밝혔고, 이후 연구는 이 수치가 정확하진 않다고 지적한다 — 방향(동시 프로젝트가 늘수록 손실 급증)은 맞지만 정확한 %는 참고치로 써야 한다.

**Kanban Work Item Age (정체 신호)**
```
Work Item Age = (오늘 날짜 − start_at) + 1
```
`remaining`이나 `spent`와 무관하게, **얼마나 오래 진행중 상태에 머물러 있는지** 자체를 신호로 쓴다. 설정한 임계값(예: 10일)을 넘으면 정체(stale)로 표시 — 병목이나 숨은 어려움의 대리 신호로 쓰인다.

### Q2-2. HR DB·Jira류 데이터만으로 계산 가능한가? (일반적 판단)

Q2-1의 모든 방식을 "HR 시스템 + 이슈 트래커 데이터만 있다면" 기준으로 걸렀다 — 아직 우리 스키마의 구체적 컬럼 유무는 안 보고, 그 방식이 요구하는 입력이 **개념적으로** HR·이슈 트래커에서 나올 수 있는 값인지만 본다.

**"불가능"에는 서로 다른 두 종류가 섞여 있어서 유형을 나눴다.** 하나는 **데이터 제약**(입력값을 HR·이슈 트래커가 원래 안 가짐 — 나중에 다른 시스템을 붙이면 풀릴 수 있음), 다른 하나는 **방법 자체의 한계**(애초에 공개된 계산식이 없거나, 분석 단위가 개인이 아님 — 데이터를 더 모아도 안 풀림). 이 둘을 같은 "불가능"으로 뭉치면 "필요한 데이터를 더 모으면 되는 것"과 "구조적으로 안 되는 것"이 구분이 안 된다.

| 방식 | 가능 여부 | 유형 | 이유 |
|---|---|---|---|
| Jira Remaining Estimate | 가능 | — | 이슈 트래커가 직접 관리하는 값 |
| Tempo Capacity/FTE | 부분 가능 | 데이터 제약 | 근무시간·휴가는 HR 데이터, "Planned Time"(회의 등)은 캘린더 데이터라 별도 시스템 필요 |
| Monday.com (Effort > Capacity) | 가능 | — | Effort=이슈 잔여시간, Capacity=HR 근무시간 |
| Wrike (일일 FTE) | 부분 가능 | 데이터 제약 | 일 단위 배정시간 분해는 이슈 트래커만으로는 거칠다 |
| Smartsheet (Allocation%) | 불가능 | 데이터 제약 | 사람이 직접 입력하는 값이라 원본 데이터 자체가 없음 (다른 시스템을 붙여도 못 풀림 — 애초에 "입력하는 사람"이 필요) |
| Harvest (Utilization) | 가능 | — | 실적 시간=이슈 트래커, Capacity=HR 근무시간 |
| Asana (Effort > Capacity) | 가능 | — | Monday와 동일 구조 |
| ClickUp (하루 배분시간) | 가능 | — | 잔여시간/근무일수 |
| Linear (Cycle Capacity) | 불가능 | 데이터 제약 | 스프린트/사이클이라는 별도 개념 자체가 필요 |
| BigPicture / Motion | 판단 불가 | **방법 자체 한계** | 애초에 공개된 수식이 없어 "가능/불가능"을 매길 대상 자체가 없음 |
| Jira Work Ratio(공식) | 조건부 | 데이터 제약 | Original Estimate 필드 개념이 이슈 트래커에 있어야 성립 — R2M과 같은 문제. 있는지는 Q3에서 확인 |
| GitLab 가용비율 | 가능 | — | 휴가·근무시간만으로 계산 |
| MS Project Resource Availability | 부분 가능 | 데이터 제약 | Calendar Exceptions 항목은 캘린더 데이터가 별도로 필요 |

| R2M | 조건부 | 데이터 제약 | "계획 시간(Original Estimate)"이라는 필드 개념이 이슈 트래커에 있어야 성립 — 있는지는 Q3에서 우리 스키마로 확인 |
| 다기준 가중합 | 방법론만 가능 | 데이터 제약(부분) | 기준값(우선순위·마감일)은 데이터에서 나오지만, 가중치 자체는 HR·Jira 데이터와 무관하게 우리가 직접 정의해야 함 |

| Gloria Mark (23분) | 신호로 가능 | — | 동시 작업 수는 이슈 트래커에서 셀 수 있고, 상수는 고정값으로 적용 |
| Weinberg 손실표 | 가능 | — | 동시진행 개수 = 이슈 상태 카운트 |
| Kanban Work Item Age | 가능 | — | 이슈의 시작일만 있으면 계산 |

**"판단 불가"로 표기한 BigPicture/Motion은 "불가능"과 다르다** — 데이터를 아무리 갖춰도 적용할 수식 자체가 공개돼 있지 않아서, 애초에 "가능/불가능"을 매길 질문 자체가 성립하지 않는다.

## Q3. 우리 프로젝트 데이터로 Q2에서 찾은 수식 중 만들 수 있는 것은?

Q2-2는 "HR 시스템 + 이슈 트래커라면 개념적으로 가능한가"를 봤다. Q3는 그걸 Q1에 실제로 적힌 컬럼명(`exist_task.*`, `mock_hr.person.*`, `mock_hr.level.*`, `mock_hr.sched.*`, `mock_hr.absence.*`)에 하나씩 직접 대입해서 다시 확인한다. 새 수식을 만들지 않고, Q2에서 찾은 것만 쓴다.

### Q3-1. HR DB·Jira 데이터로 적용 가능한 수식

#### 핵심 수식 — 바로 계산되는 값

| Q2 방식 | 우리 필드 매핑 | 판정 |
|---|---|---|
| Jira Remaining | `exist_task.remaining` | **가능 — 계산할 필요 없음.** Original Estimate가 없어도 Jira가 이미 계산해서 넘겨준 값을 그대로 쓴다 |
| Jira Work Ratio(공식) | Original Estimate 필드 | **불가 — R2M과 같은 이유.** `exist_task` 9개 컬럼 중 Original Estimate에 해당하는 게 없음 |
| 진행률(우리 자체 지표, Jira 공식과는 다른 식) | `exist_task.spent / (exist_task.spent + exist_task.remaining) × 100` | **가능** — 이름만 비슷할 뿐 Jira의 공식 Work Ratio와 다른 식이라, "Jira가 쓰는 공식과 같다"는 근거로 쓰면 안 됨 |

| GitLab 가용비율 | `Σ(absence로 안 빠진 인원-일) / Σ(전체 인원-일)` | **가능** |

| Wrike 일일 FTE | 일 단위 배정시간 분해 | **불가 — 근사만 가능.** 우리 `remaining`은 총량 하나뿐이라 날짜별로 쪼개려면 ClickUp 방식(균등분배)을 빌려써야 함 |

#### 보조 신호 — 계산은 되지만 정확한 계수가 없는 것

Q2에서 "경험칙"·"실측값"·"정책 상수"로 분류했던 것들이다. **숫자를 못 박을 수 없다고 신호 자체를 버리면 안 된다** — 이 신호들이 가리키는 방향(동시 진행이 많을수록, 오래 정체될수록 부담이 크다)은 맞고, 정확한 배율만 우리가 직접 정해야 한다.

| Q2 방식 | 우리 필드 매핑 | 계산 가능 여부 | 정확한 값이 없는 부분 |
|---|---|---|---|
| Weinberg 손실표 | `count(exist_task.status='진행중', assignee_person_id=대상자)` | **동시진행 개수는 정확히 셀 수 있다** | 손실률(0%/20%/40%/60%/75%)은 경험칙 — 우리 조직에 그대로 맞다는 보장 없음 |
| Gloria Mark 23분 15초 | 위와 동일한 동시진행 개수 | 개수는 가능 | "23분"이라는 값 자체가 우리 조직·업무 성격에 맞는지 검증 안 됨 — Weinberg 배율의 방향성을 뒷받침하는 배경 정도로만 쓸 것 |
| Kanban Work Item Age | `(오늘 − exist_task.start_at) + 1` | **가능** (단, `start_at` NULL이면 계산 불가 — Q3-3 참고) | "며칠 넘으면 정체로 볼지"의 임계값(예:10일)은 우리가 정해야 함, 연구에서 나온 숫자 없음 |
| Focus Factor | `근무일수 × 인원수 × FF` | 근무일수·인원수는 가능 | FF(0.6~0.8) 자체는 애자일 커뮤니티 경험칙 범위지 우리 조직 실측치 아님 |

**이 넷의 공통점**: 전부 "우리 데이터로 입력값은 만들 수 있는데, 그 입력값에 곱하거나 비교할 상수가 문헌마다 다르다"는 상태다. Q4에서 "이 수식들이 전부 필요한가"를 따질 때, 이 넷은 "정확한 계수가 없다고 통째로 뺄 것인가, 아니면 [정책값]이라고 명시하고 보수적으로 넣을 것인가"를 결정해야 하는 항목들이다.

### Q3-2. 필수(NOT NULL) 데이터만으로 적용 가능한 수식

Q1에서 NOT NULL인 컬럼만 추리면 다음과 같다.

```
exist_task.exist_task_id, exist_task.jira_issue_id   (둘 다 식별자, 계산에 안 씀)
mock_hr.person.emp_status                             (재직 상태, 계산에 안 씀)
mock_hr.level.rank_ord                                (Q2에서 이미 제외된 직급 계수)
mock_hr.sched.eff_from                                (날짜 경계값, 그 자체로는 계산에 안 씀)
mock_hr.absence.absence_type / start_at / end_at / status   (넷 다 NOT NULL)
```

**결론: NOT NULL 필드만으로 완결되는 Q3-1 수식은 하나도 없다.** `remaining`·`spent`·`status`·`priority`·`start_at`·`due_at`(exist_task)와 `wk_hours`·`def_wk_hours`·`fte`(sched)가 전부 NULL 허용인데, Q3-1의 모든 수식이 이 중 최소 하나를 요구한다.

**유일하게 NOT NULL만으로 완결되는 조각은 `absence` 기반 차감뿐이다.** `absence_type`/`start_at`/`end_at`/`status` 넷 다 NOT NULL이라, "승인된 휴가 기간을 가용시간에서 뺀다"는 계산 하나는 대체값 없이 항상 정확하게 된다. 그 외 유효가용용량의 기준시간(`wk_hours`)도, 업무량(`remaining`)도 전부 NULL을 만날 수 있다 — 즉 **Q3-3의 대체 정책이 선택이 아니라 필수**라는 뜻이다.

### Q3-3. NULL 허용 값의 대체 정책

| 컬럼 | NULL일 때 | 대체 정책 | 근거 |
|---|---|---|---|
| `exist_task.remaining` | 업무량 계산 불가 | 그 담당자의 다른 업무 `remaining` 중앙값으로 대체. 그 담당자 업무 전부가 NULL이면 "진행중 건수 × 기본 태스크 크기(정책값)"로 대체 | Monday.com·Asana·ClickUp·Linear가 공통으로 쓰는 대비책(Effort 없으면 1건=1단위) |
| `exist_task.spent` | 진행률·Work Ratio 계산 불가 | 0으로 간주(아직 손 안 댄 업무로 취급) | — |
| `exist_task.status` | 동시진행 카운트(Weinberg 등)에서 제외 | 카운트 대상에서 빼거나 "미분류"로 별도 집계 | — |
| `exist_task.priority` | 다기준 가중합 계산 불가 | 기본 우선순위(예: Medium)로 대체 — 어떤 값을 기본으로 할지는 정책 결정 | — |
| `exist_task.start_at` | ClickUp식 일 배분, Work Item Age 계산 불가 | 계산에서 제외하거나, 계산 기준일 자체를 `start_at`으로 대체(정체 신호는 과소평가 방향으로 안전) | — |
| `exist_task.due_at` | 마감 여유·ClickUp식 일 배분 계산 불가 | 계산에서 제외 — 임의 기본값을 넣으면 마감압박을 왜곡하니 대체보다 제외가 안전 | — |
| `exist_task.assignee_person_id` | 그 업무가 누구 것인지 모름 | 대체 대상이 아니라 **애초에 모든 개인별 부하 계산에서 제외**(미배정 업무 별도 큐로) | — |
| `sched.wk_hours` | 기준 가용시간 1차 계산 불가 | `sched.def_wk_hours`로 대체 | Q1에 이미 이 용도로 설계돼 있음(컬럼 설명: "기본(계약상) 주간 근무시간") |
| `sched.def_wk_hours` | `wk_hours`도 NULL이면 기준 가용시간 자체가 없음 | 기본 40시간 | 정책 결정, 특정 연구 근거는 아님 |
| `sched.fte` | 유효가용용량 계산 불가 | 1.0(풀타임 가정) | — |
| `sched.eff_to` | "이 근무조건이 지금도 유효한가" 판단 불가 | NULL = 현재도 유효한 것으로 해석 | Q1 컬럼 설명에 이미 명시됨 |

**대체가 아니라 "행 선택"이 필요한 경우**: `mock_hr.sched`는 `eff_from`/`eff_to`로 기간이 나뉘는 이력 테이블이라 한 사람에게 여러 행이 있을 수 있다. NULL 대체와는 다른 문제지만 같이 짚어야 한다 — 계산 기준일이 `[eff_from, COALESCE(eff_to, 미래))` 안에 드는 행 1건만 골라야 하고, 안 그러면 과거 근무조건까지 섞여 `wk_hours`/`fte` 합산 자체가 틀어진다.

## Q4. Q3에서 가능하다고 판단한 방식들을 어떻게 하나의 최종 수식으로 통합할까?

### Q4-1. 겹치는 방식 정리 — 무엇을 대표로 쓸까

Q3-1에서 "가능"으로 판정된 것들을 다시 보면, 서로 다른 서비스 이름을 달고 있어도 **실제로 재는 값은 같은 경우**가 많다. 겉모습이 다른 것과 진짜 대체 관계인 것을 나눴다.

| 그룹 | 겹치는 방식들 | 실제로 재는 값 | 채택 | 이유 |
|---|---|---|---|---|
| ① 업무량(분자) | Jira Remaining, Monday.com Effort, Asana Effort, MS Project Assignment | 그 사람에게 배정된 잔여 작업량 | `exist_task.remaining` 합계 | 넷 다 "잔여 작업량"을 각자 다른 이름으로 부르는 것뿐 — 우리한테는 원본 데이터가 `remaining` 하나뿐이라 사실상 선택의 여지가 없다(동어반복적 통합) |
| ② 가용 용량(분모) | Tempo Capacity, Actonic Defined Capacity | 근무시간 − 휴가 | Tempo식 `wk_hours×fte − 승인휴가` | Actonic은 "Defined Capacity"가 어디서 나오는지 자체 계산법을 안 주고 외부에서 받아쓰는 값이라, 실제 산출 로직이 있는 Tempo식을 채택 |
| ③ 가용 용량(팀 단위 비율) | GitLab 가용비율 | 팀 전체 인원-일 중 가용 비율(%) | **제외**(개인 Load Rate에는 안 씀) | 단위가 다르다 — 개인별 절대 시간이 아니라 팀 전체의 비율이라 분모로 바로 못 쓴다. 팀 대시보드용 별도 지표로 남겨둔다 |
| ④ 초과 판단 로직 | Monday.com(Effort>Capacity), Asana(Effort>Capacity), MS Project(Overallocated) | 업무량이 용량을 넘었는가 | **선택 불필요** | 이건 서로 겹치는 대안이 아니라, 우리가 이미 쓰려는 `Load Rate = 업무량/용량 > 1`과 동일한 구조다. 세 서비스가 독립적으로 같은 패턴에 도달했다는 것 자체가 이 구조의 근거가 된다 |
| ⑤ 실적 활용도 | Harvest Utilization, Actonic Utilization% | `spent / Capacity` | **최종 수식에서 제외**, 보조 지표로만 유지 | 둘이 완전히 같은 공식이다(이름만 다름). 다만 이건 "그동안 얼마나 바빴나"를 재는 지표지 "지금 얼마나 바쁜가"가 아니라서 Load Rate와 다른 질문에 답한다 — 섞으면 안 됨 |
| ⑥ 진행률 | 진행률(자체 지표) | `spent/(spent+remaining)` | **최종 수식에서 제외**, 개별 업무 우선순위 판단용으로 유지 | Jira의 공식 Work Ratio(Time Spent/Original Estimate)는 Original Estimate가 없어 우리는 못 쓴다 — 이건 이름만 비슷한 별도 지표다. "그 업무 자체가 얼마나 끝났는지"를 재는 지표라 "지금 총 얼마나 부담인지"와는 다른 질문이라 부하율 안에 넣으면 이미 반영된 `remaining`을 한 번 더 넣는 꼴이 된다 |
| ⑦ 버퍼(여유율) | Actonic Buffer(0.8), Focus Factor(0.6~0.8) | 가용시간에서 회의·돌발업무 몫으로 미리 빼두는 비율 | **0.8로 통일** | 아래 Q4-2에서 근거 설명 |
| ⑧ 컨텍스트 스위칭 | Weinberg 손실표, Gloria Mark 23분 | 동시 진행 개수에 따른 손실 | Weinberg 표를 정책값으로 채택, Gloria Mark는 그 근거로만 유지 | 둘은 겹치는 대안이 아니라 하나(Gloria Mark)가 다른 하나(Weinberg)의 실증 배경이다 |
| ⑨ 방법론(가중치 방식) | 다기준 가중합, R2M | — | **최종 수식에서 제외** | R2M은 Q3-1에서 이미 불가로 확정(계획시간 필드 없음). 다기준 가중합은 Load Rate 같은 비율 지표가 아니라 여러 기준을 하나의 점수로 합치는 별도 목적(예: 업무 우선순위 랭킹)의 방법론이라 여기 억지로 끼워 넣지 않는다 |

### Q4-2. 최종 수식

> **2026-08-03 정정 — 아래 수식은 구현된 것과 다르다.** 검증에서 네 가지가 실데이터로
> 틀렸음이 확인돼(→ [[업무량계산_조사_검증]]) 개정안으로 대체됐고, 구현은 개정안을
> 따른다(`services/workload/calculator.py`). 이 절은 **어떤 판단이 왜 뒤집혔는지**를
> 남기기 위해 지우지 않고 둔다. 새로 구현할 때 이 수식을 베끼지 말 것.
>
> | 여기 적힌 것 | 실제 구현 | 이유 |
> |---|---|---|
> | `× 0.8` 버퍼 | **없음** | 기획서 v5 등 설계 4개 문서는 승수가 아니라 감산항(`− 고정 비프로젝트 일정시간`)을 쓴다. 근거 없는 승수로 그 자리를 메우면 용량이 조용히 20% 준다 |
> | `× COALESCE(fte, 1)` | `wk_hours` 우선, 없을 때만 `def_wk_hours × fte` | `wk_hours`에 **이미 FTE가 반영돼 있다**(실측 7명: 20 = 40 × 0.5). 다시 곱하면 10시간이 된다 |
> | `COALESCE(…, 40)` | 둘 다 없으면 `NO_SCHEDULE`로 막음 | 40시간을 가정하면 근무조건을 모르는 사람이 풀타임으로 계산돼 한가해 보인다 |
> | 기간 창 없음 | `[기준일, 기준일+4주)` | 창이 없으면 분모는 한 주치, 분자는 총량이라 전원이 100%를 넘어 구분력을 잃는다 |
> | 휴가를 통째로 차감 | 창으로 **clip** | 육아휴직 214일을 그대로 빼면 −1552시간이 되고, 부하율 오름차순에서 휴직자가 "가장 여유 있는 사람"이 된다 |
> | 비율(1 초과가 과부하) | **%** (100 초과가 과부하) | `workload_result.load_rate` 컬럼과 설계 문서가 %다 |
> | `remaining` NULL을 중앙값으로 대체 | 대체하지 않고 건수만 노출 | 없는 값을 지어내면 거짓 정밀도가 된다 |

동시진행 손실률(Weinberg)은 미검증 정도가 커서 확정 계산에 곱연산으로 섞는 대신, **기본형(추천)**과 **확장형** 두 버전으로 나눈다. 기본형이 기본값이고, 확장형은 실측 데이터로 배율을 검증한 뒤 전환을 검토하는 옵션이다.

```
가용용량 = (COALESCE(wk_hours, def_wk_hours, 40) × COALESCE(fte, 1) − 승인된 휴가시간) × 0.8

[기본형 — 기본값]
업무량 = Σ remaining(그 사람의 진행중 업무들)
부하율 = 업무량 / 가용용량                    (1을 넘으면 과부하)

[확장형 — 동시진행 손실 반영, 검증 후 전환 권장]
조정업무량 = 업무량 × (1 + 동시진행 손실률)
부하율 = 조정업무량 / 가용용량
```

**확장형의 배율 적용 방향이 틀렸다.** Weinberg의 손실률은 *가용시간 중 사라지는 비율*이라 `× (1 + L)`이 아니라 `÷ (1 − L)`이다. 5개 동시진행(75%)이면 ×1.75가 아니라 **×4.00**이다. 확장형을 켜는 시점에 고쳐야 한다.

- **가용용량 계산** → "실제로 이번 주에 일할 수 있는 시간을 계산한다."
- **업무량 계산** → "현재 진행 중인 업무들의 남은 작업량을 모두 더한다."
- **부하율 계산** → "업무량을 가용용량으로 나눠 현재 얼마나 바쁜지를 계산한다."

각 항의 근거:

- **`COALESCE(wk_hours, def_wk_hours, 40)`**: 실제 근무시간 → 계약상 근무시간 → 40시간(주 5일×8시간, 표준 근로시간이라는 사회적 합의값) 순으로 대체. [정책값]
- **`− 승인된 휴가시간`**: `absence` 4개 컬럼 전부 NOT NULL이라 대체 없이 정확히 계산된다. `status`가 기본값 `'REQUESTED'`(미승인)인 건 반드시 제외 — 안 그러면 과부하를 과대평가한다. [실측/공식]
- **`× 0.8`**: ~~Actonic(15~20% 버퍼 권장 → 승수 0.80~0.85)과 Focus Factor(승수 0.70~0.80) 두 범위가 겹치는 지점이 0.80 하나뿐이다. 서로 다른 커뮤니티가 독립적으로 도달한 값이 한 점에서 만난다는 게 근거다. `cal_event`가 없어 못 넣는 "회의 차감" 항의 대역이다.~~ **[2026-08-03 철회 — 기본식에서 뺐다]** 논증에 세 가지 문제가 있었다. ① 구간 끝값이 맞닿은 것은 수렴의 증거가 아니다(Actonic이 10~20%였다면 교집합은 [0.80, 0.90]이 된다). ② 두 출처는 독립이 아니다 — Actonic의 15~20%는 회의·돌발업무 몫이고 Focus Factor는 **회의를 이미 뺀 뒤** 곱하는 승수라 기준점이 다르다. ③ 인용한 Focus Factor 링크 두 개 모두 그 값을 담고 있지 않다(하나는 죽은 링크). 값 자체는 업계 관행상 무리 없지만 **`− 고정 비프로젝트 일정시간` 감산항의 대역으로 승수를 쓰는 것이 잘못**이라, 지금은 감산항을 0으로 두고 제한사항으로 노출한다. 조직이 버퍼를 원하면 버전된 정책값으로 따로 적용한다. [정책값]
- **`Σ remaining`**: Jira Remaining 그대로 합산. `status`/`assignee_person_id` NULL 업무는 Q3-3대로 제외. [실측/공식]
- **`× (1+동시진행 손실률)`**: Q4-3에서 근거와 함께 다룬다 — 정책값이라 확장형에서만 켠다.

### Q4-3. 보조 신호, 왜 넣거나 뺐나

**동시진행 개수 → 이중계산 아니다.** "동시진행이 많으면 할 일도 많다"는 이미 `Σremaining`에 들어있는 사실이다(업무가 늘면 합계가 자동으로 커진다). Weinberg 배율을 추가로 곱하는 이유는 **같은 총 시간도 여러 건으로 쪼개지면 그 자체로 손실이 생긴다는 별도 효과**를 반영하기 위해서다 — APA도 작업 전환이 생산 시간의 최대 40%를 깎을 수 있다고 밝혀 Gloria Mark(23분)와 같은 방향을 가리킨다. [문헌-경험칙] 다만 정확한 배율(0/20/40/60/75%)은 Weinberg 스스로도 "엄밀한 실험이 아니다"라고 밝힌 경험칙이라 기본형에는 안 넣고, 확장형에서만 정책값으로 켠다. 6개 이상은 표에 값이 없으니 배율로 흡수하지 말고 "관리자 확인 필요" 플래그로 따로 처리한다.

**Work Item Age → 최종 수식에서 뺀다.** "4일째지만 내일 끝나는 업무일 수도 있다"는 지적은 타당하다 — 실제로 Kanban 커뮤니티(ProKanban, Vacanti의 Actionable Agile Metrics)도 고정 일수 임계값을 문제 삼고, 대신 그 업무 유형의 과거 소요시간 분포에서 85번째 백분위를 기준선으로 쓰라고 권장한다. 문제는 이 percentile 기준을 만들려면 "완료까지 실제로 며칠 걸렸는지"를 쌓아둔 이력 데이터가 필요한데, Q1 범위에는 그런 히스토리 테이블이 없다. 즉 지적된 결함(①)도 맞고, 그 결함을 고칠 방법(②)도 지금 스키마로는 못 만든다 — 그래서 자동 수식에는 안 넣고, "진행중이면서 30일 넘은 업무 목록"처럼 사람이 직접 훑어보는 느슨한 스크리닝 필터로만 남긴다.
