# 운영자 콘솔 기능 — 화면별로 뭘 보여주고, 왜 그렇게 만들었는가

> 배경: `apps/ops`(백엔드)와 `/ops/*`(프론트엔드)로 구현된 운영자 콘솔 8개 화면을 화면 단위로 정리한다. API 엔드포인트·예외 처리 매트릭스 같은 개발자용 상세는 `docs/11_코드설명/운영자콘솔_api_처리.md`에 있고, 이 문서는 **"이 화면이 왜 이런 모습인가"**에 집중한다 — 화면을 처음 보는 사람이 "이게 왜 이렇게 돼 있지?"라고 물을 법한 지점마다 이유를 남겼다.
> 작성일: 2026-07-31 (주연)
> 갱신: 2026-07-31 — 테넌트 단위가 팀으로 확정되면서 `연결 조직 현황`이 `팀 현황`으로 바뀌고 화면에서 고유 번호를 뺐다. 3·4·5장과 0장 표가 그에 맞춰 수정됐다.

---

## 0. 운영자 콘솔이란

**운영자(operator)**는 새로운 회원 역할이 아니라, 이 플랫폼을 개발·운영하는 팀 본인이다(`docs/3_설계/역할별_권한_정책.md`). 팀장·팀원이 쓰는 일반 회원가입·로그인과는 완전히 분리된 `/ops/login`으로만 들어갈 수 있고, `user_account.is_admin = true`인 계정만 이 문을 통과한다.

| 화면 | 한 줄 요약 |
|---|---|
| 운영자 로그인 | `is_admin` 계정만 통과하는 별도 로그인 |
| 운영 현황 | 오늘 확인해야 할 숫자들을 한눈에 |
| 팀 현황 | 플랫폼을 쓰는 팀별로 계정·초대가 어떤 상태인지 |
| 계정 관리 | 계정 상태 확인·정지/재활성·잘못된 연결 해제 |
| 계정 연결·초대 현황 | 모든 팀의 초대 현황 조회·이상 초대 정리 |
| 연결 서비스 현황 | Drive·Jira 연동 상태와 오류 진단 |
| 감사 로그 | 누가 뭘 했는지 시간순 기록 |
| 전역 정책 | 초대 만료 기간, 시스템 공지 |

### 화면 전체에 깔린 설계 원칙 세 가지

이 원칙들은 특정 화면 하나의 이야기가 아니라 8개 화면 전부에 반복해서 등장하므로 먼저 정리한다.

1. **운영자 권한은 즉시 회수돼야 한다.** 토큰에 서명만 확인하고 끝나는 일반 로그인과 달리, 운영자 콘솔은 **요청마다 DB를 다시 조회**해서 `is_admin`과 계정 상태를 재확인한다. 로그인 직후 권한을 뺏겨도, 유효기간이 남은 토큰이라도 바로 다음 요청부터 막힌다. 그만큼 매 요청 DB 조회 비용이 들지만, 고권한 세션이라 노출 시간을 최소화하는 쪽을 택했다.
2. **참조 무결성이 DB로 강제되지 않는다.** 이 프로젝트는 `VARCHAR(5)` 짧은 코드를 애플리케이션에서 직접 관리하고 FK를 걸지 않는다. 그래서 "링크는 있는데 가리키는 대상이 삭제된" 상황이 실제로 생긴다. 모든 화면이 이 상황에서 화면 전체를 에러로 죽이지 않고, 원본 ID는 보존한 채 이름·이메일 같은 표시용 필드만 `null`로 보여주도록 통일했다.
3. **운영자는 조회·정리는 하되, 원본 데이터는 만들지 않는다.** People DB(조직·인력)의 원천은 HR 커넥터이므로 운영자도 `org`/`person`을 직접 수정하지 않는다. 운영자가 만질 수 있는 건 플랫폼 쪽 데이터(계정 상태, 초대, 정책)뿐이다.

## 1. 운영자 로그인

**보여주는 것**: 이메일·비밀번호 입력창 하나.

**왜 이렇게 만들었나**
- 관리자 승격 경로를 API에 아예 두지 않았다. `is_admin`을 켜는 방법은 호스트에서 직접 실행하는 스크립트(`grant_admin.py`) 하나뿐이라, 자기 자신은 물론 그 누구도 요청 한 번으로 운영자가 될 수 없다.
- 이메일이 존재하지 않을 때와 비밀번호가 틀렸을 때 **같은 오류 문구**를 준다 — 계정 존재 여부 자체가 정보 유출이기 때문이다.
- 로그인 성공 즉시 감사 로그에 남는다. 실패는 안 남긴다(무의미한 브루트포스 시도로 로그가 채워지는 걸 막기 위함).

## 2. 운영 현황

**보여주는 것**: 사용 중인 팀 수, 계정 통계(전체/잠김/중복 연결/확인 필요), 커넥터 통계(연결/만료/오류), 초대 통계(대기/오늘 만료), 최근 활동 5건.

**왜 이렇게 만들었나**
- 목업 화면은 "오늘 확인할 일"을 문구로 미리 박아뒀지만, 실제 구현은 **숫자만 원자료로 내려주고 문구는 프론트가 조합**한다. 백엔드가 "무슨 일이 있다"는 서사까지 만들면, 그 서사가 실제 데이터와 어긋나는 순간(하드코딩) 신뢰할 수 없는 화면이 된다.
- "확인 필요" 계정 수는 `잠김 OR 중복 연결`로 계산한다. 이 정의는 계정 관리·팀 현황과 완전히 동일한 SQL 조각을 공유해서, 화면마다 숫자가 미묘하게 다른 문제(어느 화면은 잠김만 세고 어느 화면은 중복까지 세는 식)가 생기지 않는다.

## 3. 팀 현황

**보여주는 것**: 팀 목록(팀 이름, 팀장, 출처 조직, 팀원 수, 가입 계정 수·미가입 수, 대기 중 초대, 상태).

**왜 이렇게 만들었나 — 이 화면이 원래 계획과 가장 많이 바뀐 곳이다**

이 자리에는 원래 `연결 조직 현황`(조직 트리)이 있었다. 2026-07-31에 **팀 현황으로 교체**했다.

바뀐 이유는 테넌트 단위가 확정됐기 때문이다. 우리 플랫폼을 쓰는 단위는 회사 전체가 아니라 **회사 안의 팀**이고, 팀은 팀장이 온보딩에서 팀명을 적어 직접 만든다([[HR_어댑터와_테넌트_경계]]). 조직도는 고객사 HR 안의 사정이라 운영자가 열람할 자리가 아니다 — 트리를 남겨두면 운영자가 남의 회사 조직도를 보는 화면이 된다.

- 행을 클릭하면 `/ops/accounts?team=…`으로 넘어가 **그 팀의 계정만** 걸러 보여준다. 팀에서 계정으로 내려가는 동선이라 두 화면이 같은 목록을 중복해서 갖지 않는다.
- `출처 조직`은 팀장의 HR 소속을 참고로 보여줄 뿐, 팀 경계가 아니다. 팀 경계는 `team_member`에 저장된 명단이다.
- `상태`는 **잠긴 계정이 있거나 팀원인데 아직 가입하지 않은 사람이 있으면** `확인 필요`다. 후자는 초대가 안 갔거나 코드가 방치된 상태라 운영자가 볼 이유가 있다.
- 팀이 하나도 없으면 "아직 만들어진 팀이 없습니다"와 함께 **팀은 팀장이 만든다**는 안내를 띄운다. 운영자에게 팀 생성 기능을 주지 않는다 — 원칙 3(운영자는 원본 데이터를 만들지 않는다)과 같은 이유다.
- 목업의 `updatedAt`("오늘 09:40" 같은) 필드는 뺐다. People DB 도메인에 그런 컬럼을 새로 추가하는 건 "운영자는 People DB를 조회만 한다"는 원칙에 어긋나는 과한 변경이라 판단했다.

### 화면에 내부 식별자를 쓰지 않는다

같은 날 콘솔 전 화면에서 고유 번호(`account_id`·`person_id`·`org_id`·`conn_id`·`invite_id` 등)를 표시에서 뺐다. 운영자가 판단에 쓰는 값이 아니고, 남의 회사 직원 번호를 노출할 이유도 없다. 식별자는 API 응답과 화면 이동에는 그대로 쓰인다 — 지운 것은 **표시**뿐이다.

## 4. 계정 관리

**보여주는 것**: 전체 계정, 연결된 직원, 소속 팀, HR 조직, 매핑 상태(미연결/연결됨/중복 연결), 연결 서비스, 정지·재활성·직원 연결 해제 버튼.

**왜 이렇게 만들었나**
- 팀 현황에서 팀을 클릭해 들어오면 `?team=` 쿼리가 붙어 **그 팀의 계정만** 보인다. 필터는 화면 상태가 아니라 URL에 있어서 링크를 그대로 공유할 수 있다.
- `팀`은 우리 플랫폼의 소속이고 `HR 조직`은 고객사 인사 시스템의 소속이라 둘을 다른 열로 나눴다. 팀에 아직 안 들어간 계정은 `미소속`이다.
- **"중복 연결"이 왜 문제인가**: 이 시스템은 계정 1개가 여러 직원(PERSON)에 연결되는 걸 DB 제약으로 막지 않는다. 실수로 두 번 연결됐거나 악의적으로 여러 신원을 흉내 낸 경우 둘 다 있을 수 있어서, 운영자가 직접 확인하고 정리할 수 있어야 한다.
- **본인 계정은 잠글 수 없다.** 실수로 자기 자신을 잠그면 그 즉시 자기 토큰의 운영자 인증도 실패해서(원칙 1) 스스로 풀 방법이 없어진다. 그래서 자기 자신을 대상으로 한 잠금 요청은 서버에서 거부한다.
- **탈퇴한 계정은 상태를 바꿀 수 없다.** `WITHDRAWN`은 최종 상태로 취급한다.
- 링크는 있지만 가리키는 직원 레코드가 없는 경우, API는 `person` 전체를 `null`로 지우지 않고 `person_id`만 남긴다 — "링크가 있었다"는 사실 자체가 운영자에게 필요한 정보이기 때문이다. 화면에는 번호 대신 `직원 정보 없음(연결 대상이 삭제됨)`으로 표시한다.

## 5. 계정 연결·초대 현황

**보여주는 것**: 전체 초대 목록(초대받은 직원, 대기/수락/만료/취소), 이상 초대 폐기, 중복 연결된 직원 연결 해제.

**왜 이렇게 만들었나**
- 팀장 설정 화면의 "팀원 관리"는 **본인이 보낸 초대만** 보이지만, 이 화면은 **모든 팀의 초대**를 본다 — 운영자 권한의 핵심이 "팀 경계를 넘어서 본다"는 것이기 때문이다.
- 목록의 첫 열은 초대 기록 번호가 아니라 **초대받은 직원 이름**이다. 운영자가 사람을 특정할 때 쓰는 값이 이름이고, 번호는 보여줘도 쓸 데가 없다.
- 만료 시각이 지났지만 DB에는 아직 `PENDING`으로 남은 초대(화면엔 "만료"로 표시)도 폐기할 수 있게 했다. 상태값을 실시간으로 배치 갱신하는 대신, 조회 시점에 계산해서 보여주는 쪽을 택해 별도 배치 작업이 필요 없다.
- 연결 해제는 **그 초대 하나가 아니라 계정에 연결된 모든 직원**을 해제한다(계정 관리의 로직을 그대로 재사용). 같은 계정이 여러 초대로 중복 연결됐으면, 어느 초대를 통해 해제를 눌러도 전부 함께 풀린다.

## 6. 연결 서비스 현황

**보여주는 것**: Google Drive·Jira 연결 목록, 상태(연결됨/확인 필요/오류)별 진단 문구.

**왜 이렇게 만들었나**
- **People DB는 이 화면에 안 뜬다.** 처음엔 People DB 연결도 "연결 서비스" 중 하나로 취급했지만, 다시 보면 People DB 연결은 Drive·Jira처럼 "프로젝트가 의존하는 외부 데이터 소스"가 아니라 **가입 계정을 본인 직원 레코드에 연결하는 본인 확인 절차**의 부산물일 뿐이다. 운영자가 진짜 점검해야 할 건 "Drive·Jira 인증이 살아있는가"이지 "본인 확인을 했는가"가 아니라서, People DB는 계정 관리의 `services` 배열과 이 화면 양쪽에서 전부 제외했다.
- 상세 패널에는 소유 계정 이메일과 연결 조직만 보여주고 **직원 실명은 표시하지 않는다.** 운영자에게 필요한 건 "무엇이 문제인지"지 "누구인지"가 아니다.
- `auth_status`에 따른 진단·다음 조치 문구(`인증이 만료됐습니다` 등)는 DB에 저장된 값이 아니라 API 응답을 만들 때 그때그때 계산한다. 알 수 없는 상태값이 들어와도(스키마에 CHECK 제약이 없는 컬럼이라) 에러 없이 "알 수 없는 연결 상태입니다"로 안전하게 처리한다.

## 7. 감사 로그

**보여주는 것**: "운영 활동" 탭(운영자 콘솔 조치 + 일반 사용자 행동), "분석·결정 기록" 탭(배정 실행/추천 결과/검증 결과/PM 결정).

**왜 이렇게 만들었나**
- 처음엔 이 화면이 **운영자 콘솔 자체의 조치**(계정 잠금, 초대 폐기 등)만 기록했다. 그런데 `audit_log` 테이블 자체는 원래 "로그인/연결/승인/반려 등" 플랫폼 전체의 행동을 담게 설계돼 있었고, 실제로 팀장·팀원의 행동(회원가입, 로그인, 커넥터 연결)이 하나도 안 잡히고 있었다는 게 뒤늦게 드러났다. 그래서 지금은 **일반 사용자의 로그인·회원가입·비밀번호 재설정·커넥터 연결(Drive/Jira/People DB)** 도 함께 기록한다.
  - 팀원 초대 발급·수락은 **의도적으로 감사 로그에 안 넣는다** — `member_invite` 테이블 자체가 `created_at`/`accepted_at`을 갖고 있어서 계정 연결·초대 현황 화면에서 이미 타임라인이 보이기 때문에, 같은 정보를 두 곳에 중복해서 남기지 않는다.
  - PM 결정(승인/수정/반려)도 마찬가지 이유로 뺐다 — `decision_rec`가 매 결정마다 새 행을 쌓는 이력 테이블이라 그 자체로 감사 로그 역할을 한다.
  - 반대로 **로그인·커넥터 연결은 원본 테이블이 최신 값만 덮어쓰기 때문에**(`user_account.last_login_at`, `connector_conn.connected_at`) 과거 이력이 안 남는다 — 이 둘은 감사 로그가 유일하게 이력을 보존하는 자리라 반드시 넣었다.
- "분석·결정 기록" 4개 탭(배정 실행/추천 결과/검증 결과/결정 기록)은 지금 대부분 빈 목록이다. 추천 엔진 파이프라인이 아직 이 테이블들에 쓰지 않기 때문이며, 오류가 아니라 정상 상태다. 나중에 파이프라인이 붙으면 코드 변경 없이 그대로 채워진다.
- 대량 조회(운영 활동 최신 200건)를 매번 새로 부르지 않도록, 탭을 처음 열 때만 불러오고 이후에는 캐시해서 재사용한다.
- 표에서 기록 ID·실행 ID·스냅샷 ID를 빼고 실행 시각·업무명·요청자·결정자를 보여준다(3장 끝의 고유 번호 정책). 다만 **CSV 내보내기에는 기록 ID를 남긴다** — CSV는 나중에 DB 기록과 대조하려고 뽑는 것이라 번호가 없으면 쓸모가 없다.

## 8. 전역 정책

**보여주는 것**: 초대 코드 만료 기간(1~90일), 시스템 공지 목록, 정책 변경 이력.

**왜 이렇게 만들었나**
- 초대 만료 기간은 원래 코드에 `14`로 하드코딩돼 있었다. 이걸 DB 설정값(`sys_setting`)으로 빼서 운영자가 화면에서 바꿀 수 있게 했는데, **실제 운영 중인 기본값(14일)을 그대로 시딩**했다 — 화면 작업 한 번으로 조용히 정책이 바뀌어버리는 일을 막기 위해서다.
- 값을 저장할 때 `SELECT setting_value FROM sys_setting WHERE setting_key = %s FOR UPDATE`로 **행을 잠근 뒤** 현재 값과 비교한다(`backend/db/repositories.py:3264-3277`). 동시에 같은 값으로 두 번 저장 요청이 들어와도 하나는 정상 처리되고 나머지는 "변경된 정책이 없습니다"로 조용히 정리된다.
  > **2026-08-05 정정.** "별도의 락 처리 코드 없이 SQL 한 줄로 동시성 문제를 해결했다"고 적혀 있었으나 실제로는 `FOR UPDATE`로 행 잠금을 건다. 락이 없다고 알고 다른 곳을 같은 방식으로 짜면 경합이 생긴다.
- 정책 변경 이력은 새 테이블을 만들지 않고 `audit_log`를 재사용한다. 변경 전/후 값과 변경 사유를 `payload`에 함께 담아서, 화면에서 "무엇이 왜 바뀌었는지"를 하나의 기록으로 다 보여줄 수 있다.
- 화면에는 최신 5건만 먼저 보여주고, "전체 보기"를 눌러야 전체 이력을 유형별 필터·검색과 함께 볼 수 있다 — 이력이 쌓일수록 화면이 한없이 길어지는 걸 막기 위한 선택이다.
