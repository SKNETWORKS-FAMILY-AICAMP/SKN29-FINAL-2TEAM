# Canonical Data Model ERD

> Figma Page 3-A·3-B·3-C의 저장 구조와 동일한 논리 모델이다.
> 별도 Graph DB는 사용하지 않으며 PostgreSQL의 PK·FK·조인 테이블로 관계를 조회한다.
> 3-A는 pgvector 검색 인덱스, 3-B는 프로젝트 분석·추천 RDBMS, 3-C는 플랫폼 운영·권한 RDBMS다.
>
> **타입 표기 주의.** 아래 다이어그램에 남아 있는 `uuid`·`bigint`는 논리 표기이지 물리 타입이 아니다.
> `DB/schema.sql`의 실제 PK는 거의 전부 `VARCHAR(5)` 짧은 코드(`PJ001`·`DC001`·`PS001`…)이고,
> UUID를 쓰는 것은 `doc_block`·`chunk`·`vec_idx` **세 개뿐**이다. 물리 타입·제약의 정본은 `DB/schema.sql`이다.

## 5. 주요 제약조건

| 테이블 | 제약조건 |
|---|---|
| PERSON | `employee_id` UNIQUE, 활성 People 데이터셋 내 정규화 이메일 UNIQUE |
| USER_ACCOUNT | 정규화 이메일 UNIQUE, 비밀번호 평문 저장 금지 |
| PROJECT_MEMBER | `(project_id, account_id)` UNIQUE |
| PROJECT_SOURCE | **`(project_id)` UNIQUE** — 프로젝트 하나에 Jira 프로젝트 하나(1:1, 2026-08-04, `ux_proj_source_proj`) |
| TEAM_FOLDER | `(team_id, external_folder_id)` UNIQUE |
| EXISTING_TASK | `(proj_source_id, jira_issue_id)` UNIQUE — 같은 이슈가 두 줄이 되면 그 사람 부하가 2배로 잡힌다 |
| ORGANIZATION | 자기 자신을 `parent_organization_id`로 가질 수 없음 |
| PERSON_SKILL | `(person_id, skill_id)` UNIQUE, 숙련도 허용 범위 CHECK |
| WORK_SCHEDULE | `fte > 0`, `fte <= 1`, 적용 시작일 ≤ 종료일 |
| PERSON_ABSENCE | 시작 시각 < 종료 시각 |
| IDENTITY_LINK | `(system_type, external_email)` UNIQUE, `(person_id, system_type)` UNIQUE — `external_account_id` 컬럼은 없다 |
| DOCUMENT | DB 유니크 제약은 없다. 같은 팀에 같은 파일이 두 번 등록되지 않도록 적재 코드가 `(team_id, source_file_id)`를 확인한다. 기준 문서는 프로젝트당 1건 — `(project_id) WHERE doc_role='PRIMARY' AND deleted=false` 부분 유니크 인덱스(`ux_doc_primary_per_proj`) |
| DOCUMENT_BLOCK | `(document_id, block_order, content_hash)` 인덱스 |
| VECTOR_INDEX | 활성 Chunk당 활성 Vector 최대 1개 |
| KNOWLEDGE_ITEM_SOURCE | `(knowledge_item_id, block_id)` UNIQUE |
| NEW_TASK | PM 승인 전 Jira 쓰기 대상이 될 수 없음 |
| FEATURE_READINESS_RESULT | `status ∈ {SUCCESS, PARTIAL_RESULT, BLOCKED}` |
| WORKLOAD_RESULT | 유효 가용용량 0일 때 부하율을 강제 계산하지 않음 |
| VALIDATION_RESULT | `REJECT`면 Jira 반영 금지 |

## 6. 저장소 배치

| Figma 영역 | 물리 저장소 | 대상 |
|---|---|---|
| 3-A | PostgreSQL pgvector (`public`) | `VECTOR_INDEX`: Chunk 임베딩과 검색 필터용 최소 메타데이터 |
| 3-B | PostgreSQL RDBMS (`public`) | 프로젝트·문서·Block·Chunk·지식 모델·Jira·Snapshot·추천·검증·PM 결정 |
| 3-B 중 People DB | PostgreSQL RDBMS (**`mock_hr`**) | `ORG`·`RESPONSIBILITY_LEVEL`·`SKILL`·`PERSON`·`PERSON_SKILL`·`IDENTITY_LINK`·`WORK_SCHEDULE`·`ABSENCE` 8개 |
| 3-C | PostgreSQL RDBMS (`public`) | 회원·**팀**·프로젝트 권한·OAuth 연결·프로젝트 연동 대상·감사 로그 |
| 공통 원본 | Object Storage | Drive 원본 파일, 파싱 중간 산출물 |

People DB 8개만 **`mock_hr` 스키마**에 있다(2026-07-31). 이 데이터는 고객사 HR 시스템의 것이고 우리는 읽기만 하기 때문이다. 스키마명을 붙이지 않으면 조회가 실패하므로, 실수로 우리 테이블과 조인할 수 없다 — [[HR_어댑터와_테넌트_경계]] §8. `PERSON_SNAPSHOT`·`ASSIGNMENT_RUN` 등 분석 결과는 같은 3-B라도 우리가 만든 데이터라 `public`에 남는다.

pgvector는 원본의 기준 저장소가 아니다. `VECTOR_INDEX.chunk_id → CHILD_CHUNK.block_id → DOCUMENT_BLOCK.document_id → DOCUMENT.source_file_id`로 원문 근거를 역추적할 수 있어야 한다. 3-A·3-B·3-C는 역할상 구분이며 초기 구현에서는 하나의 PostgreSQL 인스턴스에 함께 배치한다.
