# 08/08 오프라인 멘토링 정리

중간발표 이후 프로젝트 방향 재정립 및 Agent Platform 전환 논의

- 일시: 2026.08.08 (토) 16:00~21:00
- 주요 목적: 중간발표 피드백을 바탕으로 최종발표까지의 TO-BE와 개발 우선순위 재설정
- 핵심 주제: 서비스 방향 재정의 / Agent Builder·Harness / Connector·MCP / E2E 시나리오 / 평가 체계

## 1. 이번 멘토링의 핵심

이번 멘토링은 중간발표에서 받은 피드백을 하나씩 보완하는 자리라기보다는, 남은 약 3주 동안 프로젝트를 어떤 제품으로 완성할 것인지 다시 정의하는 자리에 가까웠다.

중간발표까지는 프로젝트가 사실상 다음 흐름을 중심으로 만들어져 있었다.

> 외부 데이터 연결 → 문서 전처리 → 업무 추출 → 업무 분배 → 부하량 계산 → 대시보드

이 구조 자체가 잘못된 것은 아니지만, 결과적으로 서비스가 '업무 분배'라는 하나의 유스케이스에 지나치게 고정되어 보였다.

반면 우리가 처음 이야기했던 문제의식은 더 넓었다. 기업에는 여러 데이터와 업무 시스템이 있고, 비개발자가 이를 활용해 자신에게 필요한 AI 업무 흐름을 만들어 사용할 수 있어야 한다는 것이다.

따라서 최종 프로젝트에서는 기존 결과물을 폐기하는 것이 아니라,

> 업무 분배 단일 기능을 제공하는 서비스에서, 기업의 데이터와 도구를 연결하고 비개발자가 프로젝트 운영용 에이전트를 만들고 활용할 수 있는 플랫폼으로 확장한다.

라는 방향으로 프로젝트의 관점을 넓히기로 했다. 즉, 완전한 주제 변경(Pivot)이 아니라 기존 '프로젝트 운영 코파일럿'을 상위 개념으로 확장하는 것이다.

## 2. AS-IS: 중간발표까지 우리가 만든 것

중간발표 MVP까지 구현한 핵심 흐름은 다음과 같다.

1. Connector 연결 — Google Drive / Jira / HR Mock Data
2. 비정형 문서 처리 — Parsing / Chunking / Embedding / Vector DB 적재 및 검색
3. 업무 추출 Agent — 프로젝트 문서에서 업무 후보 추출, 구조화된 결과 생성
4. 업무 분배 로직 — 업무 현황과 가용 시간을 활용한 부하량 계산, 적절한 담당자 후보 제시
5. Frontend / Backend Prototype
6. Dashboard — 구성원 업무량, 시간 기반 부하율, 프로젝트 현황 표시

이 과정에서 문서 파싱·청킹·에이전트·업무량 계산 등 여러 기술적 실험을 진행했다는 점 자체는 의미가 있었다. 다만 최종 제품의 관점에서는 "그래서 이 플랫폼을 업무 분배 외에는 어디에 사용할 수 있는가?"라는 질문에 명확히 답하기 어려운 상태였다.

## 3. 가장 큰 방향 전환: '업무 분배 기능'에서 '환경 제공'으로

멘토님이 강조한 핵심 중 하나는 플랫폼이라면 특정 업무 하나를 잘 해결하는 것만으로는 부족하다는 점이었다.

> 좋은 플랫폼은 특정 정답을 제공하기보다, 사용자가 자기 업무에 맞는 에이전트를 구성할 수 있는 환경을 제공한다.

예를 들어 어떤 사용자는 업무 분배가 필요하지만, 다른 사용자는 프로젝트 보고서를 자동으로 만들고 싶을 수도 있고, Jira 업무를 관리하고 싶을 수도 있고, Drive 문서를 분석하고 싶을 수도 있고, 여러 에이전트를 연결해 하나의 업무 흐름을 만들고 싶을 수도 있다.

따라서 최종적으로는 "우리가 모든 업무용 에이전트를 만드는 것"이 아니라 "사용자가 필요한 에이전트를 만들고 연결할 수 있도록 하는 것"이 플랫폼의 역할이 되어야 한다.

## 4. Target User: 비개발자

이 방향에서 가장 중요한 것은 Target Audience를 명확히 고정하는 것이다. 이번 논의에서는 우리의 주요 사용자를 기업의 비개발자 실무자로 보는 것이 적절하다는 의견이 나왔다.

개발자는 Claude Code, Codex와 같은 개발 환경을 직접 활용할 수 있다. 반면 비개발자는 어떤 모델을 연결해야 하는지, Tool Calling을 어떻게 구현해야 하는지, MCP가 무엇인지, Agent Graph를 어떻게 설계해야 하는지 직접 이해하고 구현하기 어렵다.

따라서 우리는 이러한 기술을 내부적으로 감추고, 사용자가 (1) 어떤 일을 수행할 에이전트인지 (2) 어떤 데이터를 참고할지 (3) 어떤 도구를 사용할지 정도만 설정하면 실제 에이전트가 만들어지는 환경을 지향한다.

## 5. Agent Builder

사용자가 에이전트를 만들 때 직접 코딩하지 않아도 되도록 Agent Builder를 제공한다. 최소한 다음 요소는 설정할 수 있어야 한다.

- **Agent Profile** — Agent 이름 / Description / 역할·목적. 특히 Description은 단순 소개 문구가 아니라 어떤 상황에서 이 Agent를 호출할지 판단하는 중요한 정보가 될 수 있다.
- **Behavior / Instruction** — Agent가 어떻게 행동해야 하는지 정의. 어떤 기준으로 업무를 분석할지, 어떤 Tool을 언제 사용할지, 결과를 어떤 형식으로 반환할지 등을 자연어 Instruction으로 설정한다.
- **Model** — 사용 가능한 모델 중 Agent가 사용할 모델을 선택. 초기 구현에서는 복잡한 모델 라우팅보다 모델을 교체 가능한 구조로 두는 것이 중요하다.
- **Tool / MCP** — 해당 Agent가 사용할 수 있는 외부 기능 연결. 예: Jira MCP, 사내 API, Web Search, Google Drive 관련 기능.
- **Agent 사용** — 생성된 Agent는 별도의 테스트 화면에서 끝나는 것이 아니라 실제 Chat Interface에서 선택하여 사용할 수 있어야 한다.

## 6. Agent Builder보다 더 중요한 것: Agent Harness

이번 멘토링에서 기술적으로 가장 강조된 부분은 Agent Harness였다. Builder가 사용자에게 보이는 설정 UI라면, Harness는 에이전트가 안정적으로 실행될 수 있도록 뒤에서 제공하는 실행 환경 전체에 가깝다. 단순히 LangGraph로 Agent Node 몇 개를 만드는 것과는 범위가 다르다.

우리가 공부하고 설계해야 할 주요 항목:

1. **Reasoning / Agent Loop** — 요청을 받은 Agent가 어떤 작업이 필요한지 판단하고, Tool을 선택하고, 결과를 확인하고, 필요한 경우 다시 행동하는 기본 실행 구조.
2. **Tool Execution** — REST API 또는 MCP Tool 호출. Tool 목록 등록뿐 아니라 어떤 Agent에게 어떤 Tool을 허용할지, Tool Description을 어떻게 제공할지, Agent가 적절한 Tool을 선택할 수 있는지까지 고려.
3. **Context Management** — 대화가 길어질수록 전체 내용을 계속 Prompt에 넣는 방식은 한계가 있다. Short-term Context / Long-term Memory / Context Offloading / Context Compaction·Summary 고려.
4. **Agent-to-Agent** — 하나의 Agent가 모든 일을 처리하지 않고 필요할 경우 다른 Agent에 업무를 위임할 수 있는 구조. 최종 프로젝트에서 복잡한 Multi-Agent Graph 전체를 완성할 필요는 없지만, 추후 Agent끼리 연결할 수 있는 구조적 여지를 남겨두는 것이 중요하다.
5. **Permission** — Agent와 Tool이 기업 데이터를 다루므로 권한 고려. 예: Agent 생성 가능 사용자, Agent 사용 가능 사용자, 특정 MCP 사용 가능 사용자, 특정 Drive 데이터 접근 가능 사용자.
6. **Observability / Analytics** — Agent 실행 횟수, Tool 호출, Token 사용량, 오류, 실행 과정, 모델 사용량. 필요하다면 LangSmith, Langfuse 등 기존 도구를 연결하여 직접 모든 모니터링 시스템을 구현하는 부담을 줄인다.

## 7. 왜 기존 오픈소스를 분석해야 하는가

Harness를 처음부터 우리 머리로만 설계하지 말고, 이미 오랫동안 Agent 환경을 고민해 만든 제품과 오픈소스의 구조를 분해해서 학습하자는 것이 멘토님의 조언이었다.

- **Deep Agents / Deep Agents From Scratch** — Planning·TODO 관리, Context 관리, File System을 활용한 Context Offloading, Sub-Agent Delegation, Agent State, Tool 구조. 특히 Deep Agents From Scratch는 왜 장시간 작업을 수행하는 Agent에게 Planning, Context Offloading, Sub-Agent가 필요한가를 이해하기 좋은 자료다.
- **OpenCode** — 공개된 Coding Agent 제품. Agent Loop, Model 연결, Context 처리, Tool 호출, Session 관리, MCP 연결이 실제 제품 코드에서 어떻게 구성되는지 분석.
- **Claw Code** — Agent 기반 개발 환경의 구조. 실행 흐름, Context, Tool, Agent Architecture 중 적용할 수 있는 패턴을 찾는다.

중요한 것은 코드를 그대로 가져오는 것이 아니라, "왜 이런 구조를 선택했는가?", "우리가 만들 Harness에는 무엇이 반드시 필요한가?"를 이해하는 것이다.

## 8. Connector는 '개수'가 아니라 E2E

남은 일정에서는 Connector 수를 늘리는 것이 중요하지 않다. 오히려 최소 하나 이상의 Connector가 연결 → 데이터 접근 → 파싱 → 청킹 → 검색 → Agent 활용까지 완전히 이어지는 것이 훨씬 중요하다. 현재 후보는 Google Drive / Jira / HR Mock 정도면 충분하다.

발표에서도 "우리는 Connector를 세 개 만들었다"보다 "어떤 Connector가 추가되더라도 Agent가 데이터를 활용할 수 있는 동일한 흐름을 만들었다"라고 설명하는 것이 플랫폼 관점에서 더 좋다.

## 9. Connector와 MCP를 구분해야 한다

- **Connector** — 외부 데이터 소스에서 데이터를 가져와 우리가 활용할 수 있는 형태로 만드는 통로. 예: Google Drive → 문서 가져오기 → Parsing → Chunking → Embedding/Indexing → Agent가 검색. 데이터 수집·검색 기반.
- **MCP** — Agent가 외부 시스템의 기능을 Tool 형태로 사용할 수 있게 하는 인터페이스. 예: "이 프로젝트를 Jira에 만들어줘" → Jira Project 생성 Tool 호출. 데이터를 읽는 것을 넘어 외부 시스템에 행동을 수행하는 구조.

우리 플랫폼이 모든 MCP Tool을 직접 만들어 제공할 필요는 없다. 기업에서 이미 운영하는 MCP Server 또는 API가 있다면, 우리 플랫폼은 그것을 연결해서 Agent가 사용할 수 있도록 해주는 역할을 하면 된다.

## 10. MCP 구현 범위

초기 구현 범위는 과도하게 잡지 않는다. 최소 목표:

> 설정 페이지에서 MCP Server 연결 → Agent Builder에서 연결된 MCP를 Agent에 연결 → Runtime에서 Agent가 MCP 내부 Tool을 호출

시간이 허용된다면 이후 MCP Server 내부 Tool 목록 표시, Agent별 사용 Tool 선택, 관리자 승인, Tool 사용량 확인 등을 추가할 수 있다.

## 11. Jira는 대표 Action Tool로 활용 가능

기존에는 Jira에서 데이터를 가져오는 Connector 관점이 강했지만, 새 구조에서는 Jira가 좋은 Action Tool 시나리오가 될 수 있다.

1. 프로젝트 문서 분석 → 2. Agent가 Task 추출 → 3. 사용자 확인 → 4. Jira Project/Issue 생성 → 5. 결과 반환

기존 MCP에서 필요한 기능이 부족하다면 Jira REST API를 Custom MCP Server로 감싸서 필요한 Tool을 추가하는 방식도 고려할 수 있다. 중요한 것은 Jira 자체가 아니라, 기업 시스템의 API를 MCP Tool로 연결하여 Agent가 실제 행동을 수행하는 구조를 데모하는 것이다.

## 12. Knowledge / 문서 처리 방향 재검토

IBM watsonx Orchestrate 같은 제품에서는 Knowledge 영역에 문서를 넣어 Vector DB 기반으로 활용하는 구조도 확인했다. 하지만 우리 플랫폼은 범용 Agent Platform이면서 동시에 Project Operation Copilot이라는 목적이 있다. 모든 문서를 미리 업로드하여 Vector DB에 넣는 구조가 반드시 정답은 아니다.

논의된 방향 중 하나: (1) Connector에서 문서 Metadata 확인 → (2) 요청이 들어왔을 때 관련 파일 검색 → (3) 필요한 파일만 가져와 → (4) Parsing/Chunking → (5) Agent Context에 제공. 다만 이 부분은 최종 확정된 구현안이라기보다 추가 설계가 필요한 영역이다.

기존에 개발한 Parsing/Chunking/Embedding 기술을 폐기한다는 의미가 아니다. 이 전처리 파이프라인은 Agent가 기업의 비정형 데이터를 제대로 사용할 수 있도록 만드는 기반 기술로 계속 활용한다.

## 13. UI 구조도 다시 설계한다

기존 UI는 업무 분배 흐름 기준이었으므로 플랫폼 방향에 맞추어 전체 정보 구조를 다시 구성한다.

- **Chat** — 새 서비스의 핵심 인터페이스. Agent 선택, 업무 요청, Connector 데이터 활용, Tool 실행, 결과 확인.
- **Agent Builder** — Agent 생성·설정.
- **Project** — Project Operation Copilot이라는 기존 정체성을 유지하기 위해 프로젝트 단위 Context는 유지. 다만 기존의 '업무 분배 시작' 버튼 중심 구조는 제거하거나 축소.
- **Settings** — Model / Connector / MCP / Permission 등 플랫폼 설정.
- **Admin** — 필요 시 운영자용 화면. Model 상태, MCP/Tool, Token 사용량, Agent 실행 상태, Analytics, Permission.

## 14. 기존 Dashboard는 다시 정의해야 한다

기존 Dashboard는 구성원별 업무량과 부하율을 보여주는 화면이었으나, 플랫폼 방향에서는 핵심 화면일 필요가 없다. 한 가지 가능성은 Agent가 필요한 순간 Dashboard나 Report를 생성하는 것이다.

> 사용자: "이번 프로젝트 팀원들의 현재 업무 부하를 보여줘."
> Agent: HR/Jira 데이터 분석 → HTML 기반 Dashboard 생성 → Chat 안에서 시각화

이렇게 하면 기존 업무량 계산 로직도 버리지 않으면서 플랫폼의 Pre-built Tool / Demo Asset으로 재활용할 수 있다. 향후 HTML, PDF, Markdown, Drive 저장 등 다양한 Export 방식도 확장할 수 있다.

## 15. 기존 업무 추출·분배 기능은 버리지 않는다

현재까지 개발한 업무 추출 Agent와 업무 분배 로직은 플랫폼에 기본 제공되는 Pre-built Agent 또는 프로젝트 운영 Agent Platform의 대표 Demo로 활용한다.

> **Platform = 우리가 만드는 제품**
> **Task Extraction / Assignment = Platform 위에서 동작하는 대표 Use Case**

이 구분이 매우 중요하다.

## 16. Benchmark: IBM watsonx Orchestrate

기업용 Agent Platform에 어떤 요소가 필요한지 확인했다. 참고할 것: Agent Builder(Description·Behavior·Model·Knowledge·Tool), Agent 공유(조직 내 사용자와 공유), Role & Permission(Agent 사용/생성, Automation 생성, Admin 권한 구분), Tool/Connection, Guardrail(입출력 검사·기업 데이터 노출 방지), Analytics, Natural Language Workflow(Drag & Drop도 비개발자에게 어려울 수 있어 자연어로 Workflow 생성).

IBM 공식 문서에서도 User / Builder / Admin 역할을 구분하고, Builder가 Agent를 구축하고 Admin이 연결·사용자·권한 등을 관리하는 구조가 확인된다.

## 17. 우리가 IBM을 그대로 만드는 것은 아니다

watsonx Orchestrate 수준의 제품을 3주 안에 만드는 것은 현실적으로 불가능하다. Benchmark의 목적은 기능 복제가 아니라 제품의 핵심 구조를 이해하는 것이다.

- **반드시 보여줄 것**: Agent 생성, Agent 실행, Connector 데이터 활용, MCP/Tool 호출, 대표 E2E Scenario
- **구조적으로 설계할 것**: Context/Memory, Permission, Agent Pipeline
- **여력이 있다면 보여줄 것**: Agent 공유, Analytics, Guardrail, Natural Language Flow 생성
- **Future Work**: 복잡한 Automation, 고급 Multi-Agent Orchestration, Enterprise-level Governance, 대규모 Agent Catalog

## 18. 최종발표에서 가장 중요한 것: E2E

멘토님이 반복해서 강조한 것은 기능 개수가 아니라 **실제 하나의 업무가 처음부터 끝까지 동작하는가**이다.

대표 시나리오 — 사용자: "이번 프로젝트 문서를 참고해서 업무를 정리하고 Jira 프로젝트에 등록해줘."

1. Agent가 사용자 요청 분석
2. Google Drive Connector를 통해 관련 프로젝트 문서 검색
3. 필요한 문서 Parsing / Retrieval
4. Task Extraction Agent 실행
5. 필요한 경우 업무 분배 Agent 활용
6. 사용자에게 결과 확인
7. Jira MCP Tool 호출
8. Jira에 Project / Issue 생성
9. 완료 결과 및 근거 반환

이 하나의 흐름만 안정적으로 동작해도 Connector, Document Processing, Agent, MCP, Tool Calling, Project Operation이라는 프로젝트의 핵심 요소를 모두 보여줄 수 있다.

## 19. "동작한다"보다 중요한 것: 평가

중간발표에서 가장 부족했던 부분 중 하나가 평가 근거였다. 최종발표에서는 "Agent가 잘 동작했습니다"로 끝나면 안 된다. 각 요소마다 평가 기준을 만든다.

- **Document Processing**: 파싱 성공률, 정보 누락률, 표 구조 보존, Heading 구조 보존, 처리 시간
- **Retrieval**: Relevant Document Recall, Top-k Accuracy, 근거 문서 적합성
- **Task Extraction**: Task Precision, Task Recall, 누락 업무 수, 잘못 추출된 업무 수
- **Tool Selection**: 올바른 Tool 선택률, 불필요한 Tool 호출률, Tool 실행 성공률
- **E2E**: 전체 Task 성공률, 평균 처리 시간, 실패 단계, 재시도 성공률

가능하다면 기존 방식 대비 얼마나 시간을 줄였는가라는 현업 효과까지 연결한다.

## 20. 발표에서도 '기술'보다 '고객'을 먼저 생각한다

최종발표 자료는 "고객사 C-Level 또는 실무 담당자에게 PoC 결과를 발표한다"는 관점으로 만든다. LangGraph, Chunking, Embedding 같은 기술 나열보다:

1. 기업이 어떤 문제를 가지고 있었는지
2. 기존 시스템으로 왜 해결하기 어려운지
3. 우리 플랫폼이 어떤 환경을 제공하는지
4. 실제 하나의 업무가 어떻게 끝까지 수행되는지
5. 어떤 근거로 성능을 검증했는지

기술은 그 뒤에 "이 경험을 가능하게 하기 위해 우리가 이렇게 설계했다"라는 근거로 등장해야 한다.

## 21. 프로젝트의 한 줄 정의

> 기업의 데이터와 업무 도구를 연결하고, 비개발자가 프로젝트 운영에 필요한 AI Agent를 직접 만들고 활용할 수 있도록 하는 Agent 기반 Project Operation Copilot

조금 더 기술적으로 표현하면:

> Connector를 통해 기업 데이터를 활용하고 REST/MCP Tool을 실행할 수 있는 Agent Harness 위에서, 비개발자가 업무용 Agent를 구성하고 실행하는 프로젝트 운영 플랫폼

## 22. 멘토링 이후 확정된 최우선 과제

- **Priority 1. 서비스 구조 재설계** — 업무 분배 중심 IA를 폐기하고 Agent Platform 관점으로 전체 화면과 사용자 흐름 재설계. Chat / Builder / Project / Settings / Admin의 관계를 명확히. 1~2일 내 설계 초안.
- **Priority 2. Agent Harness 구조 설계** — OpenCode, Deep Agents 계열 등 분석. Agent Loop, Context, Memory, Tool Calling, MCP, Sub-Agent, Planning, State, Context Compaction. 문서 조사에서 끝내지 말고 우리 Architecture에 무엇을 적용할지까지 정리.
- **Priority 3. Connector E2E 완성** — Connector 개수 추가 중단, 최소 하나는 Connection → Fetch → Parse → Chunk → Retrieve → Agent 전체 흐름 완전 동작.
- **Priority 4. MCP 실행 구조** — 외부 MCP Server를 설정에서 등록하고 Agent가 실제 Tool을 실행하는 최소 구조. Jira를 대표 Action Scenario로.
- **Priority 5. 기존 Agent 재구성** — Task Extraction / Assignment를 플랫폼의 기본 제공 Agent로 전환, 새 플랫폼 구조 안에서 정상 실행되도록 재연결.
- **Priority 6. 평가 설계** — 개발이 끝난 뒤가 아니라 개발 전에 무엇을 측정할 것인지 정의. Document / Retrieval / Agent / Tool / E2E별 평가 기준.

## 23. 역할 분담 방향

- **비정형 문서 처리** — 기존 작업자가 계속 담당하여 빠르게 안정화. 목표는 새 기능 추가보다 Parsing / Chunking / Retrieval E2E 완성 및 평가.
- **Frontend / Backend** — 새로운 서비스 구조와 화면 흐름을 빠르게 설계·구현.
- **Agent Harness Research** — 팀원들이 참고 Repository를 나누어 분석. 각자 하나를 맡아 Architecture, Context 관리, Memory, Tool, MCP, Agent Loop를 정리한 뒤 팀에 설명. 목적은 Repository 공부가 아니라 우리 Harness Architecture의 설계 근거.

## 25. 기술 검증 과정에서 주의할 부분

- **Docling HWP/HWPX** — Docling Issue #3602는 현재 Docling이 HWP/HWPX를 지원한다는 의미가 아니라, HWP/HWPX를 정식 Input Backend로 추가해달라는 Feature Request다. 발표에서는 "Docling에서도 한국 기업·공공 부문의 HWP/HWPX 지원 필요성이 커뮤니티 이슈로 제기되고 있다" 정도로 활용한다.
- **Deep Agents From Scratch** — 공개적으로 확인되는 대표 저장소는 LangChain의 `deep-agents-from-scratch`. 참고 패턴: Task Planning, Context Offloading, Context Isolation, Sub-agent Delegation.
- **Guardrail** — "OpenAI도 Guardrail을 제공한다"는 설명은 정확하게는 OpenAI **Agents SDK**가 Agent의 Input / Output / Tool Guardrail 구조를 제공한다는 의미. 직접 모든 보안 체계를 만드는 대신 기존 SDK의 Guardrail 기능 활용을 검토할 수 있다.

## 26. 이번 멘토링에서 가장 중요한 판단

남은 기간 동안 모든 것을 구현하려 하면 다시 중간발표 때와 같은 문제가 생긴다. 중요한 것은 기능의 수가 아니라 하나의 명확한 제품 구조와 하나의 강력한 E2E Demo다.

- Builder를 예쁘게 많이 만드는 것보다 **Harness가 실제로 동작하는 것**
- Connector를 많이 만드는 것보다 **하나가 완벽하게 연결되는 것**
- Agent를 많이 만드는 것보다 **하나의 업무가 끝까지 수행되는 것**
- 기술을 많이 설명하는 것보다 **왜 이렇게 설계했는지 근거를 제시하는 것**

## 최종 정리

- **이전**: 문서에서 업무를 추출하고 적절한 담당자에게 분배하는 AI 서비스
- **이후**: 기업 데이터와 도구를 연결하여 비개발자가 프로젝트 운영 Agent를 만들고 실행할 수 있는 Agent Platform

기존에 개발했던 Parsing, Chunking, Embedding, Connector, 업무 추출 Agent, 업무 분배, Dashboard는 버리는 것이 아니라 각각 **Data Layer / Connector / Pre-built Agent / Demo Tool**로 새 구조 안에 재배치한다.

앞으로 가장 중요한 질문은 "업무 분배 Agent의 성능을 조금 더 높일까?"가 아니라 **"우리 플랫폼에서 Agent가 기업의 데이터와 Tool을 가지고 하나의 실제 업무를 처음부터 끝까지 수행할 수 있는가?"**이다. 이 질문에 명확하게 YES라고 보여주는 것이 최종 프로젝트의 가장 중요한 목표다.
