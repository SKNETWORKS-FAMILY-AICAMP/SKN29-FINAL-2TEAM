- 수행일: 2026-08-31 (Asia/Seoul)
- 대상: `https://halil-ai.site`, `https://api.halil-ai.site`
- 최초 판정: **조건부 실패 — 주요 이슈 수정 후 재검증 필요**
- 수정 후 판정: **로컬 검증 통과 — AWS 재배포 후 실서버 재검증 필요**
- 원칙: 운영 데이터 변경 없이 조회·탐색·모달 표시·검색·정렬·오류 처리만 검증
- 화면 폭: 데스크톱 1365×900, 태블릿 768×1024, 모바일 390×844

## 1. 요약

배포본의 공개 화면, 일반 사용자 로그인 이후 핵심 화면, API/DB 상태, 데스크톱·모바일 반응형,
기본 접근성, 콘솔 오류, CORS/TLS/캐시, 로컬 회귀 테스트를 점검했다.

정상 확인:

- AWS 프런트/API 모두 응답, API health의 `status`, `database`, `people`, `vector` 모두 정상
- 프런트엔드 프로덕션 빌드 성공
- Django 전체 1,809개 테스트 통과(44.196초)
- Python `pip check` 통과
- 일반/운영자 보호 경로의 로그인 리다이렉트 정상
- 로그인 실패 시 계정 존재 여부를 드러내지 않는 오류 문구 정상
- 프로젝트 검색·상세·기준 문서 후보, 문서 폴더·내 파일, 에이전트 도구/서브에이전트 모달,
  Drive 폴더 미리보기, 스킬 실패 상세가 정상 로딩
- 브라우저 콘솔 error/warn 없음
- 허용 Origin에만 CORS 응답, 임의 Origin에는 CORS 헤더 없음
- TLS 인증서 정상(2026-11-12 만료, 점검일 기준 72일 잔여)
- 해시 정적 자산 캐시 `public, max-age=31536000, immutable` 정상
- HTTP→HTTPS 308 리다이렉트 정상, TLS 1.2 연결 성공 및 TLS 1.0/1.1 연결 거절
- 보호 API가 인증 없음/잘못된 Bearer 토큰에 각각 401 JSON으로 응답
- 공개 8개 경로가 768px·390px에서 문서 전체 가로 넘침 없이 표시됨

### P2 — 배포 프런트엔드 보안 헤더 누락

- `https://halil-ai.site/`와 `/login` 응답에서 아래 헤더가 모두 비어 있다.
  - `Strict-Transport-Security`
  - `Content-Security-Policy`
  - `X-Content-Type-Options`
  - `X-Frame-Options` 또는 CSP `frame-ancestors`
  - `Referrer-Policy`
  - `Permissions-Policy`
- 영향: 클릭재킹, 콘텐츠 유형 스니핑, XSS 피해 범위, HTTPS 강제에 대한 브라우저 방어가 약하다.
- 관련 코드: `frontend/Caddyfile.static`
- 참고: API 응답은 `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: same-origin`을 반환한다.

### P2 — 배포 의존성 고위험 취약점 경고

- `npm audit --omit=dev`: high 2건
- 대상: `react-router-dom@7.18.1` → `react-router@7.18.1`
- 범위: `react-router >=7.12.0 <7.18.2`
- 내용: RSC Mode CSRF bypass (`GHSA-qwww-vcr4-c8h2`)
- 수정 가능: `react-router`/`react-router-dom` 7.18.2 이상으로 갱신 후 빌드·회귀 테스트.
- 현재 앱은 Vite SPA이며 RSC 모드를 사용하지 않아 직접 도달 가능성은 낮아 보이지만,
  배포 의존성 high 경고이므로 릴리스 전에 제거하는 편이 안전하다.
- 전체 audit에는 개발 전용 Vite→PostCSS→`nanoid@3.3.16` high 1건도 추가로 잡힌다.

### P2 — 배포 교체 순간 오래 열린 탭의 lazy chunk 실패를 복구하지 못함

- 현재 배포는 새 프런트 컨테이너로 교체되면서 이전 해시 자산을 보존하지 않는다.
- `/assets/*`의 없는 파일은 올바르게 404지만, 그 404에도
  `Cache-Control: public, max-age=31536000, immutable`이 붙는다.
- 앱은 대부분의 화면을 `React.lazy()`로 읽는데 lazy import 실패를 받는 Error Boundary나
  「새 버전이 배포됐습니다. 새로고침하세요」 복구 UI가 없다.
- 재현 가능 시나리오: 배포 전에 `/chat`을 열어 둠 → 배포 후 아직 읽지 않은 문서/설정 화면으로
  이동 → 기존 메인 번들이 이전 해시 청크를 요청 → 404 → 화면 렌더 실패.
- 관련 코드:
  - `frontend/src/App.tsx:15`
  - `frontend/src/App.tsx:78`
  - `frontend/Caddyfile.static:7`
  - `frontend/Caddyfile.static:38`
- 제안: lazy import 오류를 한 번 감지해 전체 새로고침을 안내/수행하는 Error Boundary를 추가하고,
  404 응답에는 장기 immutable 캐시를 적용하지 않거나 직전 배포 자산을 짧게 보존한다.

### P2 — 프로덕션 JavaScript/CSS가 압축 없이 전송됨

- `Accept-Encoding: br, gzip` 요청에도 `Content-Encoding`이 없고 원본 크기 그대로 전송된다.
- 실제 배포 자산 예:
  - 메인 JS: 278.1 KiB
  - 채팅 JS: 285.7 KiB
  - 설정 JS: 85.6 KiB
  - 채팅 CSS: 61.1 KiB
- 캐시와 조건부 요청(ETag→304)은 정상이나 첫 방문/새 버전 다운로드 비용이 불필요하게 크다.
- 관련 코드: `frontend/Caddyfile.static`에 `encode zstd gzip` 설정 없음.
- 제안: 내부 정적 Caddy 또는 외부 Caddy 중 한 곳에 `encode zstd gzip`을 적용하고 실제
  `Content-Encoding` 및 전송 크기를 재검증한다.

### P2 — `main` 자동 배포 전에 회귀 테스트·의존성 감사 게이트 없음

- 저장소의 GitHub Actions workflow는 `.github/workflows/deploy.yml` 하나뿐이다.
- `main` push 시 곧바로 EC2 배포를 실행하며, 그 전에 `npm run build`, Django 테스트,
  `npm audit --omit=dev`, `manage.py check --deploy` 단계가 없다.
- Docker 이미지 빌드가 TypeScript 빌드는 간접 검증하지만 1,809개 서버 테스트와 취약점 감사는
  자동 릴리스 게이트가 아니다.
- 관련 코드: `.github/workflows/deploy.yml:14`, `.github/workflows/deploy.yml:66`.
- 제안: 별도 CI job에서 빌드·테스트·audit·배포 체크를 모두 통과해야 deploy job이 실행되게 한다.

- 영향: Docker를 쓰지 않는 개발자가 즉시 실행할 때 초기 점검이 실패한다.

## 3. 검증하지 않은 변경성 시나리오

운영 데이터 변경을 피하기 위해 아래 최종 제출은 수행하지 않았다.

- 회원가입, 비밀번호 재설정/변경, 운영자 로그인 이후 조치
- 채팅 메시지 전송과 도구 승인/거절
- 프로젝트 생성·완료·삭제, 기준 문서 실제 저장
- 파일 업로드·공유·검색 토글·재처리·삭제
- 에이전트 저장·활성화·즐겨찾기·삭제
- 커넥터 변경·폴더 저장, 스킬 생성·공유·수정·삭제

전용 QA 계정과 삭제 가능한 테스트 데이터 범위를 정하면 위 시나리오를 별도 종단 테스트로 이어갈 수 있다.

## 4. 릴리스 게이트

1. 모바일 `/documents` P1 수정 및 390px/768px 재검증
2. 오래 열린 탭의 lazy chunk 실패 복구와 이전 배포 전환 시나리오 검증
3. `react-router-dom` 7.18.2 이상으로 갱신 후 `npm audit --omit=dev`, 빌드, 전체 테스트 재실행
4. Caddy 보안 헤더와 정적 압축 추가 후 실제 응답 헤더·전송 크기 재검증
5. CI에 빌드·Django 테스트·dependency audit·`check --deploy` 게이트 추가
6. 모바일 `/settings/skills` 가로 넘침 제거
7. 변경성 시나리오용 전용 QA 계정으로 최종 E2E 수행

### 빌드·회귀·배포 설정

- 프런트 프로덕션 빌드 성공.
- Django 1,809개 테스트 통과, `pip check` 통과.
- 프런트 소스에는 자동 테스트 파일이 없고 package script도 build만 있다.
- 로컬 컨테이너에서 production settings로 `manage.py check --deploy` 실행 시:
  - `security.W004`: `SECURE_HSTS_SECONDS` 미설정 — 실제 프런트/API 응답에도 HSTS가 없어 확정 이슈.
  - `security.W009`: 로컬 컨테이너의 개발용 SECRET_KEY가 약함 — AWS 환경의 실제 SECRET_KEY 강도는
    값을 읽지 않았으므로 판정하지 않음.
- 배포 스크립트는 마이그레이션 적용→서비스 교체→스키마 확인→health 순서다. 스키마 재확인이
  서비스 교체 뒤 실패할 수 있으므로, 읽기 전용 스키마 검증을 가능하면 교체 전에 수행하는 편이 안전하다.

### 재검증 증적

- 프런트 프로덕션 빌드 성공: Vite 7.3.6, 504개 모듈 변환.
- npm 전체/프로덕션 의존성 감사 모두 취약점 0건.
- Django 전체 1,811개 테스트 통과(40.966초), MIME 관련 31개 테스트 추가 재실행 통과.
- Python 컨테이너와 호스트 가상환경 모두 `pip check` 통과; 호스트 `manage.py check` 문제 없음.
- production settings `check --deploy`: `SECURE_HSTS_PRELOAD=False` 경고만 남음. HSTS preload는
  하위 도메인까지 장기간 되돌리기 어려운 정책이므로 이번 수정에서는 의도적으로 활성화하지 않았다.
- 두 Caddy 설정 문법 검증 통과. 임시 정적 서버에서 기존 해시 자산 gzip+immutable, 없는 자산
  404+no-store, robots 텍스트 응답, 잘못된 경로 HTML 404, 유효 SPA 경로 200을 확인했다.
- 로컬 브라우저에서 잘못된 경로의 전용 404 화면·title·description·canonical 제외를 확인했다.
- 390×844에서 `/`, `/login`, `/signup`, `/reset-password`의 전역 가로 넘침이 없고 주요
  독립 버튼/링크의 터치 영역이 24px 이상임을 확인했다.
- `git diff --check` 통과(Windows 줄바꿈 변환 안내만 존재), workflow YAML 파싱 통과.

### 최종 릴리스 전 남은 항목

1. 수정 커밋을 AWS에 배포한 뒤 보안 헤더, gzip/zstd, 없는 자산 404 캐시, robots, 404 상태를 실응답으로 재측정한다.
2. 로그인된 QA 계정으로 모바일 `/documents`, `/settings/skills`, 프로젝트 정렬, 모달 키보드 동작을 재확인한다.
3. 오래 열린 구버전 탭을 유지한 상태로 새 버전을 배포해 lazy chunk 복구 UI를 확인한다.
4. 데이터 변경성 시나리오는 삭제 가능한 전용 QA 데이터 범위가 정해진 뒤 수행한다.
