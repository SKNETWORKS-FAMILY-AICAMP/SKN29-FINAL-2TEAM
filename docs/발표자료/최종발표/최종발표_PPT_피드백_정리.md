# 최종 발표 PPT 기획 정리

> 2026-08-30 멘토링 회의록에서 **최종 발표 PPT에 직접 필요한 내용만** 분리한 문서입니다.  
> 목적: 담당자가 근거와 스토리라인을 전달하고, PPT 총괄이 하나의 발표 흐름으로 통합합니다.

## 1. 발표 한 문장

비개발자도 Agent를 구성·운영할 수 있는 플랫폼에 문서 파싱 보강과 실행 검증 체계를 결합해, 실제 업무 문서 기반의 신뢰 가능한 자동화를 제공한다.

## 2. 권장 발표 스토리라인

1. **시장과 포지셔닝**: Agent Platform/업무 자동화 시장에서 해결하려는 문제와 서비스의 위치를 제시한다.
2. **핵심 사용자 경험**: 비개발자가 Agent를 정의하고 Tool을 연결해 Chat에서 실행하는 흐름을 짧게 보여준다.
3. **Deep Agent 구조**: Builder, Tool 조합, Versioning, 실행 구조의 관계를 아키텍처로 설명한다.
4. **문서 파싱 차별화**: 기본 Docling의 실패 사례를 Gate별 보완과 Before/After로 제시한다.
5. **이미지·멀티모달 연결**: Description 검색 → Metadata → 원본 Crop → VLM 답변의 설계 의도를 보여준다.
6. **플랫폼 평가**: 특정 모델의 점수가 아닌 Agent 실행의 정확성·안전성·효율을 검증한 근거를 제시한다.
7. **운영과 확장**: Admin 실제 화면, Skill의 현재 범위, Versioning의 운영 확장성을 제시한다.
8. **한계와 다음 단계**: 현재 구현 범위를 인정하고 Future Work 및 QA·Demo 안정화 계획으로 마무리한다.

## 3. 장표별 핵심 메시지와 Evidence

### 3-1. 시장 조사·포지셔닝

- 기능 나열보다, Agent 구성·운영과 업무 문서 활용에서 발생하는 단절을 해결한다는 문제 정의를 먼저 제시한다.
- 국내·글로벌 유사 제품의 강점과 비어 있는 지점을 연결해 우리 서비스의 자리를 설명한다.
- 기능 비교표보다 결론 중심의 포지셔닝 장표로 구성한다.

**Evidence**: 경쟁 제품 포지셔닝 맵 또는 간결한 비교표

### 3-2. Agent Builder와 Deep Agent Architecture

- `상태 3개`, `도구 32개`처럼 맥락 없는 숫자 강조는 제거한다.
- 핵심 메시지는 다음 흐름이다: **비개발자가 Agent를 정의 → 필요한 Tool 연결 → Version 관리 → 실제 Chat 실행**.
- Versioning은 Dev/Stage/Prod 환경으로 확장 가능한 운영 포인트이므로 유지한다.
- Agent 영역에는 Deep Agent Architecture를 직접 보여준다.

**Evidence**: Builder 흐름 화면 + Versioning 화면 + Deep Agent Architecture

### 3-3. 문서 연결과 인덱싱 UX

- 커넥터 연결 후 문서가 수집·인덱싱되고, 사용자가 상태를 확인할 수 있음을 보여준다.
- 문서 페이지를 노출한다면 인덱싱 상태 확인을 차별점으로 두고, 갱신/재동기화는 후속 UX 방향으로 연결한다.

**Evidence**: 문서 페이지 실제 Screenshot + 인덱싱 상태

### 3-4. 문서 파싱: Gate별 문제 → 보완 → 결과 → 평가

- 단순 Architecture 소개가 아니라, 기본 Docling 결과의 실패 사례와 보완 Layer의 역할을 대응시킨다.
- 흐름: `Reading Order/Heading → Table Gate → Picture 보강 → Description Quality Gate → Chunking/Serialization`.
- 파라미터는 대표 1~2개만 설명한다.
  - `max_new_tokens=224`: 반복·Context Echo 완화
  - `temperature=0`, `do_sample=false`: 출력 일관성 확보
- 이 값은 제한된 브로슈어 샘플을 바탕으로 한 휴리스틱 실험값이며, 대규모 데이터에서 재튜닝이 필요함을 먼저 밝힌다.

**Evidence**: Before/After 예시 + Pipeline 그림 + 기본 Docling 대비 처리 시간/품질 비교

### 3-5. 이미지 검색과 멀티모달 답변

- Picture Description은 검색용 텍스트로 임베딩한다.
- 검색된 후보는 문서·페이지·BBox 메타데이터로 원본 Crop을 역추적한다.
- 답변에는 Description만이 아니라 실제 Crop Image를 Vision/VLM 모델에 전달하는 것이 설계 목표다.
- 모든 OpenAI-compatible 모델이 이미지 입력을 지원하지 않으므로 Admin/Runtime의 Vision Capability Check가 필요하다.

**Evidence**: `Description → Metadata → Crop → VLM` 흐름도 + Vision Capability 표시 화면

### 3-6. 플랫폼 평가

- 평가 대상은 특정 LLM의 지능이 아니라, 사용자가 만든 Agent가 플랫폼에서 올바르고 안전하며 효율적으로 실행되는지다.
- 결정론적 Rule/Assertion으로 다음을 확인한다.
  - 정상 종료와 답변 존재 여부
  - 필수 Tool 호출 및 허용 Tool 사용 여부
  - 중복 호출, 문서 사용, 데이터 유출 등 시나리오별 조건
- 동일 시나리오를 3회 반복해 출력 변동을 기록한다.
- LLM-as-a-Judge, Phoenix/OpenTelemetry, garak은 각각 보조 품질 평가·관측·보안 검증의 역할로 구분한다.
- 발표에서는 DB 컬럼과 영문 Evaluator 명칭 대신 쉬운 한국어로 **평가 목적 → 기준 → 결과 → 의미**를 보여준다.

**Evidence**: Rule 기반 항목 + 반복 시나리오 결과 + Phoenix Trace 요약

### 3-7. Skill과 Admin 운영

- 현재 Skill은 `생성 → Store 저장 → 팀 공유 → / 명시 호출`이 가능한 **Skill/Shortcut**이다.
- Query 의도에 따른 자동 Trigger/Hook은 현재 구현이 아니므로 Future Work로 분리한다.
- Admin은 실행·모델·Tool 상태를 관리하는 실제 화면을 제시한다.
- 근거 없는 최근 30일·실행 수·Tool 수는 제거한다. 실제 테스트 규모를 보일 때는 개발 과정의 증거라는 맥락을 함께 제공한다.

**Evidence**: Skill 생성/공유 화면 + 현재 한계/Future Work + Admin 실제 Screenshot

| --- | --- |
| 추가 | 시장 조사·경쟁 제품 포지셔닝, Deep Agent Architecture, Admin 실제 Screenshot |

## 5. 발표에서 먼저 인정할 한계와 Future Work

1. **문장 단위 Citation**: 답변의 주장과 근거 문서를 직접 연결
2. **Table False Negative**: 도형으로 그린 표 등 실제 표를 인식하지 못하는 사례 보완
3. **Description Gate 과삭제**: 정상 이미지 설명의 과삭제를 줄일 품질 기준과 Fallback 마련
4. **모델 Capability Routing**: Vision 지원 모델에만 Crop Image를 전달하도록 Admin/Runtime 연계
5. **Table Serialization Routing**: Markdown·Triplet·Crop+VLM을 표 복잡도에 따라 선택
6. **MCP Context Budget**: Unique Tool 수, Loop, Token/Context 사용량을 제어·요약
7. **자동 Skill Trigger**: 명시 호출 외 Query 의도 기반 Hook/Router 구현
8. **대규모 Evaluation**: 제한된 샘플의 휴리스틱을 다양한 문서·질문으로 검증

## 7. 최종 점검 체크리스트

- 각 장표가 기능 소개를 넘어 “왜 이 기능이 중요한가”에 답하는가
- 모든 숫자·지표에 출처, 기간, 측정 조건 또는 개발 과정의 맥락이 있는가
- 문서 파싱에서 Gate별 Failure Case와 Before/After가 연결되어 있는가
- 평가가 모델 점수 경쟁이 아니라 플랫폼 동작 검증임을 분명히 했는가
- 현재 구현, 설계 목표, Future Work를 혼동하지 않았는가
- Demo와 Screenshot이 실제 동작·현재 화면과 일치하며 QA가 완료되었는가

## 8. 추가 멘토링 반영: 장표 재구성 상세 지침

### 8-1. 도입부: 프로젝트 개요보다 시장·제품화 맥락을 먼저 제시

- 발표 초반은 “프로젝트 개요”부터 시작하지 않는다. **어떤 시장을 겨냥하고, 왜 지금 이 제품을 만들며, 왜 제품화할 가치가 있는가**를 먼저 설명한다.
- 기업의 AX 전환 흐름과 Agent Platform/업무 자동화 시장을 간략히 제시한 뒤, 조사한 실서비스 경쟁 제품 1~2개를 넣는다.
- 시장·경쟁 제품에서 확인한 공백을 우리 플랫폼의 문서 파싱, Agent 구성·운영, 실행 검증 차별점으로 연결한다.
- 시장 조사 파트는 전체 발표에서 약 3~4분 내로 마무리한다.

### 8-2. Agent 파트: 전체 아키텍처 → 사용자 시나리오 → 실제 화면

- 기능을 장표별로 나열하지 않는다. 먼저 **Deep Agent = Agent Harness(실행 프레임워크)** 라는 점과 전체 Agent 워크플로우를 설명한다.
- `Agent Runtime`을 블랙박스로 두지 말고, 내부의 주요 레이어를 연다.
  - Context Offloading: 오래된 대화·큰 결과·작업 파일을 요약하거나 가상 파일로 분리
  - Todo/Planning: 다단계 실행 계획 관리
  - Sub-agent: 위임 Task 처리
  - Skill/Memory: 재사용 가능한 지식과 실행 맥락 연결
- 새 Agent를 만들 때 Tool·Sub-agent 구성이 그래프에 붙고, 실행 중 Tool 호출에 따라 구조가 확장되는 동적인 그림으로 설명한다.
- 이후 아래 두 사용자 상황을 아키텍처 위에서 따라간다.
  1. 새 Agent 생성 시 백엔드에서 일어나는 구성·등록 흐름
  2. Agent에 Query를 보냈을 때 실행·Tool 호출·응답이 만들어지는 흐름
- 각 흐름에는 실제 화면 Screenshot을 연결한다. “구조를 보여준 뒤 사용자가 이렇게 사용한다”는 순서를 지킨다.
- 기존에 12페이지에서 이미 설명한 내용을 반복하는 장표는 통합한다. `Scenario Contract`, `Runtime Contract`, `API Schema` 같은 내부 용어 위주의 장표와 별도 중복 장표는 제거한다.

### 8-3. 평가 파트: 수치 나열이 아닌 검증의 기승전결

- 평가 체계는 기술 용어 분류보다 다음 세 가지 독자가 이해할 수 있는 기준으로 제시한다.
  - **통과/실패 검사**: 필수 조건을 만족했는지
  - **정량 검사**: Tool 호출률, 오류율, 중복 호출 등 수치로 보는 결과
  - **정성 검사**: LLM-as-a-Judge와 일부 사람 검토
- “91.7% 통과”처럼 결과 수치로 시작하지 않는다. 아래 순서를 따른다.
  1. 어떤 시나리오를 평가했는가
  2. 무엇을 통과로 보았는가
  3. 버전 1·2·3에서 무엇을 추가·보완했는가
  4. 각 버전에서 어떤 결과와 실패가 나왔는가
  5. 실패가 왜 제품의 다음 과제인가
- 버전 1의 단순 Query 결과도 버리지 않는다. “단일 의미 Query에서의 기준선 평가”로 위치를 명확히 한다.
- 멀티홉 Query, 중복 호출, Token/Context 초과 등 실패 사례를 구체적으로 보여주고, 엔터프라이즈 환경에서 남는 문제 및 Future Work로 연결한다.
- `델타`, `1차 계약` 등 맥락이 불명확한 표현은 쉬운 한국어로 바꾼다.

### 8-4. 파싱 파트: Docling 선택 → As-is 한계 → 보완 Pipeline

- Docling 선정 이유는 과도한 구조적 우위 주장보다 **큰 커뮤니티, 활발한 유지보수, 빠른 커스터마이징, IBM 기반의 지속 가능성**으로 짧게 설명한다.
- 다른 도구가 “안 된다”는 식으로 설명하지 않는다. 실제 기업에서 많이 쓰는 PDF와 DOCX 가운데, 비정형성이 높은 PDF·브로슈어를 대표 실험 대상으로 선택한 이유를 설명한다.
- 권장 서사:
  1. Docling 기본 Pipeline과 정형 문서 처리 결과
  2. 브로슈어 등 자유도가 높은 문서에서 나타난 As-is 문제: 읽기 순서 오류, 이미지 누락, 구조 인식 한계
  3. 전체 보완 Pipeline을 줌아웃 그림으로 제시
  4. Reading Order, Heading, Table/Picture, Quality Gate 등 각 Layer를 확대해 문제·로직·결과를 짧게 설명
  5. As-is/To-be 비교와 최종 평가 결과
- 전체 Layer를 한 장의 아키텍처에 먼저 보여주고, 이후 각 Layer를 순차적으로 강조한다. PDF 원본 위에서 List Item, Heading, 이미지 등 실제 대상 요소도 시각적으로 표시한다.
- Gate/Feature Logic은 “20~30개 문서를 눈으로 확인했고, 반복되는 오류 조건을 기준으로 규칙을 세웠다”처럼 **발견 과정과 검증 범위**를 설명한다.
- 표본 수·라벨링·평가 조건을 설명할 수 없는 Precision 등 수치는 제거한다. 설명 가능한 최종 정성 비교 또는 검증된 정량 결과만 사용한다.
- 점수가 좋지 않은 사례는 숨기지 않는다. 효과가 증명된 문서 군집과 개선되지 않은 조건을 모두 명시하고, 추가 실험 과제로 연결한다.

### 8-5. Skill 파트: 현재 범위와 검증 결과를 분리

- 현재 구현은 자동 호출 Skill이 아니라 Shortcut에 가깝다는 표현을 유지한다.
- 회사·개인의 암묵지를 저장·공유하고, 향후 Query 의도 기반 Hook/Trigger가 이를 자동 적용하는 방향을 Future Work 장표로 분리한다.
- Skill의 효과를 발표하려면 다음과 같은 검증 지표를 준비한다.
  - Skill 생성 성공률
  - Skill 실행 성공률
  - 업무 흐름 개선 또는 Tool 호출·Prompt Token 감소
  - 대표 Task별 반복 테스트 횟수와 성공률
- 실제 결과가 충분하지 않으면 미완성 평가를 과장하지 않고, 검증 계획을 Future Work로 둔다. 검증 절차만 보여주는 장표보다 “무엇을 검증했고 어떤 결과가 나왔는가”를 우선한다.

### 8-6. 시연 영상과 발표 대본

- 시연 영상은 화면을 나열하지 않는다. `Agent 탭 진입 → Agent 생성 → 생성한 Agent에 질의 → 실행 결과 확인`이라는 하나의 시나리오로 구성한다.
- Screenshot·시연 영상·발표 대본은 같은 사용자 흐름을 가리켜야 한다.
- Mermaid와 장표 하단 대본은 AI 문장을 그대로 쓰지 말고, 처음 보는 사람에게 실제로 설명하는 발표자 말투로 다시 작성한다.

### 8-7. 이번 보완의 핵심 원칙

> **아키텍처를 먼저 세우고, 그 위에서 사용자 행동·백엔드 동작·실제 화면·평가 결과를 차례로 풀어낸다.** 기능 나열이나 숫자 중심 설명보다, 제품의 문제 해결 과정과 검증 근거가 연결되는 발표를 만든다.
