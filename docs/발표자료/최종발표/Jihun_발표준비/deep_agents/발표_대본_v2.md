## 바뀐 점 요약

- 오프닝 슬라이드 신설 — "에이전트를 만들 때 / 쿼리할 때" 두 상황을 걸고 시작한다.
- 전체 파이프라인 슬라이드 신설 — 요청 도착부터 결과까지 전체 흐름을 먼저 보여준다.
- Architecture 슬라이드 — 딥에이전트가 하네스라는 점을 먼저 명시하고, Agent Runtime 블랙박스를 열어 컨텍스트 정리·할 일 기록·개인 기억·팀 지침 네 레이어와 위임 구조를 보여준다. 이 그림이 요청마다 다시 조립된다는 점도 여기서 설명한다.
- Builder 슬라이드 — Version 저장이 Runtime 그림을 그 자리에서 바꾸지 않는다는 점은 Architecture 슬라이드에서 완결한다(Builder 슬라이드에서는 예고하지 않음 — 청자가 아직 못 본 그림을 미리 언급하면 혼란스럽다는 피드백 반영).
- 기업 시스템 연결 / 업무 실행 및 결과물 슬라이드 — 파이프라인의 가드레일 검사·승인 대기 노드를 다시 짚어 주는 문장을 추가해 슬라이드 간 연결을 살렸다.
- 최종 순서: 오프닝 → Agent Builder → 기업 시스템 연결 → 전체 파이프라인 → Deep Agent Architecture → 업무 실행 및 결과물 → 실행 상태 관리. Builder 다음에 기업 시스템 연결을 배치해 "무엇을 붙일 수 있는지(도구·서브 Agent) → 어디에 연결하는지(모델·MCP·가드레일) → 그걸로 쿼리하면 어떤 흐름을 타는지" 순으로 이어지도록 재구성 — Builder / 기업 시스템 연결 / 전체 파이프라인 세 슬라이드의 연결 문장을 이 순서에 맞춰 다시 조정.

## 전체 발표 대본

### 1. 오프닝

> 지금부터 새 에이전트를 만들거나, 만들어 둔 에이전트에 쿼리를 날렸을 때 어떤 요청이 진행되고 백엔드에서 어떤 이벤트가 발생하는지 설명하겠습니다. 두 상황 다 결과적으로는 같은 지점에서 갈리는데, 순서대로 하나씩 보여드리겠습니다.

### 2. Agent Builder

> 에이전트를 만드는 과정은 이 흐름 하나로 이어집니다. 먼저 업무 담당자가 이 Agent의 역할과 행동 기준을 자연어로 적고 사용할 모델을 고릅니다. 다음으로 필요한 내장 Tool과 기업 MCP Tool, 전문 서브 Agent를 연결합니다. 저장하면 기존 설정을 덮어쓰지 않고 새 Version이 생깁니다. 기존 대화와 상위 Agent는 참조하던 Version을 그대로 쓰기 때문에 운영 중인 업무가 갑자기 바뀌지 않습니다. 활성화한 Agent는 같은 제품의 Chat에서 선택해 실제 요청으로 바로 사용할 수 있습니다.
>
> Builder에서 고르는 기업 Tool과 모델은 현업 담당자가 직접 서버 주소와 인증 정보를 입력하는 방식이 아닙니다.

### 3. 기업 시스템 연결

> 기업에서 운영 중인 모델 Endpoint와 MCP Tool 서버도 연결할 수 있습니다. 운영자가 모델과 MCP, 기업 가드레일을 등록하고 실제로 연결되는지 확인한 뒤 사용할 팀을 지정합니다. 업무 담당자는 서버 주소나 인증 키를 다루지 않고 Builder에서 허용된 모델과 Tool만 고릅니다. MCP로 제공되는 Jira나 사내 업무 시스템도 일반 Tool처럼 Agent에 붙일 수 있습니다. 가드레일은 모든 Chat 요청이 Agent에 들어가기 전에 거치는 팀 단위 검사입니다.
>
> 이렇게 구성한 Agent에게 실제로 질문을 보내면 어떤 흐름을 타는지 보여드리겠습니다.

### 4. 전체 파이프라인

> 요청이 도착하면 먼저 누가 보냈는지 확인하고, 채팅 내용 중 민감정보를 가립니다. 그다음 방금 등록한 가드레일이 이 요청을 검사합니다. 이건 저희가 만든 로직이 아니라 팀이 등록한 외부 검사 서비스입니다. 가드레일 검사가 완료되면 통과한 요청만 대화 이력에 저장되고, 이 에이전트의 현재 설정을 읽어서 Runtime을 새로 조립합니다. 조립이 끝나면 실행이 시작되고, 판단과 도구 호출을 반복하다가 답변 완료, 승인 대기, 오류 중 하나로 끝납니다. 승인 대기는 종료가 아니라 잠깐 멈춘 상태라, 사용자가 결정을 내리면 같은 실행을 이어서 진행합니다.
>
> 지금 "Runtime 조립"과 "실행", 이 두 칸이 가장 자세히 볼 부분입니다. 이 두 칸의 재료 — 도구와 서브 Agent는 방금 Builder에서, 모델과 MCP는 방금 기업 시스템 연결에서 이미 정해졌습니다.

### 5. Deep Agent Architecture (하네스 + Agent Runtime 열기)

> 이 두 칸을 채우는 건 저희가 직접 짠 실행 루프가 아닙니다. 코덱스나 클로드코드가 에이전트를 실행하는 하네스인 것처럼, 저희도 딥에이전트라는 하네스 위에 이 제품을 얹었습니다. 이 하네스가 기본으로 해주는 일은 크게 두 가지입니다. 에이전트에 Tool을 붙일 수 있게 해주고, 다른 전문 에이전트를 붙일 수 있게 해줍니다. 아까 Builder에서 업무 담당자가 Tool과 서브 Agent를 고르는 것도, 결국 이 하네스가 열어 둔 두 확장점 위에서 이뤄지는 겁니다.
>
> 그럼 이 판단이 실제로 어떻게 도는지 보여드리겠습니다. 이 판단은 혼자 도는 게 아닙니다. 네 가지가 항상 옆에 붙어서 돕습니다. 대화가 길어지면 오래된 부분은 요약하고, 결과물이 크면 대화 밖 파일로 빼서 컨텍스트를 가볍게 유지합니다. 여러 단계짜리 작업을 할 때는 할 일을 스스로 적어두고 순서를 놓치지 않습니다. 이 사용자가 다른 대화에서 말한 선호나 말투도 기억하고 있고, 팀이 정해둔 재사용 가능한 업무 절차도 참고합니다. 이 네 가지를 참고해서 Root는 매 순간 조사가 필요하면 조사 전용 에이전트나 전문 에이전트에 맡기고, 단순한 건 직접 도구를 불러 처리합니다. 결과는 항상 다시 Root로 돌아와서 다음에 뭘 할지 다시 판단하는 재료가 됩니다.
>
> 그리고 이 그림은 고정된 그림이 아닙니다. Builder에서 새 Version을 저장하는 순간 이 그림이 바로 바뀌는 건 아니고, 이 에이전트로 다음 질문이 들어오는 순간 그 Version이 반영돼서 다시 조립됩니다. 즉 여러분이 지금 Builder에서 도구 하나를 추가하고 나면, 다음 질문을 던지는 순간 이 그림에 그 도구가 그대로 반영돼서 다시 그려지는 겁니다.
>
> 그럼 이렇게 위임되거나 직접 실행되는 도구들이, 실제로 어떤 결과물을 만들어내는지 보여드리겠습니다.

### 6. 업무 실행 및 결과물

> Agent는 답만 쓰는 것이 아니라 실제 업무 결과를 만듭니다. Root나 전문 Agent가 허용된 Tool을 고르면 서버가 계정과 팀, 프로젝트 범위를 넣고 권한을 확인한 뒤 실행합니다. 결과는 Word, Excel, PDF 같은 파일이 될 수도 있고 Jira 이슈나 업무 DB 반영이 될 수도 있습니다. 외부 상태를 바꾸는 작업만 실행 직전에 사용자가 내용을 확인합니다 — 아까 파이프라인에서 본 승인 대기가 바로 이 지점입니다. 같은 호출이 다시 들어와도 한 번만 실행해 중복 등록을 막습니다.
>
> 요청마다 실행 환경을 새로 만들더라도 대화와 사용자 선호, 실행 근거까지 매번 사라져서는 안 됩니다.

### 7. 실행 상태 관리

> 이 그림 전체는 아까 말씀드린 것처럼 요청이 올 때마다 저장된 Version과 현재 연결된 모델·MCP를 읽어 다시 조립됩니다. 그런데 그때마다 매번 처음부터 시작하는 건 아닙니다. 대화 메시지와 할 일, 중단된 위치는 Checkpoint에 남아서 다음 요청에도 그대로 이어집니다. 개인 기억은 아까 보여드린 그대로 다른 대화에서도 유지되고요. 실행 중에는 Root와 전문 Agent, Tool이 거쳐간 경로와 출처, 지연, 오류까지 Trace로 남습니다.

## Q&A 추가 (5번 슬라이드용 — `deep_agent.md`의 Q&A 대비 섹션에 이어 붙일 것)

**이 네 레이어를 직접 만든 건가요?**

아니다. 컨텍스트 정리, 할 일 기록, 개인 기억, 팀 지침, 위임 구조는 딥에이전트(하네스)가 기본으로 제공하는 것이고, 우리는 그 위에 개인/팀 범위 격리와 쓰기 방어 같은 조건만 얹었다.

**컨텍스트 정리는 정확히 언제 개입하나요?**

몇 토큰부터 대화 밖으로 빼는지는 하네스 내부 로직이라 우리가 임의로 조정하지 않고 기본값을 그대로 쓴다. 계측 없이 손대지 않았다는 것이 정확한 현재 상태다.

**전문 에이전트가 또 다른 에이전트를 부를 수 있나요?**

아니다. 위임은 1단계로 막혀 있다. GP와 전문 Agent 모두 재위임 기능이 없다.

**"할 일 기록"이 팀에 보이는 업무 목록인가요?**

아니다. 이 대화 안에서만 보이는 개인 메모다. 팀이 보는 실제 업무 등록·업데이트 기능과는 별개다.
