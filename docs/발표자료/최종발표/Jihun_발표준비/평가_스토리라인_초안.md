## 0. 발표에서 지켜야 할 사실 경계

이 평가 파트에는 성격이 다른 세 트랙이 있다. 하나의 점수나 연속된 데이터셋처럼 합치지 않는다 — 이
원칙은 지훈 담당분과 검색 트랙이 나중에 한 슬라이드로 합쳐질 때도 반드시 유지돼야 한다.

| 트랙 | 무엇을 재는가 | 정본 | 공식 성적 여부 |
|---|---|---|---|
| 검색 품질 평가 (팀원 담당) | 파싱·청킹·임베딩 후 정답 근거를 검색하는 능력 | `tests/eval/` | 검색 품질 실측 |
| **Agent Eval V2 (지훈 담당)** | Agent의 과업 수행·근거·안전·복구·격리·위임 | `설계/eval/v2/`, `outputs/eval-v2-results/` | DEV 공식 판정 |
| **보조·보안 실험 (지훈 담당)** | Ragas·DeepEval·Phoenix·Garak으로 추가 관찰 | `experiments/otel_eval_lab/` | 비공식, V2 점수와 분리 |

Agent Eval V2는 별도의 fixture·gold 계약을 사용한다. 검색 골든셋이나 업무추출 부록을 V2의 정답지라고
설명하지 않는다. Ragas·DeepEval·Garak 결과도 V2의 PASS/FAIL을 변경하지 않는다.

## 1. 전체 스토리 한 줄 (도입부 — 발표자 조율 필요)

> 중간평가에서 받은 “동작은 확인했는데 얼마나 잘 동작하는지는 어떻게 아는가”라는 질문에 답하기 위해,
> 검색 품질은 정답 근거 검색률로 측정하고 Agent 전체 행동은 재현 가능한 위험 시나리오와 Hard Gate로
> 평가했습니다.

이 도입 슬라이드는 두 트랙을 함께 소개하므로 **누가 말할지(지훈 vs 검색 담당자) 팀과 조율 필요**.
아래 본문부터는 지훈 담당분만 상세하게 다룬다.

```text
중간평가 피드백: 검색·추천 정량 근거 부족
→ 측정 원칙과 실패 위험을 먼저 정의
→ 검색 품질(팀원)과 Agent 행동(지훈)을 분리 측정
→ 성공뿐 아니라 실패·무효·미실행 범위도 함께 공개
```

“9일 만에 평가 인프라를 처음부터 만들었다”라고 과장하지 않는다. 정확한 표현은 다음과 같다.

> 8월 10일 측정 원칙을 설계했고, 중간평가 피드백 이후 8월 24~28일에 실행 가능한 Agent 평가 체계로
> 구체화했습니다. (검색 품질 하네스는 별도 담당자가 같은 기간 병행했다.)

### 판정 흐름

```text
입력·증거 유효성
→ Hard Gate
→ deterministic observable
→ 필수 LLM Judge 실행
→ deterministic/Judge FAIL·UNCERTAIN 합성
→ 최종 PASS
```

| 판정 요소 | 담당 |
|---|---|
| 권한·승인·외부 부작용·격리·비밀 노출 | 결정론적 검사와 Hard Gate |
| 의미 정확성·근거 표현·불확실성 | 고정된 LLM Judge |
| Judge/fixture/수집기 장애 | `INVALID_EVALUATION_INFRA`로 Candidate FAIL과 분리 |

Judge는 `gpt-5.6-sol`, reasoning `medium`, strict parser로 고정했다. Judge는 Hard Gate나 결정론적
사실을 뒤집지 못한다.

# Q&A 대비 (지훈 담당분만)

> 검색 트랙 관련 질문(구 Q1 "문서 8종·질의 37건이면 너무 작지 않나", 구 Q2 "Recall@5 94.6%면 해결된
> 것 아닌가")은 팀원 담당이라 이 문서에서 뺐다. 그 질문이 나오면 검색 담당자에게 넘긴다.

## Q1. V1과 V2 결과를 왜 합치지 않았나?

“판정 계약과 fixture, Candidate, Git commit이 다르기 때문입니다. 서로 다른 모집단을 합치면 통과율의
의미가 없어집니다. V1은 평가 계약을 발견한 LEGACY 증거로 보존하고, V2는 동결된 조건의 36건만 공식
Core DEV 분모로 사용했습니다.”

## Q2. 왜 모든 것을 LLM Judge로 평가하지 않았나?

“다른 계정 데이터 접근, 승인 없는 외부 변경, canary 노출은 로그와 외부 상태로 확정할 수 있습니다.
이런 사실을 비결정적인 Judge에 맡기지 않고 코드와 Hard Gate로 판정했습니다. Judge는 의미 정확성과
근거 표현처럼 코드로 확정하기 어려운 부분만 담당합니다.”

## Q3. 88.9%면 Agent가 충분히 좋다고 볼 수 있나?

“현재 수치는 DEV 36건의 진단 결과입니다. S01은 3회 모두 실패했고 S06도 1회 실패했습니다. HOLDOUT이
없으므로 일반화 성능으로 표현하지 않습니다.”

## Q4. S10·S11 12/12 PASS면 격리와 위임은 안전한가?

“현재 고정 fixture의 작은 Expansion 표본에서는 모두 통과했습니다. 장기 안정성이나 모든 공격에 대한
안전을 증명한 것은 아니며 Core 통과율에도 합치지 않았습니다.”

## Q5. Garak 결과는 Agent가 순정 모델보다 안전하다는 뜻인가?

“그렇게 결론 내릴 수 없습니다. 모델과 보호 계층, 도구 구성이 다르고 표본도 3건입니다. 순정 모델의
공격 문자열 출력과 격리 Agent의 미출력을 각각 관측했을 뿐, 직접적인 A/B 성능 비교나 공식 보안
성적으로 사용하지 않았습니다.”

## Q6. Ragas·DeepEval 점수를 왜 공식 점수에 넣지 않았나?

“범용 지표는 도메인 안전 규칙을 알지 못합니다. 실제로 안전한 거절·부재 응답을 낮게 평가한 사례도
있었습니다. 그래서 V2의 도메인 판정은 유지하고, 범용 지표는 원인 분석용 보조 신호로만 사용했습니다.”

## Q7. 사람 평가는 했나?

“LEGACY 단계에는 Judge calibration을 위한 사람 검수 자료가 있었지만, V2 공식 점수에는 사람 판정이
들어가지 않았습니다. 향후 Phoenix의 HUMAN annotation 경로와 비공개 HOLDOUT을 결합하는 것이 남은
과제입니다.”

## Q8. 가장 먼저 고칠 것은 무엇인가?

“Agent에서는 S01의 WBS 상위 행·하위 표 관계 보존입니다. 그다음 Candidate를 동결하고 비공개
HOLDOUT으로 일반화를 확인해야 합니다.” (검색 쪽 우선순위는 담당자 확인 필요)
