# 에이전트 발표 — 슬라이드 구성과 대본

> 참고 문서: [00_에이전트_설명.md](00_에이전트_설명.md), [00_에이전트_내부_동작_상세_설명.md](00_에이전트_내부_동작_상세_설명.md), [07_에이전트_흐름_발표_슬라이드_구성.md](07_에이전트_흐름_발표_슬라이드_구성.md)  
> 전체 발표 안의 에이전트 파트다. 에이전트의 정의, 시작 페이지, 별도 요약 페이지는 만들지 않는다.  
> 본문은 5장으로 구성한다.

---

## 본문 구성

1. **Agent Builder** — 비개발자가 업무 방식을 정의하고 Tool·Child를 연결해 Version 발행과 Chat 실행까지 이어 간다.
2. **기업 시스템 연결** — 운영자가 사내 모델·MCP·가드레일을 팀 실행 환경에 붙인다.
3. **Deep Agent Architecture** — Root 아래에서 GP, 전문 Agent, Tool이 역할을 나눠 실행한다.
4. **업무 실행 및 결과물** — 허용된 Tool로 파일과 업무 데이터를 만들고 변경 작업만 통제한다.
5. **실행 상태 관리** — Runtime은 새로 조립하면서 대화 상태와 개인 기억, 실행 기록은 이어 간다.

이 순서는 `만들기 → 기업 환경 연결 → 내부 실행 → 실제 결과 → 운영 지속성`으로 이어진다.

---

# 슬라이드 1 — Agent Builder

## 전달할 내용

업무 담당자가 자연어로 Agent의 역할을 정하고 필요한 실행 자원을 고른다. 저장할 때는 기존 구성을 덮어쓰지 않고 새 Version을 만든다. 활성화한 Agent는 같은 제품의 Chat에서 선택해 실제 요청으로 쓴다.

## 제목

**`Agent Builder`**

## 화면 구성

제품 스크린샷은 사용하지 않는다. 4단계 프로세스를 슬라이드 전체 폭으로 크게 그린다. 각 단계에는 화면 필드명이 아니라 사용자가 실제로 정하는 내용만 넣는다.

```text
① 업무 정의                  ② 실행 자원 연결
   역할과 행동 지침             내장 Tool
   사용할 모델                  기업 MCP Tool
   응답 방식                    전문 Child Agent

          ───────────────────────────▶

③ Version 발행              ④ Chat 실행
   수정할 때 새 Version 생성       Agent 선택·활성화
   기존 참조는 그대로 유지         실제 요청으로 바로 사용
```

### 실제 배치

- 네 단계를 가로로 늘어놓되 카드 네 개처럼 보이지 않게 한다. 단계명과 보조 문구를 선 위에 직접 배치한다.
- `업무 정의 → 실행 자원 연결`은 사람이 구성하는 구간이다.
- `Version 발행`에서는 기존 선이 남고 새 선이 갈라지는 작은 분기만 넣는다. Version을 덮어쓰지 않는다는 뜻이다.
- 마지막은 Chat 말풍선 아이콘 하나로 끝낸다. 제품 화면은 넣지 않는다.
- 각 단계 설명은 두 줄을 넘기지 않는다.
- 하단 효과 문구나 별도 요약 박스는 두지 않는다. 프로세스만 보고도 정의부터 실행까지 이어지는 것을 알 수 있어야 한다.

## 대본

> 에이전트를 만드는 과정은 이 흐름 하나로 이어집니다. 먼저 업무 담당자가 이 Agent의 역할과 행동 기준을 자연어로 적고 사용할 모델을 고릅니다. 다음으로 필요한 내장 Tool과 기업 MCP Tool, 전문 Child Agent를 연결합니다. 저장하면 기존 설정을 덮어쓰지 않고 새 Version이 생깁니다. 기존 대화와 상위 Agent는 참조하던 Version을 그대로 쓰기 때문에 운영 중인 업무가 갑자기 바뀌지 않습니다. 활성화한 Agent는 같은 제품의 Chat에서 선택해 실제 요청으로 바로 사용할 수 있습니다.

## 발표자가 알고 있어야 할 사실

- Builder에서 이름, 설명, System Prompt, 모델, 추론 강도, 반복 한도, Tool, Child Agent를 정한다.
- 업무 담당자는 운영자가 연결해 둔 MCP Tool을 Builder의 `커스텀 도구` 목록에서 선택한다.
- 저장할 때마다 새 불변 Version이 생긴다. 이전 Version의 내용을 수정하지 않는다.
- 상위 Agent가 쓰는 Child는 선택 당시 Version에 고정된다.
- 특정 Agent로 만든 대화도 생성 당시 Version을 유지한다.
- 팀 기본 Chat Agent는 예외적으로 현재 Live Version을 매 요청 확인한다.
- Version 비교, 이전 Version 선택, 즉시 롤백, Dev·Stage·Prod 승격 화면은 현재 구현 범위가 아니다.

## 다음 장 연결

> Builder에서 고르는 기업 Tool과 모델은 현업 담당자가 직접 서버 주소와 인증 정보를 입력하는 방식이 아닙니다.

# 슬라이드 2 — 기업 시스템 연결

## 전달할 내용

운영자가 기업이 이미 쓰는 모델 Endpoint, MCP Tool 서버, 외부 가드레일을 등록하고 실제 연결 여부를 확인한다. 연결된 자원은 팀 범위 안에서만 사용한다. 업무 담당자는 승인된 자원만 Builder와 Chat에서 고른다.

## 제목

**`기업 시스템 연결`**

## 화면 구성

운영자에서 팀 Agent 실행으로 내려가는 한 방향 구조를 사용한다.

```text
                         기업 운영자
                    등록 · 연결 확인 · 팀 지정
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
        사내 모델 Endpoint   MCP Tool 서버     기업 가드레일
        팀 모델로 사용       업무 시스템 연결    모든 요청 사전 검사
              └───────────────┼───────────────┘
                              ▼
                         팀 실행 환경
                              │
                 Builder에서 모델·Tool 선택
                 Chat 요청은 가드레일을 먼저 통과
```

### 실제 배치

- 위에 `기업 운영자`, 가운데 연결 대상 세 가지, 아래에 `팀 실행 환경`을 둔다.
- 세 연결 대상을 독립된 효과 카드처럼 꾸미지 않는다. 운영자와 팀 사이에 놓인 연결 지점으로 그린다.
- `등록 · 연결 확인 · 팀 지정`은 운영자 바로 아래에 붙인다.
- `Builder에서 선택`과 `Chat 요청 사전 검사`는 팀 실행 환경에서 갈라지는 두 동작으로 표현한다.
- 제품 화면이나 공급자 로고는 넣지 않는다. 특정 벤더에 종속된 인상을 줄 필요가 없다.

## 대본

> 기업에서 운영 중인 모델 Endpoint와 MCP Tool 서버도 연결할 수 있습니다. 운영자가 모델과 MCP, 기업 가드레일을 등록하고 실제로 연결되는지 확인한 뒤 사용할 팀을 지정합니다. 업무 담당자는 서버 주소나 인증 키를 다루지 않고 Builder에서 허용된 모델과 Tool만 고릅니다. MCP로 제공되는 Jira나 사내 업무 시스템도 일반 Tool처럼 Agent에 붙일 수 있습니다. 가드레일은 Agent 안에서 선택하는 Tool이 아니라 모든 Chat 요청이 Agent에 들어가기 전에 거치는 팀 단위 검사입니다.

## 기업에서 의미가 있는 이유

- 기존 업무 시스템을 새 제품으로 옮기지 않고 MCP로 연결한다.
- Endpoint와 인증 정보는 운영자가 관리하고 현업에는 사용 가능한 자원만 보인다.
- 가드레일도 플랫폼이 정한 하나의 정책만 강제하지 않고 기업이 이미 운용하는 공급자를 팀별로 적용한다.
- 모델, Tool, 가드레일의 사용 범위를 팀 단위로 나눌 수 있다.

## 발표자가 알고 있어야 할 사실

- MCP와 가드레일은 팀 사용자가 직접 등록하지 않는다. 운영자 콘솔에서 등록한다.
- 등록 전에 Endpoint와 자격 정보를 사용해 실제 연결 확인을 한다.
- MCP 서버에서 읽어 온 Tool은 Agent Builder의 커스텀 도구 선택 목록에 들어간다.
- Runtime은 Agent Version의 Tool 참조와 현재 팀 MCP 목록을 합쳐 실행 Tool을 만든다.
- 기업 가드레일은 OpenAI Guardrails, Azure AI Content Safety, AWS Bedrock Guardrails 연결을 지원한다.
- 팀당 활성 외부 가드레일 하나를 사용한다.
- 가드레일 공급자 장애 시 계속 실행할지 차단할지는 팀별로 정한다. 내부 업무는 업무 연속성을, 규제 업무는 차단을 우선할 수 있다.
- 기업 가드레일은 Graph 밖에서 먼저 실행한다. 차단된 요청은 대화 DB에 저장하지 않고 Agent도 부르지 않는다.

## 다음 장 연결

> 이렇게 구성한 Agent가 실제 요청을 받으면 Root가 아래 실행 자원을 골라 일을 나눕니다.

# 슬라이드 3 — Deep Agent Architecture

## 전달할 내용

Root가 매 단계에서 직접 답할지, 조사할지, 전문 Agent에 맡길지, Tool을 실행할지 정한다. GP, 전문 Agent, Tool은 모두 Root 아래에 놓이고 결과를 다시 Root로 돌려준다.

## 제목

**`Deep Agent Architecture`**

## 화면 구성

[07_에이전트_흐름_발표_슬라이드_구성.md](07_에이전트_흐름_발표_슬라이드_구성.md)의 방향을 반영해 Root를 위에, GP·전문 Agent·Tool을 아래에 둔다. Root 주변의 작은 보조 라벨은 사용하지 않는다.

```text
요청 ─────────▶ ┌──────────────────────────────┐ ─────────▶ 최종 답변
                │             Root             │
                │  판단 → 실행·위임 → 결과 종합 │
                │          → 다시 판단          │
                └──────────────┬───────────────┘
                               │
             ┌─────────────────┼─────────────────┐
             ▼                 ▼                 ▼
        범용 GP            전문 Agent           Tool
        조사·분석           전용 모델·도구        내장 Tool
        조회 전용           맡은 분야만 처리      기업 MCP Tool
             └─────────────────┴─────────────────┘
                               │
                         결과를 Root에 반환
```

### 실제 배치

- Root를 슬라이드 상단 중앙에 가장 크게 둔다.
- 아래에는 `범용 GP`, `전문 Agent`, `Tool`을 같은 높이로 둔다.
- Root에서 아래로 향하는 선과 결과가 다시 올라오는 선을 구분한다. 위임과 결과 회수의 방향이 보여야 한다.
- 전문 Agent가 여러 개라는 뜻은 박스를 늘리는 대신 `전문 Agent A · B · …`로 적는다.
- 하단에 `코드가 강제`, `권한·승인·상한` 같은 구호를 따로 붙이지 않는다. 필요한 제한은 각 요소 안에 쓴다.
- `Version 구성`, `대화 상태`, `장기 기억` 같은 Root 주변 라벨도 넣지 않는다. 상태와 메모리는 5장에서 설명한다.

## 대본

> 실행 구조는 이렇습니다. Root가 요청 전체를 보고 매 단계의 다음 행동을 정합니다. 자료 조사나 비교가 필요하면 조회 전용 GP에 맡기고, 특정 분야의 전문 작업은 그 분야 Agent에게 넘깁니다. 단순 실행은 내장 Tool이나 기업 MCP Tool을 직접 부릅니다. 전문 Agent는 자기 모델과 Tool로 맡은 일만 처리하고 GP와 전문 Agent 모두 다시 다른 Agent를 부르지는 못합니다. 결과는 Root로 돌아오고 Root가 다음 작업이 필요한지 다시 판단한 뒤 최종 답변을 만듭니다.

## 기업에서 의미가 있는 이유

- 사용자가 `문서 검색 → 업무 추출 → Jira 초안 → Excel 작성`의 순서를 하나씩 지시하지 않아도 Root가 작업을 이어 간다.
- 전문 Agent에는 맡은 업무에 필요한 모델과 Tool만 준다. 모든 Agent에 같은 권한을 열지 않는다.
- GP는 조회 Tool만 받아 조사 과정에서 Jira나 업무 DB를 바꿀 수 없다.
- 위임을 Root 아래 한 단계로 제한해 순환 호출과 실행 증가를 막는다.

## 발표자가 알고 있어야 할 사실

- 앞단 의도 분류 모델은 없다. Root가 매 반복에서 직접 답변, Tool 호출, 전문 Agent 위임, GP 위임을 고른다.
- 전문 Agent는 자신의 Version에 저장된 모델, Prompt, Tool을 사용한다.
- 전문 Agent에는 Root의 장기 기억과 개인 스킬이 자동으로 전달되지 않는다.
- GP는 Root 모델을 사용하지만 Root Tool 중 `side_effect=false`인 조회·계산 Tool만 받는다.
- 전문 Agent와 GP에는 재위임 Tool이 없다.
- 하위 결과는 Tool 결과 형태로 Root에 돌아간다.

## 다음 장 연결

> Root가 고른 Tool은 답변용 정보만 조회하는 데서 끝나지 않고 실제 파일과 업무 데이터를 만듭니다.

# 슬라이드 4 — 업무 실행 및 결과물

## 전달할 내용

Agent는 허용된 Tool로 문서와 표, PDF 같은 결과물을 만들고 Jira나 업무 DB에도 작업을 반영한다. 모델이 임의 코드를 실행하는 방식이 아니라 서버가 입력 범위와 권한을 넣은 Tool만 실행한다.

HITL은 이 장의 주인공이 아니다. 상태 변경 경로에 붙은 짧은 통제 장치로만 보여 준다.

## 제목

**`업무 실행 및 결과물`**

## 화면 구성

Tool 호출에서 실제 산출물까지 한 줄로 진행하고 상태 변경만 아래로 잠깐 갈라진다.

```text
Root·전문 Agent
       │
       ▼
허용된 Tool 선택 ──▶ 입력·업무 범위 확인 ──▶ 실행 ──▶ 결과
                                            │          Word · Excel · PDF
                                            │          Jira · 업무 DB
                                            │
                              상태 변경이면 사용자 확인
                              동일 호출은 한 번만 실행
```

### 실제 배치

- 파이프라인이 슬라이드 중앙을 가로지르게 한다.
- 결과 지점에서 파일 아이콘과 Jira·DB 아이콘이 자연스럽게 퍼지게 한다.
- 상태 변경 분기는 `실행` 바로 아래에 붙인다. 별도 HITL 카드로 키우지 않는다.
- `승인 / 수정 / 거절 / 응답`, `run_id`, `tool_call_id` 같은 상세값은 본문에 쓰지 않는다.
- 내장 Tool의 개수나 라이브러리 이름은 넣지 않는다.

## 대본

> Agent는 답만 쓰는 것이 아니라 실제 업무 결과를 만듭니다. Root나 전문 Agent가 허용된 Tool을 고르면 서버가 계정과 팀, 프로젝트 범위를 넣고 권한을 확인한 뒤 실행합니다. 결과는 Word, Excel, PDF 같은 파일이 될 수도 있고 Jira 이슈나 업무 DB 반영이 될 수도 있습니다. 외부 상태를 바꾸는 작업만 실행 직전에 사용자가 내용을 확인합니다. 승인 과정이 다시 들어와도 같은 호출은 한 번만 실행해 중복 등록을 막습니다.

## 기업에서 의미가 있는 이유

- 자연어 요청이 실제 파일과 업무 시스템 변경으로 이어진다.
- 계정, 팀, 프로젝트 범위는 모델이 정하지 않고 서버가 넣는다.
- 허용된 Tool만 노출하므로 범용 Shell이나 임의 SQL 실행보다 실행 범위가 분명하다.
- 원본 파일을 직접 덮어쓰지 않고 결과를 새 산출물로 저장한다.
- Jira·업무 DB처럼 중복이 문제가 되는 작업은 동일 호출의 재실행을 막는다.

## 발표자가 알고 있어야 할 사실

- 모델은 `account_id`, `team_id`, `project_id`, `run_id`를 선택하거나 덮어쓸 수 없다.
- ToolLoader가 Agent Version의 Tool 참조와 팀 MCP Tool을 실행 가능한 Tool로 바꾼다.
- MCP 표준에는 조회와 쓰기를 나누는 공통 필드가 없어 연결된 MCP Tool은 현재 모두 변경 가능 Tool처럼 보수적으로 처리한다.
- 파일 Tool은 원본을 바꾸지 않고 새 결과 파일을 저장소에 등록한다.
- 상태 변경 Tool은 자동 재시도하지 않는다.
- 같은 실행의 같은 호출은 `(run_id, tool_call_id)`를 기준으로 성공 결과를 재사용한다.

## 다음 장 연결

> 요청마다 실행 환경을 새로 만들더라도 대화와 사용자 선호, 실행 근거까지 매번 사라져서는 안 됩니다.

# 슬라이드 5 — 실행 상태 관리

## 전달할 내용

Agent Runtime은 요청마다 현재 Version과 연결 정보를 읽어 다시 만든다. 대화 진행 상태는 Checkpoint에, 세션이 바뀌어도 기억할 개인 선호는 장기 기억 Store에, 실행 경로는 Trace에 따로 남긴다.

## 제목

**`실행 상태 관리`**

## 화면 구성

Runtime을 가운데 두고 무엇이 들어오며 무엇이 남는지 한 화면에서 보여 준다.

```text
Agent Version                  대화 Checkpoint
역할·모델·Tool·전문 Agent       메시지·할 일·중단 위치
          │                           │
          └──────────┐   ┌────────────┘
                     ▼   ▼
                요청마다 Runtime 조립
                Root · 전문 Agent · Tool
                     ▲               │
                     │               ├──▶ 실시간 진행
개인 장기 기억 Store ┘               └──▶ 실행 Trace
· 답변 형식·길이·말투·언어                Root·전문 Agent·Tool 경로
· 반복 작업 순서·확인 방식                 출처·지연·오류
· 자주 쓰는 Tool·분류 기준
· 직무·담당 영역·시간대
```

### 실제 배치

- 가운데 Runtime을 두고 왼쪽 위 `Agent Version`, 오른쪽 위 `대화 Checkpoint`, 왼쪽 아래 `개인 장기 기억 Store`가 들어오게 한다.
- 오른쪽에는 `실시간 진행`과 `실행 Trace`가 빠져나가게 한다.
- `장기 기억 Store` 아래에는 저장 내용을 실제 예시로 적는다. `개인화 정보` 같은 추상어로 끝내지 않는다.
- `팀 정책`이라는 입력은 두지 않는다.
- Store 세 개를 동일한 카드로 나란히 만들지 않는다. Runtime으로 들어오고 나가는 방향이 먼저 보여야 한다.

## 대본

> Agent 실행 객체는 서버에 계속 띄워 두지 않습니다. 요청이 올 때마다 저장된 Version과 현재 연결된 모델·MCP를 읽어 Runtime을 다시 만듭니다. 대신 대화 메시지와 할 일, 중단된 위치는 Checkpoint에 남겨 다음 요청에도 이어 갑니다. 세션이 바뀌어도 기억할 내용은 개인 장기 기억 Store에 따로 저장합니다. 답변 형식과 말투, 반복 작업 순서, 자주 쓰는 Tool과 분류 기준, 담당 업무처럼 오래 유지되는 정보만 대상입니다. 실행 중에는 Root와 전문 Agent, Tool의 경로와 출처, 지연, 오류를 Trace로 남깁니다.

## 기업에서 의미가 있는 이유

- 모델이나 MCP 연결이 바뀌면 다음 요청의 Runtime에 반영된다.
- 승인 대기나 서버 재시작이 있어도 Checkpoint에서 대화를 이어 갈 수 있다.
- 사용자 선호는 다른 대화에서도 이어지지만 팀과 Agent, 계정 범위가 다르면 서로 섞이지 않는다.
- 실행 경로와 오류를 같은 실행 단위로 볼 수 있어 운영 문제를 찾기 쉽다.

## 발표자가 알고 있어야 할 사실

- Runtime은 요청마다 다시 만들지만 PostgreSQL Store와 Checkpointer 연결 자체를 매번 새로 여는 것은 아니다.
- Checkpoint에는 Graph 구조가 아니라 메시지, 할 일, 중단 상태, 작업 파일이 저장된다.
- 장기 기억의 논리 경로는 `/memories/users/preferences.md` 하나다.
- 실제 저장 범위는 서버가 `(team_id, agent_id, account_id)`로 나눈다.
- 장기 기억은 명령이 아니라 참고 정보다. 현재 요청이나 최신 Tool 결과와 충돌하면 현재 값이 우선이다.
- 한 번만 적용할 지시, 프로젝트의 일시적 수치, 추측, 문서 원문은 장기 기억으로 저장하지 않는다.
- 저장 전 Memory Write Guard가 인증 비밀값과 개인정보를 다시 검사한다.
- 장기 기억은 Root만 읽는다. 전문 Agent와 GP에는 자동으로 전달하지 않는다.
- Trace에는 Agent Version, Root·전문 Agent 관계, 모델 공급자, Tool 호출, 출처, 지연, 오류가 남는다.

# 전체 발표 대본

## 1. Agent Builder

> 에이전트를 만드는 과정은 이 흐름 하나로 이어집니다. 먼저 업무 담당자가 이 Agent의 역할과 행동 기준을 자연어로 적고 사용할 모델을 고릅니다. 다음으로 필요한 내장 Tool과 기업 MCP Tool, 전문 Child Agent를 연결합니다. 저장하면 기존 설정을 덮어쓰지 않고 새 Version이 생깁니다. 기존 대화와 상위 Agent는 참조하던 Version을 그대로 쓰기 때문에 운영 중인 업무가 갑자기 바뀌지 않습니다. 활성화한 Agent는 같은 제품의 Chat에서 선택해 실제 요청으로 바로 사용할 수 있습니다.

## 2. 기업 시스템 연결

> 기업에서 운영 중인 모델 Endpoint와 MCP Tool 서버도 연결할 수 있습니다. 운영자가 모델과 MCP, 기업 가드레일을 등록하고 실제로 연결되는지 확인한 뒤 사용할 팀을 지정합니다. 업무 담당자는 서버 주소나 인증 키를 다루지 않고 Builder에서 허용된 모델과 Tool만 고릅니다. MCP로 제공되는 Jira나 사내 업무 시스템도 일반 Tool처럼 Agent에 붙일 수 있습니다. 가드레일은 모든 Chat 요청이 Agent에 들어가기 전에 거치는 팀 단위 검사입니다.

## 3. Deep Agent Architecture

> 실행할 때는 Root가 요청 전체를 보고 다음 행동을 정합니다. 자료 조사나 비교가 필요하면 조회 전용 GP에 맡기고 특정 분야의 전문 작업은 그 분야 Agent에게 넘깁니다. 단순 실행은 내장 Tool이나 기업 MCP Tool을 직접 부릅니다. 전문 Agent는 자기 모델과 Tool로 맡은 일만 처리하고 GP와 전문 Agent 모두 다시 다른 Agent를 부르지는 못합니다. 결과는 Root로 돌아오고 Root가 다음 작업이 필요한지 판단한 뒤 최종 답변을 만듭니다.

## 4. 업무 실행 및 결과물

> Agent는 답만 쓰는 것이 아니라 실제 업무 결과를 만듭니다. Root나 전문 Agent가 허용된 Tool을 고르면 서버가 계정과 팀, 프로젝트 범위를 넣고 권한을 확인한 뒤 실행합니다. 결과는 Word, Excel, PDF 같은 파일이 될 수도 있고 Jira 이슈나 업무 DB 반영이 될 수도 있습니다. 외부 상태를 바꾸는 작업만 실행 직전에 사용자가 내용을 확인합니다. 같은 호출이 다시 들어와도 한 번만 실행해 중복 등록을 막습니다.

## 5. 실행 상태 관리

> Agent 실행 객체는 요청이 올 때마다 저장된 Version과 현재 연결된 모델·MCP를 읽어 다시 만듭니다. 대신 대화 메시지와 할 일, 중단된 위치는 Checkpoint에 남겨 다음 요청에도 이어 갑니다. 답변 형식과 말투, 반복 작업 순서, 자주 쓰는 Tool과 분류 기준, 담당 업무처럼 오래 유지되는 정보는 개인 장기 기억 Store에 보관합니다. 실행 중에는 Root와 전문 Agent, Tool의 경로와 출처, 지연, 오류를 Trace로 남깁니다.

# Q&A 대비

## 왜 Builder와 Version을 한 장으로 합쳤나요?

Version은 현재 Builder에서 저장할 때 생기는 실행 관리 방식이다. 독립 장으로 만들 만큼 별도의 Version 비교나 승격 화면이 구현된 것은 아니다. 한 장에서 정의, 연결, 발행, Chat 실행의 연속성을 보여 주는 편이 현재 제품을 더 정확하게 설명한다.

## Dev·Stage·Prod는 무엇인가요?

Dev는 수정 중인 Agent를 시험하는 환경, Stage는 운영 전 최종 검증 환경, Prod는 사용자가 실제 업무에 쓰는 환경이다. 현재 제품 기능은 아니며 Version 구조를 앞으로 배포 승격 방식으로 확장할 수 있다는 설명에만 사용한다.

## 이전 Version으로 바로 롤백할 수 있나요?

현재 화면에는 이전 Version을 선택해 즉시 되돌리는 기능이 없다. 불변 Version 기록과 세션·Child의 Version 고정은 구현돼 있지만 롤백 UI는 확장 범위다.

## 기업 MCP는 누가 연결하나요?

운영자가 팀에 MCP 서버를 등록하고 연결을 확인한다. 연결된 서버의 Tool이 Builder 선택 목록에 들어가며 업무 담당자는 필요한 Tool만 Agent에 붙인다.

## 기업 가드레일은 Agent마다 고르나요?

아니다. 운영자가 공급자를 등록하고 팀에서 활성 가드레일을 정한다. 그 팀의 Chat 요청은 Agent가 실행되기 전에 가드레일을 먼저 거친다.

## 가드레일 연결이 실패하면 업무가 모두 멈추나요?

팀이 정한 장애 처리 방식에 따른다. 업무 연속성을 우선하면 검사 장애를 기록하고 진행하며 규제 업무처럼 검사를 통과하지 못한 요청을 보내면 안 되는 팀은 차단한다.

## 장기 기억에는 무엇을 저장하나요?

다른 대화에서도 다시 쓸 가능성이 높은 개인 선호만 저장한다. 답변 형식과 길이, 말투와 언어, 반복 작업 순서, 확인 방식, 자주 쓰는 Tool과 분류 기준, 직무와 담당 영역, 시간대가 대상이다. 일시적 수치나 문서 원문, 추측은 저장하지 않는다.

## 다른 사람의 메모리가 섞이지 않나요?

경로 문자열에 사용자 ID를 넣는 대신 서버가 팀, Agent, 계정 조합으로 저장 범위를 나눈다. 사용자가 Prompt로 다른 ID를 써도 저장 범위를 바꿀 수 없다.

## HITL을 본문에서 뺀 이유는 무엇인가요?

Agent의 가장 큰 차이는 Builder, 기업 연결, Deep Agent 실행에 있다. HITL은 변경 작업을 안전하게 붙이기 위한 통제 장치다. 본문에서는 상태 변경 Tool 아래 한 줄로 남기고 내부 방식은 부록에서 설명한다.

## 여러 Agent를 쓰면 무조건 정확해지나요?

무조건 정확해진다고 말하지 않는다. 전문 Agent가 좁은 역할과 Tool만 보도록 설계해 불필요한 컨텍스트와 권한을 줄였다. 정확도 향상을 수치로 주장하려면 별도의 평가 결과가 필요하다.

# 시각 자료 원칙

- 본문에는 제품 스크린샷을 쓰지 않는다.
- 한 장에는 한 흐름만 둔다.
- 화면을 선으로 반씩 나누지 않는다.
- 기능 그림과 기업 효과 목록을 따로 만들지 않는다. 효과가 생기는 지점에 짧은 설명을 붙인다.
- 동일한 크기의 카드 여러 개를 반복하지 않는다.
- 제목은 짧은 명사형으로 통일한다.
- 슬라이드 문구는 동작이 보이는 말로 쓴다. `정의`, `연결`, `발행`, `판단`, `실행`, `저장`, `복원`, `기록`을 우선한다.
