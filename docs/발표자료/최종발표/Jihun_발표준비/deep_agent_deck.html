활성화한 Agent를 선택해 실제 요청으로 사용

Builder에서 고르는 기업 Tool과 모델은 현업 담당자가 직접 서버 주소와 인증 정보를 입력하는 방식이 아니다.

발표 메모에이전트를 만드는 과정은 이 흐름 하나로 이어집니다. 먼저 업무 담당자가 이 Agent의 역할과 행동 기준을 자연어로 적고 사용할 모델을 고릅니다. 다음으로 필요한 내장 Tool과 기업 MCP Tool, 전문 서브 Agent를 연결합니다. 저장하면 기존 설정을 덮어쓰지 않고 새 Version이 생깁니다. 기존 대화와 상위 Agent는 참조하던 Version을 그대로 쓰기 때문에 운영 중인 업무가 갑자기 바뀌지 않습니다. 활성화한 Agent는 같은 제품의 Chat에서 선택해 실제 요청으로 바로 사용할 수 있습니다. Builder에서 고르는 기업 Tool과 모델은 현업 담당자가 직접 서버 주소와 인증 정보를 입력하는 방식이 아닙니다.

가드레일 검사 실패 시

대화 저장 이전에 요청이 그 자리에서 끝난다. 대화 이력에 남지 않는다.

발표 메모요청이 도착하면 먼저 누가 보냈는지 확인하고, 채팅 내용 중 민감정보를 가립니다. 그다음 방금 등록한 가드레일이 이 요청을 검사합니다. 이건 저희가 만든 로직이 아니라 팀이 등록한 외부 검사 서비스입니다. 가드레일 검사가 완료되면 통과한 요청만 대화 이력에 저장되고, 이 에이전트의 현재 설정을 읽어서 Runtime을 새로 조립합니다. 조립이 끝나면 실행이 시작되고, 판단과 도구 호출을 반복하다가 답변 완료, 승인 대기, 오류 중 하나로 끝납니다. 승인 대기는 종료가 아니라 잠깐 멈춘 상태라, 사용자가 결정을 내리면 같은 실행을 이어서 진행합니다.

우리의 제품 구조

우리는 Deep Agent 하네스 위에 제품을 얹었다.

발표 메모코덱스나 클로드코드는 모델이 에이전트처럼 일하도록 실행 환경을 제공하는 하네스입니다. 딥에이전트도 같은 역할을 하는 에이전트 실행 프레임워크이고, 저희는 그 위에 제품을 얹었습니다. 이 하네스가 제공하는 핵심 확장점은 두 가지입니다. 에이전트에 도구를 붙일 수 있고, 전문 역할을 맡는 서브에이전트를 붙일 수 있습니다. 사용자가 Builder에서 에이전트를 새로 만들거나 수정하면 선택한 도구와 서브에이전트 구성이 코드적으로 실행 그래프에 연결됩니다. 그래서 도구가 늘어나거나 서브에이전트가 추가되면 다음 요청의 Runtime은 그 변경된 구성으로 다시 조립됩니다.
