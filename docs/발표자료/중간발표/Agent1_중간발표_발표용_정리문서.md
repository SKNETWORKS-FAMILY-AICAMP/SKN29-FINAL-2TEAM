# Agent1 중간발표용 정리 문서

> 목적: Agent1 관련 설계·발표자료를 발표자가 짧고 정확하게 설명할 수 있도록 하나의 원고로 정리한다.
>
> 기준 자료: `docs/설계 및 구현/2_중간발표 이전/설계/에이전트1관련`의 `업무근거_` 시작 문서 4개와 로컬 `docs/발표자료`의 Agent1 발표자료를 대조해 작성했다. 기존 발표자료 원본 파일은 업로드 대상에 포함하지 않는다.

## 1. 발표 핵심 메시지

Agent1은 문서에서 실행 가능한 업무를 추출하고, 업무를 뒷받침할 근거가 부족하면 필요한 정보만 추가 검색하는 흐름이다. 문서에 없는 역할·공수·일정은 추측하지 않고 누락 상태로 남긴다.

업무량 계산은 LLM의 추론에 맡기지 않고 결정론적 계산으로 분리한다. 사람 후보 분석과 실제 업무 분배는 Agent1의 역할이 아니라 후속 Agent2·Agent3 영역으로 구분한다.

## 2. 본문 슬라이드 1 — 근거 기반 업무 추출

### 슬라이드 제목

**필요한 근거만 찾아 업무로 만든다**

### 화면에 보여줄 흐름

```text
선택한 Connector 데이터
  → 대표 문서와 초기 Chunk 확인
  → 업무 추출 Agent가 업무·조건·근거 해석
  → 근거가 부족하면 Query 생성 Agent가 검색 목적·Query 생성
  → Retriever가 허용 범위의 관련 Chunk 반환
  → 근거가 충분해질 때까지 반복
  → Task + 원문 위치 + missing_fields 반환
```

### 발표 멘트

> 사용자가 선택한 프로젝트와 문서 범위 안에서 먼저 업무 후보를 찾습니다. 역할, 공수, 일정, 완료 기준처럼 업무를 확정하는 정보가 부족하면 Query 생성 Agent가 부족한 정보에 맞춰 검색 기준을 만들고 Retriever가 관련 Chunk를 다시 가져옵니다. 최종 결과에는 실제 문서의 Chunk와 페이지 등 근거를 연결하고, 찾지 못한 값은 추측하지 않고 누락 상태로 표시합니다.

### 반드시 강조할 세 가지

1. 검색 범위는 사용자가 선택한 Connector·프로젝트 범위 안으로 제한한다.
2. 업무로 저장하려면 실행 행동과 이를 뒷받침하는 원문 근거가 모두 필요하다.
3. 업무량은 LLM이 임의로 정하지 않고 결정론적 계산 단계에서 처리한다.

## 3. 본문 슬라이드 2 — AS-IS에서 TO-BE로의 개선

### 슬라이드 제목

**문서 단위 처리에서 업무·필드 단위 근거 관리로**

| 구분 | AS-IS | TO-BE |
|---|---|---|
| 검색 단위 | 문서 전체와 여러 업무를 한 흐름에서 처리 | 업무 후보별로 필요한 필드를 수집 |
| 근거 관리 | 하나의 근거 구조에 여러 의미가 섞일 수 있음 | 역할·공수·일정 등 필드별 근거를 매핑 |
| 책임 분리 | 검색, 충분성 판단, 구조화 책임이 한 Node에 집중 | Task Extractor와 Evidence Validator를 분리 |
| 종료 조건 | 고정 Stage·검색 횟수 중심 | 근거 충족·새 결과 없음·검색 한도에 따른 종료 |
| 결과 상태 | 완성 결과와 제한 결과의 구분이 약함 | READY·LIMITED·BLOCKED 등 검증 상태로 표현 |

### 발표 멘트

> 개선의 핵심은 검색을 무조건 많이 하는 것이 아닙니다. 업무 후보별로 어떤 필드가 부족한지 확인하고, 각 필드가 어떤 원문 근거로 뒷받침되는지를 관리하는 것입니다. 이후 Evidence Validator가 근거와 결과를 분리해 검증하면, 정보가 부족한 경우에도 억지로 완성하지 않고 제한 또는 차단 상태로 반환할 수 있습니다.

## 4. 전체 Agent 구조에서의 역할 경계

```text
Agent1: 문서 업무·조건·근거 추출
  → Workload Calculator: 사람별 가용시간·업무량 결정론적 계산
  → Agent2: 후보 분석·업무 분배
  → Agent3: 분배안 검증
```

- Agent1은 문서 의미를 구조화하는 역할이다.
- Workload Calculator는 같은 입력에 같은 결과를 내야 하는 계산 영역이다.
- Agent2의 후보 분석은 People·Jira·WorkloadResult를 비교하므로 Agent1과 분리한다.
- Agent3은 분배 결과가 규칙과 근거를 만족하는지 검증한다.

## 5. 현재 범위와 미구현 범위

### 발표에서 완료로 설명할 수 있는 범위

- Agent1의 업무 추출 목적과 Node 간 책임
- 근거가 부족할 때 Query 생성 Agent와 Retriever를 연결하는 목표 흐름
- `TASK_CORE`, `ASSIGNMENT_REQUIREMENT`, `EXECUTION_CONDITION` 검색 기준
- `text`와 `raw_text`의 역할 구분
- 근거·누락 필드·검증 상태를 포함하는 Task 결과 구조
- 업무량 계산을 결정론적 단계로 분리하는 원칙

### 반드시 제한으로 표시할 범위

- 실제 pgvector Retriever의 반복 Tool 연동
- 검색 결과 State 누적·중복 제거와 검색 품질 평가셋
- 필드별 복수 근거 `evidence_refs`의 실제 Schema 반영
- Agent2 후보 분석·전체 업무 분배와 Agent3 검증
- 실제 Jira·People Repository 기반의 전체 종단 실행 검증

## 6. 예상 질문과 답변

### Q. Agent1이 사람까지 자동 배정하나요?

아닙니다. Agent1은 업무와 근거를 추출하고 결정론적 업무량 계산 결과를 전달합니다. 사람 후보 비교와 업무 분배는 후속 Agent2의 역할이며, 최종 검증은 Agent3에서 담당합니다.

### Q. 문서에 공수나 역할이 없으면 어떻게 하나요?

값을 추정하지 않고 `missing_fields` 또는 제한·차단 상태로 반환합니다. PM이 어떤 정보를 추가해야 확정할 수 있는지 확인할 수 있도록 하는 것이 목적입니다.

### Q. Retriever가 아무 Chunk나 가져오지 않도록 어떻게 하나요?

Agent가 검색 목적과 Query를 정하고, Retriever는 허용된 문서 범위 안에서 필터·검색·순위·중복 제거를 수행합니다. 결과에는 문서·Chunk·페이지와 검색 정보를 포함해 Citation 가능성을 남깁니다.

### Q. TO-BE는 이미 구현된 것인가요?

일부는 역할과 데이터 계약을 정리한 설계 방향이고, 실제 Retriever 반복 호출·복수 근거 Schema·Agent2·Agent3은 별도 구현과 검증이 필요한 후속 범위입니다. 발표에서는 구현 완료와 개선 목표를 구분해 설명합니다.

## 7. 30초 요약 멘트

> Agent1은 문서에서 근거 있는 업무를 추출하는 역할입니다. 정보가 부족하면 필요한 검색 목적과 Query를 만들어 관련 Chunk를 추가로 확인하고, 문서에 없는 값은 추측하지 않고 누락 상태로 반환합니다. 업무량은 LLM이 아니라 결정론적 계산으로 처리하며, 사람 후보 분석과 업무 분배는 후속 Agent2·Agent3으로 분리했습니다. 이번 개선 방향은 문서 전체를 한 번에 처리하는 방식에서 업무·필드별 근거를 관리하는 구조로 전환하는 것입니다.

## 8. 발표 진행 순서와 권장 시간

Agent1 파트는 전체 발표 흐름을 끊지 않도록 2개 본문 슬라이드와 짧은 로드맵 설명으로 구성한다. 구현 범위가 아닌 설계 목표를 설명할 때는 반드시 “현재 MVP”, “개선 방향”, “후속 구현”을 구분한다.

| 순서 | 시간 | 발표 내용 | 발표자가 남길 문장 |
|---:|---:|---|---|
| 전환 | 10초 | 문서에서 업무를 만드는 문제 제기 | “문서를 읽는 것과 업무로 확정하는 것은 다릅니다.” |
| 슬라이드 1 | 50~70초 | Agent1의 입력·판단·검색·결과 | “근거가 부족할 때만 필요한 정보를 더 찾습니다.” |
| 슬라이드 2 | 50~70초 | AS-IS와 TO-BE 개선 | “검색량보다 근거의 연결 단위를 개선합니다.” |
| 로드맵 | 20~30초 | Agent2·Agent3 역할 경계 | “자동 확정이 아니라 다음 판단을 위한 근거를 제공합니다.” |
| 마무리 | 10초 | 제한사항과 다음 단계 | “실제 Retriever 연동과 다중 근거 검증이 다음 단계입니다.” |

## 9. 슬라이드별 검수용 상세 노트

### 슬라이드 1을 검수할 때

- 입력 박스에 사용자가 선택한 Connector·프로젝트·문서 범위가 표현되어 있는지 확인한다.
- `업무 추출 Agent`와 `Query 생성 Agent`가 모두 Agent1 Workflow 안의 역할이라는 점이 보이는지 확인한다.
- Query 생성 Agent가 처음부터 무조건 실행되는 것처럼 보이지 않고, “근거 부족” 판단 뒤에 실행되는지 확인한다.
- Retriever는 업무를 해석하거나 사람을 추천하는 주체가 아니라 관련 Chunk를 검색해 반환하는 주체로 표현한다.
- 결과 박스에는 업무명만 넣지 말고 `Task + 원문 근거 + missing_fields`를 함께 표시한다.
- 발표자는 `text`를 검색·이해용, `raw_text`를 원문 인용·검증용이라고 설명한다.

### 슬라이드 1에서 피할 표현

| 피할 표현 | 바꿔 말할 표현 |
|---|---|
| AI가 문서를 읽고 업무를 자동 확정한다 | 문서 근거를 확인한 업무 후보를 제안한다 |
| Retriever가 알아서 필요한 정보를 판단한다 | Agent가 검색 목적을 정하고 Retriever가 Chunk를 반환한다 |
| 부족한 값은 AI가 추정한다 | 부족한 값은 `missing_fields`와 제한 상태로 남긴다 |
| 모든 문서를 한 번에 분석한다 | 허용된 범위에서 초기 문맥과 필요한 추가 Chunk를 검색한다 |

### 슬라이드 2를 검수할 때

- AS-IS의 문제를 “현재 코드가 항상 실패한다”라고 단정하지 말고, 여러 업무가 섞일 때 근거와 필드가 혼합될 수 있는 구조적 위험으로 설명한다.
- TO-BE의 `Evidence Validator`는 검증 책임을 분리하는 설계 방향이며, 실제 완성 기능으로 과장하지 않는다.
- `evidence_refs[].supports` 같은 필드별 복수 근거는 목표 Schema로 소개하고, 현재 MVP 결과와 구분한다.
- 검색 수렴도는 검색 횟수를 무한히 늘리는 기능이 아니라 충분한 근거·새 결과 없음·검색 한도를 기준으로 종료하기 위한 개념으로 설명한다.
- READY·LIMITED·BLOCKED는 데이터 충분성에 따른 의사결정 지원 상태이며, AI가 최종 결정을 대신한다는 뜻이 아니다.

### 슬라이드 2 발표 예시

> AS-IS에서는 한 문서에서 여러 업무를 추출하는 과정에서 역할, 공수, 일정의 근거가 서로 섞일 가능성이 있습니다. TO-BE에서는 먼저 업무 후보를 나누고, 각 후보의 필드별로 어떤 Chunk가 근거인지 매핑합니다. 검증할 수 없는 값은 완성된 것처럼 보여주지 않고 제한 또는 차단 상태로 반환해 PM이 추가 확인할 지점을 알 수 있도록 합니다.

## 10. 기존 중간발표 개요와 연결하는 방법

기존 `중간발표_개요.md`의 전체 흐름을 유지하면서 Agent1 구간만 다음처럼 연결한다.

1. 전체 서비스 문제 정의와 문서 입력 설명 뒤에 슬라이드 1을 배치한다.
2. Agent 구조를 설명하는 페이지에서는 Agent1을 “업무 추출·근거 구조화”로 요약한다.
3. 업무 분배 페이지에서는 Agent1이 사람을 배정하지 않는다는 경계를 먼저 말한 뒤 Agent2·Agent3 로드맵으로 넘긴다.
4. 구현 현황 페이지에서는 실제 연결 완료 범위와 설계·후속 범위를 분리해 표시한다.
5. Agent1 파트에서 이미 설명한 Connector·Jira·People 세부사항은 반복하지 말고, Agent1의 입력 계약과 근거 반환에 집중한다.

## 11. 발표 직전 확인 체크리스트

- [ ] 발표자 노트의 제한사항은 본문 카드보다 작게 배치한다.

## 12. 발표자 검수 후 수정이 필요한 항목

- 실제 중간발표 시점에 Agent1 종단 실행이 어디까지 연결됐는지 확인한 뒤 “완료”와 “목표” 문구를 최종 확정한다.
- Retriever의 최종 DTO 필드명이 정해지면 `text`, `raw_text`, 페이지·Chunk 식별자 표현을 실제 계약에 맞춘다.
- 업무량 계산의 실제 입력이 Jira·People DB인지 fixture인지 확인하고, 데모 화면의 데이터 출처를 표시한다.
- 다중 업무 샘플로 AS-IS의 근거 혼합 문제가 재현되는지 확인한 뒤, 재현되지 않은 내용은 “개선 가설”로 낮춰 표현한다.
