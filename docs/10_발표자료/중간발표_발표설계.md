## 1. 심사위원이 답을 원하는 세 가지

중간발표는 완성도를 겨루는 자리가 아니다. 현업 심사위원이 20분 동안 판단하는 것은 하나다.

> **이 팀이 남은 4주에 이걸 끝낼 수 있는가.**

그 판단은 세 가지 질문으로 쪼개진다.

| | 질문 | 우리 상태 |
|---|---|---|
| ① | 푸는 문제가 실제로 있는 문제인가 | **강함** — 문제 정의가 뾰족하고 근거 자료가 있다 |
| ② | 지금 만든 것이 실제로 동작하는가 | **약함** — 제품의 헤드라인인 추천이 없다 |
| ③ | 남은 것을 해낼 계획이 구체적인가 | **강함** — 병목을 정확히 알고 있다 |

발표 설계의 전부는 **②를 어떻게 방어하느냐**에 달려 있다.

## 2. 프레임 — 이것 하나만 정하고 들어간다

### 하면 안 되는 것

기능을 나열하고 상태를 붙이는 구조. "커넥터 완료 / 파싱 진행 중 / 추천 미착수"를 표로 보여주는 순간, 심사위원 머릿속에 남는 문장은 **"핵심 기능이 없다"** 하나다. 그 뒤 무슨 말을 해도 회복되지 않는다.

### 세울 프레임

> **추천을 못 만든 게 아니라, 추천이 서 있을 바닥을 먼저 만들었다.**

"AI가 업무 배정을 추천한다"는 아이디어 자체는 누구나 떠올린다. 실제로 어려운 건 그 앞단이다.

- 회사마다 양식이 다른 문서에서 업무를 꺼내는 일
- 사람 정보가 HR·Jira·문서에 흩어져 있는 것을 하나로 합치는 일
- 추천의 근거를 원문 문장까지 되짚을 수 있게 남기는 일

**이번 4주에 만든 것이 정확히 이 앞단이다.** 프레임을 이렇게 세우면 미완성이 "못 한 것"이 아니라 "순서를 정한 판단"으로 읽힌다.

### 이 프레임의 위험과 방어

위험은 하나다 — **변명처럼 들리는 것.**

방어는 두 가지뿐이다.

1. **실제로 동작하는 화면.** 말이 아니라 움직이는 것을 보여준다.
2. **검증한 숫자.** "실계정 Drive에서 문서 17건 등록 확인", "직원 57명 데이터 입력 완료" 같은 확인된 값.

이 둘이 있으면 변명이 아니라 보고가 된다. 없으면 아무리 프레임이 좋아도 무너진다.

## 3. 20분 배분

Q&A 포함 여부가 불확실하므로 **발표 17분**으로 설계하고 3분을 여유로 둔다. 넘치면 6번(기대효과)부터 줄인다.

| 구간 | 시간 | 목적 |
|---|---|---|
| 1. 도입 — 문제와 목표 | 4분 | 이 문제가 실재함을 근거로 세운다 |
| 2. 시스템 구조 | 3분 | 전체 그림과 각 단계의 역할 |
| 3. 구현 현황 | 2분 | **어디까지 왔는지 한 장으로.** 짧게 끊는다 |
| 4. **시연 영상** | 3분 | 클라이맥스. 실제로 동작하는 것 |
| 5. 남은 계획 | 3분 | 병목과 4주 일정 |
| 6. 기대효과·자체평가 | 2분 | 짧게 |
| 계 | 17분 | |

**3번을 2분으로 짧게 끊는 것이 핵심이다.** 현황 표에 오래 머무를수록 미완성이 부각된다. 빠르게 넘기고 4번 영상으로 증명한다.

## 4. 구간별 설계

### 1. 도입 — 문제와 목표 (4분)

문제 상황 → 문제 정의 → 제품 정의 순서. `중간발표_개요.md` 4~6장이 이미 잘 잡혀 있으므로 구조는 유지한다.

- HBR(Cross, Rebele & Grant 2016)의 20~35% / 3~5% 수치와 Gallup 45%는 **크게 한 번만** 쓴다. 근거는 이 두 개면 충분하다
- "업무 분배의 문제는 잘못된 사람에게 맡기는 게 아니라, 항상 같은 사람에게 맡길 수밖에 없는 구조에서 발생한다" — 이 문장이 도입의 착지점
- **AI가 배정하지 않고 PM이 결정한다**는 원칙을 여기서 못 박는다. 뒤에서 "그럼 AI가 인사를 결정하나요" 질문을 미리 막는다

### 2. 시스템 구조 (3분)

6단계 파이프라인 도식 하나로 간다. 데이터 연결 → 문서 등록 → 파싱·구조화 → 업무 추출 → 업무량·추천 → PM 검토.

이 도식은 3번과 5번에서 **색만 바꿔 재사용**한다. 심사위원이 같은 그림을 세 번 보면 구조가 머리에 남는다.

여기서 한 가지를 강조한다.

> **LLM은 문서 해석과 설명만 담당하고, 시간·부하율·필수조건은 결정론적 코드가 계산한다.**

현업 심사위원이 가장 좋아하는 지점이다. "LLM에 다 맡기지 않았다"는 것 자체가 설계 역량의 증거다.

### 3. 구현 현황 (2분)

2번 도식에 상태 색을 입힌 한 장. 완료 / 진행 중 / 미착수.

- 표현은 실측 기준으로. "설계 완료" 같은 말은 쓰지 않는다
- **여기서 변명하지 않는다.** "아직 못 했습니다"를 반복하면 그 인상만 남는다. 상태를 사실대로 보여주고 바로 넘어간다
- 한 문장으로 마무리: "문서를 근거로 쓸 수 있는 형태로 바꾸는 구간까지 지금 동작합니다"

### 4. 시연 영상 (3분) — 이 발표의 전부

**영상은 무음으로 틀지 않는다.** 3분 무음은 길게 느껴지고 청중의 집중이 흩어진다. 재생하면서 직접 내레이션한다.

영상 구성(범위는 8/4에 확정):

1. 컨테이너·DB 기동 상태 (10초)
2. Drive·Jira 커넥터 연결 화면 (20초)
3. 폴더 트리 탐색 → 읽을 폴더·역할 지정 → 저장 (40초)
4. 문서 원문 다운로드·파싱 결과 (60초) — **표가 있는 페이지를 반드시 포함**
5. Block·Chunk 분할 결과와 위치 정보 (40초)
6. (A안일 때) Task 추출 → 추천 결과 (30초)

**영상 앞뒤 멘트를 반드시 준비한다.**

- 앞: "지금부터 보실 것은 문서 한 건이 근거로 쓸 수 있는 형태로 바뀌는 과정입니다."
- 뒤: "지금 보신 구간은 실제로 동작하는 결과입니다."

### 5. 남은 계획 (3분)

2번 도식을 다시 쓰되 남은 구간을 강조한다.

- **병목을 먼저 말한다.** "문서 등록과 파싱이 아직 안 붙어 있고, 원문 다운로드가 그 연결점입니다." 약점을 먼저 꺼내면 심사위원이 그걸 캐물을 이유가 없어진다
- 4주 일정을 주 단위로. 8월 1주 원문 연결, 2주 Task 추출, 3주 추천·검증, 4주 통합·평가
- **9/3 최종발표에서 무엇을 보여줄지**를 한 문장으로 못 박는다

### 6. 기대효과·자체평가 (2분)

- 기대효과는 5장의 문제와 1:1로 대응시킨다. 새로운 이야기를 여기서 꺼내지 않는다
- 자체평가 점수는 **낮게 매기지 않는다.** 6~7점에 근거 한 줄. 지나친 겸손은 자신 없어 보인다
- 아쉬운 점에 "추천 기능 미구현"을 쓰되, 바로 옆에 "그 대신 문서 처리 기반을 먼저 확보했다"를 붙인다

## 5. 8월 4일 스위치 — A/B 대응

시연 범위를 8/4(화) 밤에 결정한다. 그때까지 발표 구조가 양쪽을 다 수용하도록 만들어 둔다.

| | A안 (추천까지) | B안 (파싱까지) |
|---|---|---|
| 3번 현황 도식 | 5단계까지 진하게 | 3단계까지 진하게 |
| 4번 영상 | 6개 구간 3분 | 5개 구간 2분 30초 |
| 5번 계획 | 검증·평가 중심 | 원문 연결 + 추천 중심 |
| 자체평가 | 7점 | 6점 |

**바뀌는 건 색과 영상 길이뿐이고, 슬라이드 장수와 순서는 그대로다.** 이렇게 해두면 8/4까지 발표 준비가 아니라 구현에 집중할 수 있다.

판단 기준: **8/4 밤에 원문 다운로드 → 파싱 → Block 저장이 한 번이라도 성공했는가.** 안 됐으면 미련 없이 B안. 8/5에 무리하게 붙이려다 8/6 아침에 아무것도 안 도는 상태가 최악이다.

## 6. 예상 질문 대비

현업 심사위원이 물을 법한 것들. **굵은 것 세 개는 반드시 나온다고 보고 준비한다.**

**① 기존 Jira·Asana·먼데이닷컴이랑 뭐가 다릅니까?**
기존 도구는 사람이 이미 정의해 둔 업무를 관리합니다. 저희는 아직 업무로 정의되지 않은 문서에서 업무를 만들어내고, 그 배정 근거를 원문 문장까지 되짚습니다. 관리 도구가 아니라 그 앞단입니다.

**② 추천이 맞는지는 어떻게 평가하나요?**
정답이 하나가 아니라서 정확도로 평가하지 않습니다. 대신 세 가지를 봅니다. 필수 제약조건 위반이 0건인가, 추천마다 근거 출처가 연결돼 있는가, 업무량 계산이 수작업 기준과 ±5% 이내인가. PM 수정률도 운영 지표로 봅니다.

**③ 4주 남았는데 추천까지 가능한가요?**
병목은 하나입니다. 원문 다운로드가 파싱과 붙는 지점이고, 이번 주에 그 앞뒤가 각각 완성됐습니다. 8월 1주에 이걸 연결하면 나머지는 이미 설계와 스키마가 준비돼 있습니다. (→ 5번 일정 슬라이드를 가리킨다)

④ **왜 LLM에 전부 맡기지 않았나요?**
휴가 일수나 부하율은 LLM이 계산하면 틀려도 틀린 걸 알 수 없습니다. 시간·부하·필수조건은 결정론적 코드로 계산하고, LLM은 비정형 문서 해석과 PM용 설명에만 씁니다.

⑤ **실제 회사 문서는 이것보다 훨씬 지저분한데요?**
그래서 폴더 단위로 문서 역할을 사용자가 지정하게 했습니다. 모든 문서를 무차별로 읽지 않고 선택한 범위만 처리합니다. 형식별 파서 대응 폭은 저희도 약점으로 보고 있고, OCR과 HWP는 후속으로 뒀습니다.

⑥ **Docling은 왜 골랐나요?**
단일 파싱 모델이 아니라 처리 단계를 조합해 워크플로우를 구성하는 SDK입니다. PDF·DOCX·XLSX가 섞여 들어오고 표 구조를 보존해야 해서, 형식별로 파이프라인을 다르게 구성할 수 있는 쪽이 맞다고 판단했습니다.

⑦ **인력 데이터는 실제인가요?**
합성 데이터입니다. 스키마는 실제 HR 데이터도 수용할 수 있는 공통 구조로 설계했고, 실제 HR 연동은 후속 확장으로 분리했습니다.

⑧ **개인정보·노무 이슈는 없나요?**
휴가 사유는 저장하지 않고 가용성 영향 시간만 씁니다. 문서 검색에는 원본 Drive 권한을 그대로 적용하고, 추천 화면은 역할 기반으로 노출을 제한합니다.

⑨ **벡터 DB를 왜 pgvector로 바꿨나요?**
초기에 ChromaDB로 시작했는데, 검색 인덱스와 관계 데이터를 별도 인스턴스로 나눌 만한 규모가 아니었습니다. 같은 PostgreSQL 안에서 운영하면 청크와 원문을 조인으로 연결할 수 있어 근거 추적이 단순해집니다.

⑩ **팀 5명이 어떻게 나눠서 했나요?**
(R&R 한 줄씩. 최원빈님 파싱 작업이 별도 환경에서 진행 중인 점은 굳이 먼저 말하지 않는다)

⑪ **AI가 인사 결정을 하는 건가요?**
아닙니다. 승인·수정·반려는 PM이 하고, 시스템은 후보와 근거만 제시합니다. 검증에서 REJECT가 나면 Jira 반영 버튼 자체가 나타나지 않습니다.

⑫ **왜 아직 원문을 안 받았나요?**
문서 저장소 인터페이스를 먼저 정해야 했습니다. 지금은 로컬이지만 나중에 S3로 바꿔야 해서, 경로를 코드에 박지 않고 `storage_key`로 조회하는 구조를 유지했습니다.

## 7. 혼자 20분 발표할 때

- **20분 단독은 길다.** 물 한 병을 단상에 올려두고, 영상 3분을 호흡 회복 구간으로 쓴다
- 슬라이드마다 목표 시간을 노트에 적고 **리허설 2회 이상.** 1회는 타이머만 재고, 2회는 팀원 앞에서
- 첫 30초와 마지막 30초는 **문장 그대로 외운다.** 시작과 끝이 흔들리면 전체가 흔들린다
- 심사위원과 눈을 맞추는 구간을 미리 정한다 — 문제 정의 착지 문장, 영상 직전 멘트, 마지막 문장
- 넘칠 때 버릴 순서를 정해둔다: **6번 → 1번 시장조사 → 2번 세부 설명.** 4번 영상과 5번 계획은 절대 줄이지 않는다
