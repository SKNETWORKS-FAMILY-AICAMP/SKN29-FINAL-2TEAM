## 4. 문제 상황

**목적** — 반복되는 장면을 보여주고, 그것이 실제로 관측되는 현상임을 근거로 뒷받침한다.

**상황 제시**

> 프로젝트 진행 중 새로운 업무가 추가되었습니다. PM은 고민합니다. "누구에게 맡기는 것이 가장 안전할까?" 결국 기존 업무 경험이 많고 신뢰할 수 있는 구성원에게 업무를 배정하게 됩니다.

- **Cross, Rebele & Grant (2016, Harvard Business Review)**
  조직에서 부가가치를 창출하는 협업의 **20~35%가 전체 구성원의 3~5%**에게서 발생합니다. 그리고 이들에게 요청이 집중되면서 **해당 구성원의 성과가 오히려 저하**되는 현상이 확인되었습니다.
  → 소수에게 업무가 몰리는 것은 특정 팀의 문제가 아니라 조직에서 반복적으로 관측되는 구조입니다.

- **Gallup**
  자신의 역할과 기대사항을 명확히 이해하고 있다고 응답한 직원은 약 **45%**입니다.
  → 역할이 명확하지 않으면 새로운 업무는 이미 검증된 사람에게 돌아갑니다.

두 수치를 크게 배치하고 출처는 각 항목 옆에 작게 표기한다.

**핵심 메시지**

> 업무 분배의 문제는 단순히 잘못된 사람에게 맡기는 것이 아니라, 항상 같은 사람에게 맡길 수밖에 없는 구조에서 발생합니다.

**시각화**

업무 추가 → PM 판단 → 경험 많은 구성원에게 반복 배정 → 업무 집중 / 불균형 발생

인물 아이콘 위에 업무 카드가 쌓이는 형태로 표현한다.

**→ 다음으로**: "그렇다면 왜 항상 같은 사람에게 맡길 수밖에 없을까요?"

## 5. 문제 정의

**목적** — 반복되는 이유를 두 가지 문제로 정리하고 문제를 정의한다.

**업무를 배정하려면 이런 정보가 필요합니다**

현재 담당 업무 · 업무량 · 예상 소요 시간 · 필요한 역량 · 현재 가용 시간

> IGM은 업무량을 단순한 업무 개수가 아니라 업무 빈도, 예상 소요시간, 중요도를 함께 고려해 산정해야 한다고 제시합니다.

**그런데 두 가지가 이를 막고 있습니다**

**① 이 정보를 한 기준으로 볼 수 없습니다**

- 신규 프로젝트의 업무와 필요 역량은 기획서·요구사항 문서 안에 문장으로만 있습니다
- 구성원의 업무 현황과 일정은 각각 다른 곳에서 관리됩니다
- PM이 직접 확인하고 머릿속에서 합쳐야 합니다

**② 판단 과정이 기록되지 않습니다**

- 어떤 정보를 보고 그 사람을 골랐는지 남지 않습니다
- 담당자가 바뀌면 판단 기준이 달라집니다
- 구성원에게 배정 이유를 설명하기 어렵습니다

**문제 정의 문장**

> 프로젝트에서는 구성원의 역할과 현재 업무량을 객관적으로 파악하기 어렵고 판단 근거도 남지 않아, 업무가 특정 구성원에게 집중되거나 배정 근거를 설명하기 어려운 문제가 발생한다.

**→ 다음으로**: "저희는 이 두 가지를 해결하는 시스템을 구현하려 합니다."

## 6. 프로젝트 목표

**목적** — 앞의 두 문제와 기능을 1:1로 대응시켜 시스템을 정의한다.

**제품 정의**

> 프로젝트 문서와 구성원 정보를 분석해 PM에게 업무 배정 판단 근거를 제공하는 AI 코파일럿

**문제와 기능의 대응** — 이 표가 슬라이드의 중심이다

| 문제 | 해결 기능 |
|---|---|
| ① 정보를 한 기준으로 볼 수 없음 | 쓰고 있는 도구를 그대로 연결 |
| | 문서에서 업무·일정·요구사항 추출 |
| | 구성원의 업무량·역량·가용시간 통합 |
| ② 판단 과정이 기록되지 않음 | 추천과 함께 판단 근거·원문 제시 |

**쓰고 있는 도구를 그대로 연결합니다**

- Google Drive의 프로젝트 문서, Jira의 업무 현황을 그대로 가져옵니다
- 이미 쓰고 있는 도구를 연결하므로 데이터를 새로 옮기거나 입력할 필요가 없습니다
- 연결할 폴더와 프로젝트 범위는 사용자가 직접 지정합니다
- Drive · Jira 아이콘이 시스템으로 연결되는 그림으로 배치한다

**제품 방향**

- AI가 업무 배정을 대신하지 않습니다. PM의 판단을 지원하는 역할입니다.

나머지 기능은 표에 적힌 것으로 충분하다. 슬라이드에서 다시 풀어 쓰지 않는다.

**→ 다음으로**: "이 기능들이 어떤 순서로 동작하는지 보시겠습니다."

## 9. 구현 현황

**목적** — 지금 무엇이 실제로 동작하는지 한 장으로 보여준다. **이 발표에서 가장 중요한 슬라이드.**

**지금 동작하는 구간**

비정형 문서 입력 → 파싱 → 구조 분석(Block 분리) → 청크 분할

이 구간이 **끊기지 않고 동작한다**는 점을 강조한다. 실제 문서 한 건이 이 경로를 통과하는 모습을 화살표 위에 얹어 보여준다.

**아직 동작하지 않는 부분**

근거 저장 → 외부 도구 연동 → 업무 정보 추출 → 업무량 계산 → 배정 후보 추천 → PM 검토 로직

7장 구조도 위에 동작 구간은 진하게, 남은 범위는 회색으로 표시한다.

**정확한 상태 구분**

| 항목 | 현재 상태 |
|---|---|
| 실행 환경 | 구성 완료 |
| 데이터 모델 | 설계·구축 완료 |
| 비정형 문서 파싱 | 구현 완료, 동작 확인 |
| 문서 구조 보존 처리 | 구현 완료, 동작 확인 |
| 화면 | 구현 완료 |
| 근거 저장 | 저장 구조만 준비, 로직 미착수 |
| 외부 도구 연동 | 데이터 구조 준비, 연동 로직 미구현 |
| 업무 추출 · 업무량 계산 · 배정 추천 | 저장 구조만 준비, 로직 미착수 |

"설계 완료"라는 표현은 쓰지 않는다. 무엇이 준비됐고 무엇이 안 됐는지를 그대로 적는다. 화면은 표에만 두고 별도 슬라이드로 설명하지 않는다.

**핵심 메시지**

> 추천 기능을 만들기 전에, 문서를 근거로 쓸 수 있는 형태로 바꾸는 단계를 먼저 만들었습니다. 비정형 문서가 구조를 잃지 않고 변환되는 구간까지 지금 동작합니다.

## 10. 문서 구조 보존

**목적** — 왜 단순 텍스트 추출이 아닌지, 무엇을 다르게 했는지 보여준다.

**일반적인 문서 추출의 한계**

문서 → 텍스트

- 표 관계 손실 — 담당자와 마감일의 연결이 끊어짐
- 제목 구조 손실 — 어느 항목에 대한 내용인지 알 수 없음
- 원본 위치 확인 불가 — 어디에서 나온 정보인지 되짚을 수 없음

**저희 방식**

문서 → 구조 단위(Block) → 검색 단위(Chunk)

**함께 남기는 정보**

문서 내 위치 · 제목 구조 · 표 정보 · 원본 페이지 · 이미지 정보

이 정보를 함께 남겨두었기 때문에, 다음 단계에서 추출한 업무 정보가 원문 어디에서 나왔는지 되짚을 수 있습니다.

**보여줄 것**

실제 문서 한 페이지와 변환 결과를 나란히 배치한다. 특히 **표가 들어간 페이지**를 고르면 차이가 가장 잘 드러난다. 왼쪽에 원본 표, 오른쪽에 헤더와 행이 보존된 변환 결과.

**→ 다음으로**: "이 결과를 담기 위해 설계한 데이터 구조입니다."

## 11. 데이터 구조

**목적** — 저장 구조가 무엇을 할 수 있게 하는지 보여준다.

**세 영역으로 나눈 구조**

- 문서·지식 관리 — 문서에서 나온 정보와 그 근거
- 인력·업무 관리 — 구성원 상태와 업무 현황
- 운영 및 기록 관리 — 처리 이력과 판단 기록

**저장소 구분**

- **PostgreSQL** — 관계 데이터와 근거 연결 관리
- **pgvector** — 의미 기반 검색

**이 구조가 답할 수 있도록 설계한 질문**

- 이 추천의 근거는 어느 문서 어느 문장인가
- 이 구성원은 지금 어떤 업무를 몇 시간 분량으로 맡고 있는가
- 이 판단은 언제 어떤 데이터를 기준으로 내려졌는가

테이블 개수보다 **어떤 질문에 답할 수 있는 구조인지**를 앞세운다. ERD는 배경으로 배치한다. 이 세 질문은 구조가 목표로 하는 것이며, 실제 조회 기능은 다음 단계에서 구현한다는 점을 함께 말한다.

**→ 다음으로**: "이 구조가 실제로 동작하는 화면을 보여드리겠습니다."

## 12. 실행 결과

**목적** — 실제로 돌아간다는 것을 눈으로 보여준다. **9장과 함께 가장 중요한 슬라이드.**

**시연 순서** — 비정형 문서 한 건이 변환되는 과정을 순서대로 보여준다

1. 실행 환경 기동 — 컨테이너와 DB가 올라온 상태
2. 문서 입력 — 실제 기획서 또는 요구사항 문서 한 건
3. 파싱 결과 — 문서에서 추출된 내용
4. 구조 분석 결과 — Block 단위로 나뉜 결과, 특히 표가 구조 그대로 보존된 부분
5. 청크 분할 결과 — 검색 단위로 나뉜 결과와 함께 남은 위치 정보

**가능하면 영상으로**

정지 화면 나열보다 짧은 화면 녹화가 훨씬 강하다. 발표 시간이 부족하면 30초 분량으로 편집해 자동 재생한다.

**마무리 문장**

## 15. 자체 평가

**목적** — 프로젝트 수행 과정과 개선점을 정리한다.

**완성도 평가**

기획 단계 목표 대비 현재 결과물의 완성도 — **○ / 10점**

점수와 함께 근거를 한 줄로 적는다. 예: 문서 처리와 데이터 기반은 계획대로 완료했으나 추천 기능이 남아 있어 ○점

**잘한 점**

- 문제 정의를 업무 분배 근거 부족으로 명확화
- 추천 기능보다 문서를 근거로 쓸 수 있게 만드는 기반을 우선 구축
- 비정형 문서를 구조를 잃지 않고 변환하는 구간을 완성

**아쉬운 점**

- 중간발표 시점에서는 추천 기능까지 구현하지 못함
- 추출 정보와 원문을 연결하는 근거 저장이 아직 남아 있음
- 외부 도구 연동이 남아 있어 실제 데이터로 검증하지 못함
- 문서 유형별 대응 폭이 좁음

**개선 방향**

- 추천 정확도 평가 기준 수립
- 다양한 문서 유형 대응
- 실제 프로젝트 환경에서 검증

**느낀 점**

- 훈련 과정에서 배운 내용을 실제 설계와 구현에 적용하며 얻은 것
- 앞으로의 진로·경력 계획과의 연관성
