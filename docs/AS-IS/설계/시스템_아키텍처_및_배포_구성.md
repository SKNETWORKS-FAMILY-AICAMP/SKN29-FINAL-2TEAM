# 시스템 아키텍처 및 배포 구성

> 작성 목적: 중간발표 7장("시스템 구조 및 개발 환경")에 들어갈 인프라 배치도를 그리기 위한 원본 자료. 멘토 피드백은 "AI 에이전트 구조뿐 아니라 실제로 이게 어느 서버에 떠 있는지도 그림으로 보여줘라 — EC2/EKS에 뭐가 있고, 모델은 RunPod에 있고, DB는 이거고" 였다(`docs/발표자료/중간발표_개요.md` 7장 참고).
>
> 이 문서는 **실제 코드·설정 파일을 근거로** 지금 진짜 돌아가는 것(AS-IS)과 아직 안 붙은 것(TO-BE)을 구분해서 적었다. 다이어그램을 그릴 때 AS-IS는 실선 박스로, TO-BE는 점선 박스로 그려서 "지금 여기까지 왔다"가 한눈에 보이게 해야 한다 — 실제로 안 붙어 있는 것을 이미 연결된 것처럼 그리면 발표에서 질문이 들어왔을 때 답할 수 없다.

---

## 0. 한눈에 보기 — AS-IS vs TO-BE

| 구성요소 | AS-IS (지금 실제로 돌아가는 것) | TO-BE (아직 안 붙었지만 계획된 것) |
|---|---|---|
| 컴퓨트 | EC2 1대, Docker Compose로 `frontend`+`web` 컨테이너 실행 | (EKS·ECS는 이번 범위에 없음 — 아래 5장 참고) |
| DB | PostgreSQL 17 + pgvector 익스텐션, 로컬은 Docker 컨테이너·AWS는 RDS로 같은 스키마 사용 | RDS의 `vector` 확장 지원 여부 최종 확인만 남음 |
| 문서 원문 저장 | EC2/컨테이너 로컬 디스크(`/var/lib/halil/documents`, Docker volume) | S3 버킷으로 이전(`boto3`/`django-storages`는 설치돼 있으나 아직 미연결) |
| 문서 파싱·임베딩 | **RunPod Serverless 에서 동작**(2026-08-05). Django 가 만료형 서명 URL 로 원문만 내주고, Worker 가 Docling 파싱·구조 보존 청킹·EmbeddingGemma 임베딩을 해서 돌려주면 Django 가 `doc_block`·`chunk`·`vec_idx` 에 적재한다 | 모델을 이미지에 굽거나 Network Volume 에 캐시해 콜드 스타트 줄이기 |
| 외부 연동 | Google Drive·Jira OAuth 연동 완료, 실제 원문 다운로드까지 동작 | — |
| 배포 자동화 | 없음 — SSH 접속 후 수동 `git pull` + `docker compose up` | CI/CD 없음(이번 범위 제외로 확정) |

## 1. 전체 컴포넌트 목록

```
[사용자 브라우저]
        │ HTTP
        ▼
[EC2 인스턴스] ── Docker Compose로 아래 두 컨테이너 실행
   ├─ frontend 컨테이너 (React + Vite)
   └─ web 컨테이너 (Django + DRF, gunicorn)
        │                              │
        │ SQL (5432)                   │ 파싱 요청 (AS-IS)
        ▼                              ▼
[RDS PostgreSQL 17 + pgvector]   [RunPod Serverless] (AS-IS, 동작)
   - 업무/조직/문서 메타데이터 등        - 문서 파싱
     40여 개 관계형 테이블               - 임베딩 생성
   - vec_idx 테이블(임베딩 벡터,          │
     768차원, 실제 적재됨)               │ 임베딩 결과 저장
        ▲──────────────────────────────┘

[web 컨테이너] ── (TO-BE) S3 버킷 ── Drive에서 받은 문서 원문
             └── (AS-IS) EC2 로컬 디스크 Docker volume ── 문서 원문

[web 컨테이너] ── OAuth 2.0 ──▶ Google Drive API, Jira API (AS-IS, 연동 완료)
```

각 컴포넌트를 아래 장에서 하나씩 설명한다.

## 2. 컴퓨트 — EC2 (AS-IS), EKS는 채택 안 함

- **EC2 인스턴스 1대**에 Docker와 Docker Compose를 설치하고, `infra/docker/docker-compose.aws.yml`로 컨테이너 두 개(`frontend`, `web`)만 띄운다. `db` 서비스는 AWS에서는 정의하지 않는다(RDS를 쓰기 때문).
- 배포는 자동화 파이프라인이 없다 — 팀원이 EC2에 SSH로 접속해 `git pull` 후 `docker compose -f infra/docker/docker-compose.aws.yml up --build -d`를 직접 실행한다(`docs/개발환경/AWS_이전_매뉴얼.md` §7).
- **EKS(쿠버네티스)는 이번 프로젝트 범위에 없다.** `AWS_이전_매뉴얼.md`에 "이번 범위에서는 ECS, ALB, CloudFront, SQS, 별도 Vector DB, Terraform, CI/CD는 사용하지 않는다"고 명시돼 있다 — 부트캠프 파이널 프로젝트 규모(시연·통합 테스트용)에 컨테이너 오케스트레이션까지 두면 과한 구성이라는 판단이다. 슬라이드에는 "EKS 대신 EC2 단일 인스턴스 + Docker Compose를 선택했다"는 걸 근거와 함께 정직하게 적는 게 낫다 — 안 쓰는 걸 있는 것처럼 그리면 안 된다.
- `web` 컨테이너는 이미지 안에서는 `gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 2`로 뜬다(로컬 개발 compose에서만 `manage.py runserver`로 override).
- `frontend` 컨테이너는 지금은 Vite 개발 서버(`npm run dev`)를 그대로 쓴다 — nginx 정적 빌드 단계는 아직 없다.

**보안 그룹**
```
브라우저 ── 5173(frontend), 8000(web) ──▶ EC2 보안 그룹
EC2 보안 그룹 ── 5432 ──▶ RDS 보안 그룹 (RDS는 인터넷에 직접 노출 안 함)
```
EC2는 22번(팀원 공인 IP만)·5173·8000만 열고, RDS는 5432를 EC2 보안 그룹에서 오는 트래픽만 허용한다.

## 3. 데이터베이스 — PostgreSQL + pgvector (AS-IS)

- 로컬 개발은 `pgvector/pgvector:pg17` Docker 이미지, AWS는 **RDS PostgreSQL**을 쓴다 — 둘 다 같은 `DB/schema.sql`을 그대로 적용해서 스키마가 동일하다. Django ORM/Migration은 쓰지 않고 SQL 파일을 직접 실행한다.
- **하나의 PostgreSQL 인스턴스 안에 관계형 테이블과 벡터 테이블이 같이 있다** — 별도 Vector DB(Pinecone 등)를 쓰지 않는다. 벡터는 `vec_idx` 테이블(컬럼: `chunk_id`, `embedding VECTOR(768)`, `embed_model`, `embed_dim` 등)에 저장하고 `vector` 익스텐션으로 코사인 유사도 검색을 한다.
- **`vec_idx`는 적재·검색 모두 동작한다** — 적재는 `backend/db/document_pipeline.py:302`, 검색은 `:343`이다.

> ⚠ **2026-08-05 정정 2건.** 차원이 `VECTOR(1536)`으로 적혀 있었다 — **768**이다
> (`DB/migrations/2026-08-04_embeddinggemma_768.sql`. 1536은 OpenAI
> `text-embedding-3-small`을 전제하던 시절 값이다). 그리고 "`vec_idx`는 스키마만 있고
> 비어 있다, 넣고 검색하는 코드 경로가 아직 없다"고 적혀 있었으나 둘 다 동작한다.
> `backend/services/createDB/vec_idx_setup.py`는 1536차원 데모 스크립트라 지금 돌리면
> **실패한다** — 현행 경로는 `services/document_pipeline/`과 `runpod_worker/`다.
- People DB(조직·직원·스킬·근무·휴가) 8개 테이블은 `mock_hr` 스키마에 별도로 분리돼 있다 — 우리가 만드는 데이터가 아니라 고객사 HR 시스템에서 읽어오는 데이터라는 경계를 스키마 레벨에서 표시한 것이다. 지금은 목업 데이터를 직접 넣어 쓴다.
- RDS 전환 시 `vector` 확장이 지원되는지 최종 확인이 남아있다(`AWS_이전_매뉴얼.md` §4) — AWS RDS PostgreSQL은 최신 엔진 버전에서 `pgvector`를 지원하므로 리스크는 낮지만, 배포 직전에 `CREATE EXTENSION IF NOT EXISTS vector;`로 재확인해야 한다.

## 4. 문서 원문 저장 — 로컬 디스크(AS-IS) → S3(TO-BE)

- Google Drive에서 받아온 문서 원문은 지금 **EC2/컨테이너의 로컬 디스크**에 저장된다. 경로는 `DOCUMENT_STORAGE_ROOT` 환경변수(기본 `/var/lib/halil/documents`)이고, Docker named volume(`document_storage`)으로 컨테이너가 재시작돼도 파일이 남게 해뒀다. 저장 키는 `build_key(team_id=…)`가 만든다 — **팀 기준이다**(2026-08-05 정정. `{proj_id}/{doc_id}.{확장자}`로 적혀 있었으나, 문서는 등록 시점에 `proj_id`가 `NULL`이라 프로젝트 기준으로는 키를 만들 수 없다).
- 저장 로직은 `backend/services/storage.py` 한 곳에 있다 — 이 파일의 주석 자체가 "지금은 로컬 디스크다. AWS 계정을 받으면 S3로 바뀌지만, 그때도 `doc.storage_key` 값은 그대로 쓸 수 있어야 한다"고 설명한다. 즉 **저장소를 S3로 바꿔도 DB에 저장하는 `storage_key` 형식·나머지 코드는 안 바뀌게** 미리 설계해뒀다.
- **다만 지금 코드는 `S3`를 실제로 호출하지 않는다.** `boto3`·`django-storages`는 `requirements/production.txt`에 이미 추가돼 있지만, `config/settings/production.py`에는 아직 `STORAGES`/`AWS_STORAGE_BUCKET_NAME` 설정이 없다 — 즉 **설치는 돼 있는데 배선이 안 된 상태**다. `AWS_이전_매뉴얼.md` §6에 S3로 바꿀 때 넣어야 할 정확한 설정 코드가 이미 적혀 있다.
- S3로 전환하면: EC2에는 Access Key를 직접 넣지 않고 **IAM Role**을 연결해서 접근한다. 버킷은 비공개 + Versioning 활성화, 경로는 `documents/{project_id}/{source_file_id}/{version}/original.pdf` 형태로 역할별로 나눈다.
- 다운로드 흐름(지금 실제로 동작): `TeamDocumentDownloadAPIView`(`POST /api/team/documents/download/`, 2026-08-05 정정 — 팀 경계로 옮겨지면서 이름이 바뀌었다) → Google Drive API에서 원문 다운로드 → `storage.py`로 로컬 디스크에 저장 → `doc.storage_key`/`content_hash`(sha256)/`cur_revision`(Drive의 headRevisionId)을 PostgreSQL에 기록.

## 5. RunPod Serverless — 파싱·청킹·임베딩 (AS-IS)

> ⚠ **2026-08-05 전면 정정.** 이 절은 "저장소 전체를 검색해도 RunPod를 호출하는 코드,
> API 키 환경변수, SDK 의존성이 하나도 없다", "실행 코드·전송 방식·모델 선정은 전부
> 미착수다"라고 적고 있었다. **셋 다 틀렸다.** 같은 문서 §0(16줄)이 이미 "RunPod에서
> 동작(2026-08-05)"이라 적어 자기모순이었다. 아래는 코드로 확인한 내용이다.

- **호출 코드**: `services/document_pipeline/runpod_client.py`. Django가 RunPod Serverless 엔드포인트에 작업을 넣고 결과를 polling해서 적재한다.
- **환경변수**: `RUNPOD_API_KEY`·`RUNPOD_ENDPOINT_ID`·`RUNPOD_JOB_TTL_MS`·`RUNPOD_EXECUTION_TIMEOUT_MS`·`RUNPOD_EMBED_WAIT_SECONDS` (`config/settings/base.py:110-122`).
- **전송 방식은 확정됐다** — **RunPod은 우리 DB에 접근하지 않는다.** 원문은 만료형 서명 URL로 받아 가고(`GET /api/internal/runpod/documents/<doc_id>/`, `apps/projects/api_urls.py:79-83`), 결과는 Django가 받아 적재한다. 사용자 OAuth 토큰이 파싱 쪽으로 넘어가면 그 토큰 하나로 그 사람의 Drive 전체를 읽을 수 있기 때문이다.
- **모델도 확정됐다**: `google/embeddinggemma-300m`(768차원). 파싱은 Docling + 조건부 EasyOCR.
- **Worker는 별도 저장소다**: `choiwon10/SKN29-RUNPOD-WORKER`의 `codex/install-triton-compiler` 브랜치가 실제로 도는 코드이고, 이 저장소의 `runpod_worker/`는 읽기용 사본이다. 워커를 고치면 그쪽에 푸시하고 RunPod 콘솔에서 빌드해야 반영된다.

**초기 구상과 달라진 점.** 기획서 v2(`docs/_archive/기획서_v2_업무분배부하조율.md`)의 "보안 sLLM(RunPod 온프레미스, 파인튜닝)"은 7~8B급 모델을 QLoRA로 파인튜닝해 업무 추출까지 RunPod에서 돌린다는 구상이었다. 실제로는 **RunPod이 파싱·청킹·임베딩만 맡고, 업무 추출은 OpenAI API로 간다.** 파인튜닝은 하지 않았다.

**운영 제약**: 최소 워커 0에 유휴 타임아웃이 지나면 워커가 내려가고, 모델이 이미지에 구워져 있지 않아 다음 요청에서 수 GB를 다시 받는다. **시연 전에 문서 하나를 미리 처리해 워커를 깨워 둔다.**

다이어그램에는 RunPod 박스를 **실선**으로 그리고 "문서 파싱·청킹·임베딩" 라벨을 붙인다. 화살표는 `web`이 RunPod에 작업을 넣고, RunPod이 **만료형 서명 URL로 원문을 되받아 가고**, 결과를 `web`이 받아 PostgreSQL(`doc_block`·`chunk`·`vec_idx`)에 적재하는 3방향이다. RunPod에서 DB로 직접 가는 화살표는 그리지 않는다 — 실제로 그런 경로가 없다.

> ⚠ **2026-08-05 정정.** 이 자리는 RunPod을 **점선 TO-BE**로 그리라고 지시하고 있었다. 이 문서 스스로 5줄에서 "안 붙어 있는 것을 붙은 것처럼 그리면 안 된다"고 적었는데, 정반대 방향의 실수였다 — 붙어 있는 것을 안 붙은 것처럼 그리라고 지시하고 있었다.

## 6. 외부 연동 — Google Drive·Jira (AS-IS, 완료)

- 둘 다 표준 **OAuth 2.0 Authorization Code Grant(3LO)** 흐름을 쓴다. `web` 컨테이너가 인가 URL을 만들어주면 사용자가 Google/Atlassian 로그인 화면에서 동의하고, 콜백으로 돌아오면 토큰을 교환해 암호화해서 PostgreSQL(`connector_conn.encrypted_credential_ref`)에 저장한다.
- 이 흐름은 실제 계정으로 인가 URL 발급·콜백까지 확인된 상태다(이 저장소의 `apps/connectors/` 코드, `docs/AS-IS/설계/Jira_Drive_커넥터_연결_설계.md` 참고).
- 다이어그램에는 `web` 컨테이너에서 바깥으로 나가는 화살표로 Google Drive API, Jira API 박스 두 개를 실선으로 그리면 된다.

## 8. 다이어그램을 그릴 AI에게 — 레이아웃 가이드

1. **좌측**: 사용자 브라우저 → (HTTP) → EC2 박스. EC2 박스 안에 `frontend`, `web` 컨테이너 두 개를 나란히 그린다(둘 다 실선).
2. **우측 상단**: RDS PostgreSQL + pgvector 박스(실선). `web`에서 화살표(5432 포트 라벨). 박스 안에 "관계형 테이블 40여 개 + vec_idx(벡터, 현재 비어있음)"라고 부기.
3. **우측 하단**: S3 박스는 **점선**으로 그리고 "TO-BE"라고 라벨. `web`에서 점선 화살표.
4. **하단**: RunPod GPU 박스는 **실선**으로 그리고 "문서 파싱·청킹·임베딩"이라고 라벨(2026-08-05 정정 — 여기도 점선 TO-BE로 적혀 있었다). 화살표는 `web` → RunPod(작업 투입), RunPod → `web`(서명 URL로 원문 요청), `web` → PostgreSQL(결과 적재). **RunPod에서 PostgreSQL로 직접 가는 화살표는 그리지 않는다.**
5. **외부**: EC2(`web`) 바깥으로 Google Drive API, Jira API 박스 두 개(실선, OAuth 2.0 라벨).
6. 범례를 반드시 넣는다: **실선 = 지금 실제로 동작, 점선 = 계획됨/미구현**. 이 구분이 이 문서 전체의 핵심이다.
7. EKS/ECS/CI-CD는 그리지 않는다 — "범위에서 제외했다"는 각주를 다이어그램 옆에 한 줄 남기는 정도로 충분하다.
