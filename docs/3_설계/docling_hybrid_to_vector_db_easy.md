# Docling HybridChunker부터 Vector DB까지 — 쉬운 설명

우리는 PDF 문서를 잘게 나눠서 “필요한 내용을 빨리 찾아주는 서랍장”에 넣으려는 거야.

```text
PDF 문서
→ 글과 표를 읽음
→ 작은 조각으로 나눔
→ 각 조각을 숫자로 바꿈
→ 숫자 서랍장(Vector DB)에 저장
→ 질문이 오면 가장 비슷한 조각을 꺼냄
```

## 1. 문서를 가져온다

나중에는 Google Drive에 있는 PDF를 가져올 거야.

예를 들면:

```text
회의록.pdf
기획서.pdf
보고서.pdf
```

문서를 가져올 때는 파일 내용만 가져오는 게 아니라, “이 파일이 무엇인지”도 같이 기억해.

```text
파일 이름: 기획서.pdf
파일 ID: Google Drive의 고유 번호
수정 버전: 몇 번째 수정본인지
파일 해시: 파일 내용이 같은지 확인하는 지문
```

파일 해시는 사람의 지문처럼 생각하면 돼. 파일 내용이 바뀌면 해시도 바뀌어.

## 2. Docling과 EasyOCR이 PDF를 읽는다

PDF는 사람에게는 문서지만, 컴퓨터에게는 글·표·그림이 섞인 페이지야.

Docling과 EasyOCR은 PDF를 읽어서 이렇게 구분해 줘.

```text
이것은 제목
이것은 일반 문단
이것은 목록
이것은 표
이것은 그림
이것은 그림 안의 글자
```

그리고 읽은 결과를 JSON 파일로 저장해.

```text
기획서.pdf
→ document.docling.json
```

이 JSON은 “PDF를 컴퓨터가 읽은 상세한 설계도”라고 보면 돼.

## 3. Docling HybridChunker가 문서를 작은 조각으로 나눈다

문서를 한꺼번에 AI에게 주면 너무 길고, 필요한 내용을 찾기도 어려워.

그래서 Docling의 `HybridChunker`가 문서를 의미 있는 작은 조각, 즉 청크로 나눠.

예를 들어 원래 문서가 이렇다면:

```text
[프로젝트 소개]
우리 프로젝트는 ...

[문제 정의]
현재 고객은 ...

[해결 방법]
우리는 다음과 같이 ...
```

청크는 대략 이렇게 만들어져.

```text
청크 1
제목: 프로젝트 소개
내용: 우리 프로젝트는 ...

청크 2
제목: 문제 정의
내용: 현재 고객은 ...

청크 3
제목: 해결 방법
내용: 우리는 다음과 같이 ...
```

여기서 중요한 점은 무작정 글자 수마다 자르지 않는다는 거야.

Docling HybridChunker는:

1. 제목, 문단, 목록, 표 같은 문서 구조를 먼저 본다.
2. 너무 긴 조각만 다시 나눈다.
3. 너무 짧은 조각은 같은 제목 아래에 있으면 합친다.
4. 표가 길어서 나뉘면, 표의 맨 윗줄 제목을 다음 조각에도 다시 넣어 준다.

그래서 표가 이렇게 잘리지 않게 도와줘.

```text
나쁜 예:
제품명 | 가격 |
A 제품 | 10만 원
B 제품 | ...

다음 청크:
20만 원
```

대신 이렇게 유지하려고 해.

```text
제품명 | 가격 |
A 제품 | 10만 원

제품명 | 가격 |
B 제품 | 20만 원
```

## 4. 청크에는 제목도 같이 붙인다

본문만 보면 무슨 이야기인지 모를 수 있어.

```text
“예산은 3천만 원으로 잡는다.”
```

이 문장만 있으면 무슨 예산인지 알기 어렵지.

그래서 AI에게는 제목까지 붙인 문장을 줘.

```text
[프로젝트 A]
[예산 계획]
예산은 3천만 원으로 잡는다.
```

우리는 이것을 `contextualized_text`라고 부를 거야.

- `text`: 청크의 실제 본문
- `contextualized_text`: 제목 문맥까지 붙인 AI용 텍스트

임베딩에는 `contextualized_text`를 사용해.

## 5. 글을 숫자로 바꾼다: 임베딩

컴퓨터는 글의 뜻을 바로 비교하기 어려워. 그래서 문장을 많은 숫자로 바꿔.

```text
“회의 일정은 다음 주 월요일입니다.”
↓
[0.12, -0.03, 0.88, ...]
```

이 숫자 묶음을 **임베딩**이라고 해.

뜻이 비슷한 문장은 숫자 모양도 비슷해져.

```text
“회의는 다음 주 월요일에 합니다.”
“다음 주 월요일 회의 일정”
```

두 문장은 단어 순서가 조금 달라도 뜻이 비슷하니까, 숫자도 가까운 곳에 놓이게 돼.

## 6. Vector DB는 숫자 서랍장이다

Vector DB는 임베딩 숫자를 저장하고, 비슷한 숫자를 빠르게 찾아주는 데이터베이스야.

청크 하나를 넣을 때는 숫자만 넣지 않아.

```text
청크 ID
파일 이름
본문
제목 경로
페이지 번호
원본 JSON 참조
임베딩 숫자
```

를 함께 저장해.

예시는 이래.

```json
{
  "chunk_id": "기획서:파일해시:실행번호:docling_hybrid:0",
  "chunk_text": "예산은 3천만 원으로 잡는다.",
  "heading_path": ["프로젝트 A", "예산 계획"],
  "page_numbers": [4],
  "source_refs": ["#/texts/82"],
  "vector": [0.12, -0.03, 0.88]
}
```

여기서 페이지 번호와 원본 참조는 나중에 “이 답은 몇 페이지에서 나왔는가?”를 알려주기 위해 저장하는 거야.

## 7. 사용자가 질문하면 찾는다

사용자가 이렇게 물어본다고 해보자.

```text
프로젝트 A의 예산은 얼마야?
```

시스템은 똑같이 질문도 숫자로 바꿔.

```text
질문
→ 임베딩 숫자
→ Vector DB에서 가장 비슷한 청크 찾기
```

그러면 Vector DB는 이런 청크를 찾아줄 수 있어.

```text
[프로젝트 A]
[예산 계획]
예산은 3천만 원으로 잡는다.
```

그리고 답변할 때는 출처도 같이 보여줄 수 있어.

```text
프로젝트 A의 예산은 3천만 원입니다.
출처: 기획서.pdf / 예산 계획 / 4페이지
```

## 8. 파일이 바뀌면 어떻게 하나?

기획서가 수정되면 예전 내용은 틀릴 수 있어.

```text
기존: 예산 3천만 원
수정: 예산 4천만 원
```

그래서 파일의 수정 버전이나 해시가 바뀌면:

```text
예전 청크 삭제 또는 비활성화
→ 새 PDF 다시 읽기
→ 새 청크 만들기
→ 새 임베딩 만들기
→ Vector DB에 다시 저장
```

이렇게 해야 오래된 예산 정보를 찾지 않아.

## 우리가 지금 만들 경로

지금은 가장 단순한 1번 방식만 만들 거야.

```text
PDF
→ Docling + EasyOCR
→ Docling JSON
→ Docling HybridChunker
→ 청크
→ 임베딩
→ Vector DB
→ 질문하면 관련 청크 찾기
```

아직 하지 않는 것:

```text
정규화 JSON 기반 자체 청커
semantic 청킹
reranker
복잡한 Drive 동기화
```

먼저 이 기본 길이 완주돼야 해.

> 문서를 읽고 → 알맞게 나누고 → 숫자로 바꾸고 → 저장하고 → 질문했을 때 관련 내용을 찾아주는 것.

이게 지금 우리가 만드는 첫 번째 목표야.

## 9. 청크가 너무 길지 않은지는 어떻게 아는가?

청크 길이는 글자 수가 아니라 **토큰(token) 수**로 알아.

토큰은 AI가 문장을 읽을 때 나누는 작은 조각이야. 한국어는 글자 수만 세면 정확하지 않아서, 반드시 임베딩 모델의 tokenizer로 세야 해.

```text
“예산은 3천만 원입니다.”
↓ tokenizer가 나눔
토큰 여러 개
↓
토큰 수 계산
```

우리가 확인할 길이는 본문 `text`가 아니라 제목까지 붙인 실제 임베딩 입력인 `contextualized_text`야.

```text
[프로젝트 A]
[예산 계획]
예산은 3천만 원으로 잡는다.
```

이 전체가 몇 토큰인지 세는 거야.

지금 A 방식 코드에서는 `all-MiniLM-L6-v2` tokenizer를 임시로 쓰고 있고, 이 모델은 보통 최대 512토큰 기준으로 다뤄. 그래서 첫 실험은 아래 기준으로 시작한다.

```text
최대 청크 길이: 512토큰
```

Docling `HybridChunker`는 제목 문맥까지 포함한 텍스트를 세면서, 512를 넘는 청크만 다시 나눈다.

다만 512가 항상 정답은 아니야. 실제 임베딩 모델을 정하면 다음 순서로 다시 맞춘다.

```text
임베딩 모델 선택
→ 그 모델의 tokenizer 사용
→ 그 모델이 받을 수 있는 최대 토큰 확인
→ 같은 tokenizer로 다시 청킹
```

실행 뒤에는 청크마다 토큰 수를 확인한다.

```text
청크 1: 180토큰
청크 2: 430토큰
청크 3: 510토큰
청크 4: 620토큰  ← 최대치 초과, 분할 필요
```

즉 지금은 512토큰으로 시작해 보고, 나중에 검색 결과를 보면서 너무 짧아 문맥이 부족한지, 너무 길어 관련 없는 내용이 섞이는지 확인해 조절하면 돼.
