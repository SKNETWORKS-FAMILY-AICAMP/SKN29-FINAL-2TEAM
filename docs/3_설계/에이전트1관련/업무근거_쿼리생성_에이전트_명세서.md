# 업무 근거 쿼리 생성 에이전트 및 업무 추출 오케스트레이션 명세

## 1. 목적

기존 업무 추출 에이전트는 하나의 목 문서 전체를 입력받아 필요한 필드만 추출했다. 목표 구조에서는 파싱·청킹된 비정형 문서가 VectorDB에 저장되므로, 업무 추출 에이전트가 필요한 근거를 단계별로 판단하고 별도의 쿼리 생성 에이전트에 검색어 생성을 요청한다.

실행은 사용자가 분석 대상 중 **대표 기획서 한 개를 선택**하는 것으로 시작한다. 선택한 문서 본문을 LLM에 직접 넣지 않고 `primary_document_id`를 State에 전달한다. 최초 `TASK_DISCOVERY` 검색은 이 대표 문서로만 제한해 업무 후보를 발견하고, 이후 보강 검색은 사용자가 허용한 `document_ids` 범위로 확장한다.

쿼리 생성 에이전트는 OpenAI API를 사용해 검색 목적에 맞는 짧고 구체적인 검색 질의를 생성한다. VectorDB 검색 결과는 원문 위치 정보와 함께 상태에 누적되며, 업무 추출 에이전트가 충분성을 다시 판단한다. 모든 필수 단계를 완료하거나 검색 한도에 도달하면 최종 업무를 추출한다.

## 2. 설계 원칙

1. 추출 에이전트가 업무 절차와 정보 충분성을 소유한다.
2. 쿼리 생성 에이전트는 업무를 추출하지 않고 검색 질의만 생성한다.
3. Retriever는 질의를 해석하지 않고 검색과 문맥 확장만 담당한다.
4. 최종 업무의 모든 핵심 값은 `document_id`, `chunk_id`, `page_numbers`, `text`로 추적 가능한 근거를 가진다.
5. 검색 횟수, Chunk 수, 중복 질의를 제한해 무한 루프와 비용 폭증을 방지한다.
6. 근거가 없으면 값을 만들지 않고 `missing_fields`와 경고를 남긴다.
7. 사용자가 선택하지 않은 문서를 시스템이 임의로 대표 기획서로 지정하지 않는다.

## 2.1 실행 시작 입력 계약

```json
{
  "project_id": "PROJECT-001",
  "primary_document_id": "DOC-001",
  "primary_document_title": "프로젝트 인증 기능 기획서",
  "document_ids": ["DOC-001", "DOC-002"],
  "analysis_goal": "프로젝트 수행 업무 추출"
}
```

- `primary_document_id`: 사용자가 기획서로 판단해 직접 선택한 대표 문서. 필수다.
- `primary_document_title`: 화면 표시 및 보조 검색 문맥. 본문 근거로 취급하지 않는다.
- `document_ids`: 후속 근거 검색이 허용된 전체 문서 범위이며 대표 문서를 포함해야 한다.
- 실행 전 대표 문서가 파싱 완료 및 VectorDB 색인 완료 상태인지 검증한다.

## 3. 고정 업무 추출 절차

| 순서 | Stage | Intent | 확인할 내용 | 다음 단계 조건 |
|---:|---|---|---|---|
| 0 | `TASK_DISCOVERY` | `TASK_DISCOVERY` | 대표 기획서에 명시된 수행 업무 후보와 직접 문장 | 하나 이상의 업무 후보 근거 확보 또는 검색 한도 도달 |
| 1 | `TASK_CORE` | `TASK_CORE` | 발견된 후보의 명시적 업무, 요구사항, 산출물, 완료 기준 | 최소 한 개의 실행 가능한 업무와 직접 근거 확보 |
| 2 | `ASSIGNMENT_REQUIREMENT` | `ASSIGNMENT_REQUIREMENT` | 역할, 책임, 기술, 경험 | 근거 확보 또는 검색 한도 도달 |
| 3 | `EXECUTION_CONDITION` | `EXECUTION_CONDITION` | 공수, 일정, 마감일, 우선순위, 의존성, 제약, 위험 | 근거 확보 또는 검색 한도 도달 |
| 4 | `FINAL_EXTRACTION` | 없음 | 누적 근거만 사용해 최종 업무 구조화 | 항상 `finalize`로 이동 |

`TASK_CORE`만은 직접 업무 근거가 없으면 업무를 생성하지 않는다. 나머지 단계는 근거가 부족해도 검색 한도 도달 후 누락 상태로 진행할 수 있다.

## 4. 에이전트 책임

### 4.1 업무 추출 에이전트

- 현재 Stage와 누적 근거를 검토한다.
- 최초 실행에서 사용자 선택 대표 문서를 기준으로 `TASK_DISCOVERY`를 수행한다.
- 현재 단계에 필요한 정보가 무엇인지 `SearchNeed`로 기술한다.
- 근거가 부족하면 `SEARCH`를 반환한다.
- 근거가 충분하면 다음 Stage로 이동한다.
- 최종 단계에서는 누적 근거만 사용해 `ExtractedTask[]`를 생성한다.
- 근거 없는 역할·기술·공수·날짜를 추정하지 않는다.

### 4.2 업무 근거 쿼리 생성 에이전트

- 입력받은 `SearchNeed`, 문서 범위, 이미 사용한 질의를 바탕으로 검색 질의를 생성한다.
- 한 번의 요청에서 기본 1개, 최대 3개의 질의를 생성한다.
- 업무 결과나 사람 추천 결과를 생성하지 않는다.
- 이전 질의를 단순 반복하지 않는다.
- Vector 검색에 적합하도록 핵심 명사, 동작, 산출물, 조건을 포함한다.

### 4.3 VectorDB Retriever

- `project_id`와 `document_ids`로 테넌트·문서 범위를 강제한다.
- `TASK_DISCOVERY`에서는 검색 범위를 `[primary_document_id]`로 강제한다.
- 질의 임베딩 검색 후 `same_heading`, `previous_chunk`, `next_chunk` 문맥을 확장한다.
- 이미 본 `chunk_id`는 제외하거나 낮은 우선순위로 처리한다.
- 정상적인 무검색 결과는 오류가 아니라 `chunks: []`로 반환한다.

## 6. StateGraph 상태

| 필드 | 설명 |
|---|---|
| `project_id`, `document_ids` | 프로젝트 및 후속 검색 허용 범위 |
| `primary_document_id` | 사용자가 선택한 대표 기획서 ID. 최초 검색 범위 |
| `primary_document_title` | 사용자 화면 표시 및 보조 문맥 |
| `stage_index`, `stages` | 고정 추출 절차와 현재 위치 |
| `search_need` | 추출 에이전트가 쿼리 에이전트에 전달한 부족 정보 |
| `query_plan` | 쿼리 에이전트가 생성한 검색 계획 |
| `query_history` | 중복 질의 방지와 감사 추적 |
| `evidence_chunks` | 중복 제거된 누적 검색 근거 |
| `stage_attempts` | 단계별 검색 횟수 |
| `max_attempts_per_stage` | 단계별 최대 검색 횟수. 기본값 2 |
| `max_total_chunks` | LLM에 전달할 최대 누적 Chunk 수. 기본값 20 |
| `extracted_tasks` | 최종 구조화 업무 |
| `warnings`, `trace` | 누락·검색 종료 이유 및 실행 추적 |

## 7. 라우팅 규칙

| 출발 노드 | 조건 | 도착 노드 |
|---|---|---|
| `validate_selection` | 대표 기획서가 선택되고 색인 완료 | `extract_tasks_agent`의 `TASK_DISCOVERY` |
| `validate_selection` | 선택 누락, 범위 불일치, 미색인 | 오류 종료 |
| `extract_tasks_agent` | `action=SEARCH`이고 한도 미도달 | `query_generation_agent` |
| `extract_tasks_agent` | 현재 단계 근거 충분 | 다음 단계로 갱신 후 자기 자신 |
| `extract_tasks_agent` | `action=FINALIZE` | `task_tools` |
| `query_generation_agent` | 정상 QueryPlan 생성 | `vector_search` |
| `vector_search` | 성공 또는 빈 결과 | `merge_evidence` |
| `merge_evidence` | 항상 | `extract_tasks_agent` |
| `task_tools` | 업무 검증·저장 완료 | `calculate_workloads` |
| `calculate_workloads` | 업무 존재 | `analyze_candidates` |
| `calculate_workloads` | 업무 없음 | `finalize` |
| `analyze_candidates` | 항상 | `finalize` |
| `finalize` | 항상 | `END` |

## 8. 종료 및 안전장치

- 단계별 검색은 기본 2회까지만 허용한다.
- 대표 기획서 선택이 없으면 그래프를 시작하지 않는다.
- `primary_document_id`가 `document_ids`에 포함되지 않으면 입력 오류로 처리한다.
- 같은 정규화 질의를 반복 생성하면 QueryPlan에서 제거한다.
- `document_id + chunk_id` 기준으로 근거를 중복 제거한다.
- 누적 Chunk가 20개를 넘으면 검색 점수와 단계 관련성을 기준으로 자른다.
- `TASK_CORE` 직접 근거가 없으면 빈 업무 목록으로 종료한다.
- 보조 필드가 없으면 `null`, `[]`, `missing_fields`를 사용한다.
- VectorDB 장애와 정상 빈 결과를 구분한다.
- OpenAI API 키와 VectorDB 비밀번호는 환경 변수로만 주입한다.

## 9. VectorDB 실제 연동 교체 지점

노트북의 `VectorRetriever` Protocol은 아래 메서드 하나만 요구한다.

```python
def search(
    *,
    project_id: str,
    document_ids: list[str],
    queries: list[str],
    intent: str,
    top_k: int,
    exclude_chunk_ids: list[str],
) -> list[RetrievedChunk]: ...
```

목 구현의 `InMemoryVectorRetriever`를 실제 pgvector 또는 검색 API Adapter로 교체하면 StateGraph 로직은 유지된다.

## 10. 수용 기준

1. 사용자가 대표 기획서 한 개를 선택해야 실행할 수 있다.
2. 초기 입력에 문서 본문 없이 `primary_document_id`와 검색 범위만 전달한다.
3. 최초 업무 발견 검색은 대표 기획서 안에서만 수행된다.
4. 추출 에이전트가 단계별 부족 정보를 명시하고 쿼리 에이전트가 이를 검색문으로 변환한다.
5. 검색 결과가 추출 에이전트로 되돌아가 다음 판단에 반영된다.
6. 모든 최종 업무에는 하나 이상의 `evidence_chunk_ids`가 있다.
7. 근거 없는 값은 추정하지 않고 누락 필드로 표시한다.
8. 반복 한도에 의해 그래프가 항상 종료된다.
9. Retriever Adapter만 교체해 실제 VectorDB에 연결할 수 있다.
