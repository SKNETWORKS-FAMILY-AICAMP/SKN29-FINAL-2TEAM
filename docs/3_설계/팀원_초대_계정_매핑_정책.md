# 팀원 초대·계정 매핑 정책

## 배경

팀장이 플랫폼에 가입하고 HR Connector를 연결하면 People DB에 조직·구성원(`org`/`person`) 데이터가 채워진다. 이 시점에는 아직 아무도 플랫폼 로그인 계정(`user_account`)을 갖고 있지 않다. 팀원이 실제로 로그인해서 자신의 배정 업무를 보려면, 언젠가 `user_account`와 `person`이 연결돼야 한다.

이 문서는 그 연결(매핑)을 **누가 신뢰의 주체가 되어, 어떤 근거로** 만드는지에 대한 정책을 정리한다.

## 핵심 원칙

1. **AI 추천·업무 배정의 대상은 항상 `PERSON`이지 `USER_ACCOUNT`가 아니다.** HR 직원이 아직 가입하지 않았어도 후보 추천에는 포함된다. 회원가입 여부는 별개 문제다.
2. **초대 가입의 `USER_ACCOUNT` ↔ `PERSON` 매핑은 이메일 비교로 판단하지 않는다.** 초대 코드가 특정 `PERSON`에 미리 연결되어 있고, 그 코드를 아는(=팀장에게 전달받은) 사람만 수락할 수 있다는 "링크 소유 = 신원 확인" 모델을 쓴다. 직접 가입한 팀장의 본인 매핑은 별도 흐름으로, People DB 커넥터에서 가입 이메일과 HR 이메일이 일치하는 `PERSON`을 사용자가 확인한 시점에 `SELF_EMAIL`로 기록한다.
3. **인증 주체는 플랫폼 운영자가 아니라 각 팀의 팀장이다.** 팀장이 "이 초대는 HR 직원 아무개에게 전달한다"고 지정하는 순간 신원 확인 책임은 팀장에게 위임된다. 플랫폼은 그 초대 코드가 안전하게(해시로만 저장, 1회용, 만료) 관리되는 것만 보장한다.
4. **기존 구조를 최대한 재사용한다.** ~~새 테넌트(`TEAM`) 개념이나~~ 새 회원 역할을 만들지 않는다.
   > **2026-07-31 정정 — `TEAM`은 결국 만들었다.** 조직도만으로는 경계를 정할 수 없다는 것이 확인됐다. 회사를 기준으로 잡으면 과다 노출이고(팀장이 전 직원 56명을 봤다), 조직을 기준으로 잡으면 팀원 한 명만 놓고는 어디까지가 우리 그룹인지 알 수 없다. 그래서 팀장이 온보딩에서 팀명을 적어 `team`·`team_member`를 명시적으로 만든다. **새 회원 역할을 만들지 않는다는 부분은 그대로 유효하다** — 역할은 여전히 가입 경로로 판정한다. [[HR_어댑터와_테넌트_경계]]
   - 초대 권한 범위 = 초대자 본인이 연결된 `person.org_id`부터 `org.up_org_id` 재귀로 이어지는 하위 조직 전체. **여기에 더해 초대자가 팀을 이미 만들었어야 한다** — 팀이 없으면 초대가 `PermissionDenied`로 거부된다. 초대는 초대자의 팀을 실어 나르고, 수락하면 그 팀이 새 계정의 테넌트가 되기 때문이다.
   - 팀장/팀원 역할은 가입 경로로 판단한다. `TEAM_INVITATION` 매핑만 팀원이며, 직접 가입은 팀장이다. `org.mgr_id`는 역할 판정에 사용하지 않는다.
   - 매핑 근거 저장은 `person_link`(외부 시스템·이메일 매칭용)를 재사용하지 않고, 이메일이 아닌 초대 코드 기반이라는 점이 명확히 드러나도록 `member_invite` / `user_person_link`를 별도로 둔다.

## 플로우

```text
팀장 직접 가입
→ People DB 커넥터에서 가입 이메일과 일치하는 PERSON 후보 확인
→ 사용자가 본인임을 확인
→ user_person_link 생성 (mapping_status=VERIFIED, match_method=SELF_EMAIL)
→ 팀장이 자신의 org 하위 트리에서 PERSON 선택 + 팀명 입력
→ team 생성 · team_member 저장 (팀장 자신도 자동 포함)
→ user_account.team_id = 새 팀
→ member_invite 발급 (team_id 포함, token_hash만 저장, 원문은 팀장에게 1회 노출 후 폐기)
→ 팀원이 초대 코드로 가입
→ user_person_link 생성 (mapping_status=VERIFIED, match_method=TEAM_INVITATION)
→ user_account.team_id = 초대의 팀 · team_member에 추가
```

팀 생성과 초대 발급은 **같은 화면(팀원 선택 모달)에서 연속으로 일어난다.** 팀명 입력란의 기본값은 팀장의 HR 소속 조직명이고, 팀장은 그대로 두거나 바꿀 수 있다. 팀을 만들지 않으면 초대 자체가 불가능하다.

People DB의 이메일 조회는 커넥터 모달에서 본인 후보를 보여 주는 단계일 뿐, 확인 전에는 매핑이나 연결 상태를 저장하지 않는다. 일치하는 활성 `PERSON`이 없거나 이미 다른 계정과 연결돼 있으면 People DB 연결이 실패하며, HR 기반 팀원 조회·초대 기능도 열리지 않는다.

### 팀원 측 UX 흐름

초대 코드 전달 수단은 팀장 재량이므로(핵심 원칙 3), 플랫폼은 이메일 발송 기능 없이 로그인 페이지에 코드 입력 탭만 제공한다.

1. 로그인 페이지의 "초대 코드 입력" 탭에서 코드를 입력하면, 가입 페이지로 넘어가기 전에 먼저 코드 유효성(존재/미만료/PENDING 여부)을 검증하고 대상 `PERSON` 이름을 보여준다.
2. 유효하면 초대 토큰을 쿼리 파라미터로 실어 가입 페이지로 이동한다(예: `/signup?invite=<token>`). 코드를 다시 입력하게 하지 않는다.
3. 이메일·비밀번호 계정 가입 완료 직후, 넘어온 토큰으로 `user_person_link`를 자동 생성한다.

### 팀장 측 초대 범위와 화면 표시

- 권한 범위는 팀장에게 연결된 `person.org_id`와 그 하위 조직 전체다.
- 모달은 본인 조직 구성원을 기본 표시·선택한다.
- 하위 조직 구성원은 기본적으로 접혀 있고 자동 선택하지 않는다. 팀장이 펼친 뒤 명시적으로 선택해야 한다.
- 이 구분은 화면 편의 정책이며, 서버의 권한 검증 범위는 항상 하위 조직 전체를 기준으로 한다.

## 데이터 모델

`DB/schema.sql` 참고. 둘 다 다른 테이블과 동일하게 FK는 걸지 않고, `backend/db/repositories.py`의 `_require_record()`로 참조 존재 여부를 애플리케이션 레벨에서 검증한다.

### `member_invite`

| 필드 | 의미 |
|---|---|
| invite_id | PK |
| team_org_id | 초대 스코프 **조직**(`mock_hr.org.org_id`) — 발급 당시 어느 HR 조직 범위였는지의 기록 |
| team_id | 초대 대상 **팀**(`team.team_id`, 2026-07-31 추가) — 수락하면 이 팀이 새 계정의 테넌트가 된다 |
| person_id | 연결 대상 HR 직원(`mock_hr.person.person_id`) |
| invited_by | 초대한 팀장 계정(`user_account.account_id`) |
| token_hash | 초대 코드 해시(원문 미저장) |
| status | PENDING / ACCEPTED / EXPIRED / REVOKED |
| expires_at | 만료 시각 |
| accepted_at | 수락 시각 |

같은 `person_id`에 `PENDING` 상태 초대가 동시에 두 개 이상 존재할 수 없도록 부분 유니크 인덱스(`ux_member_invite_pending_person`)로 강제한다.

`team_org_id`와 `team_id`는 다른 것이다. 전자는 **HR 조직**(고객사 인사 시스템의 소속), 후자는 **우리 플랫폼의 팀**이다. 권한 검증은 여전히 조직 트리로 하고(초대할 수 있는 사람의 범위), 수락 후의 소속은 팀으로 정해진다(볼 수 있는 사람의 범위). 두 축을 한 컬럼으로 합치지 않은 이유는 HR 조직이 고객사 사정에 따라 바뀌어도 우리 팀 구성은 그대로여야 하기 때문이다.

### `user_person_link`

| 필드 | 의미 |
|---|---|
| link_id | PK |
| account_id | 플랫폼 계정(`user_account.account_id`) |
| person_id | HR 직원(`person.person_id`) |
| invite_id | 근거가 된 `member_invite`(추적용) |
| mapping_status | VERIFIED / REVOKED |
| match_method | `TEAM_INVITATION`(초대 가입) / `SELF_EMAIL`(직접 가입자의 People DB 본인 확인) |
| linked_at / revoked_at | 연결·해제 시각 |

`mapping_status = VERIFIED` 기준으로 `person_id` 1개는 계정 1개에만 연결되도록 부분 유니크 인덱스(`ux_user_person_link_active_person`)로 강제한다(같은 계정이 여러 팀의 서로 다른 `PERSON`에 연결되는 것은 막지 않는다 — `account_id`는 유니크하지 않다).

## 필수 검증 규칙과 구현 위치

| 규칙 | 구현 위치 |
|---|---|
| 초대 코드는 1회만 사용 | `member_invite.status`를 PENDING→ACCEPTED로 전이시키는 트랜잭션에서 `WHERE status='PENDING'` 조건부 UPDATE로 경합 방지 |
| 초대 코드 만료 | `expires_at` 컬럼 + 수락/조회 시점에 lazy 체크(배치 작업 없음, MVP 범위 밖) |
| 이미 다른 계정과 연결된 PERSON 재연결 차단 | `ux_user_person_link_active_person` 부분 유니크 인덱스 |
| 동시 PENDING 초대 중복 발급 차단 | `ux_member_invite_pending_person` 부분 유니크 인덱스 |
| 팀장은 자신의 HR Connector 범위 내 PERSON만 초대 가능 | 직접 가입 계정이 People DB에서 `SELF_EMAIL` 매핑을 완료해야 범위가 생긴다. Repository 계층에서 연결된 `person.org_id` 기준 `org` 재귀 조회로 `team_org_id`/`person_id`가 하위 트리에 속하는지 검증한다. |
| 초대 취소 시 미수락 코드 즉시 무효화 | `status`를 REVOKED로 전이(하드 삭제 안 함 — 감사 추적 유지) |
| 잘못된 연결 해제 시 감사 로그 | 기존 `audit_log`(`action='REVOKE_LINK'` 등) 재사용, 새 로그 테이블 없음 |
| 초대 코드 원문 미저장 | `token_hash`만 저장, 원문은 발급 응답에서 1회 노출 후 서버에 남기지 않음 |

## 의도적으로 다루지 않은 것

- **초대 가입의 이메일 매칭 폴백**: 초대 가입은 이메일이 아니라 코드가 가리키는 `PERSON`을 신뢰하므로 `SELF_EMAIL`로 대체하지 않는다. 팀장이 잘못된 사람에게 코드를 전달하면 잘못된 계정이 매핑될 수 있다는 트레이드오프를 감수한다. `SELF_EMAIL`은 직접 가입한 팀장이 People DB 연결 모달에서 본인을 확인할 때만 사용한다.
- **만료 배치 작업**: `status=PENDING`이지만 `expires_at`이 지난 초대를 주기적으로 `EXPIRED`로 바꾸는 스케줄러는 아직 없다. 조회/수락 시점에 만료 여부를 확인하는 lazy 체크로 충분한 MVP 범위로 본다.
- **Jira 계정 셀프 연동**: 팀원의 Jira 이메일이 HR 이메일과 다를 수 있다는 문제는 이 정책이 다루지 않는다. Jira Connector는 **팀장 계정 기준으로 구현됐지만**(계정 단위 `connector_conn`), 팀원이 본인 Jira 계정을 직접 연동하는 흐름은 없다. 가입 시 입력 또는 마이페이지를 통한 셀프 연동은 MVP 이후로 미룬다. 그 전까지 Jira 매칭이 필요하면 `person_link`(이메일 기반)를 잠정적으로 쓴다.
- **마이페이지 전반**: Jira 셀프 연동 카드를 제외한 개인 환경설정·마이페이지 기능은 MVP 범위 밖이다.

## 시나리오: 팀장 가입부터 팀원 연동까지

```text
1. 팀장(김민우)이 초대 코드 없이 이메일·비밀번호로 직접 가입한다.
2. People DB 커넥터를 연동하고, 가입 이메일로 찾은 자신의 PERSON 레코드를 확인한다. 이 시점에 `SELF_EMAIL` 매핑이 생성된다.
3. 시스템이 김민우의 org_id 하위 트리에 속한 PERSON 목록(팀원 후보)을 보여준다.
4. 김민우가 팀원(박서준)을 선택해 member_invite를 발급받는다 (초대 코드는 이 순간 1회만 노출된다).
5. 김민우가 그 코드를 박서준에게 전달한다(이메일 등, 전달 수단은 팀장 재량).
6. 박서준이 코드로 접속해 이메일·비밀번호 계정을 만들고 초대를 수락한다.
7. user_person_link가 mapping_status=VERIFIED로 생성되어, 이후 박서준은 로그인 시 자신에게 배정된 업무를 확인할 수 있다.
```
