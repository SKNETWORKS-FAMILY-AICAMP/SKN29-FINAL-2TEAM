# 역할별 권한 정책 (운영자 / 팀장 / 팀원)

## 배경

설정·마이페이지·대시보드 화면을 설계하기 전에, 운영자·팀장·팀원 세 역할이 각각 무엇을 **조회**할 수 있고, 무엇을 **수정**할 수 있고, 무엇을 **설정**할 수 있는지부터 정리한다. 화면 레이아웃은 이 문서의 범위가 아니다.

## 핵심 원칙

1. **People DB(조직·인력)의 원천은 HR Connector다.** 어떤 역할도 `org`/`person` 데이터를 직접 수정하지 않는다 — 운영자를 포함해 전 역할이 조회만 가능하다. HR 쪽과 어긋나는 걸 막기 위함이다. 2026-07-31부터 이 8개 테이블은 `mock_hr` 스키마에 있고 `backend/services/hr/` 어댑터만 읽는다. 애플리케이션 코드에 쓰기 경로가 아예 없다.
2. **운영자는 새로운 회원 역할이 아니라 플랫폼을 개발·운영하는 팀 본인이다.** `user_account`에 role 컬럼이나 별도 권한 테이블을 추가하지 않고, 이메일 하드코딩 allowlist로 식별한다.
3. **팀장/팀원 구분은 가입 경로로 판단한다.** 초대 코드로 가입해 `user_person_link.match_method='TEAM_INVITATION'`으로 연결된 계정만 팀원이며, 그 외 직접 가입 계정은 팀장으로 본다. HR 시스템 연결 권한이 회사에서 팀장에게만 주어진다는 전제에 따른 정책이다. `org.mgr_id`는 조직의 관리자 정보일 뿐 로그인 역할 판정에는 사용하지 않는다.
4. **운영자 페이지의 보안 경계는 URL이 아니라 별도 로그인이다.** 관리자 페이지는 팀장·팀원이 쓰는 일반 이메일·비밀번호 로그인과 별개로 자체 로그인(`/ops/login` 등)을 두고, 환경변수에 등록된 운영자 자격 증명과 대조한다. URL을 내비게이션에 노출하지 않는 것은 일반 사용자 혼란을 줄이는 부가 조치일 뿐, 그 자체를 보안 경계로 삼지 않는다.

### 팀장/팀원 판정과 HR 매핑

| 구분 | 직접 가입(팀장) | 초대 코드 가입(팀원) |
|---|---|---|
| 역할 판정 근거 | 초대 코드 없이 가입 | 유효한 `member_invite`를 사용해 가입 |
| `user_person_link.match_method` | People DB 연결 시 `SELF_EMAIL` | 가입 시 `TEAM_INVITATION` |
| HR 매핑 시점 | 가입 직후가 아니라 People DB 커넥터에서 본인 확인을 완료한 시점 | 초대 코드 수락과 가입이 완료된 시점 |
| HR 매칭 실패 | People DB 온보딩이 중단되므로 팀원 조회·초대 권한이 열리지 않음 | 초대 코드가 연결한 `PERSON`을 사용하므로 이메일 자동 매칭하지 않음 |

서버는 별도 `role` 컬럼을 저장하지 않고 현재 활성 매핑의 `match_method`로 응답 역할을 계산한다. 직접 가입자가 아직 People DB를 연결하지 않았더라도 계정 역할은 팀장이지만, `person` 연결과 `scope_org_ids`가 없으므로 실제 HR 기반 조회·초대 기능은 사용할 수 없다.

초대 화면의 **기본 표시 범위**와 **권한 범위**는 구분한다.

- 기본 표시: 본인의 `person.org_id`와 같은 조직의 구성원
- 권한 범위: 본인 조직과 `org.up_org_id` 재귀로 연결된 모든 하위 조직
- 하위 조직은 화면에서 기본적으로 접어 두며, 사용자가 펼쳐야 선택할 수 있다.

## 역할별 권한 매트릭스

| | 조회 | 수정 | 설정 |
|---|---|---|---|
| **운영자** | 전체 **팀** 목록(`team`), 전체 계정 현황, 전체 Connector 연결 상태(`connector_conn`), 초대 발급/수락 현황 전체(`member_invite`), 감사 로그(`audit_log`), 전체 프로젝트 현황. **HR 조직도는 보지 않는다** — 고객사 내부 사정이다 | 계정 상태 변경(`user_account.account_status`), 문제 있는 `user_person_link` 강제 해제, 이상 초대 코드 폐기 | 플랫폼 전역 정책(초대 만료 기간 등 상수), 시스템 공지 |
| **팀장** | **본인 팀의 팀원 목록**(`team_member` 기준. 조직도 전체가 아니다), 팀원 업무량·부재 현황(`sched`/`absence`), 본인이 소유한 프로젝트, 본인이 보낸 초대 발급 현황 | 팀원 초대 발급/취소(`member_invite`), 프로젝트 생성 및 Connector 소스 연결(`proj_source`), 문서 역할 지정(`doc.doc_role`), 업무 배정 후보 수정·최종 승인, 팀원 프로젝트 접근 권한(`proj_member.access_role`, 프로젝트 화면에서 처리) | People DB·Drive·Jira 연결, 팀 업무 배정 기준 |
| **팀원** | 본인에게 배정된 업무, 본인 프로필/스킬(읽기 위주), 배정 결과 알림 | 본인 부재/일정 등록, (동의 시) 본인 스킬 정보 갱신 요청 | Jira 셀프 연동(현재 데모), 알림 환경설정 |

## 화면 배치 원칙

매트릭스의 "조회/수정" 항목이 실제로 어느 화면에 놓이는지는 아래 기준을 따른다.

- **조회 → 역할별 대시보드.** 팀장 대시보드와 팀원 대시보드는 서로 다른 화면이다(팀장은 조직·팀 워크로드 중심, 팀원은 본인 배정 업무 중심). 운영자의 조회 화면은 관리자 페이지 내부에 있다.
- **수정은 두 종류로 나뉜다.**
  - **업무 처리(워크플로우성 수정)**: 업무 배정 후보 수정·최종 승인, 팀원 초대 발급/취소 같은 행위는 그 일이 실제로 일어나는 기존 업무 흐름 화면(추천 결과 화면, 초대 플로우 등)에서 처리한다. 별도 "설정" 메뉴로 옮기지 않는다.
  - **환경설정성 수정**: Connector 연동, 팀 업무 배정 기준처럼 반복적으로 안 바뀌는 구성 값만 설정 페이지에 둔다. 팀원 프로젝트 접근 권한처럼 프로젝트 단위로 스코프가 다른 값은 설정 페이지가 아니라 해당 프로젝트 화면에 둔다. PASS/CONDITIONAL/REJECT 판정 로직 자체는 "결정론적 계산 코드"이지 팀장이 바꾸는 설정이 아니므로 설정 화면에 노출하지 않는다.
- **설정 페이지도 역할별로 분리**: 팀장 설정 / 팀원 설정(=팀원 마이페이지와 통합) / 운영자 설정(=관리자 페이지 내부).

## 화면별 상세 메뉴

팀원 초대는 프로젝트별 업무 배정과 달리 반복적인 "팀 관리" 성격이라, 워크플로우 화면이 아니라 팀장 설정 안에 둔다(화면 배치 원칙의 "업무 처리" 예외).

### 팀장 대시보드 (기존 `MainDashboardPage` 유지)

- 조직도 / 팀 워크로드 / 업무 현황 / 캘린더 / 최근 업데이트

### 팀원 대시보드 (신규)

1. 내 업무 목록 (진행중/완료/대기 상태별)
2. 최근 배정·변경 알림
3. 내 일정·부재 요약(등록 바로가기)

### 팀장 설정 (`TeamLeaderSettingsPage`) — 구현 완료

1. 연동 관리 — **People DB·Google Drive·Jira 모두 실제 연결 구현 완료.** Drive·Jira는 OAuth 인가 흐름으로 연결하고, 연결 후 읽을 폴더·프로젝트를 골라 `proj_source`에 저장한다([[Jira_Drive_커넥터_연결_설계]]). 문서 본문 파싱은 별도 진행 중이다.
2. 팀원 관리 — **구현 완료**. 본인 조직·하위 조직 팀원 조회, 초대 발급/현황(PENDING/ACCEPTED/EXPIRED), 초대 취소
3. 팀 업무 배정 기준 — 기준 근무시간(주 단위), 과부하 경고 임계값(%), 개인 근무시간 없는 팀원에게 적용되는 기본값(`CapacityPolicy`, `업무_분배_필수_데이터_정의서.md` §9). **구현 완료**(`TeamLeaderSettingsPage`). PASS/CONDITIONAL/REJECT 판정 로직 자체는 결정론적 계산 코드이므로 여기서 편집하지 않는다.
   - 최소 후보 수, 데이터 부족 시 처리 방식(CONDITIONAL vs BLOCKED, `업무_분배_로직_및_API_데이터_최종안.md` §4~5)은 후순위로 미룬다. 실제 추천 엔진이 붙기 전까지는 화면에 필드를 추가할 실익이 없다.

### 팀원 설정 (`TeamMemberSettingsPage`) — 구현 완료

1. 내 프로필 — HR 연동 정보(읽기 전용) + 계정 정보
2. 계정 연동 — Jira 셀프 연동
3. 알림 설정

### 운영자 콘솔 (`/ops`, 별도 로그인) — 8개 화면 구현 완료 (2026-07-31)

1. 운영 현황 — 팀 수·계정·커넥터·초대 통계와 최근 활동
2. **팀 현황** — 플랫폼을 쓰는 팀 목록과 팀별 계정 현황(읽기 전용). 행을 누르면 그 팀의 계정 목록으로 간다
3. 계정 관리 — 전체 계정 상태 변경(정지/재활성), 잘못된 직원 연결 해제
4. 계정 연결·초대 현황 — 모든 팀의 초대·연결 오류 조회 및 강제 해제
5. 연결 서비스 현황 — Drive·Jira 연동 상태(연결/만료/에러). People DB는 제외
6. 감사 로그 — 운영 활동 + 분석·결정 기록 4종
7. 전역 정책 — 초대 만료 기간, 시스템 공지

> 2번은 원래 `조직 현황(전체 org 조회)`이었으나 **팀 현황으로 교체**했다. 조직도는 고객사 HR 내부 사정이라 운영자가 열람할 자리가 아니고, 운영자가 알아야 하는 것은 "플랫폼을 쓰는 팀이 몇이고 그 안이 어떤 상태인가"다. 같은 이유로 콘솔 전 화면에서 고객사 직원 번호·조직 번호 표시를 뺐다. 화면별 상세는 [[운영자 콘솔 기능]], API는 [[운영자콘솔_api_처리]].

## 현재 구현의 제약

- **프로젝트 조회는 소유자 기준이다.** `GET /api/projects/`가 `owner_account_id`로만 필터하고 `proj_member`를 보지 않는다. `proj_source`·`documents`도 소유자만 수정할 수 있다. 팀장 온보딩에는 충분하지만, **팀원 대시보드를 붙일 때는 `proj_member`를 함께 봐야 한다.** 매트릭스의 팀원 "본인에게 배정된 업무" 조회가 여기에 걸린다.

## 의도적으로 다루지 않은 것

- **화면 레이아웃**: 설정/마이페이지/대시보드의 실제 UI 구성은 이 문서 이후 별도로 설계한다.
- **운영자 allowlist 저장 위치**: 환경변수로 둘지 DB 테이블로 둘지는 구현 시점에 결정한다. 규모상(개발팀 소수 인원) 별도 권한 테이블은 과함.
- **운영자의 계정 상태 변경 이력 감사 세부 규칙**: `audit_log` 재사용은 확정이나, 어떤 액션 코드를 쓸지는 구현 시점에 정한다.
- **Figma 목업(관리자 설정 3탭)의 조직 구조 편집·동기화 설정**: 핵심 원칙 1(HR Connector가 원천) 위반이라 채택하지 않는다.
- **Figma 목업의 역할별 권한 매트릭스 편집기(팀장/사원/인턴 체크박스)**: 핵심 원칙 2(새 권한 테이블을 만들지 않는다)와 충돌하고, "인턴"이라는 새 역할도 이 문서 범위 밖이라 채택하지 않는다.
- **Figma 목업의 백업 실행·아카이브 저장소 변경·데이터 갱신 주기 세부 설정**: 소수 개발팀이 쓰는 내부 운영 페이지 범위를 넘는 인프라 운영 기능이라 채택하지 않는다.
