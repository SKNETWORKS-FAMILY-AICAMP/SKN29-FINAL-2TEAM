## 1. 지금까지 만든 파싱 전략 요약

### 1.1 무엇을 하는가

```text
PDF/DOCX 원문
   ↓ PDF Backend / DOCX 구조 해석
텍스트·좌표·글꼴 추출
   ↓ Layout Model
본문·제목·표·그림 영역 분류
   ↓ OCR (EasyOCR, ko+en)
> ⚠ **2026-08-05 — OCR 은 조건부다.** 텍스트 레이어가 있는 PDF 는 OCR 을 건너뛰고
> 문서 자신의 텍스트를 쓴다. OCR 이 멀쩡한 본문을 자모 단위로 덮어써서 「중도탈락을」
> 이 「중도달락올」로 적재되던 것을 고친 결과다. 스캔본은 그대로 EasyOCR 로 읽는다.

이미지·스캔 영역의 글자 인식
   ↓ TableFormer (Accurate + Cell Matching)
표의 행·열·병합 셀 구조 복원
   ↓ Reading Order + Heading Hierarchy
읽기 순서 조립, 제목 깊이 추론
   ↓
구조가 보존된 Markdown + Docling JSON
```

목표는 "PDF를 텍스트로 뽑는 것"이 아니라 **문서 구조(제목 깊이·표의 행렬·읽기 순서)가 보존된 JSON**을 만드는 것이다. 컴퓨터에게 PDF는 사람처럼 "문서"가 아니라 글·표·그림이 좌표로 흩어진 평면이라서, 다음 세 가지를 각각 따로 판단해야 한다.

```text
텍스트 인식  = 어떤 문자열이 존재하는가
레이아웃 분류 = 그 영역이 본문·제목·표·그림 중 무엇인가
구조 추론    = 제목 깊이, 표의 행·열, 읽기 순서가 어떻게 연결되는가
```

### 1.2 지금 구현 범위

| 구분 | 현재 구현 |
|---|---|
| 입력 | PDF, DOCX |
| 출력 | Markdown, Docling JSON |
| OCR 엔진 | EasyOCR |
| OCR 언어 | 한국어 + 영어 |
| OCR 영역 | Layout Model이 검출한 영역만 (전체 페이지 X) |
| 헤딩 계층 | 활성화 (Bookmark·번호·글꼴 스타일 기반 깊이 추론) |
| 표 구조 분석 | 활성화 (Accurate 모드 + Cell Matching) |
| 그림 분류·설명·차트 추출 | 활성화 (경로만 확보, 정확도 고도화는 다음 단계) |

### 1.3 기본값을 그대로 쓰지 않고 의도적으로 튜닝한 값

> 아래 표는 슬라이드에 넣지 않는다. 발표 멘트나 질의응답에서 "왜 이렇게 설정했나"라는 질문이 나왔을 때 답하는 용도다(3절, 6절 참고). 슬라이드는 문제·검증·발견한 이슈에 집중하고, 파라미터 디테일은 말로만 짧게 짚는다.

| 파라미터 | 선택값 | 이유 |
|---|---|---|
| OCR 언어 | `ko + en` | 한국어 본문과 영문 제품명·약어가 섞인 실제 기업 문서에 대응 |
| OCR 영역 | `LAYOUT_REGIONS` | 페이지 전체가 아닌 Layout Model이 찾은 영역만 인식해 처리량·중복 인식 감소, 같은 조건으로 반복 비교 가능 |
| 표 구조 | `Accurate + Cell Matching` | 기본(Fast) 모드보다 느리지만 예측한 셀을 원문 텍스트와 재대조해 병합 셀·복잡한 표에서도 구조가 깨지지 않음 |
| 헤딩 계층 | 활성화 | Bookmark·번호·스타일 단서로 제목 검출과 별개로 "깊이"까지 추론 |

### 1.4 검증 방식 — 5단계 디버그 이미지

파이프라인 결과를 "됐겠지"로 넘기지 않고, 각 단계를 실제 이미지로 뽑아 확인한다.

```text
① cells                PDF Backend가 무엇을 읽었는가
② ocr                  필요한 이미지 글자를 OCR이 제대로 읽었는가
③ raw_layout           모델이 영역·라벨을 맞게 예측했는가
④ postprocessed_layout 후처리 뒤에도 구조가 유지되는가
⑤ Final JSON           읽기 순서·계층이 최종적으로 맞는가
```

이 검증 과정에서 실제 문서(디스플레이 장비 기업 리서치 보고서, 5페이지)를 넣어 3가지 실패 유형을 직접 찾아냈고, 각각 원인과 보완 방향까지 정리해 두었다(4절 참고). "실행해봤더니 잘 됐다"가 아니라 "실행해보고 어디서 왜 깨지는지 확인했다"는 것이 이 파트의 핵심 근거다.

> 실제 검증은 5단계로 했지만, 슬라이드에서 5단계를 전부 나열하지는 않는다(5절 참고). 발표에서는 `raw_layout`(모델이 어떻게 판단했는가) → `postprocessed_layout`(후처리로 뭐가 달라졌는가) 두 단계를 크게 보여주고, `cells`는 작게 곁들이는 정도로 압축한다. 개발 과정 자체는 5단계 그대로이고, 압축되는 건 슬라이드 전달 방식뿐이다.

## 2. 지금 범위와 다음 범위를 명확히 나눴다

| 구분 | 중간 발표에서 보여줄 부분 | 이후 발전시킬 부분 |
|---|---|---|
| 텍스트 | 정확한 본문 추출, 누락·중복·파편화 개선 | 이미지·스캔 영역 OCR 정확도 향상 |
| 레이아웃 | 다중 컬럼 구분과 읽기 순서 | 이미지 내부 복합 레이아웃 분리 |
| 헤딩 | 제목 검출과 섹션 깊이 추론 | 이미지 안 제목·라벨과 본문 구조 연결 |
| 표 | 다중 컬럼 속 표, 병합 셀, 페이지 연속 표 파싱 | 이미지로 삽입된 표의 OCR·구조 복원 |
| 이미지 | 디버그 이미지로 현재 문제점과 원인 제시 | 사진·도표·차트의 crop 분리와 상세 설명 |

이 경계를 분명히 그어둔 것 자체가 "무계획하게 만들다 만 것"이 아니라 "검증 가능한 핵심부터 완성하고 범위를 통제했다"는 근거다.

## 3. 평가자에게 보여줄 핵심 포인트 — 평가 기준 3가지에 맞춰 역순으로 재구성

평가자가 실제로 판단하는 건 다음 3가지뿐이다.

1. 이 팀이 **문제를 이해하고 있는가**
2. 라이브러리를 가져다 쓴 게 아니라 **검증하면서 개발했는가**
3. 앞으로 **개선 방향까지 설계했는가**

그래서 설명 순서도 "우리가 뭘 만들었나"가 아니라 "문제 → 검증 → 다음 계획" 순으로 이 3가지 질문에 하나씩 직접 답하는 구조로 짠다. Docling 자체(파이프라인 이름, 파라미터명)는 설명의 주인공이 아니라 위 3가지를 뒷받침하는 증거로만 쓴다.

### ① 문제를 이해하고 있는가 — "AI는 이게 제목인지 표인지 모른다"

원본 PDF를 먼저 보여주고 "이 문서를 AI가 읽으려면 뭐가 어려울까요"라고 던진다. 사람은 한눈에 제목·본문·표·차트·컬럼을 구분하지만, AI에게는 전부 좌표 위의 점일 뿐이라는 걸 색으로 구분된 같은 페이지와 나란히 보여주는 순간 평가자는 별다른 설명 없이 바로 이해한다. 여기서 Docling·파라미터 얘기는 전혀 필요 없다 — "왜 어려운 문제인지"만 30초 안에 심어주면 된다.

### ② 검증하면서 개발했는가 — raw → postprocessed를 크게 보여준다

"결과만 보지 않고, 모델이 1차로 어떻게 판단했는지와 후처리 후 뭐가 달라졌는지를 직접 비교하며 검증했다"는 게 핵심 문장이다. 5단계 디버그 체계 전체를 나열하지 않고 `raw_layout`(모델의 1차 판단) → `postprocessed_layout`(후처리 결과) 두 이미지를 크게 보여주는 것만으로 "개발자스럽게" 검증했다는 인상을 준다. `cells`는 옆에 작게 곁들이는 정도로 충분하다.

### ③ 개선 방향까지 설계했는가 — 실제로 발견한 문제 3가지 + "그래서 뭐가 좋아지는가"

가장 강력한 근거다. 실제 문서를 돌려서 레이아웃이 깨지는 지점을 3가지 찾았다. 다만 "문제→원인→개선"에서 멈추면 평가자가 마지막에 궁금해하는 "그래서 그게 왜 중요한데?"에 답이 안 된다. 개선이 최종 JSON/구조에 구체적으로 어떤 변화를 만드는지까지 한 칸 더 붙인다.

| 문제 | 원인 | 개선 방향 | 그래서 (JSON이 좋아지는 점) |
|---|---|---|---|
| 다중 컬럼·표 | 읽기 순서(Reading Order)가 컬럼을 넘나듦 | 컬럼 영역을 먼저 분리(Column Split) | 문단 순서가 뒤바뀌지 않는다 |
| 차트 | 축·범례·숫자가 개별 Text로 파편화 | 파편화된 텍스트를 상위 요소에 Parent로 연결 | 축·범례가 하나의 객체로 유지된다 |
| 복합 그림(인포그래픽) | 사진·라벨·목록이 하나의 Picture 안에서 겹침(Overlap) | Parent-Child 계층으로 재분리 | 이미지 설명을 생성할 수 있는 단위가 된다 |

세 문제를 개별로 나열하는 데서 그치지 않고, 공통점까지 짚어주면 한 단계 더 설득력이 올라간다. 컬럼도·차트도·복합그림도 결국 **"레이아웃 모델이 개별 요소는 찾아내지만, 요소들 사이의 상하위 관계·순서(구조)는 놓친다"**는 같은 문제의 다른 증상이다. 이 한 줄을 표 아래에 덧붙이면 "따로따로 3개를 고쳤다"가 아니라 "근본 원인 하나를 이해하고 있다"는 인상을 준다.

> 파라미터 튜닝 디테일(Accurate+Cell Matching, ko+en OCR 등, 1.3절)은 슬라이드에 넣지 않는다. "왜 이 설정을 썼나요"라는 질문이 나왔을 때 답으로만 쓴다 — 슬라이드는 위 3단계 흐름에만 집중한다.

## 5. PPT 시각자료 구성 제안 (개정판 — 문제 우선·검증 중심 3페이지)

> 이전 버전(4페이지, 파이프라인→파라미터→검증→문제 순)은 기술 설명이 앞서는 구조였다. 평가자는 Docling을 배우러 온 게 아니라 3절의 3가지 기준으로 판단하므로, 아래처럼 **문제 → 검증 → 발견한 이슈** 순으로 재구성한다. 총 3페이지면 충분하고, 폴더의 이미지 8장을 새 이미지 1장만 추가하면 전부 재활용할 수 있다.

### 5.1 기존 Canva 페이지와의 차이 — 실행 전 꼭 확인할 것

현재 Canva 덱에는 이미 13(강조)/14(설명)/15(검증) 3페이지가 커밋되어 있다. 이 개정안을 실제로 적용하면:

- 13페이지(강조, 텍스트만)는 **원본 PDF와 색상 라벨 비교 이미지가 있는 페이지로 교체**돼야 한다.
- 14페이지(설명, 5단계 파이프라인+파라미터+체크리스트, 텍스트 위주)는 **사실상 없어지고**, 그 내용의 핵심(파이프라인 이름, 튜닝 이유)은 발표 멘트로 흡수된다.
- 15페이지(검증, 이미지 3장)는 raw→postprocessed 중심으로 **재구성**되고, 다중 컬럼/차트/복합 그림 문제가 새 페이지로 추가된다.

즉 이 구성은 문서상의 "구상"이지 아직 Canva에 반영된 게 아니다. 반영하려면 14페이지를 사실상 새로 만들어야 하므로, 실제로 Canva를 고칠지는 별도로 결정해서 알려달라.

### 5.2 페이지 구성안 (총 3페이지)

---

**페이지 1 — "AI는 문서를 읽는 것이 아니라 좌표를 해석합니다" (신규 이미지 1장 필요)**

- **핵심 메시지**: 제목 그 자체. 사람은 제목·본문·표·차트를 한눈에 구분하지만, AI에게는 전부 좌표 위의 점일 뿐이다.
- **레이아웃**: 2단 비교만 쓴다. JSON은 이 페이지에 넣지 않는다 — 평가자는 아직 JSON에 관심이 없고, 원본과 Raw Layout 두 장만 나란히 놔도 이미 충분히 임팩트가 있다.
  1. **사람이 보는 문서** — 원본 PDF 1페이지를 아무 표시 없이 그대로.
  2. **AI가 보는 문서** — 같은 페이지에 `SECTION_HEADER`·`TEXT`·`TABLE`·`PICTURE`가 색깔 박스로 표시된 버전.
- **이미지 소스**: 2번은 새로 만들 필요 없다 — `raw_layout_page_00001.png`를 그대로 쓰면 된다. 1번(라벨 전혀 없는 순수 원본)만 폴더에 없으므로 **원본 보고서 PDF 1페이지를 라벨 없이 새로 캡처**해야 한다. 이 스크린샷 한 장만 새로 확보하면 끝이다.
- **발표 멘트**: "이 PDF를 AI가 읽으려면 뭐가 어려울까요?" 라고 질문을 던지고 30초 안에 마무리한다. Docling 이름도, 파이프라인 단계도, JSON도 여기서는 말하지 않는다.

---

**페이지 2 — 우리는 어떻게 검증했는가 (가장 강한 페이지)**

- **핵심 메시지**: "결과만 보지 않았습니다. 모델이 어디서 틀렸는지까지 추적했습니다."
- **이미지 (이미 존재, 그대로 재사용)**:
  - `raw_layout_page_00001.png` — 크게. 모델의 1차 판단(겹친 후보, 낮은 신뢰도).
  - `postprocessed_layout_page_00001.png` — 크게, 바로 옆에. 후처리 후 정리된 결과.
  - `cells_page_00001.png` — 작게, 보조 자료로. "PDF Backend가 애초에 무엇을 읽었는지"까지 확인했다는 근거.
- **큰 흐름 화살표**: `Raw Layout → Postprocessed Layout → Final JSON`을 페이지 안에 시각적으로 크게 넣는다. 사람은 흐름(화살표)을 텍스트보다 빨리 받아들인다. 5단계 이름을 전부 나열하지 않고 이 3단만 크게 보여준다.
- **발표 멘트**: "저희는 결과만 보지 않고, 모델이 어디서 틀렸는지까지 raw→postprocessed 비교로 추적했습니다."

---

**페이지 3 — 실제 문서 검증을 통해 확인한 한계와 개선 전략 (평가자가 가장 좋아할 페이지)**

- **핵심 메시지**: "그냥 라이브러리를 돌린 게 아니라, 실제로 깨지는 지점을 분석하고 전략까지 세웠습니다."
- **이미지 3장 (이미 존재, 그대로 재사용)**: 나란히 배치.
  - `postprocessed_layout_page_00002.png` — 다중 컬럼과 표: 읽기 순서 문제
  - `postprocessed_layout_page_00003.png` — 차트: 축·범례·숫자가 Text로 수십 개 파편화
  - `postprocessed_layout_page_00004.png` — 복합 그림: 하나의 Picture 안에 Picture·Text·List가 전부 겹침
- **표 (3절의 확장 표 재사용, 이미지 아래 배치)**:

| 문제 | 원인 → 개선 | 그래서 |
|---|---|---|
| 컬럼 | Reading Order → Column Split | 문단 순서가 뒤바뀌지 않음 |
| 차트 | Text Fragment → Parent 연결 | 축·범례가 하나의 객체로 유지됨 |
| 복합 그림 | Overlap → Parent-Child | 이미지 설명을 생성할 수 있는 단위가 됨 |

- **표 아래 한 줄**: "결국 하나의 공통 문제입니다 — 개별 요소는 찾아내지만, 요소 사이의 구조와 순서를 놓칩니다." 이 한 줄이 3개 문제를 "따로따로 고친 버그 목록"이 아니라 "하나의 근본 원인을 이해하고 있다"는 인상으로 바꿔준다.
- **디자인 여유가 있다면(선택)**: 표 대신 3개 이미지를 삼각형으로 배치하고 가운데로 화살표가 모이게 해서 "공통 문제 → 해결 전략" 박스로 수렴시키는 구성도 가능하다. 다만 화살표가 정확히 모이는 레이아웃은 Canva에서 손이 많이 가고 자칫 어수선해질 수 있어, **표+한 줄 요약 버전을 기본안으로 권장**한다.
- **발표 멘트**: "실행해보고 어디서 왜 깨지는지 확인했습니다." — 이 문장을 발표의 핵심 메시지로 가져간다. 평가자가 점수를 주는 이유는 정확도가 100%라서가 아니라, 결과를 체계적으로 검증하고 한계를 분석했기 때문이다.

---

### 5.3 선택 페이지 4 — 구조를 보존한다는 것 (트리로 보기)

3페이지로도 충분하지만, 시간이 남으면 이 페이지가 "그래서 우리가 지킨 게 뭔데?"에 가장 직접적으로 답한다. JSON 코드 대신 트리 그림으로 보여주는 게 핵심이다 — 사람은 JSON보다 트리를 훨씬 빨리 이해한다.

- **핵심 메시지**: "우리는 텍스트가 아니라 구조를 보존합니다."
- **그림 구성**: `원본 PDF → 최종 JSON → AI가 사용하는 구조` 흐름 아래, 실제로 확인한 페이지 내용을 그대로 살려 트리로 그린다(가상 예시가 아니라 3페이지 표에서 이미 다룬 실제 문서 내용 재사용).

```text
기업 개요 (Section)
 ├─ Paragraph  "2014년 설립된 반도체·디스플레이 장비 전문 기업..."
 ├─ Table      매출액 · 영업이익 · 영업이익률 (연도별)
 └─ Picture    사업부문 매출액 추이 차트
```

- **문구**: 코드 폰트로 JSON을 보여주지 않는다. 들여쓰기와 트리 선(├─, └─)만으로 표현하고, 최상위 박스에 "Section", 하위에 "Paragraph/Table/Picture" 정도의 라벨만 붙인다.
- **발표 멘트**: "저희가 지키려는 건 텍스트가 아니라 이 트리 구조입니다. 표는 표로, 그림은 그림으로 남아있어야 나중에 근거를 추적할 수 있습니다."

---

### 5.4 이 구성에서 의도적으로 뺀 것

- **5단계 디버그 이름 전체 나열** — 개발 과정에는 있었지만 슬라이드에서는 raw/postprocessed 2단계(+cells 보조)로 압축한다.
- **파라미터 튜닝 상세(Accurate+Cell Matching, ko+en OCR 등)** — 질의응답용으로만 남긴다(6절).
- **JSON 코드 텍스트 자체** — 메인 3페이지 어디에도 JSON 코드를 그대로 노출하지 않는다. "Final JSON"은 페이지 2의 흐름 화살표에 라벨로만 등장하고, 구조를 보여줘야 할 때는 선택 페이지 4의 트리로 대체한다.
- **"지금 범위 vs 다음 범위" 비교표(2절)** — 슬라이드에 넣지 않고 문서에만 남긴다. 질문이 나오면 답 소스로 쓴다.

## 6. 예상 질문과 답변

| 예상 질문 | 답변 방향 |
|---|---|
| 왜 Docling을 썼는가? | PDF Backend·Layout Model·OCR·TableFormer·Reading Order를 하나의 파이프라인으로 묶어 제공해서, 텍스트 인식뿐 아니라 구조(제목 깊이·표 구조·읽기 순서)까지 한 번에 복원할 수 있기 때문이다. |
| 지금 정확도는 어느 정도인가? | 텍스트·헤딩·표 구조는 중간 발표 범위에서 검증을 마쳤다. 다만 이미지 내부 텍스트(OCR)와 차트·복합 도식 분리는 아직 파편화 문제가 있고, 다음 단계 과제로 명확히 남겨뒀다(4절 이미지가 그 증거). |
| 표가 페이지를 넘어가면 어떻게 되나? | 현재는 페이지별로 별도 표 객체로 나뉠 수 있다는 한계를 인지하고 있고, 반복 헤더·열 수·데이터 타입을 이용해 페이지 연속 표를 연결하는 걸 다음 단계 튜닝 대상으로 정해뒀다. |
| Accurate 모드가 왜 필요한가, Fast보다 느린데? | 속도보다 정확도가 우선인 이유는, 우리 제품이 "근거를 원문 그대로 추적"하는 게 핵심 가치라서 표 구조가 깨지면 근거 자체가 왜곡되기 때문이다. Cell Matching으로 예측 셀을 원문과 재대조해 병합 셀에서도 구조를 지킨다. |
