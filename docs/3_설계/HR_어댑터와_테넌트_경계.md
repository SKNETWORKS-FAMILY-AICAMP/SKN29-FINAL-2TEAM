# HR 어댑터와 테넌트(팀) 경계

> 기준일: 2026-07-31
> 구현 기준: `backend/services/hr/`, `backend/db/repositories.py`(`TeamRepository`), `apps/people/api_views.py`

## 1. 왜 만들었나

People DB는 **실제 HR 시스템의 대역**이다. Workday API는 결제한 기업 고객만 쓸 수 있어 이 프로젝트에서 붙일 수 없고, 조직도·인력·근무 정보는 원래 HR 시스템 안에 있는 것이므로, Workday API 문서를 참고해 같은 모양의 DB를 만들어 대신 쓰기로 했다.

> **"나중에 실제 Workday로 갈아끼운다"가 목적이 아니다.** 갈아끼울 수 없다는 것이 전제이고, 이 목업이 계속 HR 자리를 지킨다.

문제는 설계 의도와 코드가 어긋나 있었다는 것이다. 의도상 `person`·`org`는 **남의 시스템에 있는 데이터**인데, 코드는 우리 테이블처럼 `proj`·`doc`과 나란히 조인하고 있었다. 1차 구현에서 `mock_hr` 스키마 분리를 생략하면서 그 구분이 사라졌다. 2026-07-31 점검에서 상태를 수치로 확인했다.

```
repositories.py가 org·person·level·sched를 직접 만지는 곳    43곳 / 17개 메서드
HR 전용 어댑터·클라이언트 계층                                없음
DB 스키마                                                     public 하나 (45개 테이블)
```

Drive·Jira는 `apps/connectors/clients.py`라는 어댑터를 두고 HTTP로 나가는데, People DB만 코어에 융합돼 있었다. 화면에서는 커넥터 카드로 나란히 보이지만 실제로는 **코어 스키마에 커넥터 라벨만 붙은 상태**였다.

동시에 "고객사"라는 개념이 어디에도 없어서, 플랫폼이 범용 SaaS가 아니라 **한 회사에 설치하는 사내 시스템** 모양이 돼 있었다.

## 2. 두 가지를 같이 고친 이유

같은 뿌리였다. HR을 외부 시스템으로 취급했다면 "어느 회사의 HR인가"가 자연스럽게 연결 단위로 들어왔을 것이다. 경계를 없애면서 그 질문도 같이 사라졌다.

Drive를 생각하면 분명하다. 내 Drive를 연결하면 내 폴더만 보인다 — 전체 Drive를 이메일로 뒤지지 않는다. HR도 같아야 한다.

다만 **경계의 단위는 회사가 아니라 팀이다.** 처음에는 회사로 잡았다가 뒤집었다 — 그 이유는 §3에 있다.

## 3. 테넌트는 회사가 아니라 팀이다

HR에서는 한 회사지만, **우리 플랫폼을 쓰는 것은 회사 전체가 아니라 그 안의 그룹**이다. 개발팀이 도입했다고 마케팅팀까지 쓰는 것이 아니다.

경계를 조직도에서 유도하려던 시도는 둘 다 실패했다.

| 시도 | 결과 |
|---|---|
| 회사(`org_type='COMPANY'`)를 테넌트로 | 과다. 개발팀 팀장이 회사 전 직원 56명을 보게 된다 |
| 조직(`org`)을 테넌트로 | 불가. 팀원 한 명만 놓고는 "어디까지가 우리 그룹인가"를 알 수 없다 |

그래서 팀은 **유도하지 않고 명시적으로 만든다.** 팀장이 온보딩에서 이름을 붙이고 팀원을 고르면 `team` 행이 생긴다. 이후 "이 사람이 어느 그룹인가"는 추론이 아니라 조회다.

```
1. 가입                     계정만 존재
2. 자기 회사 HR 연결          HR 대역에 접근
3. 본인 확인                 이메일로 찾은 PERSON을 사용자가 확인
4. 팀명 입력 + 팀원 선택       team + team_member 생성. 팀장 본인은 자동 포함
5. 이후 모든 조회             user_account.team_id 기준
```

`team.src_org_id`에 팀장의 HR 소속을 남긴다 — 팀에 담을 수 있는 사람의 범위(그 조직의 하위)를 판단한 근거다.

### 초대는 팀을 실어 나른다

`member_invite.team_id`에 초대자의 팀이 기록되고, 수락하는 순간 그 팀이 팀원 계정의 테넌트가 된다(`user_account.team_id`). 팀원 명부(`team_member`)에도 들어간다.

명부를 PERSON 단위로 두는 이유는 **업무 배정 대상이 계정이 아니라 사람**이기 때문이다. 아직 가입하지 않은 사람도 팀원이고 배정 대상이다.

## 4. 어댑터 계약

`backend/services/hr/`가 HR 데이터를 읽는 유일한 통로다. `org`·`person`·`level`·`sched`를 이 계층 밖에서 직접 조회하지 않는다.

**어댑터는 커서를 받지 않는다.** 호출자 트랜잭션에 얹히지 않고 스스로 연결을 열어 평범한 dict를 돌려준다. HR 원천 테이블에 애플리케이션 쓰기가 한 곳도 없어서(전부 읽기 전용) 가능한 설계다.

그 대가로 **SQL JOIN을 포기했다.** 남의 시스템 데이터와 우리 데이터를 한 쿼리로 조인하는 것 자체가 대역이라는 설정에 어긋난다. 지금은 HR을 어댑터로, 플랫폼을 SQL로 읽어 파이썬에서 합친다. 조직·인력이 수천 건 수준이라 감당된다.

**어댑터에 테넌트 개념은 없다.** HR은 회사의 인사 시스템이고 팀은 우리 개념이므로, 경계는 플랫폼(`team_member`)이 갖고 어댑터는 "주어진 조직·사람을 읽어준다"까지만 한다.

| 함수 | 쓰임 |
|---|---|
| `list_persons(person_ids=)` | 팀원 조회. 팀 경계는 호출자가 `team_member`로 정한다 |
| `list_persons(org_ids=)` · `subtree_org_ids` | 팀에 담을 후보 범위(HR 조직 기준) |
| `list_orgs` · `get_person` | 단순 조회 |
| `lookup_persons` · `lookup_orgs` | 표시용. 재직·활성 상태를 가리지 않는다 |
| `count_orgs` | 운영자 콘솔 |
| `is_available` | 연결 점검 |
| `discover_person_by_email` | 본인 확인 한 곳(§5) |

빈 리스트를 주면 빈 결과다 — 조건을 안 준 것과 구분한다. **이 구분이 없으면 "팀원이 아직 없는 팀"이 전 직원을 보게 된다.**

표시용 조회가 상태를 가리지 않는 이유는, 퇴사자에게 연결된 계정도 운영자 화면에서 이름이 보여야 하기 때문이다.

## 5. 본인 확인만 범위가 없다

`discover_person_by_email()`은 아직 팀이 정해지기 전 단계라 좁힐 근거가 없다. 실제 HR이라면 연결 자격증명이 회사를 좁혀주지만 목업에는 자격증명이 없다.

> **이 절의 앞선 서술은 틀렸다 (2026-07-31 수정).** 처음에는 "실제 HR을 붙이면 자동으로 닫힌다"고 적었다. Workday API는 결제한 기업 고객만 쓸 수 있어 **붙일 수 없다는 것이 전제**이므로 저절로 닫히지 않는다.

다만 영향은 제한적이다. 여기서 잘못된 사람을 찾아도 **사용자가 "본인이 맞습니까"에 아니오를 누르면 진행되지 않고**, 확인 이후 모든 조회는 팀 기준이기 때문이다. 이메일이 겹치는 동명이인이 실제로 생기기 전까지는 열어 둔다.

닫으려면 본인 확인보다 먼저 회사를 정하는 단계(회사 선택 화면 / 이메일 도메인 매핑)가 필요하다.

## 6. 같이 막은 실제 노출

작업 중 발견한 것이라 여기 남긴다. `GET /api/people/`와 `GET /api/organizations/`가 **인증 없이** 직원 56명의 실명·실제 이메일과 조직 9개를 반환하고 있었다. `team_overrides.sql`로 팀원 실명·실제 이메일이 들어간 데이터라 실제 노출이었다.

로그인을 요구하고 본인 팀으로 스코프를 걸었다. 이제 팀장은 회사 전 직원이 아니라 자기 팀원만 본다. 프론트·테스트 어디서도 호출하지 않던 엔드포인트라 잠가도 깨지는 곳이 없었다.

## 7. 지금 상태와 다음 단계

```
HR 직접 접근      43곳 → 0곳
테스트            121개
스키마            team · team_member 추가, user_account.team_id · member_invite.team_id 추가
```

실측(로컬 Postgres, 팀장 `임준` 기준):

| | 전 | 후 |
|---|---|---|
| `GET /api/people/` | 인증 없이 **56명**(회사 전체) | 로그인 필요 · **5명**(팀원) |
| `GET /api/organizations/` | 인증 없이 **9개** | 로그인 필요 · **2개**(팀원 소속) |

`DATABASES = {}`라 Django 테스트가 DB를 못 쓴다. 그래서 "두 팀을 넣고 교차 조회가 막히는가"는 단위 테스트로 재현하지 못하고, DB에 닿기 전에 결정되는 **가드 계약**(빈 조건과 조건 없음의 구분, 팀 없는 계정의 빈 결과)을 검증한다. 실제 동작은 로컬 DB로 확인했다.

다음 단계로 남은 것:

- **팀 없는 기존 계정** — 이번 변경 전에 만들어진 계정은 `team_id`가 비어 있어 아무도 못 본다. 온보딩을 다시 타면 팀이 생긴다. 시연 전 확인이 필요하다.
- **한 사람이 두 팀에 속하는 경우** — 지금은 `user_account.team_id` 하나뿐이라 불가능하다. 겸직이 필요해지면 별도 테이블이 필요하다.
- **§5의 본인 확인 범위** — 동명이인이 실제로 생기기 전까지는 열어 둔다.
- **`mock_hr` 스키마 분리** — 코드 경계는 세웠고 DB 네임스페이스는 아직 `public` 하나다. 목업이 계속 HR 자리를 지키므로 "보기 좋게 정리"와 "DB 권한 분리"에만 의미가 있다. 우선순위 낮음.

`mock_db.py`라는 이름은 "언젠가 진짜로 바꿀 임시물"이라는 뜻이 아니다. **실제 HR 시스템의 대역**이라는 뜻이고, 그 역할은 계속된다.
