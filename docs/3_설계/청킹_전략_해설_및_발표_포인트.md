# 청킹 전략 해설 및 발표 포인트

> 문서 상태: 발표 준비용 해설  
> 작성일: 2026-08-02  
> 원본 자료: `docling_hybrid_to_vector_db_easy.md` (청킹 파이프라인 쉬운 설명)  
> 목적: 지금까지 실제로 만든 청킹 전략을 정리하고, 평가자에게 "그냥 글자 수로 자르는 방식이 아니다"를 짧고 확실하게 설득할 핵심 포인트 2가지와 PPT 시각자료 구성안을 정리한다.

---

## 1. 지금까지 만든 청킹 전략 — 5단계 요약

```text
PDF/DOCX 원문
   ↓ Docling + EasyOCR
문서 구조 인식 (제목·문단·목록·표·그림 구분)
   ↓ Docling HybridChunker
의미 단위 청크
   ↓ all-MiniLM-L6-v2 tokenizer
임베딩(숫자 벡터)
   ↓
Vector DB 저장 (청크 ID·제목 경로·페이지·원본 참조 함께 저장)
```

문서를 가져올 때부터 파일명뿐 아니라 파일 ID, revision, 내용 해시(content hash)를 함께 기록한다. 파일이 수정되면 해시가 바뀌므로 "이 청크가 최신 버전에서 나온 것인지"를 항상 판정할 수 있다.

청킹 자체는 Docling `HybridChunker`가 담당하며, 다음 순서로 동작한다.

1. 제목·문단·목록·표 같은 문서 구조를 먼저 인식한다.
2. 너무 긴 조각만 다시 나눈다.
3. 너무 짧은 조각은 같은 제목 아래끼리 합친다.
4. 표가 청크 경계에서 잘리면, 잘린 모든 조각에 표 헤더를 반복해서 넣는다.

청크 크기 기준은 글자 수가 아니라 실제 임베딩 모델(`all-MiniLM-L6-v2`)의 tokenizer로 계산한 토큰 수이며, 그 모델의 처리 상한인 512토큰에 맞춰 분할한다. 문서가 수정되면 revision·content hash 변경을 감지해 예전 청크를 비활성화하고 새로 청킹·임베딩해 오래된 정보가 검색 결과로 나오지 않게 한다.

## 2. 진짜 중요한 차별점 2가지

여러 특징이 있지만 발표에서 전부 설명하면 늘어진다. 평가자가 "이건 그냥 튜토리얼 코드가 아니라 고민한 결과구나"라고 느낄 확률이 가장 높은 두 가지만 남긴다.

### 핵심 ① 구조 경계를 지켜서 자른다 — 표가 깨지지 않는다

시중의 많은 RAG 예제는 `chunk_size=500, overlap=50` 같은 고정 글자 수로 자른다. 그러면 표나 문장이 중간에 잘려 그 조각만으로는 의미를 잃는다.

```text
나쁜 예 (고정 글자 수 분할):
청크 A: 제품명 | 가격
        A 제품 | 10만 원
        B 제품 | ...
청크 B: 20만 원                ← 표 헤더 없이 숫자만 남음, 의미를 잃는다
```

우리는 표가 잘리는 지점에서도 헤더를 반복해서 넣는다.

```text
청크 A: 제품명 | 가격
        A 제품 | 10만 원
청크 B: 제품명 | 가격          ← 헤더가 반복돼서 이 청크 하나만 봐도 표 의미가 산다
        B 제품 | 20만 원
```

가장 시연하기 쉽고, 가장 직관적으로 "고민한 흔적"을 보여주는 지점이다.

### 핵심 ② 문맥과 근거를 청크에 같이 담아, 나중에 추적할 수 있게 한다

본문만 저장하면 이 조각 하나만 봐서는 무슨 얘기인지 알 수 없다.

```text
"예산은 3천만 원으로 잡는다."   ← 어느 프로젝트의 무슨 예산인지 알 수 없다
```

그래서 실제 검색·임베딩에 쓰는 텍스트(`contextualized_text`)에는 제목 경로를 붙인다.

```text
[프로젝트 A]
[예산 계획]
예산은 3천만 원으로 잡는다.
```

그리고 각 청크에는 `heading_path`(제목 경로), `page_numbers`(원본 페이지), `source_refs`(원본 위치)를 함께 저장한다. 검색 결과가 나왔을 때 "몇 페이지, 어느 섹션에서 나온 근거인지"를 바로 되짚을 수 있다. 이 프로젝트의 핵심 가치인 **판단 근거 추적성**과 직접 연결되는 지점이므로, 두 번째 핵심으로 반드시 남긴다.

> 참고: 토큰 수를 실제 임베딩 모델 기준으로 정확히 계산한 것, 문서 수정 시 청크를 자동으로 갱신하는 것도 잘 설계된 디테일이지만, 위 2가지만큼 한눈에 와닿지는 않는다. 시간이 부족하면 발표에서는 생략하고 질의응답에서만 답하는 걸 권장한다(7절 참고).

## 3. 발표 문장 예시 (2가지 핵심만 압축)

> "저희는 문서를 그냥 글자 수로 자르지 않았습니다. 제목·문단·표 같은 구조를 먼저 인식하고, 표는 잘려도 헤더가 반복되도록 만들어서 어떤 조각만 검색에 걸려도 의미가 살아있게 했습니다. 그리고 모든 청크에는 원본 페이지와 제목 경로를 함께 저장해서, 검색 결과가 나오면 원문 몇 페이지에서 나온 근거인지 바로 되짚을 수 있습니다. 저희 제품의 핵심 가치가 '판단 근거 추적'이라서, 청킹 단계부터 이 추적성을 전제 조건으로 설계했습니다."

구조: **① 무엇을 안 했는가(단순 글자 수 분할) → ② 무엇을 했는가(구조 보존 + 근거 보존) → ③ 왜 우리 제품에 중요한가(근거 추적성)**.

## 4. PPT 시각자료 구성 제안

### 4.1 왜 한 페이지로는 부족한가

지금 한 페이지(청킹 설명)에 들어가야 하는 내용을 세어 보면: HybridChunker 4단계 리스트, 표 분할 비교 예시, 토큰 계산 설명, `contextualized_text` 개념, 실제 JSON 예시, 저장 메타데이터 표까지 6가지 서로 다른 정보 블록이다. 이걸 한 슬라이드에 다 넣으면 평가자가 어디를 먼저 봐야 할지 모르고, 발표자도 한 슬라이드 안에서 설명 순서가 꼬인다.

**한 슬라이드 = 한 가지 핵심 메시지 + 그걸 증명하는 이미지 1개**가 원칙이다. 위 2절에서 고른 핵심 2가지를 각각 한 페이지씩 주고, 문제 제기 페이지를 앞에 붙이면 총 3페이지가 된다.

### 4.2 페이지 구성안 (총 3페이지)

기존 발표 자료의 "강조(문제 제기, 이미지 없음) → 설명(기술 상세)" 패턴을 따르되, 설명을 2페이지로 나눈다.

---

**페이지 1 — 청킹 강조 (문제 제기, 이미지 불필요)**

- 이미 만들어져 있는 페이지 그대로 유지한다. "문서를 통째로 주면 못 찾고, 글자 수로 자르면 의미가 깨진다"는 문제만 던지고 다음 페이지로 넘어간다.
- 이미지 없음 — 텍스트만으로 충분하다.

---

**페이지 2 — 청킹 설명① : 구조를 먼저 보고 자른다**

- **상단 — 왜 청킹을 하는가 (작은 흐름 다이어그램, 슬라이드 맨 위에 한 줄로 작게)**:

```text
Docling JSON → HybridChunker → Vector DB → 검색
```

  청킹이 전체 파이프라인에서 어떤 역할인지 한눈에 보여주고 바로 핵심 내용으로 넘어간다. 1절의 5단계 파이프라인을 슬라이드용으로 압축한 버전이며, 5단계 전체를 슬라이드에 다시 나열하지는 않는다.

- **핵심 메시지 한 줄**: "표·문단 구조를 지켜서 자르기 때문에, 어떤 조각만 봐도 의미가 살아있다."
- **텍스트**: HybridChunker의 4단계 리스트(구조 인식→긴 조각 분할→짧은 조각 병합→표 헤더 반복)를 그대로 나열하지 않는다. 대신 "왜 이렇게 설계했는가"에 집중해 한 문장으로만 건다 — "문서 구조(제목·문단·표)를 먼저 인식하고, 그 경계를 지키는 선에서만 자르고 합친다." 4단계 상세 리스트는 1절 배경 문서와 질의응답 대비용으로만 남긴다.
- **이미지 (필수, 비교 이미지)**: "나쁜 예 vs 좋은 예" 표 분할 비교. 아래 두 방법 중 하나를 선택한다.

  - **방법 A (권장, 실제 스크린샷)**: 실제 파이프라인에 여러 행짜리 표가 있는 문서(예: 팀 일정표, 담당자 배정표)를 넣고 돌린 뒤, HybridChunker가 만든 청크 2~3개를 실제로 캡처한다. 화면에는 "청크 1"과 "청크 2" 박스를 나란히 놓고, 각 박스 맨 위에 "담당 역할 | 시작일 | 종료일" 같은 헤더가 동일하게 반복되는 걸 볼 수 있어야 한다. 헤더 행에 노란색 하이라이트나 박스 테두리를 둘러서 "이게 반복됐다"는 걸 시각적으로 강조한다. 이미 발표 자료 문구에 "20행짜리 표를 3개 청크로 나눴을 때, 각 청크 맨 위에 헤더가 반복되는 화면"이라고 예고돼 있으므로, 실제 실행 결과를 캡처하는 게 가장 신뢰도 높은 증거가 된다.
  - **방법 B (대안, 목업 다이어그램)**: 실제 스크린샷을 만들기 어렵다면 Canva에서 직접 그린다. 좌우 2단 비교 레이아웃으로, 왼쪽은 "글자 수로 자르면" 제목 아래 회색 박스 2개(청크 A: 표 헤더+1행, 청크 B: 헤더 없이 숫자만) 를 놓고 청크 B에 빨간 X 표시나 "❌ 의미 없음" 라벨을 붙인다. 오른쪽은 "우리 방식" 제목 아래 파란 박스 2개(청크 A: 표 헤더+1행, 청크 B: 표 헤더 반복+1행)를 놓고 초록 체크 표시나 "✅ 헤더 반복" 라벨을 붙인다. 두 박스 세트 사이에 큰 화살표나 "VS" 텍스트를 넣어 대비를 강조한다. (이미 md 예시 텍스트 그대로 각 박스에 넣으면 된다 — 위 2절의 "나쁜 예/좋은 예" 텍스트 블록 참고.)

- **하단 캡션**: "구조 경계를 지키면 청크 하나만 검색돼도 완결된 의미를 유지합니다."

---

**페이지 3 — 청킹 설명② : 문맥과 근거를 함께 저장한다**

- **핵심 메시지 한 줄**: "청크에 제목 문맥과 원본 위치를 함께 저장해서, 나중에 근거를 원문까지 되짚을 수 있다."
- **이미지/텍스트 구성 (2단 레이아웃)**:
  - **왼쪽 — 텍스트 비교 박스** (이미지 아님, Canva 텍스트 박스 2개로 충분): 위 박스에 "본문만 보면"이라는 라벨과 `"예산은 3천만 원으로 잡는다." ← 무슨 프로젝트인지 모름` 텍스트, 아래 박스에 "제목 경로를 붙이면"이라는 라벨과 `[프로젝트 A]\n[예산 계획]\n예산은 3천만 원으로 잡는다. ← 청크 하나만 봐도 의미가 산다` 텍스트. 아래 박스를 파란색으로 강조한다.
  - **오른쪽 — 필드 3개만, 화살표로 연결** (전체 JSON 코드 블록을 메인 이미지로 쓰지 않는다 — 평가자는 JSON을 읽지 않는다는 점을 이번에는 확실히 반영한다):

```text
heading_path   → 문맥 유지
page_numbers   → 출처 페이지
source_refs    → 원문 위치
```

  각 필드명을 왼쪽에 밝은 박스로, 화살표 오른쪽에 의미를 큰 글씨로 배치한다. 코드 폰트를 쓰되 딱 이 3줄만 보이면 된다 — `chunk_id`·`text`·`contextualized_text`는 이 슬라이드에 아예 올리지 않는다.

- **발표 마지막 한 줄** *(이 페이지를 닫는 문장, 다음 섹션으로 넘어가기 전에 힘주어 말한다)*:

> "추천 결과를 신뢰하려면, AI가 어떤 문서를 근거로 판단했는지 끝까지 추적할 수 있어야 합니다."

  이 한 줄이 기술(청킹 메타데이터)과 서비스(업무 추천의 신뢰도)를 직접 연결한다. "구조를 보존합니다"에서 끝내지 않고, 왜 그게 이 프로젝트에 중요한지까지 닫는다.

- **참고 — 전체 레코드 예시 (슬라이드에는 넣지 않음, 질의응답 대비용)**: 6개 필드로 구성된 실제 레코드는 아래와 같다. "저 3개 필드만 있는 게 아니라 실제로는 이렇게 저장된다"는 질문이 나오면 이걸로 답한다.

```json
{
  "chunk_id": "기획서:파일해시:슬라이드:docling_hybrid:0",
  "text": "예산은 3천만 원으로 잡는다.",
  "contextualized_text": "[프로젝트 A]\n[예산 계획]\n예산은 3천만 원으로 잡는다.",
  "heading_path": ["프로젝트 A", "예산 계획"],
  "page_numbers": [4],
  "source_refs": ["#/texts/82"]
}
```

### 4.3 제외 권장 — 청킹 검증(실제 동작 화면) 페이지는 PPT에 넣지 않는다

이전 개정에서는 "시간 여유가 있으면 추가"하는 선택 페이지로 남겨뒀지만, 이번 검토에서는 아예 넣지 않는 것으로 정리한다. 청킹 파트는 이미 페이지 2(구조 보존)·페이지 3(근거 추적) 두 가지로 핵심을 다 전달했다. 여기에 토큰 수 로그(`청크 1: 180토큰, 청크 2: 430토큰...`) 같은 실행 화면을 더 얹으면, 개발자에게는 흥미로워도 평가자에게는 관심 밖 디테일이고 발표 흐름만 끊는다. 아래 예시는 슬라이드용이 아니라 "정말 실제 데이터로 돌려봤나" 같은 질의응답이 나왔을 때 답하는 배경 자료로만 남긴다.

```json
{
  "chunk_id": "hanwha (1):15156758767682194756:local-run:docling_hybrid:0",
```

## 5. 예상 질문과 답변

| 예상 질문 | 답변 방향 |
|---|---|
| 왜 고정 크기로 안 자르고 구조 기반으로 잘랐나? | 고정 크기는 표·문단이 중간에 잘려 그 조각만으로는 의미를 잃는다. 구조 경계를 지키면 청크 하나만 검색돼도 완결된 의미를 유지한다 — 페이지 2의 표 예시로 바로 시연 가능. |
| 512토큰은 왜 그 숫자인가? | 지금 쓰는 임베딩 모델(`all-MiniLM-L6-v2`)의 처리 상한이 512토큰이라 그 기준에 맞췄다. 실제 서비스에 쓸 임베딩 모델이 확정되면 그 모델의 tokenizer·상한으로 다시 맞출 계획이다. |
| 문서가 수정되면 어떻게 되나? | revision·content hash 변경을 감지 기준으로 삼아 예전 청크를 비활성화하고 새로 청킹·임베딩한다. 오래된 정보가 검색 결과로 나오지 않도록 막는 장치다. |
| 이게 왜 "업무 배정 근거"랑 연결되나? | 청크마다 원본 페이지·제목 경로·원본 참조를 저장하기 때문에, 나중에 업무 후보를 추천할 때 "이 근거는 몇 페이지, 어느 섹션에서 나왔다"를 PM에게 보여줄 수 있다. 청킹 설계가 곧 근거 추적 기능의 기반이다. |

## 6. 한 줄 요약

> 우리 청킹은 "잘 검색되게 자르는 것"이 아니라 "무엇을 어디서 가져왔는지 잃지 않고 자르는 것"을 목표로 설계했다. 구조 경계를 지켜 표·문단을 보존하는 것, 그리고 문맥·근거 메타데이터를 함께 저장하는 것 — 이 2가지가 그 목표를 구현한 핵심 장치다.
