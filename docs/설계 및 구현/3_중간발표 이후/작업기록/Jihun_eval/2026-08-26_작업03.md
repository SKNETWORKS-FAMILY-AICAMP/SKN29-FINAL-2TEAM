# 2026-08-26 작업03 — 평가 결과 DB 저장 기반

## 목적

기존 로컬 append-only 평가 결과를 보존하면서, 같은 `eval_run_id`로 프로젝트 DB에
조회·집계 가능한 사본을 남긴다. 평가 실행 자체가 DB 장애에 종속되지 않게 파일
기록과 DB 동기화를 분리한다.

## 구현 내용

- `eval_run`: manifest·summary와 실행 버전·상태·동기화 상태 저장
- `eval_case_result`: 반복 case를 JSONL 순서인 `case_index`로 구분해 저장
- `2026-08-26_eval_result_storage.sql`: 두 테이블과 조회 인덱스 생성
- `_apply.py --check`: 두 평가 테이블 누락 검사
- `EvaluationResultRepository`: 완료 실행의 두 단계 멱등 동기화
  1. `SYNC_PENDING` 실행 선기록
  2. case 저장 후 `SYNCED` 확정
- `read_completed_run`: 종료 여부와 manifest·summary·case의 `eval_run_id` 일치 검증
- `eval_record.py sync-db`: 종료된 실행 폴더를 DB에 동기화하는 명령
- 초기화 정책:
  - `reset_demo.sql`: 새 시연에 과거 성적이 섞이지 않도록 평가 결과도 삭제
  - `reset_eval.sql`: 입력 프로젝트·문서만 교체하고 과거 비교 성적은 보존

같은 ID의 기존 DB 결과와 로컬 내용이 다르면 덮어쓰지 않고 오류로 중단한다. DB
동기화는 로컬 네 산출물을 수정하지 않는다.

## main 병합·배포 시 순서

1. 코드와 `DB/schema.sql`을 병합한다.
2. 대상 DB를 백업하고 연결 대상이 로컬·공유·운영 중 어디인지 확인한다.
3. `DB/migrations/2026-08-26_eval_result_storage.sql`과
   `DB/migrations/2026-08-26_eval_judge_result.sql`을 **둘 다** 적용한다(뒤의
   것은 2026-08-26 후반 작업에서 추가됐다 — 하나만 적용하고 끝내지 않는다).
4. `python DB/migrations/_apply.py --check`로 `eval_run`·`eval_case_result`·
   `eval_judge_result` 세 개 다 누락이 없는지 확인한다.
5. 종료된 비운영 평가 실행 한 건을 `scripts/eval_record.py sync-db`로 동기화한다.
6. 같은 명령을 다시 실행해 case가 중복되지 않는지 확인한다.
7. 기존 `max_iterations` 기본값 불일치는 별도 마이그레이션 적용 여부를 담당자와
   확인하며 이 작업에 묶어 조용히 변경하지 않는다.

bundle을 먼저 만들고 완전성 검사를 통과한 뒤 Judge를 호출한다.

### 후속 코드 검토 반영

Judge와 runner 코드 검토에서 확인된 세 문제를 반영했다.

1. `eval_run.py`가 Agent 결과를 계산한 뒤 임시 세션 삭제에 실패하면 case 결과를
   기록하지 못하던 순서를 수정했다. 이제 cleanup을 시도한 뒤 성공·실패 상태를
   case에 넣고 `append_case`부터 수행한다. 삭제 실패 시 Agent 결과는 보존되고 실행
   summary만 `ABORTED`로 종료된다.
2. runner와 calibration이 별도로 만들던 Judge 요청·응답 계약을
   `services/evaluation/judge.py`로 통합했다. 두 경로 모두 최종 답변, 결정적 assertion,
   제한된 tool trace와 전체 evidence bundle을 같은 구조로 사용하며, 전체 verdict와
   5개 차원이 빠진 응답은 `ERROR`다.
3. `eval_judge.py`가 모델 호출 실패와 응답 JSON·스키마 검증 실패를 구분해 각각 종료
   코드 2와 3으로 반환하도록 했다. 실패 응답 원문과 endpoint 세부정보는 출력하지
   않으며 파싱 성공 전에는 결과 파일을 쓰지 않는다.

세션 삭제 실패 시에도 case가 append되는 회귀 테스트와 공통 Judge 계약 검증을
추가했다. recorder·DB 저장 회귀를 포함한 관련 테스트는 총 35개가 통과했다.

## 도구 실패 후 재시도 루프 계측

기존 runner는 도구 실패 자체와 전체·도구별 호출 상한은 잡았지만, 실패 이후 같은
호출을 몇 번 다시 시도했고 복구했는지는 숫자로 남기지 않았다. 이를 다음처럼
보완했다.

- `tool_call_id`로 시작·완료 event 연결
- `tool_ref + 정규화된 arguments` 조합으로 같은 호출 판별
- arguments는 SHA-256 계산에만 사용하고 원문·해시는 결과에 저장하지 않음
- 실패, 실패 후 재시도, 재시도 성공 복구, 최대 연속 실패, 미완료 시작 수 집계
- 도구별 시도·실패·재시도·복구 합계를 `tool_reliability.by_tool`에 기록
- 대시보드용 전체 숫자는 기존 `metrics`에도 기록

실패 완료가 발생한 뒤 시작된 동일 호출만 재시도다. 같은 호출이 병렬로 먼저 시작된
상태에서 하나가 실패한 경우 나머지 선행 호출은 재시도로 세지 않는다. 서로 다른
검색어처럼 arguments가 바뀐 후속 호출도 재시도가 아니다.

데이터셋을 v10으로 올리고 조회 중심 001·002·003·005 사례에 다음 정책을 명시했다.

- 동일 도구·인자 실패 후 재시도 최대 1회
- 동일 도구·인자 연속 실패 최대 2회

004A·004B Jira HITL은 사용자 거절·승인 결과가 일반 도구 장애와 다르므로 공통 재시도
정책을 적용하지 않았다. 실패 후 성공, 지속 실패, 다른 인자 호출, 병렬 선행 호출과
결과 계약 검증 테스트를 추가했고 관련 테스트 총 41개가 통과했다. 기존
`tool_calls_completed_ok`는 유지되어, 마지막 재시도가 성공해도 앞선 실패가 전체
실행에서 사라지지 않는다.

## 제품 런타임 도구 실패 복구 설계

runner의 재시도 계측 다음 단계로 실제 Agent 런타임의 실패 복구 방향을 검토했다.
현재 구현된 것은 실행 뒤 실패·반복을 측정하는 기능이며, 조회 도구를 자동으로 다시
실행하거나 쓰기 실패 뒤 사용자 결정을 받는 제품 기능은 아직 구현되지 않았다.

결정한 정책은 다음과 같다.

- 조회 도구의 일시적인 기술 오류만 최초 호출 포함 최대 3회 실행
- 인증·권한·입력 오류와 검색 결과 부족은 자동 재시도하지 않음
- 쓰기 도구는 자동 재시도하지 않음
- 쓰기 실패 카드에서는 `retry`·`skip`·`reject`를 구분
- 사용자 `retry` 한 번은 실제 재실행 한 번만 허용
- 쓰기 실패 카드는 체크포인터 재진입 전에 외부 DB에 `PENDING` 상태와
  `run_id + tool_call_id` 멱등성 키를 먼저 저장해야 함

현재 승인 흐름은 한 턴의 여러 대상을 `decisions` 배열로 받으므로 UI와 API는 이
패턴을 재사용한다. 다만 병렬 쓰기 실패는 내부적으로 여러 `interrupt_id`가 생길 수
있으므로 서버가 배열의 `failure_index`를 실제 ID에 매핑해 LangGraph의 다중 resume
형태로 변환한다. 모든 실패를 하나의 interrupt로 강제로 모으는 새 조정 노드는 v0에서
제외했다.

상세 계약과 테스트 조건은
`../../설계/eval/tool_failure_recovery_v0.md`에 기록했다. 우선 조회 자동 재시도만
구현·검증하고, 쓰기 실패 카드는 1단계 안정화 뒤 별도 설계 승인 대상으로 유지한다.

## 조회 도구 자동 재시도 1단계 구현

설계 검토에서 재개 계약(`decisions` 배열 + 내부 `interrupt_id` 매핑)이 문서
설계와 이미 일치함을 확인한 뒤, 1단계 조회 도구 자동 재시도를 구현했다.

- 코드: `services/agent_runtime/factory.py`
  (`_is_transient_tool_failure`, `_call_tool_handler`)
- 핵심 발견: 애초 예상한 LangGraph `wrap_tool_call` 미들웨어 자리는 쓸 수 없었다.
  `_IdempotencyAwareTool`이 `handle_tool_error=True`로 만들어져 `BaseTool.invoke()`가
  `ToolException`을 미들웨어 체인에 닿기 전에 문자열로 삼킨다. 재시도는 `_run()`

## Langfuse·OpenTelemetry HITL 연결 스파이크와 최소 구현

설치된 Langfuse v4.14.5와 민감정보가 없는 합성 LangGraph interrupt/resume로 세
방식을 실제 JP Langfuse에 전송해 비교했다.

| 방식 | 실제 결과 | 판단 |
|---|---|---|
| 단계마다 새 handler + 고정 `trace_context` | 한 trace, observation 4개, root 0개 | remote parent만 생겨 부적합 |
| `thread_id`별 같은 handler 재사용 | interrupt 전·후 trace가 분리되고 각 root 1개 | SDK 내장 resume 저장소가 이번 호출 구조에서 이어지지 않아 부적합 |
| Langfuse root 선발급 + trace/root ID 전달 | 한 trace, observation 5개, root 1개, 두 단계 모두 root의 자식 | 채택 |

채택 방식은 handler 캐시를 만들지 않는다. 최초 실행에서 실제 `agent-run` root를
만들고, interrupt event의 내부 `trace_resume_state`에 `langfuse_trace_id`와
`langfuse_root_observation_id`를 저장한다. resume은 새 handler를 만들되 두 ID를
`trace_context`로 받아 같은 root 아래 연결한다.

추가 구현:

- 평가 context에 `eval_run_id`, `eval_case_id`, `environment` 추가
- Agent root metadata에 run·Agent·평가 식별자 기록
- runner case 결과와 기존 DB `langfuse_trace_id` 컬럼 자동 연결
- Langfuse root 생성·callback·root 종료 실패가 Agent 실행을 막지 않게 격리
- root/resume 계약, event·승인 카드 전파, runner 저장, 장애 격리 회귀 테스트 추가

관련 74개 테스트가 통과했다. 실제 `WF-PROJECT-STATUS-001` 실행은 프로젝트 문서와
답변이 모델·Langfuse 외부 서비스로 전송될 수 있어 별도 승인 없이는 실행하지 않았다.
따라서 현재 증거는 합성 trace와 코드 회귀까지이며, 읽기 실패 사례·Jira HITL 거절
사례의 실제 trace와 HITL 대기 시간 observation은 남아 있다.

    `judge_calibration.jsonl`도 `eval_judge_result`에 동기화한다.
  - `append-case --fill-from-db` 추가 — case JSON에 `final_answer`/
    `tool_call_ids`가 없고 `agent_run_id`가 있으면 제품 DB에서 자동으로
    채운다. **사람이 UI로 실행한 case를 기록할 때 답변을 손으로 옮겨 적을
    필요가 없어졌다.** 이미 있는 값은 덮어쓰지 않는다.
- **`scripts/eval_report_viewer.py`**: 로컬 파일이 아니라 DB
  (`eval_run`+`eval_case_result`+`eval_judge_result`)를 직접 읽도록 전면
  교체했다. `fetch_final_answer_from_db`의 중복 로직을 걷어내고
  `fetch_agent_execution_summary`를 재사용한다. 이제 DB 접근이 필수라
  Docker 컨테이너 밖에서는 실행할 수 없다(기존엔 로컬 파일 fallback이 있었지만
  이번 결정으로 DB를 유일한 정본으로 좁혔다).

**검증**: TDD로 `sync_judge_result`/`fetch_agent_execution_summary`/
`load_judge_calibration_records`/`_fill_case_from_db` 전부 RED→GREEN 확인
(관련 테스트 54개 통과). 실제 DB에 대고 `ee604a4c` 실행의 Judge 결과를
`sync-db`로 동기화하고 재동기화로 멱등성(중복 0건)까지 확인했다. 화면도
로컬 파일 41건이 아니라 DB에 실제 동기화된 15건만 정확히 보여주는 것을
확인했다 — DB가 이제 화면의 유일한 정본이라는 의도와 일치한다.

**후속**: 배포 환경 검증을 할 때 이 저장 구조를 그대로 재사용한다(같은
DB 접근 방식, 같은 화면). 배포 DB에는 이 마이그레이션을 별도로 적용해야
하고, 배포 환경에서의 실제 시나리오 실행은 사람이 직접 격리·정리 절차를
지켜야 한다 — 자동으로 안전해지지 않는다.

## Judge 단독 실행 지원 — 사람 판정 없이 화면 검토용으로 돌리기

"사람 판단은 화면에서 사람이 직접 하면 되니 `--human-verdict` 없이 Judge만
돌아가면 된다"는 요구에 맞춰 `eval_judge.py`의 사람 판정 요구조건을
없앴다. 정식 calibration(사람 판정과 일치율 비교)과 화면 검토용 단독 판정을
같은 스크립트로 분리했다.

- **`services/evaluation/calibration.py`**: `make_calibration_record`의
  `human_verdict`를 필수에서 `dict | None`으로 바꿨다. `None`이면
  `comparison`도 계산하지 않고 그냥 `None`으로 둔다 — 비교 대상이 없는데
  일치율을 지어내지 않는다. TDD로 두 경우(없을 때 `comparison=None`,
  있을 때는 그대로 계산됨) 모두 확인.
- **`scripts/eval_judge.py`**: `--human-verdict`를 `required=True`에서
  `default=None`인 선택 인자로 바꿨다. 생략하면 `load_human_verdict` 호출
  자체를 건너뛰고 `human=None`으로 넘어간다. `--evidence`는 그대로
  필수다 — Judge가 마스킹 근거 없이 판단하는 것까지 허용하지는 않는다.
- **실제 검증**: `efeb10d7` 실행(아직 Judge를 돌린 적 없는 case)에
  `--human-verdict` 없이 `eval_judge.py`를 실제로 호출해 응답을 받았다.
  기록된 `judge_calibration.jsonl`에서 `human_verdict=None`,
  `comparison=None`을 확인했고, `eval_record.py sync-db`로 DB에 동기화한
  뒤 `eval_report_viewer.py`로 화면을 다시 만들어 Judge 5개 차원 판정·근거·
  요약이 사람 판정 언급 없이 정상 출력되는 것을 HTML에서 직접 확인했다
  (기존 `build_judge_panel`이 애초에 human_verdict/comparison을 표시하지
  않게 만들어져 있었으므로 화면 쪽 추가 수정은 필요 없었다).
- **문서 갱신**: `README.md`에 `--human-verdict`가 선택 인자임과 두 용도
  (화면 검토 단독 판정 vs 정식 calibration)를 구분해 설명하고 예시 명령을
  추가했다. `judge_calibration_v0.md` 서두에 이 문서는 정식 calibration
  계약이며 화면 검토용 단독 판정에는 사람 판정 파일이 필요 없다는 안내를
  추가했다.

## 두 번째 신규 시나리오(WF-STAFFING-RECOMMENDATION-002) 실행과 "사용자 입력 안 뜸" 버그

지금까지 새 파이프라인을 실제로 태운 건 `WF-PROJECT-STATUS-001` 뿐이었어서,
정말 다른 시나리오에도 그대로 동작하는지 확인하려고 `WF-STAFFING-RECOMMENDATION-002`
(인력 배치 추천)를 처음부터 새로 실행했다. 도구 호출 4회로 후보 3명을
추천했고 결정론적 판정 12/12 통과, DB 동기화·화면 재생성까지 정상
확인했다(이 case는 Judge evidence bundle이 아직 없어 Judge는 설계대로
자동 스킵되어 `UNCERTAIN`으로 남았다 — 버그 아님).

화면을 확인하던 중 **"사용자 입력이 안 뜬다"**는 진짜 버그를 찾았다. 원인은
`services/evaluation/runner.py`의 `evaluate_events()`가 애초에 반환 dict에
`input`을 담지 않았던 것 — 데이터셋 case 정의(`agent_workflow_v1.json`)에는
`input`(실제 사용자 프롬프트)이 있지만, 에이전트 실행 결과를 기록할 때
그 값을 복사해 온 적이 없었다. 그래서 `eval_report_viewer.py`의
`build_request_block()`이 찾던 `case.get("input")`은 지금까지 단 한 번도
채워진 적이 없었고, 문서 스트링에 "2026-08-26부터 사용자 입력을 DB에
남긴다"고 적어놓고도 실제로는 안 남기고 있었다.

- **`services/evaluation/runner.py`**: `evaluate_events()`가 반환하는
  case_result dict에 `"input": case["input"]`을 추가했다(TDD: 새 assertion으로
  RED `KeyError: 'input'` 확인 후 한 줄 추가로 GREEN, 관련 테스트 12개 통과).
  이제부터 실행되는 모든 case는 사용자 입력을 로컬 파일·DB에 그대로 남긴다.
- **`scripts/eval_report_viewer.py`**: 이 수정 이전에 이미 기록·동기화된
  17건은 `input`이 없는 채로 DB에 남아 있어 위 수정만으로는 화면에 소급
  적용되지 않는다. `final_answer`를 DB에서 복구하던 것과 같은 방식으로,
  `case.get("input")`이 없으면 데이터셋 파일(`agent_workflow_v1.json`)에서
  같은 case_id를 찾아 원문 `input`을 보여주는 `_recover_input_from_dataset()`를
  추가했다. case_id가 반복·재시도로 `-R1`, `-CLEAN-R1`, `-RETEST-R2`처럼
  접미사가 붙어도(`case_id == dataset_id` 또는
  `case_id.startswith(dataset_id + "-")`) 원래 데이터셋 case로 매칭한다 —
  없는 값을 지어내지 않고 있는 원문을 그대로 보여주는 것뿐이다.
- **검증**: 화면을 다시 만들어 생성된 case 페이지 17건 전부에서 "사용자
  요청" 블록이 실제 프롬프트 원문과 함께 나오는 것을 확인했다(신규 실행
  건은 `runner.py` 수정으로, 과거 실행 건은 데이터셋 복구로).

## 5개 시나리오 전부 화면 점검 — REJECTED 상태 배지 버그와 중복 식별자 표시 정리

"시나리오가 5개인데 지금 2개만 화면으로 확인했다"는 지적을 받고, 나머지
3개(`WF-PROMPT-INJECTION-003`, `WF-JIRA-HITL-004A/B`, `WF-ACTION-ITEM-GAP-005`)
의 화면을 실제로 열어 점검했다. DB에는 이미 다 동기화돼 있었지만
(auto runner가 아니라 HITL 시나리오라 `eval_record.py append-case`로 사람이
직접 기록한 것) 화면 표시 자체를 이번에 처음 확인했다.

- **REJECTED 상태 배지 버그**: `WF-JIRA-HITL-004A`는 사람이 Jira 이슈 생성을
  거절하는 게 정답인 시나리오라 case 상태가 문자열 그대로 `"REJECTED"`로
  기록된다. 그런데 `STATUS_CLASS`/`STATUS_LABEL` 사전에 `REJECTED`가 없어서
  화면에 영어 원문 "REJECTED"가 그대로 뜨고, 색상도 `"uncertain"`(주의·노랑)
  기본값으로 잘못 표시됐다 — 이 case는 사실 assertion 1개가 실패한 진짜
  실패 case였는데 노란색 "불확실"로 보여 실패라는 인상을 못 줬다. 실제로
  DB의 모든 case를 대조해 보니 `failure_reason`이 있는지 여부가 assertion
  전부 통과 여부와 예외 없이 100% 일치했다(`REJECTED`처럼 시나리오에 따라
  정답일 수도 있는 상태 문자열만으로는 성공/실패를 알 수 없기 때문). 그래서
  상태 색상을 상태 문자열이 아니라 `failure_reason` 유무로 판정하는
  `case_status_class()`로 바꿨고(`eval_report_viewer.py`), `STATUS_LABEL`에
  `REJECTED: "거절됨(HITL)"`, `NEEDS_CLARIFICATION: "확인 필요"`를 추가했다.
  전체 목록 화면(index.html)의 상태 배지도 지금까지 한글화가 안 돼 있었던
  걸 발견해 같이 고쳤다(개별 case 페이지만 번역돼 있었다).
- **중복 식별자 표시**: `ASSERTION_GLOSSARY`에 없는(=시나리오별로 사람이
  직접 지은) assertion 이름은 라벨을 식별자 그대로 쓰는데, 그 뒤에 같은
  문자열을 괄호로 또 붙이고 있었다(`user_goal_preserved
  (user_goal_preserved)`처럼 정보 없이 반복). `_assert_id_badge()`를 추가해
  라벨과 식별자가 같으면 괄호를 아예 생략하도록 고쳤다. `WF-PROMPT-INJECTION-003`·
  `WF-ACTION-ITEM-GAP-005`·`WF-JIRA-HITL-004A/B`는 assertion을 전부 사람이
  시나리오별로 직접 지은 이름을 쓰고 있어(약 40개) `ASSERTION_GLOSSARY`에
  없다 — 이 이름들을 전부 한글로 옮기는 건 각 검증 항목의 의미를 다시
  확인해야 하는 별도 작업이라 이번 범위에는 포함하지 않았다.
- **검증**: 5개 시나리오 전부 다시 화면을 만들어 상태 배지(개별 페이지 +
  전체 목록)가 올바른 한글 라벨과 성공/실패 색상으로 나오는 것과, 중복
  식별자가 사라진 것을 확인했다. 기존 관련 테스트 58개는 그대로 통과한다.

## 시나리오별 커스텀 assertion 76개 전부 한글화

남겨뒀던 "약 40개 커스텀 assertion 한글화"를 이어서 진행했다. DB의 모든
case를 대조해 지금까지 실제로 쌓인 고유 assertion 이름을 전부 뽑아보니
(기존 20개 항목 — 자동 runner 표준 15개 + Judge 5차원 — 제외) 76개였다 —
`WF-PROMPT-INJECTION-003`,
`WF-ACTION-ITEM-GAP-005`, `WF-JIRA-HITL-004A/B` 각각의 assertion뿐 아니라
`WF-PROJECT-STATUS-001-CLEAN-R1`·`WF-STAFFING-RECOMMENDATION-002-CLEAN-R1`
(자동 runner가 아니라 CLEAN 계정으로 사람이 직접 기록한 재검증 실행)도
독자적인 커스텀 이름을 쓰고 있어 포함됐다.

각 시나리오의 데이터셋 정의(`postconditions`·`required_facts`·
`forbidden_claims`)와 실제 `detail` 텍스트를 근거로 76개 전부에 한글
라벨과 분류를 붙였다(`ASSERTION_GLOSSARY`, 총 96개 항목). 기존 6개 분류
(실행/도구/안전/호출예산/근거/판정) 외에 이번에 실제로 필요해진 분류 3개
(정확성·표현·정리)를 추가했다 — 지어낸 분류가 아니라 76개를 다 훑어보고
기존 6개로는 표현이 안 되는 것만 새로 만들었다(예: "제목이 계약과 일치"는
근거·안전·도구 어디에도 안 맞아 "정확성"으로 분류).

**검증**: 생성된 case 페이지 17건 전체를 정규식으로 스캔해서 한글이 전혀
없는 assertion 라벨이 남아 있는지 확인했고, 0건이었다 — 이제 화면에 뜨는
모든 assertion·Judge 차원 라벨이 한글이다. 관련 테스트 58개 그대로 통과.
