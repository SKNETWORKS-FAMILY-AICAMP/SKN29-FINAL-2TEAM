# 2026-08-26 작업03 — 평가 결과 DB 저장 기반

## 목적

기존 로컬 append-only 평가 결과를 보존하면서, 같은 `eval_run_id`로 프로젝트 DB에
조회·집계 가능한 사본을 남긴다. 평가 실행 자체가 DB 장애에 종속되지 않게 파일
기록과 DB 동기화를 분리한다.

## 구현 내용

- `eval_run`: manifest·summary와 실행 버전·상태·동기화 상태 저장
- `eval_case_result`: 반복 case를 JSONL 순서인 `case_index`로 구분해 저장
- `2026-08-26_eval_result_storage.sql`: 두 테이블과 조회 인덱스 생성
- `_apply.py --check`: 두 평가 테이블 누락 검사
- `EvaluationResultRepository`: 완료 실행의 두 단계 멱등 동기화
  1. `SYNC_PENDING` 실행 선기록
  2. case 저장 후 `SYNCED` 확정
- `read_completed_run`: 종료 여부와 manifest·summary·case의 `eval_run_id` 일치 검증
- `eval_record.py sync-db`: 종료된 실행 폴더를 DB에 동기화하는 명령
- 초기화 정책:
  - `reset_demo.sql`: 새 시연에 과거 성적이 섞이지 않도록 평가 결과도 삭제
  - `reset_eval.sql`: 입력 프로젝트·문서만 교체하고 과거 비교 성적은 보존

같은 ID의 기존 DB 결과와 로컬 내용이 다르면 덮어쓰지 않고 오류로 중단한다. DB
동기화는 로컬 네 산출물을 수정하지 않는다.

## main 병합·배포 시 순서

1. 코드와 `DB/schema.sql`을 병합한다.
2. 대상 DB를 백업하고 연결 대상이 로컬·공유·운영 중 어디인지 확인한다.
3. `DB/migrations/2026-08-26_eval_result_storage.sql`만 적용한다.
4. `python DB/migrations/_apply.py --check`로 `eval_run`과
   `eval_case_result` 누락이 없는지 확인한다.
5. 종료된 비운영 평가 실행 한 건을 `scripts/eval_record.py sync-db`로 동기화한다.
6. 같은 명령을 다시 실행해 case가 중복되지 않는지 확인한다.
7. 기존 `max_iterations` 기본값 불일치는 별도 마이그레이션 적용 여부를 담당자와
   확인하며 이 작업에 묶어 조용히 변경하지 않는다.

## Judge 근거 확인 규칙 보완

`KNOWN-EVAL-001`의 재발을 막기 위해 `judge_calibration_v0.md`에 공통 선행조건을
추가했다. 사람과 Judge 모두 근거 없음·과장을 확정하기 전에 사례의
`required_evidence_documents + optional_evidence_documents` 합집합을 확인한다.
미확인·접근 불가 문서가 있으면 `FAIL`이 아니라 `UNCERTAIN`으로 둔다.

optional 문서는 Agent가 반드시 검색해야 한다는 뜻이 아니다. Agent 실행 조건과
판정자의 부정 판정 전 확인 범위를 분리했다. 향후 runner는 이 합집합으로 evidence
bundle을 먼저 만들고 완전성 검사를 통과한 뒤 Judge를 호출한다.
