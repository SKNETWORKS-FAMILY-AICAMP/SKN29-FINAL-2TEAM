# 2026-08-26 작업03 — 평가 결과 DB 저장 기반

## 목적

기존 로컬 append-only 평가 결과를 보존하면서, 같은 `eval_run_id`로 프로젝트 DB에
조회·집계 가능한 사본을 남긴다. 평가 실행 자체가 DB 장애에 종속되지 않게 파일
기록과 DB 동기화를 분리한다.

## 구현 내용

- `eval_run`: manifest·summary와 실행 버전·상태·동기화 상태 저장
- `eval_case_result`: 반복 case를 JSONL 순서인 `case_index`로 구분해 저장
- `2026-08-26_eval_result_storage.sql`: 두 테이블과 조회 인덱스 생성
- `_apply.py --check`: 두 평가 테이블 누락 검사
- `EvaluationResultRepository`: 완료 실행의 두 단계 멱등 동기화
  1. `SYNC_PENDING` 실행 선기록
  2. case 저장 후 `SYNCED` 확정
- `read_completed_run`: 종료 여부와 manifest·summary·case의 `eval_run_id` 일치 검증
- `eval_record.py sync-db`: 종료된 실행 폴더를 DB에 동기화하는 명령
- 초기화 정책:
  - `reset_demo.sql`: 새 시연에 과거 성적이 섞이지 않도록 평가 결과도 삭제
  - `reset_eval.sql`: 입력 프로젝트·문서만 교체하고 과거 비교 성적은 보존

같은 ID의 기존 DB 결과와 로컬 내용이 다르면 덮어쓰지 않고 오류로 중단한다. DB
동기화는 로컬 네 산출물을 수정하지 않는다.

4. `python DB/migrations/_apply.py --check`로 `eval_run`과

### 후속 코드 검토 반영

Judge와 runner 코드 검토에서 확인된 세 문제를 반영했다.

1. `eval_run.py`가 Agent 결과를 계산한 뒤 임시 세션 삭제에 실패하면 case 결과를
   기록하지 못하던 순서를 수정했다. 이제 cleanup을 시도한 뒤 성공·실패 상태를
   case에 넣고 `append_case`부터 수행한다. 삭제 실패 시 Agent 결과는 보존되고 실행
   summary만 `ABORTED`로 종료된다.
2. runner와 calibration이 별도로 만들던 Judge 요청·응답 계약을
   `services/evaluation/judge.py`로 통합했다. 두 경로 모두 최종 답변, 결정적 assertion,
   제한된 tool trace와 전체 evidence bundle을 같은 구조로 사용하며, 전체 verdict와
   5개 차원이 빠진 응답은 `ERROR`다.
3. `eval_judge.py`가 모델 호출 실패와 응답 JSON·스키마 검증 실패를 구분해 각각 종료
   코드 2와 3으로 반환하도록 했다. 실패 응답 원문과 endpoint 세부정보는 출력하지
   않으며 파싱 성공 전에는 결과 파일을 쓰지 않는다.

세션 삭제 실패 시에도 case가 append되는 회귀 테스트와 공통 Judge 계약 검증을
추가했다. recorder·DB 저장 회귀를 포함한 관련 테스트는 총 35개가 통과했다.

## 도구 실패 후 재시도 루프 계측

기존 runner는 도구 실패 자체와 전체·도구별 호출 상한은 잡았지만, 실패 이후 같은
호출을 몇 번 다시 시도했고 복구했는지는 숫자로 남기지 않았다. 이를 다음처럼
보완했다.

- `tool_call_id`로 시작·완료 event 연결
- `tool_ref + 정규화된 arguments` 조합으로 같은 호출 판별
- arguments는 SHA-256 계산에만 사용하고 원문·해시는 결과에 저장하지 않음
- 실패, 실패 후 재시도, 재시도 성공 복구, 최대 연속 실패, 미완료 시작 수 집계
- 도구별 시도·실패·재시도·복구 합계를 `tool_reliability.by_tool`에 기록
- 대시보드용 전체 숫자는 기존 `metrics`에도 기록

실패 완료가 발생한 뒤 시작된 동일 호출만 재시도다. 같은 호출이 병렬로 먼저 시작된
상태에서 하나가 실패한 경우 나머지 선행 호출은 재시도로 세지 않는다. 서로 다른
검색어처럼 arguments가 바뀐 후속 호출도 재시도가 아니다.

데이터셋을 v10으로 올리고 조회 중심 001·002·003·005 사례에 다음 정책을 명시했다.

- 동일 도구·인자 실패 후 재시도 최대 1회
- 동일 도구·인자 연속 실패 최대 2회

004A·004B Jira HITL은 사용자 거절·승인 결과가 일반 도구 장애와 다르므로 공통 재시도
정책을 적용하지 않았다. 실패 후 성공, 지속 실패, 다른 인자 호출, 병렬 선행 호출과
결과 계약 검증 테스트를 추가했고 관련 테스트 총 41개가 통과했다. 기존
`tool_calls_completed_ok`는 유지되어, 마지막 재시도가 성공해도 앞선 실패가 전체
실행에서 사라지지 않는다.

## 제품 런타임 도구 실패 복구 설계

runner의 재시도 계측 다음 단계로 실제 Agent 런타임의 실패 복구 방향을 검토했다.
현재 구현된 것은 실행 뒤 실패·반복을 측정하는 기능이며, 조회 도구를 자동으로 다시
실행하거나 쓰기 실패 뒤 사용자 결정을 받는 제품 기능은 아직 구현되지 않았다.

결정한 정책은 다음과 같다.

- 조회 도구의 일시적인 기술 오류만 최초 호출 포함 최대 3회 실행
- 인증·권한·입력 오류와 검색 결과 부족은 자동 재시도하지 않음
- 쓰기 도구는 자동 재시도하지 않음
- 쓰기 실패 카드에서는 `retry`·`skip`·`reject`를 구분
- 사용자 `retry` 한 번은 실제 재실행 한 번만 허용
- 쓰기 실패 카드는 체크포인터 재진입 전에 외부 DB에 `PENDING` 상태와
  `run_id + tool_call_id` 멱등성 키를 먼저 저장해야 함

현재 승인 흐름은 한 턴의 여러 대상을 `decisions` 배열로 받으므로 UI와 API는 이
패턴을 재사용한다. 다만 병렬 쓰기 실패는 내부적으로 여러 `interrupt_id`가 생길 수
있으므로 서버가 배열의 `failure_index`를 실제 ID에 매핑해 LangGraph의 다중 resume
형태로 변환한다. 모든 실패를 하나의 interrupt로 강제로 모으는 새 조정 노드는 v0에서
제외했다.

상세 계약과 테스트 조건은
`../../설계/eval/tool_failure_recovery_v0.md`에 기록했다. 우선 조회 자동 재시도만
구현·검증하고, 쓰기 실패 카드는 1단계 안정화 뒤 별도 설계 승인 대상으로 유지한다.

## 조회 도구 자동 재시도 1단계 구현

설계 검토에서 재개 계약(`decisions` 배열 + 내부 `interrupt_id` 매핑)이 문서
설계와 이미 일치함을 확인한 뒤, 1단계 조회 도구 자동 재시도를 구현했다.

- 코드: `services/agent_runtime/factory.py`
  (`_is_transient_tool_failure`, `_call_tool_handler`)
- 핵심 발견: 애초 예상한 LangGraph `wrap_tool_call` 미들웨어 자리는 쓸 수 없었다.
  `_IdempotencyAwareTool`이 `handle_tool_error=True`로 만들어져 `BaseTool.invoke()`가
  `ToolException`을 미들웨어 체인에 닿기 전에 문자열로 삼킨다. 재시도는 `_run()`
  내부에서 `tool.handler()`를 직접 감싸는 자리 하나에 넣었다.
- 분류: `exc`·`__cause__`·`__context__` 체인을 최대 5단계까지 따라가며
  `McpError.code`(`timeout`/`unreachable`/`429`), `requests.Timeout`/
  `ConnectionError`, `requests.HTTPError.response.status_code`(429/500/502/503/504)를
  확인한다. `OAuthError(...) from exc`로 감싼 Jira·Drive 실패도 이 체인 추적으로
  잡는다.
- 재시도: 읽기 전용 도구만, 최초 호출 포함 최대 3회, 지수 backoff+jitter. 쓰기
  도구는 항상 1회.
- 테스트: TDD로 `tests/test_factory.py::ToolTransientFailureRetryTests` 7개를
  먼저 작성해 RED(구현 전 `time` 미import로 실패)를 확인한 뒤 구현해 GREEN
  전환. `test_factory.py`·`test_tool_timeout.py`·`test_middleware_factory.py`
  120개, `test_executor.py`·`test_tool_loader.py`·`test_evaluation_*` 3개
  스위트도 회귀 없이 통과했다. `test_bootstrap.py`의 10개 오류는 로컬 호스트가
  Docker 내부 DB 주소 `db`를 해석하지 못하는 기존 환경 문제이며 이번 변경과
  무관하다.
- 알려진 한계: 재시도가 같은 tool_handler 호출 안에서 일어나 별도
  tool_started/tool_completed 쌍을 만들지 않는다. 평가 runner의
  `tool_reliability` 집계(모델의 재호출 기준)는 이 내부 재시도를 세지 못하므로,
  §7 완료조건("실전 로그로 확인")은 당분간 `logger.warning`/`logger.info`
  구조화 로그로 대신한다. DB·Langfuse·OpenTelemetry에 재시도 attempt를 남기는
  것은 8단계 관측 연동에서 함께 처리한다.
- 검증 체크포인트: Git `30b187e` (`feat: add core agent evaluation runner and calibration`).
- 관련 평가·런타임 테스트: Docker 환경 121개 통과.
- DB 보관 재확인: `20260826T050101Z-ee604a4c`, 1 case, `SYNCED`.
