## 1. `2e07626` — Jira 이슈 등록 정책이 바뀌었다 (가장 중요)

**담당자 기본값이 바뀌었다.** 이전에는 담당자를 안 정하고 등록을 요청하면
서버가 **요청한 사람 본인**으로 자동 채웠다. 지금은 **기본이 미배정**이고,
사용자가 명시적으로 "나에게 배정해줘"라고 말했을 때만(`assign_to_requester:
true`) 요청자 본인으로 채운다.

- **왜 바꿨나**: 실제 대화에서 담당자를 안 정했는데 조용히 요청자에게
  배정되는 것이, 사용자가 기대한 동작이 아니었다(2026-08-25 Jira HITL
  구현기록). 명시적으로 요청했을 때만 배정하는 쪽이 안전하다.
- **프로젝트 키 해석도 강제됐다.** 채팅에서 이미 프로젝트를 골랐다면
  (`proj_id`가 있으면) 모델이 보낸 `project_key`는 무시하고 저장된 연결을
  정본으로 쓴다. 모델이 프로젝트 이름을 Jira key로 오인하거나 임의의 key를
  추측해도 실제로는 그 채팅이 속한 프로젝트에만 등록된다.
- **부분 실패 처리도 바뀌었다.** 이슈 생성이 전부 실패했는데(`created=[]`,
  `failed=[...]`) 도구 상태가 `OK`로 보고되던 버그를 고쳐, 이제 하드 실패
  (`ToolInputError`)로 처리한다.
- **영향 범위**: `services/harness/registry.py`의 `_jira_create_issues`,
  `_fill_default_jira_assignee`, `BUILTIN_TOOLS`의 도구 설명. 프런트
  (`liveChat.ts`)는 승인 카드에 `jiraAssigneeMode`(`requester`/`explicit`/
  `unassigned`)를 추가로 보여준다.
- **병합 후 확인할 것**:
  - [ ] 담당자를 안 정하고 Jira 등록을 승인하면 실제로 미배정으로 생성되는지
  - [ ] "나에게 배정해줘"라고 말했을 때만 요청자 본인으로 배정되는지
  - [ ] 승인 카드에 담당자 처리 방식이 표시되는지
  - [ ] 이슈 생성이 전부 실패하면 성공으로 위장되지 않고 실패로 보고되는지

## 2. `55501b5` — 팀원이 TEAM 범위 스킬을 등록하려 하면 승인 카드 자체가 안 뜬다

**이전 동작**: 팀원(`member`)이 TEAM 범위로 스킬 등록을 요청하면 일단 승인
카드가 뜨고, 사용자가 승인한 **뒤에** 서버가 권한으로 막았다. 승인해도 왜
안 되는지 화면만 봐서는 알기 어려웠다.

**바뀐 동작**: `member` + `TEAM` 범위 조합이면 애초에 승인 카드를 안 띄운다
(`_skill_register_requires_confirmation`). 모델에게 주는 도구 설명에도 현재
역할이 PERSONAL만 가능한지 TEAM도 가능한지 알려준다
(`_tool_description_for_context`) — 모델이 애초에 그 요청을 안 하도록
유도한다.

- **영향 범위**: `services/agent_runtime/factory.py`. 리더(`leader`) 권한
  흐름은 안 바뀐다 — 팀원이 TEAM 범위를 시도하는 경우만 바뀐다.
- **병합 후 확인할 것**:
  - [ ] 팀원이 "팀 전체가 쓸 스킬로 등록해줘"라고 하면 승인 카드 없이 개인
    범위로만 등록되거나, 모델이 스스로 범위를 PERSONAL로 조정하는지
  - [ ] 리더의 TEAM 범위 등록은 기존처럼 승인 카드가 정상적으로 뜨는지

## 3. `5632279` — Root 에이전트 시스템 프롬프트에 규칙 2줄 추가 (전체 에이전트 영향)

`RUNTIME_SCAFFOLD`(모든 에이전트가 공유하는 기본 지시문)에 다음 두 줄이
추가됐다.

- "직접 확인된 사실과 추론·추천을 구분하고, 추론·추천을 확인된 사실처럼
  표현하지 않는다."
- "문서에 명시된 고유명칭·직책·역할·상태를 다른 확정 명칭으로 임의 변경하지
  않는다. 의미를 해석하거나 역할을 추론한 경우 반드시 추론임을 표시한다."

- **왜 추가했나**: `WF-STAFFING-RECOMMENDATION-002` 평가에서 반복 관찰된
  근거 과장(`KNOWN-EVAL-001`)을 고치려는 시도였다. **다만 이후 조사 결과
  그 특정 사례는 Agent 결함이 아니라 평가자가 근거 문서 하나를 놓친 평가
  오류로 판명됐다**(`workflow_002_staffing_recommendation.md` "판정 정정
  — 2026-08-26"). 즉 이 프롬프트 수정이 그 버그를 고친 것은 아니다 —
  버그 자체가 없었다.
- **그래도 유지하는 이유**: 이 두 규칙 자체는 일반적으로 유효한 지시문이라
  되돌리지 않았다. 특정 결함을 겨냥해 급하게 추가한 문장이 아니라는 점만
  병합하는 사람이 알아야 한다 — 이후 다른 평가에서 이 문구 때문에 답변
  스타일(예: 확정 어투가 줄고 "추정됨" 같은 표현이 늘 수 있음)이 달라지는
  게 관찰되면, 이 커밋이 원인일 수 있다는 것을 참고한다.
- **영향 범위**: `services/agent_runtime/prompts.py` — **Root와 Child 전부**,
  즉 이 저장소의 모든 에이전트 실행에 영향을 준다(특정 workflow 한정 아님).
- **병합 후 확인할 것**:
  - [ ] 일반 대화 답변 톤이 과도하게 방어적으로 바뀌지 않았는지(예: 확실한
    사실까지 "추정됩니다"로 약화하지 않는지)
  - [ ] 문서의 원문 명칭(파일명·직책 등)이 답변에서 임의로 축약·변경되는
    문제가 남아 있는지 — 남아 있다면 `2026-08-25_Jira_HITL_미리보기_편집_
    구현기록.md` §6의 "원문 파일명 보존 문제"와 같은 계열의 미해결 결함이다.
