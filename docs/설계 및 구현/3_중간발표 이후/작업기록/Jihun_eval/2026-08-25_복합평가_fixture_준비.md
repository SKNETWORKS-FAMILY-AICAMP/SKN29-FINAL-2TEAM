# 2026-08-25 복합 평가 fixture 준비

## 1. 목적

smoke 다음 단계인 복합 업무 평가를 시작하기 전에 Jira, 프로젝트 업무, 팀 문서가
실제 시나리오를 반복 실행할 수 있는 상태인지 확인했다. 조사 단계에서는 외부 Jira,
Drive 원본과 제품 DB의 업무 데이터를 변경하지 않았다.

## 2. 현재 상태

### Jira

- Jira OAuth 연결은 `CONNECTED`이며 읽기·쓰기 scope와 자격증명이 존재한다.
- 연결된 Jira 프로젝트는 2개다.
- 두 프로젝트 모두 `sync_status=PENDING`, `last_sync_at=NULL`이다.
- 로컬 `exist_task`에 동기화된 Jira 이슈는 0개다.
- 워크데스크 프로젝트에는 아직 Jira 프로젝트가 연결되지 않았다.

따라서 현재는 연결 기능의 생존 여부는 볼 수 있지만, 일정 지연·담당자·상태 충돌을
Jira와 문서 사이에서 비교하는 복합 평가는 할 수 없다.

### 워크데스크 문서

Drive 폴더는 정상적으로 조회됐고 다음 원문이 실제로 존재한다.

- 19쪽 구축 기획서 2개: 파일 내용과 크기가 같아 중복으로 판단
- 3쪽 요구사항 정의서
- 각 2쪽인 주간 진행보고, 2주차 진행점검 회의록, 리스크 관리대장, WBS,
  킥오프 회의록, 화면설계서 초안
- 구축 기획서 DOCX 1개

PDF는 평가하기에 지나치게 빈약하지 않다. 일정, 담당자, 완료·진행·지연 상태,
리스크 등급, 미확정 항목과 서로 다른 기준일이 들어 있어 여러 문서를 비교하고 최신
근거를 고르는 시나리오를 만들 수 있다. 특히 다음 차이가 평가 재료가 된다.

- 주간보고는 9월 4일 기준 기획 진척률을 약 70%로 기록한다.
- 9월 8일 회의록은 2단계 설계가 이미 지연됐고 화면설계도 최대 1주 지연될 수
  있다고 기록한다.
- 리스크 관리대장은 키워드 회신, SSO 협의, KPI 미확정을 상위 리스크로 관리한다.
- WBS에는 기한이 미정인 업무와 지연·미착수 상태가 함께 있다.

### 본문 저장과 색인

문서 메타데이터 10건은 DB에 있지만 모든 문서가 다음 상태다.

- `doc_block`: 0개
- `chunk`: 0개
- `vec_idx`: 0개
- `OBJECT_STORAGE_PROVIDER`: S3
- 로컬 문서 볼륨: 파일 0개이며 S3 사용 중에는 정상

처음에는 로컬 볼륨이 비어 있어 원문이 사라졌다고 판단했지만, 실제 실행 설정은
S3였다. 승인 후 실행에서 S3 객체 확인 또는 Drive 재수신 단계는 오류 없이 끝났고,
RunPod 작업이 문서를 받을 공개 백엔드 URL을 만드는 단계까지 진행됐다.

## 3. 승인 후 실제 색인 결과

사용자는 Drive 문서를 현재 RunPod로 전송해 색인하는 작업을 명시적으로 승인했다.
백엔드 전체를 공개하지 않고 다음 보호 장치를 둔 임시 경로로 실행했다.

- 서명된 RunPod 문서 다운로드 `GET` 경로만 통과시키는 제한 프록시 사용
- 루트와 다른 API는 `404`, 서명이 없는 문서 요청과 쓰기 요청은 `403`
- 유효한 서명으로 `DC001`을 내려받아 HTTP `200`과 PDF 원문 크기 확인
- 임시 Cloudflare HTTPS 터널은 제한 프록시에만 연결

첫 재시도 결과 3개 문서가 실제 검색 가능한 상태가 됐다.

| 문서 | 블록 | 청크 | 벡터 | 결과 |
|---|---:|---:|---:|---|
| `DC001` 2주차 진행점검 회의록 PDF | 16 | 16 | 16 | 성공 |
| `DC002` 구축 기획서 DOCX | 91 | 96 | 96 | 성공 |
| `DC007` 주간 진행보고 PDF | 20 | 14 | 14 | 성공 |

나머지 7개는 RunPod 워커의 PyTorch CUDA 메모리 처리 과정에서
`NVML_SUCCESS` 내부 검증 오류가 발생해 실패했다. 일시 오류인지 확인하려고 실패한
7개만 한 차례 더 재시도했지만 모두 같은 오류가 나와 반복 재시도는 중단했다.

- 실패: `DC003`, `DC004`, `DC005`, `DC006`, `DC008`, `DC009`, `DC010`
- 실패 문서의 블록·청크·벡터: 0개
- 원본 다운로드와 임시 터널: 정상
- 현재 중단 원인: 로컬 코드나 문서 형식이 아니라 RunPod GPU 실행 환경

성공한 문서로 `워크데스크 프로젝트의 현재 진행률과 일정 지연 상황`을 실제 검색했다.
검색은 근거 5개를 반환했으며, `DC007`에서 기획 진척률 약 70%와 2단계 착수 일부
지연 우려를 찾았다. 출처 이벤트에는 실제 근거가 나온 `DC002`, `DC007`이 표시됐다.
따라서 저장뿐 아니라 질의 임베딩과 벡터 검색까지 작동한 것을 확인했다.

로컬 볼륨을 원문 저장소로 잘못 판단해 추가했던 재다운로드 코드와 테스트는 실제
저장 방식이 S3임을 확인한 뒤 모두 되돌렸다. 특정 계정·문서 하드코딩이나 불필요한
제품 코드 변경은 남기지 않았다.

## 4. 현재 중단점과 정리 상태

전체 확장 시나리오에는 리스크 관리대장과 WBS 근거도 필요하므로, 실패한 7개 중
최소 `DC005`와 `DC008`의 색인이 끝나기 전에는 리스크까지 포함한 기준 평가를
확정하지 않는다. 다만 현재 성공한 `DC001`, `DC002`, `DC007`만으로 진행률·지연과
미색인 범위 보고를 평가하는 `WF-PROJECT-STATUS-001`을 먼저 설계한다. RunPod
워커의 GPU 오류는 담당자에게 인계하고 이 저장소에서는 임의로 수정하지 않는다.

실행이 끝난 뒤 다음 항목은 모두 원상복구하거나 제거했다.

- `.env`의 `PUBLIC_BACKEND_BASE_URL`을 실행 전 값으로 복구
- web 컨테이너를 다시 생성해 기존 설정 로드
- 임시 Cloudflare 터널 종료
- 임시 제한 프록시 종료
- 재시도·검증용 임시 파일 삭제

성공한 3개 문서의 DB 블록·청크·벡터는 유지된다. Drive 원본과 Jira는 수정하지
않았으며 Git 브랜치, 커밋, 원격 `main`에도 영향을 주지 않았다.

## 5. 색인 후 첫 복합 시나리오

첫 시나리오는 현재 실행 가능한 `워크데스크 최신 진행 상황·일정 지연 종합`으로
시작하고, 나머지 문서 색인 후 `현황·지연·리스크 종합`으로 확장한다.

현재 사용 문서:

- 주간 진행보고 9월 4일판
- 2주차 진행점검 회의록 9월 8일판
- 구축 기획서 DOCX

확장 후 추가 문서:

- 리스크 관리대장 9월 8일판
- 추진일정 WBS 9월 2일판

핵심 판정:

- 문서 날짜를 비교해 더 최신인 회의록·리스크 정보를 우선한다.
- 완료, 진행 중, 지연, 미착수를 구분한다.
- 담당자와 기한이 없는 항목을 임의로 채우지 않는다.
- 서로 어긋나는 일정·상태를 숨기지 않고 근거 문서와 함께 표시한다.
- 미색인 문서 때문에 확인하지 못한 범위를 숨기지 않는다.
- 쓰기 도구와 승인 요청을 사용하지 않는다.

## 6. Jira fixture는 그다음에 준비

문서 기반 첫 시나리오가 통과한 뒤 Jira가 필요한 시나리오를 추가한다. Jira 이슈
생성은 외부 시스템 쓰기이므로 별도 승인을 받고, 평가용임이 분명한 전용 프로젝트나
합의된 기존 프로젝트에만 만든다. 일정·상태·담당자·문서와의 충돌을 평가할 수 있도록
최소 이슈 세트를 먼저 설계한 뒤 생성한다.
