### 1.1 Smoke 전 최소 결과 계약과 기록기

첫 smoke도 비교 가능한 평가 증거이므로 실행 전에 최소 저장 구조를 준비한다.
이 단계는 완성된 평가 runner나 정식 DB 스키마를 만드는 작업이 아니다. 수동
실행이라도 동일한 형식으로 빠짐없이 기록하고 안전한 내부 위치에 보존하기 위한
최소 계약이다.

실행마다 먼저 `eval_run_id`를 만들고 다음 네 산출물을 기록한다.

```text
eval_run_id/
├─ run_manifest.json
├─ case_results.jsonl
├─ summary.json
└─ report.md
```

- `run_manifest`: git commit, dataset/rubric, Agent·model·prompt·runtime, 환경과 반복 수
- `case_results`: 사례별 판정, 내부 run/tool call과 Langfuse trace ID, 실패 단계·사유
- `summary`: 성공·실패, 안전 위반, 확보 가능한 latency·token·호출 수 집계
- `report`: 사람이 읽는 결론, 대표 실패, 한계와 원시 결과 위치

v0 결과 계약의 필수 필드는 다음과 같다.

- `eval_run_id`, `case_id`, `started_at`, `finished_at`
- `git_commit`, dataset ID/version, Agent/version, model/runtime
- `status`, assertion별 pass/fail과 실패 사유
- 내부 `agent_run_id`, `tool_call_id`, Langfuse trace ID
- 현재 수집 가능한 latency·token·호출 수
- 승인 결정, side effect와 cleanup 결과

수동 기록기는 JSON/JSONL을 append-only로 쓰고 기존 실행을 덮어쓰지 않는다.
원시 결과는 Git이 아닌 접근 통제된 내부 저장 위치에 둔다. Git에는 fixture·평가
기준과 비민감 요약만 남긴다. 현재 인프라에 object storage가 없다면 main 통합 후
팀이 합의한 내부 공유 위치를 먼저 정하고, 개인 로컬 디스크만을 유일한 원본으로
사용하지 않는다.

## 2. 공통 원칙

1. 평가 데이터는 제품 응답을 만드는 하드코딩이 아니라 변경 전후를 비교하는
   시험지다.
2. 최종 답변뿐 아니라 목표 달성, 도구·인자, trajectory, 권한, 승인, DB
   postcondition, 실패 보고를 함께 평가한다.
3. 안전한 여러 실행 경로를 허용하고 업무 규칙상 필요한 순서만 강제한다.
4. 안전·권한·승인·tenant 격리 위반은 평균 점수로 상쇄하지 않는다.
5. latency와 token 성능 예산은 실측 기준선보다 먼저 임의로 정하지 않는다.
6. Git과 내부 저장소를 정본으로 두고 Langfuse를 유일한 원본으로 삼지 않는다.
7. 사용자 원문, 문서 전체, 비밀값과 대용량 trace를 Git에 넣지 않는다.
8. 평가 실행은 덮어쓰지 않고 실행별 ID와 버전을 남긴다.
9. 실제 코드·도구·Agent ID는 실행 전에 조회하고 제품 코드에 평가 fixture를
   하드코딩하지 않는다.
10. 좋은 결과만 고르지 않고 실패, 표본 수와 평가하지 않은 범위를 함께 기록한다.

### 3.3 사례별 수동 확인 절차

각 사례는 다음 순서로 확인한다.

1. 새 평가 세션과 실행 식별자를 만든다.
2. 데이터셋의 입력을 수정하지 않고 보낸다.
3. 발생한 root/child run과 tool call ID를 기록한다.
4. HITL 사례는 승인 전 DB postcondition을 먼저 확인한다.
5. 데이터셋에 지정된 승인 또는 거절을 한 번만 수행한다.
6. 최종 응답, 도구·인자·횟수·상태와 DB postcondition을 확인한다.
7. Langfuse trace ID를 내부 실행 ID와 연결해 기록한다.
8. 쓰기 사례의 cleanup을 수행하고 잔여 데이터가 없는지 확인한다.

## 4. 2단계 — 복합 업무 workflow 5~8개 선정

### 4.1 선정 기준

- 실제 사용자가 Agent에게 맡길 가치가 있는 업무인가
- 여러 정보원·도구·단계가 필요한가
- 최종 결과와 DB 상태로 성공을 판정할 수 있는가
- 권한·승인·실패 복구 중 하나 이상을 포함하는가
- 기존 시나리오와 다른 실패 유형을 드러내는가
- sandbox에서 반복 실행하고 정리할 수 있는가

### 4.2 우선 검토할 후보

1. 프로젝트 현황, 지연 업무와 근거를 종합한 주간 보고
2. 문서·업무·담당자를 연결한 회의 자료 작성
3. 후속 업무 초안 제시 후 승인받아 정확히 한 번 등록
4. 여러 서브에이전트 조사 결과의 충돌 확인과 종합
5. 일부 도구 timeout이 포함된 부분 성공·재시도·보고
6. 문서에 없는 정보와 서로 충돌하는 RAG 근거 처리
7. 권한이 부족한 사용자의 쓰기 요청 차단
8. 문서 안의 악성 지시를 따르지 않는 prompt injection 방어

후보를 모두 채우는 것이 목표가 아니다. 실제 제품 도구와 fixture로 재현 가능하고
서로 다른 품질을 측정하는 5~8개만 `agent_workflow_v1`으로 확정한다.

## 5. 3단계 — 사례별 판정 기준 설계

각 workflow에는 다음을 기록한다.

### 5.1 정확성

- 사용자 목표와 기대 결과
- 필요한 사실과 근거
- 금지된 주장과 추측
- 필수·금지 도구
- 인자 predicate
- 허용 가능한 tool path
- 업무상 필요한 순서
- 최종 DB·외부 시스템 postcondition

### 5.2 안전성

- 승인 전 금지되는 side effect
- 역할별 금지 도구
- 허용 tenant·project·path
- 중복 쓰기 금지
- 성공한 쓰기 재시도 금지
- 평가 종료 cleanup

### 5.3 안정성

- 허용 재시도 수
- timeout과 복구 가능 여부
- 부분 성공 시 보고해야 할 성공·실패 항목
- 최종 `SUCCESS`, `PARTIAL_RESULT`, `REJECTED`, `NEEDS_CLARIFICATION` 조건
- 실패 단계와 오류 코드

하나의 완전 고정 trajectory를 정답으로 만들지 않는다. 결정적 규칙은 assertion,
계획·위임·근거 활용 같은 의미 품질은 rubric과 사람 교차검증으로 판정한다.

## 6. 4단계 — latency·token·비용 측정 설계

### 6.1 Latency

- `end_to_end_latency`: 사용자 요청부터 최종 응답까지
- `active_execution_latency`: 승인 대기 제외 실제 실행
- `approval_wait_latency`: 승인·거절 대기
- `time_to_first_token`: 첫 응답 표시까지
- root model, child model, tool별 latency
- warm 실행과 cold start 분리

### 6.2 Token과 비용

- root 입력·출력 token
- child 입력·출력 token
- 재시도·후처리 token
- 공급자가 제공하는 cache token
- 전체 모델 호출 수
- 성공 작업당 전체 token과 비용

root 마지막 호출만 집계하지 않는다. 같은 평가 실행에 속한 모든 root/child 모델
호출을 `eval_run_id`와 내부 trace 관계로 합산한다.

- 추가 질문 사례: 7,926
- 읽기·검색 도구 1회 사례: 약 15,600~21,600
- v1 복합 서브에이전트 사례: 26,334

출력보다 입력 비중이 매우 높다. 공통 scaffold, Agent 지시, 도구 schema, 메모리·스킬
지침, 대화 이력과 도구 호출 뒤 반복되는 모델 입력이 합쳐진 구조적 비용으로 본다.
다만 현재 기록은 run 전체 합계라 어느 부분이 얼마를 차지했는지는 아직 알 수 없다.
성능 예산을 정하기 전에 다음을 먼저 수행한다.

1. 독립 사례는 반드시 새 채팅에서 실행한다.
2. root/child와 모델 호출 회차별 입력·출력 token을 나눈다.
3. 가능하면 scaffold, Agent 지시, tool schema, memory/skill, 대화 이력의 크기를
   구분해 기록한다.
4. 같은 사례를 반복한 뒤 기준선과 예산을 정한다.
5. 측정 결과 없이 프롬프트나 도구를 임의로 제거하지 않는다.

### 6.3 효율과 안정성

- 도구별·전체 호출 수
- 중복 Tool 호출률
- 재시도 수와 복구 성공률
- 실패 단계 분포
- 불필요한 서브에이전트 위임
- 성공한 side effect의 재실행 여부

## 7. 5단계 — 수동 반복 실행과 최초 기준선

runner를 만들기 전에 사람이 workflow를 실행하여 설계가 현실적인지 확인한다.

- 일반적인 읽기 workflow: 최초 1회, 변동이 크면 3회
- HITL·서브에이전트·병렬·RAG 경계·실패 복구: 최소 3회
- warm 실행을 공식 latency 기준으로 사용
- cold start는 별도 관측값으로 기록
- 사용자 승인 대기 시간은 active latency에서 제외

수동 실행에서 확인할 내용:

- [ ] fixture가 반복 가능한가
- [ ] 성공·실패 판정이 모호하지 않은가
- [ ] 정상적인 대체 trajectory를 잘못 실패 처리하지 않는가
- [ ] 필요한 trace·DB 필드가 실제로 존재하는가
- [ ] cleanup이 성공하고 잔여 side effect가 없는가
- [ ] 실행 간 결과 변동을 설명할 수 있는가

최초 기준선에는 성공률, 절대 성공·실패 수, 안전 위반, p50/p95 active latency,
token·비용, 호출 수와 실패 유형을 포함한다.

## 8. 6단계 — 성능 예산과 배포 기준

성능 예산은 7단계 실측 후 확정한다.

### 절대 실패 조건

- 승인 전 side effect 발생
- 권한 우회 또는 tenant 간 데이터 노출
- 거절한 작업 실행
- 성공한 쓰기 중복 실행
- 민감정보 마스킹 실패

### 기준선 기반 조건

- workflow 성공률 허용 하락폭
- active latency p50/p95 허용 범위
- 성공 작업당 token·비용 허용 범위
- 모델·도구 호출 수 상한
- 도구별 재시도 상한
- RAG·semantic 점수 허용 하락폭

단 한 번의 LLM Judge 점수로 배포를 막지 않는다. 반복 결과, 결정적 규칙,
사례별 실패와 사람 검토를 함께 사용한다.

## 9. 7단계 — 정식 평가 DB·보관 구조 확정

§1.1의 v0 결과 파일로 smoke와 workflow를 보존한 뒤, 실제 조회·집계에 반복해서
필요한 필드를 기준으로 정식 저장 구조를 확정한다. 사용하지 않을 DB 컬럼과 파일
경로를 제품 코드에 미리 하드코딩하지 않는다.

```text
Git
├─ dataset·rubric·성능 예산
├─ 비민감 버전별 요약 보고서
└─ 실패·개선 이력

프로젝트 DB
├─ eval run·사례별 판정
├─ latency·token·비용·호출 수
├─ Agent·model·prompt·runtime 버전
└─ 내부 run/trace ID 매핑

내부 object storage
├─ 대용량 JSONL·상세 산출물
├─ 마스킹된 원시 평가 결과
└─ 상세 trace·fixture
```

각 실행에는 덮어쓰지 않는 `eval_run_id`를 부여한다. 최소 산출물은 다음과 같다.

- `run_manifest`: 실행 조건과 모든 버전
- `case_results`: 사례별 판정·점수·실패 단계와 사유
- `summary`: 성공률·안전 위반·p50/p95·token·비용·버전 변화
- `report`: 사람이 읽는 결론·대표 실패·한계·증거 링크

정식 구조가 준비되면 v0 JSON/JSONL 결과를 `eval_run_id` 기준으로 가져오고, 원본
artifact와 import 결과의 건수·ID·요약값이 일치하는지 검증한다. 따라서 첫 smoke와
수동 기준선도 이후 대시보드와 버전 비교에서 빠지지 않는다.

## 10. 8단계 — 평가 runner 구현

runner의 책임은 다음으로 제한한다.

```text
dataset 읽기
→ fixture 검증과 평가 세션 생성
→ Agent 실행
→ 필요한 HITL 결정 적용
→ trace·DB·외부 postcondition 수집
→ deterministic·semantic 판정
→ 내부 결과 저장과 비민감 보고서 생성
→ cleanup
```

구현 순서는 다음과 같다.

1. read-only smoke
2. read-only workflow
3. isolated role·권한
4. HITL 승인·거절
5. 서브에이전트
6. 실패 주입·부분 성공

쓰기 사례는 sandbox 외 실행을 기본 거부하며 자동 승인하지 않는다. 실패한 평가가
제품 데이터에 영향을 주지 않도록 idempotency와 cleanup을 검증한다.

## 11. 9단계 — Langfuse Experiment·Score 연결

내부 저장이 성공한 뒤 같은 평가 결과를 Langfuse에 연결한다.

```text
내부 eval_run_id
↔ Langfuse dataset run
↔ root/child/tool trace
↔ 사례별 score
```

Langfuse는 trace 탐색과 비교 UI이며 정본이 아니다. Langfuse 전송이나 조회가
실패해도 내부 평가 결과는 보존되어야 한다.

## 12. 10단계 — Agent 성능 개선 반복

```text
실패 발견
→ 재현
→ 원인 분류
→ 최소 수정
→ smoke
→ workflow
→ holdout
→ latency·token·비용 비교
→ 개선 보고서 저장
```

원인은 도구 선택, 인자, RAG 근거성, 위임, HITL, 실패 복구, 프롬프트,
컨텍스트, 모델, latency와 token으로 분류한다. 정확성이 좋아졌더라도 안전성,
latency 또는 비용이 크게 악화되면 전체 개선으로 판정하지 않는다.

## 13. 11단계 — holdout과 배포 gate

개발 중 결과를 보며 튜닝하지 않는 비공개 holdout을 별도로 유지한다.

```text
smoke                         10개
smoke 포함 개발·기준선       20개
비공개 holdout               10개
첫 전체 평가                 30개
```

- PR-fast: schema·권한·HITL·중복 실행 등 deterministic 검사
- Nightly-semantic: 핵심 개발 사례와 반복 실행
- Release-candidate: 전체 개발 dataset과 비용·지연
- Final-holdout: 비공개 holdout 포함 결과와 사람 검토

holdout 결과를 보고 수정한 사례는 다음 주기부터 개발 dataset으로 옮기고 새로운
holdout으로 교체한다.

## 14. 12단계 — 결과를 사람에게 보여주는 방식

### 공통 한 페이지 보고서

- 평가 commit·dataset·rubric·Agent·model·runtime 버전
- 사례 수와 반복 횟수
- 업무 성공률과 절대 성공·실패 건수
- 승인·권한·중복 쓰기·tenant 격리 위반 건수
- active latency p50/p95와 성공 작업당 token·비용
- 이전 버전 대비 향상·악화
- 대표 실패와 수정 계획
- 평가하지 않은 범위와 sandbox 한계

### 대상별 표시

- 외부 발표·의사결정자: 한 페이지 scorecard와 버전 전후 비교
- 개발자: 사례별 실패 단계, root/child/tool trace와 DB postcondition
- 운영자: 버전·기간별 성공률, p95, 비용, timeout과 실패 유형 추세

“안정적”이라는 주장은 표본과 실패를 숨기지 않고 다음처럼 표현한다.

```text
복합 workflow N개를 총 M회 실행
성공 X/M, 안전 위반 0건
p50/p95와 성공당 token은 이전 버전 대비 Y만큼 변화
남은 실패는 Z 유형이며 현재 한계로 기록
```

## 15. 13단계 — 프로젝트 공통 OpenTelemetry

평가 runner와 기준선으로 실제 필요한 필드를 확인한 다음 도입한다.

```text
Agent·Django·tool·DB
→ 프로젝트 공통 OpenTelemetry
→ OTel Collector
├─ Langfuse
└─ 내부 저장소·관측 플랫폼
```

OTel GenAI semantic convention을 우선하고 프로젝트 고유 속성만 `skn.*`로
정의한다. 평가·session·내부 run ID는 correlation attribute로 연결하되 trace의
parent-child 관계를 별도로 중복 구현하지 않는다.

## 16. 14단계 — 사내 플랫폼과 Langfuse Cloud 제거

실제로 사용한 기능부터 내부화한다.

```text
버전별 평가 요약
→ 실행 목록·상세와 실패 검색
→ latency·token·비용 추세
→ 평가 비교와 운영 알림
→ 권한·보존·삭제·재전송
```

정해진 기간 동안 Langfuse와 내부 플랫폼에 병행 전송하여 trace 누락,
root/child/tool 연결, token·비용 오차, HITL, 평가 점수, 마스킹과 조회 성능을
비교한다. 내부 플랫폼의 정합성과 운영성이 검증된 뒤에만 다음을 수행한다.

- [ ] Langfuse Cloud 전송 중단
- [ ] API key와 배포 secret 폐기
- [ ] 외부 보존 데이터 삭제 정책 확인·실행
- [ ] 내부 대시보드와 장애 대응 절차로 운영 전환

재현성을 위해 유지한다. 각 단계의 완료 결과와 실제 수치는 기존 실행을 덮어쓰지
않고 별도 실행 결과와 보고서에 남긴다.
