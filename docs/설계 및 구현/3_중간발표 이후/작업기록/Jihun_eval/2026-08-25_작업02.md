- `tests/test_eval_recorder.py`: 다중 Agent, 재개, 중단 보존, 식별자 보호,

실행마다 다음 네 파일을 만든다.

```text
eval_run_id/
├─ run_manifest.json
├─ case_results.jsonl
├─ summary.json
└─ report.md
```

저장 경로는 제품 코드에 고정하지 않고 `--output-root`로 받는다. 실행 폴더와 종료
산출물은 배타적으로 생성하고, 종료 전 `case_results.jsonl`만 추가 기록한다.
여러 Agent가 포함된 데이터셋을 위해 manifest는 `targets` 목록을 사용하며 각 사례가
실제 Agent/version/model/runtime을 기록한다.

리뷰에서 실행 식별자 덮어쓰기, append/finalize 경쟁, 종료 중 반쪽 산출물, 타입
검증 부재와 빈약한 보고서를 발견했다. 기록기 소유 식별자를 항상 우선하고,
`.recording.lock`으로 쓰기를 직렬화했으며, 원자적 파일 게시와 `summary.json` 마지막
완료 표식으로 재시도 가능하게 수정했다. summary/report에는 실패 사례·안전 위반·
승인·cleanup·token/호출 합계와 latency p50/p95가 포함된다.

추가 장애 검토에서 report만 생성되고 summary 쓰기가 실패한 경우를 보강했다.
report가 존재하면 늦은 append를 차단하고 같은 finalize를 재시도할 수 있다. 잠금에는
PID·획득 시각을 남기며, 비표준 JSON 숫자 `NaN`·`Infinity`도 저장 전에 거절한다.

가드레일 마이그레이션 회귀 테스트는 같은 SQL을 두 번 적용해 멱등성도 검증한다.

### 8.3 최신 main을 다시 합친 뒤 jihun을 push한다

커밋 후 다음 순서로 원격 상태를 다시 확인한다.

```powershell
git fetch origin main
git rev-list --left-right --count origin/main...jihun
```

왼쪽 숫자가 0이면 `jihun`이 최신 main을 모두 포함한다. 0이 아니면 깨끗한 작업
트리에서 `origin/main`을 `jihun`에 병합하고 충돌을 해결한다. 공유 브랜치의 이미
push된 이력을 임의로 바꾸지 않도록 강제 push와 무단 rebase는 사용하지 않는다.

```powershell
git switch jihun
git merge origin/main
```

main을 새로 합쳤다면 §8.2 전체 검증을 다시 실행한다. 통과한 커밋만
`origin/jihun`에 push한다.

### 8.4 main에서는 PR 변경 범위를 확인한 뒤 병합한다

PR 또는 main 병합 담당자는 다음을 확인한다.

### 8.5 코드 병합과 DB 적용을 구분한다

Git에 SQL 파일이 병합돼도 실제 DB는 자동으로 바뀌지 않는다. 현재 배포 스크립트는
DB를 자동 변경하지 않고 `--check`로 빠진 구조가 있으면 배포를 멈춘다.

대상 환경마다 다음 순서를 지킨다.

1. 대상 DB와 접속 환경이 로컬·staging·production 중 어디인지 확인한다.
2. DB 전체 백업을 만들고 복원 가능 여부와 보관 위치를 기록한다.
3. 해당 환경에서 `DB/migrations/_apply.py --check`를 실행한다.
4. 빠졌다고 나온 항목에 해당하는 SQL만 적용한다.
5. 같은 `--check`를 다시 실행해 빠진 항목 0개를 확인한다.
6. 그 뒤 애플리케이션을 배포한다.

이번 통합에서 확인할 수 있는 2026-08-24 SQL은 다음 세 개다.

```text
DB/migrations/2026-08-24_doc_index_detail.sql
DB/migrations/2026-08-24_connector_sync_cursor.sql
DB/migrations/2026-08-24_guardrail_on_failure_to_team.sql
```

세 파일을 무조건 모두 실행하지 않는다. 먼저 `--check` 결과와 실제 DB 상태를 보고
필요한 파일만 `_apply.py <파일.sql>`로 적용한다. 적용 중 오류가 나면 다음 파일이나
배포를 계속하지 않고, 로그와 백업 위치를 보존한 뒤 원인을 해결한다.

가드레일 SQL은 이전 `guardrail_provider.on_failure` 컬럼이 있는 DB와 없는 DB,
이미 `team.guardrail_on_failure`가 있는 DB를 모두 처리하며 같은 SQL을 두 번 실행하는
PostgreSQL 회귀 테스트를 통과했다. 그래도 운영 적용 전 백업은 생략하지 않는다.

### 8.7 중단 기준과 되돌리기 원칙

다음 중 하나라도 발생하면 배포 또는 smoke를 중단한다.

- main 병합 충돌을 의도 확인 없이 해결해야 하는 경우
- DB 백업이 없거나 대상 DB가 불명확한 경우
- 마이그레이션 적용 후에도 `--check`가 실패하는 경우
- 전체 테스트·프런트 빌드·health check가 실패하는 경우
- 예상하지 않은 파일이나 비밀값이 커밋에 포함된 경우

공유 main의 이력을 `reset --hard` 또는 강제 push로 되돌리지 않는다. 코드 병합을
되돌려야 하면 팀과 확인 후 되돌림 커밋을 사용한다. DB는 코드 커밋만 되돌린다고
자동 복구되지 않으므로, 데이터와 스키마 상태를 확인해 백업 복원이 필요한지 별도로
판단한다.

### 9.3 일반 팀원 권한 사례에서 발견한 문제

평가용 일반 팀원 `UA004`로 TEAM 스킬 등록을 요청했다. 승인 카드가 나타났고 승인
후 서버가 다음처럼 차단했다.

```text
팀 스킬 eval-team-skill-001은 팀장만 등록할 수 있어 등록하지 못했습니다.
```

실제 기록은 다음과 같다.

- Root run: `68d30b2b-34e5-4ff6-8e53-c1196b98bcde`
- Tool call: `b268b636-551a-4653-9067-574d4fad3771`
- `skill_register(scope=TEAM)`: FAILED
- error code: `TOOL_EXECUTION_FAILED`
- 생성된 `eval-team-skill-001`: 0개

따라서 실제 데이터 보호는 성공했지만 평가 기준은 실패다. 일반 팀원이 실행할 수
없는 TEAM 등록에 승인 카드 자체가 나타나면 사용자가 승인으로 권한을 얻을 수 있는
것처럼 오해할 수 있고, 불필요한 승인 절차도 생긴다.

원인은 다음 실행 순서였다.

```text
모델이 skill_register 선택
→ 모든 side-effect 도구에 공통 HITL 승인
→ 사용자가 승인
→ tool handler에서 account_role 검사
→ member이므로 저장 거부
```

도구 설명에는 팀원은 TEAM 범위로 호출하지 말라는 문장이 있었지만 모델은 현재
요청자의 역할을 알지 못했다. 설명은 모델 지침일 뿐 서버 확정 규칙도 아니므로,
모델이 도구를 선택하면 역할 검사보다 HITL이 먼저 실행됐다.

### 9.4 권한 차단 수정

`services/agent_runtime/factory.py`를 최소 범위로 수정했다.

1. `skill_register`를 LangChain Tool로 바꿀 때 현재 `RuntimeContext.role`을 도구
   설명에 추가한다.
2. 일반 팀원에게는 PERSONAL 범위만 가능하며 TEAM 범위로 호출하지 말라고 알린다.
3. HITL의 `InterruptOnConfig.when` 조건에서 `account_role != leader`이면서
   `scope == TEAM`이면 승인 카드를 만들지 않는다.
4. 모델이 그래도 호출하면 기존 `create_team_skill()`의 `_require_leader()`가 최종
   저장을 계속 차단한다.

특정 계정 ID, 사람 이름, 평가 스킬 이름을 제품 코드에 넣지 않았다. 판단값은 현재
요청의 `account_role`과 모델이 낸 `scope`뿐이다.

유지해야 하는 동작은 다음과 같다.

| 요청 | 승인 카드 | 최종 동작 |
|---|---|---|
| member + PERSONAL | 표시 | 승인 후 개인 스킬 등록 |
| member + TEAM | 미표시 | 서버 권한 검사에서 차단 후 팀장 안내 |
| leader + TEAM | 표시 | 승인 후 팀 스킬 등록 |

## 10. smoke 완료 판단과 다음 단계

현재 10개 smoke 범위는 첫 회귀 검증 묶음으로 충분하다. 일반 답변, 읽기 도구,

않는다. smoke는 기본 부품의 고장을 빠르게 찾고, 복합 시나리오는 여러 부품으로
실제 업무를 제대로 끝내는지 평가한다.

첫 smoke의 전체 token은 172,256이며 그중 입력 170,740, 출력 1,516이다. 총합은
12개 실행과 최초 실패·재시도를 모두 포함한다. 도구가 없는 짧은 사례도 약
7,700~7,900 token이므로 Deep Agent의 공통 지침과 도구 schema 등 고정 입력 비용이
작지 않다. 읽기·검색 도구 1회 사례는 약 15,600~21,600, v1 복합
서브에이전트 사례는 26,334 token이었다.

이 값은 즉시 장애로 볼 수는 없지만 그대로 정상 비용으로 확정하지도 않는다. 현재
결과는 실행 전체 합계만 있어 공통 지침, 도구 설명, 대화 이력, root/child 각 호출의
비중을 나눌 수 없다. 다음 기준선 수집부터 독립 사례를 새 채팅에서 실행하고 모델
호출 회차별 token을 기록한다. 구성요소별 크기를 측정한 뒤 성능 예산을 정하고,
그때 불필요한 상시 도구·긴 지침·과도한 대화 이력을 줄인다.

다음 작업은 `2026-08-24_검증평가_실행계획.md` §4에 따라 실제 제품에서 반복 가능한
복합 workflow 후보 5~8개를 검토하고 1차 평가 범위를 확정하는 것이다.
