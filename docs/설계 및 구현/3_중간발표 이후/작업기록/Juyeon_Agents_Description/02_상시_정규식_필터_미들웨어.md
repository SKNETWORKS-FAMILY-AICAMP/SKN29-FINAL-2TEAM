| | 이전 | 지금(2026-08-26) |
|---|---|---|
| 가리는 코드 | `apps/chat/api_views.py`가 `mask_sensitive()`를 직접 호출 | `SensitiveInputMaskMiddleware`가 그래프 안에서 처리 |
| 호출 지점 | 두 곳(최초 입력, `_history()` 재전송) | 한 곳(`before_model`, 매 모델 호출 직전) |
| 그래프 진입 시점 | 이미 가려진 문자열이 들어옴 | 원문 그대로 들어오고, 모델을 부르기 직전에 가려짐 |

가리는 **대상 패턴 자체는 안 바꿨다** — `sensitive_text.py`의 credential/pii/authority 세 카테고리, `mask_sensitive()` 함수 그대로 재사용한다. 바뀐 건 "어디서, 언제" 가리느냐다.

## 왜 미들웨어로 옮겼나

호출 지점이 둘로 나뉘어 있으면 그중 하나를 빠뜨릴 위험이 항상 있다 — 실제로 이전 구조는 "최초 입력"과 "과거 이력 재전송"을 매번 각각 가려야 했고, 셋째 지점(스킬 명시 호출의 `skill_request`)까지 더해 세 곳을 따로 관리했다. `before_model`은 **그 시점의 `state["messages"]` 전체**를 보므로, 메시지가 이번 턴에 새로 들어왔든 과거 이력이 통째로 재전송됐든 같은 코드가 같은 자리에서 처리한다 — 호출 지점을 늘릴 필요가 구조적으로 없어졌다.

## 동작 원리

```python
def before_model(self, state, runtime):
    messages = state["messages"]
    new_messages = list(messages)
    any_modified = False
    for i, message in enumerate(messages):
        if not isinstance(message, HumanMessage) or not message.content:
            continue
        masked = mask_sensitive(str(message.content))
        if masked == str(message.content):
            continue
        new_messages[i] = HumanMessage(content=masked, id=message.id, name=message.name)
        any_modified = True
    return {"messages": new_messages} if any_modified else None
```

핵심 결정 세 가지:

1. **`HumanMessage`만 본다.** 모델 답변·도구 결과는 이 미들웨어의 대상이 아니다 — 그건 PIIMiddleware(§2-②)가 다른 카테고리(credit_card·ip·mac_address)로 이미 맡고 있다. 겹쳐서 처리하지 않는다.
2. **가장 최근 메시지 하나가 아니라 전부 다시 본다.** langchain 표준 `PIIMiddleware`는 최근 `HumanMessage` 하나만 검사한다 — 그 미들웨어가 지키는 값은 매 턴 새로 도착하는 것뿐이라 그걸로 충분하다. 이 미들웨어는 그렇게 하면 안 된다 — 체크포인터가 없어 과거 대화가 이번 호출에 한꺼번에 실리는 경로(`stream_adapter.py`의 `thread_id` 없는 분기)가 있고, 거기서 최근 것만 가리면 예전 `_history()`가 막던 재전송 누출이 다시 열린다.
3. **같은 `id`로 교체한다.** LangGraph의 `add_messages` reducer는 같은 `id`를 가진 메시지를 새로 추가하지 않고 그 자리에서 갱신한다 — `id`가 바뀌면 원문과 마스킹본이 둘 다 상태에 남는 사고가 난다. `PIIMiddleware`와 같은 패턴이다.

`mask_sensitive()` 자체가 멱등이라(`MASK_PLACEHOLDER`는 세 카테고리 어디에도 안 걸림) 매 모델 호출마다 전체를 다시 훑어도 이미 가려진 부분은 그대로 통과한다 — 손해는 정규식 재실행 비용뿐이고, 메시지 개수가 `HISTORY_LIMIT`(20)로 상한이 있어 무시할 만하다.

## 예외 — `suggest_title()`

대화 제목을 짓는 `suggest_title()`(`services/harness/naming.py`)은 deep agent 그래프를 거치지 않고 OpenAI를 **직접** 호출한다. 이 미들웨어의 보호 범위는 그래프 안쪽뿐이라 이 경로는 구조적으로 못 덮는다 — 그래서 `api_views.py`가 지금도 그 자리(`question=mask_sensitive(model_input)`)에서만 직접 `mask_sensitive()`를 부른다. "완전히 미들웨어로 옮겼다"는 말은 **그래프로 들어가는 값**에 한정된다.

## 배선 위치

`MiddlewareFactory.build()`의 공통 목록(Root/Child)에 PIIMiddleware 바로 뒤에 붙는다. GP(범용 서브에이전트)에는 아직 안 붙는다 — GP가 사용자 원문을 직접 보는 경로가 없어서다(PIIMiddleware와 같은 판단, §2-②).

## 한계

- **멀티파트 메시지(이미지 등)를 다루지 못한다.** `str(message.content)`로 강제 변환한 뒤 그 결과를 새 `content`로 그대로 넣는다 — content가 리스트(구조화된 블록)였다면 문자열 하나로 뭉개진다. 이 프로젝트는 아직 채팅에 이미지·멀티파트 입력을 안 쓰므로 지금은 문제가 안 되지만, 나중에 멀티모달 입력을 받게 되면 이 미들웨어부터 다시 봐야 한다. langchain 표준 `PIIMiddleware`도 같은 한계를 갖고 있다(참고 구현 그대로 따른 것이지 이 프로젝트가 새로 만든 결함이 아니다).
- **형태 판단의 한계는 그대로 물려받는다.** `sensitive_text.py` 모듈 docstring의 한계(여러 조각으로 쪼개면 못 잡음, 전화번호 오탐 가능, 권한 키워드는 문맥 무시)는 패턴 자체를 재사용하므로 이 미들웨어에도 똑같이 적용된다.
