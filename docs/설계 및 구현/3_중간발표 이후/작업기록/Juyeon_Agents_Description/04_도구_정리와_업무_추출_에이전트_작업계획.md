# Root 기본 도구 조사와 최종 분류

- 작성일: 2026-08-27
- 목적: 실제 서비스와 오픈소스의 분류·명명 방식을 조사한 뒤 Root에 제공할 Tool의 이름과 카테고리를 확정한다.

## 0. 결론

1. 카테고리는 Tool이 아니라 Tool을 찾기 위한 화면 그룹이다.
2. 실제 서비스처럼 카테고리는 `검색`, `문서`, `업무`, `팀`, `데이터`, `계산`처럼 짧은 명사로 쓴다.
3. `Jira`는 카테고리가 아니라 `업무` 카테고리 안의 서비스 배지로 표시한다.
4. `tool_ref`는 코드와 DB 호환성을 위해 바꾸지 않고, 사용자에게 보이는 한국어 `name`만 바꾼다.
5. 현재 구현된 선택 Tool 17개와 신규 로컬 Tool 10개를 합쳐 기본 Tool 27개를 제공한다.
6. 스킬 생성용 Tool 2개는 Builder 카테고리에 보이지 않고 항상 켜지는 시스템 Tool로 유지한다.
7. 입력·생성·설명·편집을 포함한 이미지 관련 Tool은 이번 범위에서 제외한다.

## 1. 실제 서비스와 오픈소스 조사

인터넷의 모든 서비스와 Tool은 계속 추가되므로 전부를 유한하게 조사할 수는 없다. 대신 사용자가 많은 자동화 서비스, 업무용 마켓, Agent Tool 카탈로그의 공식 문서를 대표 표본으로 조사하고, 여러 곳에서 반복되는 카테고리와 행동 이름을 기준으로 삼았다.

### 1.1 카테고리를 어떻게 나누는가

| --- | --- | --- | --- |

| [Formatter by Zapier](https://zapier.com/apps/formatter/integrations) | Date/Time, Text, Numbers, Utilities | Transform이라는 행동 아래 날짜·텍스트·숫자를 구분 | 계산·변환은 별도 유틸리티 영역으로 분리 |
| [Make](https://www.make.com/en/integrations/category/file-document-management) | File & Document Management, Productivity, HR Management 등 | Search, Get, List, Create, Update 같은 Module 이름 사용 | 대상과 행동을 Tool 이름에서 바로 알 수 있게 함 |
| [n8n](https://n8n.io/integrations/) | Analytics, Communication, Data & Storage, Productivity, Utility | Regular, Trigger, Core Node를 구분 | `데이터`, `업무`, `계산`처럼 짧은 명사형 카테고리가 적합 |

| [Google Workspace Marketplace](https://workspace.google.com/marketplace) | Business tools, Productivity, Communication, Utilities | Works with Docs·Sheets·Drive 같은 제품 필터 제공 | 카테고리와 서비스 필터를 분리 |

| [CrewAI Tools](https://github.com/crewAIInc/crewAI-tools) | File Management, Web Scraping, Database 등 | FileWriterTool, PDFSearchTool 등 대상+행동 이름 사용 | 개발용 이름은 명확하지만 사용자 화면에는 자연스러운 한국어로 번역 |
| [MCP Reference Servers](https://github.com/modelcontextprotocol/servers) | Fetch, Filesystem, Git, Memory, Time | 서버 기능을 짧은 한 단어로 표현 | 카테고리와 기능 이름을 짧게 유지 |

### 1.2 긴 카테고리 이름을 쓰는가

Make의 `File & Document Management`, n8n의 `Data & Storage`처럼 두 대상을 묶은 이름도 존재한다. 하지만 대부분의 상위 카테고리는 `Productivity`, `Analytics`, `Utility`, `Communication`처럼 한두 단어다.

우리 화면의 `파일 만들기·정리`, `프로젝트·업무`는 설명에 가까워 카테고리 탭으로는 길다. 다음처럼 바꾸는 편이 자연스럽다.

| 이전 이름 | 최종 이름 | 이유 |
| --- | --- | --- |
| 자료 찾기 | `검색` | 문서·웹 검색 목적을 가장 짧게 표현 |
| 파일 만들기·정리 | `문서` | 파일 생성·변환·PDF·압축을 포괄하며 사용자에게 익숙함 |
| 프로젝트·업무 | `업무` | 프로젝트는 업무를 묶는 상위 정보이므로 같은 영역에서 제공 가능 |
| 팀·일정 | `팀` | 사람·업무량·부재를 포함. 날짜 계산은 `계산`으로 분리 |
| 데이터·비교 | `데이터` | 표 처리·품질·파일 비교를 포함 |
| 새 카테고리 | `계산` | 날짜·시간·수식·단위를 결정적으로 계산 |

### 1.3 Tool 이름에 공통으로 쓰는 행동

Make와 Microsoft는 `Search`, `Get`, `List`, `Create`, `Update`, Zapier는 `Find`, `Transform`, Jira는 `Create issue` 같은 이름을 쓴다. 한국어에서는 다음처럼 번역하는 것이 자연스럽다.

| 영문 행동 | 자연스러운 한국어 | 사용 기준 |
| --- | --- | --- |
| Search / Find / Query | `검색` | 조건이나 질문으로 관련 결과를 찾음 |
| Get | `조회` | 특정 대상 하나 또는 현재 상태를 가져옴 |
| List | `목록` | 여러 항목을 나열함 |
| Create file | `만들기` | Word·Excel 같은 새 결과 파일 생성 |
| Create record / issue | `등록` | 업무·Jira 이슈 같은 업무 기록 생성 |
| Update | `수정` | 기존 상태나 값을 바꿈 |
| Sync | `동기화` | 원본 저장소의 최신 변경을 반영 |
| Extract | `추출` | 문서 안에서 본문·표·업무를 꺼냄 |
| Transform | `가공` | 정렬·필터·결합·형식 변환 |
| Validate / Data quality | `품질 검사` | 누락·중복·타입·스키마 오류 확인 |
| Compare / Diff | `비교` | 두 파일의 변경점 확인 |

| `document_search` / 문서 검색 | 현재 | 팀·프로젝트 문서에서 질문과 관련된 근거 문장 검색 | PostgreSQL 청크, `VectorSearchRepository`, RunPod 임베딩 |

### Jira 표시 방식

`Jira`만 카테고리로 두는 것보다 다음처럼 분리한다.

```json
{
  "category": "업무",
  "provider": "Jira",
  "capability": "조회",
  "requires_connection": true
}
```

UI에서는 `업무` 안에 Jira Tool을 놓고 `Jira` 배지를 표시한다. 서비스만 보고 싶으면 별도 `Jira` 필터를 사용한다.

## 7. 팀

| 최종 Tool | 상태 | 용도 | 구현 |
| --- | --- | --- | --- |
| `people_list` / 팀원 조회 | 현재 | 팀원의 이름·직책·조직·기술 조회 | `TeamRepository`, `list_person_skills()` |
| `workload_report` / 업무량 조회 | 현재 | 팀원별 주간 업무 시간과 남은 여유 계산 | HR·업무 PostgreSQL 데이터, `services/workload/calculator.py` |
| `absence_list` / 부재 일정 조회 | 현재 | 승인된 휴가·교육 등의 기간 조회 | `backend.services.hr.list_absences()` |

### 팀 카테고리에 더 넣을 Tool이 있는가

현재 데이터로 만들 수 있는 원자적 조회 Tool은 위 세 개면 충분하다.

- `팀원 추천`: 팀원·업무량·부재를 함께 판단해야 하므로 Tool이 아니라 전용 에이전트 역할이다.
- `팀 가용성 브리핑`: `people_list`, `workload_report`, `absence_list`를 종합하는 에이전트 응답이다.
- `스킬 매트릭스`: `people_list`가 이미 사람별 기술을 반환하므로 별도 Tool을 만들면 중복된다.
- `업무 배정`: 조회가 아니라 사람에게 영향을 주는 결정이며 현재 자동 배정 정책도 없으므로 추가하지 않는다.

즉 Tool을 더 늘리기보다 이후 `팀 현황` 또는 `업무 매칭` 기본 에이전트가 세 Tool을 묶어 쓰는 것이 맞다.

## 8. 데이터

### `table_transform` — 표 가공·집계

- **용도:** CSV·JSON·XLSX·Parquet의 일부 행 보기, 필터, 정렬, 그룹 집계, 파일 결합, 기본 통계, 형식 변환
- **구현:** [DuckDB](https://github.com/duckdb/duckdb), XLSX 입력은 openpyxl 또는 DuckDB Excel extension 검토
- **입력:** SQL 문자열이 아니라 `columns`, `filters`, `sort`, `group_by`, `metrics`, `limit` 구조
- **허용 동작:** `preview`, `filter`, `sort`, `aggregate`, `join`, `statistics`, `convert`

### `data_quality_check` — 데이터 품질 검사

- **용도:** 빈 값, 중복 행·중복 키, 잘못된 타입, 허용 범위, 날짜·이메일 형식, 열 구성과 JSON Schema 오류 확인
- **구현:** [Frictionless](https://github.com/frictionlessdata/frictionless-py), [jsonschema](https://github.com/python-jsonschema/jsonschema), DuckDB, openpyxl
- **허용 동작:** `infer_schema`, `validate_schema`, `check_missing`, `check_duplicates`, `check_types`, `check_constraints`

### 두 Tool을 나누는 이유

`데이터 분석`이라는 이름은 품질 검사까지 포함하는 것처럼 들려 모호하다. 따라서 행동을 기준으로 구분한다.

| 사용자 요청 | 호출 Tool |
| --- | --- |
| “부서별 평균 업무 시간을 계산해줘” | `table_transform` |
| “마감일 기준으로 정렬해줘” | `table_transform` |
| “두 엑셀을 합쳐줘” | `table_transform` |
| “빈 값이나 중복된 행이 있는지 봐줘” | `data_quality_check` |
| “이 CSV가 정해진 열과 타입을 지키는지 검사해줘” | `data_quality_check` |

### `file_compare` — 파일 비교

- **용도:** 두 파일의 내용 차이를 형식에 맞게 비교한다.
- **구현:** DOCX·PDF는 형식별 parser와 Python 표준 `difflib`, XLSX는 openpyxl의 시트·셀 비교

| 형식 | 비교 범위 | 결과 위치 |
| --- | --- | --- |
| DOCX | 문단·표 셀의 추가·삭제·변경 | 문단 번호·표/셀 |
| PDF | 추출 가능한 본문·표의 추가·삭제·변경 | 페이지 번호 |
| XLSX | 시트, 셀 값, 수식, 행·열의 추가·삭제·변경 | 시트명·셀 주소 |

따라서 DOCX, PDF, XLSX를 모두 지원할 수 있다. 다만 PDF의 픽셀 단위 디자인 변경, DOCX의 모든 글꼴·여백 변경까지 비교하는 것은 아니다. PDF에 추출 가능한 글자가 없으면 내용 비교가 불가능하다고 명확히 반환한다.

## 11. 화면과 데이터 구조

Tool마다 한 개의 `category` 문자열만 두면 Jira 같은 서비스, 조회·쓰기 행동, 연결 필요 여부를 표현할 수 없다. 화면 응답을 다음처럼 확장한다.

```json
{
  "tool_ref": "jira_create_issues",
  "name": "Jira 이슈 등록",
  "category": "업무",
  "provider": "Jira",
  "capability": "등록",
  "requires_connection": true,
  "side_effect": true
}
```

| 필드 | 화면에서 하는 역할 |
| --- | --- |
| `category` | 검색·문서·업무·팀·데이터·계산 탭 |
| `provider` | 플랫폼, Jira, 웹, 연결 문서, 내 파일 배지·필터 |
| `capability` | 검색, 조회, 추출, 만들기, 수정, 등록, 계산, 검사 배지 |
| `requires_connection` | 연결이 없을 때 비활성 상태와 안내 표시 |
| `side_effect` | 실행 전 승인 필요 표시 |

## 12. 파일 Tool 공통 계약

```json
{
  "input_file_ids": ["file_123"],
  "operation": "compare",
  "options": {}
}
```

- 서버 로컬 경로 대신 권한이 확인된 `file_id`만 받는다.
- 원본을 덮어쓰거나 삭제하지 않고 새 결과 파일을 만든다.
- 결과 파일은 기존 저장소와 PostgreSQL 문서 메타데이터에 등록한다.
- 실행 중에만 격리된 임시 디렉터리를 사용하고 종료 후 지운다.
- 파일 수, 총용량, 페이지·행 수, 실행 시간 상한을 둔다.
- CLI는 Shell 없이 고정 argv와 허용 옵션만 사용한다.
- LLM에는 전체 바이너리나 대용량 원문 대신 요약·일부 행·페이지 근거만 반환한다.

## 14. 최종 결정

1. 조사 내용은 삭제하지 않고 설계 근거로 문서 맨 앞에 둔다.
2. 카테고리는 짧은 명사 6개로 통일한다.
3. 사용자 표시 이름만 자연스러운 한국어로 바꾸고 `tool_ref`는 유지한다.
4. 기본 Tool은 현재 17개와 신규 로컬 10개를 합친 27개다.
5. 데이터 기능은 `표 가공·집계`와 `데이터 품질 검사`로 명확히 분리한다.
6. `파일 비교`는 DOCX·PDF·XLSX를 형식별 방식으로 지원한다.
7. 팀 카테고리에는 중복 Tool을 추가하지 않고, 복합 판단은 이후 기본 에이전트가 담당한다.
