# 스킬 발표 — 슬라이드 구성과 대본

> 원본: [01_스킬_개념_정리.md](01_스킬_개념_정리.md), [03_스킬_검증_등록_설계.md](03_스킬_검증_등록_설계.md)  
> 전체 발표 중 스킬 세그먼트 3장. 심사위원은 실무자이므로 스킬의 정의는 설명하지 않는다. 첫 장은 실제 화면, 둘째 장은 등록 과정, 셋째 장은 팀 공유 효과에 집중한다.

## 슬라이드 1 — 스킬 검증 및 실행

### 이 장에서 전달할 것

스킬은 등록 전에 테스트를 거치며, 등록된 스킬은 채팅에서 `/스킬이름`으로 직접 호출할 수 있다. 이 장에서는 설명을 늘리지 않고 실제 화면 두 장으로 이 두 사실만 보여 준다.

### 화면 구성

`스킬 등록 화면`과 `/스킬이름으로 직접 호출` 화면을 좌우로 배치한다. 왼쪽에는 `새스킬_등록_화면.png`를 사용하고, 두 이미지 바깥의 흰색 프레임은 없앤다. 호출 화면 아래에는 `향후 개선 · 요청과 업무 상황을 보고 자동 선택`만 한 줄로 표시한다. 왼쪽 등록 화면은 다음 장의 검증 화면과 위치와 크기를 완전히 같게 맞춘다.

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ 검증한 Skill만 등록해 반복 업무에 재사용합니다                            │
│                                                                         │
│ 스킬 등록 화면                       /스킬이름으로 직접 호출               │
│ ┌─────────────────────────────────┐  ┌──────────────────────────────┐ │
│ │                                 │  │                              │ │
│ │      새 스킬 등록 화면               │  │      채팅창 호출 화면            │ │
│ │      이미지 비율 그대로              │  │      이미지 비율 그대로          │ │
│ │                                 │  │                              │ │
│ └─────────────────────────────────┘  └──────────────────────────────┘ │
│                                      향후 개선 · 요청과 업무 상황으로 자동 선택│
└─────────────────────────────────────────────────────────────────────────┘
```


#### 사용할 화면

- 스킬 등록 화면: `./image/새스킬_등록_화면.png`
  - 별도의 흰색 컨테이너 없이 배치한다. 다음 장의 `스킬 검증 화면`과 동일한 위치·너비·높이를 사용한다.
- 호출 화면: `./image/명시적_스킬_사용_화면.png`
  - 이미지 전체가 보이도록 원본 비율로 맞춘다. 화면 제목은 `등록된 Skill 호출`이 아니라 `/스킬이름으로 직접 호출`로 쓴다.
  - **주의**: 이 캡처의 `/` 목록에는 `[팀]` 배지가 붙은 항목이 보인다. 최근 수정으로 `/` 목록에는 **활성화된 내 스킬만** 뜨도록 바뀌었고(팀 카탈로그 항목은 트리거로 실행되지 않는다 — `발표자용 상세 §5`), 슬라이드 문구와도 어긋난다. 배포 후 다시 캡처하거나, `[개인]` 항목 한 줄만 보이게 크롭한다. 데모에서 부를 스킬(`work-progress-report-email`)이 `[개인]`으로 뜨는 상태로 캡처하면 "만들기 → 검증 → 호출"이 한 스킬로 이어져 깔끔하다.

### 대본

> 스킬 등록 화면에서 보시다시피 저희는 어떤 업무를 스킬로 만들지 한 문장으로 입력할 수 있고, 채팅창에서는 `/스킬이름`으로 등록된 스킬을 직접 호출할 수 있습니다. 향후에는 요청과 업무 상황을 보고 필요한 스킬을 자동으로 선택하도록 개선할 예정입니다.

## 슬라이드 2 — 스킬 등록 과정

### 이 장에서 전달할 것

스킬은 설명을 입력하자마자 등록하지 않는다. 필요한 요청에서 실행되는지, 필요하지 않은 요청에서 잘못 실행되지 않는지를 분리된 환경에서 먼저 확인하고, 검증을 통과한 경우에만 등록한다.

### 화면 구성

왼쪽에는 `스킬 검증 화면`이라는 제목과 `스킬_검증_상세.png`를 배치하고, 오른쪽에는 `스킬 등록 과정` 네 단계를 세로로 배치한다. 왼쪽 이미지의 위치와 크기는 앞 장의 `스킬 등록 화면`과 완전히 같게 맞춘다. 각 단계의 제목과 세부 내용은 하나의 블록 안에 넣고, 단계 사이에는 아래 방향 화살표를 둔다.

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ 필요한 요청과 불필요한 요청을 확인한 뒤 등록합니다                       │
│                                                                         │
│ 스킬 검증 화면                         스킬 등록 과정                   │
│ ┌──────────────────────────────────┐   ┌────────────────────────────┐ │
│ │                                  │   │ 01 업무 방식 설명           │ │
│ │       스킬 등록 중 화면              │   │ 담당 업무·조건 / 입력·결과·예외│ │
│ │                                  │   └────────────────────────────┘ │
│ │                                  │                 ↓                │
│ │                                  │   ┌────────────────────────────┐ │
│ │                                  │   │ 02 검증 환경 준비           │ │
│ │                                  │   │ 테스트 케이스 준비          │ │
│ │                                  │   └────────────────────────────┘ │
│ │                                  │                 ↓                │
│ │                                  │   ┌────────────────────────────┐ │
│ │                                  │   │ 03 요청별 동작 확인         │ │
│ │                                  │   │ 긍정·부정 요청 / 답변 확인  │ │
│ │                                  │   └────────────────────────────┘ │
│ │                                  │                 ↓                │
│ │                                  │   ┌────────────────────────────┐ │
│ │                                  │   │ 04 통과한 스킬 등록         │ │
│ └──────────────────────────────────┘   │ 개인 스킬로 게시            │ │
│                                        └────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────────┘
```

### 대본

> 스킬 등록 과정을 자세히 보시면 먼저 사용자가 어떤 스킬을 만들지 문장을 입력합니다. 한 문장이어도 됩니다. 그다음 바로 등록하는 게 아니라, **이 스킬이 필요한 요청에서는 제대로 실행되고, 필요하지 않은 요청에서는 잘못 실행되지 않는지를 확인합니다.**
>
> 한 번 등록된 스킬은 이후 여러 사용자 요청에 영향을 줄 수 있기 때문에, 잘못 실행되면 오히려 답변 품질을 떨어뜨릴 수 있습니다. 그래서 실제 환경과 분리된 검증 환경에서 먼저 테스트하고, **검증을 통과한 스킬만 최종 등록하도록 했습니다.**

## 슬라이드 3 — 팀 스킬 공유

### 이 장에서 전달할 것

한 사람이 만든 스킬을 팀원이 가져와 같은 절차와 기준으로 업무에 적용한다. 개인 기능을 나누는 데서 끝나는 것이 아니라, 팀의 처리 방식이 맞춰지고 비슷한 스킬을 각자 다시 만드는 일도 줄어든다.

한 문장으로 줄이면 **`개인이 만든 업무 방식을 팀이 같은 절차로 실행한다`**이다.

### 화면 구성

첨부한 `팀 스킬` 화면 한 장을 왼쪽에 크게 두고, **그 오른쪽 옆에** `팀 공유 효과`와 업무 효과 세 가지를 세로로 나란히 놓는다. 화면 아래 설명 문구는 두지 않는다.

```text
┌─────────────────────────────┐    ┌─────────────────────────────┐
│                             │    │ 팀 공유 효과                    │
│                             │    │                             │
│      팀 스킬 실제 화면          │    │ ■ 업무 표준화                  │
│   (등록된 스킬 · 공유중)         │ →  │   같은 절차·기준으로 처리        │
│                             │    │                             │
│                             │    │ ■ 중복 작업 감소                │
│                             │    │   검증된 방식을 다시 안 만듦       │
│                             │    │                             │
│                             │    │ ■ 담당자 의존도 완화             │
│                             │    │   담당자가 바뀌어도 절차 유지      │
└─────────────────────────────┘    └─────────────────────────────┘
        왼쪽 ~60%                          오른쪽 ~35%
```

#### 배치 원칙

- 왼쪽 약 60%에는 첨부한 팀 스킬 화면 한 장만 배치한다.
- 스크린샷은 `팀 스킬 2` 탭, `등록된 스킬` / `내가 공유한 스킬` 필터, 스킬 이름과 `공유중` 배지가 읽히도록 크롭한다.
- 첨부 화면은 **공유한 사람 시점**이라 배지가 `공유중`이고 오른쪽 버튼이 `중지`다. 가져가는 팀원 시점에서는 `내 스킬로 등록` 버튼과 `이미 등록됨` 배지가 보인다 — 이 시점 캡처가 있으면 "팀이 가져다 쓴다"는 메시지에 더 맞으므로 그쪽으로 교체한다.
- 목록은 두 개면 충분하다. 스킬 이름과 설명 글자가 발표 화면에서 읽히도록 키운다.
- 화면 오른쪽 옆 약 35% 폭에 `업무 표준화` / `중복 작업 감소` / `담당자 의존도 완화`를 위에서 아래로 나란히 놓는다.
- 각 항목은 굵은 제목 한 줄 + 보조 문장 한 줄. 카드·아이콘은 쓰지 않는다.
- 셋은 순서가 있는 단계가 아니라 나란한 효과다. 사이에 화살표를 넣지 않는다. 화면에서 오른쪽 목록으로 이어지는 화살표 하나만 둔다.


#### 사용할 화면

- `./image/팀스킬_공유_화면.png`

### 대본

> 저희는 여기서 개인화로 끝내지 않았습니다. 검증을 통과한 스킬은 팀에 공유할 수 있습니다. 예를 들어 한 사람이 만든 '업무 진행 보고 메일' 스킬을, 팀원이 가져와 같은 양식으로 씁니다. 사람마다 제각각이던 처리 방식이 하나로 맞춰지고, 이미 검증된 방식을 각자 다시 만들 필요도 없어집니다. 개인이 만든 절차가 팀의 공통 실행 기준이 된다는 점이 저희 차별점입니다.

## 부록 1 — 등록 검증

### 이 장에서 전달할 것

등록 검증은 스킬이 필요한 요청과 필요하지 않은 요청을 올바르게 구분하는지, 그리고 실제 답변이 정해둔 형식과 업무 범위를 지키는지를 확인한 시험이다. 5개 스킬을 각각 36회씩 확인했고, 검증 결과 5개 모두 등록했다.

### 화면 구성

- 제목 오른쪽에 `등록 결과 5개 모두 등록`을 짧게 표시한다.
- 제목 아래에는 `필요한 요청 6개 + 불필요한 요청 6개를 각각 3회 실행 · 스킬당 36회 · 총 180회`를 한 줄로 쓴다.
- 검증 항목의 뜻은 블록이나 카드로 나누지 않고, 표 위에 불렛 한 줄씩 배치한다.
- 테스트 방법과 세 항목 설명은 모두 `15px`로 맞춰 발표 화면에서 바로 읽히게 한다.
- 불렛 아래에는 5개 스킬의 결과를 한 표로 보여준다.
- 표 아래에는 업무 진행 보고 메일의 실제 오선택 질문과 개선 방향을 `14px`로 두 줄 적는다.

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 등록 검증                                            등록 결과 5개 모두 등록 │
│ 필요한 요청 6개 + 불필요한 요청 6개를 각각 3회 실행 · 총 180회              │
│                                                                            │
│ • 필요한 요청 선택 — 스킬을 써야 하는 요청 18회 중 스킬이 선택된 횟수       │
│ • 불필요한 요청 오선택 — 쓰면 안 되는 요청 18회 중 잘못 선택된 횟수          │
│ • 최종 답변 기준 충족 — 형식·사실·업무 범위 등 미리 정한 기준을 지킨 개수    │
│                                                                            │
│ ┌──────────────────┬────────────┬────────────┬──────────────┐              │
│ │ 스킬             │ 필요한 요청 │ 불필요 요청 │ 최종 답변 기준 │              │
│ │                  │ 선택       │ 오선택      │ 충족           │              │
│ ├──────────────────┼────────────┼────────────┼──────────────┤              │
│ │ 업무 진행 보고 메일 │ 18/18      │ 3/18       │ 8/8           │              │
│ │ 기획 메모 정리      │ 18/18      │ 0/18       │ 9/9           │              │
│ │ 문장 작성·번역      │ 18/18      │ 0/18       │ 9/9           │              │
│ │ 제안서 작성         │ 18/18      │ 0/18       │ 6/7           │              │
│ │ 경쟁사 분석         │ 18/18      │ 0/18       │ 8/9           │              │
│ └──────────────────┴────────────┴────────────┴──────────────┘              │
│ 오선택 질문 · “고객사에 보낼 프로젝트 진행 상황 안내 메일을 작성해줘.       │
│                외부 고객이 이해하기 쉽게 설명하고 문의 방법도 넣어줘.”       │
│ 개선 방향 · 내부 상사·책임자 보고 전용임을 명시하고 외부 고객 안내는 제외   │
└────────────────────────────────────────────────────────────────────────────┘
```

### 대본

> 먼저 등록 검증입니다. 스킬마다 이 스킬을 써야 하는 요청 6개와 쓰면 안 되는 요청 6개를 만들고, 각 요청을 3회씩 실행했습니다. 그래서 스킬 하나당 36회, 5개 스킬은 총 180회 확인했습니다.
>
> 필요한 요청 선택은 써야 하는 상황에서 실제로 선택된 횟수이고, 불필요한 요청 오선택은 쓰면 안 되는 상황에서 잘못 선택된 횟수입니다. 최종 답변 기준 충족은 반복 횟수가 아니라, 실제 답변이 형식과 사실, 업무 범위 같은 세부 기준을 몇 개 지켰는지를 뜻합니다.
>
> 필요한 요청은 5개 스킬 모두 18회 전부 선택됐습니다. 업무 진행 보고 메일은 “고객사에 보낼 프로젝트 진행 상황 안내 메일을 작성해 달라”는 외부 고객용 요청을 3회 모두 잘못 선택했습니다. 내부 상사나 책임자에게 보내는 보고 전용임을 스킬 설명에 명시하고, 외부 고객 안내 요청은 제외하도록 선택 기준을 보완할 계획입니다.

## 부록 2 — 스킬 사용 전후 비교

### 이 장에서 전달할 것

같은 업무를 `매번 상세하게 지시하는 방법`과 `저장한 스킬을 사용하는 방법`으로 각각 실행해, 사용자가 작성해야 하는 요청의 길이와 모델이 실제로 읽는 입력량, 결과 품질을 비교했다. 총 300회 중 274회가 결과 요구사항을 충족했고, 스킬 사용 시 전체 결과 품질은 89.3%에서 93.3%로 4.0%포인트 높아졌다.

### 화면 구성

- 제목 오른쪽에 `결과 요구사항 충족 274/300 · 91.3%`를 표시한다.
- 제목 아래에는 `5개 스킬 × 10개 업무 × 3회 반복 × 2가지 방법 = 총 300회`를 한 줄로 쓴다.
- 두 가지 방법은 같은 줄에서 `매번 상세하게 지시 150회 / 저장한 스킬 사용 150회`로 설명한다.
- 비교 항목의 뜻은 블록이나 카드가 아니라 불렛 한 줄씩 배치하고, 등록 검증 장과 같은 `15px`를 사용한다.
- 표는 한 칸에 두 조건을 합치지 않는다. `사용자 입력 토큰`, `실제 모델 입력 토큰`, `결과 품질`을 각각 `상세 지시`와 `스킬 사용`의 두 열로 분리한다.
- 사용자 입력 토큰과 실제 모델 입력 토큰의 `스킬 사용` 값 아래에는 상세 지시 대비 증감률을 괄호로 표시한다.
- 스킬별 결과 품질은 `25/30`처럼 충족 횟수만 표시하고, 비율은 `전체 결과 품질` 행의 `89.3%`, `93.3%`만 남긴다.
- 표 아래에는 제안서 작성의 품질이 1건 낮아진 이유를 등록 검증 장의 하단 설명과 같은 `14px`로 쓴다. 내용 누락이 아니라 `5천 명`을 `5,000명`으로 바꿔 쓴 정확 표기 검사 실패다.
- 표 아래에 별도의 요약 카드나 `3개 개선·1개 동일·1개 감소` 문구는 넣지 않는다.

### 대본

> 다음은 스킬 사용 전후 비교입니다. 5개 스킬에서 같은 업무 10개를 골라 3회씩 반복하고, 매번 상세하게 지시하는 방법과 저장한 스킬을 사용하는 방법으로 나눠 총 300회를 실행했습니다.
>
> 사용자 입력 토큰은 사용자가 직접 작성해야 하는 요청의 길이입니다. 실제 모델 입력 토큰은 저장된 스킬 지침까지 포함해 모델이 읽은 전체 입력량이고, 결과 품질은 필수 내용과 표현, 의미 기준을 모두 지킨 실행의 비율입니다.
>
> 스킬을 사용하면 사용자가 직접 작성하는 입력은 모든 업무에서 절반 이상 줄었습니다. 모델은 저장된 지침을 추가로 읽기 때문에 실제 입력량은 늘었지만, 전체 결과 품질은 89.3%에서 93.3%로 4.0%포인트 높아졌습니다. 제안서는 한 건 낮아졌는데, 내용 누락이 아니라 원문의 `5천 명`을 `5,000명`으로 바꿔 써 정확한 숫자 표기 검사에서 미충족 처리된 경우입니다. 즉 사용자의 작성 부담을 줄이면서 전체 품질을 유지하거나 개선한 결과입니다.

## 본문 슬라이드에서 제외할 내용

- 스킬의 정의와 `SKILL.md` 구조
- progressive disclosure와 토큰 비용
- 자동 선택의 내부 배선 설명 (Future Work로 `자동 Trigger / Hook` 한 줄만 언급하고 상세는 제외)
- 검증 수치는 본문에서 제외하고 부록 1·2에서만 제시
- Store namespace와 미들웨어 이름
- `allowed-tools`와 서브에이전트 전달 방식
- 독립 사본의 상세 버전 정책
