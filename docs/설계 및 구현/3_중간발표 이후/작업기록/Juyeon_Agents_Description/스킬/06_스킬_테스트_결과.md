# 스킬 테스트 결과 — 발표자가 이해하기 쉬운 설명

> 스킬 검증 HTML의 숫자를 처음 보는 사람도 이해할 수 있도록 풀어 쓴 문서다. 발표 자료에는 「PPT 부록 2페이지 구성안」을 사용하고, 나머지는 발표자 이해와 질의응답용으로 활용한다.

## 1. 이번 테스트에서 확인한 것

| 구분 | 확인 질문 | 쉽게 말하면 |
|---|---|---|
| **등록 검증** | 필요한 요청에 선택되고, 불필요한 요청에는 끼어들지 않으며, 최종 답변이 지침을 지키는가? | 실제로 등록해 사용해도 되는가? |
| **사용 전후 비교** | 절차를 매번 길게 쓸 때와 저장한 스킬을 사용할 때 결과가 어떻게 달라지는가? | 스킬로 저장해서 쓸 가치가 있는가? |

두 검증은 목적이 다르므로 한 숫자로 섞지 않는다.

## 2. 테스트한 다섯 가지 스킬

발표에서는 영문 스킬 이름을 사용하지 않는다.

| 발표용 이름 | 하는 일 |
|---|---|
| **업무 진행 보고 메일 작성** | 진행 내용·이슈·다음 계획을 정리해 상사에게 보낼 보고 메일을 작성한다. |
| **기획 메모를 개발 명세로 정리** | 기획 메모를 유저 스토리, 인수 조건, 우선순위, 테스트 항목으로 정리한다. |
| **문장을 자연스럽게 작성·번역** | 마케팅·UI·이메일 등의 문장을 자연스럽게 다듬고 표현 선택 이유를 설명한다. |
| **고객 요구사항으로 제안서 작성** | 고객 과제와 해결안, 제안 범위, 추진 계획, 기대효과, 확인 필요 사항을 연결한다. |
| **경쟁사 비교 분석** | 여러 경쟁사 자료를 같은 기준으로 비교표에 정리하고 우리 회사의 시사점을 도출한다. |

# 1부. 등록 검증

## 3. 네 가지 지표를 왜 사용했나

| 발표용 이름 | 확인하는 것 | 계산 방법 |
|---|---|---|
| **필요한 요청 선택률** | 써야 하는 상황을 놓치지 않는가? | 선택해야 하는 요청 중 실제 선택한 수 |
| **선택 정확도** | 선택한 요청이 이 스킬의 업무가 맞는가? | 올바른 선택 수 ÷ 전체 선택 수 |
| **불필요한 요청 오선택률** | 쓰면 안 되는 상황에 잘못 끼어들지 않는가? | 잘못 선택한 요청 수 ÷ 불필요한 요청 수 |
| **최종 답변 기준 충족률** | 답변이 형식·사실·범위 기준을 지켰는가? | 통과한 세부 기준 수 ÷ 확인한 세부 기준 수 |

필요한 요청 선택률만 보면 아무 요청에나 스킬을 선택해도 좋은 점수를 받을 수 있다. 선택 정확도만 보면 확실한 요청에만 반응하고 필요한 요청을 놓칠 수 있다. 두 선택 지표가 좋아도 최종 답변이 틀리면 사용할 수 없다. 그래서 **잘 찾아 쓰는지**와 **쓴 뒤 잘 수행하는지**를 나눠 확인했다.

## 4. 긍정 6개·부정 6개·3회 반복의 뜻

- **긍정 요청 6개:** 이 스킬을 사용해야 하는 직접 요청, 바꿔 말한 요청, 이전 문맥이 필요한 요청이다.
- **부정 요청 6개:** 비슷하지만 목적이 다르거나 다른 스킬이 맡아야 하는 요청이다.
- **3회 반복:** 같은 요청을 새 실행으로 세 번 확인해 2회 이상 같은 판단이 나온 결과를 사용했다.

```text
필요한 요청 6개 × 3회 = 18회
불필요한 요청 6개 × 3회 = 18회
선택 판단 합계          = 36회
```

선택 판단과 별도로 성격이 다른 세 요청의 최종 답변을 실행했다. 각 답변에서 형식, 사실 보존, 제외 범위, 필요한 도구 사용을 2~3개의 세부 기준으로 검사했다. 따라서 최종 답변은 3건이지만 세부 기준의 총수는 스킬에 따라 다르다.

## 5. 등록 검증 결과

| 스킬 | 필요한 요청 선택 | 불필요한 요청 오선택 | 선택 정확도 | 최종 답변 기준 충족 | 등록 |
|---|---:|---:|---:|---:|---|
| **업무 진행 보고 메일 작성** | 6/6 | **1/6** | 6/7 | 8/8 | **등록** |
| **기획 메모를 개발 명세로 정리** | 6/6 | 0/6 | 6/6 | 9/9 | **등록** |
| **문장을 자연스럽게 작성·번역** | 6/6 | 0/6 | 6/6 | 9/9 | **등록** |
| **고객 요구사항으로 제안서 작성** | 6/6 | 0/6 | 6/6 | 6/7 | **등록** |
| **경쟁사 비교 분석** | 6/6 | 0/6 | 6/6 | 8/9 | **등록** |

다섯 스킬 모두 필요한 요청 6개를 전부 선택했다. 신규 두 스킬은 불필요한 요청을 한 건도 잘못 선택하지 않았다. 제안서와 경쟁사 분석은 최종 답변 세부 기준에서 각각 한 항목씩 놓쳤지만 등록 기준인 80% 이상을 충족했다. 다섯 스킬 모두 현재 등록 상태다.

## 6. 보고 메일의 오선택 16.7%는 무엇인가

사용하면 안 되는 요청 6개 중 아래 한 건을 잘못 선택했다.

> “고객사에 보낼 프로젝트 진행 상황 안내 메일을 작성해줘. 외부 고객이 이해하기 쉽게 설명하고 문의 방법도 넣어줘.”

이 스킬은 내부 상사나 책임자에게 보내는 진행 보고 메일만 맡는다. 모델이 `프로젝트 진행 상황 + 메일 작성`에 반응해 외부 고객 메일까지 선택했다.

```text
불필요한 요청 오선택률 = 1/6 = 16.7%
선택 정확도             = 6/7 = 85.7%
```

발표에서는 “필요한 내부 보고 요청은 모두 잡았지만 외부 고객용 안내 메일 한 건도 잘못 선택해, 내부·외부 수신자 경계를 강화해야 한다는 개선점을 찾았다”고 설명한다.

# 2부. 스킬 사용 전후 비교

## 7. 무엇과 무엇을 비교했나

같은 업무 사례를 두 조건에서 비교했다.

- **매번 상세 지시:** 사용자가 결과 형식, 주의사항, 제외 조건을 요청마다 직접 적는다.
- **저장한 스킬 사용:** 같은 절차를 스킬에 저장하고 사용자는 실제 업무 내용만 입력한다.

확인 질문은 “같은 업무 절차를 매번 길게 입력하지 않고 스킬로 저장해도 결과 품질이 유지되거나 좋아지는가?”이다.

## 8. 왜 총 300회인가

```text
스킬 5개 × 업무 사례 10개 × 반복 3회 × 두 조건 = 총 300회
```

각 스킬은 상세 지시 30회와 스킬 사용 30회, 합계 60회다. 300회 모두 모델 실행 자체는 오류 없이 끝났다.

## 9. 결과 요구사항 충족 274/300의 뜻

한 번의 실행은 모델 오류가 없고, 사례별 필수 내용이나 표현을 포함하며, 의미 평가 항목을 모두 만족해야 통과했다.

| 스킬 | 매번 상세 지시 | 저장한 스킬 사용 | 차이 |
|---|---:|---:|---:|
| **업무 진행 보고 메일 작성** | 25/30, 83.3% | **30/30, 100.0%** | +16.7%포인트 |
| **기획 메모를 개발 명세로 정리** | 28/30, 93.3% | 28/30, 93.3% | 차이 없음 |
| **문장을 자연스럽게 작성·번역** | 29/30, 96.7% | **30/30, 100.0%** | +3.3%포인트 |
| **고객 요구사항으로 제안서 작성** | **28/30, 93.3%** | 27/30, 90.0% | -3.3%포인트 |
| **경쟁사 비교 분석** | 24/30, 80.0% | **25/30, 83.3%** | +3.3%포인트 |

전체 합계는 274/300, 91.3%다. PPT에서는 전체 합계만 보여 주지 말고 스킬별 차이도 함께 보여 준다. 제안서 스킬처럼 저장한 스킬 사용 결과가 조금 낮아진 경우도 숨기지 않는다.

## 10. 실패한 26건은 어디서 발생했나

### 기존 세 스킬의 10건

| 원인 | 건수 | 설명 |
|---|---:|---|
| 같은 의미의 다른 단어 사용 | 5건 | `오늘` 대신 `금일`, `회신일` 대신 `회신 일정`을 사용했다. |
| 제외 범위를 요구사항으로 추가 | 4건 | 제외한 시스템 설정 자동 추종을 인수 조건·테스트 항목으로 다시 넣었다. |
| 결과 대신 확인 질문만 제공 | 1건 | 오류 문구를 다듬지 않고 대상 언어와 채널을 되물었다. |

`금일`을 `금요일`로 쓴 것이 아니다.

> 입력: “검토 요청은 **오늘 등록**”  
> 출력: “**금일 법무 검토 요청을 등록할 예정입니다.**”

> 입력: “**회신일은 미정**”  
> 출력: “원천 부서 **회신 일정은 현재 미정**”

의미는 맞지만 필수 단어를 글자 그대로 찾는 보수적 검사에서 실패했다.

### 신규 두 스킬의 16건

신규 실패 16건에는 의미 평가 실패가 없었다. 모두 같은 의미를 다른 표기로 쓴 정확 단어 검사 실패였다.

| 스킬 | 건수 | 실제 차이 |
|---|---:|---|
| 제안서 작성 | 5건 | `5천 명`을 `5,000명`으로 쓰거나 `80곳`을 그대로 반복하지 않았다. |
| 경쟁사 분석 | 11건 | `29달러`를 `$29`, `미공개`나 `자료가 없다`를 `정보 없음`으로 썼다. 일부는 `9~18시`를 `평일 업무시간`으로 바꿨다. |

제안서 스킬은 `5천 명` 대신 `5,000명`을 사용했지만 수강 신청, 이수증 발급, 공공 클라우드 보안, 예산·사업 기간 미정을 모두 반영했다. 경쟁사 분석도 `자료가 없다` 대신 `정보 없음`이라고 썼지만 정보 공백을 정확히 표시했다. 다음 평가에서는 숫자 표기와 동의 표현을 허용하거나 의미 평가를 우선하는 것이 좋다.

## 11. 표 열 제목은 이렇게 쓴다

한 열 안에 `상세 지시 → 스킬`처럼 두 값을 넣지 않고 별도 열로 분리한다.

| 스킬 | 사용자 입력<br>상세 지시 | 사용자 입력<br>스킬 사용 | 모델 입력<br>상세 지시 | 모델 입력<br>스킬 사용 | 응답시간<br>상세 지시 | 응답시간<br>스킬 사용 |
|---|---:|---:|---:|---:|---:|---:|
| 업무 진행 보고 메일 작성 | 119.5 | 56.5 | 5,468.5 | 5,853.5 | 3.4초 | 3.6초 |
| 기획 메모를 개발 명세로 정리 | 105.5 | 42.5 | 5,454.5 | 5,763.5 | 14.5초 | 8.8초 |
| 문장을 자연스럽게 작성·번역 | 116.5 | 34.0 | 5,465.5 | 5,883.0 | 3.2초 | 2.4초 |
| 고객 요구사항으로 제안서 작성 | 140.5 | 59.0 | 5,489.5 | 5,976.0 | 15.5초 | 12.4초 |
| 경쟁사 비교 분석 | 140.5 | 69.0 | 5,489.5 | 6,096.0 | 12.5초 | 9.7초 |

두 번째 부록 페이지에서는 결과 품질 표를 먼저 보여 주고, 그 아래에 입력 토큰과 응답시간 표를 배치한다. 이 순서로 읽어야 결과 품질을 확인한 뒤 사용 부담과 처리시간의 변화를 이해할 수 있다.

## 12. 사용자 입력은 줄고 모델 입력은 늘어난 이유

| 스킬 | 사용자 입력 변화 | 실제 모델 입력 변화 |
|---|---:|---:|
| 업무 진행 보고 메일 작성 | 52.7% 감소 | 7.0% 증가 |
| 기획 메모를 개발 명세로 정리 | 59.7% 감소 | 5.7% 증가 |
| 문장을 자연스럽게 작성·번역 | 70.8% 감소 | 7.6% 증가 |
| 고객 요구사항으로 제안서 작성 | 58.0% 감소 | 8.9% 증가 |
| 경쟁사 비교 분석 | 50.9% 감소 | 11.0% 증가 |

사용자는 저장된 절차를 반복해서 쓰지 않아 입력이 짧아진다. 반면 모델은 저장된 스킬 본문을 추가로 읽으므로 실제 모델 입력은 늘어난다. 장점은 전체 토큰 절감이 아니라 **사용자 작성 부담 감소와 절차 재사용**이다.

문장 작성·번역의 70.8% 감소도 짧은 요청 자체가 70.8% 줄었다는 뜻이 아니다. 형식과 주의사항을 매번 상세하게 적는 조건과 비교했기 때문에 나온 수치다. 사용자가 원래부터 “이 문장 자연스럽게 번역해줘”라고만 쓴다면 감소 효과는 더 작다.

## 13. 응답시간은 어떻게 설명하나

보고 메일은 3.4초에서 3.6초로 약 0.2초, 4.4% 늘었다. 반면 나머지 네 스킬은 짧아졌다. 응답시간은 서버 상태와 출력 길이에도 영향을 받으므로 “스킬은 항상 빠르다” 또는 “항상 느리다”고 일반화하지 않는다.

# 3부. PPT 부록 2페이지 구성안

두 페이지는 서로 다른 질문에 답한다.

1. **부록 1:** 이 스킬을 등록해도 되는가?
2. **부록 2:** 등록한 스킬을 사용하면 무엇이 달라지는가?

한 페이지에 두 검증을 섞지 않는다. 첫 페이지에서 등록 근거를 이해시킨 뒤, 두 번째 페이지에서 사용 가치와 한계를 보여 준다.

## 14. 부록 1 — 다섯 스킬 모두 등록 기준을 통과했다

### 이 페이지가 답할 질문

> 스킬이 필요한 상황을 제대로 구분하고, 실제 답변에서도 정해 둔 지침을 지키는가?

### 권장 제목

> **요청 구분과 답변 지침을 확인해 5개 스킬을 등록했습니다**

### 상단: 검증을 어떻게 했는가

아래 세 단계를 왼쪽에서 오른쪽으로 배치한다.

| 1. 요청을 구분하는지 확인 | 2. 실제 답변이 지침을 지키는지 확인 | 3. 기준 충족 시 등록 |
|---|---|---|
| 스킬을 **써야 하는 요청 6개**와 **쓰면 안 되는 요청 6개**를 준비 | 성격이 다른 요청 3개를 실제로 수행 | 요청 구분과 답변 기준을 모두 확인 |
| 같은 요청을 각각 **3회 실행** | 형식·사실 보존·업무 범위 등 **7~9개 세부 항목** 검사 | 통과한 스킬만 플랫폼에 등록 |
| 3회 중 **2회 이상 같은 판단**을 최종 결과로 사용 | 지킨 항목 수를 `통과 항목/전체 항목`으로 표시 | 최종 결과: **5개 모두 등록** |

단계 아래에 다음 설명을 한 줄로 넣는다.

> 스킬 하나당 요청 선택 판단은 `12개 요청 × 3회 = 36회`이며, 다섯 스킬은 총 180회 판단했습니다.

### 중앙: 네 가지 검증 기준

영문 지표명은 쓰지 않고 다음 문장형 이름을 사용한다.

| 화면에 표시할 이름 | 숫자를 읽는 방법 | 확인하려는 질문 |
|---|---|---|
| **써야 할 요청을 선택** | `6/6` = 써야 할 요청 6개 중 6개 선택 | 필요한 상황을 놓치지 않았는가? |
| **쓰면 안 될 요청을 잘못 선택** | `1/6` = 쓰면 안 될 요청 6개 중 1개를 잘못 선택 | 비슷하지만 다른 업무에 끼어들지 않는가? |
| **선택한 요청 중 올바른 선택** | `6/7` = 선택한 7개 중 6개가 실제 담당 업무 | 스킬이 선택한 요청은 얼마나 정확한가? |
| **최종 답변에서 지킨 항목** | `8/8` = 확인한 답변 기준 8개를 모두 충족 | 스킬을 사용한 뒤 결과도 지침을 지켰는가? |

### 하단: 등록 검증 결과

| 스킬 | 써야 할 요청을 선택 | 쓰면 안 될 요청을 잘못 선택 | 선택한 요청 중 올바른 선택 | 최종 답변에서 지킨 항목 | 결과 |
|---|---:|---:|---:|---:|---|
| 업무 진행 보고 메일 작성 | 6/6 | **1/6** | **6/7** | 8/8 | 등록 |
| 기획 메모를 개발 명세로 정리 | 6/6 | 0/6 | 6/6 | 9/9 | 등록 |
| 문장을 자연스럽게 작성·번역 | 6/6 | 0/6 | 6/6 | 9/9 | 등록 |
| 고객 요구사항으로 제안서 작성 | 6/6 | 0/6 | 6/6 | 6/7 | 등록 |
| 경쟁사 비교 분석 | 6/6 | 0/6 | 6/6 | 8/9 | 등록 |

표 아래에는 결론과 개선점을 분리해 쓴다.

> **결론:** 다섯 스킬 모두 써야 할 요청 6개를 전부 선택했고, 최종 답변 기준도 등록 기준인 80% 이상을 충족해 모두 등록했습니다.  
> **확인된 개선점:** 보고 메일 스킬은 외부 고객용 안내 메일 1개도 잘못 선택했습니다. 내부 보고와 외부 안내의 경계를 더 분명하게 보완할 필요가 있습니다.

### 부록 1 발표 대본

> 먼저 스킬을 등록해도 되는지 확인했습니다. 스킬마다 써야 하는 요청 여섯 개와 쓰면 안 되는 요청 여섯 개를 준비하고, 같은 요청을 세 번씩 실행했습니다. 세 번 중 두 번 이상 같은 판단이 나온 값을 최종 결과로 사용했습니다. 그다음 성격이 다른 요청 세 개를 실제로 수행해 형식, 사실 보존, 업무 범위 같은 답변 기준을 지켰는지 확인했습니다.
>
> 표의 숫자는 모두 성공 건수와 전체 건수입니다. 예를 들어 6/6은 써야 할 요청 여섯 개를 전부 선택했다는 뜻이고, 6/7은 스킬이 선택한 일곱 개 중 여섯 개가 올바른 선택이었다는 뜻입니다. 다섯 스킬 모두 필요한 요청을 놓치지 않았고 답변 기준도 등록 기준을 충족해 등록했습니다. 다만 보고 메일 스킬은 외부 고객용 안내 메일 한 건도 선택해, 내부 보고와 외부 안내의 경계를 보완해야 한다는 개선점을 확인했습니다.

## 15. 부록 2 — 저장한 스킬은 설명 부담을 줄이고 결과 품질을 대체로 유지했다

### 이 페이지가 답할 질문

> 같은 업무 절차를 스킬로 저장해 사용하면, 매번 자세히 설명할 때와 비교해 결과 품질·입력량·응답시간이 어떻게 달라지는가?

### 권장 제목

> **저장한 스킬은 사용자 작성 부담을 줄이고 결과 품질을 유지했습니다**

제목 바로 아래에 핵심 숫자를 한 줄로 크게 배치한다.

> **사용자 입력 50.9~70.8% 감소 · 결과 충족: 상세 지시 134/150회, 스킬 사용 140/150회**

### 상단: 무엇과 무엇을 비교했는가

영문 약어 대신 비교한 두 조건을 그대로 적는다.

| 매번 상세하게 지시 | 저장한 스킬 사용 |
|---|---|
| 사용자가 결과 형식·포함 내용·주의사항을 요청마다 작성 | 결과 형식과 주의사항은 스킬에 저장 |
| 업무 내용과 실행 절차를 함께 입력 | 사용자는 그때의 업무 내용만 입력 |

두 조건 아래에 공정한 비교 조건을 한 줄로 표시한다.

> 같은 10개 업무 사례를 각 조건에서 3회씩 실행했습니다. `5개 스킬 × 10개 사례 × 3회 × 2조건 = 총 300회`이며, 모델과 입력 사실은 동일하게 유지했습니다.

### 중앙: 결과 요구사항 충족 비교

`결과 요구사항 충족`은 오류 없이 답변을 만들고, 사례에서 요구한 필수 내용·표현·의미 기준을 모두 만족한 실행을 뜻한다.

| 스킬 | 매번 상세하게 지시 | 저장한 스킬 사용 | 차이 |
|---|---:|---:|---:|
| 업무 진행 보고 메일 작성 | 25/30, 83.3% | **30/30, 100.0%** | +16.7%포인트 |
| 기획 메모를 개발 명세로 정리 | 28/30, 93.3% | 28/30, 93.3% | 차이 없음 |
| 문장을 자연스럽게 작성·번역 | 29/30, 96.7% | **30/30, 100.0%** | +3.3%포인트 |
| 고객 요구사항으로 제안서 작성 | **28/30, 93.3%** | 27/30, 90.0% | -3.3%포인트 |
| 경쟁사 비교 분석 | 24/30, 80.0% | **25/30, 83.3%** | +3.3%포인트 |
| **전체** | **134/150, 89.3%** | **140/150, 93.3%** | **+4.0%포인트** |

표 오른쪽이나 아래에 다음 결론을 강조한다.

> 스킬 사용 후 3개 업무는 결과 충족이 늘었고, 1개는 같았으며, 제안서 작성은 1건 감소했습니다. 따라서 “항상 품질이 좋아진다”가 아니라 **전체적으로 품질을 유지하면서 일부 업무에서 개선됐다**고 설명합니다.

### 하단: 입력량과 응답시간 비교

모든 값은 세 번 실행한 결과의 중앙값이다. 두 값을 화살표로 합치지 않고 조건별 열로 나눈다.

| 스킬 | 사용자 입력 토큰<br>상세 지시 | 사용자 입력 토큰<br>스킬 사용 | 실제 모델 입력 토큰<br>상세 지시 | 실제 모델 입력 토큰<br>스킬 사용 | 응답시간<br>상세 지시 | 응답시간<br>스킬 사용 |
|---|---:|---:|---:|---:|---:|---:|
| 업무 진행 보고 메일 작성 | 119.5 | 56.5 | 5,468.5 | 5,853.5 | 3.4초 | 3.6초 |
| 기획 메모를 개발 명세로 정리 | 105.5 | 42.5 | 5,454.5 | 5,763.5 | 14.5초 | 8.8초 |
| 문장을 자연스럽게 작성·번역 | 116.5 | 34.0 | 5,465.5 | 5,883.0 | 3.2초 | 2.4초 |
| 고객 요구사항으로 제안서 작성 | 140.5 | 59.0 | 5,489.5 | 5,976.0 | 15.5초 | 12.4초 |
| 경쟁사 비교 분석 | 140.5 | 69.0 | 5,489.5 | 6,096.0 | 12.5초 | 9.7초 |

표 아래에는 숫자의 의미를 세 문장으로 정리한다.

- **사용자 입력:** 상세 지시를 스킬에 저장했기 때문에 사용자가 직접 작성한 분량은 50.9~70.8% 감소했다. 이는 원래 짧은 요청과 비교한 값이 아니라, 같은 절차를 매번 상세히 적은 조건과 비교한 값이다.
- **실제 모델 입력:** 모델은 저장된 스킬 본문을 추가로 읽기 때문에 5.7~11.0% 증가했다. 사용자 작성 부담은 줄지만 전체 입력 토큰이 줄어드는 구조는 아니다.
- **응답시간:** 다섯 스킬 중 네 스킬은 짧아졌고, 보고 메일은 3.4초에서 3.6초로 약 0.2초 늘었다. 응답시간은 서버 상태와 출력 길이의 영향도 받으므로 항상 빨라진다고 일반화하지 않는다.

### 부록 2 발표 대본

> 다음은 저장한 스킬을 사용하는 것이 실제로 어떤 차이를 만드는지 확인한 결과입니다. 비교한 것은 매번 형식과 주의사항까지 자세히 적는 방식과, 그 절차를 스킬에 저장하고 업무 내용만 입력하는 방식입니다. 다섯 스킬에서 같은 업무 사례 열 개를 각각 세 번 실행해, 조건별 150회씩 총 300회를 비교했습니다.
>
> 결과 요구사항을 모두 충족한 실행은 상세 지시 방식이 150회 중 134회, 스킬 사용 방식이 150회 중 140회였습니다. 세 업무는 좋아졌고 한 업무는 같았으며, 제안서 작성은 한 건 줄었습니다. 따라서 스킬이 항상 품질을 높였다고 말하기보다, 전체적으로 품질을 유지하면서 일부 업무에서 개선됐다고 보는 것이 정확합니다.
>
> 사용자가 직접 작성하는 입력은 절반 이상 줄었습니다. 반면 모델은 저장된 스킬 지침을 추가로 읽기 때문에 실제 모델 입력은 5.7~11.0% 늘었습니다. 응답시간은 다섯 스킬 중 네 스킬에서 짧아졌지만 보고 메일은 약 0.2초 늘어, 속도 개선을 스킬의 보장 효과로 보지는 않았습니다.

## 16. 두 페이지에서 사용하는 표현 원칙

- **써야 할 요청을 선택**처럼 무엇을 확인했는지 바로 드러나는 이름을 쓴다.
- **선택한 요청 중 올바른 선택**처럼 성공 건수와 전체 건수의 관계가 보이는 이름을 쓴다.
- 잘못 끼어든 요청은 **쓰면 안 될 요청을 잘못 선택**이라고 쓴다.
- 최종 답변 평가는 **최종 답변에서 지킨 항목**이라고 쓴다.
- 사용 전후 평가는 **매번 상세하게 지시한 결과와 저장한 스킬을 사용한 결과 비교**라고 쓴다.
- 퍼센트만 쓰지 않고 `6/6`, `134/150`처럼 성공 건수와 전체 건수를 함께 쓴다.
- 시간은 밀리초가 아니라 초 단위로 쓰며, 소수점 첫째 자리까지만 표시한다.
- `성공률 91.3%`만 단독으로 강조하지 않는다. 어떤 조건에서 몇 건이 통과했는지 함께 보여 준다.
