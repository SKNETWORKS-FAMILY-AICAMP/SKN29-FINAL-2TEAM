# 스킬(Skill)이란 무엇인가

이 프로젝트가 쓰는 "스킬"은 새로 만든 개념이 아니다. [Agent Skills 명세](https://agentskills.io/specification)를 deepagents가 구현한 것을 그대로 가져다 쓴다. 이 문서는 공식 명세·공식 가이드([agentskills.io](https://agentskills.io), [platform.claude.com](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)) 기준으로 "스킬이 뭐고, 왜 쓰고, 어떻게 써야 잘 불려오고, 모델이 실제로 어떻게 쓰는지"를 다룬다. 이 프로젝트만의 배선(DB 위치, 로딩 시점, 권한, 활성화 토글)은 [00_내부_흐름_분석.md](00_내부_흐름_분석.md) §7과 이어서 설명한다.

---

## 한 줄 정의

**스킬 = 이름·설명 + 실제 지침이 담긴 문서 하나**(`SKILL.md`). 에이전트는 평소엔 이름·설명만 보다가, 필요하다고 판단하면 그 문서를 직접 열어 본문을 읽는다.

## 왜 쓰는가

시스템 프롬프트에 모든 지침을 다 적어두면 두 가지 문제가 생긴다.

| 문제 | 스킬이 푸는 방식 |
|---|---|
| 모든 지침이 매 호출마다 토큰으로 실림(안 쓰는 지침도) | 이름·설명만 상시 노출, 본문은 필요할 때만 읽음 |
| 지침이 길어질수록 시스템 프롬프트가 비대해지고 관리가 어려움 | 지침 하나당 파일 하나 — 새로 추가·수정해도 다른 지침과 안 섞임 |
| "이럴 땐 이렇게 답해라" 같은 절차적 지식을 코드로 못 박기 애매함 | 자연어 문서로 저장 — 코드 배포 없이 텍스트만 바꾸면 반영됨 |

핵심 아이디어는 **"자주 안 쓰는 지식을 평소엔 이름표만, 필요할 때 펼쳐 읽는" 것** — 이를 "progressive disclosure(점진적 공개)"라 부른다.

## 실제로 뭘 스킬로 만드나 — 회사 사례 4개 + 판단 기준

스킬은 **"무슨 일을 할지"를 저장하는 게 아니라, 그 일을 우리 조직의 방식으로 반복해서 수행하는 방법을 저장하는 것**이다. Anthropic이 공개한 실제 업무용 스킬 저장소([anthropics/knowledge-work-plugins](https://github.com/anthropics/knowledge-work-plugins))에서 네 개를 가져왔다.

### 1. `call-prep` — 영업 미팅 준비

**설명**: 고객사 정보, 참석자 조사, 이전 관계와 추천 안건을 바탕으로 영업 미팅을 준비한다. "A사와 미팅 준비해줘", "내일 고객 미팅 대비해줘" 같은 요청에 사용한다.

- 일정에서 회의와 참석자를 확인한다.
- 고객사의 산업·규모·최근 뉴스와 사업 현황을 조사한다.
- 참석자의 직책과 의사결정 역할을 정리한다.
- CRM이 연결되어 있으면 이전 접촉과 영업 기회를 확인한다.
- 이번 미팅의 목표와 예상 질문을 정리한다.
- 대화 주제와 추천 안건을 정해진 형식으로 출력한다.
- 커넥터가 없어도 사용자가 제공한 정보와 웹 조사로 진행한다.

단순 회사 검색과 다른 점은, 여러 출처를 정해진 순서로 조사하고 이를 실제 미팅 전략으로 바꾸는 절차가 있다는 것이다. ([원문](https://github.com/anthropics/knowledge-work-plugins/blob/main/sales/skills/call-prep/SKILL.md))

### 2. `legal-response` — 반복 법무 문의 답변

**설명**: 준비된 템플릿으로 반복적인 법무 문의 답변을 작성하되, 템플릿 답변으로 처리하면 안 되는 상황은 별도로 판별한다. 정보주체 요청, 소송 보존 통지, 협력사 법무 문의, NDA 요청, 소환장 등에 사용한다.

- 문의 종류를 분류한다.
- 회사가 승인한 답변 템플릿을 찾는다.
- 사건에 맞게 이름·날짜·계약 내용 등을 채운다.
- 규제기관·수사기관·소송 위협 같은 위험 신호를 검사한다.
- 위험 신호가 있으면 자동 답변을 중단하고 법무 담당자에게 넘긴다.
- 전송 전에 법무 전문가가 검토해야 한다고 표시한다.
- 답변에 확인되지 않은 법적 판단을 추가하지 않는다.

이 사례는 "메일 초안 작성"도 충분히 좋은 스킬이 될 수 있다는 증거다. 다만 일반적인 메일 작성이 아니라 템플릿·예외 판정·검토와 이관 절차가 포함된 회사 업무라는 게 다르다. ([원문](https://github.com/anthropics/knowledge-work-plugins/blob/main/legal/skills/legal-response/SKILL.md))

### 3. `runbook` — 운영 절차서 작성

**설명**: 반복해서 수행하는 운영 업무의 절차서를 만들거나 수정한다. 담당자가 바뀌어도 실행할 수 있도록 단계별 명령·문제 해결·롤백·비상 연락 절차를 작성할 때 사용한다.

- 작업 목적·담당자·실행 주기를 기록한다.
- 필요한 권한·시스템·입력 자료를 확인한다.
- 각 실행 단계를 정확한 명령이나 행동으로 작성한다.
- 단계마다 정상 결과와 실패 시 조치를 함께 적는다.
- 완료 여부를 확인할 검증 방법을 둔다.
- 문제 증상·가능한 원인·해결 방법을 표준화한다.
- 실패했을 때 되돌리는 방법을 기록한다.
- 직접 해결할 수 없는 상황의 연락·보고 경로를 작성한다.

담당자의 머릿속에만 있던 경험을 누가 실행해도 같은 결과가 나오도록 표준화하는, 전형적인 회사용 스킬이다. ([원문](https://github.com/anthropics/knowledge-work-plugins/blob/main/operations/skills/runbook/SKILL.md))

### 4. `brand-voice-enforcement` — 회사 말투 적용

**설명**: 회사 브랜드 가이드에 맞춰 이메일·제안서·발표 자료·LinkedIn 게시물·Slack 메시지와 영업 콘텐츠를 작성하거나 고친다. "우리 회사 말투로 바꿔줘", "브랜드에 맞게 작성해줘" 같은 요청에 사용한다.

- 현재 대화나 회사 저장소에서 브랜드 가이드를 찾는다.
- 브랜드의 고정된 말투와 상황별 어조를 구분한다.
- 이메일·제안서·게시물 등 결과물 종류에 맞게 적용한다.
- 금지된 표현·과장된 주장·어울리지 않는 말투를 제거한다.
- 작성 후 브랜드 기준을 다시 적용해 검사한다.
- 어떤 브랜드 원칙을 반영했는지 설명한다.
- 가이드를 찾지 못하면 임의로 브랜드 말투를 만들지 않고 사용자에게 확인한다.

이것도 결국 "메일 초안 작성" 스킬이다. 차이는 회사의 고유한 말투와 검사 기준을 반복 적용한다는 것. ([원문](https://github.com/anthropics/knowledge-work-plugins/blob/main/partner-built/brand-voice/skills/brand-voice-enforcement/SKILL.md))

### 스킬로 만들 행동의 특징

1. **반복된다** — 매주, 매월, 또는 비슷한 상황마다 같은 절차를 수행한다.
2. **일반 모델이 모르는 회사 규칙이 있다** — 그 조직만의 템플릿·용어·기준.
3. **여러 단계의 순서가 중요하다.**
4. **출력 형식이 정해져 있다.**
5. **실수 방지 규칙이 있다** — "이 경우엔 자동 처리하지 말고 사람에게 넘겨라" 같은.
6. **검증할 수 있다** — 결과가 맞았는지 확인할 방법이 있다.
7. **템플릿이나 참고 자료를 재사용한다.**

## SKILL.md 구조 — 실제로 무엇이 저장되는가

스킬 하나는 파일 하나(`SKILL.md`)다. YAML frontmatter + 본문 두 부분으로 나뉜다.

```markdown
---
name: pdf-processing
description: PDF 텍스트 추출, 폼 채우기, 여러 PDF 병합. PDF 문서를 다루거나 사용자가 PDF·폼·문서 추출을 언급할 때 사용.
license: MIT
compatibility: pypdf, pdf2image 패키지 필요
allowed-tools: read_file execute
metadata:
  author: juyeon
---

## 절차
1. ...
2. ...
```

명세가 정의하는 필드(공식 명세 원문 기준):

| 필드 | 필수 | 제약 | 용도 |
|---|---|---|---|
| `name` | 필수 | 1~64자, 소문자·숫자·하이픈만, 하이픈으로 시작·끝·연속(`--`) 불가, **폴더명과 일치해야 함** | 스킬 식별자 — 명시적 호출(`/스킬이름`)에도 이 값을 씀 |
| `description` | 필수 | 1~1024자 | **무엇을 하는지 + 언제 쓰는지**를 같이 적어야 함 — 아래 "description 작성법" 참고 |
| `license` | 선택 | — | 라이선스 이름/참조 |
| `compatibility` | 선택 | 1~500자 | 특정 제품·패키지·네트워크 접근이 필요할 때만. **대부분의 스킬엔 필요 없다**(공식 가이드 명시) |
| `allowed-tools` | 선택 | 공백으로 구분한 도구 이름 목록 | 이 스킬이 미리 승인받는 도구(실험적 기능). **키가 하이픈이다** — `allowed_tools`로 쓰면 deepagents 파서가 그 값을 인식하지 못하고 조용히 무시한다(`_parse_skill_metadata`가 `frontmatter_data.get("allowed-tools")`로 실측 확인) |
| `metadata` | 선택 | 임의의 `key: value` 문자열 쌍 | 명세가 정하지 않은 값을 얹는 확장 슬롯. 이 프로젝트는 여기에 `enabled: "true"/"false"`를 얹어 활성화 토글을 구현했다(§7) |

frontmatter 아래 본문은 자유 형식 마크다운 — 실제 절차·예시·주의사항 등, 에이전트가 "이 스킬을 쓰기로 했을 때" 읽을 내용이 전부 여기 들어간다.

**디렉터리 구조도 정해져 있다.** `SKILL.md` 하나만 있어도 되지만, 필요하면 세 종류를 더 둘 수 있다:

| 디렉터리 | 용도 | 로딩 시점 |
|---|---|---|
| `scripts/` | 에이전트가 실행할 수 있는 코드(Python·Bash 등) | 지침이 실행을 지시할 때 |
| `references/` | 상세 참고 문서(`REFERENCE.md`, 도메인별 파일 등) | 지침이 "필요하면 읽어라"라고 안내할 때 |
| `assets/` | 템플릿·이미지·데이터 파일 같은 정적 자원 | 지침이 참조할 때 |

## LLM이 실제로 이 정보를 어떻게 쓰는가 — 3단계(progressive disclosure)

공식 가이드가 정의하는 표를 그대로 옮기면:

| 단계 | 무엇이 로딩되나 | 언제 | 토큰 비용 |
|---|---|---|---|
| 1. 카탈로그 | `name` + `description` | 세션 시작 시, 스킬마다 | 스킬당 약 50~100 토큰 |
| 2. 본문 | `SKILL.md` 전체 | 스킬을 쓰기로 판단한 순간 | 5,000 토큰 이하 권장 |
| 3. 리소스 | `scripts/`·`references/`·`assets/`의 개별 파일 | 본문이 그 파일을 참조할 때 | 파일마다 다름 |

deepagents의 `SkillsMiddleware`가 이 흐름을 그대로 구현한다:

1. **평소(매 모델 호출마다)**: `name` + `description` 목록만 시스템 프롬프트에 문자열로 나열됨. `allowed-tools`가 있으면 그 목록도, 본문은 절대 안 실림. "이 스킬을 쓰려면 `{경로}`를 읽어라"라는 안내가 같이 붙는다.
2. **에이전트가 필요하다고 판단하면**: 목록에서 하나를 고르고, 그 경로를 `read_file`로 직접 연다 — 이 순간에만 본문 전체가 컨텍스트에 들어온다.
3. **그 세션 안에서는 다시 안 읽어도 됨**: 한 번 읽은 본문은 대화 상태(`messages`)에 남아 있으니, 같은 스킬을 또 쓸 일이 있으면 이미 읽은 내용을 그대로 참고한다(다시 `read_file`을 부를 수도 있음 — 강제되진 않음).

이 구조 때문에 스킬 개수가 아무리 늘어도 **상시 비용은 카탈로그 길이에만 비례**하고, 본문 읽기 비용은 실제로 그 스킬을 쓴 턴에만 발생한다. 스킬 20개를 설치해도 20개 본문을 다 미리 읽는 게 아니라, 그 대화에서 실제로 쓰인 것만 읽는다.

### "메타데이터만 읽는다"는 말의 정확한 뜻

세션 시작 시 카탈로그에 실리는 "메타데이터"는 실질적으로 **`name` + `description`**뿐이다(위 표 그대로). SKILL.md의 `metadata:` 필드(이 프로젝트가 `enabled`를 넣는 그 필드)는 다른 층이다 — 세션 시작 시 파일을 파싱할 때 같이 읽히긴 하지만, 모델에게 텍스트로 보여지는 게 아니라 **카탈로그를 만들기 전에 필터링하는 데만** 쓰인다(`SkillVisibilityMiddleware`가 `enabled="false"`인 항목을 먼저 빼고, 남은 것만 카탈로그로 만듦). 즉 "메타데이터"라는 단어가 (1) 카탈로그에 실리는 가벼운 정보라는 일반적 의미와 (2) SKILL.md frontmatter의 `metadata:`라는 구체적 필드 이름, 두 가지로 겹쳐 쓰이니 헷갈리지 않아야 한다.

## description을 어떻게 써야 스킬이 잘 불려오는가

**description이 트리거 전체를 책임진다.** 카탈로그 단계에서 에이전트가 아는 건 이름과 설명뿐이다 — description이 "언제 쓰는지"를 못 전달하면, 본문이 아무리 훌륭해도 그 스킬은 죽은 스킬이다.

### 원칙 (공식 가이드)

| 원칙 | 설명 |
|---|---|
| 명령형으로 쓰기 | "이 스킬은 ~한다"가 아니라 "~할 때 이 스킬을 써라" — 에이전트는 "지금 행동할지 말지"를 판단하는 입장이다 |
| 사용자 의도 중심 | 스킬 내부 구현이 아니라 사용자가 이루려는 것을 묘사 — 에이전트는 사용자가 요청한 내용과 매칭한다 |
| 적극적으로 넓게 | "CSV"나 "분석"이라는 단어를 안 써도 해당하는 상황까지 명시적으로 적어라 |
| 간결하게 | 1024자 제한을 지키되, 문장 몇 개~짧은 단락이면 충분하다 |

**좋은 예 / 나쁜 예** (공식 가이드 원문):

```yaml
# 나쁜 예
description: Helps with PDFs.

# 좋은 예
description: Extracts text and tables from PDF files, fills PDF forms, and
  merges multiple PDFs. Use when working with PDF documents or when the user
  mentions PDFs, forms, or document extraction.
```

**주의할 함정**: 에이전트는 보통 자기 혼자서도 처리 가능한 단순한 한 단계짜리 요청에는 스킬을 안 부른다 — description이 완벽히 맞아도. "이 PDF 읽어줘" 정도는 기본 도구로 끝나 스킬이 안 트리거될 수 있다. description이 진짜 힘을 발휘하는 지점은 **전문 지식·도메인 워크플로우·낯선 형식**처럼, 스킬 없이는 에이전트가 실수하기 쉬운 상황이다.

### 얼마나 정확해야 하나 — 실측 방법론

공식 가이드는 "감으로 쓰지 말고 재보라"고 말한다:

1. **평가 질의 20개를 만든다** — 트리거돼야 하는 질의 8~10개, 트리거되면 안 되는 질의 8~10개.
   - 트리거돼야 하는 쪽: 문체·격식·오타를 섞고, 스킬 도메인을 직접 언급 안 한 것도 포함("CSV 분석해줘"가 아니라 "이 데이터로 팀장한테 보여줄 표 하나 만들어줘").
   - 트리거되면 안 되는 쪽: **니어미스(near-miss)**가 가장 값지다 — 키워드는 겹치지만 실제로 다른 작업. "CSV 분석" 스킬이라면 "엑셀 서식 고쳐줘"(스프레드시트라는 개념은 겹치지만 다른 작업)가 "오늘 날씨 어때"보다 훨씬 유용한 반례다.
2. **각 질의를 3번씩 돌려 트리거율을 잰다** — 모델은 비결정적이라 같은 질의도 매번 다르게 반응할 수 있다. 트리거돼야 하는 질의는 트리거율 0.5 이상, 트리거되면 안 되는 질의는 0.5 미만이면 통과.
3. **train/validation을 나눈다**(6:4) — train 결과로만 description을 고치고, validation으로 "그 개선이 일반화됐는지"를 따로 확인한다. 실패한 질의의 단어를 그대로 넣는 건 과적합이다 — 그 질의가 대표하는 더 넓은 범주를 찾아 고쳐야 한다.
4. **반복**: 트리거 안 되면 범위를 넓히고, 오탐되면 "이 스킬이 하지 않는 것"을 명시해 경계를 좁힌다. 최대 5회 반복.

이 전체 루프는 내장 `skill-creator`가 **스크립트로** 돌린다 — 어떻게 동작하는지, 왜 우리가 이 코드를 그대로 못 쓰는지는 뒤쪽 "공식 skill-creator 방식" 절에서 자세히 다룬다.

## allowed-tools를 지금 쓰면 안 되는 이유

`allowed-tools`는 "이 스킬이 미리 승인받아 쓸 도구 목록"이라는 의도로 만들어진 필드다. 실제로 조사해보니 지금 시점에 이 필드를 쓸 이유가 없다 — 근거 네 가지:

1. **공식 문서 자체가 CLI 전용이라고 명시한다.** Claude Agent SDK 문서: "Agent SDK는 SKILL.md의 `allowed-tools`를 무시한다. CLI용으로 만든 스킬을 SDK 프로젝트로 가져온다면, `ClaudeAgentOptions`(Python)나 `Options`(TypeScript)의 `allowedTools` 파라미터로 도구 제한을 **직접 다시 구현해야 한다.**" — SDK 쪽은 SKILL.md 필드가 아니라 **세션/쿼리 설정값**으로 도구를 제어하는 게 정석이라는 뜻이다.
2. **CLI에서도 실제로 안 먹힌다.** [claude-code#37683](https://github.com/anthropics/claude-code/issues/37683) — `allowed-tools: Read, Write, Glob, Skill`이라고 정확히 적어도 모델이 `Bash`·`Grep`·`Explore` 같은 금지된 도구를 그대로 쓴다는 재현 사례가 있고, "not planned"로 닫혔다. **가장 성숙한 구현체(Claude Code)조차 이 필드를 강제하지 않는다.**
3. **deepagents도 같다.** 앞서 실측한 대로, deepagents는 이 필드를 파싱해서 카탈로그에 "-> Allowed tools: ..."라는 **텍스트 한 줄**로 보여주는 게 전부다. 실제 승인이나 검증은 전혀 없다.
4. **이 프로젝트는 이미 같은 역할을 다른 층에서 하고 있다.** SDK의 `allowedTools`(세션 단위 도구 제한)와 구조적으로 같은 자리를 이 프로젝트는 `agent_versions.tool_refs`(에이전트별 도구 목록)가 이미 맡고 있다. 스킬 안에 도구 이름을 다시 적을 필요가 없다 — 그 에이전트가 어떤 도구를 쓸 수 있는지는 스킬이 아니라 에이전트 정의가 정한다.

**"우리가 도구를 명시해서 있는 도구를 쓰게 하는 방식인 거야?"** — 그렇다면 그건 `allowed-tools`가 아니라 **이미 있는 `agent_version_tools`**가 그 일을 한다. 스킬 쪽에 별도 필드를 만들 이유가 없다.

**"HITL 있는 도구는 HITL을 다 할 수 있는 거지?"** — 그렇다. `allowed-tools`/`allowedTools`는 어느 구현체에서든 "이 도구를 아예 부를 수 있는가"만 결정하지, **이미 걸려 있는 승인 절차를 건너뛰게 하지 않는다.** 이 프로젝트의 side_effect/HITL 게이트(§4-4)는 도구 실행 시점에 독립적으로 걸리는 별개 검사라, 스킬이 어떤 도구를 "추천"해도 승인 카드는 그대로 뜬다.

## SKILL.md 본문은 어떻게 써야 하는가

**본문은 그냥 마크다운 텍스트다.** 특별한 문법이나 시스템 기능이 아니라, 에이전트가 그 스킬을 골랐을 때 그대로 읽는 "설명서"다. 아래 예시 하나로 "재사용 가능한 패턴"이 실제로 뭘 뜻하는지 보여준다:

```markdown
---
name: jira-issue-registration
description: 회의록·요청 메모에서 업무를 뽑아 Jira 이슈로 등록할 때 사용한다.
---

## 절차
1. 입력에서 담당자·기한·업무 내용을 뽑는다.
2. 담당자 이름을 실제 Jira 계정과 대조한다.
3. jira_create_issues로 등록한다.
4. 등록 결과(이슈 번호)를 사용자에게 요약해 돌려준다.

## 출력 형식
| 담당자 | 업무 | 기한 | 이슈 번호 |
|---|---|---|---|

## 주의사항
- 담당자 이름이 회의록엔 "김대리"처럼 직급으로만 나올 수 있다 — 반드시 실제
  계정과 대조한 뒤 등록한다.
- 기한이 없는 업무는 임의로 날짜를 만들지 말고, 등록 전에 사용자에게 물어본다.
```

이 예시 안에 세 가지 패턴이 이미 다 들어 있다 — **"패턴을 쓴다"는 건 별도 기능을 구현하는 게 아니라, 본문에 그냥 이렇게 적어두는 것 자체**다:

| 패턴 | 위 예시에서 어디 | 왜 |
|---|---|---|
| 체크리스트 | `## 절차`의 번호 매긴 단계 | 순서가 있는 다단계 작업에서 단계를 안 건너뛰게 |
| 출력 템플릿 | `## 출력 형식`의 표 | "표로 정리해줘"라고 산문으로 설명하는 것보다 표를 그대로 보여주는 쪽이 훨씬 잘 지켜짐 |
| Gotchas | `## 주의사항` | 상식으로는 못 맞히는, 이 회사만의 함정("김대리"가 실제 계정명이 아니라는 것) |

안 써도 스킬은 동작한다 — 다만 순서·형식·함정을 명시적으로 안 적으면 에이전트가 매번 스스로 판단해서 결과가 들쭉날쭉해질 수 있다는 게 요지다.

### 그 외 작성 원칙

본문이 활성화되면 시스템 프롬프트·대화 이력·다른 활성 스킬과 컨텍스트 창을 나눠 쓴다. 토큰 하나하나가 경쟁 상대가 있다는 뜻이다.

| 원칙 | 설명 |
|---|---|
| 에이전트가 모르는 것만 넣는다 | PDF가 뭔지, HTTP가 뭔지는 설명할 필요 없다. 이 조직만의 관례, 낯선 API, 비직관적인 예외 케이스만 |
| 하나의 일관된 단위로 범위를 잡는다 | 함수 하나가 하나의 일을 하듯 — 너무 좁으면 스킬 여러 개가 동시에 로딩돼야 하고, 너무 넓으면 정확히 트리거되기 어렵다 |
| 적당한 디테일 | 모든 예외를 다 다루려 하지 말 것 — 지나치게 상세하면 관련 없는 지침까지 따라가다 삼천포로 빠진다 |
| 500줄/5,000토큰 이하 | 넘으면 `references/`로 분리하고, 본문에는 "**언제** 그 파일을 읽어야 하는지"를 명시 |

**지시의 강도는 위험도에 맞춘다**: 여러 접근이 다 통하는 작업은 "왜"를 설명하고 자유를 주고, 순서가 정확해야 하는 작업(DB 마이그레이션 등)은 "정확히 이 명령만 실행"처럼 명령적으로 쓴다.

## 실서비스에서는 스킬을 언제 불러오는가

일반적인(공식 가이드가 정의하는) 수명주기와, 이 프로젝트가 실제로 이걸 구현한 지점을 나란히 놓는다.

| 단계 | 공식 가이드가 말하는 일반적 방식 | 이 프로젝트의 실제 구현(§7) |
|---|---|---|
| ① 발견(discovery) | 세션 시작 시 스킬 디렉터리를 스캔해 메타데이터만 읽음 | 세션 첫 턴에 `PostgresStore`에서 내장→개인→팀 순으로 소스를 훑어 이름·설명을 그래프 상태(`skills_metadata`)에 캐싱 |
| ② 카탈로그 공개 | `name`+`description`을 시스템 프롬프트나 전용 도구 설명에 나열 | 매 모델 호출마다 캐싱된 목록을 시스템 프롬프트에 다시 삽입(디스크 재조회 아님) |
| ③ 활성화(activation) | 모델이 필요하다고 판단해 파일을 읽거나 전용 도구를 호출. 사용자가 슬래시 명령으로 직접 지정할 수도 있음 | 암묵적 호출은 모델이 `read_file`로 직접 열람. 명시적 호출(`/스킬이름`)은 `apps/chat/api_views.py`가 정규식으로 파싱해 본문을 직접 모델 입력에 박아 넣음(모델의 판단을 기다리지 않음) |
| ④ 세션 중 갱신 | 명세는 구체적으로 규정 안 함 | `skill_register` 성공 직후 방금 등록한 스킬 하나만 다시 읽어 캐시에 얹는 `SkillRegisterSyncMiddleware` — 같은 세션에서 만든 스킬을 그 세션 안에서 바로 쓸 수 있게 함 |
| ⑤ 컨텍스트 보호 | 컨텍스트 창이 차서 오래된 메시지를 요약·정리(compaction)할 때 스킬 내용은 제외 대상으로 보호해야 함 — 안 그러면 대화 중간에 조용히 지침을 잃음 | 이 프로젝트가 아직 명시적으로 다루지 않는 지점(SummarizationMiddleware §4-5 참고) — 별도 확인 필요 |
| ⑥ 이름 충돌 | 스코프별 우선순위를 정해야 함(보통 "더 좁은 스코프가 이긴다": 프로젝트 > 사용자) | 내장→개인→팀 순으로 병합, **나중 소스가 이긴다** — 팀 스킬이 개인 스킬을 가림(§7). "더 좁은 스코프가 이긴다"는 업계 관례와 **반대 방향**이라는 점을 알아 둘 필요가 있다 |
| ⑦ 필터링 | 비활성화·권한 없는 스킬은 카탈로그에서 아예 숨겨야 함(활성화 시점에 막는 게 아니라) | `SkillVisibilityMiddleware`가 `metadata.enabled="false"`인 스킬을 카탈로그 자체에서 제외(§7) |

## 공식 skill-creator 방식

내장 `skill-creator`([anthropics/skills](https://github.com/anthropics/skills)의 `skill-creator`)는 순수 프롬프트가 아니다 — 스킬 디렉터리 안에 **실행 가능한 스크립트를 같이 들고 다닌다**:

| 파일 | 역할 |
|---|---|
| `run_loop.py` | 전체 반복 루프를 돌리는 진입점 |
| `run_eval.py` | 질의 하나를 실제로 실행해 스킬이 트리거됐는지 판정 |
| `improve_description.py` | 실패 결과를 보고 새 description 후보를 LLM으로 생성 |
| `aggregate_benchmark.py` | 여러 실행 결과를 통계로 집계 |
| `generate_report.py` | 브라우저에서 보는 HTML 리포트 생성 |
| `package_skill.py` | 완성된 스킬을 `.skill` 파일로 패키징 |
| `quick_validate.py` | frontmatter 형식만 빠르게 검증 |

**루프 동작 방식** (`run_loop.py` 실측):

1. `--max-iterations`(기본 5)까지 반복한다.
2. 매 반복마다 train 세트를 실행하고, **train 실패 건수가 0이면 즉시 종료**(`exit_reason = "all_passed"`), 아니면 다음 반복으로.
3. 반복이 끝나도(5회 다 써도) 실패가 남아 있으면 그냥 **거기서 멈춘다** — "목표 점수 미달이라 등록을 거부"하는 로직은 없다. 마지막까지 나온 후보 중 가장 나은 걸 결과로 낼 뿐이다.

**"점수가 낮으면 어떻게 되나 — 프롬프트를 알아서 고치나?"** — 부분적으로는 그렇다:

- `improve_description.py`가 실패 질의를 "놓친 것"(트리거됐어야 하는데 안 됨)과 "오발동"(트리거되면 안 되는데 됨) 두 종류로 나누고, 이걸 근거로 **Claude에게 새 description을 만들어 달라고 요청**한다. 이때 "실패 사례 단어를 그대로 넣지 말고, 더 넓은 범주로 일반화하라"는 지시가 같이 들어간다.
- 하지만 **이 스크립트는 SKILL.md를 직접 고치지 않는다.** 새 description 후보를 JSON으로만 돌려주고, 그걸 실제로 적용할지는 **사람이 결정**한다. 자동화된 건 "분석해서 더 나은 후보를 제안하는 것"까지고, "파일에 반영하는 것"은 항상 사람 몫이다.

즉 "점수가 낮아서 등록을 못 한다"는 일은 없다 — 이 평가는 애초에 **등록의 필수 관문이 아니라, 등록한 뒤(또는 등록 전) 선택적으로 돌리는 품질 개선 루프**다.

## 우리 프로젝트에 이 방식을 그대로 가져올 수 있는가

**결론: 알고리즘(반복 개선 절차)은 가져올 수 있지만, 코드는 그대로 못 돌린다.** 세 가지가 이 프로젝트의 실제 구조와 안 맞는다:

| 걸림돌 | 내용 |
|---|---|
| `claude -p` 의존 | `run_eval.py`는 Claude Code CLI 바이너리를 서브프로세스로 직접 부른다(`claude -p "$query" --output-format json`). 우리는 Claude Code가 아니라 우리 자신의 deep agent 런타임이라, 이 명령 자체가 존재하지 않는다 |
| 트리거 판정 방식 | 공식 스크립트는 Claude Code의 JSON 출력에서 `tool_use`가 `Skill`이라는 이름의 도구를 불렀는지로 판정한다. 우리 이벤트 스트림엔 그런 이름의 도구가 없다 — 지금 우리가 확실히 잡을 수 있는 신호는 명시 호출(`/스킬이름`)의 `skill_applied` 이벤트뿐이고, 암묵적 호출(모델이 스스로 `read_file`)은 신호가 깨끗하지 않다(앞서 논의한 것과 같은 지점 — `read_file`은 스킬 파일이든 다른 파일이든 똑같이 쓰이는 범용 도구라서) |
| 파일 위치 | 공식 스크립트는 로컬 파일시스템의 `SKILL.md` 경로를 그대로 다룬다. 우리 스킬은 Postgres Store 안 가상 경로다 — 스크립트가 그 자리에서 바로 못 연다 |

**포팅하려면 실제로 필요한 것**:
1. `claude -p` 대신 우리 `executor.run()`(또는 그에 준하는 실행 경로)을 여러 번 호출하는 우리 자신의 러너.
2. `Skill` 도구 이름 매칭 대신, `read_file` 호출의 경로가 그 스킬 경로와 일치하는지 보거나 — 더 깨끗하게 하려면 이전에 논의한 대로 **전용 `activate_skill` 도구를 새로 만들어** 그 호출만 세는 방식(공식 구현 가이드가 권장하는 패턴과 같다, "이건 스킬 트리거였다"고 코드로 분류하려면 결국 이 결정이 먼저 필요하다).
3. `SKILL.md`를 로컬 파일로 열고 닫는 대신, `services/agent_runtime/skills/service.py`의 조회·수정 함수를 쓰도록 스크립트 로직을 바꾸기.

지금 규모(팀 스킬 몇 개)에서 이 인프라 전체를 갖출 필요가 있는지는 별개 판단이지만, "공식 코드를 그대로 쓸 수 있는가"의 답은 명확히 **아니오**다 — 셋 다 이 프로젝트 아키텍처와 정면으로 다르다.

## Child(서브에이전트)도 스킬을 알아야 하지 않나 — 나중에 할 거다

**지금 상태**: 이 프로젝트의 Root는 스킬을 받지만, Child(1단계 위임 대상)는 못 받는다(§4-8). deepagents 자체는 서브에이전트 spec에 `skills=`를 주면 스킬을 넘겨줄 수 있게 **이미 지원한다**(GP가 실제로 이 경로로 스킬을 받는다) — Child가 못 받는 건 이 프로젝트의 `create_child_graph()` 래퍼 함수가 그 파라미터를 아예 안 받게 만들어 둔 의도적 설계다.

**왜 문제가 될 수 있는가(사용자 판단)**: 스킬 본문에 "주석 쓰지 마라", "컨텍스트를 짧게 유지해라" 같은 지침이 있으면, 그 지침을 아는 건 Root뿐이다. Root가 Child에게 위임할 때 넘기는 건 위임 설명문 한 문장뿐이라(§5), Child는 그 스킬의 존재 자체를 모른 채 작업하고 — 스킬이 명시적으로 금지한 걸 그대로 저지를 수 있다. Root가 위임 설명문에 스킬 내용을 매번 옮겨 적어야 하는데, 그걸 강제하는 코드는 없다(§4-8에서 이미 확인한 지점).

**공식 생태계도 이 패턴을 인식하고 있다.** `agentskills.io`의 구현 가이드는 "서브에이전트 위임(subagent delegation)"을 명시적으로 다룬다 — "일부 클라이언트만 지원하는 고급 패턴"으로 분류하며, "스킬 지침을 메인 대화에 주입하는 대신, 스킬을 별도의 서브에이전트 세션에서 실행하고 그 서브에이전트가 작업 결과 요약만 메인 대화로 돌려준다"고 설명한다. 즉 "Child도 스킬을 알아야 한다"는 요구는 이 프로젝트만의 특수한 사정이 아니라, 표준 자체가 알고 있는 미해결 설계 공간이다.

1. deepagents가 이미 지원하는 경로를 그대로 쓴다 — `create_child_graph()`가 `skills=`를 받아 그대로 전달하게 고침(GP와 같은 방식).
2. 서브에이전트 위임 패턴처럼, Root가 위임 시점에 관련 스킬 본문을 스스로 추려 위임 설명문에 포함시키도록 프롬프트로 유도한다(코드 변경 없음, 신뢰도는 낮음).
