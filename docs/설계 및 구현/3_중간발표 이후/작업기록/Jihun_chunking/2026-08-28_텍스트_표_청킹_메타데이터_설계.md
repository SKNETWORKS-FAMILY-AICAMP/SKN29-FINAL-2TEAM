# 텍스트·표 청킹 메타데이터 설계

> 인계서(`docling_document_serialization_chunking_handoff_spec.md`)의 팀 결정 목록(D-01~D-12) 중
> 텍스트·표 트랙(① 청커/토크나이저, ② 표 표현)을 다룬다. 그림 트랙(D-05~D-08)은 범위 밖이다.

## 1. 배경

파싱(Docling 변환)은 이미 프로덕션에서 안정적으로 돈다. 이 문서는 "파싱 결과를 어떻게
청크로 자르고, 청크에 어떤 정보를 붙일지"만 다룬다. 파싱 자체(OCR, 보강, 헤딩 승격 등)는
`runpod_worker/pipeline.py`에 이미 구현되어 있고 이 문서의 대상이 아니다.

## 2. 전제

- 파싱 결과(DoclingDocument)는 안정적으로 나온다고 가정한다 — 파싱 담당 확인 완료.
- `blocks[].heading_path`는 현재 파싱 단계에서 채워지도록 구현되어 있다고 가정한다
  (기존 `runpod_worker/pipeline.py`의 플레이스홀더는 파싱 쪽에서 해소하기로 확인됨).
- 표 셀에 `row_header`/`column_header` 표시가 하나도 없는 표는 파싱 단계에서 걸러지고
  청킹으로 넘어오지 않는다 — 청킹 쪽에서 안전장치(fallback)를 따로 만들 필요가 없다.
- 대표 문서 기반 실측 검색 품질 평가(recall/precision)는 이 설계의 범위가 아니다.
  DoclingDocument 구조와 임베딩 원리에 근거한 구조적 설계이며, 실측 검증은 대표 문서
  코퍼스가 마련된 뒤 별도로 진행한다.

## 3. 저장 구조 원칙

청크 관련 데이터는 세 테이블에 나눠 저장한다(`DB/schema.sql`에 이미 존재).

| 테이블 | 역할 |
|---|---|
| `doc_block` | 원문 구조·위치 (페이지, heading_path, 원본 내용, 표 구조 원본) |
| `chunk` | 검색용 문장, 순서, 토큰 수, 청커 버전 |
| `vec_idx` | **오직 `chunk_id` + 임베딩 벡터 + (필요한 경우) 검색 필터용 최소 메타데이터** |

**벡터 인덱스에는 최소한만 둔다.** 근거: `backend/db/document_pipeline.py:1069`의 실제 주석 —
과거 `vec_idx.metadata`에 bbox·binary_hash 등을 다 넣었다가, 평균 927자·최대 7,622자로
불어났는데 검색 코드도 화면도 그 값을 쓰지 않아 2026-08-05에 읽는 쪽 코드에서 제외했다.
검색은 `vec_idx`에서 유사도로 `chunk_id`를 찾은 뒤 `chunk` → `doc_block`을 join해서
원문·근거를 가져오는 흐름이며, 이 흐름은 이미 `backend/db/repositories.py`에 구현되어 있다.

이번 설계도 같은 실수를 반복하지 않는다 — 아래 메타데이터는 전부 `chunk`/`doc_block`에
저장하고, `vec_idx`에는 `chunk_id`와 임베딩 외에 새로 추가하지 않는다.

## 4. 임베딩되는 문자열과 메타데이터의 구분

**임베딩 모델에 들어가는 것은 청크의 `text`(또는 `contextualized` 버전) 문자열 하나뿐이다.**
나머지 메타데이터는 임베딩에 영향을 주지 않고, 검색 결과를 보여줄 때(출처·근거)만 쓰인다.
단, 제목·캡션처럼 `text` 안에 실제로 섞어 넣기로 정한 것은 예외적으로 임베딩에 영향을 준다
(Anthropic의 Contextual Retrieval과 같은 원리 — 문맥을 문장에 미리 녹여 검색 정확도를 높임).

원칙: 문서 안에 실제로 존재하는 의미 있는 문맥(제목)은 임베딩 문자열에 섞고, 파서가
내부적으로 판단한 처리 방식 라벨(orientation 등)은 절대 섞지 않는다 — 후자를 섞으면
내용이 다른 청크끼리 형태만 같다는 이유로 벡터가 가까워지는 부작용이 생긴다.

## 5. 공통 메타데이터 (텍스트+표 공통)

| 항목 | 내용 | 저장 위치 |
|---|---|---|
| `chunk_id` | 청크 고유 번호 | `chunk.chunk_id` |
| `chunk_type` | "text" 또는 "table" | 컬럼 없음 — `doc_block.block_type`으로 판단 |
| `doc_item_refs` | 원본 문서 위치(self_ref) | `doc_block.src_locator` |
| `headings` | 제목 경로 | `chunk.heading_path` |
| `page_nos` | 페이지 번호 | `doc_block.page` |
| `token_count` | 토큰 수 | `chunk.token_cnt` |
| `sequence` | 문서 내 읽기 순서 | `chunk.chunk_idx` |
| `chunker_profile` | 청커 버전 이름표 | `chunk.chunker_ver` |

## 6. 텍스트 청크

### 6.1 임베딩 문자열

이미 구현되어 있다. `runpod_worker/pipeline.py`의 `hybrid.contextualize()`가 제목 경로를
문장에 녹여 `chunks[].text`를 만든다. 제목 안 붙은 원본은 `chunks[].raw_text`로 별도 보존한다
— 두 값을 하나로 합치지 않는다(인계서 11장 원칙과 일치, 나중에 어느 쪽이 검색에 더
유리한지 실측 비교할 여지를 남긴다).

텍스트 청크는 이번 설계에서 추가로 바꿀 것이 없다 — 기존 구현을 그대로 채택한다.

## 7. 표 청크

표는 텍스트와 다르게 취급해야 한다. 텍스트는 이미 제목이 문장에 녹아 있지만, 표는
셀 값만으로 문장을 만들고 제목·문맥이 전혀 안 들어간다.

### 7.1 표 직렬화 방식 판단 (3종)

기존 구현(`_product_records`/`_generic_row_records`)은 "Model"이라는 열 이름 텍스트가
있는지로만 판단했다. 이를 Docling이 표 셀마다 이미 부여하는 `row_header`/`column_header`
표시 기반 판단으로 교체한다 — 특정 단어에 의존하지 않고 표 구조 자체로 판단하므로 더
일반적이다.

**판단 절차:**

1. 표의 모든 `table_cells`를 본다.
2. `column_header = true`인 셀이 있는 행이 있는가? (통상 위쪽)
3. `row_header = true`인 셀이 있는 열이 있는가? (통상 왼쪽)

**결과 분류:**

| 열 헤더 | 행 헤더 | 표 종류 | 레코드 단위 | 라벨 출처 |
|---|---|---|---|---|
| ✅ | ❌ | 일반 표 | 행 하나 = 문장 하나 | 열 헤더 텍스트 |
| ❌ | ✅ | 항목-값 표 | 행 하나 = 문장 하나 | 그 행의 행 헤더 텍스트 하나 |
| ✅ | ✅ | 교차표(제품비교표 등) | 칸 하나 = 문장 하나 | 행 헤더 + 열 헤더 (진짜 트리플렛) |
| ❌ | ❌ | (해당 없음) | — | 파싱 단계에서 이미 걸러짐 — 청킹 단계에서 처리하지 않음 |

3종 모두 특정 열 이름 문자열에 의존하지 않으므로, "Model"이 아닌 다른 이름의 표도
동일하게 처리된다.

**헤더가 한쪽만 있을 때의 축소 규칙:** 원래 (행이름, 열이름, 값) 3요소가 다 있어야 완전한
문장이 나오는데, 한쪽 헤더가 없으면 그 축의 이름을 **지어내지 않는다.**

- 열 헤더만 있는 표(케이스 A): 각 값에 열 헤더 라벨을 붙여 한 행에 여러 개 나열.
  `"업무명: 설계 / 담당자: 김OO / 기한: 9/10"`
- 행 헤더만 있는 표(케이스 B): 라벨은 그 행의 행 헤더 텍스트 하나뿐이다. 값이 하나면
  `"사업명: OO 시스템 구축"`처럼 깔끔한 pair가 되고, 라벨 없는 값 열이 여러 개면 가짜
  열 이름(`"1번째 값"` 등)을 만들지 않고 같은 라벨 아래 값만 나열한다:
  `"매출: 500, 600, 700"`.

### 7.2 표 임베딩 문자열에 추가할 것

**제목 경로(headings)만 추가한다.** 캡션은 추가하지 않기로 확정했다 — 표 자체에 이미
열/행 이름이 라벨로 붙어 있어 캡션 없이도 최소한의 문맥이 확보된다고 판단.

예: 기존 "제품 모델: X / 가격: 10만원" → "{제목 경로} / 제품 모델: X / 가격: 10만원"

### 7.3 표 전용 메타데이터 (payload)

텍스트 청크에는 없고 표 청크에만 있는 정보. 임베딩 문자열에는 포함하지 않는다 — 파서가
내부적으로 판단한 처리 방식 라벨이라 문서 내용이 아니기 때문(4장 원칙).

| 항목 | 내용 | 저장 위치 |
|---|---|---|
| `attributes` | 행/열/셀 구조화 값 (원본 표 데이터, 폐기하지 않음) | `doc_block.struct_content` |
| `table_ref` | 원본 표 위치 | `doc_block.src_locator` |
| `orientation` | 7.1에서 판단한 표 종류 (디버깅·품질 확인용) | **⚠️ 현재 저장할 컬럼 없음 — 8장 참고** |

## 8. 이번 설계에서 다루지 않은 것 / 후속 과제

- **그림(picture) 트랙** — 인계서 D-05~D-08. 이번 범위에서 제외.
- **`orientation` 저장용 컬럼** — `doc_block` 또는 `chunk`에 새 컬럼 추가가 필요하다.
  지금 `ingest()`(`backend/db/document_pipeline.py`)는 이 값을 어디에도 쓰지 않고,
  유일하게 닿는 `vec_idx.metadata`는 실제로 안 읽히는 자리라 사실상 유실된다. DB
  마이그레이션과 `ingest()` 수정이 별도 작업으로 필요하다.
- **LLM 기반 표 직렬화** — 대안으로 검토했다(표마다 LLM에 자연어 설명을 맡기는 방식,
  row/column header 판단 규칙 자체가 필요 없어짐). 이번엔 비용·속도 이유로 규칙 기반을
  채택했다. 규칙 기반으로 커버 안 되는 표가 실제로 많이 발견되면 재검토 대상.
  참고: 이 대안이 필요 없는 이유는 대형 LLM의 문서 이해가 표를 이미지로 직접 읽고
  이해하는 방식(비전 기반)이라 별도 구조 판별이 필요 없기 때문이고, 우리 파이프라인은
  사전에 검색용 텍스트를 만들어 벡터DB에 저장해야 하는 제약이 있어 사정이 다르다.
- **검색 품질 실측(recall/precision)** — 대표 문서 코퍼스(`tests/eval/documents/`
  재활용 여부 포함)와 질문-정답 세트가 마련된 뒤 별도로 진행한다. 이번 설계는 구조적
  근거로만 판단했다.
- **`vec_idx.metadata`의 죽은 INSERT** — `backend/db/document_pipeline.py:600-606`이
  안 읽히는 값(doc_id, source_refs, pages, chunk_type, chunk_meta)을 여전히 쓰고 있다.
  이번 설계 범위는 아니지만 정리 대상으로 남겨둔다.
