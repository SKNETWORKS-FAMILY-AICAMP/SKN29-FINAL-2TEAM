## 1. (2026-08-19 이전 설계, 이제 무효) 기본 챗 에이전트는 개인 메모리만, Builder로 만들어 공유한 에이전트는 지금처럼 공유+개인

### 왜 지금 구조에서 실제로 문제가 되는지

`agents` 테이블에 `is_default_chat`(팀당 정확히 1개, `agents_one_default_chat_per_team`
유니크 인덱스로 강제)이 이미 있다. 이 하나의 `agent_id`를 **팀원 전체가 같이
쓴다** — Builder로 만들어 공유한 에이전트는 팀장이 의도적으로 만들고 활성화한
것이지만, 기본 챗 에이전트는 아무도 그렇게 결정한 적 없이 모두가 기본값으로
같이 쓰는 대화 상대다.

지금 공유 메모리(`/memories/AGENTS.md`)의 namespace는 `(team_id, agent_id)`다
(`build_memory_backend()`). 팀원 A가 기본 챗 에이전트에게 "항상 이렇게
대답해"라고 말하면 그 내용이 이 namespace에 저장되고, **같은 팀원 B가 전혀
다른 대화를 시작해도 그 파일이 매 턴 시스템 프롬프트에 자동 주입된다**(`memory_paths()`
가 `AGENTS.md`를 항상 포함). 본인이 동의하거나 요청한 적 없는 내용이 남의
한마디로 자기 대화에 끼어드는 구조다. Builder로 만든 팀 공유 에이전트는
`agent_id`가 그 에이전트만의 것이라 이런 문제가 없다 — 기본 챗 에이전트만
"팀당 1개를 전원이 공유"하는 특수한 경우라 이 문제가 생긴다.

### 설계

`AgentDefinition`에 `is_default_chat: bool = False` 필드를 추가하고, DB
SELECT 한 줄(`AgentVersionRepository.get_definition()`, 이미 `agents`를
JOIN하고 있어 `a.is_default_chat` 컬럼만 추가하면 된다)로 채운다.

`memory/backend.py`의 `build_memory_backend()`와 `memory_paths()`에
`include_shared: bool = True`를 추가한다.

```python
def build_memory_backend(*, team_id, agent_id, account_id, include_shared=True):
    routes = {MEMORY_USERS_PATH_PREFIX: StoreBackend(namespace=_personal_namespace)}
    if include_shared:
        routes[MEMORY_PATH_PREFIX] = StoreBackend(namespace=_shared_namespace)
    return CompositeBackend(default=StateBackend(), routes=routes)

def memory_paths(*, include_shared=True) -> list[str]:
    return [MEMORY_FILE] if include_shared else []
```

`factory.py`의 `build()`가 `root_kwargs`를 채우는 자리에서
`include_shared = not definition.is_default_chat`을 계산해 두 함수 모두에
넘긴다. `include_shared=False`면 `/memories/AGENTS.md` 경로는 그냥
`CompositeBackend.default`(휘발성 `StateBackend`)로 떨어진다 — 모델이
실수로 그 경로에 뭘 써도 이번 대화 안에서만 존재하고 다음 대화엔 안 남는다.
에러를 낼 필요도, 새 예외를 만들 필요도 없다.

**같이 고쳐야 하는 것**: `_MEMORY_ROUTING_PROMPT`가 지금은 "팀 규칙은
AGENTS.md에 써라"라고 무조건 안내한다 — 기본 챗 에이전트에게는 이 안내가
거짓말이 된다(써도 안 남으니까). `memory_system_prompt()`에도 같은
`include_shared` 플래그를 받아, `False`면 라우팅 안내에서 "공유(AGENTS.md)"
항목을 빼고 "개인(preferences.md)"만 남긴 문구를 반환하게 해야 한다.

## 2. 메모리 쓰기 내용 방어 — "금칙어를 막는다"가 아니라 "저장 가능한 정보의 종류를 좁힌다"

### 2026-08-19 재작성 — 왜 "단어 목록으로 막는다"는 틀을 버렸는가

원래 설계(아래 옛 버전 참고)는 방어를 "패턴 뚜렷한 것(규칙 기반)"과 "패턴
안 뚜렷한 것(단어 목록 기반)" 두 층으로 나누고, 후자에 "관리자 비밀번호"·
"루트 계정" 같은 보안 민감 **문구**를 키워드로 막는 안을 넣었다. 이 부분이
잘못됐다는 지적을 받아들인다 — 예를 들어 모델이

> "이 사용자는 관리자 권한을 가지고 있다."

를 쓰려는 상황을 생각해 보면, 이게 (a) 사용자가 실제로 그렇게 말해서 적는
건지 (b) 대화 맥락을 모델이 잘못 추론해서 지어낸 건지, 코드가 문자열만
보고는 구분할 수 없다. 이건 "위험한 단어가 들어갔는가"의 문제가 아니라
"이게 애초에 사실인가, 그리고 이 사용자에 대해 항상 참인가"의 문제다 —
문자열 패턴 검사로 풀 수 있는 질문이 아니다.

그래서 틀 자체를 바꾼다. **"금칙어가 있으면 막는다"가 아니라 "애초에
저장해도 되는 정보의 종류가 아니면 막는다"**를 기준으로 삼는다. 이렇게
분류를 좁히면, "관리자 권한을 가지고 있다"는 문장은 금칙어가 있어서
막히는 게 아니라 애초에 "권한/보안 관련 사실"이라는, 사실 여부와
무관하게 개인 장기 메모리(`preferences.md`)에 들어갈 자격이 없는
카테고리라서 막힌다 — 그 문장이 참인지 거짓인지 판단하려 들지 않는다는
점이 핵심이다(참이어도 막는다).

### 카테고리별 처리 — 코드로 강제 가능한 것과 프롬프트에만 맡길 수밖에 없는 것

| 카테고리 | 예시 | 처리 | 강제 위치 |
|---|---|---|---|
| credential/secret | API 키, 비밀번호, 토큰 | 차단 | 코드 (`write_guard`, 정규식) |
| 개인정보 | 주민등록번호, 카드번호, 전화번호 패턴 | 차단 | 코드 (`write_guard`, 정규식) |
| 권한/보안 관련 사실 | "관리자 권한이 있다", "루트 계정을 쓴다", "내부 접속 정보는 X다" | 보수적으로 차단(사실 여부 안 따짐) | 코드 (`write_guard`, 키워드 — 카테고리 전체를 막음) |
| 모델이 추론한 사실 | 사용자가 직접 말하지 않았는데 대화 흐름으로 모델이 짐작한 것 | 저장 금지 | 프롬프트만 (`_MEMORY_ROUTING_PROMPT`) |
| 단순 대화 내용 | 지나가는 잡담, 저장 의도 없는 말 | 저장 금지 | 프롬프트만 (`_MEMORY_ROUTING_PROMPT`) |
| 프로젝트 한정 사실/1회성 결과 | "이번 프로젝트는 DB를 쓴다", "지난번엔 A로 처리했다" | 저장 금지 | 프롬프트만 (`_MEMORY_ROUTING_PROMPT`) |
| 지속적 개인 선호·작업 습관 | "한국어로 답해줘", "짧게 답하는 걸 선호한다" | 저장 허용 | — |

**정직하게 나눠야 하는 지점**: 앞 세 줄(credential/secret, 개인정보,
권한·보안 관련 사실)은 문자열 패턴·키워드로 code-level에서 실제로 걸러낼
수 있다 — 값의 **형태**(API 키 형식, 주민번호 자릿수, "권한"·"계정"·
"접속 정보" 같은 단어)만 보면 되지, 그 내용이 참인지 거짓인지 판단할
필요가 없기 때문이다. 반대로 뒤 세 줄(모델이 추론한 사실, 단순 대화 내용,
프로젝트 한정 사실)은 **판단의 대상이 문자열의 형태가 아니라 그 문장이
생겨난 맥락**이다 — "이 문장을 사용자가 직접 말했는지, 모델이 지어냈는지",
"이게 이 프로젝트에만 해당하는 얘기인지, 이 사용자에 대해 항상 참인지"는
정규식이 답할 수 있는 질문이 아니라, 그 순간 대화를 보고 있는 모델
자신만 답할 수 있는 질문이다. 그래서 이 세 줄은 `write_guard`(도구 실행을
가로채는 코드)가 아니라 `_MEMORY_ROUTING_PROMPT`(모델에게 쓰기 전에
스스로 판단하게 하는 지시문)의 몫으로 남긴다 — 이미
`services/agent_runtime/memory/backend.py`의 `_MEMORY_ROUTING_PROMPT`를
"이 사용자에 대해 프로젝트와 무관하게 항상 참인가"를 직접 묻는 형태로
다시 써서 반영했다(코드 반영·테스트 완료, 정본:
`2026-08-19_03_장기메모리_개인전용_최종구조.md` §7-8). **한계를 숨기지
않는다**: 이 프롬프트 지침은 모델이 오판할 가능성을 완전히 없애지
못한다 — 코드가 강제할 수 없는 영역이라는 뜻이지, 코드 방어로는 도달할
수 없다는 걸 인정하고 가는 것이다.

### 설계 — `write_file`/`edit_file`을 감싸는 새 검사 미들웨어 (앞 세 카테고리만 담당)

`middleware/factory.py`가 이미 커스텀 미들웨어를 조립하는 자리이니 같은
패턴으로 새 미들웨어를 하나 추가한다(`memory/write_guard.py` 정도의 새 파일
— path가 `/memories/users/`로 시작하는 `write_file`/`edit_file` 호출만
대상으로 하므로 범용 `middleware/`가 아니라 `memory/` 패키지에 두는 게
책임 분리에 맞다. 팀 공유 경로는 2026-08-19 결정으로 이제 없다). 훅은
`wrap_tool_call`(`ToolRetryMiddleware`가 같은 훅으로 도구 실행을 감싸는
것과 같은 자리) — 실제 handler를 부르기 **전에** 인자(`content` 또는
`new_string`)를 검사하고, 걸리면 실행 자체를 안 하고 거부 사유를 담은
`ToolMessage(status="error")`를 돌려준다. 모델이 그 사유를 보고 다시 시도할
기회는 남긴다(완전히 죽이지 않음 — `_run()`이 다른 예외를 처리하는 것과 같은
철학).

**검사 내용 — 코드로 강제 가능한 세 카테고리만, 형태 기준으로 판단한다.**

1. **credential/secret**: API 키/토큰 형태(`sk-[A-Za-z0-9]{20,}`류),
   `password\s*[:=]`, 흔한 시크릿 변수명(`AWS_SECRET`, `DB_PASSWORD` 등)
   뒤에 실제 값이 붙은 경우 — 값의 형태만으로 신뢰성 있게 잡힌다.
2. **개인정보**: 주민등록번호·카드번호 등 자릿수·형식이 고정된 패턴.
3. **권한/보안 관련 사실**: "관리자 권한"/"루트 계정"/"내부 접속 정보"
   같은 단어가 포함된 문장은 **그 문장이 사실인지 여부와 무관하게** 통째로
   막는다 — 이 카테고리는 애초에 참/거짓을 가리는 게 목적이 아니라, "이런
   종류의 사실은 개인 장기 메모리에 안 남긴다"는 정책이기 때문이다. 위
   두 줄보다 오탐이 늘어날 수 있다는 걸 인정한다(예: 사용자가 자기소개
   삼아 "저는 이 시스템 관리자입니다"라고 한 것도 걸릴 수 있음) — 그래도
   "권한 관련 서술은 아예 개인 메모리에 안 남기고, 필요하면 실제 권한
   테이블을 조회한다"는 게 더 안전한 기본값이라고 본다.

**모델이 추론한 사실 / 단순 대화 내용 / 프로젝트 한정 사실은 이 미들웨어의
검사 대상이 아니다** — 위에서 밝혔듯 문자열 형태로 판단할 수 없는
카테고리라서, `write_guard`에 억지로 이런 걸 잡으려는 규칙(예: "이건
추측성 표현이다" 같은 패턴)을 넣지 않는다. 억지로 넣으면 오탐만 늘고
실제로는 못 잡는다 — 차라리 이 부분은 프롬프트의 몫으로 명확히 남기고,
코드 쪽 책임 범위를 정직하게 좁히는 쪽을 택한다.

**적용 범위**: `/memories/users/`(이제 유일한 장기 메모리 경로)로 시작하는
`write_file`/`edit_file`에만 건다 — 그 외 파일(스크래치 공간, `StateBackend`로
떨어지는 경로)에는 이 검사가 필요 없다.

**같이 정해야 하는 것**: 걸렸을 때 그 사실을 사용자에게도 보여줄지(예: "이
내용은 저장하지 않았습니다" 같은 안내를 응답에 포함시킬지) — 이건
UI/제품 결정이라 이 문서에서 미리 정하지 않는다.

이 설계는 아직 코드에 반영하지 않았다(`write_guard.py` 자체가 미착수).
실제 `deepagents`/`langchain` 설치 소스로 검증한 코드 반영 직전 단계의
구체적 설계(정확한 클래스·함수 시그니처, 정규식/키워드 목록, `factory.py`
배선 지점, 테스트 계획)는 `2026-08-19_04_write_guard_구현설계.md` 참고.

## 3. (2026-08-19 이전 설계, 이제 무효) "팀 공용 프롬프트를 아예 없애자"는 판단에 대해 — 없애지 말고, 쓸 수 있는 사람을 제한해야 한다

### 결론

팀원 아무나의 "우리 팀은 앞으로 이렇게 할 거야"가 다른 팀원 전체에게 무조건
적용되는 지금 구조는 잘못됐다는 데 동의한다. 하지만 그 해결책이 "팀 공용
메모리 자체를 없앤다"는 아니라고 본다 — 문제는 **공유 메모리가 존재한다는
것**이 아니라 **누구나 그걸 쓸 수 있다는 것**이다. 이 둘을 구분해야 한다.

### 왜 완전히 없애면 안 되는가

팀 공용 메모리는 `AGENTS.md`만이 아니라 Builder로 팀장이 의도적으로 만들어
공유한 에이전트의 존재 이유이기도 하다(`2026-08-18_01` §4 — 팀장이 활성화를
결정한 순간부터 "팀 소관"이 되는 게 이미 이 프로젝트의 기존 설계다). 팀
규칙·컨벤션을 에이전트가 기억해서 매번 안내하는 건 실무 도구로서 실제로
가치가 있는 기능이다 — 그 가치까지 같이 버리는 건 과한 대응이라고 본다.
1번에서 다룬 기본 챗 에이전트 문제는 "팀장이 결정한 적 없는 공유"라서
생기는 문제였지, "공유 자체"가 문제는 아니었다.

### 실제 서비스는 이 문제를 "누가 쓸 수 있는가"로 푼다

GitHub Copilot의 저장소 커스텀 지시사항(`.github/copilot-instructions.md`)을
확인해 보면, 이 파일은 저장소에 병합되는 즉시 그 저장소의 **모든** 협업자에게
적용된다 — 즉 공유 자체는 아무 제약 없이 강력하게 동작한다. 대신 "누가 그
파일을 바꿀 수 있는가"는 일반 코드와 똑같은 권한·PR 리뷰 절차를 그대로
따른다(GitHub Docs, "Adding repository custom instructions for GitHub
Copilot"). 즉 "아무나 한마디로 전체 팀 규칙을 바꿀 수 있다"가 아니라
"그 저장소에 커밋할 권한이 있는 사람만" 바꿀 수 있다 — 공유는 강력하게,
쓰기는 기존 권한 체계로 제한하는 조합이다.

ChatGPT Enterprise 쪽은 workspace 설정 전반이 "모든 역할이 볼 수는 있지만
소유자·관리자만 핵심 설정을 바꿀 수 있다"는 원칙(OpenAI Help Center,
"Managing workspace settings in ChatGPT Enterprise")까지는 확인했지만, custom
instructions 자체에 대한 세부 권한 문서는 이번 조회로 확정하지 못했다 — 이
부분은 확정된 근거로 주장하지 않는다.

### 이 코드베이스에는 이미 정확히 이 목적의 장치가 있다 — 그런데 메모리 쓰기에는 안 걸려 있다

`runtime_policy.py`의 `RuntimeCapabilityPolicy`에 이미
`write_tool_allowed_roles: frozenset[AccountRole] = {"leader"}`가 기본값으로
있고, `is_tool_allowed_for_role()`이 "부수효과 있는 도구는 leader만" 판정을
실제로 하고 있다(외부 도구 — Jira 발행, task 등록 같은 것들). 그런데 이 검사는
`factory.py`의 `_to_langchain_tool()`이 이 프로젝트 자체의 `Tool` 객체를 감쌀
때만 걸린다. `write_file`/`edit_file`은 deepagents가 `FilesystemMiddleware`/
`MemoryMiddleware`로 직접 제공하는 내장 도구라서 애초에 이 RBAC 검사 자리를
거치지 않는다 — 즉 **지금 이 프로젝트가 이미 "부수효과 있는 건 leader만"이라는
정책을 갖고 있으면서도, 메모리 쓰기에는 그 정책이 적용되고 있지 않다.** 새
개념을 만들 필요 없이 이미 있는 정책을 메모리 쓰기까지 넓히면 된다.

### 설계

2절에서 만든 `memory/write_guard.py`(`wrap_tool_call`)에 내용 검사보다 먼저
역할 검사를 추가한다 — `/memories/AGENTS.md`(공유 경로)로 가는 `write_file`/
`edit_file`은 `context.role`이 `write_tool_allowed_roles`(기본값 `{"leader"}`)에
있을 때만 통과시키고, 아니면 실행 전에 거부한다. `/memories/users/`(개인
경로)는 이 검사 대상이 아니다 — 본인 개인 메모리는 본인이 항상 쓸 수 있어야
한다.

member가 "우리 팀은 이제 이렇게 할 거야" 같은 말을 하면, 거부하면서 이유를
`ToolMessage(status="error")`로 돌려준다 — 모델이 이걸 보고 "그 요청은 개인
메모리에는 남겨둘 수 있지만, 팀 전체 규칙으로 정하려면 팀장에게 요청해야
한다"는 식으로 사용자에게 안내할 수 있게(강제하는 문구는 아니고, 모델이
이 사유 텍스트를 받아 자연스럽게 안내하도록 유도). 완전히 묵살하는 것보다,
"개인 메모리로는 남길 수 있다"는 대안을 같이 주는 쪽이 2절의 철학(완전히
죽이지 않고 다시 시도할 기회를 남긴다)과도 맞는다.

### 승인 방식(팀장 수락)을 안 쓰는 이유

"모두가 쓸 수 있되 팀장이 수락해야 반영된다"는 방식은 검토했지만 쓰지 않기로
한다 — 배보다 배꼽이 커진다는 판단에 동의한다. 위 설계는 **승인이 아니다**:
`context.role`을 보고 그 자리에서 바로 허용/거부하는 동기 판정이라, member의
쓰기 시도는 그 즉시 끝난다(성공하거나, 이유를 듣고 끝나거나). "일단 요청을
큐에 넣고 팀장이 나중에 승인하면 반영된다"는 별개의 방식이고, 이건 실제로
꽤 무거워진다:

- 이 프로젝트의 HITL(`HumanInTheLoopMiddleware`)은 지금 "요청한 사람이 그
  자리에서 자기 요청을 확인"하는 동기 흐름만 있다 — "다른 사람(팀장)이
  나중에 승인"하는 새 엔진용 resume API 자체가 아직 존재하지 않는다
  (`2026-08-19_01` §2에서 이미 확인한 공백). 이걸 새로 만들어야
  한다는 뜻이고, 메모리 한 줄 쓰는 것치고는 인프라 대가가 너무 크다.
- 승인 대기 동안 member의 대화 턴이 멈춘다. member는 지금 당장 챗을 하고
  있는데, "팀장이 언제 승인할지 모르는 상태"로 그 턴이 멈추는 건 채팅
  에이전트의 기본 기대(바로 답한다)와 어긋난다.
- 메모리 쓰기는 되돌릴 수 있는 내부 동작이다(다시 수정·삭제 가능, 외부
  시스템에 영향 없음) — HITL이 원래 막으려는 대상(Jira 발행처럼 외부에 실제
  영향을 남기는 되돌리기 어려운 동작)과 성격이 다르다. 위험도가 낮은
  동작에 위험도가 높은 동작과 같은 무게의 방어를 씌울 필요는 없다.

동기 role 검사는 이미 있는 정책(`write_tool_allowed_roles`)을 재사용하는
것뿐이라 새 인프라가 필요 없고, member의 턴도 멈추지 않는다 — 같은 목적을
더 가벼운 방법으로 이미 달성한다.

### 그런데 role 게이트만으로는 부족하다 — "leader가 나눈 모든 대화가 잠재적으로 팀 메모리가 될 수 있다"

지적한 문제에 동의한다. leader만 쓸 수 있게 막아도, **leader가 그 순간에
실제로 "이걸 팀 규칙으로 정하자"고 의도했는지는 role 게이트가 구분하지
못한다.** `_MEMORY_ROUTING_PROMPT`의 "이건 기억할 가치가 있는가"라는 판단은
모델이 대화 흐름만 보고 스스로 내리는 것이라, leader가 그냥 지나가는 말로
한 얘기도 모델이 "이건 팀 규칙이다"라고 잘못 판단하면 그대로 `AGENTS.md`에
들어가 그 순간부터 전 팀원에게 매 턴 주입된다. **role은 "누가 쓸 수
있는가"만 정할 뿐, "이번이 실제로 의도된 저장인가"는 안 걸러준다** — 이 둘은
다른 질문이고, role 하나로는 두 번째 질문에 답이 안 된다.

그렇다고 3절 앞부분에서 이미 기각한 "팀장 수락" 방식으로 돌아가는 건 아니다
— 거기서 기각한 건 **다른 사람(member)이 요청하고 leader가 나중에
승인**하는 비동기 방식이었다. 여기서 필요한 건 그것과 다르다: **leader
본인이 leader 본인의 쓰기를, 그 자리에서 바로** 확인하는 것 — 이건 이미 이
프로젝트가 side_effect 도구에 쓰고 있는 HITL과 똑같은 모양(같은 대화 안에서
같은 사람이 그 자리에서 확인)이라 새로운 패턴이 아니다.

### 실제로 이 목적의 기능이 deepagents에 이미 있다 — `FilesystemPermission`의 `mode="interrupt"`

`deepagents==0.7.5` 실제 설치 소스(`middleware/_fs_interrupt.py`)를 확인하니,
`FilesystemPermission.mode`는 `"allow"`/`"deny"`뿐 아니라 `"interrupt"`도
받는다. `mode="interrupt"`인 규칙에 걸리는 `write_file`/`edit_file` 호출은
그래프 조립 단계에서 자동으로 `HumanInTheLoopMiddleware`의 `interrupt_on`에
등록돼(`_build_interrupt_on_from_permissions`), **실제 쓰기가 일어나기 전에
멈추고 사람의 approve/edit/reject/respond 결정을 기다린다.** 새로 만들
필요가 없다 — 이미 만든 `permissions.py`의 `build_filesystem_permissions()`에
규칙을 role에 따라 다르게 추가하기만 하면 된다:

- `context.role == "leader"`: `/memories/AGENTS.md`(그리고 프로젝트 공유
  메모리도 같은 이유로 포함) 쓰기에 `mode="interrupt"` — 쓰기 자체는
  허용되지만, 실제로 저장되려면 그 자리에서 확인이 필요하다. "leader가
  나눈 모든 대화가 자동으로 저장"이 아니라 "leader가 확인한 것만 저장"이
  된다.
- `context.role != "leader"`(member): 같은 경로에 `mode="deny"` — 확인창도
  없이 애초에 시도 자체가 막힌다(교차 승인 없음 — 위에서 이미 기각한 이유와
  같다).

### 정직한 한계 — 지금 당장 켤 수는 없다

`interrupt` 모드가 실제로 동작하려면 멈춘 실행을 다시 진행시킬 방법(resume)이
있어야 한다. `2026-08-19_01` §2에서 이미 확인한 공백인데, **새 엔진(이
프로젝트의 deepagents 기반 실행 경로)용 resume API 자체가 아직 없다** —
`ChatConfirmAPIView`는 레거시 엔진 전용이고, `Command(resume={"decisions":
...})`를 새 엔진에 보내는 엔드포인트는 어디에도 없다(테스트 스크립트가
그래프 객체를 직접 조작하는 것 말고는). 지금 이 `interrupt` 규칙을 켜면
멈춘 채로 아무도 재개시킬 방법이 없어서 대화가 그냥 멈춰버린다.

그래서 이건 메모리 때문에 새로 인프라를 만드는 게 아니라, **HITL 전체가
이미 안고 있던 그 공백이 먼저 풀려야 하는 것**이다 — 그 API가 생기면
side_effect 도구뿐 아니라 이 메모리 확인도 규칙 한 줄 추가로 거의 공짜로
따라온다. 순서는: 지금 당장은 leader:allow / member:deny 동기 게이트만
켜고(인프라 없이 지금 바로 가능), leader 쪽 "매번 확인"은 resume API가
만들어진 뒤 `mode="interrupt"`로 승격하는 걸 다음 단계로 남긴다.

## 4. (2026-08-19 이전 설계, 이제 무효 — 실제로는 이 우려와 별개로 개인 전용으로 결정됨) 그럼 공용 메모리를 없애면 개인 메모리만 남는 건데, 그걸로 충분한가 — 아니라고 본다

3절 결론대로 공용 메모리 자체는 없애지 않기로 했지만, "개인 메모리만
있어도 되는가"는 그것대로 따로 답할 가치가 있는 질문이다. 개인 메모리만
남기면 잃는 게 분명히 있다:

- **팀 공유 에이전트의 존재 이유가 없어진다.** Builder로 팀장이 의도적으로
  만들어 활성화한 에이전트(`2026-08-18_01` §4)는 "이 팀은 이렇게 일한다"는
  맥락을 팀원 전체가 매번 다시 알려주지 않아도 되게 하려고 있는 기능이다.
  개인 메모리만 있으면 팀원 각자가 같은 내용을 각자 자기 메모리에 따로
  넣어야 하고, 그러면 "팀 에이전트"가 사실상 "각자의 개인 봇 N개"와
  다를 게 없어진다.
- **프로젝트 공유 메모리(`/memories/projects/{project_id}.md`)도 같이
  무너진다.** 이건 이번 세션에서 이미 만들고 검증까지 한 기능인데, 이
  파일은 애초에 "그 프로젝트를 같이 하는 사람이면 누가 썼든 다 같이
  본다"는 게 존재 의미다(예: 프로젝트 진행 상황, 결정 사항). 이걸 개인
  메모리로 내리면 프로젝트에 새로 합류한 사람은 이전 맥락을 전혀 못 보게
  된다 — "권한 없는 사람이 팀 정책을 강제한다"는 원래 문제와는 아예 무관한
  기능인데 같이 없어지는 셈이다.
- 이 프로젝트의 목표 자체가 "실무적으로 필요한 팀 업무 관리 플랫폼"이다 —
  팀 단위로 맥락을 공유하는 게 핵심 가치 중 하나인데, 메모리를 개인 단위로만
  묶으면 그 핵심 가치와 정면으로 부딪힌다.

즉 "개인 메모리만"은 이번에 실제로 드러난 문제(권한 없이 팀 규칙을 강제하는
것)와 무관한 기능들까지 같이 잘라내는 과잉 대응이라고 본다. 3절의 role
게이트로 "누가 쓸 수 있는가"만 좁히면 이 문제는 그것만으로 해결되고, 공유
메모리·프로젝트 메모리·팀 공유 에이전트가 갖는 원래 가치는 그대로 남는다.

## 5. (2026-08-19 이전 설계, 참고용 — 팀 메모리 자체는 없어졌지만 "메모리 vs 문서 조회"의 구분 논리는 여전히 유효) 팀 메모리에는 실제로 뭐가 쌓이나 — 프로젝트 문서 조회와는 저장 위치·정확성이 다르다

### 팀 메모리에 뭐가 저장되나

`_MEMORY_ROUTING_PROMPT`가 모델에게 지시하는 기준은 "SHARED(팀/에이전트 전체가
알아야 함)인가 PERSONAL(이 사용자만)인가"다. 팀 규칙·프로젝트 사실·결정사항이
SHARED로 분류되고, `AGENTS.md`(핵심, 짧게)나 `projects/{project_id}.md`(상세
이력)에 쓰인다. **핵심은 이게 "어디에도 문서화되어 있지 않은 것"이라는
점이다** — 예를 들어 "이 팀은 커밋 메시지를 한국어로 쓴다", "이 프로젝트는
Jira 대신 task_register만 쓰기로 회의에서 정했다" 같은, 대화 중에만 드러나고
어떤 업로드 문서에도 안 적혀 있는 내용이다.

### 프로젝트 문서는 이미 별도로, 그때그때 다시 조회한다 — 메모리로 옮겨 저장하지 않는다

이 플랫폼엔 이미 `document_search`(팀 문서에서 근거 문장 검색, 2단계 —
`doc_meta.summary_vec`으로 문서를 먼저 좁히고 그 안에서 청크 검색)·
`document_list`(문서 목록)·`project_list`(프로젝트 목록)·`task_list`(등록된
업무) 같은 읽기 전용 Tool이 있다(`services/harness/registry.py`,
`BUILTIN_TOOLS`). 이것들은 **매 호출마다 DB의 지금 상태를 그대로 다시
조회한다** — 문서가 바뀌면 다음 호출에서 바뀐 내용이 그대로 나온다.

`_document_search`의 실제 소스를 확인해 보면, 검색 결과를 요약해서 메모리
파일(`AGENTS.md`/`projects/*.md`)에 자동으로 옮겨 적는 코드는 없다 — 결과는
그 턴의 `ToolMessage`로만 모델에게 전달되고, 모델이 다음 요청에서 또
필요하면 또 조회한다. **StateBackend로 저장되는 것도 아니다** —
`StateBackend`는 memory route(`/memories/`)에 안 걸린 나머지 파일 도구(모델이
작업 중에 쓰는 휘발성 스크래치 공간)의 기본값일 뿐이고, `document_search`
결과를 자동으로 거기 담는 로직도 마찬가지로 없다. 문서 검색 결과가 메모리에
남으려면, 모델이 `_MEMORY_ROUTING_PROMPT`의 "이건 기억할 가치가 있는가"
판단을 거쳐 스스로 `write_file`/`edit_file`을 불렀을 때뿐이다 — 그것도 이미
문서에 있는 내용을 그대로 베끼기보다는(다시 검색하면 되니까), 문서 검색만
으로는 알 수 없는 결정·컨벤션을 적는 용도로 프롬프트가 유도한다.

### 그래서 "문서를 계속 보면 되는 거 아닌가"에 대한 답

문서화되어 있는 내용이라면 맞다 — `document_search`가 매번 최신 문서를
다시 찾는 게 메모리에 박제해 두는 것보다 오히려 더 정확하다(문서가
바뀌었는데 메모리는 안 바뀌면 그게 더 위험한 오래된 정보다). 메모리가
필요한 지점은 **문서화가 안 되는 것**이다 — 구두로만 오간 팀 컨벤션, 대화
중에만 나온 결정, 사용자 개인 습관처럼 어떤 업로드 문서에도 존재하지 않는
정보는 `document_search`로 아무리 찾아도 안 나온다. 그런 것들을 매번 다시
설명하지 않아도 되게 하는 게 메모리의 실제 존재 이유다 — "문서에 있는 걸
또 저장"하는 중복 기능이 아니다.

이 설계도 아직 코드에는 반영하지 않았다.
