## 1. 서브 에이전트 alias·위임 설명 자동화

**요청**: "서브 에이전트를 고를 때 alias·위임 설명을 또 입력하게 하지 마라
— 에이전트 만들 때 이미 이름·설명을 입력한다."

`AgentVersionEditPage.tsx`의 서브 에이전트 추가 폼에서 alias·위임 설명
입력란(`Input`/`textarea`)을 없애고, 고른 자식 에이전트 자신의
`name`/`description`을 그대로 스냅샷으로 써서 `SubagentRef`를 만든다.
자식의 설명이 비어 있으면 추가를 막고("먼저 그 에이전트의 설명을 채워
주세요"), 두 후보의 이름이 같아 alias가 충돌하면 에러로 안내한다 — 백엔드는
`alias`/`delegation_description` 필드와 검증(`services/agent_runtime/
subagents/validation.py`)을 그대로 두고 프론트에서만 자동으로 채워 보낸다.

이 변경은 커밋됨(`80efef1`).

## 2. 에이전트 삭제 — 소유자·팀장 권한 + 사용 중 차단

**요청**: "만든 사람이거나 권한 있는 사람(팀장)이면 삭제 가능하게 하고,
삭제를 누르면 확인 대신 바로 사용 중인 에이전트 목록을 보여줘라."

### 2.1 권한

`apps/accounts/permissions.py`에 `require_owner_or_leader(account_id,
owner_account_id, detail)` 추가 — 본인 소유면 무조건 통과, 아니면 기존
`require_leader`로 넘긴다. `agents.owner_account_id`는 이미 스키마에 있었지만
`agent_version_response()`가 안 내려주고 있어서 추가했다
(`apps/agents/serializers.py`).

### 2.2 삭제는 소프트 — ARCHIVED

`AgentVersionCrudRepository.delete()`(`backend/db/agent_platform.py`)는 행을
지우지 않고 `agents.status = 'ARCHIVED'`로 내린다 — `AgentCrudRepository.delete`
(옛 비버전 스키마)와 같은 이유: `agent_run`·`chat_session`이 이 버전들을
가리키고 있어서, 지우면 그 실행이 어느 에이전트였는지 잃는다.
`list_for_team()`은 `status <> 'ARCHIVED'`라 자동으로 목록에서 빠진다.
기본 챗 에이전트(`is_default_chat`)는 지울 수 없게 막는다(비활성화 금지와
같은 이유 — 꺼지면 Chat 랜딩이 대화 상대 없이 빈다).

### 2.3 사용 중인 서브 에이전트는 삭제 차단

이 에이전트를 서브 에이전트로 참조하는 **살아있는**(ARCHIVED 아닌) 다른
에이전트가 있으면 삭제를 막고 그 이름들을 에러 메시지에 담는다. 안 막으면
그 부모는 다음 실행에서 `factory.build()`가 매 호출마다 다시 돌리는
`validate_subagents()`(`services/agent_runtime/subagents/validation.py`)가
`InactiveSubagentError`를 던져 **부모 전체가 실행 불가**가 된다 — 부분
기능만 빠지는 게 아니라 통째로 막힌다. 이 조회 로직을
`AgentVersionCrudRepository._dependent_parent_names()`로 빼서 `delete()`와
새 `list_dependents()`가 같이 쓴다.

**"확인 대신 바로 목록"**을 위해 `GET /agents/versions/<id>/dependents/`
(`AgentVersionDependentsAPIView`)를 새로 만들었다. 프론트(`startDelete()`)는
삭제 버튼을 누른 시점에 이 엔드포인트를 먼저 불러서:
- 사용 중인 부모가 있으면 → "지금은 지울 수 없습니다" + 이름 목록 모달
- 없으면 → 기존 "이 에이전트를 지울까요?" 확인 모달(ChatPage의 대화 삭제
  확인과 같은 `Modal` 패턴)

두 경로 모두 `AgentVersionListPage.tsx`에 상태(`blockedDelete`/
`pendingDelete`)로 분리돼 있다. 실제 삭제 시점에도 `delete()`가 같은
조회를 한 번 더 하므로(경합 대비) 사전 조회 결과만 믿고 삭제를 강행하지
않는다.

### 2.4 검증

`manage.py shell`로 리포지토리 레이어, curl로 HTTP 레벨까지 확인:
- 소유자·팀장 둘 다 삭제 성공, 그 외 계정은 (역할이 leader뿐인 시드라 실제
  member 거부 케이스는 코드 리뷰로만 확인 — `require_leader`와 동일 패턴이라
  신뢰)
- 기본 챗 에이전트 삭제 시도 → `RepositoryError`로 차단
- 부모가 참조 중인 자식 삭제 시도 → `400 {"detail":"다른 에이전트가 서브
  에이전트로 쓰고 있어 지울 수 없습니다: <부모 이름>"}`, 부모를 먼저 지우면
  자식도 정상 삭제
- `/dependents/` 엔드포인트: 연결 전 `[]`, 연결 후 부모 이름이 담겨 옴

## 3. 기본 챗 에이전트를 관리 화면에서 숨김

**요청**: "기본 챗 에이전트가 에이전트 설정 화면에 보이는 게 싫다 — 아무것도
안 골랐을 때 자동으로 그걸로 떨어지기만 하면 된다."

`AgentVersionListPage.tsx`에서 `is_default_chat`인 에이전트를 렌더링에서만
뺀다(`visibleAgents` 필터). **백엔드 응답 자체는 안 건드렸다** —
`ChatPage.tsx`가 같은 목록(`listAgentVersions`)에서 `is_default_chat`
플래그로 기본 상대를 찾아 자동 선택하는 로직(`active.find(row =>
row.is_default_chat)`)이 이미 있어서, 목록에서 아예 빼면 그 로직이 깨진다.
즉 "안 보이지만 여전히 목록엔 있다" — 관리 화면만 필터링.

## 4. 개인 / 팀 공유 분리

**요청**: "에이전트를 저장만 하면 개인 페이지에서 보이고, 활성화하면 팀
공유 페이지에서 보이게, 에이전트 탭을 개인/팀 공유 둘로 나눠라."

### 4.1 결정 사항 (지훈 확인)

두 가지를 먼저 물어서 확정했다:
1. **다른 팀원의 미활성(DRAFT) 에이전트가 "개인" 탭에 안 보이게 막을지** →
   **막는다.** "개인"이 이름값을 하려면 목록만 안 보이는 게 아니라 접근
   자체가 막혀야 한다.
2. **활성화됐다가 "사용 중지"(DISABLED)된 에이전트는 어디 보이나** → **팀
   공유 탭에 계속.** 한 번이라도 팀에 공유된 적이 있으면 계속 팀 소관.

결과적으로 분류 기준은 새 컬럼 없이 **기존 `status`** 하나로 충분하다:
`DRAFT` = 개인, `ACTIVE`/`DISABLED` = 팀 공유. (참고: `agents.visibility`
컬럼이 스키마에 이미 있지만 "v1은 항상 TEAM 고정"이라고 못 박혀 있다 — 이
기능은 그 컬럼을 안 쓰고도 구현됐다. `visibility`를 실제로 여러 값으로
쓰는 건 여전히 범위 밖.)

### 4.2 백엔드 — 목록과 접근 둘 다 막는다

`AgentVersionCrudRepository.list_for_team()`에 조건 추가:
`(a.status <> 'DRAFT' OR a.owner_account_id = %s)` — 팀 스코프는 그대로
두고 DRAFT만 소유자 필터를 얹는다.

`_writable_agent_version()`(`get`/`publish`/`set_status`/`delete`/
`list_dependents`의 공통 게이트)에 `account_id` 파라미터와
`enforce_draft_privacy: bool = True`를 추가해서, DRAFT인데 요청자가
소유자가 아니면 `PermissionDenied`를 던진다. **목록에서만 숨기고 URL을
직접 알면 그대로 뚫리는 반쪽짜리 프라이버시를 피하려는 것.**

**충돌 하나 발견하고 고침**: `delete()`도 이 게이트를 그대로 타면 §2에서
만든 "소유자 또는 팀장 삭제 가능" 규칙과 부딪힌다 — 팀장이 남의 DRAFT를
못 지우게 된다. `delete()`는 `enforce_draft_privacy=False`로 불러서 이
가드를 건너뛴다 — 뷰 레이어의 `require_owner_or_leader`가 이미 더 정확한
권한을 확인했고, 삭제는 내용을 보여주지도 바꾸지도 않는 관리 동작이라
조회·수정과 같은 잣대를 안 쓴다는 판단.

### 4.3 프론트 — 라우트 기반 탭

`SettingsPage.tsx`(팀/Connector/MCP/Model 탭)와 같은 패턴을 그대로 썼다:
- `routes.ts`에 `agentVersionsTeam: '/agents/versions/team'` 추가,
  `agentVersions`(`/agents/versions`)가 "개인" 몫
- `App.tsx`에 두 라우트 모두 같은 `AgentVersionListPage` 엘리먼트로 연결
- `AgentVersionListPage.tsx`가 `useLocation().pathname`으로 활성 탭을 가리고,
  이미 받아온 한 번의 목록(`visibleAgents`)을 `status === 'DRAFT'` 기준으로
  클라이언트에서 나눠 보여준다(API 호출은 하나로 충분 — 서버가 이미
  본인이 볼 수 있는 것만 돌려주므로 개인 탭에 뜨는 DRAFT는 항상 내 것이다)
- `APP_NAV_ITEMS`의 "에이전트" 항목 `match`에 두 경로 다 추가해 사이드바가
  어느 탭에서나 활성으로 보이게 함

### 4.4 검증

`manage.py shell` + curl로: 소유자 목록엔 뜨고 비소유자 목록엔 안 뜸,
비소유자가 URL로 직접 GET 시도 → `403`, 팀장이 남의 DRAFT를 삭제하는
것(관리자 오버라이드)은 여전히 `204` 성공. 프론트 두 라우트 다 200으로
로드 확인.

## 5. 카드에서 버전 번호 대신 서브 에이전트 이름

**요청**: "목록 카드에 v1/v2 안 뜨고, 대신 어떤 에이전트가 서브 에이전트로
붙어 있는지 보여줘라."

`list_for_team()` SELECT에 서브쿼리 하나 추가 — 그 에이전트의
`current_version_id`가 위임하는 자식들의 이름을 `json_agg`로 모은다
(`subagent_names`). `agent_version_response()`가 이 필드를 그대로 내려주고
(상세 조회는 이미 `subagents`에 alias까지 있는 전체 정보가 있어 이 필드는
빈 배열로 둔다 — 목록 전용), `AgentVersionListPage.tsx`가
`{agent.version !== null && <Badge>v{agent.version}</Badge>}`를 지우고
`agent.subagent_names.join(', ')`을 아이콘과 함께 보여준다. 서브 에이전트가
없으면 그 줄 자체를 안 그린다.

curl로 목록 응답에 `subagent_names:["<자식 이름>"]`가 정확히 담기는 것,
상세 응답은 `subagent_names:[]`(빈 배열)인 것을 확인.

## 6. 남은 일 / 확인 필요

  접근"으로만 확인했다. `require_leader`와 동일한 검증 함수를 쓰므로
  코드상으로는 member도 같은 이유로 막히지만, 실측은 못 함.
- 프론트 UI는 tsc 통과·라우트 200 확인까지만 했고, 브라우저 클릭 테스트는
  지훈 쪽에서 진행 필요.
