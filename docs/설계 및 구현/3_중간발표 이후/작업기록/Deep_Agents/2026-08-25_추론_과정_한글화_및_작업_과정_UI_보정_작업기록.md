# 추론 과정 한글화 및 작업 과정 UI 보정 작업기록

> 여기서 “추론 과정 한글화”는 모델의 비공개 Chain of Thought를 번역하거나 노출한다는 뜻이 아니다. 기존 화면에 노출되던 영어 Reasoning Summary는 숨기고, 도구 실행 전에 모델이 생성한 짧은 **한국어 사용자용 작업 안내**와 실제 도구 이벤트를 구분해 보여주는 작업이다.

- 작업 일시: 2026-08-25
- `jihun` 통합 시작 기준: `origin/jihun` `bf8e832`
- 로컬 통합 브랜치: `codex/jihun-reasoning-korean-progress`

- 완료 시각: 2026-08-25 18:10 KST

별도 비교 스파이크에서 가능성을 확인한 뒤, 최신 `jihun` 브랜치에 제품 코드 변경만 옮겼다. 스파이크 서버, 비교 전용 UI, 로컬 Docker 설정은 이 브랜치에 포함하지 않았다.

## 2. 문제와 목표

기존 QA 화면은 모델의 Reasoning Summary가 영어로 보일 수 있었고, 실제 사용자가 알아야 할 진행 상태와 내부 관측용 이벤트의 경계가 불분명했다. 또한 웹 검색 결과와 도구 호출이 누적되면 같은 단계와 URL이 반복되어 최종 답변을 밀어냈다.

이번 변경의 목표는 다음과 같다.

1. 내부 Reasoning은 사용자 화면에서 숨긴다.
2. 도구가 필요할 때 모델이 짧은 한국어 작업 안내를 먼저 생성한다.
3. 실제 도구의 시작·완료·실패와 입력·출력을 접을 수 있는 형태로 표시한다.
4. 검색과 도구가 여러 번 실행되면 순서는 보존하되 중복 표시는 줄인다.
5. 최종 답변의 출처 URL은 클릭 가능한 링크로 제공한다.

## 3. 변경 전후

| 구분 | 변경 전 | 변경 후 |
|---|---|---|
| 모델 추론 | 영어 Reasoning Summary가 UI에 노출될 수 있음 | 내부 Reasoning 이벤트는 수집하되 사용자 작업 과정에서는 숨김 |
| 진행 안내 | 도구명 중심의 고정 문구 | 모델이 도구 호출 전에 생성한 짧은 한국어 안내 사용 |
| 안내 누락 | 별도 처리 없음 | 한국어 안내가 없으면 애플리케이션 fallback 문구 표시 |
| 도구 상세 | 결과 중심, 입력/출력 구분이 약함 | 도구별 상태와 입력·출력을 접어서 확인 |
| 반복 호출 | 같은 단계가 계속 늘어남 | 동일 단계는 실행 횟수로 집계하고 도구 이벤트는 순서대로 유지 |
| 웹 출처 | 링크가 길게 모두 노출될 수 있음 | URL 중복 제거 후 `검색한 링크 N개` 토글에 수납 |
| 내부 문서 | 웹 링크와 같은 목록에 혼합 | `참고한 문서 N개` 토글로 분리 |
| 답변 링크 | 일반 텍스트가 될 수 있음 | Markdown 링크와 일반 HTTP(S) URL을 안전한 새 탭 링크로 렌더링 |

## 4. 실행 및 이벤트 계약

### 프롬프트

`services/agent_runtime/prompts.py`에 다음 원칙을 추가했다.

- 사용자에게 사고 과정이나 Chain of Thought를 보여주지 않는다.
- 도구가 필요하면 같은 응답에서 도구 호출 전에 1~2문장의 자연스러운 한국어 작업 안내를 만든다.
- 도구가 필요 없는 답변에는 억지 진행 안내를 만들지 않는다.
- 같은 도구를 다시 호출하면 첫 결과에서 부족했던 점과 추가 확인 목적을 짧게 설명한다.
- 웹 출처는 `[제목](https://...)` 형식으로 제공하고 같은 URL을 반복하지 않는다.

프롬프트만 바꾼 작업은 아니다. 실제 화면에 안정적으로 전달하기 위해 백엔드 이벤트 추출과 프론트 이벤트 조립도 함께 변경했다.

### 백엔드 이벤트

`services/agent_runtime/events.py`가 OpenAI SDK 객체형 메시지 블록도 읽고, 도구 호출 전 일반 텍스트를 첫 번째 `tool_started` 이벤트에 아래 필드로 연결한다.

```json
{
  "type": "tool_started",
  "user_update": "최신 공식 문서와 현재 시간을 각각 확인하겠습니다.",
  "user_update_source": "model"
}
```

모델이 한국어 안내를 만들지 못한 경우에는 다음처럼 명시적인 fallback을 사용한다.

```json
{
  "user_update": "요청을 처리하기 위해 필요한 도구를 확인하고 있습니다.",
  "user_update_source": "application_fallback"
}
```

Reasoning 이벤트 자체는 관측성과 기존 계약 호환성을 위해 백엔드에 남겨 두었다. 사용자 화면만 이를 작업 기록으로 사용하지 않는다.

### 프론트 이벤트 조립

`frontend/src/pages/ChatPage/liveChat.ts`에서 다음을 처리한다.

- `reasoning` 이벤트는 사용자 작업 과정에 추가하지 않음
- `user_update`를 도구 이벤트 바로 앞에 배치
- 도구 입력값을 보존해 상세 토글에서 표시
- 같은 검색 URL을 URL 기준으로 중복 제거
- 여러 검색어와 반복 단계를 누적하되 같은 단계는 `N회 실행`으로 집계

## 5. UI 변경

- 작업 과정 전체는 기존처럼 접고 펼칠 수 있다.
- 도구 호출마다 실행 중·성공·실패·거절 상태를 구분한다.
- 도구 입력과 결과는 별도 토글로 제공한다.
- `token`, `password`, `secret`, `api key`, `authorization`, `credential` 계열 키는 화면 표시 전에 마스킹한다.
- 웹 링크는 `검색한 링크 N개`, 내부 문서는 `참고한 문서 N개`로 분리해 기본 접힘 상태로 표시한다.
- 상단의 `N/N 단계`는 작업 진행률이고, 링크 토글의 `N개`는 출처 수이므로 서로 다른 지표로 유지한다.

## 7. 로컬 실행과 검증

### 환경 확인

실제 값은 문서나 Git에 기록하지 않는다. 실행 환경에는 사용하는 공급자에 맞춰 최소한 다음 항목이 필요하다.

- `OPENAI_API_KEY`
- 팀/에이전트에 저장된 모델 설정 (`OPENAI_MODEL` 환경변수로 고정하지 않음)
- 웹 검색을 시연할 경우 `WEB_SEARCH_API_KEY` (현재 구현은 Tavily 사용)
- `DATABASE_URL`

현재 프로젝트 설정은 `OPENAI_BASE_URL`을 읽지 않으므로 기본 OpenAI 엔드포인트를 사용한다. 호환 API나 프록시 지원이 필요하면 환경변수만 추가하지 말고 모델 팩토리의 명시적 지원을 함께 구현해야 한다.

## 8. 운영 반영 전 논의할 항목

1. 일반 사용자에게 도구 입력·출력을 어디까지 공개할지 결정해야 한다. 현재 프론트 마스킹은 편의 기능이며 서버 측 비밀정보·개인정보 필터를 대체하지 않는다.
2. `application_fallback` 안내를 모델 생성 안내와 시각적으로 구분할지 결정할 수 있다. 현재는 자연스러운 사용자 경험을 위해 같은 형태로 표시한다.
3. 사용자용 작업 안내를 실행 로그에 별도 영속화할지 결정해야 한다. 현재는 실시간 이벤트 계약에 연결한다.
4. 하위 에이전트가 많아질 경우 평면 목록 대신 하위 작업별 계층 구조를 추가할 수 있다.
5. 배포 전 실제 QA 모델·서비스 티어·웹 검색 공급자 조합으로 반복 시나리오를 확인해야 한다.

## 10. 사용자 관점 재검증 후 UI 보정

로그인된 실제 채팅에서 한 대화 높이 8,533px, 화면 높이 469px인 사례를 확인했다. 기존 구현은 대화를 열자마자 마지막 답변 하단으로 이동했고, 완료 카드에는 `웹 검색 완료`, 진행 막대, `웹 검색하는 중`, 검색 링크, 작업 과정이 동시에 남아 최종 답변보다 먼저 한 화면을 차지했다.

다음 원칙으로 보정했다.

- 저장된 대화와 새 질문은 마지막 턴의 **시작점**을 한 번 보여준다.
- 답변이 길어져도 사용자가 읽는 위치를 강제로 하단으로 끌지 않는다.
- 아래에 내용이 남으면 `최신 내용 보기` 버튼을 표시하고, 사용자가 맨 아래를 선택했을 때만 실시간 출력을 따라간다.
- 사용자가 위로 스크롤하면 자동 추적을 즉시 중단한다.
- 완료 후 진행 막대·단계 목록·검색 결과는 기본 화면에서 숨기고 `웹 검색 완료 · 도구 3회 · 15.0초`처럼 한 줄로 요약한다.
- 작업 과정은 별도 토글로 유지하며, 같은 도구가 연속 실행되면 `웹 검색 · 2회 완료`로 묶는다. 펼치면 1차·2차 실행의 입력과 결과를 각각 확인할 수 있다.
- 웹 검색에서 수집한 전체 URL은 최종 답변의 실제 인용 출처와 혼동하지 않도록 `검색 상세 · 결과 N개`로 명명해 작업 과정 상세에 둔다.
- 검색어·검색 결과·참고 문서 후보는 기본적으로 접어 최종 답변을 밀어내지 않는다.

브라우저 검증 결과:

- 저장된 대화를 열면 마지막 질문과 완료 요약, 답변 시작 부분이 한 화면에 보임
- `최신 내용 보기` 클릭 후 하단까지 남은 거리 약 0px, 버튼 숨김
- 위로 스크롤하면 버튼 재표시
- 반복 웹 검색 2회를 하나로 묶고 `1차 실행`, `2차 실행` 하위 토글 표시
- 완료된 카드에서 진행 막대와 `웹 검색하는 중` 문구 제거

   - 표마다 `표 펼치기` 버튼을 제공해 기존 Modal 안에서 최대 1,200px 폭으로 전체 표를 볼 수 있다. 같은 React 표 노드를 다시 표시하므로 모델 재호출과 토큰 비용은 없다.
   - 모바일에서는 버튼을 아이콘으로 축약하고 표 자체는 가로 스크롤을 유지한다.
   - 프롬프트는 열 수를 임의로 제한하지 않고, 비교에 필요한 열을 유지하되 긴 부가 설명은 표 아래로 분리하도록 변경했다.

4. **입력부와 푸터 정렬**
   - 중단 사각형을 실제 약 8px에서 약 10px로 키우고 48×48px 버튼 외곽은 유지했다.
   - 도구 선택 `+` 버튼을 36×36px에서 42×42px로 바꿔 한 줄 입력칸 중심과 맞췄다.
   - 대화 목록이 있는 AppShell에만 사용자 푸터의 기본 높이를 85px로 지정하고 사이드바 내부 여백까지 경계선을 확장해, 한 줄 입력 상태에서 오른쪽 입력 푸터의 상단선과 이어지게 했다. 여러 줄 입력은 오른쪽만 일시적으로 커지며 JS 높이 동기화는 추가하지 않았다.
