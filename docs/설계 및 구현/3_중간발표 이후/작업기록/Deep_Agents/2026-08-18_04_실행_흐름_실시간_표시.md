# 2026-08-18_04 — 추론·도구 진행·위임을 실시간으로 보여주기

> `2026-08-18_03_도구_선택_그룹화.md`의 후속. 지훈 요청으로 이어서 진행한
> 별도 작업 — 아직 커밋 전.

## 1. 배경 — "생각 과정이 실시간으로 안 보인다"

`2026-08-18_02`에서 만든 "생각 과정 N단계" 카드는 한 번에 다 끝난 뒤에야
뜨는 방식이었다. 지훈이 "스트리밍으로 실시간으로 볼 수 없냐"고 물어서 조사한
결과: relay(`_relay()`)와 프론트(`liveChat.ts`)는 이미 이벤트가 나올 때마다
바로 흘려보내는 구조라 손댈 필요가 없었고, 유일한 원인은 백엔드가
`stream_mode="updates"`만 구독한다는 것 — 이 모드는 모델 노드 하나가
**통째로 끝나야** 완성된 `AIMessage`를 준다. 토큰·조각 단위로 받으려면
`stream_mode="messages"`가 필요했다.

## 2. reasoning 실시간 스트리밍

**구현**:
- `stream_adapter.py`: `runtime.stream(...)`의 `stream_mode`에 `"messages"`
  추가(`["updates", "custom"]` → `["updates", "custom", "messages"]`).
- `events.py`: `EventMapper`에 `_classify_reasoning_delta()` 신설.
  `stream_mode="messages"`가 주는 `AIMessageChunk`의 reasoning 블록은
  `{"type": "reasoning", "index": <문단 아이템 번호>, "summary": [{"index":
  <문단 안 파트 번호>, "type": "summary_text", "text": <이번 조각>}]}` 모양으로
  온다(실측 확인 — 디버그 스크립트로 실제 OpenAI 호출을 떠 봄). `(block_index,
  summary_index)` 쌍을 커서로 들고 있다가, 같은 쌍이 다시 오면 "이어지는
  델타"(`append: true`)로, 다르면 "새 문단"(`append: false`)으로 표시한다.
  모델 호출이 끝나면(`"updates"` 모드의 model 노드 완료) 커서를 지워서 다음
  호출의 첫 조각이 이전 호출 끝에 잘못 이어붙지 않게 한다.
- **기존 `_extract_reasoning()`(완성된 `AIMessage.content`에서 한 번에 뽑던
  함수)는 제거했다** — 그대로 두면 실시간으로 이미 다 보여준 내용이 모델
  호출이 끝날 때 완성본으로 한 번 더(중복) 나갔을 것이다.
- 프론트(`api/chat.ts`/`liveChat.ts`): `reasoning` 이벤트에 `append: boolean`
  추가. `append`가 true면 `reasoningSteps`의 마지막 항목에 텍스트를
  이어붙이고, false면 새 항목을 만든다.
- `ChatCards.tsx`의 `ReasoningTrace`에 `defaultOpen` prop 추가 — **지금
  스트리밍 중인 턴(`live.running`)은 펼쳐서 시작**하도록 `ChatPage.tsx`에서
  넘긴다. 원래 "지난 턴은 접어서 시작"만 있었는데, 실시간으로 써지는 걸
  보여주는 게 이 기능의 목적이라 접힌 채로 두면 매번 사람이 직접 펴야
  했다 — 지난 턴/새로고침 시엔 여전히 접힘.

**주의할 점 하나**: "요약(summary) 문단"의 granularity가 이전과 달라졌다.
이전엔 모델 호출 한 번당 reasoning 항목 하나(여러 문단을 `\n`으로 합친
덩어리)였는데, 지금은 문단(summary_index)마다 별도 "단계"로 뜬다 — OpenAI가
실제로 나눠 보내는 단위 그대로라 더 정확하지만, 카드에 뜨는 "N단계" 숫자가
전보다 늘어날 수 있다.

**검증**: `tests/test_events.py`의 `ReasoningEventTests` 전면 재작성(델타
누적·새 문단 판정·모델 호출 경계에서 커서 리셋·자식 네임스페이스 등 케이스별
확인). 실제 OpenAI 호출로 원시 스트림 모양을 먼저 실측하고,
`AgentExecutor.run()` 전체 경로로 97개 조각이 순서대로 오고 중복 없이
합쳐지는 것까지 확인.

## 3. "출처는 왜 안 보이냐" → tool_progress 미처리 버그 발견

지훈이 "지금 툴은 어떤 걸 호출했는지, 출처 같은 건 어디를 보고 있는지 같은
정보는 스트리밍에서 안 뜨냐"고 물어서 조사하다가, **의도한 것보다 훨씬 큰
버그**를 발견했다.

**발견**: `task_extraction`/`jira_get_issues`처럼 진행 이벤트를 흘리는 도구는
`services/agent_runtime/tools/adapters.py`의 `_drain_with_progress()`가 매
이벤트에 `tool_ref`를 얹어 `get_stream_writer()`로 흘려보내고,
`events.py`의 `_classify_progress()`가 이걸 **전부** `type: "tool_progress"`
로 감싸 원본은 `detail`에 옮겨 담는다(2026-08-14 엔진 교체 이후 항상 이
모양). 그런데 `frontend/src/pages/ChatPage/liveChat.ts`의 `reduce()`는 옛
엔진 시절 모양(`stage`/`queries`/`stage_done`/`task_extraction_result`/
`jira_status`가 **최상위 타입으로 직접** 온다는 가정)을 그대로 두고 있어서,
`tool_progress`를 처리하는 케이스가 아예 없었다 — `default`로 빠져 조용히
버려지고 있었다.

**영향 범위**: 검색어·진행 단계 표시 정도의 문제가 아니었다 —
`task_extraction_result`(업무 추출 결과, 확인 카드 데이터)와 `jira_status`
(Jira 현황 카드 데이터)도 같은 경로로 오기 때문에, **채팅에서 업무를
뽑으면 확인 카드 자체가 안 뜨고, Jira 현황도 안 떴다.** `ChatPage.tsx`의
`run()`이 `task_extraction_result`를 최상위 타입으로 다시 확인하는 별도
코드(체크박스 초기 선택용)도 같은 이유로 죽어 있었다.

`services/harness/registry.py`의 `_drain_with_progress()`가 실제로 만드는
raw 이벤트 모양을 그대로 `EventMapper.convert()`에 넣어 셸에서 직접
확인해서 이 분석을 실측으로 확정했다(`{'type': 'tool_progress', ...,
'detail': {'type': 'task_extraction_result', ...}}`로 나옴).

**수정**: `liveChat.ts`에 `unwrapToolProgress()` 추가 — `tool_progress`
이벤트를 원래 모양(`{...event.detail, tool_ref: event.tool_ref}`)으로 풀어서
기존 다섯 케이스가 그대로 처리하게 한다(로직을 두 곳에 안 둔다).
`subagent_alias`가 있으면(자식 네임스페이스 진행) 안 푼다 — `tool_started`/
`reasoning`과 같은 "서브 에이전트 자신의 것은 최상위에 안 보여준다" 규칙.
`ChatPage.tsx`의 `run()`도 같은 함수로 고침. `api/chat.ts`에 `detail`의
실제 모양을 나타내는 `ToolProgressDetail` 타입을 새로 붙였다.

**검증**: 목(mock) DB로 실제 그래프를 돌려 `stage`/`sources`/`stage_done`이
`tool_progress.detail`로 감싸져 오는 것, 프론트 타입체크가 새 언랩 로직과
맞물려 클린한 것을 확인. (자동화된 프론트 테스트 러너가 이 저장소에 없어서
`reduce()` 자체의 런타임 동작은 코드 추적으로 검증 — 이 환경엔 브라우저·
playwright도 없어 실제 화면은 직접 못 봄.)

## 4. document_search — "출처"(어느 문서를 보는 중인지) 계측

**구현**: `services/harness/registry.py`의 `_document_search()`를
제너레이터로 바꿨다(`_extract_tasks`와 같은 패턴). 진행 단계:
1. `{"type": "stage", "step": 1, "total": 2, "label": "관련 문서 좁히는 중"}`
2. coarse 검색이 끝나면 좁힌 문서 목록을 `{"type": "sources", "step": 1,
   "documents": [{"id": doc_id, "label": file_name}, ...]}`로 — 색인 안 된
   문서도 숨기지 않고 전부 보여준다(이 함수의 기존 "정직 표기" 원칙과 동일).
2. `{"type": "stage", "step": 2, "total": 2, "label": "본문에서 근거 찾는 중"}`
3. `{"type": "stage_done", "step": 2, "found": ..., "evidence": ...}`

직접 호출하던 기존 테스트(`tests/test_document_meta.py`)는 제너레이터를
끝까지 돌려 반환값을 얻는 헬퍼(`_run_document_search`)로 고쳤다.

**프론트**: 새 `sources` 이벤트/`SourceRef` 타입(`{id, label, url?}`) 추가.
`ProgressCard`에 파일 아이콘과 함께 후보 문서 이름 목록으로 표시(줄바꿈
없이 `queries`와 같은 자리, `stage` 전환에 초기화되지 않고 다음 단계가
도는 동안에도 계속 보임 — `queries`와 다른 점).

**검증**: 이 환경엔 팀에 색인된 실제 문서가 없어서, DB/임베딩을 mock한
실제 deepagents 그래프(스크립트 모델)로 전체 파이프라인을 돌려
`tool_started → stage → sources(문서 2건) → stage → stage_done →
tool_completed → result` 순서를 확인했다.

## 5. web_search — 같은 방식으로 확장

**질문**: "웹 검색에서 어떤 페이지를 검색하고 있는지도 안 뜨는데?"

**조사**: `services/websearch/client.py`가 Tavily `/search`를 **단일 POST
호출**로 부른다 — Tavily가 내부적으로 여러 페이지를 찾아서 결과 목록
하나로 한 번에 돌려준다. 즉 document_search와 달리 **우리가 제어하는 여러
단계가 없다** — "지금 이 페이지 보는 중" 같은 진짜 페이지 단위 실시간은
이 API로는 애초에 불가능하다(스트리밍 API가 아님).

**구현**: `_web_search()`도 제너레이터로 바꿔서, 검색 결과(제목·URL)가
도착하는 즉시 — 모델의 최종 답을 기다리지 않고 — `sources` 이벤트로
바로 보여주게 했다. document_search와 **같은 `sources` 이벤트를 공유**하기
위해 `SourceDocument`(`{doc_id, file_name}`) 타입을 `SourceRef`(`{id, label,
url?}`)로 일반화했다 — `url`이 있으면 웹 결과, 없으면 내부 문서. 화면은
`url` 유무로 링크(새 탭)와 일반 텍스트를 가른다.

직접 핸들러를 호출하던 기존 테스트(`tests/test_websearch.py`) 하나도
`list(...)`로 끝까지 돌리도록 고쳤다(제너레이터라 호출만으론 예외가 안 남).

**검증**: Tavily HTTP 호출을 mock한 실제 그래프 실행으로 `tool_started →
stage → sources(URL 2건, url 필드 채워짐) → tool_completed → result` 확인.

## 6. 서브 에이전트 위임 — "다른 에이전트에서도 흐름이 보이냐"는 질문에서 발견한 또 다른 공백

지훈이 "다른 에이전트에서도 마찬가지로 실행 흐름이 보이는거지?"라고 물어서
답하다가 하나 더 발견했다: 같은 도구를 쓰는 다른 에이전트(빌더로 만든
커스텀 에이전트 포함)는 이번 계측이 도구 레벨이라 그대로 적용되지만,
**서브 에이전트에게 위임하는 동안은 화면에 아무 표시가 없었다.**
`subagent_started`/`subagent_completed` 이벤트는 이미 `events.py`가 내고
있었는데(§14 계약에 있던 기존 이벤트), `liveChat.ts`가 이 둘을 처리하는
케이스 자체가 없어서 위임이 걸리는 동안 진행 카드가 멈춘 것처럼 보였다.

**결정**(지훈 확인): 위임 자체("지금 위임 중이다/끝났다")는 보여주되,
서브 에이전트 **자신의** reasoning·도구 진행은 여전히 최상위에 안 보여주는
기존 원칙은 그대로 둔다(Child는 메모리가 없다는 것과 같은 설계 판단).

**구현**:
- `cardTypes.ts`에 `SubagentRun`(`{runId, alias, name, taskSummary, status}`)
  추가. `liveChat.ts`: `subagent_started`가 `RUNNING`으로 새 항목을 만들고,
  `subagent_completed`가 **`run_id`로 정확히 짝을 맞춰**(FIFO 아님 —
  `tool_started`/`tool_completed`와 같은 이유, 병렬 위임 가능) 상태만
  `DONE`/`FAILED`로 바꾼다.
- `ProgressCard`에 위임 목록 섹션 추가 — 스피너(RUNNING)/체크(DONE)/
  실패 아이콘(FAILED) + "○○ 에이전트에게 위임[ 완료/실패]" + task_summary.
- `ChatPage.tsx`: 위임이 진행 중이면 카드 제목도 "○○ 에이전트에게 위임
  중"으로 최우선 표시(그동안 "생각하는 중"에 멈춰 있던 것보다 실제
  상황에 더 가까움).

**검증**: mock 모델 두 개(부모·자식)로 실제 위임을 그래프 레벨에서
재현해 `subagent_started`(run_id, subagent_alias, subagent_name,
task_summary)와 `subagent_completed`(같은 run_id, status)의 실제 필드
이름·값을 확인 — 프론트 필드 접근이 정확히 맞아떨어지는 것까지 실측.

## 7. 남은 일

- 이 문서에 적은 항목 전부 **아직 커밋 전**이다.
- 이 환경엔 브라우저·playwright가 없어서 실제 화면 렌더링은 못 봤다 —
  전부 목(mock) 데이터로 파이프라인 끝까지, 타입체크까지만 확인했다.
  브라우저 확인은 지훈 몫으로 남음.
- `sources`가 색인 안 된 문서·URL 없는 결과까지 전부 보여주는 "정직 표기"
  원칙은 지켰지만, `not_indexed`처럼 화면에서 "아직 못 읽음" 배지를 따로
  붙이지는 않았다 — 지금은 그냥 나열만 한다.
