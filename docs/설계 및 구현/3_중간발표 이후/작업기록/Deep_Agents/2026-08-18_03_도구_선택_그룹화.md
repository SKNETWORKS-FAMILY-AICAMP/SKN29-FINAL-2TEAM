# 2026-08-18_03 — 도구 선택 화면 카테고리 그룹화

> `2026-08-18_02_챗_사이드바_재구성과_추론_과정_표시.md`의 후속. 멘토 피드백을
> 받아 진행한 별도 작업 — 아직 커밋 전.

## 1. 배경 — 멘토 피드백

멘토가 도구 선택 UI를 보고, 지금처럼 도구를 하나하나(Jira 이슈 생성, Jira
이슈 조회 …) 따로 체크하게 하지 말고 "Jira를 선택하면 그 기능들이 자동으로
다 켜지는" 방식이어야 한다고 지적했다. 지훈이 이 피드백을 그대로 옮겨
"바로 만들지 말고 어떻게 할지 먼저 의논해보자"고 요청해, 구현 전에 설계
논의부터 진행했다.

## 2. 조사 — 지금 구조

- 내장 도구 13개(`services/harness/registry.py`의 `BUILTIN_TOOLS`)가 전부
  평평한 목록으로 저장·표시되고 있었다. 저장(`agent_tool`/
  `agent_version_tools`)도, 실행 조회(`ToolLoader.load()`)도 leaf
  `tool_ref` 문자열 하나하나를 다루는 구조라 그룹 개념이 코드 어디에도
  없었다.
- **한 번 있었다가 사라진 설계**: `docs/작업기록/jihun_buildingpage/
  2026-08-11_에이전트_도구_카탈로그_선택UI_v1.md`에 `category` 필드(문서/
  사람·부하/업무/Jira연동)를 붙였던 기록이 있는데, 그 뒤 도구를 6종→13종
  으로 늘리는 리팩터(`c6a3df3`)에서 필드째로 빠졌다. 처음 하는 고민이
  아니라 복원에 가까웠다.
- `ToolPickerModal.tsx`는 이미 MCP 탭에서 "서버 카드 안에 개별 도구
  체크박스" 패턴을 쓰고 있었다(서버 단위 마스터 체크박스는 없음) —
  내장 도구에도 같은 패턴을 얹으면 된다는 게 조사에서 나온 결론.
- MCP 도구를 서버 단위로 몰아 켜는 안은 2026-08-11에 이미 검토됐다가
  기각된 적이 있다(그때 이유: 저장이 도구 단위라 스키마 변경이 필요하고,
  MCP 도구는 어차피 전부 승인 게이트를 타서 개별 선택의 실익이 적음) —
  이번 요청은 그 대상이 아니라 **내장 도구** 쪽이라 별개로 판단했다.

## 3. 설계 논의 — 정한 것

지훈과 세 가지를 정했다:

1. **그룹 안 개별 체크박스는 계속 보여준다**(마스터 체크박스 + 개별
   체크박스 둘 다). 완전히 숨기는 안도 검토했지만, 마스터 체크박스는
   순수 화면 계산이라 나중에 "완전히 숨기기"로 바꿔도 저장 포맷·백엔드는
   안 건드리고 `ToolPickerModal` 렌더링만 고치면 된다는 것을 확인한 뒤
   1안으로 결정.
2. **`category`는 백엔드 `Tool` 정의에 필드로 둔다** — 프론트 정적
   매핑은 새 도구가 생길 때마다 두 곳(레지스트리 설명·프론트 매핑)을
   같이 고쳐야 해서 어긋나기 쉽다는 이유.
3. **`task_*` 4개는 성격대로 둘로 쪼갠다**: `task_extraction`(AI로
   문서에서 업무를 뽑는 기능)은 "업무 추출(AI)", 나머지 셋
   (`task_list`/`task_update`/`task_register`, 등록된 업무를 조회·수정
   하는 CRUD)은 "업무 관리".
4. **MCP 서버 쪽 마스터 체크박스는 이번엔 안 한다** — "일단 MCP는
   나중에 보자"(지훈). 서버 카드 구조는 그대로 두고 내장 도구 탭만
   손댐.

저장 포맷은 그대로 둔다(`tool_refs`는 여전히 leaf 문자열 배열) — 그룹은
순전히 화면 표현이고, 실행 경로(`ToolLoader.load()`, `agent_version_tools`,
`chat_session.tool_refs_override`)는 전혀 안 건드린다는 것도 이 시점에
확인했다.

## 4. 구현

**백엔드**:
- `services/harness/registry.py`의 `Tool` dataclass에
  `category: str = "기타"` 필드 추가. `BUILTIN_TOOLS` 13개 전부에 지정 —
  Jira(2: `jira_create_issues`/`jira_get_issues`), 문서(2:
  `document_search`/`document_list`), 업무 추출(AI)(1: `task_extraction`),
  업무 관리(3: `task_list`/`task_update`/`task_register`), 프로젝트(1:
  `project_list`), 팀원(1: `people_list`), 근무(2: `workload_report`/
  `absence_list`), 웹 검색(1: `web_search`). MCP 도구를 만드는
  `_mcp_tool()`/`_agent_tool()`은 `category` 인자를 안 넘겨 기본값
  "기타"로 남는다 — 어차피 이 값들은 `BUILTIN_TOOLS` 카탈로그로 안
  나가서 화면에서 안 쓰인다.
- `apps/agents/serializers.py::builtin_tool_response()`가 `category`를
  응답에 실어 보냄.

**프론트**:
- `frontend/src/api/agents.ts`의 `ToolChoice`에 `category?: string`
  추가(MCP 도구는 없을 수 있어 옵셔널).
- `ToolPickerModal.tsx`: "툴 선택" 탭을 flat map에서 카테고리별 카드로
  바꿈 — `groupByCategory()`가 첫 등장 순서를 그대로 유지해 묶고, 각
  카드 헤더에 "전체 선택" 마스터 체크박스(그 카테고리 도구가 전부
  선택됐으면 체크)를 얹었다. MCP 탭 구조(서버 카드 + 개별 체크박스)는
  안 건드림.
- **마스터 체크박스 전용 콜백을 새로 뺐다(`onToggleGroup`)**: 처음에는
  `onToggle`을 그룹 크기만큼 연달아 부르는 안을 생각했는데, 세 호출부
  중 `ChatPage.tsx`의 `toggleSessionTool`은 `sessionToolOverride` 상태를
  `await`로 API 응답을 받은 뒤에야 갱신하는 구조라, 같은 렌더 틱 안에서
  연달아 부르면 매번 같은(아직 안 바뀐) `current`를 기준으로 계산해
  **뒤 호출이 앞 호출을 덮어쓰고 마지막 도구 하나만 반영되는 버그**가
  났을 것이다. 그래서 그룹 전체를 한 번에 계산해 한 번만 저장하는
  별도 콜백을 두고, 세 호출부(`AgentEditPage.tsx`의 `toggleToolGroup`,
  `AgentVersionEditPage.tsx`의 `toggleToolGroup`, `ChatPage.tsx`의
  `toggleSessionToolGroup`) 전부에 대응하는 배치 토글 함수를 만들어
  연결했다. `ChatPage.tsx`는 기존 `toggleSessionTool`의 저장 로직을
  `applySessionToolRefs(nextList)`로 뽑아 단일·그룹 토글이 같은 경로를
  타게 정리했다.
- 마스터 체크박스의 "전체 선택" 판정은 `ConfirmCard`(업무 확인 카드)가
  이미 쓰던 것과 같은 2상태(선택/미선택) 방식을 그대로 따랐다 — 부분
  선택일 때 대시(indeterminate) 표시를 새로 만들지 않고, 기존 `Checkbox`
  컴포넌트를 안 건드리는 쪽을 택함(이 저장소에 이미 있는 패턴을
  재사용해 새 컴포넌트 API를 늘리지 않음).

## 5. 검증

- 백엔드 전체 테스트 771개 통과(`python manage.py test`), 새 필드가
  포지셔널 인자 충돌 없이 들어갔는지도 기존 스위트가 그대로 커버.
- `apps/agents/serializers.py::builtin_tool_response()`를 셸에서 직접
  호출해 13개 도구가 의도한 8개 카테고리로 정확히 나오는 것 확인.
- `GET /api/agents/tools/`를 실제 로그인 토큰으로 호출해 HTTP 응답에도
  `category`가 그대로 실려 오는 것까지 확인 — `2026-08-18_01`에서 만든
  member 테스트 계정(UA004)의 비밀번호를 모르고 있어서, 검증을 위해
  `testpass1234`로 재설정했다(로컬 DB 데이터만 바뀜, 코드 변경 아님).
- `tsc --noEmit -p tsconfig.app.json` 통과.
- **화면은 직접 못 봤다** — 이 작업 환경엔 브라우저·playwright가 없어서
  실제 렌더링 확인은 못 했고, 검증된 MCP 카드 구조를 그대로 재사용한
  것으로 신뢰도를 높이는 데 그쳤다. 브라우저 확인은 지훈 몫으로 남음.
