# 2026-08-21_03 — 외부 Write Tool 재시도 안전성

## 1. 이 문서의 결론

`main` 병합으로 들어온 외부 Write Tool idempotency(`factory.py`의
`_IdempotencyAwareTool`, `tool_call_idempotency` 테이블)는 문서1·문서2가
"아직 없다"고 적어둔 항목이지만, 실제로 뜯어보니 **절반만 해결한 상태다.**

1. 이 idempotency가 막는 것: HITL resume·checkpoint 재시도로 **같은
   `tool_call_id`** 가 프레임워크에 의해 다시 실행되는 경우.
2. 이 idempotency가 안 막는 것: 모델이 timeout·오류를 보고 스스로 판단해
   **새 `tool_call_id`** 로 같은 작업을 다시 시도하는 경우 — 문서2 §7이
   "side-effect Tool은 idempotency가 확인되지 않으면 자동 재시도하지
   않는다"고 이미 원했던 바로 그 경우다.
3. `2026-08-21_01`(Tool timeout 재설계)이 만드는 timeout 메커니즘
   자체가 이 위험을 실제로 키운다 — timeout은 "실패"가 아니라 "결과를
   모름"이라, 모델이 재시도하면 원래 호출이 뒤늦게 성공하고 재시도도
   성공해 중복이 날 수 있다.
4. 해결책은 두 단계로 충분하다고 판단했다 — 완전 자동 차단(3안)은 채택
   하지 않는다.
   - **1단계**: timeout 메시지를 `side_effect` 여부로 갈라 side-effect
     도구는 "실행 여부 불명, 자동 재시도 금지"를 명시한다
     (`2026-08-21_01` §6에 반영 완료).
   - **2단계**: 재시도도 결국 HITL 승인을 다시 거치므로, 그 승인 카드에
     "직전 timeout과 같아 보이는 요청" 경고를 띄운다(이 문서 §4).
5. 자동 차단(같은 run 안에서 같은 도구+비슷한 입력의 재시도를 서버가
   강제로 막는 것)은 채택하지 않는다 — "비슷한 입력"의 판단 기준이
   모호해 오탐(false positive)이 정당한 재시도까지 막을 수 있고, 이
   저장소가 지금까지 택해 온 "판단은 사람에게 남기고 서버는 정보만
   정직하게 준다"는 방향과도 안 맞는다. 실제로 중복 실행 사고가
   확인되면 그때 다시 검토한다.

**2026-08-21 구현 완료** — 1단계는 `middleware/tool_timeout.py`의
`_TIMEOUT_MESSAGE`, 2단계는 `mcp_call_note`의 `TIMED_OUT` 행
(`McpCallNoteRepository.record_timeout()` / `has_timeout_in_run()`)과
`hitl_warnings.py`의 경고. 3단계(자동 차단)는 §4.3대로 채택하지 않았다.

## 2. 실제 구현이 무엇을 막는지 — 정확한 범위

`services/agent_runtime/factory.py`:

```python
idempotency_scope = (
    tool.side_effect and langchain_tool_call_id and context.run_id
)
```

키는 `(run_id, langchain_tool_call_id)`다. `langchain_tool_call_id`는
모델이 낸 `AIMessage.tool_calls[i]["id"]`이고, 이 값은 checkpoint에 그대로
저장돼 재개해도 같은 값으로 남는다(`DB/migrations/2026-08-19_tool_call_
idempotency.sql` 주석). 그러므로 이 메커니즘이 실제로 막는 건 "같은
tool_call이 프레임워크 사정으로 두 번 실행되는 것"이다.

```text
막힘: 승인 카드 뜸 → 재개 → LangGraph가 같은 super-step을 재실행하며
      같은 tool_call_id가 다시 들어옴 → 캐시된 결과 반환, 진짜 실행 skip

안 막힘: timeout/오류로 첫 tool_call이 끝남 → 모델이 새 tool_call(다른
      tool_call_id)로 같은 작업을 다시 요청 → 캐시 키가 다르므로 miss →
      진짜로 다시 실행
```

## 3. 왜 지금 이게 더 급해졌나 — `2026-08-21_01`과의 연결

`2026-08-21_01`이 되살리는 timeout 미들웨어는 `future.result(timeout=...)`
로 "기다리기를 포기"할 뿐 실행 중인 스레드를 강제로 죽이지 못한다(같은
문서 §6, 이전 설계에도 있던 정직한 기록). 즉:

```text
jira_create_issues 호출 → 480초 지나 우리는 포기, 모델에게 에러 반환
  → 그런데 백그라운드 스레드는 계속 돌고 있음
  → 481초째에 실제로 성공 (record_result()도 뒤늦게 실행됨,
    원래 tool_call_id로)
  → 모델은 "실패했나 보다" 판단해 새 tool_call_id로 재시도
  → 새 tool_call_id는 캐시에 없으므로 진짜로 다시 실행
  → Jira 이슈 2개 생성
```

timeout 미들웨어가 없던 때는 이 시나리오 자체가 없었다(그냥 무한 대기).
`2026-08-21_01`이 timeout을 다시 넣는 순간 이 위험이 실제로 열리므로, 두
문서를 같이 반영해야 한다.

## 4. 채택한 설계 — 정보를 정직하게 주고 판단은 사람에게 둔다

### 4.1 1단계 — timeout 메시지 명시 (완료, `2026-08-21_01` §6)

MCP 도구가 timeout나면 "실행 여부가 확인되지 않았습니다. 자동으로
다시 시도하지 마세요"를 명시한다. MCP는 항상 side_effect=True라
`side_effect`로 분기할 필요조차 없다 — 이 timeout 미들웨어가 다루는
대상이 애초에 MCP뿐이라 메시지는 하나로 고정한다(`2026-08-21_01` §6,
2026-08-21 정정). 프롬프트 수준 방어라 모델이 무시할 수 있다는 한계는
있다 — 그래서 2단계가 필요하다.

### 4.2 2단계 — 승인 카드 경고

모델이 메시지를 무시하고 재시도하더라도, side-effect 도구는 재시도든
아니든 항상 HITL 승인을 거친다(기존 메커니즘, `interrupt_on`). 이 카드에
"같은 run 안에서 같은 `tool_ref`가 timeout 이력이 있다"는 경고를
추가한다.

```text
[승인 대기] jira_create_issues(title="분기별 보고서 작성")
⚠ 같은 도구가 이 대화에서 방금 timeout으로 결과를 확인하지 못했습니다.
   이미 실행됐을 수 있습니다 — 승인 전에 확인해 주세요.
```

**판단 기준은 "같은 `tool_ref`" 하나로 좁힌다** — 입력값(args) 유사도까지
비교하지 않는다. args 비교는 "제목이 한 글자만 달라도 다른 요청인가"
같은 모호한 판단이 필요해 오탐·누락이 쉽다. `tool_ref` 단위는 거칠지만
확실하다 — 같은 run 안에서 같은 write 도구가 최근에 timeout났다는 사실만
보여주고, 그게 지금 승인하려는 요청과 같은 건지는 사람이 내용을 보고
판단한다.

**구현 지점**: HITL 카드를 만드는 곳(`interrupt_on` 처리 경로)이
`tool_call_idempotency`와 별도로, 이 run 안에서 timeout으로 끝난
`(run_id, tool_ref)` 목록을 조회할 수 있어야 한다. 지금 `tool_call_
idempotency`는 **성공한** 결과만 기록하므로(§2), timeout 사례는 별도로
기록할 자리가 없다 — `2026-08-21_01`의 timeout 미들웨어가 timeout이 나는
시점에 이 목록에 `(run_id, tool_ref, tool_call_id)`를 남기도록 같이
구현해야 한다(신규 테이블 또는 `tool_call_idempotency`에 상태 컬럼 추가 —
구체적 스키마는 구현 착수 시 결정).

### 4.3 채택하지 않은 3단계 — 자동 차단

승인 자체를 막고 별도 확인을 강제하는 안은 기각했다. 이유는 §1-5와 같다 —
판단 기준(무엇을 "같은 요청"으로 볼지)이 모호해 오탐 위험이 있고, 이
저장소는 지금까지 "숨기지 않고 알려주되 막지는 않는다"는 방향을 일관되게
택해 왔다(RBAC 노출 정책 변경, `runtime_policy.py`의 `is_tool_allowed_
for_role()` 판단 등). 실제 중복 실행 사고가 관측되면 그때 재검토한다.

## 5. 이 설계가 풀지 않는 것

- args까지 비교하는 정교한 중복 탐지 — §4.2에서 의도적으로 배제했다.
- 자동 차단 — §4.3에서 의도적으로 배제했다.
- MCP 서버 자체의 idempotency(예: idempotency-key 헤더 지원) — 우리가
  통제할 수 없는 외부 서버의 특성이라 플랫폼이 보장할 수 없다.
- Run 전체 wall-clock timeout·진짜 취소 전파 — `2026-08-21_01` §6과
  동일하게 범위 밖이다.
