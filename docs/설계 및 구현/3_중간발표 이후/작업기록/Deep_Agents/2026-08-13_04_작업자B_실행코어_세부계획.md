### 8순위 — 프롬프트 인젝션 방어 2단계

**2026-08-19: 사용자 판단으로 마지막 순서로 미룸** — 아래 후보 조사는 끝냈지만

**방향 재검토(2026-08-19)**: 원래 설계(`2026-08-19_01` §6-2)는 자체 규칙
(패턴 목록)으로 harness/MCP 도구 결과를 스캔하는 안이었는데, 이 방식은 오탐을
줄이려면 실제로 걸어 보고 계속 튜닝해야 한다 — **이 프로젝트는 그 튜닝
과정에 시간을 쓰지 않기로 했다.** 대신 이미 이 문제를 상품화해 파는
외부 guardrail API로 대체할 수 있는지를 검토한다. 붙는 자리는 원래
설계와 같다 — harness/MCP 도구 결과가 모델에게 전달되기 직전(`wrap_tool_call`,

매칭 대신 외부 API에 그 텍스트를 보내 판정을 받는 것으로 바뀔 뿐이다.

**후보 세 곳 조사 결과(2026-08-19, 웹 검색으로 확인 — 링크는 완료 보고서에
남길 것)**

| | 탐지 대상 | 호출 방식 | 가격 | 비고 |
|---|---|---|---|---|
| **Microsoft Prompt Shields**(Azure AI Content Safety) | User Prompt Attack + **Document/Indirect Attack**(우리가 겨냥하는 케이스와 정확히 일치 — 문서·이메일 등 외부 콘텐츠에 숨은 지시) | REST(`.../contentsafety/text/v1/`), API 키 인증 | 공개 문서에 가격이 안 나와 있음 — Azure 포털에서 별도 확인 필요 | 지원 언어에 한국어가 없다(중/영/불/독/서/이/일/포) — 한국어 콘텐츠 탐지 정확도 실측 필요 |
| **Google Model Armor** | Prompt Injection/Jailbreak, 민감정보, 안전 필터, 악성 URL, 이미지 OCR까지 | REST/gRPC(`SanitizeUserPrompt`/`SanitizeModelResponse`), **LangChain 네이티브 통합 지원**(공식 문서에 명시) | **투명하게 공개** — 월 2백만 토큰 무료, 이후 $0.10/백만 토큰 | 이 프로젝트가 이미 LangChain/deepagents 기반이라 통합 부담이 가장 작아 보인다 |
| **Lakera Guard** | Prompt injection, 데이터 유출, jailbreak | 자체 REST API(Playground/API 키 제공 확인) | 페이지에서 확인 못 함 | **2026년 Check Point가 인수 발표**(~3억 달러 규모) — 독립 API로서 계속 이 형태로 남을지, 가격·로드맵이 어떻게 바뀔지가 불확실하다. 지금 이 프로젝트가 신규로 붙이기엔 제품 연속성 리스크가 있다 |

**설계 시 같이 풀어야 할 것**

1. **지연시간**: 매 tool 결과마다 외부 API를 왕복으로 부르면 응답이 그만큼
   느려진다 — Tool별 timeout을 일괄로 걸지 않기로 한 지금은 정해진 예산이
   없으니, 이 API 호출 자체가 새로운 지연 요인이 되지 않을 정도로 빨라야
   한다. 스캔 대상을 harness/MCP 결과 중 실제로 외부 콘텐츠를 담는 도구로
   좁히는 게 맞다(모든 tool 결과를 다 보낼 필요는 없다).
2. **장애 시 정책(fail-open vs fail-closed)**: 외부 API가 타임아웃/장애
   나면 원문을 그냥 통과시킬지, 통과 자체를 막을지 정해야 한다.
3. **비용**: 토큰 기반 과금이라 스캔하는 텍스트 양에 비례해 계속 든다 —
   무료 티어(Model Armor 기준 월 2백만 토큰) 안에서 실제 트래픽이 감당되는지
   가늠이 필요하다.
4. **키 관리**: 새 외부 서비스 자격증명이 하나 더 늘어난다(Tavily/RunPod/
   OpenAI와 같은 취급).

**아직 결정 안 한 것**: 세 후보 중 하나를 확정하지 않았다 — 위 표의 근거만
정리했다. Model Armor가 가격이 투명하고 LangChain 통합이 공식으로 있다는
점에서 지금 스택과 가장 잘 맞아 보이지만, 한국어 정확도(Prompt Shields는
한국어 미지원이 확인됨, Model Armor/Lakera는 한국어 정확도 자체를 아직
확인 못 함)는 셋 다 실제로 붙여서 테스트해봐야 안다. 3순위(1단계)가 이미
배포돼 있어 최소 방어선은 있는 상태 — 급하지 않게 후보를 좁히면 된다.

### 11순위 — Jira 담당자별 쓰기 권한(팀원 본인 담당 건만)

**2026-08-19: 사용자 판단으로 나중으로 미룸** — 아래 조사·설계 방향은 끝냈지만
착수는 나중에 한다.

**요구사항(2026-08-19)**: 지금 `jira_create_issues`(side_effect=True)는
`runtime_policy.is_tool_allowed_for_role`이 역할 하나만 보고 이진 판단한다
— leader면 전부 허용, member면 전부 차단(`DEFAULT_WRITE_TOOL_ALLOWED_ROLES
= {"leader"}`). "이슈 단위로 담당자가 본인인지"를 볼 개념 자체가 지금
없다. 팀원이 **본인이 담당자인 이슈에 한해서만** Jira에 쓸 수 있게
하고 싶다.

**실제 코드로 확인한 것**

- `jira_create_issues`의 `input_schema`는 이미 issue별
  `assignee_account_id`를 받는다(`services/harness/registry.py`) —
  다만 이건 우리 서비스의 내부 `account_id`가 아니라 **Jira Cloud 원본
  accountId**다(`apps/connectors/clients.py::create_jira_issues` —
  "GDPR 이후 이메일로는 안 된다, Atlassian accountId여야 한다"는 주석까지
  확인).
- 우리 내부 `account_id`(로그인 계정) → Jira accountId로 가는 매핑이
  지금 스키마에 없다. 있는 건 **반대 방향**뿐이다: `mock_hr.person_link
  (person_id, sys_type='JIRA', ext_email)`가 "Jira 이슈 담당자 **이메일**
  → HR person_id"를 매핑해서 `exist_task.assignee_person_id`를 채우는
  데 쓰인다(읽기 전용 동기화 경로, `DB/schema.sql`). `person_id` ↔
  `account_id`는 또 별도로 `member_invite` 흐름에서 매핑된다(같은 파일
  "PAGE 3-C" 절 — 팀장이 HR person을 지정해 초대 코드를 발급하고 팀원이
  수락하면 매핑됨).
- 이 둘을 이으면 이론상 "내 account_id → 내 person_id → 내 ext_email"까지는
  알 수 있지만, Jira API에 실제로 넘겨야 하는 값은 **accountId**라서
  마지막 한 칸(이메일 → Jira accountId)이 비어 있다. Jira 사용자 검색
  API(`/rest/api/3/user/search?query=`)로 그때그때 조회하거나, 한 번
  리졸브해서 어딘가 저장해 둬야 한다.

**설계 방향(초안 — 착수 전, 검증 필요한 것들이 있다)**

1. 팀원에게도 `jira_create_issues` 노출 자체는 열어준다 — 다만 지금의
   이진 규칙(`is_tool_allowed_for_role`)에는 "본인 담당 건에 한해 member도
   허용"이라는 제3의 상태를 표현할 자리가 없어서, `runtime_policy.py`의
   권한 모델 확장이 먼저 필요하다.
2. 실행 직전(`_to_langchain_tool()._run()`의 역할 재검사 자리, 또는
   `_jira_create_issues` 핸들러 자체)에서 issue별로 "이 accountId가
   호출자 본인 것인가"를 검사한다 — 위 person_link/member_invite 체인을
   실제로 태워 확인해야 한다.
3. 배치(`issues` 배열)에 본인 담당과 아닌 담당이 섞여 있을 때 어떻게
   할지 정해야 한다 — 전체 거부 vs 본인 담당분만 통과시키고 나머지는
   개별 실패로 응답(이미 `create_jira_issues`가 "건별 성공·실패를 그대로
   돌려준다"는 계약이라 이쪽이 더 자연스러워 보인다).

**확인 필요(미검증)**: `person_link.ext_email`이 실제로 로그인 계정
이메일과 항상 같은 값인지(팀원이 다른 이메일로 Jira를 쓸 가능성),
지금 Jira 연동이 쓰는 저장된 정적 토큰(사용자별 OAuth가 아니라 팀 단위
토큰)의 권한 범위로 `user/search` API를 실제로 호출할 수 있는지 — 이
둘은 실제 Jira 연결로 라이브 테스트해봐야 안다.

### 12순위 — 채팅 응답 시간 계측 — 완료(2026-08-19)

`agent_started`부터 `result`/`error`까지의 총 완료 시간(wall-clock)을
`time.monotonic()` 기반으로 재서 스트림 이벤트(`duration_ms`)와 대화
이력에 실어 보내는 것이다 — 새 DB 컬럼 없이 스트림 자체 타이밍에서
즉석으로 계산한다. HITL resume으로 재개된 스트림은 `EVENT_AGENT_STARTED`
를 새로 안 내서 `duration_ms`가 안 붙는데, 조작된 값을 꾸며내는 대신
정직하게 생략한다. 자세한 기록은
`2026-08-19_13_채팅응답시간계측_구현완료.md`.
