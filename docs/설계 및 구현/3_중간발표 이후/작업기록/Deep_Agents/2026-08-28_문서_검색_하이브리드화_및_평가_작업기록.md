### 수행 내용과 변경 전후

- 기존 `document_search`는 임베딩 코사인 유사도만 사용하고 모델이 `top_k`를
  1~20 사이로 바꿀 수 있었다. 도구 입력을 `query` 하나로 단순화하고 결과 수를
  서버에서 20개로 고정했다.
- `chunk.raw_text` 컬럼을 새로 만들지 않았다. 키워드 검색은 제목 경로 등 청킹
  문맥이 붙은 기존 `chunk.search_text`를 사용하고, 모델에 돌려주는 실제 근거
  본문은 이미 파싱 결과로 보관 중인 `doc_block.content`를 사용한다.
- lexical 후보는 PostgreSQL `simple` 전문검색, `pg_trgm` 부분어절 유사도,
  정확 포함 보너스로 구성한다. 후보군 안에서 각 점수를 정규화하고 lexical
  0.5 + 코사인 0.5로 최종 순위를 계산한다. lexical 내부 초기 가중치는
  FTS 0.55 + trigram 0.25 + 정확 포함 0.20이다.
- 벡터·FTS·trigram에서 각각 60개 후보를 모아 합친 뒤 Top-20을 반환한다.
  팀·개인·공유·프로젝트 문서 범위, 현재 revision, active/deleted/access 필터와
  미색인 문서를 결과에 명시하는 기존 정책은 유지했다.
- `pg_trgm` 확장과 `search_text`의 FTS·trigram GIN 인덱스를 멱등 마이그레이션으로
  추가하고, 공식 마이그레이션 검사기가 확장과 비고유 인덱스도 확인하도록 했다.
  업무 추출이 쓰는 기존 순수 벡터 검색은 변경하지 않아 역할별 검색 경로를 분리했다.

### 검증 결과와 제한

- 로컬 PostgreSQL에 마이그레이션을 적용했고 공식 검사 52개 항목 모두 통과했다.
- 실제 PostgreSQL에서 새 하이브리드 쿼리를 실행해 FTS·pg_trgm 연산자와 psycopg
  파라미터 결합이 정상임을 확인했다. 현재 로컬 DB에는 색인 문서가 없어 결과
  품질 자체는 측정하지 못했고 빈 범위 실행으로 SQL 호환성을 검증했다.

  수집 전에 중단되므로 의존성이 갖춰진 `web` 컨테이너에서 검증했다.
- 0.5:0.5 및 lexical 내부 가중치는 합리적인 초기값이지 품질 실험으로 확정된

### 공용 DB 활용 위험 검토

- 현재 `.env`의 `DATABASE_URL`은 공용 RDS가 아니라 Docker 로컬 DB
  `db:5432/project_copilot`이다. AWS Compose도 같은 `.env`를 읽으므로 현재 로컬
  환경변수만으로는 공용 DB에 접속할 수 없다.
- 웹·워커의 `DATABASE_URL`을 RDS로 바꾸면 평가와 무관한 쓰기·백그라운드 작업이
  공용 DB에 반영될 수 있어 금지한다.
- 공용 DB를 활용하려면 별도 읽기 전용 role과 평가 전용 연결 변수를 사용하고,
  승인받은 문서의 현재 revision·block·활성 chunk·embedding만 로컬 격리 DB로
  복사한 뒤 로컬에서 평가한다. 계정·대화·업무 표와 S3 원문은 기본적으로 제외한다.
- 공용 DB에 청크·embedding이 없다면 RDS 메타데이터만 가져와도 검색 평가는
  불가능하다. 이 경우 승인된 원문 또는 비식별 복사본을 로컬에서 색인해야 한다.

### 공용 DB 읽기 전용 실측

- 사용자가 `.env`에 추가한 `EVAL_SOURCE_DATABASE_URL`은 서울 RDS와 SSL 연결을
  가리킨다. 비밀값은 출력하거나 애플리케이션 컨테이너에 주입하지 않았다.
- 연결 계정은 SELECT 전용이 아니고 DB CREATE 및 `doc` INSERT/UPDATE/DELETE가
  가능한 고권한 계정이다. 대신 일회성 psycopg 세션에서 transaction read-only,
  statement timeout 5초, lock timeout 1초를 강제하고 SELECT 집계 후 rollback했다.
- 공용 DB에는 사용 가능한 문서 13개, 활성 청크 301개, 벡터 301개가 있다.
  현재 revision이 완전히 색인된 10개 중 개인 Markdown 2개는 제외하고 팀 PDF
  8개만 실문서 평가 복사 후보로 정했다. 본문과 파일명은 출력하지 않았다.
- 첨부 피드백을 반영해 실문서 템플릿에 `content_hash`, 검색 가중치·Top-K·모델,
  실행 commit SHA 동결 필드를 추가했다. 사전 합격 기준은 Recall@20 벡터 이상,
  MRR·Precision@5 하락폭 0.05 이내, 금지 근거 Top-3 잠식 0으로 수치화했다.
- 팀 PDF 8개의 본문·청크·embedding을 로컬로 복사하는 단계는 데이터 반출이므로
  사용자 확인 후 별도 읽기 전용 추출기로 진행한다.

### 보강 내용

- 복사 시점의 승인 문서 8개를 정확한 `doc_id + revision + content_hash` manifest로
  동결했다. 가져오기 스크립트는 현재 조건에 맞는 임의의 8개가 아니라 이 세 값이
  모두 일치할 때만 실행된다.
- 기존 출처 미확인 벡터는 보존한다. 재임베딩 결과는 별도 `verified_vector`에 두고
  모델·차원·document 모드·정규화·본문 hash·생성 시각·commit SHA를
  `verified_vector_run`과 함께 기록한다. 294개를 모두 받은 뒤 하나의 로컬 DB
  트랜잭션으로 저장하며 기존 결과가 있으면 덮어쓰지 않는다.
- RunPod 전송 payload는 최대 20개씩의 `chunk.search_text` 배열뿐이다. 파일명,
  원본 PDF, block 전체, 문서·계정 ID, 대화·업무 데이터는 보내지 않는다.
- Golden 파일의 본문 미포함과 로컬 DB의 추출 본문 포함을 별도 필드로 분리했다.
  폐기 도구의 `evaluation-complete`는 만료 전 즉시 삭제를 허용하고, `expired`만
  예정 시각 전에 거부하므로 기존 정책과 일치함도 재확인했다.

### 검증과 현재 차단 요인

- Django `QueryEmbeddingTests` 3개가 통과해 기존 query 모드와 새 document 모드
  응답 검증이 함께 동작한다.
- 실제 본문 전송 전 비민감 문자열 한 건으로 배포 상태를 확인했다. 현재 RunPod
  endpoint는 `embed_documents`를 아직 지원하지 않아 FAILED를 반환했다. 따라서
  실문서 294개는 전송하지 않았다.
- 이 저장소의 `runpod_worker`는 읽기용 사본이고 실제 배포 정본은 별도 비공개
  저장소와 고정 이미지다. 운영 endpoint의 이미지 변경은 기존 문서 처리·검색에도
  영향을 줄 수 있으므로 별도 배포 승인과 정본 저장소 접근 없이 진행하지 않는다.
