# 도구 연쇄 실패 — 이미 실패가 확정된 뒤에도 다음 호출을 보내던 곳 수정 (2026-08-20)

## 요청

"Jira 인증이 만료되어 등록하지 못했습니다"가 지금은 실제 **등록(생성) 호출까지
가서** 뜨는데, 그 전에 있는 **조회 호출에서 이미 실패가 정해지는데도** 다음
호출까지 마저 보낸다 — 이렇게 이미 결과를 아는 호출을 또 보내 토큰(도구
호출)을 낭비하는 곳을 전부 찾아서 고쳐 달라는 요청.

## 찾은 것 — 정확히 이 패턴에 해당하는 곳 2곳(+1)

찾는 기준: **"먼저 하는 호출 A가 실패했는데, 그 실패 이유가 뒤에 하는 호출
B도 반드시 똑같이 실패시킬 이유(예: 같은 자격증명)일 때, A의 실패를
삼키고(swallow) B를 마저 보내는 코드"**. Jira/Drive 커넥터 코드
(`apps/connectors/clients.py`) 전체와 이걸 조합해 쓰는
`services/harness/registry.py`, `services/document_intake/service.py`를
훑었다.

### 1. `find_jira_account_id_by_email()` — 신고하신 바로 그 사례

`services/harness/registry.py`의 `_jira_create_issues()`(`jira_create_issues`
도구의 실제 구현)는 이렇게 돈다.

```
_fill_default_jira_assignee()  # 담당자 안 정했으면 요청자 이메일로 Jira 계정 조회
    → find_jira_account_id_by_email()  # ← "조회"
create_jira_issues()  # 실제 이슈 등록  ← "등록"
```

**문제**: 조회와 등록 둘 다 `credential_for(account_id=..., connector_type=JIRA)`로
같은 팀장의 Jira 자격증명을 쓴다. 그런데 `find_jira_account_id_by_email()`은
`OAuthError`(자격증명 만료·재연결 필요 등)까지 "그냥 못 찾았다"로 뭉뚱그려
삼키고 `None`을 돌려줬다. 그러면 코드는 아무 일 없었다는 듯 등록 호출로
넘어가고, 거기서 **똑같은 자격증명으로 똑같이** 막혀서야 비로소
"Jira 인증이 만료되었습니다"가 나왔다 — 실패할 걸 이미 아는 Jira API 호출을
한 번 더 보낸 것이다(신고하신 것과 정확히 같은 현상).

**고친 것**: `OAuthError`만 따로 떼서 삼키지 않고 그대로 올리게 했다. "정말
못 찾은 것"(검색 결과 0건·다건, 네트워크 오류, 이상 응답)은 원래 원칙대로
계속 조용히 `None`으로 접는다 — 이건 다음 호출이 반드시 같은 이유로
실패한다는 보장이 없기 때문이다. `cloud_id`가 없는 경우도 같은 이유로
예외를 올리도록 같이 고쳤다(등록 쪽이 내는 것과 같은 메시지로).

파일: `apps/connectors/clients.py`(`find_jira_account_id_by_email`),
`services/harness/registry.py`(`_fill_default_jira_assignee`,
`_jira_create_issues` 문서화만 보강, 로직은 그대로).

### 2. `_fetch_and_summarize()`의 문서 일괄 수신 — 같은 패턴을 배치로

`services/document_intake/service.py`가 연결된 Drive 폴더의 대기 문서를
하나씩 내려받는 곳(`intake_connector_documents`, 채팅 도구가 아니라
프로젝트 화면의 백엔드 배치). 문서마다 `download_drive_file()`을 부르는데,
Drive 자격증명이 만료된 경우 **첫 번째 문서에서 이미 그걸 알게 되는데도**
남은 문서 전부에 대해 똑같이 실패할 다운로드를 계속 시도하고 있었다 —
문서가 15건이면 15번 다 실패를 반복하는 구조.

**고친 것**: `OAuthError`가 나면 그 시점에서 배치를 멈추고, 아직 못 받은
나머지 문서에는 같은 사유를 일괄로 남긴다. 파일 하나만의 문제(디스크 오류
등, `OSError`/`RepositoryError`)는 원래 원칙("한 건의 실패는 그 한 건으로
끝난다")대로 그대로 두고 나머지는 계속 시도한다 — 이건 다음 파일도 같은
이유로 실패한다는 보장이 없어서다.

파일: `services/document_intake/service.py`.

### (참고) 이 패턴이 아니라서 그대로 둔 곳들

Drive 쪽 나머지 함수들(`_drive_children`, `list_drive_files`,
`get_drive_folders`, `download_drive_file`)은 실패를 삼키지 않고 그 자리에서
바로 예외를 올리고 있어 이미 올바르게 동작하고 있었다 — 손대지 않았다.
`services/harness/runner.py`, `tracing/`, `guardrails/` 등의 넓은
`except Exception`들은 "이 호출 하나의 실패로 전체를 죽이지 않는다"는
용도(로그 적재, 제목 생성 등)라 뒤이어 같은 이유로 반드시 실패하는 두
번째 호출이 없다 — 이 패턴에 해당하지 않는다.

## 검증

기기에서 새로 받은 스냅샷(services/backend/apps/tests/DB/config) 위에
수정분을 얹고, 원본과 diff로 의도한 변경만 있는지 확인한 뒤 관련 테스트만
실행했다.

- 새로 추가한 테스트 11개(`test_connectors.py` 6개,
  `test_harness.py` 3개, 새 파일 `test_document_intake.py` 2개) 전부 통과.
- `tests.test_connectors`, `tests.test_harness` 전체(104개, 원래 93개 +
  신규 11개) 재실행 — 실패 2건·에러 3건은 전부 이번 수정과 무관한 기존
  문제(수정 전 원본 스냅샷에서 그대로 재현 확인): Jira OAuth scope 문구
  드리프트 1건, 이 테스트 환경에 `ANTHROPIC_API_KEY`/`OPENAI_API_KEY`가
  없어서 나는 것 2건, 실제 DB에 네트워크로 못 붙어서 나는 것 2건(이 샌드박스
  자체의 알려진 제약). 새로 생긴 실패는 0건.

## 남은 것

- Jira OAuth authorize scope가 테스트 기대값(`read:jira-work read:jira-user
  offline_access`)과 실제 코드(`write:jira-work` 포함)가 어긋나 있다 —
  이번 요청과 무관해서 손대지 않았지만, 실제로 등록(쓰기) 권한을 요구하는
  스코프라면 의도적인 변경인지 확인이 필요해 보인다.
- 이 패턴(먼저 실패가 조회 단계에서 확정되는데 등록 단계까지 가는 것)이
  Jira/Drive 밖에도 있을 수 있다 — MCP 커넥터(`services/mcp/`)는 서버마다
  자격증명 구조가 달라 이번 훑기에서는 우리 내장 커넥터(Jira/Drive)만
  확인했다. 필요하면 MCP 쪽도 같은 기준으로 별도로 봐야 한다.
