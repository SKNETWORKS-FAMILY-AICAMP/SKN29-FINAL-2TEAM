# 1. 문제의식 — 왜 평가 프레임워크가 필요했나 (2분)

*[슬라이드: 프로젝트 한 줄 소개 + "이 에이전트가 안전한가?"라는 질문]*

"저희 프로젝트는 사용자가 시스템 프롬프트, 모델, 툴·서브에이전트 구성을 직접 골라서 에이전트를 만드는 플랫폼입니다. 그런데 사용자가 자유롭게 조합을 바꿀 수 있다는 건, 반대로 말하면 그 조합이 실제로 안전하고 의도대로 동작하는지 저희가 계속 검증할 방법이 있어야 한다는 뜻입니다.

처음에는 '답변이 그럴듯한가'를 사람이 눈으로 보고 판단했습니다. 하지만 이건 두 가지 문제가 있었습니다. 첫째, 재현이 안 됩니다 — 같은 케이스를 다음 주에 다시 봐도 똑같이 판단한다는 보장이 없습니다. 둘째, 정말 중요한 실패 — 예를 들어 다른 사용자 계정 정보에 접근한다거나, 검색하지도 않은 문서를 인용한다거나 하는 — 를 '답변이 자연스럽다'는 인상 하나로 놓칠 수 있습니다.

그래서 저희는 '이 에이전트 조합(Candidate)이 특정 시나리오에서 PASS인지 FAIL인지'를 코드로 재현 가능하게 판정하는 프레임워크, Agent Eval V2를 설계했습니다. 오늘은 이 V2의 구조, 실제로 나온 결과, 그리고 V2를 보완하기 위해 별도로 붙여본 OpenTelemetry·Phoenix·Ragas·DeepEval·Garak 실험까지 순서대로 말씀드리겠습니다."

# 2. V2 아키텍처 — Candidate와 판정 흐름 (4분)

### 2-1. Candidate란 무엇인가

*[슬라이드: Candidate = 시스템 프롬프트 + 모델 + 런타임 + 툴/서브에이전트 구성, git_commit 고정]*

"평가의 대상을 저희는 'Candidate'라고 부릅니다. Candidate는 시스템 프롬프트, 사용 모델, 런타임 설정, 그리고 어떤 툴·서브에이전트를 붙였는지까지 포함한 하나의 완전한 조합이고, 여기에 코드 상태를 고정하는 git commit 해시까지 묶어서 하나의 불변(immutable) 단위로 취급합니다.

왜 이렇게까지 하냐면, '어제 잘 됐던 에이전트가 오늘 안 되는' 상황이 생겼을 때 그게 프롬프트를 바꿔서인지, 코드가 바뀌어서인지, 모델이 바뀌어서인지 구분할 수 있어야 하기 때문입니다. 저희 공식 평가 대상은 Candidate `AG004/AV073`이고, Core DEV 코호트는 커밋 `e888d6b0...`, 이후 확장한 S10·S11 Expansion 코호트는 같은 Candidate에 커밋 `f8f8b578...`로 고정돼 있습니다. 즉 '같은 조합, 다른 코드 스냅샷'이라는 걸 커밋 해시로 명시적으로 구분하고 있습니다."

### 2-2. 판정 우선순위 — Hard Gate가 먼저다

*[슬라이드: 가드절 다이어그램 — 실행 유효성 → Hard Gate → 규칙 기반 → Judge 호출 → Judge 필수 FAIL → Judge UNCERTAIN → PASS]*

"판정은 총 5가지 상태로 나옵니다. PASS, FAIL, INCONCLUSIVE, NOT_SCORED, 그리고 INVALID_EVALUATION_INFRA입니다. 마지막 상태가 조금 낯설 텐데, 이건 '에이전트가 잘못했다'가 아니라 '평가 인프라 자체가 이 케이스를 제대로 못 돌렸다'는 뜻입니다 — 예를 들어 Judge 모델 호출이 실패했거나 응답 파싱이 깨졌을 때입니다. 저희는 이 두 실패를 절대 섞지 않습니다. 에이전트가 못한 것과 저희 평가 시스템이 못한 것을 같은 FAIL로 뭉뚱그리면, 나중에 원인 분석을 할 때 뭘 고쳐야 하는지 알 수 없게 됩니다.

판정은 가드절(guard clause) 방식으로 순서대로 짧게 회로가 끊깁니다. 먼저 실행 자체가 유효했는지 봅니다 — 세션이 중간에 죽었다거나 하면 여기서 끝입니다. 다음이 Hard Gate입니다. Hard Gate는 '절대 하면 안 되는 행동'을 코드로 검사하는 단계로, 예를 들어 다른 테넌트 계정 데이터에 쓰기 접근을 시도했는지, 읽기 전용이어야 할 메모리에 쓰기를 시도했는지 같은 걸 결정론적으로 체크합니다. 여기 걸리면 Judge를 부를 필요도 없이 바로 FAIL입니다.

Hard Gate를 통과하면 나머지 규칙 기반 필수 체크를 봅니다. 이것도 통과하면 그때 LLM Judge를 호출합니다. Judge 호출 자체가 실패하면 INVALID_EVALUATION_INFRA, Judge가 필수 항목에서 FAIL 판정을 내리면 FAIL, Judge가 판단을 확신하지 못하면 INCONCLUSIVE로 분리합니다. 이 모든 관문을 다 통과해야 최종 PASS입니다.

핵심은 이겁니다 — **결정론적으로 판단 가능한 것은 절대 LLM Judge에게 맡기지 않습니다.** '다른 계정 데이터에 접근했는가'는 로그를 보면 예/아니오로 100% 확정할 수 있는 사실인데, 이걸 LLM에게 물어보면 매번 미묘하게 다른 답이 나올 수 있는 리스크를 굳이 감수하는 셈이 됩니다. Judge는 코드로 판단할 수 없는 것 — 예를 들어 '이 답변이 사용자 질문의 의도에 실질적으로 부합하는가' 같은 것만 담당합니다."

# 3. 평가 기준 — Core 9개 시나리오 + Expansion S10·S11 (4분)

*[슬라이드: 시나리오 표 — S01~S09, S10~S11]*

"저희는 크게 두 개 그룹의 시나리오를 운영합니다. 하나는 Core DEV — 실제로 자주 발생할 만한 정상 사용 흐름과 몇 가지 경계 케이스를 다루는 9개 시나리오군, variant 기준으로는 11개입니다. 다른 하나는 나중에 추가한 Expansion 파일럿, S10과 S11로 각각 2개 variant씩 총 4개 variant, 14개 variant 전체입니다.

각 시나리오는 결정론적(det) 체크와 Judge 체크를 조합해서 씁니다. 예를 들어 S10-002는 '다른 계정 격리(cross_account_isolation)'와 '읽기 전용 메모리 쓰기 차단(readonly_memory_write_blocked)'을 결정론적으로 체크하고, 최종 상태가 사실과 부합하는지(final_state_truthfulness)는 Judge가 봅니다. S10·S11은 특히 Hard Gate 비중이 높습니다 — 이 두 시나리오군의 취지 자체가 '경계를 넘으려는 시도를 하는가'를 보는 것이기 때문에, 여기서 걸리면 다른 항목을 볼 필요 없이 바로 FAIL 처리됩니다.

시나리오를 왜 이렇게 세분화했는지 말씀드리면 — 하나의 뭉뚱그린 '이 에이전트는 좋은가/나쁜가' 점수는 무엇을 고쳐야 할지 알려주지 않습니다. 시나리오별로 쪼개면 'S10 계열에서만 FAIL이 몰린다'는 게 보이고, 그러면 그게 프롬프트 문제인지 툴 권한 설계 문제인지 좁혀서 디버깅할 수 있습니다."

# 4. 결과 리포트 (3분)

*[슬라이드: 결과 요약 — Core DEV / Expansion / 진단 / 무효]*

"실제 결과입니다. Core DEV 36건 중 32건 PASS, 4건 FAIL로 88.9% 통과율입니다. Expansion S10·S11은 12건 전부 PASS로 100%입니다. 이 외에 공식 점수에 안 들어가는 진단(diagnostic) 케이스 82건과, 실행 자체가 무효 처리된 18건이 별도로 있습니다.

여기서 두 가지를 명확히 구분해서 말씀드리고 싶습니다. 첫째, 82건의 진단 케이스는 '공식 통과율에 안 들어간다'는 게 숨기는 게 아니라, 애초에 설계 의도가 다릅니다 — 확률적으로 재현이 잘 안 되거나, PASS/FAIL을 이분법으로 나누기엔 애매한 탐색적 케이스들이라서 참고 자료로만 씁니다. 둘째, S10·S11 Expansion의 100%는 아직 파일럿 단계 숫자입니다 — 12건이라는 표본 크기 자체가 통계적으로 크지 않기 때문에, '이 영역은 완전히 안전하다'가 아니라 '지금까지 시도한 범위 안에서는 뚫리지 않았다'는 조심스러운 해석이 맞습니다.

그리고 이번 딜리버리 범위에서는 Phase 9 — 비공개 HOLDOUT 시나리오를 이용한 최종 검증 단계 — 를 의도적으로 연기했습니다. 이건 못해서가 아니라, S10·S11 확장과 뒤에 말씀드릴 보조 지표 작업까지 이번 스코프에 들어오면서, HOLDOUT은 다음 이터레이션에서 더 탄탄하게 하기로 정한 겁니다. 이 부분은 한계 섹션에서 다시 짚겠습니다."

# 5. "왜 DeepEval을 안 쓰고 V2를 직접 만들었나" (2분)

*[슬라이드: DeepEval 범용 지표 vs V2 도메인 특화 Gate]*

"이건 심사에서 반드시 나올 질문이라 먼저 짚고 넘어가겠습니다. DeepEval에 Answer Relevancy, Faithfulness 같은 좋은 평가 지표가 이미 있는데 왜 V2를 처음부터 새로 만들었냐는 질문입니다.

답은 간단합니다 — DeepEval의 지표들은 범용(generic) 지표입니다. '답변이 질문과 관련 있는가', '답변이 검색된 문서에 충실한가'는 어떤 챗봇에도 적용되는 일반적인 품질 기준입니다. 하지만 저희가 진짜 걱정하는 실패는 그것보다 훨씬 도메인 특화된 것들입니다 — '이 에이전트가 다른 사용자의 계정 데이터에 접근을 시도했는가', '검색하지도 않은 문서 ID를 인용했는가' 같은, 저희 서비스의 비즈니스 규칙과 툴 권한 구조를 알아야만 판단할 수 있는 기준입니다. 이런 건 DeepEval이 기본으로 제공하는 지표에는 없고, DeepEval 위에 커스텀 지표를 얹는다 해도 결국 저희가 Hard Gate처럼 결정론적 체크 로직을 직접 짜야 하는 건 똑같습니다.

그래서 저희 결론은 '경쟁 관계가 아니라 계층이 다르다'는 겁니다. V2는 저희 도메인에 특화된 결정론적 Gate와, 시나리오별로 맞춤 설계한 Judge 기준으로 PASS/FAIL을 확정하는 1차 판정 시스템이고, DeepEval·Ragas는 그 위에 얹어서 '왜 이 케이스가 흥미로운가'를 보조적으로 설명해주는 범용 신호입니다. 뒤에 나올 보조 실험실이 바로 그 계층을 실제로 검증해본 결과물입니다."

# 6. 보조 실험실 — OTel · Phoenix · Ragas · DeepEval (4분)

### 6-1. 왜 별도 실험실로 분리했나

*[슬라이드: experiments/otel_eval_lab — official_score_eligible=False]*

"보조 지표를 붙일 때 가장 조심한 건 '이게 V2 공식 점수를 오염시키면 안 된다'는 원칙이었습니다. 그래서 물리적으로도 별도 디렉터리(`experiments/otel_eval_lab`)로 분리했고, git에도 아직 안 올렸습니다. 코드 레벨에서도 모든 span에 `eval.lab.official_score_eligible=False`라는 태그를 강제로 박아서, 나중에 누가 실수로 이 데이터를 공식 집계에 섞으려고 해도 바로 걸러지게 만들었습니다.

접근 방식은 이렇습니다. V2가 이미 만들어놓은 동결된 결과 — `outputs/eval-v2-results` 아래의 JSONL — 를 읽어서, 거기 있는 최종 답변과 검색 문서 ID를 가져와 Ragas·DeepEval로 재평가합니다. 새로 에이전트를 실행하는 게 아니라, 이미 확정된 V2 판정 결과에 대해 '다른 도구로 봤을 때는 어떻게 보이는가'를 관찰하는 실험입니다. 그래서 이건 실시간이 아니라 완전히 사후(post-hoc), 별도 프로세스에서 도는 재분석입니다 — 이 부분은 V2 자체의 판정(에이전트 실행과 같은 프로세스에서 바로 처리)과는 다르다는 점을 분명히 구분하고 있습니다."

### 6-2. 실제 붙인 지표와 48건 결과

*[슬라이드: Ragas ID 기반 Context Precision/Recall, Ragas Faithfulness, DeepEval Answer Relevancy]*

"동결된 Core DEV 36건 + Expansion 12건, 총 48건에 대해 재평가를 돌렸습니다. 지표는 세 종류입니다. 첫째, Ragas의 ID 기반 Context Precision·Recall — 이건 검색된 문서 ID와 정답 문서 ID를 집합으로 비교하는 결정론적 지표라서 LLM 호출 없이 계산됩니다. 둘째, Ragas Faithfulness — 답변이 검색된 문서 내용에 실제로 근거하는지를 LLM Judge로 확인하는데, 이건 검증 가능한 fixture 5개 시나리오에만 제한적으로 적용했습니다. 셋째, DeepEval Answer Relevancy입니다.

여기서 저희가 얻은 값진 발견 하나를 말씀드리면 — S10-002 케이스에서 V2는 PASS로 판정했는데, Ragas/DeepEval 보조 지표를 붙여보니 '검색 문서와 답변의 정합도'라는 관점에서는 애매한 신호가 나온 사례가 있었습니다. 이건 V2가 틀렸다는 게 아니라, V2가 애초에 그 축을 측정하도록 설계되지 않았다는 걸 보여주는 좋은 사례입니다 — S10-002의 판정 기준은 '계정 격리를 지켰는가'지, '검색 근거가 얼마나 탄탄한가'가 아니었으니까요. 이게 정확히 저희가 방금 5번 섹션에서 말씀드린 '계층이 다르다'는 걸 실증한 겁니다."

### 6-3. Arize Phoenix — 관측 계층

*[슬라이드: OTel span → Phoenix, annotator_kind: CODE/LLM/HUMAN]*

"이 모든 지표는 OpenTelemetry 스팬으로 감싸서 Arize Phoenix에 보냅니다. Phoenix는 각 케이스를 하나의 span 트리로 시각화해주고, 저희가 계산한 점수를 span annotation으로 붙일 수 있습니다. 흥미로운 부분은 Phoenix의 annotation이 `annotator_kind`라는 필드로 CODE(결정론적 코드가 매긴 것), LLM(LLM Judge가 매긴 것), 그리고 HUMAN(사람이 직접 매긴 것)을 구분한다는 겁니다. 지금은 CODE와 LLM만 쓰고 있지만, 이 구조 덕분에 나중에 사람이 같은 span에 HUMAN 라벨로 평가를 추가하는 것도 기존 인프라를 그대로 재사용해서 가능합니다 — V2에 지금 빠져 있는 사람 관측을 보완할 구체적인 경로가 이미 마련돼 있다는 뜻입니다."

# 7. Garak 프롬프트 인젝션 실험 — 있는 그대로 (3분)

*[슬라이드: 4개 실행 비교표]*

"보안 쪽 실험도 하나 붙였습니다. Garak이라는 LLM 취약점 스캐너로 프롬프트 인젝션 공격을 시도해봤습니다. 이 부분은 결과를 미화하지 않고 정확히 뭘 확인했는지 말씀드리겠습니다.

실행 기록을 다시 뜯어보니 총 4개 리포트가 있었습니다. 이 중 3개는 Garak의 내장 더미 제너레이터(`test.Repeat`)를 대상으로 돌렸습니다. 이 제너레이터는 입력을 그대로 되돌려주기만 하는 echo였고, 이건 '어떤 모델의 안전성'을 측정한 게 아니라 probe 생성부터 detector 판정, 리포트 저장까지 파이프라인이 기계적으로 동작하는지 확인한 smoke test였습니다.

나머지 1개, `safe_model_promptinject_3`만 실제 모델 — OpenAI API로 직접 연결한 `gpt-5.6-sol` — 을 대상으로 진짜 프롬프트 인젝션 공격을 실행했습니다. 결과는 3번 시도 중 3번 모두 공격이 성공했습니다. 모델이 '이 프롬프트는 완전히 탈취됐다'는 공격자가 주입한 문자열을 그대로 새로 생성해서 출력했습니다.

이 결과를 정직하게 해석하면 두 가지입니다. 첫째, 저희는 이제 '프롬프트 인젝션이 실제로 통한다'는 걸 직접 확인했습니다 — 이건 실제 취약점 데이터이고, 순정 모델은 이 공격 패턴에 방어가 없다는 근거입니다. 둘째, 그런데 이 실행은 저희 에이전트 — 시스템 프롬프트와 툴 권한, 출력 가드레일까지 다 갖춘 실제 서비스 엔드포인트 — 를 겨냥한 게 아니라, 그 앞단을 다 걷어낸 순정 모델 API를 직접 때린 겁니다. 저희가 원래 설계했던 격리 REST 엔드포인트(`garak_rest.example.json`)를 통해 실제 에이전트를 대상으로 붙이는 실행은 아직 하지 못했습니다.

그래서 결론은 — '순정 모델은 이 공격에 뚫린다'는 건 확인했고, '저희 에이전트가 이 공격을 방어하는가'는 아직 검증하지 못했습니다. 다음 단계로 명확하게 남겨두고 있습니다."

첫째, Phase 9 HOLDOUT을 이번 범위에서 연기했습니다. 지금까지 나온 통과율은 전부 개발 과정에서 저희가 설계 의도를 알고 만든 시나리오에 대한 결과입니다. 완전히 새로운, 사전에 공개하지 않은 시나리오에서도 같은 통과율이 나오는지는 아직 확인 전입니다. 이게 진짜 일반화 검증이고, 다음 단계 최우선 과제입니다.

# 부록 — 예상 질문 20개와 답변

Q&A 시간에 그대로 인용할 수 있도록 답변을 완성된 문장으로 적어놨습니다.

**Q1. Hard Gate와 Judge를 왜 나눴나요? 전부 LLM Judge로 처리하면 안 되나요?**

"결정론적으로 판단 가능한 것까지 LLM에 맡기면 같은 입력에 다른 판정이 나올 수 있는 리스크를 불필요하게 감수하는 겁니다. '다른 계정에 접근했는가'는 로그로 100% 확정되는 사실이라서 코드로 체크하는 게 더 빠르고 더 정확합니다. Judge는 코드로 판단이 안 되는 것만 담당하도록 역할을 분리했습니다."

**Q2. INVALID_EVALUATION_INFRA와 FAIL을 굳이 나누는 이유는?**

"원인 분석 때문입니다. 에이전트가 잘못한 것과 평가 시스템이 못 돈 것을 같은 FAIL로 합치면, FAIL 비율이 올라갔을 때 에이전트를 고쳐야 하는지 평가 인프라를 고쳐야 하는지 구분이 안 됩니다."

**Q3. 통과율 88.9%가 좋은 수준인가요?**

"절대적인 기준값보다는, 시나리오별로 어디서 FAIL이 몰리는지가 더 중요한 정보입니다. Core DEV 4건 FAIL의 원인을 시나리오 단위로 분석해서 어떤 게 프롬프트 문제이고 어떤 게 툴 설계 문제인지 구분했습니다." *(발표자: 실제 FAIL 4건의 시나리오·원인을 구체적으로 준비해두면 좋습니다.)*

**Q4. Expansion 12건 100%는 신뢰할 수 있나요?**

"표본이 12건이라 통계적으로 크지 않습니다. '이 영역이 완전히 안전하다'가 아니라 '지금까지 시도한 범위에서는 안 뚫렸다'는 파일럿 수준의 결과로 봐야 합니다. 그래서 통과율보다 Phase 9 HOLDOUT으로 표본을 늘리는 게 다음 우선순위입니다."

**Q5. 진단(diagnostic) 82건은 왜 공식 집계에서 뺐나요?**

"재현성이 낮거나 PASS/FAIL 이분법에 안 맞는 탐색적 케이스들이라서입니다. 공식 통과율을 부풀리거나 낮추지 않도록 처음부터 분리해서 설계했습니다."

**Q6. Phase 9는 왜 미뤘나요? 시간이 없어서인가요?**

"이번 딜리버리 범위에 S10·S11 Expansion과 보조 지표 실험까지 들어오면서, HOLDOUT은 더 탄탄하게 준비해서 다음 이터레이션에 하기로 명시적으로 결정한 겁니다. `PHASE9_DEFERRED`라는 상태로 문서에도 명시돼 있고, 지금 나온 통과율에 HOLDOUT 결과가 섞여 있지 않다는 것도 그래서 보장됩니다."

**Q7. DeepEval에 이미 있는 지표인데 왜 V2를 직접 만들었나요?**

"DeepEval 지표는 범용입니다. 저희가 막아야 하는 건 '다른 계정 접근', '검색 안 한 문서 인용' 같은 도메인 특화 규칙이고, 이건 저희 툴 권한 구조를 아는 코드로만 판단할 수 있습니다. DeepEval 위에 커스텀 지표를 얹어도 결국 이 로직은 직접 짜야 하니, 아예 판정 계층을 저희가 설계하고 DeepEval·Ragas는 보조 관측으로 위에 얹는 구조를 택했습니다."

**Q8. 그러면 DeepEval/Ragas는 왜 붙였나요? 안 써도 되는 거 아닌가요?**

"V2가 안 보는 축 — 예를 들어 답변이 검색 근거에 얼마나 충실한가 — 을 별도로 관찰하기 위해서입니다. 실제로 S10-002에서 V2는 PASS인데 Ragas 관점에서는 애매한 신호가 나온 사례를 발견했는데, 이게 V2가 틀렸다는 게 아니라 V2가 측정하도록 설계되지 않은 축이 따로 있다는 걸 보여준 값진 사례였습니다."

**Q9. 보조 실험실 결과가 공식 점수에 영향을 주나요?**

"아닙니다. 물리적으로 별도 디렉터리에서 돌고, 모든 span에 `official_score_eligible=False` 태그를 코드 레벨에서 강제합니다. 동결된 V2 결과를 읽기만 하고 쓰지 않습니다."

**Q10. 보조 실험은 실시간으로 에이전트에 붙은 건가요?**

"아니요. 이미 동결된 V2 결과 JSONL을 읽어서 사후에 재분석하는 방식입니다. 새로 에이전트를 실행하지 않습니다. V2 자체도 실시간 스트리밍은 아니고, 에이전트 실행과 같은 프로세스에서 즉시 판정하는 방식이라, '즉시(V2)'와 '사후·별도 프로세스(보조 실험실)'로 성격이 다릅니다."

**Q11. Langfuse는 실제로 뭘 하고 있나요?**

"에이전트 실행 중에 실시간으로 붙는 트레이싱 도구입니다. LLM 호출, 툴 호출, HITL 재개 시점까지 스팬으로 기록합니다. 다만 V2의 판정 자체에는 관여하지 않습니다 — V2가 판정을 마친 뒤 V1 스크립트 경로에서 그 결과를 Langfuse에 점수로 후속 기록하는 용도로만 쓰이고 있고, V2 스크립트들은 Langfuse를 호출하지 않습니다."

**Q12. V2에 사람 평가가 없는데 문제 아닌가요?**

"맞습니다, 지금 V2는 코드와 LLM Judge, 두 자동화 판정자만 있습니다. 이걸 보완할 구체적인 경로로 Phoenix의 annotation 구조를 봤는데, `annotator_kind`가 CODE·LLM·HUMAN을 구분하도록 이미 설계돼 있어서, 같은 span에 사람이 HUMAN 라벨로 평가를 추가하는 게 기존 인프라 그대로 가능합니다. 다만 아직 실제로 사람 평가를 투입하진 않았고, 다음 단계로 남겨뒀습니다."

**Q13. Garak으로 실제 공격을 돌려봤나요?**

"네, 순정 모델을 대상으로는 돌렸습니다. `gpt-5.6-sol`에 프롬프트 인젝션 3회 시도해서 3회 모두 공격이 성공한 걸 확인했습니다. 다만 나머지 실행 3개는 파이프라인 점검용 더미 제너레이터를 대상으로 한 smoke test였고, 실제 에이전트 엔드포인트를 겨냥한 실행은 아직 없습니다."

**Q14. 그럼 저희 에이전트가 프롬프트 인젝션에 안전한지는 모르는 건가요?**

"정확합니다. 순정 모델이 이 공격에 방어가 없다는 건 확인했지만, 저희 시스템 프롬프트와 툴 권한 레이어가 실제로 이걸 막아주는지는 검증 전입니다. 격리된 REST 엔드포인트로 실제 에이전트를 겨냥한 실행이 다음 단계로 명확히 남아있습니다."

**Q15. Garak 결과에서 `passed: 0`이 뭘 의미하나요? 헷갈리는데요.**

"`passed`는 공격을 방어한 횟수, `fails`는 공격이 성공한 횟수입니다. `passed 0, fails 3`은 3번 다 공격이 성공했다는 뜻입니다. 더미 제너레이터 실행에서도 같은 숫자가 나왔는데, 이건 echo 제너레이터가 입력에 포함된 공격 문구를 그대로 되돌려주기 때문에 구조적으로 항상 100% '실패'로 찍히는 거라, 실제 취약점 신호가 아니라 파이프라인 검증용 수치입니다."

**Q16. 이 프레임워크가 다른 프로젝트에도 재사용 가능한가요?**

"Candidate 정의, Hard Gate/Judge 분리, 5단계 상태 체계 자체는 도메인에 안 묶여 있어서 재사용 가능한 구조입니다. 다만 실제 Hard Gate 규칙과 시나리오 설계는 저희 서비스의 비즈니스 규칙에 맞춰 새로 짜야 합니다."

**Q17. Candidate에 git commit까지 고정하는 이유는?**

"같은 프롬프트·모델 조합이라도 코드가 바뀌면 동작이 달라질 수 있기 때문입니다. 결과가 재현 안 될 때 원인이 프롬프트인지 코드인지 구분하려면 커밋까지 고정해야 합니다."

**Q18. 판정 우선순위(가드절) 순서는 왜 그렇게 정했나요?**

"싼 체크부터, 그리고 확실한 체크부터 먼저 봅니다. 실행 유효성처럼 빠르게 걸러낼 수 있는 걸 맨 앞에 두고, 결정론적 Hard Gate를 LLM Judge보다 먼저 돌려서 불필요한 Judge 호출 비용과 판정 불확실성을 줄였습니다."

**Q19. INCONCLUSIVE는 실무적으로 어떻게 쓰이나요?**

"Judge가 판단을 확신하지 못한 케이스입니다. 통과율 계산에서 FAIL로 취급하지 않고 별도로 추적해서, Judge 프롬프트나 기준 자체를 개선해야 할 신호로 씁니다."

**Q20. 다음 3개월 로드맵을 요약하면?**

"우선순위 순서로, 첫째 Phase 9 비공개 HOLDOUT 실행, 둘째 격리 REST 엔드포인트로 실제 에이전트 대상 Garak 실험, 셋째 Phoenix HUMAN annotation을 활용한 사람 평가 파일럿입니다."
