# Agent Eval V2 — HOLDOUT 비공개 저장소·커밋먼트 설정 가이드

이 문서는 `01_HOLDOUT_비공개_문제_제작_가이드.md`를 실제로 실행하기 전에, Custodian이
먼저 준비해야 하는 인프라를 다룬다. 현재 이 프로젝트 저장소에는 아래 두 가지가 아직
존재하지 않는다. 이 문서는 그 존재하지 않는 상태를 어떻게 채우는지 안내한다.

## 1. 접근 제한 비공개 저장소를 만든다

`README.md`와 `01_HOLDOUT_비공개_문제_제작_가이드.md`는 "비공개 저장소에 실제
package를 둔다"는 것을 전제로 쓰여 있다. 이 비공개 저장소는 지금 존재하지 않으므로
Custodian이 라운드 시작 전에 직접 만들어야 한다.

최소 조건은 다음과 같다.

- 이 프로젝트의 공개/공유 Git 저장소와 **물리적으로 분리**돼 있어야 한다. 같은 저장소의
  private 브랜치나 하위 폴더로는 부족하다 — 실수로 merge되거나 clone 범위에 딸려 나올
  위험이 있다.
- 접근 권한 목록에 지훈님(Candidate 개발자) 계정이 **포함되면 안 된다.** Custodian과
  Reviewer만 접근 가능해야 한다.
- 버전 관리가 가능해야 한다(Git 권장). fixture/gold를 수정할 때마다 새 커밋으로 남겨서
  나중에 "검수 당시 버전"을 특정할 수 있어야 한다.
- 저장소 자체의 이름이나 존재 여부도 공개 채널(팀 전체 채팅, 공개 위키)에 그대로
  노출하지 않는 것을 권장한다.

권장 구조는 `01_HOLDOUT_비공개_문제_제작_가이드.md` 4절의 구조를 그대로 따른다.

```text
private-holdout/                      (별도 비공개 저장소 루트)
├─ secrets/
│  └─ hmac_secret.key                 (2절에서 생성, 이 저장소에만 존재)
└─ SXX-HOLDOUT-001/
   ├─ fixture.yaml
   ├─ gold.yaml
   ├─ sources/
   │  └─ 승인된 실제 PDF 또는 평가용 snapshot
   ├─ private_package_manifest.json
   └─ review_record.yaml
```

## 2. HMAC 커밋먼트를 만드는 도구

`01_HOLDOUT_비공개_문제_제작_가이드.md` 3.7절이 요구하는 "UTF-8·LF·정렬된 canonical
form 기준 HMAC commitment"를 만들어주는 스크립트가 현재 이 프로젝트 어디에도 없다.
아래 `tools/make_commitment.py`가 그 역할을 한다. 이 스크립트는 반드시 **비공개
저장소 안에서만** 실행한다 (원본 fixture/gold 내용이 스크립트 실행 중 메모리에
올라가기 때문에, 공개 저장소가 체크아웃된 환경에서 돌리지 않는다).

### 2.1 비밀키를 한 번 생성한다 (라운드마다 한 번)

```bash
python3 -c "import secrets; print(secrets.token_hex(32))" > private-holdout/secrets/hmac_secret.key
chmod 600 private-holdout/secrets/hmac_secret.key
```

이 파일은 비공개 저장소 밖으로 절대 나가면 안 된다. `04_public_manifest.template.yaml`
주석에 명시된 대로, 공개 매니페스트에는 이 키도, 이 키로 만들기 전의 plain hash도
들어가면 안 된다 — 오직 `make_commitment.py`가 계산한 최종 opaque HMAC 값만 들어간다.

### 2.2 fixture / gold / package 전체에 대해 커밋먼트를 만든다

```bash
python3 tools/make_commitment.py \
  --secret private-holdout/secrets/hmac_secret.key \
  --fixture private-holdout/S01-HOLDOUT-001/fixture.yaml \
  --gold    private-holdout/S01-HOLDOUT-001/gold.yaml \
  --package-dir private-holdout/S01-HOLDOUT-001
```

출력되는 세 값 `fixture_commitment` / `gold_commitment` / `private_package_commitment`를
그대로 `04_public_manifest.template.yaml`의 동일 이름 필드에 붙여넣는다. 그 세 값 외에
스크립트가 출력하는 다른 어떤 값도 공개 매니페스트에 넣지 않는다.

### 2.3 fixture나 gold를 수정했다면

수정할 때마다 2.2를 다시 실행해서 커밋먼트를 재생성하고, 공개 매니페스트의 값도
같이 갱신한다. `05_HOLDOUT_검수_체크리스트.md`의 "검수 중 변경했다면 다시 commitment를
만들고 재검수했다"가 바로 이 절차를 말한다.

## 3. 이 절차가 왜 필요한가 (Reviewer/Custodian에게 설명할 때 참고)

공개 저장소에는 실제 문제·정답 내용이 아니라 그 내용의 "지문(fingerprint)"만 남긴다.
나중에 라운드가 끝나고 비공개 package를 공개할 때, 이 지문을 다시 계산해서 원래
공개했던 커밋먼트와 일치하는지 확인하면 "라운드 중간에 문제나 정답이 바뀌지 않았다"는
것을 제3자도 검증할 수 있다. HMAC을 쓰는 이유는 단순 해시(SHA-256)만 쓰면 내용을 모르는
사람도 무차별 대입으로 원문을 추측·검증할 여지가 이론상 생기기 때문에, 비밀키를 섞어서
그 경로를 막는 것이다.
