# 문서 검색 하이브리드 설계 및 평가 요약

## 1. 문서 목적과 현재 결론

이 문서는 문서 검색을 왜 벡터 단독 방식에서 하이브리드 방식으로 개선했는지,
현재 제품 코드의 최종 검색 계약이 무엇인지, 어떤 평가 결과까지 신뢰할 수 있는지를
팀원이 한 번에 확인하기 위한 정본 요약이다.

기존 벡터 검색은 표현이 달라도 의미가 비슷한 내용을 찾는 데 유리하지만 프로젝트명,
고유 용어, 날짜, 숫자처럼 정확한 문자열이 중요한 질문에는 약점이 있었다. 현재는
키워드 기반 lexical 검색과 의미 기반 vector 검색을 함께 사용하고 두 점수를
`0.5 : 0.5`로 결합해 상위 20개 근거 후보를 반환한다.

```text
사용자 질문
  ├─ lexical 검색: FTS + trigram + exact contains
  └─ vector 검색: embedding cosine similarity
          ↓
     점수 0.5 : 0.5 결합
          ↓
       Top-20 후보
          ↓
 doc_block.content를 근거 본문으로 반환
```

Top-20은 최종 답 20개가 아니라 에이전트가 답변과 근거 판단에 사용할 검색 후보군이다.

## 2. 최종 기술 계약

| 구분 | 현재 기준 |
|---|---|
| 도구 | 기존 루트 에이전트 `document_search` |
| 입력 | `query` 하나 |
| 결과 수 | 서버에서 Top-20 고정 |
| lexical 검색 대상 | `chunk.search_text` |
| 근거 반환 본문 | `doc_block.content` |
| lexical 구성 | PostgreSQL FTS 0.55 + pg_trgm 0.25 + exact contains 0.20 |
| 최종 결합 | lexical 0.5 + vector 0.5 |
| 후보 수집 | vector·FTS·trigram 각 60개를 합친 뒤 재정렬 |
| 별도 `raw_text` | 추가하지 않음 |

기존 팀·개인·공유·프로젝트 문서 범위, 현재 revision, 접근 권한, 활성·삭제 상태
필터와 미색인 문서 표시 정책은 그대로 유지한다. 업무 추출 경로가 사용하는 기존
순수 벡터 검색도 변경하지 않아 목적이 다른 검색 경로를 분리했다.

## 3. 데이터 흐름과 필드 역할

```text
문서 파싱 결과(현재 저장 계약 기준)
        ↓
doc_block.content
  실제 근거로 보여줄 파싱 본문
        ↓ 청킹 및 제목·절 문맥 보강
chunk.search_text
  검색 적중률을 높이기 위한 텍스트
        ↓ 임베딩
vec_idx.embedding
  의미 유사도 검색용 벡터
```

검색에는 제목 경로와 절 문맥이 붙은 `chunk.search_text`가 유리하다. 반면 사용자와
에이전트에 근거를 제시할 때는 검색을 위해 덧붙인 문맥이 아닌 실제 파싱 본문인
`doc_block.content`를 반환한다.

별도의 `chunk.raw_text`는 만들지 않았다. 현재 `doc_block.content`가 근거 본문을
보존하고 `chunk.search_text`가 검색 역할을 담당하므로, 같은 내용을 다시 저장하면
데이터 중복과 동기화 비용만 늘어난다고 판단했다. 과거 Agent1 실험의
`text/raw_text` DTO 제안은 현재 제품 저장 계약과 구분한다.

정식 Docling 기반 파싱·청킹·임베딩 파이프라인은 현재 통합 중이다. 통합 완료 후
실제 생성되는 `doc_block.content`, `chunk.search_text`, embedding이 이 검색 계약과
일치하는지 다시 확인한다.

## 4. 검색 방식별 역할

- Vector Search는 표현이 달라도 의미가 비슷한 문장을 찾는 데 유리하다.
- Lexical Search는 프로젝트명, 제품명, 약어, 날짜, 숫자와 같은 실제 단어·문자열을
  찾는 데 유리하다.
- FTS는 단어 단위 일치를, `pg_trgm`은 부분 문자열과 작은 표기 차이를, exact
  contains는 정확한 표현 포함을 강한 신호로 사용한다.
- Hybrid Search는 두 방식의 후보를 합치므로 한쪽 검색의 약점을 다른 쪽이 보완한다.

한국어는 조사 때문에 단순한 전체 AND 검색이 쉽게 실패한다. 이를 줄이기 위해
원형 토큰과 조사 제거형 토큰을 prefix OR 쿼리로 만들고, 부분어절 검색을 함께 쓴다.

예를 들어 질문이 `언제까지 끝내야 해?`이고 문서에 `완료 기한은 9월 30일이다`라고
적혀 있다면 표현이 달라도 의미가 가까운 vector 검색이 유리하다. 질문과 문서에
`PROJ-1042`가 함께 있다면 정확한 이슈 번호를 잡는 lexical 검색이 유리하다.
하이브리드 검색은 두 종류의 질문을 하나의 검색 경로에서 보완한다.

## 5. 평가 지표를 읽는 방법

| 지표 | 이 작업에서의 의미 |
|---|---|
| Recall@20 | 필요한 근거를 후보 20개 안에 얼마나 빠뜨리지 않고 넣었는가 |
| Precision@5 | 가장 위의 5개 결과 중 실제 필요한 근거가 차지하는 비율 |
| Precision@20 | 후보 20개 중 실제 필요한 근거가 차지하는 비율 |
| MRR | 첫 번째 정답 근거가 얼마나 상위에 등장하는가 |
| Golden Set | 사람이 질문별 정답 근거를 미리 지정한 평가 기준 |
| Development | 가중치와 검색 구조를 조정하는 데 사용하는 평가 데이터 |
| Holdout | 조정에 사용하지 않고 독립적으로 결과를 확인하는 평가 데이터 |

Recall은 에이전트에 필요한 근거를 누락하지 않는지를, Precision은 후보가 불필요한
내용으로 과도하게 채워지지 않는지를 본다. MRR은 첫 정답을 얼마나 빨리 만나는지를
측정한다. 따라서 하나의 지표만으로 검색 품질 전체를 단정하지 않는다.

## 6. 가중치 선택 당시 개발 평가 결과와 해석 범위

아래 수치는 합성 문서 8종·절 95개·질의 14개로 0.5/0.5 가중치를 선택한 당시의
확정 결과다. 벡터 단독 대비 현재 하이브리드 방식이 다음과 같이 개선됐다.

| 지표 | Vector only | Hybrid 0.5/0.5 |
|---|---:|---:|
| Evidence Recall@20 | 0.933 | 1.000 |
| Precision@20 | 0.129 | 0.154 |
| MRR | 0.756 | 0.851 |

이 결과에서는 평가 대상 근거가 모두 Top-20 안에 들어왔고 첫 정답의 평균 순위도
개선됐다. 개발·holdout 분리 점검에서도 holdout Recall@20과 MRR은 1.0이었다.

다만 이 14질의 세트는 하이브리드 구조와 가중치를 개발하던 소규모 자료다. 최신
main 병합 후 동일 legacy 평가기를 다시 실행하면 fixture와 corpus 변경의 영향으로
일부 수치가 달라진다. 재실행 수치는 위의 당시 확정 결과와 직접 비교할 수 없으며,
일반적인 제품 검색 성능을 증명하거나 새 가중치를 선택하는 근거로 사용하지 않는다.

## 7. 현재 정식 평가와 legacy 평가의 관계

- 현재 정식 기준은 최신 main의 프로젝트별 PDF 100종과 기본·확장 합계 140질의
  앵커 기반 평가 체계다.
- 기존 14질의 자료는 `document_search_hybrid_legacy.json`에 보존한 개발·감사
  기록이다.
- 두 평가는 문서 구성과 JSON 계약, 목적이 다르므로 결과를 합치거나 직접 비교하지
  않는다.

정식 main 평가는 넓은 문서·질의 범위의 회귀 검증 기준이고, legacy 평가는 왜 현재
하이브리드 구조와 0.5/0.5가 선택됐는지를 추적하는 근거다.

## 8. 실문서 평가를 보류한 이유

공용 DB에서 승인된 PDF 8개·청크 294개의 로컬 평가 스냅샷을 준비했지만 기존
embedding의 모델·버전·생성 과정인 provenance를 확인할 수 없었다. 동시에 다른
팀원이 Docling·청킹·임베딩 정식 파이프라인을 통합 중이어서, 별도 RunPod Worker
기능과 평가 전용 재임베딩 경로를 만들면 제품 정본과 충돌할 가능성이 있었다.

따라서 다음을 제거했다.

- 로컬 `.env`의 고권한 `EVAL_SOURCE_DATABASE_URL`
- 로컬 `eval_real` 스키마의 문서 8개·청크 294개
- 임시 import·cleanup 스크립트와 승인 목록·Golden 템플릿
- 읽기 전용 Worker 사본에 시험적으로 추가했던 재임베딩 경로

공용 DB에는 쓰기 요청을 보내지 않았다. 실문서 평가는 정식
`Docling → 청킹 → 임베딩 → 제품 DB 저장` 경로가 통합된 뒤, 같은 제품 경로로
재색인한 데이터에 사람이 먼저 질문과 정답 근거를 작성하는 방식으로 재개한다.

## 9. 주요 의사결정 흐름

```text
벡터 단독 검색
  → lexical + vector 하이브리드 적용
  → 14질의 개발·holdout 평가와 Golden Set 재검수
  → 평가 데이터 누수 방지 보강
  → 공용 DB 실문서 독립 평가 준비
  → embedding provenance 불명 및 공식 파이프라인 통합 확인
  → 임시 실문서 평가 환경 폐기·보류
  → main의 PDF 100종·140질의 평가 체계를 정본으로 통합
```

## 10. 알려진 한계와 다음 작업

- 0.5/0.5는 현재 개발 평가로 선택한 운영값이며 모든 문서 유형의 전역 최적값을
  의미하지 않는다.
- 후보군 안의 최대값으로 lexical·vector 점수를 각각 정규화하므로 최종 점수는
  동일 질의의 후보 간 상대 순위다. 질의 간 품질이나 절대 신뢰도로 해석하지 않는다.
- trigram의 `<%` 후보 조건은 DB 세션의
  `pg_trgm.word_similarity_threshold`에 영향을 받으며 PostgreSQL 기본값은 `0.6`이다.
  운영 DB의 값을 배포 전 기록하고 배포·평가 환경에서 같은 값으로 고정해야 결과를
  재현할 수 있다. 긴 문장 질의는 기본 임계값을 넘기 어려워 trigram 후보가 거의
  추가되지 않고, 전체 질의 문자열이 그대로 포함된 경우의 `exact_raw > 0`에 주로
  의존할 수 있다. lexical 가중치 0.25가 항상 실제 후보 기여도 0.25를 보장하지 않는
  이유이므로 평가에서는 후보 경로별 적중 건수도 함께 관찰한다.
- 현재 vector 후보 쿼리는 전체 허용 범위에서 cosine 점수를 계산해 정렬한다. 향후
  HNSW 같은 ANN 인덱스를 적용할 때는 거리 연산자 기반 후보 수집으로 쿼리를 함께
  바꾸고 recall 회귀를 다시 측정해야 한다.
- 의미가 비슷한 여러 문서의 세밀한 구별, 긴 자연어 paraphrase, 숫자·표 데이터의
  복합 질의는 정식 평가 체계에서 계속 관찰해야 한다.
- 정식 Docling 파이프라인 통합 후 실제 제품 데이터의 embedding provenance를
  고정하고 실문서 평가를 다시 수행해야 한다.
- 가중치 변경은 정식 main 평가와 별도 holdout 결과가 함께 개선될 때만 검토한다.

## 11. 배포 전 필수 점검

하이브리드 검색은 PostgreSQL `pg_trgm` 확장과 두 검색 인덱스를 전제로 한다.
`infra/deploy.sh`의 `_apply.py --check`는 새 컨테이너를 기동한 뒤 실행되므로 누락을
알리기는 하지만 새 코드가 먼저 뜨는 것을 막는 사전 점검은 아니다. 따라서 배포
담당자는 제품 배포 DB를 대상으로 다음 순서를 지킨다. 평가용 DB나 과거
`EVAL_SOURCE_DATABASE_URL`을 제품 배포 확인에 사용하지 않는다.

1. 배포 전 읽기 전용으로 확장·임계값·스키마 상태를 확인한다.

   ```sql
   SELECT extname FROM pg_extension WHERE extname = 'pg_trgm';
   SHOW pg_trgm.word_similarity_threshold;
   ```

2. 누락 시 권한을 가진 DB 담당자가 변경 내용을 검토한 뒤에만
   `CREATE EXTENSION IF NOT EXISTS pg_trgm;`과
   `DB/migrations/2026-08-28_document_search_hybrid_indexes.sql`을 적용한다.
3. 새 애플리케이션을 띄우기 전에 다음 검사가 통과하는지 확인한다.

   ```bash
   python DB/migrations/_apply.py --check
   ```

4. 배포 후 승인된 테스트 계정·팀 범위에서 대표 질의를 한 번 실행한다. SQL 오류가
   없고 결과가 20개 이하이며 다른 팀·개인 문서가 섞이지 않는지 확인한다.

확장 생성과 마이그레이션 적용은 RDS 쓰기 작업이다. 문서에 명령이 있다는 이유만으로
자동 실행하지 않고 DB 담당자의 승인·백업·적용 창을 따른다.

## 13. 용어 요약

- **Lexical**: 실제 단어와 문자열 일치를 중심으로 찾는 검색 방식
- **Vector**: 문장의 의미를 벡터로 바꿔 의미상 가까운 내용을 찾는 방식
- **FTS**: 데이터베이스의 단어 기반 전문 검색
- **pg_trgm**: 문자열을 세 글자 조각으로 비교해 부분 일치와 표기 차이를 보완하는
  PostgreSQL 확장
- **Exact contains**: 질문의 정확한 문자열이 검색 대상에 포함됐는지 보는 신호
- **Hybrid**: lexical과 vector 검색 결과를 결합하는 방식
- **Provenance**: 임베딩이 어떤 모델·버전·과정으로 만들어졌는지 나타내는 출처 정보
