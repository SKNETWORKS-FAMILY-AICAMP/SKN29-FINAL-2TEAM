# RunPod Worker 통합 가이드

> 범위 주의: 이 문서는 국소 Reading Order와 인계받아 검증한 Heading 후처리를
> 최신 Worker에 연결하기 위한 가이드다. 원빈님 작업본의 표·이미지 정보 보완 및
> OCR/PaddleOCR-VL 관련 변경을 포함한 전체 문서처리 통합 절차서는 아니다.

## 결론

정본은 `choiwon10/SKN29-RUNPOD-WORKER` 저장소다. 이 문서 폴더에는 설명과 검증
근거만 있고 실행 코드는 포함하지 않는다. 코드는 별도 canonical handoff
`docling_postprocess_merge_handoff_20260825_v2`에서 가져와 담당 팀원의 최신
Worker 브랜치에 적용한다. 현재 프로젝트의 `runpod_worker/`는 읽기용 사본이므로
먼저 수정하지 않는다.

## 고정된 처리 순서

```text
Docling 2.119 변환
  -> Reading Order policy="validated-local-v1" (구현 버전 v1.1)
  -> 기존 density heading promotion
  -> HybridChunker
  -> embedding / output
```

Reading Order를 먼저 두는 이유는 60건의 자동 적용 검증이 Docling 원본
`text/list_item/paragraph/caption` 라벨을 입력으로 수행됐기 때문이다. 헤딩 승격을 먼저
실행하면 일부 라벨이 `section_header`로 바뀌어 검증한 입력 계약과 달라진다.

주의: 호출 인자는 `validated-local-v1`이다. `validated-local-v1.1`은 audit의
`policy_version`에 기록되는 구현 버전이며 호출 가능한 policy 이름이 아니다.

## 요구 버전

- Python 3.12
- `docling==2.119.0`
- `transformers==5.8.0`
- 운영 Worker가 사용하는 CUDA/Torch 조합 유지

기존 읽기용 사본의 `runpod_worker/requirements.txt`는 아직 `docling==2.117.0`이므로
정본 Worker에서 2.119로 올린 뒤 전체 파싱 회귀 테스트를 실행해야 한다.

## 파일 배치

별도 canonical handoff 패키지의 `code/` 내용을 Worker 코드 아래 독립 모듈
디렉터리로 옮긴다. 기존 헤딩 및 원빈님 최신 표·이미지·OCR 코드를 덮어쓰지 않는다.

```text
worker/
  pipeline.py
  density_heading_correction.py
  reading_order_postprocess/
    worker_reading_order_adapter.py
    run_reading_order_postprocess.py
    apply_reviewed_structure.py
    validate_postprocess_proposals.py
    scan_structure_order_router.py
    scan_comparison_grid_flows.py
    scan_form_row_flows.py
    scan_stage_detail_flows.py
    reading_order/
```

실제 import 경로는 담당 브랜치 패키지 구조에 맞춰 한 번만 정리한다.

## pipeline.py 연결 위치

현재 `result = converter(use_ocr).convert(path)` 직후, 기존
`promote_headings_by_density(result)` 호출 전에 연결한다.

```python
document, reading_order_audit = postprocess_docling_document(
    result.document,
    policy="validated-local-v1",
)
result.document = document

promoted_headings = promote_headings_by_density(result)
chunks, diagnostics, dropped = _chunk_document(
    result.document, max_tokens, merge_peers
)
```

최종 `validation`에는 다음 요약을 추가한다.

```python
"reading_order": {
    "outcome": reading_order_audit.get("outcome", "PRESERVED"),
    "policy_version": reading_order_audit.get("policy_version"),
    "candidate_count": reading_order_audit.get("candidate_count", 0),
    "applied_count": reading_order_audit.get("applied_count", 0),
    "failure_reason": reading_order_audit.get("failure_reason"),
},
```

외부 계약은 `CORRECTED` 또는 `PRESERVED` 두 결과만 사용한다. 검토 필요 후보는 자동
대기열을 만들지 않고 audit에만 남기며, Worker 출력은 원본 보존으로 끝낸다.

## 배포 순서

1. 정본 Worker 브랜치에서 Docling 2.119 버전 고정.
2. 코드를 배치하고 먼저 `shadow`로 대표 문서 smoke test.
3. 기존 헤딩 승격 건수와 Chunk 수가 예상치 않게 변하지 않는지 확인.
4. `validated-local-v1`로 전환해 보정 1건 이상인 문서를 실행.
5. 원본 ref, parent_ref, Docling schema, Chunk 생성, embedding까지 통과 확인.
6. 정본 Worker PR 병합 후 현재 프로젝트의 읽기용 사본을 동일 커밋으로 동기화.

## VLM 관련 경계

현재 Worker의 Docling 내장 `do_picture_description=True`는 변환 과정 안에서 실행되므로,
변환 후의 순서 보정이 이미 생성된 내장 이미지 설명을 다시 만들지는 않는다. 이번 병합은
우선 HybridChunker와 뒤 단계에 전달되는 문서 순서를 고친다. 앞뒤 문맥을 넣는 별도 VLM
설명 단계를 추가한다면 반드시 Reading Order와 Heading 보정 뒤에 배치한다.
