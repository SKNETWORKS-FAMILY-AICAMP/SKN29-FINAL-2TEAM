# 멘토링 설명자료: 국소 읽기 순서 보정과 헤딩 개선

작성일: 2026-08-28
실험 기준: Docling 2.119.0 완성 JSON 이후 후처리

## 1. 30초 요약

Docling 자체 모델이나 OCR을 수정한 것이 아니라, **Docling이 만든 완성 JSON 뒤에서** 두 가지 좁은 문제를 보정하는 실험이다.

1. 같은 페이지·같은 `parent_ref` 안에서 바로 붙은 두 sibling의 순서가 좌표·구조상 뒤집힌 경우 최소 교환한다.
2. `list_item`으로 잘못 분류된 전체 요소가 실제 소제목인 경우에만 `section_header` 승격 후보로 만든다.

둘 다 애매하면 원본을 유지한다. 목표는 전체 문서 순서를 재구성하는 것이 아니라, **확신도가 높은 국소 오류만 낮은 비용으로 고치는 것**이다.

## 2. 왜 필요한가

읽기 순서가 틀리면 텍스트뿐 아니라 이미지·표 설명을 만들 때 앞뒤 문맥이 잘못 전달된다. 그러면 VLM 설명과 이후 Chunk의 문맥도 흔들릴 수 있다.

멘토링에서 확인한 핵심 오류는 서로 다르다.

- `SIBLING_ORDER_ERROR`: 같은 부모 안에서 인접한 두 요소의 순서만 뒤집힘
- `PARENT_RELATION_ERROR`: 애초에 다른 카드·행·그룹이 같은 부모로 묶이거나 부모가 잘못됨
- `TEXT_EXTRACTION_ERROR`: PDF에서 글자가 누락되거나 깨짐

이번 범위는 첫 번째만 자동 보정한다. 나머지는 순서 룰로 억지로 고치지 않고 audit/backlog에 남긴다.

## 3. 파이프라인에서 들어가는 위치

```text
PDF
 ↓
Docling 2.119 변환
 ↓
완성 Docling JSON (body, self_ref, parent_ref, bbox, label)
 ↓
[이번 작업] 국소 순서 detector → 구조/좌표 guard → 최소 swap
             └─ 헤딩 후보 detector → list_item 승격 제안(기본 비활성)
 ↓
검증된 JSON 또는 원본 JSON + audit
 ↓
Chunk/VLM 문맥 확장
```

Heading·OCR·Docling 내부 모델을 직접 변경하지 않는 이유는, 순서 후처리의 효과와 upstream 파싱 효과를 분리해 검증하기 위해서다.

## 4. 국소 순서 보정 규칙

### 4.1 자동 보정 조건

| 조건 | 현재 기준 | 의미 |
|---|---:|---|
| 페이지 | 동일 page 필수 | 페이지를 넘는 대규모 재배열 방지 |
| 부모 | 동일 `parent_ref` 필수 | 서로 다른 그룹을 섞지 않음 |
| JSON 관계 | 바로 인접 sibling | 먼 요소의 연쇄 오보정 방지 |
| 시각적 중간 sibling | 0개 | 직접 교환 가능한 경우만 자동화 |
| 좌우 정렬 차이 | `≤ 0.035` (페이지 정규화) | 같은 열/흐름의 보조 신호 |
| 세로 차이 | `0.005 ~ 0.08` 자동 대역 | 가까운 국소 역전만 처리 |
| 세로 검토 대역 | `0.08 ~ 0.18` | 자동 변경 없이 REVIEW 후보로 회수 |
| 작업 | `SWAP_ADJACENT` | 두 요소만 교환하는 최소 변경 |

텍스트 연속성(`아래 간격 ≤0.08`, `오른쪽 간격 ≤0.05`, 겹침·크기 유사도)은 보조 신호다. 단독으로 순서를 결정하지 않는다. 한국어 문단은 최소 20자·3토큰·12음절 조건을 사용해 짧은 라벨을 문단으로 오인하지 않게 한다.

### 4.2 상태 처리

```text
강한 증거 + 모든 guard 통과 → AUTO_REORDER_ELIGIBLE
확장 대역/복합 geometry     → REVIEW_REQUIRED
부모 충돌/구조 모호          → PRESERVED
```

최종 운영 출력은 `보정된 JSON` 또는 `원본 유지 JSON` 두 갈래다. `REVIEW_REQUIRED`는 개발·감사용 내부 상태이며, 무인 운영에서는 원본 유지로 귀결된다.

### 4.3 현재 지표

- 기존 확정 AUTO 후보: `60 TP / 0 FP`
- 관측 Precision: `100%`
- Wilson 95% 하한: `93.9828%`
- 신규 문서 후보: `2 TP / 0 FP`, 이 중 `1건 AUTO`, `1건 REVIEW`
- 적용기는 JSON ref 보존·dangling ref·cycle·멱등성을 검사한다.

이 수치는 **후보의 안전성**이지 전체 문서 순서 정확도나 Recall이 아니다.

## 5. 헤딩 개선 규칙

### 5.1 최초 density 가설

처음에는 한화 사례에서 다음 네 신호를 모두 만족하면 헤딩 후보로 보았다.

| 신호 | 초기값 |
|---|---:|
| 위·아래 밀도 창 | `120pt` |
| 본문 대비 글자 크기 | `1.15배 이상` |
| 짧은 텍스트 | `60자 이하` |
| 위쪽 공백 | `4pt 이상` |
| 밀도 차이 | `density_below - density_above ≥ 0` |

교차문서 22개 DEV 행에서 숫자 threshold만 1,120조합 비교한 결과, 최고 F1은 `8 TP / 10 FP`였고 Precision 95% 이상을 강제하면 Recall이 25%까지 떨어졌다. 숫자만 미세 조정하는 방향을 버리고 구조 guard를 추가했다.

### 5.2 AutoResearch-lite 방식

AutoResearch-lite는 모델 재학습이나 LLM 자율 연구가 아니다.

```text
Docling 2.119 JSON 고정
 → 사람이 원문/overlay 확인 후 TP·FP 라벨 고정
 → 로컬에서 threshold 조합 전수 평가
 → DEV 결과와 입력 hash 기록
 → 규칙 동결
 → 처음 보는 HOLDOUT으로 별도 검증
```

동일 성능이면 더 단순한 기존 기준을 우선하고, HOLDOUT 결과를 보고 threshold를 사후 조정하지 않는다.

### 5.3 최종 list-item 전용 정책

대상은 요소 내부를 쪼개지 않고 **whole element가 `list_item`인 경우**로 제한했다.

| 조건 | 최종 실험값 |
|---|---:|
| 원본 label | `list_item` |
| 다음 요소 label | `text` |
| 다음 요소 들여쓰기 차이 | `0 ~ 25pt` |
| 다음 요소 세로 차이 | `0 ~ 35pt` |
| 반복 날짜 카드 guard | 후보 3개 이상이면 차단 |
| 목차·index/key-value·기존 헤딩 중복 | 차단 |

DEV는 9개 문서 ID, 144행(`TP 18 / FP 126`)이다. 96개 조합을 비교해 최종 기록값에서 `12 TP / 0 FP / 6 FN / 126 TN`을 얻었다.

- Precision: `100%`
- Recall: `66.7%`
- F1: `0.80`
- Precision Wilson 95% 하한: `75.75%`

단, 동일한 `12/0/6/126`을 만든 조합이 36개였다. 따라서 `0~25pt / 35pt`는 유일한 수학적 최적값이 아니라, 안전성 guard 안에서 선택한 재현 가능한 동률 정책이다.

### 5.4 독립 검증과 현재 결론

- list-item HOLDOUT v1: `0 TP / 0 FP`, 67개 정상 보존
- 신규 양성 HOLDOUT 2회: 자동 후보 0건
- 한화 데모: 3건 JSON 승격·schema/ref/parent 검증 통과

따라서 헤딩 정책은 **default-off 실험 기능**으로 전달한다. 새 문서에서 양성 후보가 반복 재현되기 전에는 운영 자동승격으로 올리지 않는다.

## 6. 파라미터를 이렇게 정한 이유

1. 초기값은 한화 사례에서 출발했으므로 처음부터 범용 최적값으로 주장하지 않았다.
2. 교차문서에서 숫자만 바꿔서는 FP와 FN을 동시에 줄일 수 없음을 전수 탐색으로 확인했다.
3. 목차·카드·key-value 같은 구조적 오탐을 먼저 guard로 차단했다.
4. 양성 문서가 부족한 상태에서 Recall을 키우기보다, `FP=0`과 정상 보존을 우선했다.
5. 같은 성능을 내는 threshold가 많아 가장 보수적이고 설명 가능한 값을 동결했다.

주의: `autoresearch_lite`의 Python 기본 dataclass에는 과거 기준값(`indent 4~40pt`, `vertical 25pt`)이 남아 있고, 최종 실험 기록은 `0~25pt`, `vertical 35pt`다. 통합 시에는 코드 기본값에 의존하지 말고 최종 정책을 명시적으로 주입하거나, 팀원 코드에서 이 불일치를 정리해야 한다.

## 7. 멘토링 피드백 반영 현황

| 피드백 | 현재 반영 |
|---|---|
| 전체 순서복원보다 범위 명확화 | `Local Sibling Order Correction`으로 명칭·범위 고정 |
| sibling 오류와 parent 오류 분리 | 별도 라벨·audit·backlog로 분리 |
| 완성 JSON 이후 후처리 | Docling 내부/OCR 변경 없이 JSON 후단에 배치 |
| threshold 근거 제시 | DEV 전수 탐색, 문서·행 수·라벨·Wilson 지표 기록 |
| 범용성 확인 | 교차문서·신규 HOLDOUT·복잡 레이아웃으로 분리 검증 |
| 보수적 자동화 | 확실한 인접 관계만 AUTO, 나머지는 원본 유지 |
| 실험 효과 계량 | Precision/Recall/Wilson/정상 보존/멱등성 제시 |

아직 하지 못한 것:

- parent 관계 자체가 틀린 문서의 자동 복구
- 텍스트 추출 누락·깨짐 복구
- 동일 VLM·동일 prompt의 보정 전후 description A/B
- 신규 문서에서 헤딩 양성 후보 반복 재현

## 9. 멘토링에서 확인받을 질문

1. 현재처럼 `FP=0`을 우선한 보수 정책을 유지할지, 양성 문서 확보 후 Recall을 더 노릴지?
2. 코드 기본값과 최종 실험값의 불일치를 통합 전에 어느 위치에서 정리할지?

4. 순서 보정 전후 VLM 문맥 A/B를 최종 평가 지표로 포함할지?

## 한 문장 결론

> Docling 2.119 완성 JSON 뒤에서 동일 parent의 확실한 인접 sibling 역전만 최소 교환하고, list-item 헤딩 승격은 구조 guard와 AutoResearch로 보수적으로 제안하는 후처리 계층이며, 현재는 높은 후보 정밀도와 안전성은 확인했지만 전체 순서복원·범용 Recall·자동 헤딩 운영승격까지 검증된 상태는 아니다.
