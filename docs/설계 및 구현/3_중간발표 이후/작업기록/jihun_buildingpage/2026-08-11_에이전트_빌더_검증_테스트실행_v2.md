## 1. 빌더 검증 에이전트

### 1.1 무엇을 하는가

`docs/빌더_에이전트_구체화.md` §1-§3에 정리해 둔 설계를 실제로 구현했다.
사용자가 이름·설명·behavior(자연어 행동 지시)·도구를 채우고 제출하면, 그
내용을 구조화 출력 한 번으로 검토한다.

- **refined_instruction** — behavior 문장을 실행용 지시문으로 다듬는다. 모든
  에이전트에 이미 적용되는 공통 스캐폴드 규칙(근거 대기, 확인 후 진행 등)은
  다시 적지 않고, behavior에 없는 지시를 지어내지 않는다.
- **description_check.note** — description에 동사(뭘 하는지)·대상(뭐에
  대해)·산출물(뭘 내는지) 세 요소가 있는지 본다. 애매하면 사유, 명확하면
  `null`.
- **tool_match_check** — behavior 문장과 선택한 도구를 대조해 `missing_tools`
  (필요해 보이는데 안 고른 도구)와 `unused_tools`(골랐는데 안 쓰일 것 같은
  도구)를 뽑는다.
- **overall** — 셋 중 하나라도 걸리면 `warn`, 전부 문제없으면 `pass`.

**저장을 막지 않는다.** warn이 나와도 확인 화면에 경고를 띄우는 데까지가
역할이고, 사용자가 그대로 저장하면 저장된다(§3 원칙 그대로 구현). 존재하지
않는 tool_ref를 고르는 것 같은 진짜 무결성 오류는 이 검증이 다루지 않는다 —
저장 시점 `AgentCrudRepository.create`의 `_check_tool_refs`가 별도로 막는다.

### 1.2 구현

- `services/agent_builder/service.py`(신규) — `check_builder_input()`. pydantic
  모델(`BuilderCheckResult`, `DescriptionCheck`, `ToolMatchCheck`)로 출력
  스키마를 고정하고, OpenAI `client.responses.parse(text_format=...)`로 호출한다.
  `services/task_extraction`, `services/document_meta`가 이미 쓰는 것과 같은
  패턴이다. 모델은 가장 싼 모델(`OPENAI_PLAN_MODEL`) + 낮은 추론 — 이 판단이
  문장 다듬기·표면 대조 수준이라 `document_meta._summarize`의 요약 판단과
  같은 급으로 봤다. DB에 접근하지 않는다 — 도구 이름·설명은 호출자가 이미
  풀어서 넘긴다(`selected_tools`/`unselected_tools`), 테스트하기 쉽게 하려는
  의도다.
- `apps/agents/serializers.py` — `BuilderCheckSerializer`(입력 검증),
  `builder_check_response()`(출력 변환).
- `apps/agents/api_views.py` — `AgentBuilderCheckAPIView`. `tool_refs`로 넘어온
  코드값을 내장 도구 + 팀 MCP 도구 카탈로그와 대조해 이름·설명이 붙은 형태로
  나눈 뒤 서비스에 넘긴다. **저장하지 않는다** — 확인 화면에 띄울 결과만
  돌려준다.
- `POST /agents/build/check/` (신규 라우트).

## 2. 빌더 테스트 실행

### 2.1 배경 — "다른 프로덕트의 샌드박스"와 비교

사용자가 "다른 프로덕트는 샌드박스를 만들어 거기서 검증한다는데 우리도
그럴 수 없냐"고 물었다. 다른 프로덕트가 말하는 샌드박스는 대개 **외부
서비스가 따로 제공하는 진짜 테스트 인스턴스**(Stripe 테스트 키, Salesforce
샌드박스 조직 등)다. 우리 프로젝트에 그대로 적용하려면 팀이 지금 연결한
진짜 Jira 계정과 별개로 **테스트 전용 Jira 연결**을 하나 더 만들 수 있어야
하는데, Jira Cloud의 샌드박스 사이트 기능은 보통 유료 엔터프라이즈 플랜에만
있어 일반 팀이 무료로 구할 수 있다고 가정하기 어렵다. 커넥터 연결 화면에
"테스트용 연결" 개념을 추가하고 라우팅을 바꾸는 것 자체는 어렵지 않지만,
사용자가 테스트용 Jira 사이트를 별도로 준비해야 한다는 전제가 이 프로젝트
스코프 안에서 항상 성립한다고 보기 어려워 이번 범위에서는 택하지 않았다.

대신 **"쓰기 도구만 실제로 안 부르고 시뮬레이션"** 으로 같은 목적(진짜
Jira 이슈가 안 생김)을 달성했다. 읽기 도구는 애초에 팀 자신의 데이터라
"남의 것을 잘못 건드릴" 위험이 없으므로 실제로 실행한다 — 위험한 것은
외부 시스템에 쓰는 도구뿐이라 거기만 좁혀 다뤘다.

### 2.2 무엇을 확인하려는 것인가

"에이전트가 실제로 작동하는가"가 아니라 **"어떤 도구를 어떤 순서로 부르는가,
어떤 도구는 안 부르는가"** 를 보는 것이 목적이다(사용자 코멘트: "어쨌든
에이전트가 그 동작 과정을 따라가고 어떤 툴이 호출되고 어떤 툴이 호출이
안되는지, 실제 어떤 툴이 더 필요한지 알 수 있는거잖아"). 그래서 화면도
최종 답변 텍스트보다 도구 호출 목록에 더 큰 자리를 준다(§2.4).

### 2.3 결정한 것 — 저장 없이 그 자리에서 실행

두 가지 선택지를 놓고 논의했다.

| 안 | 장점 | 단점 |
|---|---|---|
| 저장 없이 그 자리에서 실행(채택) | 화면 설정값을 그대로 실행기에 넘긴다. 임시 저장이 없어 깔끔 | 기존 실행기(`run_agent`)가 DB의 에이전트만 돌릴 수 있어서 코드를 고쳐야 함 |
| 임시로 먼저 저장한 뒤 실행 | 기존 저장 로직을 그대로 씀 | 사용자가 아직 확정 안 한 에이전트가 DB에 잠깐이라도 남음(테스트만 하고 취소해도 흔적 발생 가능) |

전자를 채택 — 실행기를 확장하는 편이 "확정 안 한 것이 DB에 남는" 부작용보다
낫다고 판단했다.

### 2.4 구현 — 백엔드

- `services/harness/registry.py` — `load_for_refs(*, tool_refs, team_id)` 신규.
  기존 `load_for_agent`가 `agent_tool` 테이블에서 읽어 온 목록으로 하던 조립을,
  **아직 저장하지 않은 후보 목록**에도 쓸 수 있게 분리했다. `load_for_agent`는
  이제 `load_for_refs`를 감싸는 얇은 함수다(`AgentRepository.tool_refs(agent_id)`
  로 얻은 목록을 넘길 뿐).
- `services/harness/runner.py::run_agent` — 두 파라미터 추가.
  - `draft: dict | None` — 주면 `agent_id`·DB 조회를 건너뛰고 이 값(`team_id`,
    `instruction`, `model`, `reasoning_effort`, `max_iterations`, `tool_refs`)
    으로 agent/tools를 조립한다. `agent_id`는 여전히 `None`으로 남아 —
    `trace.run(agent_id=None, ...)`이 그대로 동작한다(v1 이전 세션에서
    `agent_run.agent_id`를 nullable로 만들어 둔 것을 그대로 재사용, §3 참고).
  - `dry_run: bool` — `True`면 승인이 필요한 도구(`side_effect=True`)를 실제로
    부르지 않는다. `EVENT_TOOL_CALL_STARTED`/`EVENT_TOOL_CALL_FINISHED`(상태
    `"SIMULATED"`, `arguments` 포함)만 내보내고 다음으로 넘어간다.
    `trace.tool_call()`도 걸지 않는다 — 실제로 일어나지 않은 호출을 감사
    로그에 남기지 않기 위해서다. 읽기 전용 도구는 dry_run이어도 그대로
    실행된다.
- `apps/agents/serializers.py` — `BuilderTestRunSerializer`(instruction,
  tool_refs, model, reasoning_effort, max_iterations, user_input).
- `apps/agents/api_views.py` — `AgentBuilderTestRunAPIView` + `_builder_test_events()`.
  `run_agent(None, user_input, {"account_id": ...}, draft=draft, dry_run=True)`를
  불러 이벤트를 NDJSON으로 스트리밍한다. 실패 처리 패턴은
  `apps/projects/api_views.py::_extraction_events`와 같다 — 응답이 이미
  시작된 뒤라 상태 코드를 바꿀 수 없어, 마지막 줄에 `error` 이벤트를 싣는다.
- `POST /agents/build/test/` (신규 라우트).

`task_extraction` 도구는 `proj_id`가 있어야 도는데, 지금 테스트 요청에는 그
값이 없다 — 이 도구를 고른 채로 테스트하면 실패로 뜬다. 알려진 공백으로
남겨 둔다(§4).

## 3. 실제로 걸린 문제 — `NotNullViolation`

사용자가 실제로 테스트 실행을 눌렀을 때 `테스트 실행에 실패했습니다:
NotNullViolation`이 떴다. 원인은 이번에 새로 짠 코드의 버그가 아니라 **v1
이전 세션에서 만든 마이그레이션(`DB/migrations/2026-08-11_chat_agentless.sql`,
`chat_session.agent_id`·`agent_run.agent_id`를 nullable로 바꾸는 것)이 실제
DB에 아직 적용되지 않은 상태**였기 때문이다. 이 세션 내내 DB에 직접 접근할
수 없어 파일만 만들고 실행은 못 했고, `agent_id`가 없는 채로 실행 기록을
남기는 코드 경로(에이전트 없는 채팅, 이번 테스트 실행)를 실제 DB로 확인해
본 것이 이번이 처음이라 이제야 드러났다.

해결은 그 마이그레이션을 실제로 적용하는 것뿐이다. 사용자 환경(Windows,
PowerShell)에 맞춰 아래 명령을 안내했다.

```powershell
Get-Content DB\migrations\2026-08-11_chat_agentless.sql -Raw | docker compose -f infra\docker\docker-compose.yml exec -T db psql -U project_copilot -d project_copilot -v ON_ERROR_STOP=1
```

이 마이그레이션이 적용되면 "에이전트 없는 채팅"과 "빌더 테스트 실행" 둘 다
같은 이유로 막혀 있었을 가능성이 커서, 둘 다 함께 풀린다.

## 4. 검증

- 백엔드: `python -m py_compile`로 `services/harness/registry.py`,
  `services/harness/runner.py`, `services/harness/__init__.py`,
  `services/agent_builder/service.py`, `services/agent_builder/__init__.py`,
  `apps/agents/serializers.py`, `apps/agents/api_views.py`,
  `apps/agents/api_urls.py`, `tests/test_harness.py` 전부 통과.
- 프론트: `npx tsc -b --noEmit` 통과(코드 추가할 때마다 반복 확인).
- 실제 라이브 DB·API로 붙여 본 것은 사용자가 직접 했고, 그 과정에서 위
  `NotNullViolation`이 나왔다 — 마이그레이션 적용 뒤 재확인이 필요하다.

## 5. 남아 있는 것

- **빌더 검증 결과를 보여줄 확인 화면이 없다.** `POST /agents/build/check/`는
  동작하지만, 그 결과(다듬은 지시문·경고)를 사용자에게 어떤 화면/UI로 보여줄지
  아직 설계하지 않았다(`빌더_에이전트_구체화.md` §6과 동일 항목).
- **빌더 흐름을 어느 화면에서 시작할지 미정.** 이번에 만든 검증·테스트
  실행은 전부 API/컴포넌트 레벨로는 동작하지만, "이름·설명·behavior·도구를
  입력하는 첫 화면" 자체가 아직 없다 — 지금은 기존 `AgentEditPage.tsx`(수동
  생성·편집 폼)에 테스트 실행 버튼만 얹은 상태다.
- **`task_extraction` 도구는 테스트 실행에서 항상 실패한다** — `proj_id`를
  받을 방법이 아직 없다.
- **진짜 샌드박스(전용 테스트 커넥터)는 만들지 않기로 했다** — §2.1의 이유.
  나중에 필요해지면 커넥터 연결 화면에 "테스트용 연결" 개념을 추가하고
  라우팅을 바꾸는 방향으로 갈 수 있다.
- **마이그레이션 적용 확인이 아직 안 끝났다** — 사용자가 위 명령을 돌린 뒤
  실제로 테스트 실행이 되는지 재확인이 필요하다.
