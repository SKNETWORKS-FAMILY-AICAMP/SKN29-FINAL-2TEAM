# 에이전트 빌더 구현 + 생명주기(DRAFT/ACTIVE/DISABLED) — 2026-08-12 작업 기록

> 이 문서는 명세가 아니라 **작업기록**이다 — 무엇을 왜 그렇게 했는지, 무엇을
> 스킵했는지, 중간에 뭐가 틀어졌는지를 시간 순으로 남긴다. "메인에 무엇을
> 추가해야 하는가"의 정본은 `에이전트_빌더_구현_명세.md`(v1~v4)이고, 이 문서는
> 그 명세와 **지금 실제로 한 일**이 어디서 갈라졌는지를 기록한다.

## 0. 시작 지점 — 명세와 실제 코드가 이미 갈라져 있었다

`docs/작업기록/jihun_buildingpage/`의 v1~v4 문서와 `에이전트_빌더_구현_명세.md`는
Cowork 세션에서 쓴 것이라 "pre-v1 baseline이 이미 있다"고 전제한다. 그런데
막상 메인을 열어보니 그 전제가 상당수 깨져 있었다:

- `Tool` dataclass에 `category` 필드가 없다.
- `services/harness/registry.py`에 `load_for_refs`가 없다 — `load_for_agent`
  만 있고, 그마저도 팀원이 그 사이 **에이전트가 에이전트를 부르는 위임 구조**
  (`agent:*` 정문, `AGENT_TOOL_WILDCARD`, `MAX_AGENT_DEPTH`)를 얹어 완전히
  다른 모양이 돼 있었다.
- "agentless 모드"(agent_id 없이 도는 실행)가 없다 — `run_agent`의
  `agent_id`가 `str`(필수)이고, `agent_run.agent_id` 컬럼도 **`NOT NULL`**
  이었다. 명세가 언급한 마이그레이션(`2026-08-11_chat_agentless.sql`)은 실제로
  반영된 적이 없다.
- `services/harness/scaffold.py`의 공통 지시문이 "계획을 먼저 늘어놓지 않는다.
  바로 한다"를 명시한다 — v4가 넣으려던 `write_todos`(계획 도구)와 정면으로
  충돌한다.
- 내장 도구가 6종이 아니라 **13종**이었고(팀원이 `feat(tools): 도구를 6종에서
  13종으로 늘린다`로 이미 확장), 명세가 추가하려던 `task_status`,
  `team_member_info`, `jira_update_issue` 셋과 이름도 내용도 다르다.

즉 "그대로 복붙"은 불가능했고, **무엇을 스킵하고 무엇을 지금 구조에 맞게
새로 짜야 하는지 판단**하는 일이 먼저였다.

## 1부. 빌더 플로우 이식 — 검증 → 도구 확인 → 대화 테스트

### 1.1 스킵한 것 (사용자 확인됨)

- **v1 전체**(`Tool.category`, `ToolPickerModal` 팝업, MCP 탭) — 팀원이 이미
  다른 형태로 도구 카탈로그 작업을 끝냈다는 판단하에 스킵. 지금 있는 인라인
  체크리스트 UI를 그대로 썼다. *(→ §1.4에서 결국 다시 추가함, 아래 참고)*
- **`write_todos`(계획 도구, v4)** — 현재 스캐폴드의 "바로 한다" 원칙과
  충돌해서 넣지 않았다.
- `tests/test_harness.py`의 `write_todos` 관련 기대값 수정 — 애초에 안 넣으니
  해당 없음.

### 1.2 실제로 이식한 것

**백엔드**
- `services/harness/registry.py`: `load_for_refs(*, tool_refs, team_id)`
  신규 — `load_for_agent`의 앞부분(내장+MCP 조립)만 떼어, 아직 `agent_tool`
  행이 없는 **저장 전 초안**도 도구를 조립할 수 있게 했다. 위임(`agent:`)
  브랜치는 안 넣었다 — 빌더 도구 카탈로그가 애초에 그 도구를 안 준다.
- `services/harness/trace.py`: `run_ephemeral()` / `tool_call_ephemeral()`
  신규 — **DB에 기록을 남기지 않는** `RunTrace` 짝. `agent_run.agent_id`가
  `NOT NULL`인데 초안엔 넣을 id가 없고, 저장 전 시험 실행을 평가 로그에
  실제 실행처럼 남기면 안 된다는 이유.
- `services/harness/runner.py`:
  - `run_agent`에 `draft: dict | None`, `dry_run: bool` 추가. `draft`가 있으면
    DB 조회 없이 그 값으로 조립하고, `trace.run_ephemeral()`을 쓴다.
  - `dry_run=True`면 승인 필요 도구를 실제로 안 부르고 `SIMULATED` 이벤트만
    낸다.
  - `check_tools()` 신규 — 선택한 도구 전부를 모델 판단 없이 순서대로 직접
    불러본다. 기존 `_injected()`를 그대로 재사용(중복 작성 안 함).
  - `grounded` 플래그 — `write_todos`가 없으니 "쓸 수 있는 도구가 있었는데
    하나도 안 부르고 답했는가"만 본다(`made_tool_call or not tools`).
- 신규 패키지 `services/agent_builder/` — `check_builder_input()`,
  `BuilderCheckResult`(pass/warn/reject). 명세 §6.4를 거의 그대로 썼다 — 이
  파일은 `category`나 특정 도구 목록에 의존하지 않아서 수정이 거의 필요
  없었다.
- `apps/agents/`: `BuilderCheckSerializer`/`BuilderTestRunSerializer`/
  `BuilderToolCheckSerializer`, `AgentBuilderCheckAPIView`
  (`POST build/check/`), `AgentBuilderTestRunAPIView`(`POST build/test/`,
  NDJSON), `AgentBuilderToolCheckAPIView`(`POST build/check-tools/`) 신규.

**프런트엔드**
- `frontend/src/api/client.ts`: `streamNdjson<TEvent>()`를 제네릭 공용
  함수로 승격 — `chat.ts`에 있던 비공개 복사본을 지우고 그 공용 함수를
  가져다 쓰게 리팩터(중복 제거).
- `frontend/src/api/agents.ts`: `BuilderTestEvent`, `BuilderCheckResult`,
  `ToolCheckResult`와 관련 API 함수 신규.
- 신규 컴포넌트 3종(`AgentEditPage/` 아래): `InstructionCheckPanel.tsx`
  (1단계 — 자동 검증, `reject`가 아니면 지시문 자동 채움), `ToolCheckPanel.tsx`
  (2단계 — 도구별 직접 확인, `input_schema`로 입력 폼 자동 생성),
  `TestRunModal.tsx` + `.module.css`(3단계 스테퍼: 검증 → 도구 확인 → 대화
  테스트).
- `AgentEditPage.tsx`: "테스트로 실행해보기" 카드 추가, 저장 직전
  `checkBuilderInput` 호출해 `reject`면 저장을 막는 게이트 추가.

### 1.3 검증

- Django `manage.py check`, 프런트 `tsc -b --noEmit` 통과.
- `build/check`·`build/test`·`build/check-tools` 세 엔드포인트를 curl로 직접

  ToolPickerModal 자체가 애초에 카테고리별로 안 묶고 평평한 목록으로 보여줘서

- `AgentEditPage.tsx`의 인라인 체크리스트를 칩(chip) 요약 + "도구 선택"

즉 v1을 통째로 스킵하지는 못했고, "카테고리 태깅"만 계속 스킵하고
"팝업 UI"는 나중에 들여왔다.

## 2부. 에이전트 생명주기 — DRAFT / ACTIVE / DISABLED

### 2.1 문제 제기

1부에서 만든 저장 게이트(`reject`면 저장 자체를 막음)는 검증되지 않은
에이전트가 Chat에 노출되는 건 막지만, **부작용이 있었다** — 검증에 걸리거나
사용자가 중간에 창을 닫으면 공들여 쓴 이름·설명·지시문이 **DB 어디에도
없이 통째로 사라진다.**

사용자가 이 문제를 짚으며 8단계 상태 머신을 제안했다:
`DRAFT → VALIDATING → NEEDS_REVIEW/BLOCKED → READY → ACTIVE → DISABLED`.

### 2.2 검토 — 8단계를 4단계로 줄인 이유

핵심 방향(생성=초안 저장, 게시=활성화는 별도 행위)은 동의했다. 다만
`VALIDATING`/`BLOCKED`/`NEEDS_REVIEW`/`READY`를 **DB 상태로 영구 저장하는
것**은 반대했다:

- `VALIDATING`은 지금 백그라운드 워커 없는 **동기 API 호출**(1~5초)이다.
  DB row 상태 전이로 만들면 write만 늘고 경쟁 상태 위험만 커진다 — 프런트
  상태로 충분하다(`InstructionCheckPanel`이 이미 그렇게 함).
- `READY`/`NEEDS_REVIEW`/`BLOCKED`는 사실 지금의 pass/warn/reject 그대로다.
  저장해두면 사용자가 지시문을 한 글자만 고쳐도 **오래된 값**이 남는다.
  결국 활성화 버튼을 누르는 순간엔 무조건 다시 검증해야 하니, 저장해둔
  중간 상태는 그 시점엔 의미가 없다.

그래서 **DRAFT → ACTIVE → DISABLED**(+ 기존 `ARCHIVED`=삭제) 4개로 줄이고,
pass/warn/reject는 계속 "그때그때 다시 묻는 값"으로 뒀다.

### 2.3 main 충돌 여부 확인

착수 전에 `git merge-tree`로 jihun과 origin/main을 실제 3-way 머지
시뮬레이션해 **충돌 0건**을 확인했다. origin/main이 그 사이 앞서간 커밋
2개(`fce6885`, `9c252c6`)는 `apps/chat/*`, `ChatSessionRepository`(다른
클래스), `runner.py`의 `_default_model`/`_tool_spec`(내가 건드린
`run_agent`/`check_tools`와 다른 구역 — 모델에 보내는 함수 이름에서 `:`를
빼는 버그 수정)만 건드렸고, `apps/agents/*`·`AgentEditPage`·`AgentListPage`는
전혀 안 건드렸다.

### 2.4 좋았던 발견 — DB 컬럼이 이미 있었다

`agent.status` 컬럼이 **이미 존재**했다(`VARCHAR(20) DEFAULT 'ACTIVE'`,
지금까지 `ACTIVE`/`ARCHIVED` 소프트 삭제용으로만 씀). `list_for_team`과
`callable_agents`(위임용)가 이미 `status = 'ACTIVE'`로 거르고 있어서,
**마이그레이션 없이** 값 종류만 늘리면 됐다.

또 하나 중요한 발견: `AgentListPage.tsx`와 `ChatPage.tsx`가 **같은
`listAgents()`**를 쓰고 있었다. 서버가 ACTIVE만 주게 두면 초안이 관리
목록에서도 안 보여서 "찾아서 이어 쓰기"가 안 된다 — 그래서 서버 필터는
`status <> 'ARCHIVED'`(DRAFT/ACTIVE/DISABLED 다 보임)로 넓히고, **Chat
쪽에서만 프런트에서** `status === 'ACTIVE'`로 다시 좁혔다.

### 2.5 구현

**백엔드**
- `backend/db/agent_platform.py`(`AgentCrudRepository`):
  - `list_for_team`: `status = 'ACTIVE'` → `status <> 'ARCHIVED'`.
  - `create()`: `status` 하드코딩(`'ACTIVE'`) → 파라미터 `status: str = "DRAFT"`.
  - `set_status(*, agent_id, account_id, status)` 신규 — `_writable_agent`
    재사용(기존 `update`/`delete`와 같은 패턴).
- `apps/agents/api_views.py`:
  - `AgentActivateAPIView`(`POST <id>/activate/`) — **DB에 저장된 현재
    값으로 서버가 다시 검증**한다(클라이언트가 "나 통과했음"이라고 보내는
    값을 안 믿음). `reject`면 409, 아니면 `ACTIVE`.
  - `AgentDisableAPIView`(`POST <id>/disable/`) — 검증 없이 바로 `DISABLED`.
  - 두 뷰가 검증 서비스 자체 실패(`PipelineConfigurationError`/`ValueError`)
    를 다루는 방식이 다르다 — `build/check`는 사용자에게 에러를 보여줘야
    하니 503을 내고, `activate`는 그것 때문에 활성화를 막지 않는다(배포
    사고 방지). 중복 코드를 없애려고 `_run_builder_check()` 헬퍼로 카탈로그
    조립+검증 호출을 뽑아 두 곳에서 같이 쓴다.
- `DB/schema.sql`: `status` 컬럼 주석만 갱신(실제 스키마 변경 없음).

**프런트엔드**
- `agents.ts`: `Agent.status` 필드, `activateAgent()`/`disableAgent()`.
- `AgentEditPage.tsx`: 상태 배지, `saveDraft()`(검증 없이 create/update만) +
  `handleTempSave`/`handleActivate`/`handleDisable`/`handleSaveActive` 네
  경로로 분리. 새 에이전트는 "임시 저장" 시 `navigate(..., { replace: true })`
  로 URL을 `/agents/<id>/edit`으로 바꿔치기해 뒤로가기 시 빈 폼이 다시 뜨지
  않게 했다.
- `AgentListPage.tsx`: 카드에 상태 배지, 상태별 액션(ACTIVE는 기존 + "사용
  중지", DRAFT는 "Chat에서 사용" 숨기고 "이어서 작성", DISABLED는 "다시
  활성화"). 활성화가 LLM 검증 때문에 몇 초 걸린다는 걸 실측으로 확인하고
  나서, 처리 중 버튼을 잠그고 라벨을 바꾸는 `pendingId` 상태를 추가했다
  (아래 §2.6 참고).
- `ChatPage.tsx`: `listAgents()` 결과를 `status === 'ACTIVE'`로 필터링한
  뒤에야 정문 에이전트 탐색과 "에이전트 없음" 배너 판단에 쓴다.

### 2.6 검증 중 발견한 것 — 활성화는 몇 초 걸린다

Playwright E2E로 "사용 중지 → 다시 활성화"를 검증하다가, 고정된 2초 대기
뒤 찍은 스크린샷에서 상태가 안 바뀐 것처럼 보이는 일이 있었다. 서버 로그를
보니 실제로는 `POST .../activate/`가 **200으로 성공**했고, `curl`로도
`status: ACTIVE`가 바로 확인됐다 — 테스트 스크립트의 대기 시간이 문제였다.

원인은 `activate`가 매번 `check_builder_input`(LLM 호출)을 다시 돌리기
때문에 실제로 몇 초가 걸린다는 것. 이건 진짜 제품 이슈이기도 해서(목록
페이지 버튼에 로딩 표시가 없어 중복 클릭 위험), `AgentListPage.tsx`에
`pendingId` 상태를 추가해 처리 중엔 버튼을 잠그고 "검증하는 중…"/"처리하는
중…"으로 라벨을 바꿨다. 이후 DOM 상태를 직접 기다리는(`waitForFunction`)
재검증으로 정상 동작을 확인했다.

### 2.7 최종 검증

- curl: `POST /agents/`(status 안 주면 DRAFT) → `GET /agents/`(DRAFT가
  목록에 보임) → `POST activate/`(빈 내용 → 409 reject) → 내용 채우고
  다시 `activate/`(200 ACTIVE) → `disable/`(DISABLED) → `activate/`(ACTIVE
  복구) — 전 구간 curl로 1차 확인.
- Playwright: 새 에이전트 폼에서 이름만 넣고 "임시 저장" → URL이
  `/agents/<id>/edit`로 바뀌는지 → 내용 부족한 채 "활성화" 눌러 409 에러가
  뜨고 폼 내용이 안 사라지는지 → 채우고 "활성화" → `/chat`으로 이동 →
  목록에서 "활성" 배지 확인 → "사용 중지" → "비활성" 배지 확인 → "다시
  활성화" → "활성" 배지 복귀까지 전부 스크린샷으로 확인.
- `tsc -b --noEmit`, `manage.py check` 통과.

## 3. 스코프에서 뺀 것 (다음에 볼 것)

- **운영자 콘솔에서의 강제 DISABLE.** `/api/ops/*`에 에이전트 관련
  엔드포인트가 아직 없다. 지금은 팀 소유자가 `AgentListPage`에서 직접
  켜고 끄는 자율 토글로만 만들었다. 나중에 운영자 강제 중지가 필요해지면
  같은 `AgentDisableAPIView`를 운영자 콘솔에서도 재사용할 수 있다.
- **정문(플랫폼) 에이전트의 생명주기.** `is_prebuilt` 에이전트는 이 생명주기를
  안 타고 시드 스크립트가 항상 `ACTIVE`로 만든다는 전제를 그대로 뒀다 —
  건드리지 않았다.
- `write_todos`/`PLANNING_TOOL`(v4) — 여전히 스킵 상태. 필요해지면 지금
  스캐폴드의 "바로 한다" 원칙부터 다시 논의해야 한다.
