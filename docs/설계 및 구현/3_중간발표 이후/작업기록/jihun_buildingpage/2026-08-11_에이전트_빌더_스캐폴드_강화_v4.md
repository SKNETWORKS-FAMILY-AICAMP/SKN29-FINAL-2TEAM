## 0. 무엇을 다시 열지 않았는가

이미 "적용 / 구조만 / 여지만 / 비적용"으로 정리해 둔 표는 이번에도 그대로
따랐다.

| 패턴 | 8/10 판정 | 이번에 다시 열었는가 |
|---|---|---|
| Task Planning (TODO) | 적용 | **적용을 실제 코드로 완성**(§1) — 유일하게 손댄 항목 |
| Context Offloading (가상 파일시스템) | 구조만 | 안 열었다 — 대표 시나리오의 툴콜 상한·결과 크기 제한으로 여전히 충분 |

## 1. `write_todos` — 계획을 실제 도구로

### 1.1 갭

`services/harness/scaffold.py`의 `COMMON_SCAFFOLD`는 "답하기 전에 무엇을
할지 짧게 계획한다"고 말만 했지, 그 계획이 상태로 저장되고 다음 턴에
참조되는 구조는 없었다 — `services/harness`를 통틀어 `write_todos` 같은
도구가 아예 없었다. deep-agents 원전이 말하는 "recitation"(계획을 반복해서
되뇌어 긴 작업에서도 목적을 안 잃는 장치) 효과를 전혀 못 내고 있었다.

### 1.2 설계 — 상태 저장소를 새로 안 만든다

deep-agents 프로덕션판은 Agent State에 별도 필드로 todo 리스트를 저장한다.
우리 Runner는 그런 상태 객체가 없지만, **이미 있는 `messages` 리스트가 매
턴 이어 붙고 있다는 사실만으로 충분하다.** `write_todos` 호출 결과
(function_call_output)가 그대로 `messages`에 남고, 다음 턴에 모델이 다시
읽는다 — 별도 저장 인프라 없이 "recitation"과 같은 효과를 낸다.

그래서 도구는 아주 얇다: 받은 `todos` 배열을 검증(상태값이 `pending`/
`in_progress`/`completed` 중 하나인지, 빈 `content`는 버리는 정도)해서
그대로 돌려주기만 한다. 매번 **전체 목록**을 새로 받는다 — 부분 수정이
아니다. 이것도 deep-agents 원전과 같은 계약이다.

### 1.3 어디에 붙는가 — 선택 대상이 아니라 스캐폴드와 같은 층

`write_todos`를 `BUILTIN_TOOLS`에 넣지 않았다. 그 딕셔너리는 빌더 화면에서
사용자가 체크박스로 켜고 끄는 업무 도구 카탈로그다(`/agents/tools/`,
`ToolPickerModal`). 계획 도구는 성격이 다르다 — 스캐폴드 문구처럼 모든
에이전트에 **항상** 붙어야 하고, 비개발자 사용자가 "이 도구를 쓸지 말지"
판단할 대상이 아니다.

- `services/harness/registry.py` — `PLANNING_TOOL`(신규, `ref="write_todos"`)
  을 `BUILTIN_TOOLS`와 별도 상수로 뒀다. `load_for_refs()`가 조립을 끝낸
  뒤 무조건 `available["write_todos"] = PLANNING_TOOL`을 붙인다 — 선택
  목록(`tool_refs`)에 있든 없든 상관없다.
- `services/harness/runner.py::run_agent` — `agent_id is None`(에이전트를
  안 고른 기본 채팅) 분기는 `load_for_refs`를 안 거치고 `tools = {}`를
  직접 만들던 자리라 별도로 `tools = {PLANNING_TOOL.ref: PLANNING_TOOL}`로
  바꿨다. "도구 없는 채팅"에도 계획 도구는 예외로 붙는다.
- **자동으로 빠지는 것들**: 도구 카탈로그 응답(`builtin_tool_response()`),
  도구별 직접 확인(`check_tools`, 호출자가 준 `tool_refs`만 순회하므로
  `write_todos`가 그 목록에 들어올 일이 없다), 빌더 검증의 tool_match_check
  대조(같은 이유) — 전부 `BUILTIN_TOOLS`를 기준으로 도는데 그 딕셔너리에
  없으니 아무 데도 안 나타난다. **별도 필터링 코드를 추가하지 않고 자료
  구조 선택만으로 격리를 얻었다.**

### 1.4 스캐폴드 문구 갱신

`COMMON_SCAFFOLD`의 [진행 방식] 절을 deep-agents 원전의 뉘앙스("Avoid for
single, trivial actions" — 간단한 작업엔 쓰지 마라)를 살려 바꿨다.

```
- 한두 번의 도구 호출로 끝나는 간단한 요청은 계획 없이 바로 처리한다.
- 여러 단계로 나뉘는 요청이면 write_todos로 할 일을 목록으로 적어 두고, 단계가
  끝날 때마다 상태(pending/in_progress/completed)를 갱신한다. 다시 적을 땐
  항상 전체 목록을 새로 보낸다 — 일부만 보내면 나머지는 빠진 것으로 본다.
```

`check_builder_input()`(빌더 검증 에이전트, v3 §4)도 이 스캐폴드 텍스트를
그대로 프롬프트에 embed하고 있어서(`_SCAFFOLD_TEXT`), 코드 한 곳만 고쳤는데
검증 프롬프트도 자동으로 `write_todos`를 알게 됐다 — 개별 지시문에
"계획을 세워라"를 또 적으라고 요구하지 않는다.

## 2. 근거 신호를 코드로 — `grounded` 플래그

### 2.1 문제

지난 대화에서 짚은 것: 스캐폴드의 [근거] 절("근거 없이 추측하지 않는다")은
순전히 텍스트 지시라, 모델이 안 지켜도 코드가 알아챌 방법이 없었다.
완전한 사실 검증(최종 답변 문장과 도구 결과를 대조해 각 주장이 실제로
뒷받침되는지 보는 것)은 그 자체로 별도 LLM 판단이 필요한 연구에 가까운
문제라 이번 범위에 넣지 않았다. 대신 **결정론적으로 셀 수 있는 가장 거친
신호** 하나를 코드로 만들었다: **쓸 수 있는 도구가 있었는데 하나도 안
부르고 답을 냈는가.**

### 2.2 구현

- `services/harness/runner.py::run_agent` — 루프 시작 전에
  `made_tool_call = False`를 두고, 도구 호출이 실제로 시도될 때마다(승인
  대기 전 시뮬레이션 포함, `write_todos`는 제외) `True`로 올린다.
  `write_todos`는 새 사실을 확인하는 도구가 아니라 계획 도구라 이 판단에서
  뺀다 — 계획만 세우고 아무것도 안 찾아본 답변까지 "근거 있음"으로 치면
  안 된다.
  ```python
  def _grounded() -> bool:
      data_tools_available = any(ref != PLANNING_TOOL.ref for ref in tools)
      return made_tool_call or not data_tools_available
  ```
  도구 자체가 없는 에이전트(순수 대화형)는 애초에 확인할 게 없으니
  `grounded=True`로 본다 — "확인할 게 있었는데 안 봤다"가 아니라 "볼 게
  없었다"이기 때문이다.
- 정상 종료(`EVENT_RESULT`, 도구 호출 없이 최종 답 낸 시점)와 상한 초과
  종료 두 곳 모두에 `"grounded": _grounded()`를 실어 보낸다.
- 스캐폴드 [근거] 절에도 한 줄 추가했다: "쓸 수 있는 도구가 있는데 하나도
  안 부르고 사실을 단정하면 안 된다." — 코드가 감지하는 것과 같은 규칙을
  텍스트로도 한 번 더 못박았다.

### 2.3 프론트엔드 노출

빌더 테스트 모달(v3 §3.2의 3단계, "대화 테스트")에만 우선 붙였다 — 실제
Chat 화면(`chat.ts`)은 이번에 건드리지 않았다(동작 중인 코드를 이 작업
때문에 손댈 이유가 없다는 기존 판단, v2와 같은 이유). 답변이 완료됐는데
`grounded === false`면 "이 답변은 쓸 수 있는 도구를 하나도 안 부르고
나왔습니다 — 근거 없이 단정한 내용일 수 있습니다" 경고를 최종 답변 박스
바로 아래 띄운다.

- `frontend/src/api/agents.ts` — `BuilderTestEvent`의 `result` variant에
  `grounded?: boolean` 추가.
- `frontend/src/pages/AgentEditPage/TestRunModal.tsx` — `resultGrounded`
  상태 추가, `result` 이벤트에서 채우고 모달 열 때·재실행 시 초기화한다.

### 2.4 이걸로 뭘 못 잡는가 — 정직하게 남겨 둔다

이 신호는 "도구를 아예 안 불렀는가"만 본다. **도구를 불렀는데 그 결과와
안 맞는 말을 덧붙이는 경우(더 미묘한 환각)는 여전히 못 잡는다** — 그건
최종 답변 문장과 도구 출력을 대조하는 별도 검증(예: 인용 표시를 강제하고
그 인용이 실제 도구 결과에 있는지 코드로 대조하는 방식)이 필요하고, 이번
범위에 넣지 않았다. §5에 남긴다.

## 3. 검증

- 백엔드: `python -m py_compile`로 `services/harness/registry.py`,
  `services/harness/runner.py`, `services/harness/scaffold.py`,
  `services/harness/__init__.py`, `services/agent_builder/service.py`,
  `apps/agents/api_views.py`, `apps/agents/serializers.py`,
  `tests/test_harness.py` 전부 통과.
- **기존 단위 테스트 두 건이 이번 변경으로 깨질 걸 코드 리뷰로 미리
  찾아서 고쳤다** — `write_todos`가 이제 모든 도구 목록에 항상 섞여
  들어가므로:
  - `RegistryTests.test_허용_목록에_없는_내장_도구는_빠진다` — `set(tools)`
    기대값을 `{"document_search"}` → `{"document_search", "write_todos"}`로.
  - `test_agent_id가_없으면_도구_없이_기본_대화로_돈다`(이름도
    `_업무_도구_없이_` 로 수정) — 모델에 넘어가는 `tools`가 빈 리스트라는
    기대를 `["write_todos"]` 하나만 있다는 기대로.
  - `EVENT_RESULT`에 `grounded` 키를 추가하는 변경은 기존 테스트가 전부
    `events[-1]["text"]`처럼 **개별 키만 읽지 dict 전체를 비교하지 않아서**
    깨지는 곳이 없었다.
- **이 세션의 샌드박스에는 Django/DB 환경이 없어 `manage.py test`를 실제로
  돌리지 못했다** — `django`가 없어 처음엔 `ModuleNotFoundError`, 최소
  패키지를 설치한 뒤에도 `config/settings/base.py`가 요구하는 `environ`
  등 의존성이 이어져서, 이 mount에는 프로젝트의 전체 의존성 목록이 없다는
  걸 확인만 하고 멈췄다. 위 두 건의 수정은 **코드를 손으로 따라가며
  검증**한 것이지 실제 테스트 러너로 통과를 확인한 게 아니다 — 사용자
  환경에서 `python manage.py test tests.test_harness`로 재확인이 필요하다.
- 프론트: `npx tsc -b --noEmit` 통과.

## 4. 왜 이번엔 실제 OpenAI 호출로 확인 안 했는가

이번 변경은 프롬프트 문구(스캐폴드)와 도구 스키마 추가가 대부분이라, "모델이
`write_todos`를 실제로 잘 쓰는지"는 코드 리뷰만으로는 확인할 수 없다 —
라이브로 몇 번 굴려 봐야 안다. v3 §5에 남긴 reject 라이브 확인과 같은
성격의 숙제로 §5에 합쳐 남긴다.

## 5. 남아 있는 것

- **`manage.py test tests.test_harness` 실제 실행 확인이 안 됐다**(§3).
- **`write_todos`가 실제 모델 호출에서 의도대로 쓰이는지 라이브 확인이
  안 됐다** — 간단한 요청엔 안 쓰고 여러 단계 요청에만 쓰는지, 목록을
  일부만 다시 보내는 실수를 하지는 않는지.
- **`grounded` 플래그가 실제로 유용한 신호인지도 라이브로 안 봤다** — 특히
  오탐(정말 필요 없어서 안 부른 걸 "근거 없음"으로 잘못 표시하는 경우)이
  얼마나 나오는지는 실사용해 봐야 안다.
- **v3 §5의 reject 라이브 확인**도 여전히 남아 있다 — 합쳐서 다음에 한
  번에 확인하는 게 효율적일 것.
- **더 정교한 근거 검증(인용-도구결과 대조)은 이번에 안 만들었다**(§2.4) —
  필요해지면 별도로 설계해야 한다.
- **실제 프로덕션 Chat 화면에는 `grounded` 경고가 아직 안 뜬다**(§2.3) —
  지금은 빌더 테스트 모달에서만 보인다.
