# 작업기록 v3 — 빌더 검증 고도화와 도구별 직접 확인 (2026-08-11)

> `2026-08-11_에이전트_빌더_검증_테스트실행_v2.md`(이하 v2)의 후속. v2가
> "검증 에이전트와 테스트 실행을 처음 만든 것"까지 다뤘다면, 이 문서는
> **실제로 써 보면서 드러난 문제를 고친 것**을 다룬다 — 모델이 도구를
> 안 부르는 상황을 확인하는 별도 경로, 검증·확인·실행 세 단계를 한 흐름으로
> 묶은 것, 그리고 검증 자체를 "경고만 하는 것"에서 "너무 부실하면 막는 것"
> 으로 강화한 것.
>
> 이번에도 `docs/빌더_에이전트_구체화.md`는 고치지 않는다 — 그 문서가
> 명시한 "hard fail 없음" 원칙에 이번에 예외(reject)가 생겼지만, 원본 문서를
> 계속 고쳐 쓰는 대신 이 v-시리즈 문서로 변경 이력을 남기기로 했다(사용자
> 결정).

## 1. 도구별 직접 확인 — 모델이 도구를 안 부르는 문제

### 1.1 실제로 걸린 문제

v2에서 만든 "대화로 테스트"(채팅식 테스트 실행)로 실제 확인해 보니 두 가지
문제가 나왔다.

1. **모델이 엉뚱한 도구를 골랐다.** `task_status`·`team_member_info`·
   `jira_update_issue` 세 도구가 정확히 필요한 지시문에 `document_search`를
   일부러 하나 더 넣어 "잘못된 도구가 섞여도 괜찮은지" 확인해 봤는데, 모델이
   `document_search`만 두 번 부르고 "현재 제공된 도구로는 마감일을 직접
   변경할 수 없습니다"라고 답했다 — `jira_update_issue`가 분명히 있는데도.
   사용자에게 "선택한 도구가 실제로 다 선택돼 있었는지"를 먼저 확인했고,
   ("1번이야") 4개 도구가 다 선택된 상태에서 모델이 잘못 고른 것으로
   확인됐다. **이 자체의 근본 원인(왜 `document_search`를 우선 골랐는지)은
   끝내 밝히지 못했다** — `services/harness/scaffold.py`를 훑어봤지만 결론을
   못 내고 대화가 다음 주제로 넘어갔다. 아직 미해결(§5).
2. **0건이 나오고 거기서 멈췄다.** 도구를 `task_status` 등 올바른 것들로
   다시 골라 테스트하니 `task_status`가 0건을 반환하고 모델이 거기서
   멈췄다. 사용자는 처음엔 버그로 의심했지만, 실제로는 스캐폴드의 "확인하지
   못한 것은 비워 두고 확인하지 못했다고 적는다" 원칙대로 **정상 동작**이었다
   — `exist_task` 테이블에 시드 데이터가 없고 실제 Jira 프로젝트 연동
   (`JiraProjectSelectPage.tsx` → `ProjecSourceRepository.register_from_jira`)
   으로만 채워지기 때문에 생긴, 데이터 공백 문제였다.

이 두 가지를 겪고 나서 사용자가 "정확히 툴 다 확인 할 수 있게 해 달라"고
요청했다. 처음엔 이걸 "새 기능을 만들어 달라"는 뜻으로 확대 해석해서
아래 §1.2 기능 전체를 만들었는데, 나중에 사용자가 "예시를 다시 만들란
말이었다"고 정정했다 — 실제로는 테스트용 예시 하나를 다시 달라는 요청이었다.
과잉 해석이었다는 걸 인정했고, 다만 이미 만든 기능이 "모델이 도구를 안
불러서 확인이 안 되는" 근본 문제 자체는 해결하므로 그대로 남겨 뒀다.

### 1.2 구현 — `check_tools()`

모델의 판단을 거치지 않고, 선택한 도구를 **순서대로 전부 직접 호출**해서
성공/실패/시뮬레이션 여부를 보여주는 별도 경로를 만들었다. "대화로 테스트"
가 못 하는 것 — 모델이 안 부른 도구는 확인 자체가 안 되는 것 — 을 메운다.

- `services/harness/runner.py` — `check_tools(*, team_id, account_id,
  tool_refs, arguments_by_ref=None) -> list[dict]`.
  - `_CHECK_EXCLUDED_TOOLS = frozenset({"task_extraction"})` — `proj_id`가
    있어야 도는 도구라 이 경로에서는 항상 `SKIPPED`로 건너뛴다(v2 §5에 남긴
    공백과 같은 이유).
  - `tool_refs`를 순서대로 돌면서 `registry.resolve`로 도구를 찾고, `side_effect`
    도구는 (실행 승인 절차가 이 경로엔 없으므로) 무조건 `SIMULATED`, 나머지는
    `trace.tool_call(...)` 안에서 실제로 호출한다.
  - 하나가 실패해도(`try/except Exception`) 나머지 도구는 계속 확인한다 —
    한 도구 실패로 전체 확인이 멈추면 안 된다.
  - 전체를 `trace.run(agent_id=None, session_id=None, parent_run_id=None)`로
    감싸 감사 로그에 남긴다.
- `apps/agents/serializers.py` — `builtin_tool_response()`에 `input_schema`
  (JSON Schema) 추가, `BuilderToolCheckSerializer`(tool_refs, arguments) 추가.
- `apps/agents/api_views.py` — `AgentBuilderToolCheckAPIView`.
- `POST /agents/build/check-tools/` (신규 라우트).
- 프론트 `ToolCheckPanel.tsx`(신규) — 선택된 도구마다 `input_schema.properties`
  로 입력 폼을 자동으로 만든다(string→입력창, integer/number→숫자 파싱,
  나머지→JSON 텍스트 영역). "전체 도구 확인" 버튼으로 한 번에 다 부르고,
  결과를 성공(초록)/실패(빨강)/시뮬레이션(주황)/건너뜀(회색) 배지로 보여준다.

## 2. 지시문·설명 검증 결과 화면

v2에서 `check_builder_input()`(검증 에이전트)은 API로는 동작했지만 그
결과(다듬은 지시문, 경고)를 보여줄 화면이 없었다(v2 §5 공백). 이걸
`InstructionCheckPanel.tsx`(신규)로 채웠다 — `TestRunModal`의 세 번째 탭으로
붙여서, overall 배지(통과/확인해 볼 점)·description 검증 의견·tool_match
누락/불필요 목록·다듬은 지시문(적용 버튼 포함)을 보여준다.

## 3. 검증·확인·실행을 한 흐름으로 묶기

### 3.1 문제 의식

세 기능(①설명·지시문 검증 §2, ②도구별 직접 확인 §1.2, ③대화로 테스트 실행,
v2 §2)이 각각 독립된 탭으로만 존재해서 서로 이어지지 않았다. 사용자 요청:
"테스트 하기 누르면 설명·지시문 검증이 들어가고, 휴먼인더루프로 사람이
고치면 다시 검증되고, 그다음 도구가 다 되는지 확인하고, 마지막으로 실제
대화에서 그 도구들이 다 불리는지·빠진 게 없는지 — 이 세 개가 한 번에
검증돼야 한다."

### 3.2 구현 — `TestRunModal.tsx`를 단계형으로 재구성

독립 탭 3개를 **순서가 있는 3단계**로 바꿨다. 탭처럼 보이지만 번호가
붙고("1. 설명·지시문 검증", "2. 도구 확인", "3. 대화 테스트"), 각 단계
안에 "다음 단계로" 버튼이 있어 앞에서 정한 값이 뒤로 그대로 이어진다.
모달을 열 때마다 항상 1단계부터 다시 시작한다.

- **1단계(`InstructionCheckPanel`)** — 모달이 열리면 자동으로 한 번
  검증한다. 결과로 받은 `refined_instruction`을 지시문 편집칸에 바로
  채워 준다(사람이 이어서 손볼 수 있게). 사람이 설명·지시문을 고치고
  "수정한 내용으로 다시 검증하기"를 누르면 같은 자리에서 다시 돈다 —
  이게 요청한 휴먼인더루프 루프다. "다음 단계"를 누르면 그 시점의
  설명·지시문이 `AgentEditPage`의 실제 상태(`onApplyDescription`/
  `onApplyInstruction`)에 반영되고 2단계로 넘어간다.
- **2단계(`ToolCheckPanel`, §1.2 그대로 재사용)** — "다음 단계: 대화
  테스트" 버튼만 추가했다. 도구 확인 결과와 무관하게 넘어갈 수 있다 —
  실패한 도구가 있다는 사실 자체가 유용한 정보이지, 진행을 막을 이유는
  아니라고 봤다.
- **3단계(대화로 테스트, v2 §2.5 그대로)** — 답변이 끝나면 추가로 **"선택한
  도구 대비 호출 결과"** 를 보여준다. `tool_call_started` 이벤트에서 받은
  `tool_ref`를 단계마다 기록해 뒀다가(`TestStep.toolRef` 필드 추가), 이번
  대화에서 한 번도 안 불린 `tool_refs`를 이름으로 나열한다. "이 질문에
  필요 없었을 수도 있고 모델이 놓쳤을 수도 있다"는 문구를 같이 보여주고,
  2단계(도구별 직접 확인)나 다른 질문으로 다시 확인해 보라고 안내한다 —
  §1.1에서 겪은 "모델이 안 부른 도구는 확인이 안 된다" 문제를 3단계
  안에서도 눈에 띄게 만든 것.

## 4. 빌더 검증 고도화 — 스캐폴드 인지, reject 등급, 저장 게이트

### 4.1 문제 의식

사용자가 세 가지를 지적했다.

1. **스캐폴드(공통 지침)를 검증이 몰랐다.** `services/harness/scaffold.py`
   의 `COMMON_SCAFFOLD`는 모든 에이전트에 이미 적용되는 공통 규칙(계획 안내,
   도구 호출 상한, 근거 원칙, 외부 변경 승인)인데, v2의 검증 프롬프트는 이걸
   "공통 규칙이 있다"고 막연히만 언급했지 실제 문구를 모델에게 보여주지
   않았다 — 그래서 중복·모순 여부를 정확히 판단하기 어려웠다.
2. **너무 부실하면 아예 반려돼야 한다.** v2까지는 `overall`이 `pass`/`warn`
   둘뿐이고 `빌더_에이전트_구체화.md` §3의 "hard fail 없음" 원칙대로 warn도
   저장을 막지 않았다. 그런데 설명·지시문이 사실상 비어 있거나 "알아서
   해줘" 식이면, 그건 "참고만 하고 넘어가도 되는 경고"가 아니라 "다듬을
   실질 내용 자체가 없는" 문제다 — 이런 경우는 막아야 한다.
3. **지시문에 꼭 들어가야 할 내용을 정의해야 한다.** description의 기준
   (동사·대상·산출물)은 v2부터 있었지만 instruction(behavior)의 충분성
   기준은 없었다.

### 4.2 결정 — 지시문 필수 4요소

behavior가 다음 네 가지를 실질적으로 담고 있는지를 기준으로 삼았다(도구를
하나도 안 골랐으면 ③은 보지 않는다).

| 요소 | 의미 | 예 |
|---|---|---|
| ① 트리거 조건 | 언제/어떤 요청에 반응하는지 | "마감 임박 업무를 물으면" |
| ② 절차 | 무엇을 어떤 순서로 확인·처리하는지 | "먼저 업무 현황을 보고, 막힌 게 있으면 담당자를 찾는다" |
| ③ 도구 사용 기준 | 선택한 도구를 어떤 상황에 쓰는지 | "담당자를 못 찾으면 팀원 정보 도구로 재확인" |
| ④ 판단 기준 | 이 도메인에서 뭘 "문제/막힘/승인 필요"로 볼지 | "마감일이 지났으면 막힌 업무로 본다" |

### 4.3 구현 — 백엔드 (`services/agent_builder/service.py`)

- `_SCAFFOLD_TEXT = COMMON_SCAFFOLD.format(max_iterations=6)` — 빌더가
  만드는 에이전트는 항상 `max_iterations=6` 고정값을 쓰므로(§4,
  `빌더_에이전트_구체화.md` §4) 그 값으로 스캐폴드 문구를 채워 시스템
  프롬프트에 실제 텍스트를 그대로 넣었다. 이제 모델이 "이미 공통 적용되는
  내용"을 정확히 알고 (a) `refined_instruction`에서 중복 제거, (b) behavior가
  그 원칙과 모순되면(예: "근거 없이 그냥 답해", "승인 없이 바로 등록해")
  지적할 수 있다.
- `InstructionCheck` 모델(신규, `note: str | None`) — §4.2의 4요소 충족
  여부를 본다. `BuilderCheckResult`에 `instruction_check` 필드로 추가.
- `BuilderCheckResult.overall: Literal["pass", "warn", "reject"]` — 기존
  pass/warn에 reject 추가. `reject_reason: str | None` 필드 신설(reject일
  때만 채움).
- **reject 판정 기준**: description과 behavior 중 하나라도 사실상 비어
  있거나 "알아서"·"적절히"·"필요하면 처리" 같은 위임 표현뿐이라 §4.2의
  ①~④ 중 단 하나도 구체적으로 뽑을 수 없는 수준. **"애매해서 참고하라"가
  아니라 "다듬어서 고칠 수 있는 재료 자체가 없다"** 는 뜻이라 warn과
  질적으로 다르게 취급한다.
- reject일 때 `refined_instruction`은 빈 문자열로 둔다 — 없는 내용을
  지어내지 않는다는 원칙(스캐폴드의 "근거 없이 추측 금지"를 검증 자체에도
  적용한 것).
- `apps/agents/serializers.py::builder_check_response()` — `instruction_check`,
  `reject_reason` 필드를 응답에 추가.

### 4.4 구현 — 프론트엔드

- `frontend/src/api/agents.ts` — `BuilderCheckResult`에 `instruction_check`,
  `overall: 'pass' | 'warn' | 'reject'`, `reject_reason` 추가.
- `InstructionCheckPanel.tsx`:
  - `OVERALL_LABEL`에 `reject`(danger 톤, "반려 — 내용을 다시 써야 합니다")
    추가.
  - `reject_reason`을 에러 박스로 눈에 띄게 보여준다.
  - "지시문 내용" 블록 추가 — `instruction_check.note`를 보여준다.
  - **reject일 때 `refined_instruction`(빈 문자열)으로 사람이 이미 입력한
    지시문 초안을 덮어쓰지 않는다** — `run()`에서 `overall !== 'reject'`일
    때만 `draftInstruction`을 갱신하도록 조건을 걸었다. 빈 문자열로 자동
    갱신했다면 reject가 뜨는 순간 사람이 쓰던 내용이 사라지는 사고가 났을
    것이다.
  - "다음 단계: 도구 확인" 버튼을 `result.overall === 'reject'`일 때
    비활성화한다 — 내용을 고치고 다시 검증해서 pass/warn이 될 때까지
    §3.2의 2단계로 못 넘어간다.
- `AgentEditPage.tsx::handleSave()` — **저장 버튼도 막는다**(이번 요청).
  저장 직전에 항상 `checkBuilderInput()`을 한 번 부르고, `overall ===
  'reject'`면 `reject_reason`(없으면 기본 안내 문구)을 페이지 에러로
  보여주고 저장을 멈춘다. **검증 호출 자체가 실패하면(OpenAI 설정 문제
  등) 저장까지 막지는 않는다** — 인프라 문제 때문에 저장이 아예 불가능해
  지면 안 되므로, 실제로 `reject` 판정이 나온 경우에만 막도록 `catch`에서
  조용히 넘어가게 했다.

## 5. 검증

- 백엔드: `python -m py_compile`로 `services/agent_builder/service.py`,
  `services/agent_builder/__init__.py`, `apps/agents/serializers.py` 통과.
- 프론트: 변경할 때마다 `npx tsc -b --noEmit` 통과 (`ToolCheckPanel.tsx`,
  `InstructionCheckPanel.tsx`, `TestRunModal.tsx`, `AgentEditPage.tsx`,
  `frontend/src/api/agents.ts` 전부 포함).
- **reject 판정이 실제 OpenAI 호출에서 의도한 대로 나오는지는 라이브로
  확인하지 못했다** — 이 세션에서는 코드 작성과 타입 체크까지만 했다.
  "이름: 업무 도우미 / 설명: 업무를 도와주는 에이전트 / 지시문: 사용자가
  물어보면 알아서 확인하고 필요하면 처리해줘"처럼 일부러 부실하게 만든
  예시(이 세션 중 사용자 요청으로 만들어 둠)로 실제 reject가 뜨는지 다음에
  확인이 필요하다.
