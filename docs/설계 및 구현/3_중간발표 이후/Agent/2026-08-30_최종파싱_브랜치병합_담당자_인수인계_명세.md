## 4. 추가 보완 레이어

### 4.1 읽기 순서 보완

`runpod_worker/reading_order_postprocess/`가 담당한다. Docling 구조를 분석해 검증된 동일
parent·인접 항목의 역전만 수정한다. 전체 문서를 좌표순으로 무리하게 재정렬하지 않는다.
수정된 구조는 DoclingDocument로 다시 검증한다. 이후 헤딩 밀도 계산은 화면의 단순 수직
좌표가 아니라 보정된 `reading_order_index`를 사용한다.

Worker 연결점은 `worker_reading_order_adapter.py`다. 하위 패키지에는 affiliation,
continuation, correction, detector, evaluation, features, mapping, relation audit,
semantic scope, review triage, VLM context, XY-cut shadow와 검증 도구가 포함된다.

### 4.2 헤딩 보완

`runpod_worker/density_heading_correction.py`가 담당한다. Docling이 일반 `text`로 분류한
실제 헤딩 후보를 글자 높이, 위아래 문맥 밀도, 여백, 열 구조와 보정된 읽기 순서로
판정해 `section_header`로 승격한다. 그림 내부 항목은 후보에서 제외한다. 자동 승격은
일반 `text`만 대상으로 하며 `list_item`은 참고값으로만 사용한다.

### 4.3 테이블 보완

`runpod_worker/table_gate.py`가 담당한다. TableFormer ACCURATE/cell matching 결과에서
다음 고정밀 오탐만 제거한다.

- `DOT_LEADER_TOC`
- `TITLE_PAGE_LIST`
- `SHORT_SINGLE_CELL_FRAGMENT`
- `ALL_BULLETED_LONG_TEXT`
- `ALL_SENTENCE_EXTREME_TEXT`
- `FULL_WIDTH_PAGE_NUMBER_LIST`

그 외 TableItem은 fail-open으로 보존한다. 셀 임의 삽입, span 재구성, 다른 TableFormer
모드 재시도는 하지 않는다. 살아남은 표는 기존 구조 보존 청킹으로 보내며 제품 열 구조가
있으면 제품별 record, 아니면 행별 record를 만든다.

### 4.4 문맥 기반 이미지 설명

`runpod_worker/context_picture_description.py`가 담당한다. 읽기 순서·헤딩·테이블 보완이
끝난 문서를 embedded Docling JSON으로 다시 읽고 Qwen VLM을 실행한다. caption, section
path와 sibling 문맥은 최종 구조를 기준으로 한다.

| 항목 | 값 |
|---|---|
| VLM batch | `4` |
| element batch | `4` |
| 최소 picture 면적 | 페이지의 `0.02` |
| classification confidence | `0.5` |
| 전체 문맥 | `1200`자 |
| 앞뒤 sibling 문맥 | 합계 `500`자 |
| 최대 이미지 변 | `1280` |
| 생성 최대 token | `224` |
| sampling | 사용 안 함 |
| repetition penalty | `1.25` |

caption, footnote, reference, 직전 section header, 동일 parent·동일 페이지의 앞뒤 text를
사용한다. header/footer/page number, 다른 picture와 table은 주변 text에서 제외한다.
chart, flow, drawing, screenshot, map, photo, chemistry, table, generic route별 prompt를
사용한다.

prompt 누출, 입력 echo, 길이 불량, 비한국어, 무효 응답과 반복 문장은 저장하지 않는다.
통과한 설명만 PictureItem `meta.description`에 기록한다. Qwen 단계만 실패하면 문서 전체를
실패시키지 않고 구조 보완 문서를 유지하며 audit에 실패 원인을 남긴다.

### 4.5 Description 우선·기본 시리얼라이저 fallback

`runpod_worker/picture_description_serializer.py`가 담당한다. PictureItem의 검색·임베딩
문장은 승인된 `meta.description.text`가 있으면 그 값만 사용한다. 이 경우 다음은
포함하지 않는다.

- caption
- picture classification과 confidence
- molecule/chart 등 다른 picture meta
- image placeholder
- picture 내부 OCR text
- heading 직렬화 문자열
- 같은 heading 아래의 인접 본문

Docling은 item serializer와 meta serializer를 각각 실행하므로 description이 중복될 수
있다. 승인된 description이 있을 때만 `PictureMetaSuppressingSerializer`가 picture
meta의 별도 경로를 억제하고 `DescriptionOnlyPictureSerializer`가 description을 한 번만
반환한다. description이 없거나 품질 검증에서 탈락하면 Docling 기본 Picture·meta
serializer를 사용해 caption·기본 annotation을 검색 fallback으로 남긴다.

기존 운영값 `merge_peers=true`에서는 이미지 description과 뒤 본문이 합쳐질 수 있다.
`DescriptionOnlyHybridChunker`는 picture ref가 든 청크를 merge 경계로 고정한다.
picture가 아닌 청크끼리는 Docling의 원래 merge를 유지한다. picture 청크에는
`contextualize()`가 아니라 `chunk.text`를 사용하므로 heading도 붙지 않는다.

현재 `chunk_type`은 호환성을 위해 `text`를 유지한다. 별도 DB type 추가가 아니라 picture
ref 하나와 description 우선·기본 serializer fallback 검색 문장을 보장하는 단계다.

## 5. 응답 계약

기존 최상위 응답, `blocks`, `chunks`, `embeddings`와 768차원 계약은 유지한다. 다음
audit만 추가됐다.

```json
{
  "validation": {
    "passed": true,
    "promoted_heading_count": 2,
    "final_parse": {
      "stage_order": ["docling", "reading_order", "heading", "table_gate", "picture_description"],
      "reading_order": {},
      "heading": {},
      "table_gate": {},
      "picture_description": {}
    }
  }
}
```

`promoted_heading_count`는 하위 호환을 위해 유지한다. 현재 Django ingest는
`validation.passed`만 필수 검사하고 추가 audit은 무시하므로 기존 API를 깨지 않는다.

## 9. `main` 병합 담당자 절차

### 병합 전

1. 작성자 브랜치와 commit hash를 확인한다.
2. 작성 브랜치가 기준 `main` 커밋 `7807143` 이후의 변경을 포함하는지 확인한다.
3. 그 사이 `origin/main`이 변경됐다면 최신 main과 충돌을 먼저 해결한다.
4. `pipeline.py`, `requirements.txt`, `density_heading_correction.py`,
   `tests/test_document_pipeline.py` 충돌은 자동 선택하지 말고 양쪽 로직을 검토한다.
5. 신규 파일과 `reading_order_postprocess/` 전체가 commit됐는지 확인한다.
6. 의존성 pin, VLM batch 4, 레이어 실행 순서와 serializer 연결을 확인한다.
7. 관련 테스트를 실행한다.

## 10. `main` 병합 후 RunPod 배포

통합 저장소의 `runpod_worker/`는 실제 배포 정본이 아니라 프로젝트 사본이다. 실제 배포
정보는 다음과 같다.

```text
Worker 저장소: choiwon10/SKN29-RUNPOD-WORKER
기존 배포 브랜치: codex/install-triton-compiler
Docker Hub: somber7/skn29-runpod-worker
Endpoint: SKN29-RUNPOD-WORKER-IMG
```

현재 확인한 로컬 PC에는 별도 Worker 저장소 clone과 Docker CLI가 없다. 담당자 또는 배포
권한 보유자가 아래 작업을 수행해야 한다.

### 10.1 실제 Worker 저장소 동기화

1. `choiwon10/SKN29-RUNPOD-WORKER`를 clone한다.
2. `codex/install-triton-compiler`의 compiler/build-essential 보완을 유지한다.
3. 통합 저장소 `runpod_worker/` 내용을 Worker 저장소 root에 반영한다.
4. 아래 배포 필수 파일을 확인한다.

```text
Dockerfile
handler.py
pipeline.py
requirements.txt
density_heading_correction.py
table_gate.py
context_picture_description.py
picture_description_serializer.py
reading_order_postprocess/
```

5. 실제 Worker 저장소에서 diff를 검토하고 commit/push한다.

### 10.2 Docker image 생성

RunPod 호환을 위해 `linux/amd64`로 build하고 `latest`가 아닌 고정 tag를 사용한다.

```powershell
docker login
docker build `
  --platform linux/amd64 `
  --tag somber7/skn29-runpod-worker:<새-고정-tag> `
  .
docker push somber7/skn29-runpod-worker:<새-고정-tag>
```

Docker Hub `somber7` namespace에 push 권한이 필요하다. private image라면 RunPod Registry
인증도 유효해야 한다.

### 10.3 기존 RunPod Template 갱신

Endpoint를 새로 만들거나 삭제하지 않는다. 기존 Endpoint가 사용하는 Serverless
Template의 Container Image만 다음으로 변경한다.

```text
docker.io/somber7/skn29-runpod-worker:<새-고정-tag>
```

저장 후 기존 Worker가 `Outdated`를 거쳐 교체되고 새 Worker가 `Ready`가 되는지 확인한다.

### 10.4 유지할 Endpoint 설정

| 항목 | 값 |
|---|---|
| Endpoint type | Queue |
| GPU count | 1 |
| Active workers | 0, 시연 전 필요하면 일시적으로 1 |
| Max workers | 1 |
| Idle timeout | 300초 |
| Execution timeout | 1,800초 |
| FlashBoot | 활성 |
| 환경변수 | 기존 `HF_TOKEN`, `EMBEDDING_MODEL`, `EMBEDDING_DEVICE` |

새 환경변수나 DB 접속정보는 필요 없다. Worker는 서명된 HTTPS `source_url`을 받고 결과만
반환하며 DB transaction은 Django가 담당한다.

VLM batch 4의 첫 운영 검증은 48 GB GPU가 안전하다. 24 GB GPU는 peak VRAM을 확인하기
전까지 fallback에서 제외한다. OOM 발생 시 동시 처리 수, converter cache 해제, batch 4
peak VRAM을 확인한다. batch 4는 사용자 확정값이므로 측정 없이 임의 변경하지 않는다.

## 12. DB와 Backend 영향

### DB migration 불필요

현재 DB에는 이미 `doc_id`, `cur_revision`, `file_name`, `storage_key`, block의
`block_type`, `page`, `src_locator`, chunk의 `search_text`, vector의 `embedding`이 있다.
기존 응답 구조와 768차원 계약도 유지하므로 이번 파싱 병합에는 migration이 필요 없다.

### 이번 병합으로 되는 범위

- 이미지 VLM description 생성
- description 우선·기본 Picture serializer fallback 검색 문장 생성
- 이미지와 인접 본문의 merge 방지
- picture ref, page, bbox 보존 기반 유지
- description embedding 저장·검색 기반 생성

### 이미지 검색 결과의 원본 crop 역추적 구현

이미지 description 또는 기본 serializer fallback은 검색용 인덱스이며 해당 문장을
임베딩한다. 서버 고정 하이브리드 상위 20개 안에 `PICTURE` 청크가 포함되면
`chunk → block_id → doc_id/revision →
storage_key + src_locator.prov[].bbox`로 원본을 역추적한다. 문서 제목이나 페이지 번호만으로
찾지 않으므로 동명 문서와 개정본을 혼동하지 않는다.

도구는 다음 두 개로 분리했다.

| 도구 | 사용 모델 | 반환 |
|---|---|---|
| `document_search` | 모든 모델 | 상위 일반 본문 텍스트와 최소 인용 정보. PICTURE description은 점수 계산에만 사용 |
| `document_search_with_images` | 이미지 입력 지원 모델만 | 동일 하이브리드 검색과 상위 `PICTURE` 근거의 서명된 원본 PDF crop 이미지 |

검색 결과 수는 모델 입력이 아니라 서버에서 20개로 고정한다. PICTURE의 `search_text`는
벡터·FTS·trigram 하이브리드 점수 계산에만 사용하며 모델의 텍스트 evidence에는 넣지
않는다. 이미지 도구는 서로 다른 `block_id` 기준 상위 5개만 원본 crop으로 첨부한다.
문서명, MIME, block type, page, revision은 역추적에 사용하고 최종 이미지 evidence에는
이미지 URL·문서명·페이지만 추가한다. bbox와 벡터 DB의 무거운 metadata 전체는 모델에
전달하지 않는다.

`DocumentPictureCropAPIView`는 URL 서명에 들어 있는 `block_id + doc_id + revision`이
현재 문서 revision의 `PICTURE` block과 정확히 일치하는지 다시 조회한다. 삭제·접근 철회
문서, 과거 revision, PDF가 아닌 문서와 storage key가 없는 문서는 반환하지 않는다.
Docling의 `BOTTOMLEFT`/`TOPLEFT` 좌표를 PDF 좌표로 변환하고 4pt 여백, 2배율 PNG로
동적 렌더링한다. 서명 기본 유효시간은 900초다.

crop 이미지는 DB나 Worker 디스크에 영구 저장하지 않고 Django가 보관한 원본에서 응답
시점에 만든다. 따라서 이 목적만으로 Network Volume은 필요 없다. Network Volume은 모델
cache와 cold start 완화용 선택사항이다. DOCX는 렌더러에 따라 페이지 좌표가 달라질 수
있으므로 첫 crop API는 PDF만 대상으로 제한하는 것이 안전하다.

### 모델 capability와 에이전트 빌더

기본 OpenAI·Anthropic 모델은 모델 선택 목록에 `이미지` 표시가 붙는다. 운영자가 등록하는
OpenAI-compatible 모델은 등록 화면의 `이미지 입력 지원` 체크값을 암호화된
`connector_conn` payload에 함께 저장한다. 기존 테이블을 그대로 사용하므로 DB migration은
없다. 체크하지 않은 커스텀 모델은 텍스트 전용으로 취급한다.

에이전트 편집 화면은 텍스트 모델에서 `document_search_with_images` 선택을 비활성화하고,
이미 선택된 상태에서 텍스트 모델로 바꾸면 해당 도구를 제거한다. 프론트 우회 요청에
대해서도 에이전트 저장·활성화 API와 실제 `ToolLoader` 실행 시점에서 다시 차단한다.

### Backend 배포 시 추가 확인

- `requirements/base.txt`에 추가된 `PyMuPDF>=1.26,<2.0` 설치
- 외부 모델이 접근할 수 있는 HTTPS `PUBLIC_BACKEND_BASE_URL` 설정
- 필요 시 `DOCUMENT_PICTURE_CROP_TOKEN_MAX_AGE_SECONDS` 조정(기본 900초)
- Backend 프로세스 재배포 및 정적 프론트 재빌드
- RunPod Endpoint와 Worker 코드는 이번 역추적 기능 때문에 추가 수정할 필요 없음
