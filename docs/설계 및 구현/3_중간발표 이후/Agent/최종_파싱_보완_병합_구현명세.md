# 최종 파싱 보완 병합 구현 명세

## 1. 반영 범위

`C:/final_project/parser/final_parse` 산출물을 현재 `main`의
`runpod_worker` 실행 계약에 맞게 병합했다. 독립 실험 드라이버를 그대로 복사하지
않고, Worker의 다운로드·형식 분기·선택적 OCR·구조 보존 청킹·EmbeddingGemma
임베딩 경계를 유지한 채 다음 네 보완 레이어를 청킹 직전에 연결했다.

```text
PDF/DOCX/MD 다운로드
  → Docling 기본 변환
  → Reading Order 보완
  → Density Heading 보완
  → TableItem 비표 gate
  → 문맥 기반 Picture Description
  → HybridChunker + 구조 보존 표 청킹
  → EmbeddingGemma 768차원
  → 기존 Worker 응답
```

## 2. 최종 파싱 원본 검사 결과와 수정

| 검사 항목 | 발견 내용 | 병합 처리 |
|---|---|---|
| Python 구문 | 원본 `.py`와 노트북 셀은 구문 통과 | 병합본 전체 `py_compile` 재검사 |
| 외부 경로 | `final_parse_pipeline.py`가 `C:/final_project/parser` 개발 폴더를 runtime에 요구 | Worker 안으로 검증 모듈을 vendor하여 배포 경로 의존 제거 |
| Heading schema | JSON dict의 `label`만 `section_header`로 바꾸는 경로는 discriminated model 검증 위험 | 기존 Worker의 `SectionHeaderItem` 객체 교체 방식 유지 |
| Heading policy | R&D detector는 `list_item`도 후보 | 운영은 `text`만 적용, `list_item`은 shadow-only |
| Heading density | 기존 Worker는 좌표 120pt 창, 최종본은 보정된 순서의 앞뒤 3개 item | 최종본의 `reading_order_index` 기반 계산으로 교체 |
| Picture module | notebook `exec` 전용이라 import와 상수가 없고 `_ref_value` 구현도 누락 | 독립 import 모듈화, 상수·routing·실행 함수·ref normalizer 추가 |
| Picture 순서 | 기존 Worker는 Docling 변환 중 이미지 설명 | 구조 보완 뒤 embedded JSON을 다시 읽어 설명하도록 이동 |
| Table | 기존 Worker는 TableFormer 기본 옵션과 모든 검출 table 청킹 | ACCURATE/cell matching 명시 후 고정밀 비표 gate 선적용 |
| 버전 | Worker 2.117 / Transformers 4.x, 최종본 2.119 / 5.8 | Worker 요구 버전을 최종본에 맞춤 |

## 3. Docling 기본 변환

### 3.1 유지한 메인 Worker 정책

- PDF 텍스트 연산자 `Tj/TJ`가 200개 이상이면 텍스트 레이어가 있는 것으로 보고
  OCR을 끈다. 이는 정상 PDF 본문을 OCR이 훼손했던 실측 문제를 막는 기존 정책이다.
- `force_backend_text=True`를 유지한다.
- PDF, DOCX, Markdown 및 `text/plain → .md` 형식 계약을 유지한다.
- 임베딩과 청킹은 기존 EmbeddingGemma tokenizer, 768차원, 최대 2048 입력 검증을
  그대로 사용한다.

### 3.2 변경한 활성 옵션

| 옵션 | 값 |
|---|---|
| Docling | `2.119.0` |
| Transformers | `5.8.0` |
| Sentence Transformers | `6.0.0` |
| layout | `DOCLING_LAYOUT_HERON` |
| OCR | EasyOCR `ko/en`, `LAYOUT_REGIONS`, scale `3.0`, confidence `0.35` |
| table | `do_table_structure=True` |
| TableFormer | `ACCURATE`, `do_cell_matching=True` |
| picture classification | 첫 변환에서 활성, compile 비활성 |
| built-in picture description | 비활성 |
| chart extraction | 비활성 |
| images | scale `2.0`, page/picture image 생성 |
| parsed pages | 활성 |
| heading hierarchy | bookmark/numbering/style, threshold `0.8`, max level `6` |
| batch | OCR/layout/table 각각 `1` |

내장 설명과 chart extraction은 구조 보완 전 문맥을 사용하고 Granite model GPU 중복
적재 위험이 있어 사용하지 않는다.

## 4. Reading Order 보완

`reading_order_postprocess/`는 전달 패키지의 검증 구현 전체를 포함한다. 호출 policy는
`validated-local-v1`, audit 구현 버전은 `validated-local-v1.1`이다.

자동 적용은 동일 parent의 인접 sibling 두 개가 `LOCAL_VERTICAL_INVERSION`, `HIGH`,
`AUTO_REORDER_ELIGIBLE`, `SWAP_ADJACENT`이고, 사이 sibling 0, 단순 geometry,
text quality risk 없음일 때만 수행한다. comparison grid/form/stage-detail scanner와
dense row guard가 위험을 찾으면 원본을 보존한다.

변경은 parent `children`의 두 참조 위치뿐이다. ref multiset, item 수, label, bbox,
text와 provenance는 바뀌지 않는다. 적용 뒤 모든 ref resolve와 Docling schema를
검사하며 실패하면 adapter가 원본 객체를 반환한다.

## 5. Heading 보완

문서 순회에서 `text`, `list_item`, `section_header`, `caption`, `footnote`를 문맥으로
수집한다. picture 아래 텍스트는 제외한다.

- column 기준: left 좌표 gap `100pt`
- body height: 같은 page/column의 일반 `text` cell height median
- density: 보정된 `reading_order_index`의 앞뒤 최대 `3`개 평균 문자 수
- 짧음: `60`자 이하
- 상대 크기: `height >= body_height × 1.15`
- 위 여백: 첫 item 또는 `gap_above >= 4pt`
- density score: `below - above >= 0`

네 detector 조건을 모두 만족해도 운영 guard를 추가로 통과해야 한다.

- 원본 label `text`만 자동 적용
- `key_value_region/key_value_area` 제외
- density-only `list_item`은 shadow-only

적용 시 같은 ref와 모든 구조 필드를 가진 `SectionHeaderItem(level=1)`으로 교체하고
전체 document schema를 재검증한다.

## 6. TableItem 보완

`TABLEITEM_HIGH_PRECISION_FAIL_OPEN_V1` gate를 청킹보다 먼저 실행한다. cell text,
문장·bullet·점선 leader·페이지 번호, span과 bbox를 사용한다.

Reject reason은 `DOT_LEADER_TOC`, `TITLE_PAGE_LIST`,
`SHORT_SINGLE_CELL_FRAGMENT`, `ALL_BULLETED_LONG_TEXT`,
`ALL_SENTENCE_EXTREME_TEXT`, `FULL_WIDTH_PAGE_NUMBER_LIST`다. 그 외는 전부
보존한다. reject는 `document.delete_items`로 ref-safe 삭제하며, 삭제 뒤 gate를
재실행해 reject가 남지 않아야 한다.

이 gate 뒤의 기존 구조 보존 표 청킹은 살아남은 실제 table에만 적용된다. 제품 열
구조가 있으면 제품별 record, 아니면 일반 행 record를 만들고 table-only HybridChunk는
기존처럼 제거한다.

## 7. 문맥 기반 이미지 설명

구조 보완이 끝난 document를 embedded Docling JSON으로 임시 저장하고 JSON backend로
다시 읽는다. Picture classifier top class와 confidence, picture/page 면적을 사용한다.

- 최소 picture 면적: 페이지의 `0.02`
- 분류 confidence: `0.5`
- 문맥 총 길이: `1200`자
- 앞뒤 sibling 문맥: 합계 `500`자
- VLM 최대 이미지 side: `1280`
- VLM batch: `4`
- 생성: 최대 `224` token, sampling 없음, repetition penalty `1.25`

문맥은 caption, footnote, reference, 직전 section header, 같은 parent·같은 페이지의
앞뒤 text다. header/footer/page number, 다른 picture와 table은 주변 text에서 제외한다.
chart/flow/drawing/screenshot/map/photo/chemistry/table/generic route별 prompt를 사용한다.

prompt 누출, 구조화 입력 echo, 너무 짧거나 긴 응답, 비한국어, 무효 응답과 반복 문장은
저장하지 않는다. 성공 설명은 picture `meta.description`에 기록한다.

청킹 시 `DescriptionOnlySerializerProvider`를 `HybridChunker`에 주입한다. 이 provider는
PictureItem 직렬화 결과로 승인된 `meta.description.text`만 사용한다. caption, picture
classification, molecule/chart 등 다른 picture meta, image placeholder와 picture 내부 OCR
text는 이미지 검색 문장에 포함하지 않는다. Docling은 item serializer와 meta serializer를
각각 실행하므로 picture meta 경로는 별도로 억제해 description이 두 번 들어가는 것도
방지한다. 일반 text/table/list와 해당 meta 직렬화는 Docling 기본값을 유지한다.

운영값 `merge_peers=true`에서 이미지 description이 같은 heading의 인접 본문과 다시
합쳐지지 않도록 picture ref가 든 청크를 merge 경계로 취급한다. picture가 아닌 연속
청크는 기존 Docling merge를 그대로 실행한다. 최종 임베딩 문장은 picture 청크에만
`chunk.text`를 사용하고, 일반 청크는 기존 `contextualize()`를 사용한다. 따라서 이미지
검색 문장은 heading·caption 없이 VLM description만 가진다. 승인된 description이 없는
picture는 빈 이미지 청크를 만들지 않는다.

첫 변환 classification이 실패하면 PDF만 classification 없이 한 번 재시도한다. Qwen
후단만 실패하면 구조 보완 document를 유지하고 audit에 정확한 예외를 남긴다.

## 8. Worker 응답과 호환성

기존 응답 최상위 schema, blocks, chunks, embedding과 기존 validation 필드는 유지한다.
추가 필드는 다음 하나다.

```json
{
  "validation": {
    "passed": true,
    "promoted_heading_count": 2,
    "final_parse": {
      "stage_order": ["docling", "reading_order", "heading", "table_gate", "picture_description"],
      "reading_order": {},
      "heading": {},
      "table_gate": {},
      "picture_description": {}
    }
  }
}
```

`promoted_heading_count`는 하위 호환을 위해 남기고 실제 적용 수를 기록한다.

## 9. DB·Backend·배포 영향 보고

### 9.1 DB

이번 병합에 DB migration은 필요하지 않다. `backend/db/document_pipeline.py`의 ingest는
`validation.passed`만 검사하고 새 `validation.final_parse`를 컬럼에 저장하지 않는다.
blocks, chunks, vector schema와 768차원 계약도 바뀌지 않는다.

이미지 활용 목적은 crop 파일을 DB에 저장하는 것이 아니다. Picture description을
독립 검색 대상으로 임베딩하고, 검색에 걸렸을 때 원본 문서에서 해당 영역을 다시
렌더링한다. 이때 기존 컬럼을 다음과 같이 사용한다.

- `doc.doc_id`, `cur_revision`, `file_name`, `storage_key`: 원본 식별·표시·조회
- `doc_block.block_type='PICTURE'`, `page`, `src_locator.prov[].bbox`: 이미지 위치
- `chunk.search_text`, `vec_idx.embedding`: VLM 설명 검색

제목은 화면 표시값이며 원본 식별 키로 쓰지 않는다. 실제 crop 요청은 이름 중복과
revision 경합을 피하도록 `doc_id + revision + chunk_id`로 받고, 서버가 DB의 page/bbox를
조회하는 방식이 안전하다.

현재 스키마에는 필요한 필드가 있지만 서비스 연결은 아직 완성되지 않았다.

1. Worker는 picture description마다 picture ref 하나만 가진 전용 chunk를 보장한다.
2. `VectorSearchRepository.search`가 `block_type`, `page`, `src_locator`, `file_name`,
   `revision`, `mime_type`을 함께 반환해야 한다.
3. 현재 evidence view에서 제외한 locator 중 위의 작은 필드만 다시 노출해야 한다.
4. 인증·문서 권한·현재 revision을 검사한 crop API가 원본 PDF 페이지를 렌더링하고
   Docling bbox의 좌표 원점을 변환해 PNG/WebP로 응답해야 한다.
5. 프론트는 텍스트 답변과 별도로 구조화된 image evidence를 렌더링해야 한다.

따라서 이 목적 자체에는 DB migration이 아니라 Worker·검색 SQL·Backend crop API·응답
schema·Frontend 수정이 필요하다. DOCX는 PDF처럼 안정적인 페이지 렌더 좌표 계약이
없으므로 우선 PDF picture만 동적 crop 대상으로 제한한다.

단, 단계별 audit을 장기 보존하거나 운영 화면에서 조회하려면 별도 JSONB 컬럼 또는
object storage 저장 설계가 필요하다. 이는 현재 요청 범위에는 포함하지 않았다.

### 9.2 Backend/API

요청 payload와 응답 필수 필드가 유지되므로 Django API 수정은 필요하지 않다. 새 audit은
추가 JSON 필드이며 현재 ingest가 무시해 하위 호환된다.

### 9.3 RunPod Worker

실제 변경이 필요한 핵심 대상이다.

- `runpod_worker/pipeline.py`
- `density_heading_correction.py`
- 신규 `reading_order_postprocess/`
- 신규 `table_gate.py`
- 신규 `context_picture_description.py`
- 신규 `picture_description_serializer.py`
- `requirements.txt`
- Worker README와 회귀 테스트

이 저장소의 `runpod_worker/`는 읽기용 사본이라는 기존 운영 문서가 있다. 실제 배포
정본 저장소에도 같은 변경을 반영하고 Docker image를 재빌드한 뒤 Endpoint tag를
교체해야 서비스에 적용된다.

### 9.4 RunPod 자원

Qwen 설명을 후단에서 로드하므로 첫 변환 converter cache를 비우고 CUDA cache를 정리한다.
그 대신 문서별 layout/TableFormer model 재로딩 비용과 Qwen VRAM/다운로드 용량이 늘 수
있다. 실제 Endpoint에서 cold start, peak VRAM, container disk와 처리 시간을 측정해야 한다.
