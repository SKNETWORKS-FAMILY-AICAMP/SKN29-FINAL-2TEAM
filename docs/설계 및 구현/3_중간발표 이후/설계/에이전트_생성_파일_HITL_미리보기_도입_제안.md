# 에이전트 생성 파일 HITL 미리보기 도입 제안

> 기준 코드: 2026-08-27에 확인한 최신 `origin/main` (`a1f0562`)
> 목적: Excel·Word 등 파일을 실제 저장하기 전에 사용자가 내용을 확인하고 승인·거절할 수 있게 한다.

## 2026-08-28 마감 일정 기준 구현 결정

회의 내용과 실제 HITL 이벤트 흐름을 다시 대조한 결과, 아래의 임시 파일·렌더링 구조는 장기 확장안으로 보류하고 **기존 승인 이벤트에 들어 있는 생성 예정 입력을 보여 주는 경량안**을 먼저 적용했다.

| 구분 | 이번 적용 | 장기안으로 보류 |
|---|---|---|
| 미리보기 근거 | `awaiting_confirmation.action_requests[].args` | 승인 전 임시 XLSX·DOCX 파일 |
| 지원 도구 | 내장 `table_export`, `document_create` | 임의 MCP·사용자 생성 도구 |
| 표시 | 제목, 행·열 수, 표 앞 20행·12열 / 문서 앞 4,000자 | 실제 Office 렌더링, 시트·페이지 탐색 |
| 서버·DB | 변경 없음 | 초안 ID, TTL, 해시, 임시 저장소 |
| 승인 의미 | 표시한 **생성 예정 내용**으로 도구 실행 승인 | 실제 생성된 초안과 최종 저장물 동일성 승인 |

이 경량안은 실제 파일을 미리 렌더링하지 않으므로 완성 파일의 서식·수식·페이지 배치는 검증하지 못한다. 대신 사용자가 무엇을 생성하려는지 모른 채 승인하던 문제를 낮은 비용으로 완화하며, 미리보기 실패나 미지원 도구는 기존 승인 카드로 돌아가 실행을 막지 않는다. 추가 LLM 호출이나 토큰 비용도 없다.

## 문서를 처음 읽는 분을 위한 요약

### 누구를 위한 기능인가

에이전트에게 “업무 현황을 Excel로 만들어 줘”, “보고서를 Word로 만들어 줘”라고 요청하고, 생성 결과를 저장하기 전에 검토해야 하는 일반 사용자·PM·승인자를 위한 기능입니다.

### 현재 무엇이 불편한가

현재 파일 생성 도구는 실행되면 파일을 만든 뒤 “내 파일”에 저장하고 다운로드 카드를 보여줍니다. 승인 절차가 연결되더라도 사용자는 파일의 실제 표나 문서 내용을 보지 못한 채 **도구 실행 자체**를 승인할 수 있습니다.

### 장기적으로 무엇을 바꾸자는 것인가

최종 저장 전의 임시 파일을 만들고 승인 화면 안에서 내용을 보여줍니다. 사용자가 승인하면 정식 파일로 저장하고, 거절하면 임시 파일을 버립니다.

### 이번 문서에서 결정된 것과 아직 제안인 것

| 구분 | 내용 |
|---|---|
| 코드로 확인한 현행 | 파일 생성·“내 파일” 저장·완료 후 다운로드, HITL 승인·거절, Jira 승인 전 필드 미리보기 |
| 이번 구현 | 기존 이벤트 입력 기반의 표·문서 생성 예정 내용 미리보기 |
| 장기 권장안 | 필요성이 확인되면 임시 초안 계층을 넣고 XLSX부터 실제 내용 미리보기 제공 |
| 팀 결정 필요 | 승인 전 임시 파일 생성 허용 여부, 저장 위치·보관 시간, 담당자 분담 |
| 이번 작업에서 하지 않은 것 | 서버·DB·이벤트 계약·실제 파일 렌더링 변경, 배포 |

### 사용자가 보게 될 화면 예시

```text
┌ 업무 부하표를 만들려고 합니다 ─────────────────────┐
│ 파일: 4주_업무부하.xlsx                              │
│ 시트 1개 · 32행 · 6열                                │
│                                                       │
│ [미리보기]                                            │
│ 팀원     배정시간     가용시간     부하율             │
│ 김지훈      24           160          15%              │
│ 임준억      40           160          25%              │
│ … 처음 50행 표시                                     │
│                                                       │
│                    [거절] [다시 만들기] [승인 및 저장] │
└───────────────────────────────────────────────────────┘
```

승인 전에는 일반 문서 목록이나 검색에 나타나지 않습니다. 승인 후에는 지금과 동일하게 “내 파일”에 저장되고 다운로드 카드가 나타납니다.

### 용어를 쉽게 풀면

| 용어 | 이 문서에서의 뜻 |
|---|---|
| HITL | AI가 바로 확정하지 않고 사람의 승인·거절을 기다리는 절차 |
| 초안(Artifact Draft) | 아직 정식 저장되지 않은 임시 생성 파일 |
| Artifact | Excel·Word·PDF·이미지처럼 에이전트가 만든 결과물 |
| 이벤트 계약 | 서버가 화면에 상태와 데이터를 어떤 필드로 전달할지 정한 규칙 |
| TTL | 승인되지 않은 임시 파일을 자동 삭제하기까지의 보관 시간 |
| 내용 해시 | 사용자가 본 초안과 저장할 파일이 같은지 확인하는 지문 값 |

## 1. 한 문장으로 설명하면

현재는 에이전트가 파일을 만든 **뒤에** 다운로드할 수 있습니다. 제안 기능은 파일을 영구 저장하기 **전에 임시 초안과 미리보기를 만들고**, 사용자가 내용을 확인한 뒤 승인하면 저장하고 거절하면 폐기하는 흐름입니다. 이는 AI의 내부 생각을 보여주는 기능이 아니라, **실제로 저장될 결과물을 검토하는 기능**입니다.

```text
현재
도구 호출 → 파일 생성·내 파일 저장 → 완료 카드와 다운로드

제안
도구 호출 계획 → 임시 초안 생성 → 미리보기 + 승인/거절
                                    ├─ 승인 → 내 파일에 영구 저장
                                    └─ 거절 → 임시 초안 폐기
```

## 2. 왜 필요한가

승인 버튼만 있고 결과물을 볼 수 없다면 사용자는 사실상 다음 내용을 모른 채 승인합니다.

- 표의 열·행·계산 결과가 요청과 맞는지
- 문서 제목과 본문에 빠진 내용이나 잘못된 내용이 없는지
- 민감정보 또는 불필요한 데이터가 포함되었는지
- 파일 형식과 분량이 의도한 결과인지

특히 현재 `table_export`는 모델이 표 값을 옮겨 적어 XLSX를 만들기 때문에 원본과 다를 가능성이 코드 주석에도 명시되어 있습니다. 이 경우 미리보기는 장식이 아니라 **승인 판단의 근거**입니다.

다만 모든 도구 호출에 미리보기가 필요한 것은 아닙니다. 조회 도구는 기존 사용자용 결과 요약이 적절하고, 파일 생성·외부 전송·등록처럼 결과가 남는 도구에만 적용하는 것이 맞습니다.

## 3. 현재 프로젝트에는 무엇이 이미 있는가

아래는 제안 사항이 아니라 최신 `main` 코드에서 확인한 현행입니다.

- 영구 파일과 구분되는 **임시 초안 상태**
- 미리보기용 안전한 조회 API
- 초안 만료·삭제 정책
- 승인한 미리보기와 실제 저장 파일이 같은지 확인하는 내용 해시
- 파일 형식별 렌더러
- 사용자 제작 도구·MCP 도구도 사용할 수 있는 공통 미리보기 계약

## 4. 권장 구조

HITL 미들웨어가 Excel·Word를 직접 화면으로 변환하게 하지 않습니다. 기존 승인 기능은 계속 “무엇을 승인하는가”만 전달하고, 파일 초안 생성·미리보기·자동 삭제는 별도의 **임시 결과물 서비스**가 담당하는 편이 안전합니다. 이렇게 나누면 승인 기능 담당 코드가 파일 형식마다 복잡해지는 것을 막을 수 있습니다.

```text
Agent / Tool
  │  생성할 파일의 데이터 또는 초안 요청
  ▼
Artifact Draft Service (신규)
  ├─ 임시 파일 생성
  ├─ 안전한 미리보기 데이터 생성
  ├─ content_hash 계산
  └─ TTL 만료 관리
  │
  ▼
awaiting_confirmation (기존 이벤트 확장)
  └─ artifact_previews[]
       ├─ artifact_id
       ├─ file_name / mime_type
       ├─ preview_type / preview_ref
       ├─ summary
       └─ content_hash
  │
  ▼
ConfirmCard (기존 UI 확장)
  ├─ 미리보기
  ├─ 승인
  └─ 거절
       ├─ 승인: hash 검증 → 내 파일에 최종 저장 → produced_file
       └─ 거절: 초안 폐기 → 도구 실행 취소/재작성
```

### 4.1 제안 계약 예시

```json
{
  "artifact_id": "draft_...",
  "file_name": "4주_업무부하.xlsx",
  "mime_type": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
  "preview_type": "table",
  "preview_ref": "/api/artifact-drafts/draft_.../preview",
  "summary": {
    "sheet_count": 1,
    "row_count": 32,
    "column_count": 6
  },
  "content_hash": "sha256:...",
  "expires_at": "2026-08-27T18:00:00+09:00"
}
```

승인 요청에는 `artifact_id`와 `content_hash`를 함께 보냅니다. 서버는 승인 시점에 해시가 다르면 저장하지 않고 다시 확인하도록 해야 합니다. 사용자가 본 초안과 실제 저장되는 파일이 달라지는 문제를 막기 위해서입니다.

## 5. 미리보기 수준별 난이도와 효용

아래 일정은 현재 구조를 기준으로 한 상대적 추정이며, 담당자 분담·스토리지 정책·배포 환경에 따라 달라집니다.

| 단계 | 제공 기능 | 난이도 | 예상 작업량 | 사용자 효용 | 한계 |
|---|---|---:|---:|---:|---|
| 0. 현행 | 생성 완료 후 파일명·다운로드 | 이미 구현 | - | 낮음 | 승인 전 확인 불가 |
| 1. 생성 계획 미리보기 | 파일명, 형식, 표 열·행 수, 문서 개요 | 낮음 | 1~3인일 | 중간 | 실제 렌더링 결과와 다를 수 있음 |
| 2. XLSX·CSV 초안 미리보기 | 시트 목록, 읽기 전용 표, 행·열 수, 일부 수식 표시 | 중간 | 4~8인일 | 매우 높음 | 초안 저장·TTL·해시·API 필요 |
| 3. PDF·이미지·텍스트 | 페이지/이미지/안전한 텍스트 뷰어 | 중간 | 추가 3~7인일 | 높음 | 파일 크기·페이지 제한 필요 |
| 4. DOCX·PPTX 범용 미리보기 | PDF 변환 또는 페이지·슬라이드 이미지 | 높음 | 추가 1~3주 | 높음 | 변환기·폰트·워커·운영 비용 증가 |
| 5. 사용자·MCP 도구 공통화 | 등록 도구가 동일 계약으로 미리보기 제공 | 높음 | 별도 설계 필요 | 확장성 높음 | 신뢰 경계와 호환성 관리 필요 |

### 비용 관점

- 표·PDF·이미지 렌더링은 결정론적 코드로 처리하면 **추가 LLM 토큰은 들지 않습니다**.
- CPU, 임시 스토리지, 네트워크 전송 비용과 응답 대기 시간은 늘어납니다.
- 별도 LLM을 호출해 초안을 요약하면 토큰 비용과 왜곡 가능성이 생기므로 MVP에는 권하지 않습니다.
- 미리보기 데이터가 이미 도구 입력에 있다면 그 데이터를 그대로 구조화해 보여주는 것이 가장 저렴하고 정확합니다.

## 6. 파일 형식별 권장 UX

### XLSX·CSV — 1차 도입 권장

- 파일명, 시트 수, 전체 행·열 수 표시
- 기본은 첫 시트의 처음 50~100행만 읽기 전용 그리드로 표시
- 시트 전환, 가로·세로 스크롤, 전체 화면 미리보기 제공
- 수식은 실행하지 않고 수식 문자열 또는 계산된 저장값만 표시
- 외부 링크·매크로는 실행하지 않음
- 승인 후에만 “내 파일”에 저장

### DOCX

- 1차에는 제목·본문 개요 또는 안전한 텍스트 미리보기만 제공
- 이후 PDF 또는 페이지 이미지 변환을 붙여 실제 레이아웃 확인 지원
- 시스템 폰트 차이로 변환 결과가 달라질 수 있음을 표시

### PDF·이미지

- 브라우저 기본 PDF 뷰어나 서버가 만든 페이지 이미지를 사용
- 이미지는 안전한 MIME·크기 검증 후 인라인 표시

### 미지원 형식

- 파일명, MIME, 크기, 생성 도구, 만료 시각만 표시
- 임시 파일 직접 다운로드는 정책 결정 전에는 제공하지 않는 편이 안전함

## 7. 사용자 제작 도구와 MCP 도구는 어떻게 연결하는가

모든 도구 결과를 프론트가 추측해 해석하는 방식은 확장하기 어렵습니다. 도구가 선택적으로 공통 `artifact_draft` 계약을 반환하도록 하는 것이 좋습니다.

```json
{
  "artifact_draft": {
    "artifact_id": "draft_...",
    "file_name": "report.xlsx",
    "mime_type": "...",
    "preview_type": "table",
    "content_hash": "sha256:..."
  }
}
```

- 내장 도구: 서버가 계약 준수를 보장하므로 전체 미리보기 가능
- 플랫폼에서 만든 사용자 도구: SDK/스키마 검증을 통과하면 동일하게 표시
- MCP·외부 도구: 임의 HTML·원격 URL을 그대로 렌더링하지 않고, 서버가 가져와 검사한 안전한 초안만 표시
- 계약 미지원 도구: 기존 HITL 설명과 입력값만 표시하는 안전한 fallback 유지

이 구조에서는 새로운 도구가 추가되어도 `ConfirmCard`에 도구 이름별 분기를 계속 늘리지 않아도 됩니다.

## 8. 기존 코드에 미치는 영향

### 백엔드 — 중간 이상

- `table_export`·`document_create`를 **준비(prepare)**와 **확정(commit)** 단계로 분리
- 임시 초안 저장소와 TTL 정리 작업 추가
- 승인 시 pending action과 초안의 소유자·해시 검증
- `awaiting_confirmation` 이벤트에 `artifact_previews` 추가
- 거절·중단·세션 만료 시 초안 폐기
- 기존 `file`/`produced_file` 계약은 승인 완료 후 결과로 유지

### 프론트엔드 — 중간

- 승인 카드에 형식별 미리보기 영역 추가
- 로딩·실패·만료·재생성 상태 처리
- 큰 표는 일부 행만 표시하고 전체 화면/스크롤 제공
- 키보드 접근성, 모바일 화면, 승인 버튼과의 시각적 우선순위 검증

### 데이터·운영 — 중간 이상

- 영구 문서와 섞이지 않는 초안 저장 위치 필요
- 사용자·테넌트별 접근 통제 필요
- TTL 만료와 고아 파일 정리 필요
- 변환 실패율, 생성 시간, 저장 용량, 승인·거절률 관측 필요

### 기존 기능 호환성

- 조회 도구와 현재 사용자용 도구 결과 UI에는 영향 없음
- 기존 Jira HITL은 유지 가능
- `artifact_previews`가 없는 기존 이벤트는 지금 UI로 동작하도록 optional 필드로 추가
- 완료 후 `ProducedFilesCard`와 “내 파일” 흐름은 유지

## 9. 보안·정합성 원칙

- 임시 초안은 승인 전 외부 공유·검색·일반 문서 목록 노출 금지
- 승인 요청 사용자와 초안 소유자가 같은지 검증
- `content_hash`가 다르면 승인 무효화 후 재확인
- HTML, JavaScript, 매크로, 외부 참조, 수식의 실행 금지
- MIME·확장자·크기·페이지·행 수 제한
- 로그에는 파일 본문과 민감정보를 남기지 않음
- 실패 시 “미리보기 생성 실패”와 “파일 생성 실패”를 구분
- 승인·거절·만료·최종 저장을 감사 로그에 기록

## 10. 권장 도입 순서

### 0단계 — 팀 합의

다음 세 가지를 먼저 정합니다.

1. 승인 전 임시 파일 생성을 허용할 것인가
2. 초안을 어디에 얼마나 오래 보관할 것인가
3. 이 기능의 백엔드·HITL·프론트 책임자를 어떻게 나눌 것인가

### 1단계 — 계약과 계획 미리보기

- `artifact_previews[]` 이벤트 계약을 optional로 정의
- `table_export`, `document_create`에 파일명·형식·개요 미리보기 제공
- 실제 저장은 기존대로 유지하거나 기능 플래그 뒤에 둠
- 목적: UI와 계약을 작은 범위에서 검증

> 이 단계는 기술 검증용입니다. 실제 파일 내용을 보여주지 않으므로 “보고 승인한다”는 최종 목표를 달성한 것으로 간주하지 않습니다.

### 2단계 — XLSX 초안 MVP

- `table_export`를 prepare/commit으로 분리
- 임시 XLSX, 표 미리보기 API, TTL, 해시 검증 구현
- 승인하면 “내 파일”에 저장, 거절하면 폐기
- 현재 가장 큰 정합성 위험과 사용 빈도를 고려하면 우선 가치가 가장 높음

### 3단계 — DOCX와 일반 형식

- DOCX는 텍스트 미리보기부터 적용
- PDF·이미지·텍스트의 공통 뷰어 추가
- 운영 여건이 확보되면 DOCX·PPTX 렌더링 워커 도입

### 4단계 — 사용자 도구·MCP 확장

- 도구 SDK에 `artifact_draft` 스키마 공개
- 외부 도구 결과 검증·격리 정책 적용
- 미지원 도구 fallback과 호환성 테스트

## 11. MVP 완료 기준

- 사용자가 XLSX의 파일명·시트·열·행·주요 내용을 승인 전에 확인할 수 있음
- 승인 전 초안이 “내 파일”과 검색 결과에 나타나지 않음
- 승인한 내용과 저장된 파일의 해시가 같음
- 거절·중단·만료 시 초안이 정리됨
- 오래된 클라이언트와 미리보기 미지원 도구가 기존 방식으로 계속 동작함
- 미리보기 생성 실패 시 사용자가 원인과 다음 선택지를 알 수 있음
- 접근 권한이 없는 사용자가 미리보기 URL로 초안을 열 수 없음

## 12. 검증 시나리오

1. 5열·20행 XLSX 생성 → 표 미리보기 → 승인 → 동일 파일 다운로드
2. 미리보기 후 초안 변조 → 해시 불일치로 승인 차단
3. 거절 → “내 파일” 미생성 및 임시 객체 삭제
4. 브라우저 종료·세션 만료 → TTL 이후 초안 정리
5. 1,000행 이상 표 → 제한된 행만 미리보기, 전체 행 수는 정확히 표시
6. 수식·외부 링크·매크로 포함 입력 → 실행 없이 안전하게 표시 또는 차단
7. DOCX 변환 실패 → 승인 흐름 전체가 죽지 않고 텍스트/메타데이터 fallback
8. MCP 도구가 임의 URL을 반환 → 직접 iframe 렌더링하지 않고 안전한 fallback

## 13. 팀에서 결정할 항목

| 결정 | 선택지 | 권장 |
|---|---|---|
| 승인 전 파일 생성 | 계획만 표시 / 격리된 임시 초안 생성 | XLSX는 격리 초안 |
| 초안 저장소 | 기존 개인 파일 저장소의 별도 prefix / 별도 저장소 | 별도 prefix + 별도 상태 |
| 초안 TTL | 30분 / 2시간 / 24시간 | 초기 2시간, 운영 지표로 조정 |
| 첫 형식 | XLSX / DOCX / 모두 | XLSX 우선 |
| 미리보기 요약 | 결정론적 메타데이터 / LLM 요약 | 결정론적 방식 |
| 외부 도구 | 처음부터 범용 / 내장 도구 검증 후 확장 | 내장 도구 우선 |
| 승인 후 수정 | 새 초안 생성 / 기존 초안 직접 편집 | 새 초안과 재승인 |

## 14. 최종 권장안

전체 형식용 범용 미리보기를 한 번에 만들기보다, **현재 존재하는 HITL과 파일 카드 사이에 XLSX 임시 초안 단계를 먼저 넣는 것**을 권장합니다.

이 방식은 사용자에게 가장 필요한 “내용을 보고 승인한다”는 가치를 빠르게 검증하면서도, Jira HITL이나 기존 파일 다운로드 계약을 깨지 않습니다. XLSX에서 초안 수명주기·권한·해시·TTL이 검증된 뒤 DOCX·PDF·MCP 도구로 확장해야 운영 위험과 팀 간 충돌을 줄일 수 있습니다.

공통 백엔드 계약과 HITL 흐름을 변경하므로, 구현 전에는 파일 생성 도구 담당자·HITL 담당자·프론트 담당자가 0단계의 세 항목에 합의해야 합니다.

## 15. 팀원에게 전달할 짧은 설명

> 현재는 에이전트가 Excel·Word 파일을 만든 뒤 바로 “내 파일”에 저장하므로, HITL 승인이 있어도 실제 결과물을 보고 판단하기 어렵습니다. 파일을 격리된 임시 초안으로 먼저 만들고 승인 카드에서 미리 본 뒤, 승인 시에만 영구 저장하는 구조를 제안합니다. 기존 Jira 승인 UI와 완료 후 파일 다운로드는 재사용하고, 우선 XLSX부터 검증한 뒤 DOCX·PDF·사용자 도구로 확장하는 것이 가장 안전합니다.

## 16. 2026-08-28 경량 구조형 문서 구현 범위

마감 전 과도한 초안 저장소·렌더링 워커를 만들지 않는다는 결정에 따라, 현재는
`document_create`의 승인 요청 인자 자체를 미리보기와 최종 DOCX가 함께 읽는 중간안까지 구현한다.

- 기존 `title + body` 호출은 그대로 동작한다.
- 새 호출은 `template_id=business_report`, 부서·작성자·작성일·보안 등급 `metadata`, 제목·문단·목록·안내·표·페이지 구분 `blocks`를 선택적으로 사용한다.
- `blocks`는 최대 100개, 문서 안 표는 최대 20열·200행으로 제한하고 서버에서 검증한다.
- 승인 전 카드와 승인 후 대화 기록은 동일한 입력을 렌더링하므로 별도 요약 LLM 호출과 추가 토큰 비용이 없다.
- Excel과 Word 미리보기 모두 카드 우상단의 확대 액션으로 큰 모달에서 다시 볼 수 있다.
- 과거 `body` 기반 기록도 안전한 Markdown 렌더링으로 제목·목록·강조를 유지한다. raw HTML과 비 HTTP(S) 링크, 외부 이미지는 실행·표시하지 않는다.
- 실제 DOCX는 한글·영문 글꼴, 문서명 헤더, 페이지 번호, 메타데이터, 안내 박스와 문서 내부 표를 생성한다.

이번 단계에서 지원하는 것은 **내장 업무보고서 서식과 구조형 내용 스키마**다. 사용자가 올린
DOCX를 그대로 템플릿으로 재사용하는 기능은 placeholder·스타일·표 구조를 분석하고 승인할 별도
계약이 필요하므로 포함하지 않는다. 고정밀 페이지 미리보기 역시 임시 파일·해시·TTL·렌더링
워커가 필요한 장기안으로 유지한다.
