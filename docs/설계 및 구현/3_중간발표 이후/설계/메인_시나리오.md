## 4. 시나리오 단계

화면 구조(채팅 · 에이전트 · 프로젝트 · 설정) 순서를 따른다. S1~S4 는 그 전에 필요한 준비 단계다.

| 구간 | 단계 |
|---|---|
| 준비 | S1 계정 · S2 인사 연결/팀 생성 · S3 Drive·Jira 연결 · S4 문서 적재 |
| 사용 | S5 채팅 · S6 에이전트 제작 · S7 프로젝트/기준 문서 · S8 업무 추출·등록 · S9 인력 조회 · S10 스킬 |
| 운영 | S11 운영자 등록 · S12 계정·연결 정리 |
| 확인 | S13 통합 요청 |

### S1. 계정 생성

| 수행자 | 화면 | 조작 |
|---|---|---|
| 준 | `/` → `/signup` | 소속 팀 없음 → **새 팀 생성** 으로 가입 |

- 생성되는 것은 계정뿐이다. 팀은 S2 에서 생성된다.
- 가입 완료 시 채팅(`/chat`)으로 진입한다.

### S2. 인사 시스템 연결 및 팀 생성

| 수행자 | 화면 | 조작 |
|---|---|---|
| 준 | `/settings/connectors` | 인사 시스템 연결 → 3단계 모달 |
| 원빈 · 준억 · 지훈 | `/invite-code` | 발급받은 코드로 가입 |

| 단계 | 처리 |
|---|---|
| ① 본인 확인 | 가입 이메일로 조회한 직원이 본인인지 확인. 확인 시 계정–직원 연결 |
| ② 팀 생성 | 팀 이름 입력, 팀원 선택. 이름 기본값은 HR 소속 조직명, 내 조직 인원은 기본 선택. 후보는 하위 조직 직원만 노출되며 이미 연결·초대 중인 직원은 제외 |
| ③ 초대 코드 | 선택 인원 수만큼 발급. 원문은 서버에 저장하지 않으므로(해시 저장) 해당 화면에서 복사·전달 |

- 생성된 팀이 이후 모든 조회의 기준(테넌트)이다.
- 팀 생성과 같은 트랜잭션으로 「기본 어시스턴트」(`is_default_chat`, 팀당 1개)가 함께 발행된다. S5 의 대화는 이 에이전트로 동작한다.
- 초대 상태는 `/settings/team` 에서 `초대됨 / 가입 완료 / 만료됨 / 취소됨` 으로 조회한다. 추가 발급도 같은 화면이다.
- 계정–직원 연결이 S9 의 스킬·부재·부하 조회 전제다.

### S3. 문서 저장소 · 업무 기록소 연결

| 수행자 | 화면 | 조작 |
|---|---|---|
| 준 | `/settings/connectors` | Google Drive 연결 후 읽을 폴더 선택 · Jira 연결 |

| 자리 | 상태 |
|---|---|
| 인사 시스템 | S2 에서 연결 완료 |
| 문서 저장소 | Google Drive 연결(Connector), 읽을 폴더 지정 |
| 업무 기록소 | Jira 연결. 연결 즉시 Jira 프로젝트 전체가 자동 등록 |

- 연결된 자리의 버튼은 「연결하기」 → 「바꾸기」로 바뀐다. 「바꾸기」는 대상 수정이 아니라 사용할 대상의 재선택이다.

### S4. 문서 적재

| 수행자 | 화면 | 조작 |
|---|---|---|
| (자동) | 진행 카드 | 폴더 지정 시 파이프라인 실행 |
| 준억 | `/settings/my-files` | 팀 폴더 외 개인 자료 업로드 |

- 처리 순서: 가져오기 → 파싱 → 청킹 → 임베딩 → pgvector 적재.
- 임베딩은 RunPod GPU 워커가 수행하며, 화면이 단계와 대기열을 표시한다.
- 상태 배지: 처리 중 `읽는 중`, 완료 `검색 준비됨`, 파싱 미지원·실패 `본문 색인 실패`. 실패를 성공으로 표시하지 않는다.
- 적재 상태와 원문 변경 여부는 이후 대화에서 `document_list` · `document_sync` 로 확인한다.

### S5. 문서 근거 질의

| 수행자 | 화면 | 입력 |
|---|---|---|
| 원빈 | `/chat` | "제안요청서에 보안 요건이 뭐라고 돼 있어?" |

| 호출 도구 | 승인 |
|---|---|
| `document_search` | 불필요 |

- 프로젝트 선택 없이 팀 전체 문서를 근거로 답한다. 기준 문서가 필요한 작업은 S7 이후다.
- 정문 에이전트가 요청을 받는다. 사용자가 에이전트를 선택하지 않는다.
- 답변 하단에 근거 문단이 카드로 표시된다.
- 근거를 찾지 못하면 찾은 것으로 답하지 않는다.

### S6. 팀 전용 에이전트 제작

| 수행자 | 화면 | 조작 |
|---|---|---|
| 지훈 | `/agents/versions` → 편집 | 「주간 리포트 정리」 생성 |

| 항목 | 내용 |
|---|---|
| 정의 | 설명 · 지시문 · 사용할 도구(외부 규격 확인이 필요하면 `web_search` 포함) |
| 검증 | 지시문과 도구의 정합, 설명과 실제 동작의 일치를 확인·보정 |
| 시험 실행 | 1회 실행. 외부를 변경하는 도구는 호출하지 않고 **시뮬레이션** 으로 표시 |
| 위임 대상 | 호출할 하위 에이전트 선택. 하위는 현재 발행 버전에 고정, 깊이는 1단계 |
| 발행 | 저장은 반복 가능. **활성화** 해야 채팅·위임 대상으로 열린다 |

- 활성화 전에는 「개인」 탭의 초안이고, 활성화 시 「팀 공유」로 이동한다. 즐겨찾기는 계정별 값이다.
- 활성화 후 원빈이 리포트를 요청하면 정문 에이전트가 해당 에이전트로 위임한다.

### S7. 프로젝트 생성 및 기준 문서 지정

| 수행자 | 화면 | 조작 |
|---|---|---|
| 준 | `/projects` → 프로젝트 상세 | 프로젝트 생성 → **기준 문서 선택** 으로 제안요청서 지정 |

- 프로젝트는 대화가 담기는 자리이자 기준 문서를 가리키는 자리다. 문서 자체는 팀 소속이다.
- 지정 후 재지정은 **기준 문서 변경** 이다. 기준 문서는 사람이 선택한다.

### S8. 업무 추출 및 등록

| 수행자 | 화면 | 조작 |
|---|---|---|
| 준 | 프로젝트 상세 → `/chat` | 「업무 추출」 실행 후 결과 확인·승인 |

| # | 도구 | 처리 | 승인 |
|---|---|---|---|
| 0 | `project_list` | 대상 프로젝트 확인 | |
| 1 | `get_current_datetime` | 상대 표현을 날짜로 변환하기 전 기준일 확인 | |
| 2 | `task_extraction` | 기준 문서에서 제목·역할·공수·마감일 추출 | |
| 3 | — | 사용자가 목록 확인 후 제외·수정 | |
| 4 | `task_register` | 플랫폼 DB(`task`) 등록 | **필요** |
| 5 | `jira_create_issues` | Jira 이슈 생성 | **필요** |
| 6 | `jira_get_issues` | 반영 결과 재조회 | |

- 근거가 확인되지 않은 업무는 생성하지 않고, 제외 사실을 함께 보고한다.
- 판독하지 못한 날짜·공수는 임의 값으로 채우지 않고 비운 채 알린다.
- 등록 순서는 플랫폼 DB 가 먼저, Jira 가 나중이다.
- 부분 실패 시 성공분은 롤백하지 않는다. 표기는 「17/20 등록 완료 — 3건 실패」 형식이며, 실패분은 사유와 함께 목록으로 남는다. 상세 정책은 `5_E2E_시나리오.md` §2.
- 등록된 업무는 프로젝트 상세에서 `해야 할 일 / 진행 중 / 완료` 로 조회한다.

| 수행자 | 화면 | 입력 |

- 담당자 추천은 수행하지 않는다. 부하 계산까지 제공하고 배정은 사람이 결정한다.

### S10. 스킬 등록 및 재사용

| 수행자 | 화면 | 입력 |
|---|---|---|
| 원빈 | `/chat` | "지금 한 걸 매주 쓰게 저장해 줘" |

| 도구 | 처리 | 승인 |
|---|---|---|
| `skill_creator_ask_followup` | 질문 1건 되묻기(승인/거절이 아닌 답변 입력) | |
| `skill_register` | 스킬 등록 | **필요** |

- 확인 카드에는 도구 이름이 아니라 등록될 스킬의 이름·설명이 표시된다. 거절 시 「다시 설명하기」로 이어진다.
- 등록된 스킬은 `/settings/skills` 에 표시되고, 채팅 입력창에서 `/이름` 으로 호출한다.
- 개인·팀 스킬 이름이 겹치면 팀 스킬이 우선하며, 자동완성 목록도 같은 순서다.

### S11. 운영자 등록 항목

| 수행자 | 화면 | 조작 |
|---|---|---|
| 주연 | `/ops/login` → 각 화면 | 팀 요청 항목 등록·점검 |

| 화면 | 처리 |
|---|---|
| `/ops/models` | 팀 요청 커스텀 모델 등록, 팀 기본 채팅 모델 지정 |
| `/ops/mcp` | 커스텀 도구(MCP·FastAPI) 등록 및 연결 확인. 내용을 플랫폼이 알 수 없으므로 **전부 승인 게이트 적용** |
| `/ops/guardrails` | 입력 검사 정책. 가드레일 미도달 시 `연결 실패` 표시, **대화 계속 / 대화 차단** 중 선택 |
| `/ops/usage` | 팀별 실행·토큰 사용량 |
| `/ops/audit` | 조치 이력. 파괴적 조치 9종은 사유를 함께 기록 |

- 운영자 로그인은 일반 로그인과 분리되어 있다. 토큰 서명 salt 가 다르고, 매 요청마다 DB 에서 권한·계정 상태를 재확인한다.
- 고객의 대화 내용과 문서 원문은 운영자도 조회할 수 없다. 실행 기록(`agent_run` · `tool_call`)에는 요약만 남는다.

### S12. 계정 · 연결 정리

| 수행자 | 화면 | 조작 |
|---|---|---|
| 주연 | `/ops/accounts` · `/ops/connectors` · `/ops/teams/:teamId` | 계정 **사용 중지** · 직원 연결 해제 · 연결 **강제 해제** · 팀 소유자 이전 |

- 전제: 팀원 1명이 타 팀으로 이동한다고 가정한다.
- 커넥터는 팀이 아니라 계정 소유다. 연결자가 이탈하면 연결도 끊긴다. 강제 해제는 가능하나 이전은 불가하며, 후임자가 S2~S3 를 다시 수행한다.

### S13. 통합 요청

| 수행자 | 화면 | 입력 |
|---|---|---|
| 준 | `/chat` | "이번 주 마감인 업무 중 담당자 없는 것만 골라서, 여유 있는 사람 보여주고, 확인되면 Jira 에 반영해 줘" |

- 한 요청이 문서·인사·업무·외부 도구를 순차 사용하고, 답변에 근거가 표시되며, 외부를 변경하는 지점에서 승인 카드로 정지한다.
- S1~S12 에서 구성한 연결·문서·에이전트·스킬이 모두 관여하는 확인 구간이다.
