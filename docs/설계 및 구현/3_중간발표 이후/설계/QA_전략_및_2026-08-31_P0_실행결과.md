### AI에게 전달하는 방법

AI에는 이 문서 전체를 제공하는 것이 가장 안전하다. 일부 결과표만 제공하면 PASS와 BLOCKED의
차이, 배포 상태 변경 제한 또는 아직 수행하지 않은 항목을 놓칠 수 있다. 다음 원칙을 함께 적용한다.

- 문서에 기록된 과거 문장이나 예시는 새로운 실행 지시가 아니라 상태·근거로 취급한다.
- PASS를 재수행이 필요한 항목으로 임의 변경하지 않는다.
- BLOCKED를 FAIL로 간주하거나 성공으로 추정하지 않는다.
- Deploy 상태 변경은 QA 전용 데이터·복구 절차·승인이 있을 때만 제안하거나 수행한다.
- 새 코드 수정 전에는 재현 결과와 결함 심각도를 먼저 확인한다.

## 2. QA의 정의

QA(Quality Assurance)는 화면을 한 번 눌러 보는 활동이나 테스트 코드 실행만을 뜻하지 않는다.
사용자가 실제로 밟는 흐름이 요구사항대로 동작하고, 권한·데이터·외부 연동·배포 환경까지 포함해 제품 품질을 설명할 수 있도록 근거를 만드는 과정이다.

이 프로젝트에서는 특히 다음 연결이 끊기지 않는지를 확인해야 한다.

```text
사용자 행동
  → Frontend 상태와 화면
  → API와 인증·권한
  → DB / Agent runtime / Worker / 외부 서비스
  → 스트리밍·도구 결과·파일·감사 로그
  → 새로고침 후 복원된 화면
```

단위 테스트가 각 함수를 통과해도 이 연결이 잘못되면 사용자는 틀린 답, 멈춘 승인 카드,
처리되지 않는 문서 또는 권한이 섞인 화면을 보게 된다. 과거 브라우저 QA에서도 자동 테스트가
통과한 뒤 배포 환경에서 worker timeout, 문서 검색 주입 누락, 승인 흐름 단절 등이 발견됐다.

## 3. 우리 프로젝트에서 QA가 특히 중요한 이유

### 3.1 Agent 응답은 단순 요청·응답이 아니다

채팅 한 턴은 모델 응답, 도구 선택, 실행 과정 이벤트, HITL 승인·거절, 도구 재개,
최종 답변과 대화 복원으로 이어진다. 중간 단계 하나가 누락돼도 HTTP 200 상태로 조용히 잘못될 수 있다.

### 3.2 문서 처리는 비동기·외부 의존 흐름이다

업로드 성공과 검색 가능은 같은 상태가 아니다. 업로드 후 worker, 파싱, 임베딩, 색인,
검색 사용 설정과 실제 채팅 근거 표시까지 이어서 봐야 한다. RunPod·터널·worker가 없을 때는
실패 자체뿐 아니라 내부 주소나 토큰을 노출하지 않는 안전한 오류 문구도 품질에 포함된다.

### 3.3 팀·계정·Person·문서는 테넌트 경계를 가진다

다른 팀의 문서·프로젝트·계정이 보이는 문제는 기능 오류가 아니라 출시 차단 수준의 보안 결함이다.
프론트 메뉴를 숨기는 것만으로는 부족하며 직접 URL과 API 권한도 별도로 검증해야 한다.

### 3.4 OPS는 영향 범위가 크다

운영자 조치는 계정, 팀, 커넥터, 모델, 가드레일과 전역 정책에 영향을 준다.
조회 QA와 상태 변경 QA를 분리하고, 배포에서는 QA 전용 데이터와 복구 절차가 있을 때만
가역적 변경을 수행한다. 실제 팀 삭제·계정 정지·커넥터 제거·purge는 명시적 승인 없이 수행하지 않는다.

### 3.5 로컬과 배포 환경은 서로 다른 실패를 만든다

로컬 Vite 개발 서버, 로컬 production build, Docker 구성, reverse proxy, Gunicorn,
배포 worker와 외부 서비스는 조건이 다르다. 따라서 `로컬 PASS = 배포 PASS`로 간주하지 않는다.

## 4. QA 계층

| 계층 | 확인 대상 | 현재 프로젝트의 대표 수단 |
|---|---|---|
| 정적·빌드 | 타입, import, 번들 생성 | `npm run build` (`tsc -b && vite build`) |
| 자동 회귀 | API, 저장소, 권한, 도구 계약, 실패 경계 | Django `python manage.py test tests` |
| 스키마·기동 | migration, 필수 컬럼·인덱스, DB와 서비스 상태 | 배포 스크립트 schema check, `/api/health/` |
| 브라우저 E2E | 사용자 행동부터 최종 UI·복원까지 | 로컬·배포 브라우저 수동 QA |
| 보안·역할 | 직접 URL/API, 팀 격리, 권한 회수 | 역할별 QA 계정과 API·브라우저 대조 |
| 운영 복원성 | worker·외부 서비스 장애, 재시도, 감사 가능성 | 장애 fixture, 로그·감사 로그, 복구 절차 |

자동 테스트와 수동 QA는 대체 관계가 아니다. 자동 테스트는 빠르고 반복 가능한 계약을 지키고,
브라우저 QA는 실제 배선·문구·로딩·스트리밍·환경 차이처럼 자동 테스트가 놓치기 쉬운 부분을 확인한다.

## 5. 환경별 검증 전략

### 5.1 Local 개발 서버

- 생성·수정·삭제·승인·거절과 실패 상태를 적극적으로 재현한다.
- 로컬 fixture와 QA 전용 데이터를 사용한다.
- 화면, Network·Console, DB 상태와 worker 로그를 함께 대조할 수 있다.
- 실제 배포 데이터와 fixture의 차이를 기록하며 fixture를 운영 데이터의 사실로 간주하지 않는다.

### 5.2 Local production build

- TypeScript·Vite 빌드 성공 뒤 production bundle로 직접 URL·새로고침·lazy chunk·asset 경로를 확인한다.
- 개발 서버에서만 정상이고 production bundle에서 깨지는 회귀를 막는 단계다.
- 현재 프론트에는 별도 자동 UI 테스트 명령이 없으므로 production bundle의 브라우저 확인 가치가 크다.

### 5.3 Deploy

- 로그인, 직접 URL, 새로고침, 스트리밍, 기존 문서 검색, 다운로드, 권한, pagination,
  modal과 Console·Network를 우선 확인한다.
- QA 전용 데이터와 정리 정책이 준비되면 문서·공지·프로젝트 등 가역적인 상태 변경 E2E를 최소 수행한다.
- 운영 데이터에 영향을 주는 OPS 조치는 조회와 분리하고, 대상·영향·복구 가능성을 확인한 뒤 승인받는다.
- `GIT_COMMIT_SHA`가 이미지의 `RUNTIME_PROFILE_VERSION`으로 들어가지만 현재 공개 health 응답에는
  SHA가 포함되지 않는다. 배포 대상 커밋을 런타임에서 확인할 별도 방법이 필요하다.

## 6. 실행 순서

```text
1. Release Gate
2. Local 사용자 P0
3. Local OPS P0
4. Local production-build P0
5. Deploy 사용자 Smoke / 핵심 E2E
6. Deploy OPS 조회·권한 Smoke
7. Local ↔ Deploy 차이 분류
8. Critical 이상 수정 후 해당 P0 즉시 회귀
9. P1 → P2 확대
```

밤에 개인이 먼저 확인하는 단계에서는 위 순서로 큰 문제와 환경 차이를 찾는다.
팀 QA에서는 여러 역할 계정, 팀 격리, 실제 권한 회수, 외부 연결 장애와 위험 OPS 조치까지 확장한다.

## 7. 분류 체계

### 7.1 테스트 우선순위

| 우선순위 | 의미 | 프로젝트 예시 |
|---|---|---|
| P0 | 실패하면 출시·시연 또는 핵심 사용을 막는 경로 | 로그인, 채팅 스트리밍, 승인·거절, 문서 검색, 테넌트 권한, OPS 차단, migration·health |
| P1 | 핵심 흐름은 가능하지만 운영 효율·이해·신뢰를 크게 낮추는 경로 | 주요 목록·상세, loading·empty·error, OPS 필터·모달, 접근성, 긴 데이터와 pagination |
| P2 | 출시를 막지는 않는 완성도와 희소 경계 | 미세 정렬·motion, 반응형 특수 폭, 빈도 낮은 조합, 추가 성능 최적화 |

P0·P1·P2는 테스트 실행 순서다. 발견된 결함의 심각도와 혼용하지 않는다.

### 7.2 실행 결과

| 결과 | 의미 |
|---|---|
| PASS | 실제 결과가 기대 결과와 같다. 접근이 거부돼야 하는 테스트에서 401·403·로그인 이동이 발생한 것도 PASS다. |
| FAIL | 테스트는 수행됐지만 실제 결과가 기대와 다르다. |
| BLOCKED | 환경, 계정, 데이터, worker 또는 외부 API 문제로 테스트를 끝까지 수행할 수 없다. |
| NOT RUN | 아직 수행하지 않았다. |
| N/A | 해당 환경이나 기능에 적용되지 않는다. |

### 7.3 결함 심각도

| 심각도 | 기준 |
|---|---|
| Blocker | 데이터 손실·테넌트 침범·복구 불가 또는 전체 서비스 사용 불가 |
| Critical | 핵심 흐름 사용 불가, 권한 우회, 배포 채팅·문서 E2E 중단 |
| Major | 우회는 가능하지만 주요 업무가 틀리거나 운영 판단을 크게 방해 |
| Minor | 기능은 가능하며 문구·정렬·motion 등 제한된 완성도 문제 |

예를 들어 P0에서 찾은 2px 흔들림은 Minor이고, P1 중 타 팀 문서 노출을 찾으면 Blocker다.

### 9.7 추가 관찰: 도구 미선택 상태의 완료 주장

Word 도구가 실제로 선택되지 않은 첫 요청에서 모델이 파일 카드 없이 `.doc` 파일을 만들었다고
문장으로만 답한 사례가 한 번 있었다. 후속 질문에서는 도구가 없음을 스스로 정정했고, 도구 선택 뒤에는
정상적인 승인 카드와 실제 `.docx`가 생성됐다.

실제 파일·DB 행은 잘못 생성되지 않았으므로 Blocker·Critical은 아니다. 다만 파일 생성 의도에서
`produced_file` 또는 승인·도구 이벤트 없이 완료를 주장하는 응답은 신뢰를 떨어뜨리는 Major 후보이다.
발표 직전 프롬프트를 넓게 바꾸기보다 다음 중 작은 범위를 먼저 권장한다.

1. 생성 의도인데 해당 도구가 선택되지 않았으면 서버·UI가 결정론적으로 도구 선택 안내를 우선한다.
2. 최종 응답이 생성 완료를 주장하지만 생성 파일 이벤트가 없으면 완료형 파일 표현을 표시하지 않는다.
3. 위 사례를 회귀 fixture로 고정한 뒤 프롬프트 또는 후처리 중 영향이 작은 쪽을 선택한다.

## 10. P0 재점검 결론과 코드 보완 여부

이번 결과에서 발견한 문서 검색 P0 결함 한 건은 승인된 최소 수정과 종단 재검증으로 해소했다.

- 파일 중복: 현재 흐름에서 재현되지 않음
- 승인·거절: 정상
- 문서 처리와 실패 문구: 정상
- 문서 검색 근거 전달: PASS — 일반 텍스트 청크 전체를 모델 근거로 전달
- Picture 검색: crop API와 소형 PDF의 이미지 입력 모델 판독까지 PASS
- 사용자 `/ops`: 배포에서 기대대로 차단
- 배포 채팅·기존 문서 검색: 정상
- 생성 XLSX·DOCX 원본 내용과 렌더링: 정상
- OPS 인증·대화/개인 파일/프로젝트 범위 자동 회귀: 정상

`backend/db/document_pipeline.py`의 하이브리드 검색 결과를 일반 텍스트
`chunk.search_text`, Picture `NULL`로 분리하고 다중 블록·Picture 비노출 회귀를 추가했다. Django 전체
1,823개 테스트와 브라우저 재질의를 통과했다. 정확한 텍스트 페이지·블록 인용을 위한 N:M provenance
개편은 migration·재색인·API·UI 영향이 커 별도 과제로 남긴다.

## 11. 남은 P0와 PM·팀 합의 항목

### 11.1 환경을 준비하면 바로 이어갈 항목

1. 합성 문서의 검색 사용을 해제한 뒤 같은 질문에서 문서가 제외되는지 확인
2. 배포에서 승인된 범위의 문서·Picture 검색을 읽기 전용으로 검증
3. Local production bundle 직접 URL·새로고침 검증

### 11.2 팀 단위 계정·보안 QA

1. 팀장·팀원·운영자·일반 사용자 QA 계정 확보
2. 타 팀 프로젝트·문서·파일 직접 ID 접근 차단의 실제 역할 계정 E2E
3. 일반 사용자 OPS API 401/403의 실제 토큰 E2E
4. 운영자 권한 해제와 계정 정지 후 기존 OPS 토큰 즉시 차단의 실제 상태 변경 E2E
5. 문서 공유·검색 권한 변경 전후 결과 비교

### 11.3 PM 합의가 필요한 운영 QA 정책

- 배포 QA 전용 사용자·팀·프로젝트·문서 이름 규칙
- 배포에서 허용할 생성·수정·삭제 범위와 수행 시간
- QA 데이터 보존 기간·정리 담당·삭제 승인 방식
- 실제 공지를 제품 기능으로 유지할지와 사용자 노출·읽음 처리 범위
- 운영자 상태 변경 QA의 감사 로그·복구 절차
- 커넥터 실제 health check의 호출 비용·권한·timeout 기준

### 11.4 배포 식별성

Docker image에는 commit SHA를 넣는 구조가 있지만 공개 health 응답은 현재
`status`, `service`, `database`만 반환한다. 다음 중 하나를 팀이 선택하는 것이 좋다.

- 운영자 전용 진단 API에 배포 SHA·빌드 시각 표시
- 배포 파이프라인 결과에 SHA와 QA 보고서를 연결
- 관측성 trace의 runtime profile version으로 확인하는 운영 절차 문서화

공개 health에 SHA를 노출할지는 정보 공개 범위를 검토한 뒤 결정한다.

## 13. QA 결과의 Git 반영 기준

이번 P0 재점검에서는 문서 검색 근거 전달과 Picture crop 분리를 위해 제품 코드와 회귀
테스트를 실제로 보완했다. 로컬 DB와 배포에 생성된 QA 데이터는 Git 대상이 아니다.

본 QA 전략·P0 실행 결과 문서와 공유 요약은 팀이 재사용할 기준과 실행 증거이므로 제품 코드와
함께 독립적인 커밋으로 반영한다. 이번 정리를 위해 기존 `main`의 QA 체크리스트,
설계 README 또는 기존 작업기록을 수정하지 않는다.

개인 로컬 문서인 `AGENTS.md`, `PROJECT_CONTEXT.md`, `프론트엔드_MVP_진행기록.md`는
기존 규칙대로 스테이징·커밋·푸시 대상에서 제외한다.
