# 평가 설계 v1 — 개발 전에 정의한다

> 2026-08-10 작성. 08/12 온라인 멘토링 리뷰 대상.
> 중간발표 최대 약점 = 평가 근거 부재. 최종발표에서 "잘 동작했습니다"로 끝내지
> 않기 위해, **무엇을·어떻게·무슨 데이터로** 측정할지 개발 전에 정한다.
> 지표값이 아니라 측정 체계를 확정하는 문서다.

## 0. 원칙

1. **측정은 자동이 기본, 수작업은 정답셋 구축에만 쓴다.** 실행 로그
   (`agent_run`·`tool_call`, 아키텍처 초안 §3)와 DB에서 뽑을 수 있는 지표를
   우선한다. 사람이 매번 세는 지표는 발표 전 1회성으로 끝나고 재현이 안 된다.
2. **정답셋(골든셋)은 작게, 대신 근거 있게.** 3주 일정에서 대규모 라벨링은
   불가능하다. 데모 문서 기준 소규모 골든셋을 팀 합의로 만들고, 규모의 한계는
   발표에서 숨기지 않고 명시한다.
3. **콜드/웜을 구분해서 잰다.** RunPod 콜드 스타트(수 분)가 섞이면 처리 시간
   지표가 왜곡된다. 모든 시간 지표는 웜 기준으로 재고 콜드는 별도 1회 기록.
4. **인과 단정 금지, 팀 규모 환산 금지** ([[problem-evidence]]의 How to apply와
   동일 원칙을 우리 지표에도 적용).

## 1. Document Processing — 담당: 원빈

정답셋: **골든 문서셋 G-DOC** — 데모에 쓸 PDF·DOCX **10건**(8/11 확정. 원안 5~8에서 상향 — §8-1) (표 포함 2건 이상,
스캔본 1건 이상 포함). 각 문서에 대해 "있어야 하는 것"(섹션 수, 표 수, 표의
행·열, Heading 목록)을 수작업으로 1회 기록.

| 지표 | 정의 | 측정 방법 |
|---|---|---|
| 파싱 성공률 | 등록 시도 문서 중 `doc_block` 생성까지 완료된 비율 | 파이프라인 로그·DB 카운트 (자동) |
| 정보 누락률 | G-DOC의 "있어야 하는 것" 대비 산출물에 없는 항목 비율 | G-DOC 대조 (수작업 1회 + 스크립트 보조) |
| 표 구조 보존율 | G-DOC 표 중 행·열 구조가 보존된 비율 | 표 청크 검사 — 기존 표 구조 보존 청킹 작업 기록 활용 |
| Heading 구조 보존율 | G-DOC Heading 중 블록 구조에 남은 비율 | `doc_block` 검사 |
| 처리 시간 | 문서 1건 등록→검색 가능까지 (웜 기준) | RunPod job 시간 + 적재 시간 로그 |

기존 실측 재료: `doc_block` 935 · `chunk` 456 · `vec_idx` 456,
`ml/task_classifier`의 라벨링 데이터(chunks_labeled.csv), 청킹 한도 초과 시
표만 제외하는 규칙(AS-IS §4)의 발생 빈도도 로그로 집계.

## 2. Retrieval

정답셋: **골든 질의셋 G-QUERY** — G-DOC에 대한 질의 **12~15개**(8/11 확정. 원안 20~30에서 하향 — §8-1). 각 질의에 "이
청크/문서가 나와야 한다"를 팀원 2인 합의로 라벨 (1인 라벨의 주관 편향 방지).

| 지표 | 정의 | 측정 방법 |
|---|---|---|
| **문서 단위 Recall (coarse)** | 정답 문서가 요약 임베딩 후보 상위 k에 든 비율 — 8/11 전환된 2단계 검색(아키 §5)의 누락 리스크 검증용 | 스크립트 자동 (메타 임베딩 질의) |
| Recall@k (fine) | 정답 청크가 상위 k(5·10)에 든 비율 | 스크립트 자동 (pgvector 질의 반복) |
| Top-k Accuracy | 상위 1건이 정답 문서에 속한 비율 | 〃 |
| 근거 적합성 | 추출 결과의 근거(E1~E20)가 실제로 해당 업무를 뒷받침하는지 | 샘플 업무 20건 × 근거를 2인이 O/△/X 평정 |

주의: 질의는 실제 사용 상황을 흉내 낸다 — 추출 파이프라인이 만드는 질의
스타일(문서 어휘 기반, AS-IS §6)과 사용자가 Chat에 칠 자연어 질문 두 계열을
섞는다.

## 3. Task Extraction

정답셋: **골든 업무 목록 G-TASK** — 데모 기준 문서 1~2건에 대해 "사람이 뽑으면
이 업무들이 나온다"를 팀 전원 합의로 확정 (제안요청서 기준 업무 15~25건 예상).
합의 과정 자체를 기록해 두면 발표 Q&A 근거가 된다.

| 지표 | 정의 | 측정 방법 |
|---|---|---|
| Precision | 추출 업무 중 G-TASK에 대응하는 비율 | 추출 결과 ↔ G-TASK 매칭 (수작업 매칭, 3회 반복 실행 평균) |
| Recall | G-TASK 중 추출된 비율 | 〃 |
| 오추출 수 / 누락 수 | 절대 수치 (발표에서 %보다 직관적) | 〃 |
| 근거 유효율 | 업무별 근거 인용이 유효한 비율 | §2의 근거 적합성과 공유 |
| 재현 안정성 | 같은 문서 3회 실행 시 업무 목록의 일치도 | 자동 (업무 제목 매칭) |
| missing_fields 정직성 | 문서에 없는 공수·담당·일정을 지어내지 않았는지 | G-TASK에 "문서에 없음" 항목을 미리 표기하고 대조 |

## 4. Tool Selection — 신규 (Harness 완성 후)

정답셋: **시나리오 프롬프트셋 G-PROMPT** — 15~20개 프롬프트에 기대 Tool을 라벨.
Tool이 필요 없는 프롬프트(그냥 질문)를 1/3 섞는다 — 불필요 호출률을 재려면
"호출하면 안 되는 상황"이 셋에 있어야 한다.

| 지표 | 정의 | 측정 방법 |
|---|---|---|
| 올바른 Tool 선택률 | 기대 Tool과 실제 첫 호출 Tool 일치 비율 | `tool_call` 로그 자동 집계 |
| 불필요 호출률 | Tool 불필요 프롬프트에서 호출이 발생한 비율 | 〃 |
| Tool 실행 성공률 | 호출된 Tool이 에러 없이 결과를 반환한 비율 | 〃 (MCP 오류 포함) |

## 5. E2E — 대표 시나리오 (`5_E2E_시나리오.md`)

측정 단위: 시나리오 전체 1회 실행 ("문서 참고해 업무 정리하고 Jira 등록"까지).

| 지표 | 정의 | 측정 방법 |
|---|---|---|
| E2E 성공률 | N회(≥10, 웜 기준) 중 STEP 9까지 완주한 비율 | `agent_run` 상태 자동 집계 |
| 평균 처리 시간 | 요청→완료 (사용자 확인 대기 시간 제외) | run 로그의 단계별 타임스탬프 |
| 실패 단계 분포 | 실패가 어느 STEP에서 났는지 | `tool_call`·run 로그 |
| 재시도 성공률 | 실패 후 1회 재시도로 복구된 비율 | 〃 |
| PARTIAL_RESULT 처리 | 부분 실패 시 사용자에게 부분 결과+사유가 전달되는지 | 시나리오 테스트 (표 제외 규칙과 동일 철학) |

**현업 효과 (발표 마지막 카드):** 같은 기준 문서로 "수작업으로 업무 목록을
만들고 Jira에 등록"하는 시간을 팀원 1인이 1회 실측 → Agent 소요 시간과 나란히
제시. "N배 빠르다"가 아니라 "이 문서 기준 X분 → Y분" 형태로, 표본 1건임을
명시한다.

## 6. 측정 인프라

- 자동 집계의 원천은 `agent_run`·`tool_call` 테이블 (아키텍처 초안 §3 스키마) —
  **Harness 개발 첫 주에 로그 적재부터 넣는다.** 나중에 붙이면 발표 전 측정이
  불가능하다.
- 평가 스크립트는 `tests/eval/` 아래에 둔다 (기존 `def test_` 289개와 분리 —
  평가는 통과/실패가 아니라 수치 산출). **아직 없다. 원빈이 만든다.**
- 골든셋 파일은 `docs/설계 및 구현/3_중간발표 이후/설계/eval/` 아래 버전 관리 (G-DOC 목록, G-QUERY,
  G-TASK, G-PROMPT).

### 8-0. 예외 — `coarse_recall` 은 평가가 아니라 설계 검증이다

> ⚠ **이 절은 폐기됐다 (2026-08-24).** `coarse_recall` 은 A(요약 임베딩)와
> A′(tsvector 하이브리드) 중 고르기 위한 지표였는데, 8/24 멘토링에서 **둘 다
> 탈락하고 전량 색인으로 갔다**(`12_문서처리_방식_비교.md` §6). 요약 단계
> 자체가 없어져 잴 대상이 사라졌다.
>
> 아래 판단의 전제(「요약이 부족하면 A′ 로 확장」)는 실측으로 확인됐다 —
> 한국어 RFP 는 **본문의 13~16% 만** 요약에 들어갔다. 다만 해법이 A′ 가
> 아니었을 뿐이다.
>
> **대신 재야 할 것은 `Recall@k`(fine · 청크 검색)다.** §2 에 이미 정의돼
> 있고, 골든셋이 필요한 것도 그대로다(§8-1' 의 규모 조정 참고). 멘토링 Q7 의
> RAGAS `context_recall`·`context_precision` 이 같은 것을 묻는다.

A안(요약 임베딩으로 문서 좁히기)은 팀 반론("긴 문서는 요약으로 못 찾는다")을
받아 **"Recall 로 실측하고 미달이면 tsvector 하이브리드(A′)로 확장"** 이라는
**조건부 확정**이었다(`12_문서처리_방식_비교.md` §5). **A′ 로 가야 한다는 걸
3주차 말에 알면 코드를 고칠 시간이 없다.** `doc_meta.extracted_text` 에 원문을
버리지 않고 보관한 이유가 이것이다. → **3주차 초반까지 반나절 확보.**

### 8-1'. 규모 재조정 (실물 확인 후)

아래 8-1 의 「문서 10 · 질의 12~15」는 **실물을 보지 않고 정한 숫자였다.**
`~~docs/참고자료/개발_기획서_샘플/~~(2026-08-25 삭제 · git 이력에 있다) ` 실측 11건 중 hwp 1건은 Docling 미지원이고,
나머지도 **주제가 전부 달라 서로 헷갈리지 않는다**(RFP · 체중기록 PRD ·
나이인증 스펙 …). 그러면 Recall 이 1.0 으로 나와도 아무것도 증명하지 못한다 —
문서가 3건일 때와 같은 문제가 형태만 바꿔 남는다.

→ **정보시스템 구축 계열 4~5건 · 질의 6~8개**로 좁힌다. 서로 헷갈리는 세트라야
숫자에 의미가 생긴다. 규모의 한계는 발표에서 숨기지 않고 명시한다(§0-2 원칙).

→ **G-TASK · G-PROMPT 는 설계만 남기고 측정은 Future Work.**


**출발점 실측**: 골든셋은 **0건**이고, 측정 코드도 **없다** — 준이 8/11 에 올려
뒀던 `tests/eval/`(README + `coarse_recall.py`)은 **2026-08-14 에 지웠다.**
멘토링 결과로 베이스 코드를 짜다 들어간 자리표시였고, 이 영역은 원빈에게 일임했다.
**구현 방식은 맡은 사람이 정한다.** 옛 뼈대가 필요하면 git 이력에 있다.
지금까지 근거로 인용해 온
**0.291 > 0.150 > 0.108 은 Recall 이 아니다** — 「이 사업의 사업 기간」 **질의 1건**을
팀 문서 **3건**에 던졌을 때의 유사도 서열이다(감리용역 0.291 > IR사업 0.150 >
회사소개 0.108 — 8/11 실연동 확인 기록).
문서 단위 Recall 은 아직 한 번도 재지 않았다.

1. **골든셋 규모 — 문서 우선. G-DOC 10건 · G-QUERY 12~15건.**
   원안(문서 5~8 · 질의 20~30)에서 **문서를 늘리고 질의를 줄였다.** 이유:
   coarse 는 후보를 **거르는** 단계라 문서가 3건이면 Recall@3 이 거의 항상 1.0 이
   나온다 — 분모가 없으면 질의를 30개 만들어도 숫자가 의미를 못 갖는다.
   문서 확보는 `~~docs/참고자료/개발_기획서_샘플/~~(2026-08-25 삭제 · git 이력에 있다) ` 의 RFP·요구사항 문서로 싸게 되고,
   질의는 라벨링 인건비가 든다. **G-TASK 1~2건 · G-PROMPT 15~20 은 원안 유지.**

2. **LLM-as-judge — 쓴다. 단 사람 표본으로 교차검증.**
   근거 적합성·업무 매칭을 LLM 으로 전수 채점해 **반복 측정**을 가능하게 하고,
   그중 약 20% 를 사람이 겹쳐 보아 **일치율을 함께 제시**한다.
   "LLM 이 LLM 을 채점했다"는 반론을 숫자로 막는 것이 목적이다.

3. **현업 효과 — 시간 비교 + 측정 조건 명시.**
   "문서 N장·업무 20건 기준, 수작업 X분(측정 1회) → Agent Y분" 형식.
   **표본이 1건이라는 사실을 숨기지 않고 적는다** — 화면의 정직 표기 원칙과 같은 기준이다.

## 9. 제품 화면과의 경계 (8/11 확정)

품질 지표(Recall 등)는 **화면에 넣지 않는다.** 실시간 계산 경로가 없어 화면에
올리면 하드코딩이 되고, 그건 `작업목록.md` 작업 7에서 금지한 바로 그것이다.
제품 화면에 노출하는 것은 **실행 기록까지**다(`agent_run`·`tool_call` →
`작업목록.md` 작업 10). 발표는 두 층으로 나눈다 — **제품 안에 실행 근거 / 이 문서에 평가 설계.**
