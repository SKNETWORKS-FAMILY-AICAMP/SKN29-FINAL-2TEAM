# 도구 실패 복구 정책 v0

## 1. 목적

도구 호출이 실패했을 때 Agent가 같은 요청을 무제한 반복하거나, 쓰기 도구를
중복 실행하는 문제를 막는다. 조회 실패와 쓰기 실패는 위험도가 다르므로 동일한
방식으로 처리하지 않는다.

이 문서는 두 범위를 구분한다.

- 평가 runner의 재시도 **계측·판정**: 구현 완료
- 실제 Agent 런타임의 재시도·사용자 결정 **동작**: 구현 예정

## 2. 현재 구현 상태

평가 runner는 도구 event를 분석해 다음 값을 기록한다.

- 도구별 시도·실패·재시도·복구 횟수
- 같은 도구와 같은 인자의 실패 후 재시도 횟수
- 최대 연속 실패 수
- 시작됐지만 완료 event가 없는 호출 수

현재 데이터셋 v10의 조회 workflow 임시 판정 기준은 동일 입력 재시도 최대 1회,
연속 실패 최대 2회다. 이는 **현재 Agent가 자동 재시도한다는 뜻이 아니다.** 실행
결과에 반복이 있었는지 runner가 사후 측정하는 기준이다.

## 3. 제품 런타임 목표 정책

### 3.1 조회 도구의 기술적 실패

조회 도구가 일시적인 기술 오류로 실패하면 자동 재시도한다.

- 최초 호출을 포함해 최대 3회 실행한다.
- 자동 재시도는 최대 2회다.
- timeout, 연결 끊김, HTTP 429, HTTP 5xx 등 일시 오류만 대상으로 한다.
- 예외 분류 시 `exc`, `exc.__cause__`, `exc.__context__` 체인을 확인한다.
- 재시도 사이에는 짧은 지수 backoff와 jitter를 적용한다.
- 최대 횟수 뒤에도 실패하면 오류 결과를 Agent에 돌려주고 더 이상 자동 실행하지
  않는다.

인증·권한·입력 오류 같은 영구 오류는 자동 재시도하지 않는다.

- HTTP 400, 401, 403, 404
- 스키마·직렬화·검증 오류
- 도구가 명시적으로 반환한 업무 규칙 위반
- HITL 거절·취소

### 3.2 조회 결과 부족

검색 결과가 없거나 충분하지 않은 것은 기술 오류가 아니다. 별도 자동 재시도
미들웨어를 적용하지 않는다. Agent가 다른 검색어·도구를 선택할 수 있으며 기존
전체·도구별 호출 상한으로 반복을 제한한다.

### 3.3 쓰기 도구 실패

쓰기 도구는 자동 재시도하지 않는다. 생성·수정·삭제를 다시 실행하면 중복 생성이나
중복 변경이 발생할 수 있기 때문이다.

장기 목표는 실패 뒤 사용자에게 다음 결정을 묻는 카드다.

- `retry`: 사용자가 명시적으로 허용한 한 번만 다시 실행
- `skip`: 해당 작업을 건너뛰고 Agent 실행을 계속함
- `reject`: 전체 쓰기 흐름을 거절하고 종료함

한 번의 사용자 승인으로 허용되는 실제 재시도는 한 번뿐이다. 재시도도 실패하면
같은 승인으로 다시 반복하지 않고 새로운 실패 상태로 처리한다.

## 4. 쓰기 실패 카드의 재진입 안전성

LangGraph는 `interrupt()`에서 재개할 때 해당 노드를 처음부터 다시 실행한다.
따라서 다음 순서는 금지한다.

```text
쓰기 도구 실행 → 실패 → interrupt()
```

이 구조에서는 재개 시 `interrupt()` 앞의 쓰기 도구가 다시 실행될 수 있다. 안전한
순서는 다음과 같다.

```text
쓰기 도구 실행 실패
→ 외부 DB에 PENDING 실패 상태와 멱등성 키 저장
→ interrupt()
→ 재진입 시 DB 상태를 가장 먼저 확인
→ 사용자의 결정에 따라 한 번만 상태 전이·실행
```

멱등성 키는 최소한 `run_id + tool_call_id`를 포함한다. 상태 전이는
`UPDATE ... WHERE status = 'PENDING'` 형태로 원자적으로 수행해 중복 클릭과 경합을
막는다. `SKIPPED`와 `REJECTED`는 서로 다른 상태로 보존한다.

## 5. 승인 카드와 재개 계약

현재 제품은 한 턴의 승인 대상을 한 번의 `interrupt()`에 배열로 묶고
`Command(resume={"decisions": [...]})` 형태로 재개한다. 쓰기 도구 실패 카드도
사용자와 API에는 같은 배열 형태를 유지한다.

```json
{
  "decisions": [
    {"failure_index": 0, "type": "retry"},
    {"failure_index": 1, "type": "skip"}
  ]
}
```

다만 병렬 도구 실행 중 발생한 실패들은 LangGraph 내부에서 서로 다른
`interrupt_id`를 가질 수 있다. 서버는 사용자에게 내부 ID를 직접 노출하지 않고,
DB에 저장한 `failure_index`와 실제 `interrupt_id`를 연결해 내부적으로 다음처럼
재개한다.

```python
Command(
    resume={
        interrupt_id_1: {"decision": "retry"},
        interrupt_id_2: {"decision": "skip"},
    }
)
```

즉 UI·API는 기존 배열 패턴을 재사용하고, 런타임 내부는 LangGraph의 다중 interrupt
재개 방식을 사용한다. 모든 실패를 한 interrupt로 강제로 모으는 별도 조정 노드는
구조 변경이 크므로 v0 범위에서 제외한다.

## 6. 단계별 구현 순서

### 1단계 — 조회 도구 자동 재시도

1. 도구를 읽기·쓰기로 분류하는 단일 정책 함수를 만든다.
2. 재시도 가능한 기술 오류 분류기를 만든다.
3. 조회 도구에 최초 포함 최대 3회 실행과 backoff를 적용한다.
4. 기존 전체·도구별 호출 상한과 중복 적용되는 방식을 명시한다.
5. 기존 trace event에 시도 번호와 최종 실패 분류를 남긴다.
6. runner의 `tool_reliability` 계측으로 실제 동작을 검증한다.

필수 테스트:

- 첫 호출 성공 시 추가 호출 없음
- timeout 뒤 성공
- 429·5xx 뒤 성공
- 3회 모두 실패 후 종료
- 400·401·403·404는 즉시 종료
- 결과 0건은 미들웨어 자동 재시도 없음
- 쓰기 도구는 기술 오류여도 자동 재시도 없음
- 병렬 조회 호출 간 재시도 상태가 섞이지 않음

### 2단계 — 쓰기 실패 사용자 결정 카드

1단계가 실전에서 안정된 뒤 별도 설계 승인 후 진행한다.

1. 실패 상태 DB 테이블과 멱등성 키를 설계한다.
2. 원자적 상태 전이와 재진입 방어를 구현한다.
3. 실패 event와 카드 UI를 구현한다.
4. 기존 `decisions` 배열 API를 확장한다.
5. API 배열을 내부 `interrupt_id` 매핑으로 변환한다.
6. retry·skip·reject와 병렬 실패를 검증한다.
7. 중복 클릭·재전송·서버 재시작·체크포인트 재개 테스트를 수행한다.

## 7. 완료 기준

조회 재시도 1단계 완료 조건:

- 일시적인 조회 오류만 최초 포함 최대 3회 실행된다.
- 영구 오류·결과 부족·쓰기 도구는 자동 재시도하지 않는다.
- runner 결과에서 시도·실패·복구와 상한 초과를 확인할 수 있다.
- 기존 HITL과 도구 호출 상한 테스트가 회귀하지 않는다.

쓰기 실패 카드 2단계 완료 조건:

- 사용자 결정 전 쓰기 side effect가 추가 발생하지 않는다.
- 한 번의 `retry` 결정은 실제 재실행 한 번만 허용한다.
- 재개·중복 클릭·병렬 실패에서도 같은 쓰기가 중복 실행되지 않는다.
- `skip`과 `reject`가 실행 상태와 평가 결과에 구분되어 남는다.

- 지금 문서 설계만 유지할 범위: **2단계 쓰기 실패 사용자 결정 카드**

## 9. 1단계 구현 결과 (2026-08-26)

- 코드: `services/agent_runtime/factory.py`
  - `_is_transient_tool_failure(exc)`: `exc`·`__cause__`·`__context__` 체인을
    최대 5단계까지 따라가며 `McpError.code`(`timeout`/`unreachable`/`429`),
    `requests.Timeout`/`ConnectionError`, `requests.HTTPError`의
    `response.status_code`(429/500/502/503/504)를 확인한다. Jira·Drive
    커넥터가 `raise OAuthError(...) from exc`로 원인을 감싸는 경우도 이 체인
    추적으로 잡는다.
  - `_call_tool_handler(tool, resolved)`: `tool.handler(**resolved)`를 감싸
    읽기 전용 도구(`side_effect=False`)에만 최초 호출 포함 최대 3회, 지수
    backoff(`0.2s * 2^n` + jitter)로 재시도한다. 쓰기 도구는 분류 결과와 무관하게
    항상 1회만 시도한다.
  - 삽입 위치: 애초 예상했던 LangGraph `wrap_tool_call` 미들웨어 자리는 쓸 수
    없었다 — `_IdempotencyAwareTool`이 `handle_tool_error=True`로 만들어져
    `BaseTool.invoke()`가 `ToolException`을 미들웨어 체인에 닿기 전에 문자열로
    삼킨다. 그래서 `_run()` 내부, `tool.handler()`를 직접 부르는 자리 하나에만
    넣었다.
- 테스트: `tests/test_factory.py::ToolTransientFailureRetryTests`(신규 7개) —
  최초 성공 시 미재시도, MCP timeout/HTTP 429 뒤 복구, 3회 소진 후 종료,
  영구 오류(401) 미재시도, 쓰기 도구는 일시 오류여도 미재시도, `OAuthError`가
  감싼 `requests.Timeout`도 원인 체인으로 재시도 판별. 기존
  `test_factory.py`·`test_tool_timeout.py`·`test_middleware_factory.py`
  120개와 `test_evaluation_*` 3개 스위트 전부 회귀 없이 통과.
- 범위 밖(의도적으로 다루지 않음):
  - 검색 결과 0건·부족은 예외가 아니므로 애초에 이 경로를 안 탄다(§3.2와 일치).
  - 재시도가 같은 `tool.handler()` 호출 안에서 일어나므로 LangGraph 관점에서는
    여전히 하나의 tool_call이다. 평가 runner의 `tool_reliability` 집계는
    trace event 간 재호출(모델이 같은 도구를 다시 부르는 경우)을 재시도로
    세는 방식이라, 이번 내부 재시도는 그 집계에 잡히지 않는다. 실전 로그
    확인(§7 완료조건의 "일시적인 조회 오류만 최초 포함 최대 3회 실행된다")은
    현재 `logger.warning`/`logger.info` 구조화 로그로 확인한다 — DB·평가
    runner에 재시도 횟수를 별도로 적재하는 것은 아직 하지 않았다.
  - Langfuse·OpenTelemetry에 재시도 attempt를 span으로 노출하는 것은 8단계
    관측 연동에서 함께 처리한다.
- 다음 단계: 실전 로그로 §7 1단계 완료조건(정상 조회 불필요 반복 없음, 재시도
  가능한 장애만 재실행, 최대 3회에서 확실히 멈춤)을 확인한 뒤 2단계(쓰기 실패
  카드) 설계 승인을 받는다.
