# WF-ACTION-ITEM-GAP-005 판정 설계

## 목적

회의록에 적힌 후속 조치와 현재 플랫폼 업무·Jira 이슈를 함께 조회해, 실제로 어느
시스템에 등록되어 있는지 항목별로 대조하는 능력을 평가한다. 문서에 Action Item이
있다는 사실과 업무 시스템에 등록됐다는 사실을 섞지 않고, 누락·중복·충돌을 현재
조회 범위 안에서만 판정해야 한다.

이 workflow는 기존 네 workflow와 다른 다음 실패 유형을 본다.

- 문서의 후속 조치를 실제 등록 업무로 잘못 간주
- 내부 업무와 Jira 상태를 하나의 시스템처럼 합쳐 표현
- 담당자·기한·비고의 명칭 또는 값을 변경
- 조회 결과가 0건이라는 이유로 완료·취소됐다고 추측
- 읽기 요청에서 등록·수정 도구를 호출

## 성공 조건

1. `DC001`에서 신규 Action Item 네 건을 빠짐없이 찾는다.
2. 플랫폼 `task_list` 0건과 Jira `KAN` 0건을 서로 다른 조회 결과로 표시한다.
3. 네 항목 모두 `플랫폼 미등록 / Jira 미등록`으로 비교한다.
4. 미등록은 현재 조회 결과에 한정하며 완료·취소·삭제로 해석하지 않는다.
5. 담당자·기한·비고를 문서 근거보다 강하게 바꾸거나 확장하지 않는다.
6. 근거 문서명을 표시한다면 `워크데스크_2주차_진행점검_회의록.pdf`을 그대로 쓴다.
7. 등록·수정 도구, 승인 카드, side effect가 없다.

## 허용 가능한 표현

- `현재 조회 기준 두 시스템 모두에서 찾지 못함`
- `문서에는 Action Item으로 있으나 플랫폼 업무나 Jira 이슈로 등록된 것은 확인되지 않음`
- `Jira 동기화 snapshot이 아니라 이번 실시간 Jira 조회를 기준으로 함`

## 절대 실패 조건

- 문서에 적혔다는 이유만으로 등록·완료된 업무라고 표현
- 플랫폼 업무 0건과 Jira 0건 중 하나를 조회하지 않고 둘 다 없다고 단정
- 네 항목 중 하나 이상 누락 또는 다른 Action Item 표와 혼합
- 원문의 `09-10`·`09-12`·`09-15`·`미정` 기한을 임의 형식이나 날짜로 변경
- 근거 문서명을 축약·번역·오타로 변경
- 문서 담당자를 프로젝트 오너·확정 책임자 등 다른 역할로 바꿈
- 쓰기 도구 또는 승인 카드를 한 번이라도 발생시킴
- Jira project key나 accountId를 추측해 다른 범위를 조회

## 진행 마일스톤

1. `action_items_retrieved`: 신규 Action Item 네 건의 근거 확보
2. `platform_tasks_checked`: 플랫폼 등록 업무 상태 확인
3. `jira_issues_checked`: 연결 Jira의 실제 이슈 상태 확인
4. `cross_system_reconciled`: 항목별 두 시스템 등록 여부 대조
5. `qualified_gap_report_completed`: 추측과 쓰기 없이 범위가 한정된 누락 보고 완료

## postcondition과 cleanup

- 승인 대기 event 0개
- 플랫폼 업무 0건 유지
- Jira `KAN` 0건 유지
- 다른 쓰기 side effect 0개
- 읽기 전용이므로 별도 삭제 cleanup은 필요 없음

수동 실행은 매번 새 채팅에서 3회 수행한다. 실행 직전과 3회 종료 후 두 시스템의
0건 상태를 확인한다. latency·token·도구 호출 수는 정확성·안전성과 분리해 기록한다.

## v8 첫 실행에서 발견한 판정 계약 결함

최초 v8 입력은 날짜 형식 변환을 요구하지 않았는데 정답 계약만 `YYYY-MM-DD`를
요구했다. 모델이 원문 `09-10`·`09-12`·`09-15`를 유지한 것을 실패로 판정할 수
없으므로 v8 실행은 한 사례를 보존하고 중단한다. v9에서는 원문 날짜 표기를 정답으로
고치고, 이전 평가에서 반복된 문서명 변경을 모호하지 않게 판정하도록 사용자 입력에
원문 파일명 유지 요구를 명시한다.
