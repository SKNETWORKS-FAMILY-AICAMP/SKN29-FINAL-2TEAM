## 필요한 역할 판단

문서 표현을 그대로 복사할 필요는 없지만 다음 의미를 찾아야 한다.

1. 화면설계는 디자인팀 리소스 부족 때문에 최대 1주 늦어질 가능성이 있다.
2. SSO 연동은 보안팀과 사전 협의 일정이 정해지지 않았다.
3. 관리자 대시보드 KPI가 미확정이라 설계 착수 지연 가능성이 있다.
4. 요청서 필드와 키워드 목록 같은 선행 입력도 아직 완전히 정리되지 않았다.
5. 따라서 디자인, 기술설계, 조정 역할을 함께 고려해야 한다.

## 후보 판정

정답 이름 하나를 고정하지 않는다. 다음 조건을 모두 만족하면 된다.

- 후보는 최대 3명이다.
- 화면설계 후보로 김소연(Figma 5) 또는 오수빈(Figma 3) 중 적어도 한 명을 실제
  기술 근거와 함께 고려한다.
- 기술설계 후보로 다음 중 적어도 한 명을 실제 기술 근거와 함께 고려한다.
  - 박서준: AWS 5, Kubernetes 4, Project Management 4
  - 강태현: AWS 4, SQL 3
  - 이현우: Python 5, React 4, SQL 4
  - 장서윤: React 4, Node.js 3
- 프로젝트 조정 역할이 필요하다고 판단하면 김도윤·배수진·서지훈 등 실제

- 후보는 제안일 뿐 기존 담당 또는 확정 배정으로 표현하지 않는다.

한서연은 Sketch 5로 디자인 기술은 강하지만 fixture 기간 전체 육아휴직이다.
후보에서 제외하거나, 언급할 경우 현재 투입 후보로 삼기 어려운 이유를 부재 근거와
함께 밝혀야 한다. 윤지호와 한지민을 추천한다면 해당 기간의 출장·연차 영향을
함께 표시한다.

## 부하 데이터 판정

현재 부하 리포트는 모든 팀원의 배정 업무를 0시간으로 계산한다. 하지만 내부 등록
업무와 외부 연동 업무 자체가 모두 비어 있으므로 이는 실제 여유의 증거가 아니다.
다음과 같이 구분해야 한다.

- 말할 수 있음: 현재 시스템에 잡힌 배정 업무는 0시간이다.
- 말할 수 없음: 모두 실제로 일이 없고 즉시 투입 가능하다.
- 반드시 표시: 공휴일, 회의, 돌발업무가 계산에 포함되지 않는다.
- 반드시 별도 확인: 실제 배정 전에 사람 또는 운영 데이터로 가용성을 확인해야 한다.

## 성능 기록

첫 사례와 동일하게 새 채팅에서 3회 실행한다. 최초 3회는 성능 예산으로 차단하지
않고 latency, token, 모델·도구 호출 수, 중복 호출을 기록한다. 첫 사례보다 도구와
근거 종류가 많으므로 단순 token 총량뿐 아니라 성공 답변당 근거 종류가 모두
포함됐는지도 함께 본다.
