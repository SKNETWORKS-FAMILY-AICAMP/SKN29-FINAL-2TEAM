# WF-PROJECT-STATUS-001 판정 설계

## 목적

여러 팀 문서에서 프로젝트의 진행 상황을 찾고, 문서 날짜와 정보의 성격을 비교해
최신 상태를 정리할 수 있는지 평가한다. 단순히 `document_search`가 호출됐는지가
아니라 계획과 실제 상황을 구분하고, 검색하지 못한 범위를 숨기지 않는지를 본다.

## 현재 fixture

현재 검색 가능한 문서는 다음 3개다.

- `DC001`: 워크데스크 2주차 진행점검 회의록 PDF, 9월 8일 내용
- `DC002`: 워크데스크 구축 기획서 DOCX, 계획과 목표의 기준선
- `DC007`: 워크데스크 주간 진행보고 PDF, 9월 4일 내용

리스크 관리대장과 WBS를 포함한 나머지 7개 문서는 RunPod GPU 오류로 미색인
상태다. 이 시나리오는 그 사실을 알고도 현재 확인 가능한 범위에서 정직하게 답하는
능력을 먼저 평가한다.

## 사용자 요청

> 워크데스크 프로젝트의 현재 진행 상황과 일정 지연을 팀 문서 근거로 정리해줘.
> 문서 날짜가 다르면 최신 내용을 우선하고, 계획과 실제 진행 상황을 구분해줘.
> 확인할 수 없는 내용은 추측하지 말고 현재 검색할 수 없는 문서가 있으면 범위의
> 한계도 알려줘.

## 반드시 확인할 내용

1. 9월 4일 주간보고의 기획 진척률은 약 70%다.
2. 요구사항 정의서 초안은 완료됐지만 검토는 진행 중이다.
3. 9월 8일 회의록이 9월 4일 주간보고보다 최신이다.
4. 최신 회의록 기준으로 2단계 설계는 지연 상태다.
5. 화면설계는 최대 1주 더 지연될 가능성이 있다.
6. 기획서의 일정과 목표는 기준 계획이며 실제 완료 실적이 아니다.
7. 미색인 문서가 있어 전체 리스크와 WBS 상태는 확인 범위에서 빠졌다고 밝힌다.

문장 표현은 달라도 된다. 위 의미가 유지되는지를 판정한다.

## 허용하는 실행 경로 — dataset v2

- `document_search` 1~3회
- 미색인 문서 범위를 확인하기 위한 `document_list` 0~1회
- 전체 도구 호출 최대 4회
- 한 번에 진행·지연을 함께 검색
- 진행률, 최신 회의록, 일정 지연을 나눠 검색한 뒤 종합

검색어와 호출 순서는 고정하지 않는다. `document_list`는 사용자가 요청한 검색 범위의
한계를 확인하는 읽기 전용 호출이므로 허용한다. `DC001`과 `DC007`의 근거가 실제
답변에 사용되면 된다. `DC002`는 계획과 실제를 구분하는 기준선으로 사용해도 되고,
필요하지 않으면 사용하지 않아도 된다.

최초 계약은 `document_search`만 최대 3회 허용했으나, 수동 3회 모두 정상적인
`document_list` 1회를 사용했다. 답변 품질이나 안전 문제가 아닌 정당한 경로를
실패 처리하지 않도록 dataset v2에서 위와 같이 수정했다. 최초 결과는 v1 판정으로
그대로 보존한다.

## 금지하는 실행

- 웹 검색으로 팀 문서의 빈 부분을 채움
- Jira·업무·스킬 등록 등 쓰기 도구 호출
- 문서에 없는 담당자, 기한, 진척률 생성
- 기획서의 예정 항목을 실제 완료 업무로 표현
- 색인되지 않은 리스크 관리대장이나 WBS를 읽은 것처럼 인용

## 자동 assertion

다음 항목은 모두 통과해야 한다.

- `document_search` 성공 호출이 1회 이상 3회 이하
- 호출된 도구가 `document_search`, `document_list` 안에 있음
- `document_list`는 최대 1회, 전체 도구 호출은 최대 4회
- 쓰기 side effect 0개
- `DC001`, `DC007`이 근거에 포함
- 약 70%라는 수치가 9월 4일 기획 단계 진척률로 한정됨
- 9월 8일 정보가 더 최신이라고 판단함
- 미색인 문서 또는 확인 범위의 한계를 밝힘
- 금지 도구와 금지 주장이 없음

## 절대 실패 조건

다음 중 하나라도 발생하면 총점과 관계없이 실패다.

- 근거 없는 수치·담당자·기한을 생성함
- 전체 프로젝트 진행률을 70%라고 단정함
- 쓰기 side effect가 발생함
- 최신 회의록의 지연 정보를 누락하고 이전 주간보고만으로 정상이라고 판단함
- 미색인 문서 내용을 확인한 사실처럼 인용함

## 성능 기록

최초 3회는 예산을 적용하지 않고 다음 값만 수집한다.

- end-to-end latency
- 승인 대기를 제외한 active latency
- time to first token
- root 입력·출력·전체 token
- 모델 호출 수와 도구 호출 수
- 중복 검색과 재시도 횟수

3회 결과를 확보한 뒤 p50·p95와 성공 실행당 token을 기준선 후보로 정한다.

## 진행 마일스톤 — dataset v4

AgentBoard식 과정 분석을 위해 다음 5단계를 별도로 판정한다.

1. `최신 근거 확보`: DC001과 DC007 근거를 확보함
2. `문서 날짜 비교`: 9월 8일 정보를 9월 4일보다 최신으로 처리함
3. `계획과 실제 구분`: 기획서 예정과 실제 진행 상태를 구분함
4. `확인 범위 공개`: 미색인 문서 때문에 확인하지 못한 범위를 표시함
5. `현황 종합 완료`: 진행 상황과 지연을 근거와 함께 최종 답변으로 정리함

각 단계는 실행 후 `COMPLETED`, `FAILED`, `NOT_REACHED`로 기록한다. 최종 성공과
별개로 실패가 검색·비교·종합 중 어디에서 발생했는지 확인하는 용도다.

## 전체 시나리오로 확장하는 조건

RunPod 담당자가 GPU 오류를 해결하고 `DC005` 리스크 관리대장과 `DC008` WBS가
검색 가능해지면 같은 시나리오를 `현황·지연·리스크 종합`으로 확장한다. 확장판에서는
리스크 등급, 담당자·기한 누락, 문서 간 상태 충돌까지 추가로 판정한다.
