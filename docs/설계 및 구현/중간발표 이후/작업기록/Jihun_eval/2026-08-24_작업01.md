## 1. 작업 배경

Deep Agent 평가를 실행하기 전에 기존 `agent_run`·`tool_call` 추적 흐름을 점검했다.
그 결과 HITL(Human-in-the-loop) 승인 대기 구간에서 실제 실패가 아닌 도구 호출이
`FAILED / STREAM_CLOSED`로 기록될 수 있는 문제를 확인했다.

기존 추적기는 LangChain의 도구 호출 ID와 DB의 `tool_call_id` 관계를 현재 Python
스트림의 메모리에만 보관했다. 승인 요청으로 첫 스트림이 종료되면 이 관계가
사라졌고, 다음 resume 스트림에서는 원래 `PENDING` 행을 찾을 수 없었다. 또한
첫 스트림의 종료 정리 로직이 승인 대기 중인 루트·서브에이전트 실행과 도구 호출을
실패로 오인할 수 있었다.

이 상태로 평가를 시작하면 다음과 같은 왜곡이 발생한다.

- 승인 대기 호출이 실행 실패로 집계된다.
- 승인 후 성공한 호출이 기존 `PENDING` 행을 정상적으로 닫지 못한다.
- 사용자가 거절하여 실행되지 않은 호출이 성공 또는 실패로 잘못 집계될 수 있다.
- 도구 성공률과 평가 기준선의 신뢰도가 떨어진다.

## 2. 구현한 내용

### 2.1 DB 상관관계 키 추가

`tool_call` 테이블에 nullable `langchain_tool_call_id VARCHAR(64)` 컬럼을 추가했다.
동일한 실행에서 동일한 LangChain 호출이 중복 기록되지 않도록 다음 부분 UNIQUE
인덱스도 추가했다.

```sql
CREATE UNIQUE INDEX ux_tool_call_run_langchain_id
    ON tool_call (run_id, langchain_tool_call_id)
    WHERE langchain_tool_call_id IS NOT NULL;
```

관련 파일:

- `DB/schema.sql`
- `DB/migrations/2026-08-24_tool_call_hitl_lifecycle.sql`
- `backend/db/agent_platform.py`

레거시 Harness는 LangChain 호출 ID가 없으므로 저장소 인자를 선택값으로 유지했다.
따라서 기존 호출 경로는 예전처럼 새 행을 기록하고, Deep Agent 경로만 영속
상관관계 키를 사용한다.

### 2.2 승인 대기 상태 보존

HITL interrupt가 발생하면 현재 스트림에서 열린 루트 실행뿐 아니라 서브에이전트
실행도 함께 `PENDING`으로 유지하도록 변경했다. 열려 있던 도구 호출 역시 DB에서는
`PENDING` 상태를 유지하고, 현재 스트림의 orphan 정리 대상에서만 제거한다.

승인 카드에는 resume에 필요한 최소 추적 상태를 저장한다.

- 대기 중인 서브에이전트 정보
- namespace와 서브에이전트 실행의 대응 관계
- 대기 중인 직접 도구 호출 정보
- `action_index`와 `(run_id, tool_call_id)`의 대응 관계
- 중단 시점에 열려 있던 실행 ID 목록

관련 파일:

- `services/agent_runtime/events.py`
- `services/agent_runtime/executor.py`
- `services/agent_runtime/tracing/__init__.py`

### 2.3 resume 완료 처리

resume 스트림에는 첫 스트림의 메모리상 DB UUID 매핑이 없다. 따라서 도구 완료
이벤트가 오면 `(run_id, langchain_tool_call_id)`로 기존 `PENDING` 행을 찾아
`OK` 또는 `FAILED`로 갱신하도록 변경했다.

resume 시점에는 실제 도구 시작 시각을 알 수 없으므로 사람의 승인 대기 시간을
도구 실행 시간으로 잘못 포함하지 않도록 `duration_ms`는 `NULL`로 유지한다.

### 2.4 사용자 거절 상태 분리

사용자가 거절한 호출은 실제 handler가 실행되지 않는다. 이를 실행 실패와 구분하기
위해 `tool_call.status`에 `REJECTED` 상태를 사용하고, `error_code`에는
`HITL_REJECTED`를 기록하도록 변경했다.

resume 이후 미들웨어가 거절 결과를 정상 `ToolMessage`로 반환하더라도 저장소의
`status = 'PENDING'` 조건 때문에 `REJECTED` 행이 `OK`로 덮이지 않는다.

관련 파일:

- `apps/chat/api_views.py`
- `backend/db/agent_platform.py`

### 2.5 운영 지표 보정

도구 성공률의 분모를 실제 실행이 완료된 호출로 제한했다.

```text
도구 성공률 = OK / (OK + FAILED)
```

`PENDING`은 승인 대기 또는 실행 중인 호출이고, `REJECTED`는 사용자가 실행하지
않기로 결정한 호출이므로 성공률 분모에서 제외한다. 운영 화면에는 두 상태를 별도
열로 표시한다.

관련 파일:

- `backend/db/repositories.py`
- `frontend/src/api/opsUsage.ts`
- `frontend/src/pages/OpsUsagePage/OpsUsagePage.tsx`

## 3. 추가한 회귀 검증

다음 시나리오를 테스트에 반영했다.

- 도구 시작 시 LangChain 호출 ID가 DB 저장소로 전달되는지
- 승인 대기 시 열린 도구 호출이 실패로 닫히지 않는지
- 서브에이전트 실행과 그 내부 도구 호출도 함께 보류되는지
- resume 스트림이 원래 `PENDING` 행을 성공 또는 실패로 닫는지
- 동일한 병렬 호출이 원래 순서대로 승인 요청과 대응되는지
- resume 시 서브에이전트 namespace/run 매핑이 복원되는지

- 기존 레거시 Harness 호출이 계속 동작하는지
- 운영 집계 응답에 `PENDING`과 `REJECTED`가 구분되는지

### 5.3 수동 HITL QA — 루트·서브에이전트 완료

DB 반영 후 실제 채팅에서 루트 에이전트의 승인·거절 흐름을 검증했다.

- 승인 전: 대상 `tool_call` 행이 `PENDING`으로 유지됨
- 승인 후: 같은 행이 `OK`로 종료되고 중복 행이 생기지 않음
- 거절 후: 같은 행이 `REJECTED / HITL_REJECTED`로 종료됨
- 승인·거절 카드가 각각 표시되고 종료 후 다시 대기 카드로 선택되지 않음
- 연속 클릭으로 동일 확인 요청이 중복 전송되지 않도록 프런트에 즉시 잠금을 추가함
- 도구 실제 완료 이벤트를 기준으로 서버가 완료 메시지를 확정하여, 모델의 승인 안내 문구가 최종 결과를 덮지 않음

서브에이전트 내부 승인 대기 → 승인 → 도구 성공 흐름도 추가로
검증했다. 최종 확인 결과는 다음과 같다.

- 루트 `agent_run`: `DONE`
- 서브에이전트 `agent_run`: 부모 `run_id`와 연결된 같은 행이 `DONE`
- 서브에이전트의 `tool_call`: 승인 전 `PENDING`, 승인 후 같은 행이 `OK`
- 같은 `(run_id, langchain_tool_call_id)` 행은 1개만 존재하여 추가 중복 0개
- 개인 스킬의 실제 저장 확인

이 과정에서 승인 대기 이벤트의 `trace_resume_state`와
`suspended_run_ids`가 채팅 메시지 최상위에 저장되지 않는 문제를
발견해 수정했다. 또한 LangGraph가 같은 interrupt를 루트와 서브그래프
namespace에서 두 번 보낼 수 있어, 같은 `interrupt_id`는 한 번만 이벤트로
변환하도록 고정했다. 이벤트·채팅 회귀 테스트 133개가 통과했다.

별도 관찰 사항으로, 서브에이전트가 사용자가 준 스킬 본문에 위임 지시의
승인 안내 문장을 덧붙여 도구 인자로 보낸 사례가 있었다. HITL 추적 정합성은
성공했으나, 위임 전·후 인자 보존은 별도 품질 평가 항목으로 남긴다.

최종 완료 기준은 다음과 같다.

- 승인 전: 대상 `tool_call.status = 'PENDING'`
- 승인 후 성공: 같은 행이 `OK`
- 거절 후: 같은 행이 `REJECTED`, `error_code = 'HITL_REJECTED'`
- 승인 대기 중인 호출이 `FAILED / STREAM_CLOSED`로 기록되지 않음
- 같은 `(run_id, langchain_tool_call_id)`에 중복 행이 생기지 않음

결정적 assertion을 수행하는 평가 runner다. 실제 LLM 호출과 side effect를
발생시키기 전에 read-only 5개 사례부터 실행하는 순서로 진행한다.

```text
마이그레이션 검사 보완 완료
→ 로컬 DB 마이그레이션 및 재확인 완료
→ 루트 HITL 승인·거절 QA 완료
→ 서브에이전트 HITL QA 완료
→ Langfuse Python SDK v4 전환 완료
→ LangSmith 비활성화·연결 제거 완료
→ 평가 기준선 수집 준비 및 시작
```

이 순서를 완료해야 P0 추적 정합성이 실제 실행 환경에도 반영됐다고 판단할 수 있다.

## 7. `main <- jihun` 병합 시 DB 마이그레이션 인계

> 이 절은 **최신 `main`에 `jihun` 브랜치를 병합하는 방향**만 다룬다.
> 병합 담당 AI는 `main`에 이미 존재하는 마이그레이션을 지훈 브랜치 버전으로
> 되돌리거나, `main`의 최신 스키마를 통째로 덮어쓰면 안 된다.

### 7.1 지훈 브랜치가 main DB에 추가하는 마이그레이션

| 순서 | 파일 | 역할 | 위험도 |
|---:|---|---|---|
| 1 | `2026-08-22_team_default_model.sql` | 레거시 `agent.model`을 `team.default_model`로 이전 | 순서 의존 |
| 2 | `2026-08-24_tool_call_hitl_lifecycle.sql` | HITL 호출 ID 컬럼과 부분 UNIQUE 인덱스 추가 | 비파괴 |
| 3 | `2026-08-22_drop_legacy_agent.sql` | 레거시 테이블과 레거시 전용 기록 제거 | 파괴적 |

첫 번째와 세 번째 파일의 순서는 바꿀 수 없다. `team_default_model.sql`은
레거시 `agent`와 `agent_tool`을 데이터 원본으로 읽으므로, 두 테이블을 삭제한
뒤에는 실행할 수 없다. 컬럼이 이미 있더라도 원본 테이블이 없으면 SQL이 실패할
수 있으므로 무조건 재실행하지 말고 대상 DB 상태를 먼저 확인한다.

`drop_legacy_agent.sql`은 단순한 `DROP TABLE`이 아니다. 새 `agents` 테이블에
대응되는 행이 없는 과거 `chat_session`, `chat_message`, `agent_run`, `tool_call`도
삭제한다. 실행 전 백업과 삭제 예상 건수 확인이 필수다.

여기서 폐기하는 `draft`는 레거시 bridge/실행 경로를 뜻한다. 현재 빌더 생명주기의
`agents.status = 'DRAFT'`는 정상 데이터이므로 삭제하거나 일괄 변경하지 않는다.

### 7.2 병합·배포·마이그레이션 강제 순서

병합 담당 AI는 다음 순서를 지킨다.

1. 대상이 최신 `main` DB인지 확인하고 DB를 백업한다.
2. `agent`, `agent_tool` 존재 여부와 팀별 기본 채팅 에이전트 누락 여부를 조회한다.
3. 기본 채팅 에이전트가 없는 팀이 있으면
   `backend/services/createDB/backfill_default_chat_agents.py --all-teams`로 보강하고
   결과를 다시 확인한다.
4. 레거시 테이블이 존재하는 동안 `2026-08-22_team_default_model.sql`을 실행한다.
5. 레거시 기본 모델과 `team.default_model` 이전 결과를 대조한다.
6. `2026-08-24_tool_call_hitl_lifecycle.sql`을 실행하고 컬럼 및 UNIQUE 인덱스를 확인한다.
7. 병합된 코드를 빌드·테스트하고 배포한다. 이 시점까지 레거시 테이블을 지우지 않는다.
8. 채팅, 에이전트 실행, HITL 승인·거절 smoke test를 수행한다.
9. 레거시 코드 경로를 더 이상 사용하지 않는 것이 확인된 뒤에만
   `2026-08-22_drop_legacy_agent.sql`을 실행한다.
10. 마지막으로 `DB/migrations/_apply.py --check`를 실행한다.

`_apply.py`의 최종 검사에는 레거시 `agent`/`agent_tool` 부재 조건이 있으므로,
레거시 삭제를 의도적으로 미룬 단계에서는 해당 검사가 실패할 수 있다. 이를 이유로
검사 코드를 제거하지 말고, 최종 삭제 후 다시 실행한다.

대상 DB 사전 확인에 사용할 최소 조회는 다음과 같다.

```sql
SELECT to_regclass('public.agent')      AS legacy_agent,
       to_regclass('public.agent_tool') AS legacy_agent_tool;

SELECT count(*) AS teams_without_default_chat
FROM team AS t
WHERE NOT EXISTS (
    SELECT 1
    FROM agents AS a
    WHERE a.team_id = t.team_id
      AND a.is_default_chat = true
);

SELECT count(*) AS legacy_only_chat_sessions
FROM chat_session AS s
WHERE NOT EXISTS (
    SELECT 1 FROM agents AS a WHERE a.agent_id = s.agent_id
);

SELECT count(*) AS legacy_only_agent_runs
FROM agent_run AS r
WHERE NOT EXISTS (
    SELECT 1 FROM agents AS a WHERE a.agent_id = r.agent_id
);
```

### 7.3 병합 충돌 해결 기준

`DB/migrations/_apply.py`와 `DB/schema.sql`은 양쪽 브랜치가 모두 수정했으므로
한쪽 파일을 그대로 선택하지 않는다.

`_apply.py`에는 main의 최신 검사 항목을 모두 유지하면서 다음 지훈 브랜치 항목을
합친다.

- `team.default_model`
- `tool_call.langchain_tool_call_id`
- `tool_call.ux_tool_call_run_langchain_id`의 존재 및 UNIQUE 여부
- 레거시 `agent`, `agent_tool` 부재 검사
- 따옴표 안의 세미콜론을 SQL 구분자로 오인하지 않는 `_split_statements` 수정

`schema.sql`에는 main의 `team.guardrail_on_failure`, `connector_conn.sync_cursor`,
`doc.index_detail` 등 최신 구조를 유지하면서 다음 최종 구조를 합친다.

- `team.default_model` 존재
- `tool_call.langchain_tool_call_id` 존재
- `ux_tool_call_run_langchain_id` 부분 UNIQUE 인덱스 존재
- 레거시 `agent`, `agent_tool` 정의 제거

`2026-08-24_drop_doc_meta.sql`은 지훈 브랜치 병합 때문에 필요한 마이그레이션이
아니다. main 측 별도 결정 사항이므로 이번 병합을 이유로 임의 실행하지 않는다.

### 7.4 DB 외 인계 사항

LangSmith 제거는 DB 마이그레이션이 아니다. 해당 변경까지 병합 범위에 포함한다면
배포 환경의 `LANGCHAIN_*`/`LANGSMITH_*` 추적 변수를 제거하고, Langfuse v4
의존성이 설치되도록 web 이미지를 다시 빌드해야 한다.

2026-08-24 현재 작업 트리에는 HITL 후속 수정, LangSmith 제거, Langfuse v4 전환,
평가 데이터셋 관련 **미커밋 변경이 남아 있다**. 따라서 현재 원격
`origin/jihun`만 main에 병합하면 이 변경들은 포함되지 않는다. 병합 전에 변경
범위를 검토하여 커밋·푸시하거나, 의도적으로 후속 PR로 분리했다는 기록을 남긴다.

### 7.5 병합 완료 기준

- `main`의 기존 마이그레이션 및 최신 스키마가 보존됨
- 모든 팀에 기본 채팅 에이전트가 정확히 하나 존재함
- `team.default_model` 이전 결과가 확인됨
- HITL 컬럼과 부분 UNIQUE 인덱스가 존재함
- 병합 코드 배포 후 채팅·실행·승인·거절 smoke test가 통과함
- 레거시 전용 데이터 삭제 건수를 확인하고 승인한 뒤 테이블을 제거함
- `agents.status = 'DRAFT'` 데이터는 보존됨
- 최종 `_apply.py --check`가 통과함
