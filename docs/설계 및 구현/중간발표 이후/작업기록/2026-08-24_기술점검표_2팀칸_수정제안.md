## 1. 필수 — 코드와 다르거나 파일 안에서 모순인 것

### 1-1. 시트 4 D10 — RAG 「구현 완료」가 시트 2 와 어긋난다

**위치** 시트 4, 10행 (`C10 = 근거 기반 문서 검색·RAG`)

| | |
|---|---|
| 현재 D10 | `구현 완료` |
| 현재 E10 | `자연어 요청 → 관련 Chunk 검색 → 원문 근거를 포함한 Agent 응답 생성` |

**문제.** 같은 파일 시트 2 의 I8 이 「검색·추천 정량평가는 최종 테스트 결과 정리가 필요함」이라고 적고 있는데, 시트 4 의 같은 기능은 「구현 완료」다. 심사위원이 두 시트를 같이 보면 앞뒤가 맞지 않는다.

**코드 확인 결과**

```
tests/eval/                     디렉터리 자체가 없음      → 골든셋 미구축
DB/schema.sql, DB/migrations/   hnsw · ivfflat 0건        → 순차 스캔
backend/db/document_pipeline.py ORDER BY embedding <=>    → 순수 벡터 검색
                                (tsvector · ts_rank 없음) → 하이브리드 검색 없음
```

**제안 D10**

```
구현 완료 / 성능 지표 미확보. 벡터 유사도 검색과 근거 표시는 동작하며 조회 문서
ID 를 실행 이력에 기록함(tool_call.retrieved_doc_ids). 벡터 인덱스(hnsw) 미적용
으로 순차 스캔 상태이며, 하이브리드 검색과 정량평가 골든셋은 미착수임.
```

**제안 E10**

```
자연어 요청 → 관련 Chunk 검색 → 원문 근거를 포함한 Agent 응답 생성. 골든셋
기준 검색 정확도를 수치로 제시하고, hnsw 인덱스 적용 전후 검색 지연을 동일
질의로 비교 제시함.
```

> 이 항목은 중간평가 피드백 ③ 의 유일한 순수 미반영과 같은 자리다. 마감 전에
> 골든셋을 만들면 시트 2 I8 과 이 칸을 함께 올릴 수 있다.

## 2. 권장 — 「구현 완료」가 미구현 부분을 덮고 있는 것

두 칸 모두 **틀린 말은 아니다.** 다만 발표 필수 섹션이 정확히 그 미구현 부분을
묻고 있어, 질문을 받았을 때 답이 준비돼 있어야 한다.

### 2-1. 시트 3 G9 — Loop 의 Verification

**위치** 시트 3, 9행 (Loop) / 현재 `G9 = 구현 완료`

**왜.** 준비 PDF 의 발표자료 필수 섹션 ④ 가 「**Verification** / Loop — 검증 과정 및
Loop 동작」이다. Loop 자체는 완료가 맞지만, 검증 계층은 부분이다.

**있는 것** 입력 가드레일(외부 공급자 Moderation·Jailbreak) · 민감정보 마스킹 ·
프롬프트 인젝션 방어 1단계 · 메모리 write guard · 서브에이전트 순환/깊이/권한
검증(`subagents/validation.py`) · 검색 결과 revision 필터

**없는 것** 모델 응답의 사실성을 자동 검증한 뒤 재시도하는 루프

**제안 G9**

```
구현 완료(Loop 동작·호출 상한·중단·재개). 검증 계층은 부분 적용 — 입력 가드레일,
민감정보 마스킹, 프롬프트 인젝션 방어 1단계, 메모리 write guard, 서브에이전트
순환·깊이·권한 검증은 구현했으나, 모델 응답의 사실성을 자동 검증 후 재시도하는
루프는 미구현임.
```

### 2-2. 시트 3 G7 — MCP 의 적용 범위

**위치** 시트 3, 7행 (MCP) / 현재 `G7 = 구현 완료`

**왜.** 외부 MCP 경로는 완료가 맞다. 다만 **내장 도구 15종은 in-process

**제안 G7**

```

내장 도구 15종은 in-process 레지스트리로 운영되어 MCP 를 경유하지 않으며,
MCP 는 외부·커스텀 도구 확장 경로로 사용함.
```

## 3. 권장 — 시트 4 에 핵심 기능 1건 추가

**현재 2팀 7개 기능에 운영자 콘솔·관측성·보안이 없다.** 준비 PDF 의 권장 기술에
「보안(JWT·RBAC·암호화)」과 「모니터링·관측성」이 들어 있어, 실제로 만든 것을
빠뜨리는 셈이다.

**행을 하나 늘리면 다른 팀 행이 오히려 빈 양식과 맞는다.**

```
현재    : 2팀 8~14 (7행)  |  3팀 15~21  |  4팀 22~28
추가 후 : 2팀 8~15 (8행)  |  3팀 16~22  |  4팀 23~29   ← 빈 양식의 원래 위치
```

빈 양식은 3팀을 16~22행, 4팀을 23~29행에 두고 있다. 2팀에 한 행을 더하면 두 팀이
제자리로 돌아간다. 양식 하단 안내도 「핵심 기능이 많을 시 추가하여 작성」이다.

**추가할 15행**

| 열 | 내용 |
|---|---|
| C15 | `운영자 콘솔·관측성·권한 통제` |
| D15 | `구현 완료. 운영자 화면 15종(팀·계정·모델·커스텀 도구·가드레일·사용 현황·감사 로그 등). 실행·도구 호출·가드레일 이벤트를 적재하고 30일 단위 요약을 제공함. 역할별 도구 차단, 팀장 전용 7개 경로, 민감정보 마스킹, 프롬프트 인젝션 방어 1단계를 적용함.` |
| E15 | `운영자가 팀별 실행 수·성공률·토큰·가드레일 발동을 화면에서 확인하고, 특정 문서를 지정해 해당 문서를 조회한 실행을 역추적하는 것까지 시연` |

> 행을 늘리지 않기로 하면, 최소한 D14(HITL 승인 기반 Jira·업무 반영)에
> 「역할별 권한 통제 및 감사 로그 적용」 한 문장을 붙여 두는 편이 낫다.

### 4-1. 시트 2 I8 — Mock HR 의 성격을 한 마디로 밝힌다

**현재 I8**


**사실 확인 결과 이 표기가 맞다.** `mock_hr` 스키마(`person`·`org`·`level`·`sched`)가
배선돼 있고 `people_list`·`workload_report`·`absence_list` 도구가 이를 읽는다.
역량(`skills`/`proficiency`)과 가용량(capacity profile·absence)까지 들어 있다

다만 피드백 원문이 「**실제 조직의** 구성원 경험·역량·가용량 데이터」였으므로,
데이터 출처가 대역이라는 점을 먼저 밝혀 두면 질문을 받았을 때 흔들리지 않는다.

**제안 I8**

```
VLM 기반 이미지·차트 처리 반영. 조직 데이터는 역량·가용량 구조까지 반영했으나
실제 조직 데이터가 아닌 Mock HR(person·org·level·sched)을 데이터 출처로 사용함.
Graph DB는 현재 요구사항상 미적용. 검색·추천 정량평가는 최종 테스트 결과 정리가
필요함.
```
