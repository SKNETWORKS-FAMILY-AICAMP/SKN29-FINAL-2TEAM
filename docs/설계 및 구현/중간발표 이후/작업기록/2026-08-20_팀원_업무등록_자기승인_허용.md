# 2026-08-20 — 팀원의 업무 등록(부수효과 도구), 자기 승인(HITL)으로 허용

## 요청

"지금 승인 필요한 것들을 팀원이 팀장 승인이 필요하다고 했었는데, 팀원이 자기꺼
등록할 수 있게끔 다시 수정하고 싶어. 단, HITL 해서 업무를 실제로 등록하기 전에
'등록할까요?' 라는 질문에 승인 버튼을 눌러야 실행할 수 있게 하고 싶어."

## 배경 — 2026-08-19의 결정과 그 이후

2026-08-19 "도구 실행 안정화와 권한 정책" 작업(§8)에서 정책이 한 번 정해져
있었다: 노출은 역할과 무관하게 항상 하되(모델이 도구 존재 자체는 항상 알아야
"그런 기능이 없다"고 잘못 답하지 않는다), **실행은 `leader`만** 되고, `member`가
부르면 승인 카드 없이 곧바로 `ToolException`으로 거부됐다. 그때 "승인 카드를
띄우면 부른 사람 본인이 눌러 승인해 버릴 수 있어 권한 경계가 뚫린다"는 게
이유였다.

이번 요청은 그 판단을 뒤집는 것이 아니라 **전제를 다시 확인한 것**이다: 애초에
`leader`도 "자기 요청을 자기가 승인"하는 구조였다(HITL은 self-approval-only —
[[2026-08-19_05_HITL_resume_구현_완료]] 참고, 팀장이 팀원의 요청을 승인하는
교차 역할 라우팅은 원래부터 없다). 그렇다면 "본인이 눌러 승인한다"는 게
`member`에게만 위험하고 `leader`에게는 괜찮은 이유가 없다 — 둘 다 승인 대기를
거치면 "즉시 거부"보다 안전하지 않을 이유가 없고, 오히려 팀원이 자기 업무를 직접
등록하지 못해 매번 팀장에게 대신 시켜야 하는 쪽이 더 큰 실무 불편이었다.

## 확인한 범위

`is_tool_allowed_for_role(side_effect: bool, account_role)`은 도구별이 아니라
"부수효과가 있으면 전부" 한 스위치로 판단한다. 지금 `side_effect=True`인 도구는
`task_register`, `task_update`, `jira_create_issues`, 그리고 팀이 연결한 MCP
쓰기 도구 전부(개수는 팀마다 다름) — 넷 다 이번 변경의 영향을 받는다. 사용자에게
"task_register만 열까, 부수효과 도구 전부를 열까"를 확인했고 **전부 여는 쪽**을
선택받았다 — 도구별로 나누려면 이 함수 시그니처 자체(`side_effect: bool` →
도구 참조를 받는 구조)를 바꿔야 해서 지금 요청보다 범위가 컸다.

## 수정

**`services/agent_runtime/runtime_policy.py`**:
`DEFAULT_WRITE_TOOL_ALLOWED_ROLES`를 `frozenset({"leader"})`에서
`frozenset({"leader", "member"})`로 바꿨다. `is_tool_allowed_for_role()`
자체(부수효과 없으면 항상 허용, 있으면 `write_tool_allowed_roles`로 판단)는
안 바꿨다 — 값만 바뀐 것이지 메커니즘을 새로 만들지 않았다.

**`services/agent_runtime/factory.py`**: 코드는 안 바꿨다 — `build()`가
`interrupt_on`을 만드는 자리가 실행 허용 판단과 **같은 함수**
(`is_tool_allowed_for_role()`)를 이미 쓰고 있어서, 정책 값 하나만 바뀌어도 두
경로가 동시에 정확히 맞물린다:

1. `_to_langchain_tool()`의 `_run()` — `member`의 실행이 더는 `ToolException`
   으로 막히지 않는다.
2. `build()`의 `interrupt_on` 구성 — `member`가 실행 허용 대상에 들어오는
   순간, 그 도구가 `member`의 `interrupt_on`에도 자동으로 포함된다.

**결과**: `member`가 `task_register`(등)를 부르면 `HumanInTheLoopMiddleware`가
실행 직전에 멈추고 "등록할까요?" 확인 카드를 띄운다 — `leader`가 원래 겪던
것과 완전히 같은 자기 승인(self-approval) 경로다. 승인 버튼을 눌러야 실제
`task.handler()`가 실행된다. 주석만 갱신했다(예전 "member는 위 `_run()`에서
바로 거부되므로 승인 카드가 뜰 이유가 없다"는 문장이 이제 틀린 설명이라
`factory.py`/`runtime_policy.py`/`tools/adapters.py`의 관련 주석·docstring을
전부 다시 썼다).

여전히 남겨 둔 것: `write_tool_allowed_roles`를 배포 시점에 좁힐 수 있는 구조
자체(`RuntimeCapabilityPolicy(write_tool_allowed_roles=frozenset({"leader"}))`)
는 지우지 않았다 — 기본값이 열렸을 뿐 역할 검사 코드 자체가 없어진 게
아니다(테스트로 회귀 확인).

## 문서 갱신

이 파일 외에, [[2026-08-19_도구_실행_안정화와_권한_정책_작업기록]] §8은 **그
날짜 시점의 결정을 그대로 둔다**(역사적 기록이라 고치지 않는다) — 대신 이
문서가 그 결정이 오늘 다시 바뀌었다는 걸 남긴다. `docs/설계 및 구현/중간발표 이전/설계/
역할별_권한_정책.md`는 이번 변경과 다른 권한 계층(HTTP API 수준의
`require_leader` 가드 — 초대·팀 명부·업무량 기준 등)을 다루는 문서라 손대지
않았다 — 이번 변경은 챗 에이전트의 도구 실행 RBAC(`services.agent_runtime`)
쪽이다.

## 남은 것

- 팀원 계정으로 실제 로그인해 "회의록 정리 업무를 이번 주 금요일 마감으로
  등록해줘" 같은 요청을 보내 확인 카드가 뜨고, 승인 버튼을 눌러야 실제 등록이
  되는지 실측 확인 필요(단위 테스트는 `_to_langchain_tool()`/`build()`
  수준까지만 확인했고, 실제 그래프 실행·스트림·화면까지는 이번 변경 범위에서
  손대지 않았다 — 다만 그 경로 자체는 `leader`가 이미 매일 쓰던 것과 동일한
  코드라 별도 배선이 필요 없다).
- `task_register`에 아직 담당자(assignee) 필드가 없다(2026-08-19 계측 작업
  때 이미 확인, 사용자가 "지금은 날짜만 고치고 담당자는 나중에"로 명시적으로
  미룸) — 그래서 지금은 팀원이 "내 담당으로" 등록해도 그 소유권이 데이터에
  남지 않는다. 이번 변경은 "누가 등록할 수 있는가"(RBAC)만 다루고, "등록된
  업무가 누구 것인가"(assignee)는 별도 결정이 필요하다.
