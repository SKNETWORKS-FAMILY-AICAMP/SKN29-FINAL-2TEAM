# 2026-08-21_02 — MCP 쓰기 승인 범위 변경 반영

## 1. 이 문서의 결론

`17e8c62`가 `DEFAULT_WRITE_TOOL_ALLOWED_ROLES`를 `{leader}`에서
`{leader, member}`로 넓혔다. `2026-08-20_02_에이전트_병렬실행_설계.md`
§3.2가 "MCP 호출은 팀장 권한과 HITL 승인을 거친다"고 적은 문장은 이제
사실과 다르다.

1. 문서2 §3.2의 해당 문장을 "팀장 권한"이 아니라 "승인 허용 역할
   (`write_tool_allowed_roles`, 현재 leader+member)과 HITL 승인"으로
   고친다 — 완료.
2. 문서2 §11의 Phase 순서를 바꾼다 — **Phase 3(병렬 HITL, 호출별 승인)을
   Phase 2(쓰기 직렬화)보다 먼저 하는 것으로 앞당긴다.** 자기 승인 가능한
   대상이 leader 전용에서 팀 전체로 넓어진 만큼, "카드 하나로 몰아
   승인"의 위험이 커졌다고 판단했다(2026-08-21 사용자 판단, 아래 §3의
   2번 안 채택). §5에 반영.
3. 승인자를 요청자 본인이 아닌 제3자로 강제할지는 이 문서에서 결정하지
   않는다 — 제품 정책 판단이 필요해 별도 결정 사항으로 남긴다.

## 2. 무엇이 바뀌었나

`runtime_policy.py`의 변경 커밋 주석이 이전 상태를 이렇게 기록하고 있다.

> 그때는 실행 시점 재검사(`_run()`)가 유일한 방어선이라, member는 도구를
> 실행하려 하면 곧바로 `ToolException`(권한 없음)으로 막혔다(`interrupt_on`
> 도 같이 안 걸었다 — 승인 카드를 띄우면 부른 사람 본인이 눌러 승인해
> 버릴 수 있어서, 승인 대기 없는 즉시 거부가 그 시점의 유일한 경계였다).

즉 원래 설계는 **"자기 요청을 자기가 승인하는 구조는 member에게는 안전하지
않다"** 고 보고, member에게는 승인 카드조차 보여주지 않고 곧바로 거부했다.
2026-08-20에 이 판단이 바뀌었다 — "팀원이 자기 업무를 직접 등록할 수 있게
하고 싶다"는 요구를 받아, member도 side-effect 도구를 부를 수 있게 열고,
그 대가로 leader가 이미 해오던 것과 같은 자기 승인(HITL 확인 카드) 구조를
그대로 적용했다.

```text
이전: leader → 자기 승인으로 실행 가능
      member → 시도 자체가 즉시 거부 (승인 카드 없음)

지금: leader → 자기 승인으로 실행 가능
      member → 자기 승인으로 실행 가능 (leader와 동일 경로)
```

방어선이 사라진 게 아니라 "역할이 아니면 거부"에서 "역할과 무관하게 실행
전에 스스로 승인"으로 옮겨간 것이라는 게 그 변경의 판단이다.

## 3. 왜 문서2에 영향을 주는가

문서2 §3.3은 이미 다음을 지적했다.

> 현재 Chat API는 한 카드의 모든 호출에 같은 승인 또는 거절을 적용한다.
> 첫 호출의 목록 항목만 부분 선택할 수 있고, 호출별 승인·거절은 할 수 없다.

이 문제는 승인 카드를 누르는 사람이 자기 자신일 때 특히 크다 — 다른
사람이 두 번째로 검토하는 게 아니라, 본인이 "여러 개를 한 번에 승인"
버튼을 누르면 그대로 실행된다. 변경 전에는 이 경로를 쓸 수 있는 사람이
leader뿐이었지만, 지금은 팀의 모든 member가 쓸 수 있다. 병렬 side-effect
호출을 한 번에 여러 개 만들고 실수로 통째 승인해 버릴 수 있는 대상 범위가
넓어졌다는 뜻이다.

문서2 §11 구현 순서는 원래 이 문제(구 Phase 3 — 병렬 HITL, action별
결정)를 쓰기 직렬화(구 Phase 2) 다음으로 두고 있었다. 검토 과정에서
고려한 대안은 두 가지였다.

1. 호출별 승인 기능 자체를 앞당긴다 — 근본 해결책을 먼저 만든다.
2. 기능은 원래 순서대로 두고, 그 전까지 카드 하나에 side-effect 호출이
   일정 개수를 넘으면 통째 승인 버튼을 막는 임시 상한만 먼저 넣는다.

**1번으로 결정했다.** 임시 상한(2번)은 나중에 결국 1번도 다시 만들어야
해서 작업이 두 번 드는 데다, 지금 이 문제의 본질이 "승인 UI/API가
호출 단위가 아니다"라는 구조적인 것이라 임시방편보다 구조를 먼저 고치는
쪽을 택했다. §5에 반영.

## 4. 남는 질문 — 이 문서가 답하지 않는 것

승인자를 요청자 본인이 아닌 다른 사람(예: 팀장)으로 강제해야 하는
경우가 있는지는 순수한 실행 안정성/동시성 설계 범위를 벗어난다. 이건
"자기 승인을 허용할지"에 대한 제품 정책 재판단이 필요한 질문이라, 이
문서에서 결정하지 않고 열어 둔다. 지금 판단은 "이미 그렇게 정해졌다"는
사실을 반영하고, 그 사실이 문서2의 우선순위 판단에 미치는 영향만
정리한다.

## 5. 문서2에 반영한 구체적 수정 — 완료

`2026-08-20_02_에이전트_병렬실행_설계.md`에 다음 두 가지를 실제로 반영했다.

**§3.2 문장 교체**

```diff
- 따라서 MCP 호출은 팀장 권한과 HITL 승인을 거친다.
+ 따라서 MCP 호출은 승인 허용 역할(`write_tool_allowed_roles`, 2026-08-20부터
+ leader+member)과 HITL 승인을 거친다. 승인자는 요청자 본인이 될 수 있다
+ (`is_tool_allowed_for_role()` — `2026-08-21_02` 참고).
```

**§11 구현 순서 — Phase 2/3 교체**

```diff
- Phase 2 — 쓰기 직렬화
- Phase 3 — 병렬 HITL
+ Phase 2 — 병렬 HITL (자기 승인 대상 확대에 따라 앞당김, 2026-08-21)
+ Phase 3 — 쓰기 직렬화
```

새 Phase 2의 검증 항목 중 "승인된 side-effect 호출이 쓰기 정책에 따라
직렬화되는지 확인"은, 이 시점엔 Phase 3(쓰기 직렬화)이 아직 없으므로
새 Phase 3으로 넘겨 그때 다시 검증하는 것으로 조정했다.
