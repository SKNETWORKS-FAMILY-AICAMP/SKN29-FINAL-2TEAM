> 2026-08-11 작성. 8/11 팀 논의(A안 비효율 지적 — "긴 문서는 짧은 요약으로 못
> 찾는다")를 받아 업계 조사 후 절충안(A′)을 정리한 문서. **아직 결정 아님 —
> 회의 안건.** 확정되면 아키 §5를 이 문서 기준으로 갱신한다.

## 1. 선택지 정의

| | 방식 | 비용이 드는 곳 |
|---|---|---|
| **A** | 폴더 지정 시 메타데이터+**요약**만 등록 → 사용 시 해당 문서만 풀 처리 | 요약 LLM 1회(원 단위)+임베딩 1개. GPU는 사용분만 |
| **B** | 폴더의 **모든 문서**를 즉시 풀 파이프라인(Docling GPU 파싱·OCR·청킹·청크 임베딩) | 문서당 GPU 수십 초~수 분 × 전체 문서 수 |
| **A′** | A + **추출한 원문 텍스트를 전문(full-text) 인덱스에 전량 저장** — coarse 검색을 "요약 임베딩+본문 키워드 검색" 하이브리드로 | A와 거의 같음 (tsvector는 이미 쓰는 Postgres 기능, CPU) |

## 2. 리소스 비교 (8/11 산정)

- 문서 1건당: B가 A의 **수십 배** (GPU 파싱·OCR + 문서당 청크 30~40개 임베딩
  vs CPU 추출+요약 1회+임베딩 1개. 실측: chunk 456개 ≈ 문서 십수 건 분량).
- 총량: B는 **안 쓸 문서에도** 전액 지불. A는 사용된 문서에만 풀 비용(캐시
  유지). 사용률 10~30% 가정 시 A가 3~10배 이상 저렴. 사용률 100%여도 A의
  추가 비용은 요약분(전체의 몇 %)뿐 — **A의 최악 ≈ B의 평상시.**
- 운영: 워커 max 1이라 B는 폴더 연결 순간 수백 건 큐 → 몇 시간 온보딩.
  B가 이기는 유일한 축은 사용 시점 지연 0인데, 우리는 첫 파싱을 진행 카드
  ("문서를 읽는 중")에 흡수하므로 상쇄됨.

## 3. 업계는 어떻게 하나 (8/11 조사)

세 갈래가 다 실존한다:

1. **전량 사전 인덱싱** — OpenAI File Search(업로드 시 자동 파싱·청킹·임베딩),
   Dify·watsonx Knowledge, M365 Copilot(테넌트 전체 Semantic Index). 업계
   기본값. **단 이들의 인제스천은 CPU 텍스트+임베딩 API라 문서당 비용이 싸다**
   — 우리 B가 비싼 건 전량이라서가 아니라 GPU Docling·OCR이라는 무거운 전처리
   때문.
2. **요약 기반 계층 검색** — LlamaIndex Document Summary Index가 A안과 동일
   패턴(요약으로 문서 찾고 → 청크로 내려감). 공인된 설계다.
3. **인덱스 없음·온디맨드 탐색** — Claude Code는 임베딩 없이 grep+파일 열기.
   "인덱스 유지비 vs 질의 시 비용" 논쟁이 현재진행형인 실제 제품 방식.

출처: OpenAI File Search·Retrieval 문서, LlamaIndex Document Summary Index
블로그, MS Learn Semantic Index for Copilot, Claude Code 무인덱스 분석 글들
(0_참고링크는 커밋 메시지 대신 이 문서 하단).

## 4. 팀 반론과 수용

**반론(8/11 팀원)**: "내용이 길면 짧은 요약으로는 찾기 힘들다" — **타당하다.**
100페이지 RFP의 세부 키워드(특정 기술명·조항)는 몇 줄 요약에 안 담기고,
요약 임베딩만으로는 coarse에서 누락된다. M365가 시맨틱 인덱스와 별개로 전문
인덱스를 유지하는 이유가 정확히 이것.

**수용 방식(A′)**: 요약을 만들려면 어차피 가벼운 텍스트 추출을 한다. 그
추출 텍스트를 버리지 않고 Postgres 전문 검색(tsvector)에 넣으면 — 본문
어디에 있는 키워드든 걸린다. 비싼 GPU 정밀 처리(표 구조 보존 청킹·청크
임베딩)만 온디맨드로 남긴다.

> **A vs B는 거짓 이분법이었다. 정확한 분해는 "가벼운 인덱싱(추출 텍스트
> 전문 검색+요약 임베딩)은 전량, 비싼 처리(GPU 정밀)는 온디맨드".**

## 5. A′ 상세 — 어떻게 동작하나

**등록 시 (폴더 지정하면 자동, 문서당 CPU 몇 초 + LLM 요약 1회)**

```
Drive 메타(파일명·경로·수정일)
 + 가벼운 텍스트 추출 (PDF 텍스트 레이어, CPU)
 → ① 추출 텍스트 → doc_fulltext (tsvector 전문 인덱스)
 → ② LLM 요약·주제·유형 → doc_meta + 요약 임베딩 1개
```

**사용 시**

```
질의 → coarse: 전문 검색(BM25/tsvector) + 요약 임베딩 유사도 (하이브리드 랭킹)
     → 후보 상위 k 중 미처리 문서만 GPU 풀 파이프라인 (진행 카드 "문서를 읽는 중")
     → 적재는 캐시로 유지 (재사용 시 즉시)
     → fine: 청크 벡터 검색 → 문단 단위 근거 발췌 (E1~E20 품질 그대로)
```

- hwp·스캔본: 텍스트 추출 실패 시 전문 인덱스에도 못 들어감 → 상태 "실패"
  표기(화면 반영 완료), OCR은 온디맨드 처리 시점에 GPU에서.
- 평가: coarse 누락 리스크는 **문서 단위 Recall(coarse)** 지표로 검증
  (4_평가 §2 반영 완료). 전문 검색 추가로 이 지표가 A 대비 오를 것으로 기대.

## 6. 상태 — **폐기됨. 2026-08-24 멘토링에서 B(전량 색인)로 갔다**

> ⚠ **이 문서의 선택지 비교는 끝난 논의다.** A 도 A′ 도 채택되지 않았다.
> 아래 8/11 결정은 그 시점의 기록으로 남겨 둔다.
>
> **8/24 멘토링 결론** — 「어떤 문서만 인덱싱할 것인가」로 문제를 바꾸지 말고
> **전체 인덱싱을 어떻게 빠르고 점진적으로 완료할 것인가**에 집중한다. 요약
> 기반 후보 검색은 보조 수단이지 전량 색인을 대신하는 주 경로가 아니다.
> 그 지적이 A 와 A′ 를 **둘 다** 탈락시킨다 — A′ 도 결국 coarse 를 주 경로로
> 두는 설계다.
>
> **그래서 요약 단계를 통째로 없앴다**(`2648a1a`). 폴더를 저장하면 그 문서
> 전부가 본문까지 색인되고(`_index_all`), 검색은 색인된 본문에서 직접 찾는다.
> `doc_meta` 테이블도 폐기했다(`2026-08-24_drop_doc_meta.sql`).
>
> **§4 의 반론은 실측으로 확인됐다.** 「긴 문서는 짧은 요약으로 못 찾는다」가
> 맞았다 — 한국어 RFP 실측에서 **본문의 13~16% 만** 요약에 들어갔다
> (`SUMMARY_INPUT_MAX_CHARS = 12000`, 실물 7~9만 자). 다만 해법은 A′ 가
> 아니라 전량 색인이었다.
>
> `coarse_recall` 검증은 **하지 않았고 이제 필요 없다.** 그 지표는 A 와 A′
> 중 고르기 위한 것이었는데 둘 다 폐기됐다.
