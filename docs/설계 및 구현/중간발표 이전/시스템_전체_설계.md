# 시스템 전체 설계

> **이 문서의 역할 — 정합성 기준.**
>
> 다른 문서와 어긋나면 **이 문서가 맞다.** 여기 적힌 것은 전부 코드에서 확인한
> 것이고, 다른 문서를 베끼지 않았다. 문서가 여러 개로 갈라지면서 없어진 화면을
> 근거로 컬럼을 설명하거나, 이미 구현된 것을 「미착수」로 적어 둔 문서가 생겼다
> (2026-08-05 전수 점검에서 12건). 그것을 막으려고 기준을 하나 둔다.
>
> **갱신 규칙**: 기능이 바뀌면 이 문서를 먼저 고치고, 다른 문서는 이 문서와
> 대조해서 고친다. 여기에 없는 세부는 각 설계 문서가 갖는다.
>
> 기준일: 2026-08-05

## 1. 이 시스템이 하는 일

팀의 Drive 문서에서 **새 프로젝트의 업무를 뽑고**, Jira에서 **팀의 현재 부하를
읽어**, 둘을 합쳐 누구에게 무엇을 맡길지 판단하도록 돕는다.

지금 완성된 것은 앞의 절반이다 — 문서에서 업무를 뽑아 사람이 확인하는 데까지.
뒤의 절반(업무 분배·추천)은 화면만 있고 로직이 없다(§8).

## 2. 구성요소

```
[브라우저]
   │
   ▼
[frontend]  React + Vite (Docker)
   │  HTTP/JSON
   ▼
[web]  Django 5.2 + DRF (Docker)
   │                    │                      │
   │ psycopg (raw SQL)  │ HTTPS                │ HTTPS
   ▼                    ▼                      ▼
[PostgreSQL 17      [RunPod Serverless]   [Google Drive]
 + pgvector]         파싱·청킹·임베딩       [Jira]
                          │                 [OpenAI]
                          │ 만료형 서명 URL로 원문 수신
                          └──────────▶ [web] /api/internal/runpod/...
```

**Django ORM을 쓰지 않는다.** `DATABASES = {}`이고 `backend/db/repositories.py`가
psycopg로 직접 SQL을 쓴다. 스키마는 `DB/schema.sql`이 정본이며 마이그레이션은
`DB/migrations/*.sql`에 멱등 스크립트로 둔다.

**RunPod Worker는 별도 저장소다.** `choiwon10/SKN29-RUNPOD-WORKER`의
`codex/install-triton-compiler` 브랜치가 실제로 도는 코드이고, 이 저장소의
`runpod_worker/`는 읽기용 사본이다. 워커를 고치면 그쪽에 푸시하고 RunPod
콘솔에서 빌드해야 반영된다.

**RunPod은 우리 DB에 접근하지 않는다.** 원문은 만료형 서명 URL로 받아 가고,
결과는 Django가 받아 적재한다. 사용자 OAuth 토큰이 파싱 쪽으로 넘어가면 그
토큰 하나로 그 사람의 Drive 전체를 읽을 수 있다.

## 3. 테넌트 경계 — 팀

우리 플랫폼을 쓰는 단위는 회사가 아니라 **회사 안의 팀**이다. 팀장이 온보딩에서
팀을 만들고(`team`), 초대로 팀원을 채운다(`team_member`, `user_account.team_id`).

무엇이 어디에 매달리는지가 이 시스템에서 가장 자주 틀리는 지점이다.

| 것 | 매달리는 곳 | 왜 |
|---|---|---|
| 커넥터 연결 `connector_conn` | 계정 | OAuth는 사람이 승인한다 |
| Drive 폴더 `team_folder` | **팀** | 폴더는 경로일 뿐이고 프로젝트를 만들지 않는다 |
| 문서 `doc` | **팀** | 등록 시점에는 어느 프로젝트의 것인지 모른다 |
| Jira 프로젝트 `proj_source` | 프로젝트 | 프로젝트 하나에 Jira 하나(1:1) |
| 기준 문서 `doc.proj_id` + `doc_role='PRIMARY'` | 프로젝트 | 프로젝트당 한 건. 부분 유니크 인덱스로 강제 |

권한 검사는 `_require_team`·`_require_team_project`가 한다. 소유자
(`proj.owner_account_id`) 검사가 아니라 팀 검사다 — 팀장이 등록한 문서를 팀원이
못 여는 것은 경계 정의와 어긋난다.

## 4. 흐름 1 — Drive 문서를 검색 가능하게 만든다

```
폴더 선택        team_folder                    (온보딩 / 설정)
   ↓
신규 파일 스캔    Drive API vs doc.src_file_id
   ↓
등록             doc 행 생성
   ↓ ─────────── 여기서 멈추지 않는다 ───────────
원문 수신        Drive → 문서 저장소(doc.storage_key)
   ↓
파싱·청킹·임베딩  RunPod Worker → doc_block / chunk / vec_idx
```

**등록은 검색 가능한 상태까지 간다.** 나누면 「등록은 됐는데 못 쓰는 문서」가
남고 그것을 사용자가 따로 관리해야 한다. 그래서 문서 관리 화면에 처리할 문서를
고르는 칸이 없다. 화면이 문서마다 순차로 진행하며 상태를 보여주고, 한 건이
실패해도 나머지는 계속한다.

**Drive에서 사라진 문서**는 자동으로 내리지 않는다. 휴지통·완전삭제·폴더 밖
이동이 전부 「안 잡힘」으로 똑같이 보여서, 잠깐 옮겨 둔 문서가 조용히 사라진다.
사람이 확인하면 `doc.deleted`를 켜고 **파싱 산출물은 실제로 지운다** —
`chunk.search_text`에 원문이 그대로 들어 있어 플래그만 세우면 원문이 남는다.
파일이 다시 나타나면 되살린다.

### 파싱 규칙

- **텍스트 레이어가 있는 PDF는 OCR을 돌리지 않는다.** 압축 스트림의 `Tj`/`TJ`
  연산자를 세어 판정한다. OCR이 멀쩡한 본문을 자모 단위로 덮어써서
  「중도탈락을」이 「중도달락올」로 적재되던 것을 고친 결과다. 스캔본은 EasyOCR
  (`ko`,`en`)로 읽는다.
- **표는 행·제품 단위로 다시 만든다.** 구조를 잃지 않기 위해서다.
- **한도를 넘는 청크**는 표가 걸렸으면 그것만 빼고 문서는 살린다. 표 한 줄
  때문에 본문 수백 블록을 잃지 않는다. 무엇을 뺐는지는 결과에 남는다. 표가 안
  걸렸는데 넘쳤으면 우리 청킹 문제라 실패시킨다.

## 5. 흐름 2 — Jira에서 팀의 현재 부하를 읽는다

```
Jira 프로젝트 선택  →  proj(ACTIVE) + proj_source (1:1)
       ↓ 갱신
   exist_task        이슈·담당자·상태·추정·잔여·마감
       ↓
   업무량 계산        services/workload/  →  대시보드
```

Jira에서 온 프로젝트는 **이미 진행 중인 것**이고, 업무를 새로 뽑을 대상이
아니라 팀원의 현재 부하를 재는 재료다. 그래서 프로젝트 상세에 「업무 분배」가
없다.

**이력이 없다.** `exist_task_snap`에 **적재하는** 코드가 없어서(프로젝트 삭제 시
정리하는 DELETE 하나뿐이다) 번다운·속도 같은 시간축 지표는 만들 수 없다. 대시보드가 「지금」과 「곧 닥칠 마감」만 보여주는 이유다.

## 6. 흐름 3 — 기준 문서에서 업무를 뽑는다

```
기준 문서 1건 선택  →  DRAFT 프로젝트 생성 + doc_role='PRIMARY'
        ↓
   1단계 TASK_DISCOVERY        기준 문서 안에서만
   2단계 TASK_CORE             팀 문서 전체
   3단계 ASSIGNMENT_REQUIREMENT      〃
   4단계 EXECUTION_CONDITION          〃
        ↓  근거 중복 제거 → 기준 문서 14 + 보조 6 = 20건
   5단계 정리                  업무 + 근거
        ↓
   1차 확인 화면
```

**사람이 고르는 것은 기준 문서 하나다.** 근거 문서는 에이전트가 찾는다 — 무엇이
어디 적혀 있는지 미리 알아야 고를 수 있는데, 그걸 대신 찾아 주는 것이 이 기능의
목적이라 순서가 거꾸로였다.

**검색 경계는 팀이다.** 프로젝트로 좁히면 방금 만든 DRAFT에 묶인 문서가 기준
문서 하나뿐이라 2~4단계가 1단계와 같아진다.

**질의는 문서의 어휘로 만든다.** 질의 생성 에이전트에 기준 문서의 첫머리(앞
12청크, 1,500자)를 함께 준다. 파일명만 주면 「사업 수행 범위에 포함된 업무
영역」 같은 일반 문장을 만들고, 그런 벡터는 실제 과업이 아니라 사업관리
보일러플레이트와 가장 가깝다. 문서 제목·파일명·날짜를 질의에 넣는 것은
금지한다 — 검색 대상이 그 문서인데 제목을 넣으면 변별력이 0이고 목차·표지가
대신 검색된다.

**근거 인용은 `E1`~`E20` 짧은 번호로 받는다.** 36자 UUID를 옮겨 적게 하면 하나만
틀려도 추출 전체가 실패한다. 모르는 번호는 그 업무에서만 떨어뜨리고, 근거가
하나도 확인되지 않은 업무는 만들지 않는다.

**모델은 단계마다 다르다.**

| 단계 | 모델 | effort |
|---|---|---|
| 검색어 생성 1~4 | `gpt-5.6-luna` | `low` |
| 정리 5 | `gpt-5.6-sol` | `xhigh` |

같은 프롬프트 실측에서 Luna 2.8초/192토큰, Sol 53.3초/4,883토큰이었고 Sol 쪽
질의 품질이 오히려 나빴다. 판단이 필요한 곳에만 추론을 쓴다.

**추출 응답은 NDJSON 스트림**이다. 몇 분이 걸리므로 단계·검색어·근거 수를 한
줄씩 내보낸다. 응답이 시작된 뒤의 실패는 마지막 줄의 `error`로 알린다.

## 9. 운영 제약

**RunPod 콜드 스타트.** 최소 워커 0에 유휴 타임아웃이 지나면 워커가 내려가고,
모델이 이미지에 구워져 있지 않아 다음 요청에서 수 GB를 다시 받는다. 시연 전에는
문서 하나를 미리 처리해 워커를 깨워 둔다. 워커 슬롯이 하나(max 1)라 그 하나가
물리면 엔드포인트 전체가 멈춘 것처럼 보인다 — 실제로 두 번 겪었고, 콘솔에서 그
워커를 종료하면 다른 호스트에 재배치된다.

**Cloudflare Quick Tunnel.** RunPod이 원문을 받아 갈 HTTPS 주소가 필요한데,
Quick Tunnel은 재실행할 때마다 주소가 바뀐다. 바뀌면 `.env`의
`PUBLIC_BACKEND_BASE_URL`과 `ALLOWED_HOSTS`를 고치고 **컨테이너를 재생성**해야
한다 — `docker compose restart`는 `env_file`을 다시 읽지 않는다.

**OpenAI 비용.** 검색어 생성을 Sol로 돌리면 한 번 추출에 그 단계만 $0.6가
나간다. `OPENAI_SERVICE_TIER=priority`는 요금이 2배다(기본 `auto`).

## 10. 확정된 결정과 이유

바꾸려면 여기 적힌 이유부터 반박해야 한다.

| 결정 | 이유 |
|---|---|
| 폴더·파일 역할 지정 제거 (2026-08-04) | 폴더 역할을 파일이 물려받아 「01_기획」에 든 것은 무엇이든 기획서가 됐고, 그 값으로 분기하는 코드는 없었다 |
| `doc_role` 재정의 → `NULL`/`PRIMARY` | 문서의 종류가 아니라 프로젝트와의 관계. `SUB`는 스키마에 남았지만 쓰지 않는다 — 같은 회의록이 여러 프로젝트의 근거일 수 있는데 `proj_id`는 하나만 가리킨다 |
| 검색 경계 = 팀 | 프로젝트로 좁히면 2~4단계가 1단계와 같아진다 |
| 등록이 임베딩까지 | 나누면 「등록은 됐는데 못 쓰는 문서」를 사용자가 관리해야 한다 |
| 사라진 문서는 사람이 확인 후 정리 | 자동으로 내리면 잠깐 옮겨 둔 문서가 조용히 사라진다 |
| 정리 시 파싱 산출물까지 삭제 | `chunk.search_text`에 원문이 그대로 있다 |
| 임베딩 768차원 고정 | `google/embeddinggemma-300m`. 청킹 토큰 계산도 같은 tokenizer |
| 근거 없는 값은 지어내지 않음 | `missing_fields`로 드러낸다. 추천의 근거가 무너진다 |
