## 0. 공통 구조

- 앱 위치: `apps/ops/`(Django, ORM 미사용 — `DB/schema.sql` 테이블을 Repository가 raw SQL로 직접 조회).
- 라우트 prefix: `/api/ops/`.
- 인증: `Authorization: Bearer <토큰>` 헤더. 토큰 유효기간은 2시간이며, 일반 로그인 토큰과는 서명 salt가 달라 서로 바꿔 쓸 수 없다.
- **운영자 인증이 필요한 API**(`/auth/me/`, `/auth/logout/`, `/overview/`, `/teams/`, `/accounts/...`, `/invites/...`, `/connectors/`, `/audit/...`, `/policies/...`)는 토큰 서명·만료 확인에 더해 **요청마다 DB를 다시 조회**해서 계정이 여전히 운영자(`is_admin = true`)이고 상태가 `ACTIVE`인지 재확인한다. 로그인 이후 운영자 권한이 회수되거나 계정이 잠기면, 유효기간이 남은 토큰이라도 다음 요청부터 즉시 차단된다.
- 운영자 권한 부여·회수는 **콘솔에서 한다**(`POST /api/ops/accounts/{account_id}/admin/`, 4.5절). 원래는 호스트에서 `grant_admin.py`를 돌려야만 바뀌었는데, 운영자가 하나도 없거나 담당이 바뀔 때마다 DB 앞에 앉을 사람이 필요해서 콘솔로 옮겼다(2026-08-13). **첫 운영자만 그 스크립트로 만든다** — 아무도 없는 상태에서는 콘솔에 들어갈 수 없기 때문이다. 안전장치는 4.5절에 있다(본인 강등 불가·마지막 운영자 보호).
- DB 조회·연결 실패는 인증 단계에서 발생하든 요청 처리 중 발생하든 관계없이 전부 `{"detail": "데이터베이스 요청을 처리할 수 없습니다."}` + `503`으로 통일해서 응답한다.
- 정의되지 않은 HTTP 메서드로 호출하면(예: 조회 전용 API에 `POST`) `405`와 `{"detail": "메서드 \"POST\"는 허용되지 않습니다."}`를 반환한다. 정의되지 않은 쿼리 파라미터는 조용히 무시된다.

## 1. 섹션 1 — 운영자 로그인

### 1.1 `POST /api/ops/auth/login/`

요청 바디: `{"email": string, "password": string}`

| # | 입력·상황 | HTTP | 응답 `detail` | 비고 |
|---|---|---|---|---|
| 1 | `email` 필드 누락 | 400 | `{"email": ["이 필드는 필수 항목입니다."]}` | |
| 2 | `password` 필드 누락 | 400 | `{"password": ["이 필드는 필수 항목입니다."]}` | |
| 3 | 이메일 형식이 아님 | 400 | `{"email": ["유효한 이메일 주소를 입력하세요."]}` | |
| 4 | 빈 JSON(`{}`) | 400 | 두 필드 오류를 함께 반환 | |
| 5 | JSON 자체가 깨짐 | 400 | `{"detail": "JSON parse error - ..."}` | 파서가 만드는 진단 메시지라 영어로 나온다 |
| 6 | 가입되지 않은 이메일 | 401 | `이메일 또는 비밀번호가 올바르지 않습니다.` | 계정 존재 여부를 노출하지 않으려고 비밀번호 오류와 문구를 통일 |
| 7 | 비밀번호 불일치 | 401 | `이메일 또는 비밀번호가 올바르지 않습니다.` | |
| 8 | 가입은 됐지만 `is_admin = false` | 403 | `운영자 권한이 없는 계정입니다.` | 비밀번호까지 맞아야 이 문구가 나오므로, 다른 이메일의 운영자 여부는 알 수 없음 |
| 9 | 계정 상태 `LOCKED` | 403 | `사용할 수 없는 계정입니다. 운영자에게 문의해 주세요.` | 운영자 여부 확인보다 먼저 체크 |
| 10 | 계정 상태 `WITHDRAWN` | 403 | 〃 | |
| 11 | 이메일·비밀번호·`is_admin=true`·`ACTIVE` 모두 정상 | 200 | `{"token": "...", "admin": {"account_id","email","display_name"}}` | 로그인 시각 기록 + 감사 로그에 `OPS_LOGIN` 기록 |
| 12 | 로그인 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` | |

## 2. 섹션 2 — 운영 현황

### 2.1 `GET /api/ops/overview/`

읽기 전용, 입력값 없음. 인증 실패 응답은 1.2절과 동일하다.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰 | 200 | 아래 2.2절 응답 구조 |
| 10 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

### 2.2 응답 구조

```json
{
  "team_count": 1,
  "org_count": 9,
  "accounts": { "total": 2, "locked": 0, "duplicate_mapping": 0, "needs_review": 0 },
  "connectors": { "total": 0, "connected": 0, "expired": 0, "error": 0 },
  "invites": { "pending": 0, "expiring_today": 0 },
  "recent_activity": [
    { "audit_id": "AL012", "action": "OPS_LOGIN", "target_type": null, "target_id": null,
      "occurred_at": "2026-07-30T06:13:13.577244Z", "actor_display_name": "관리자", "actor_email": "rhksflwk@halil.com" }
  ]
}
```

각 필드의 산출 방식:

| 필드 | 산출 방식 |
|---|---|
| `team_count` | 만들어진 팀 수. 운영 현황 카드 `사용 중인 팀`이 이 값을 쓰고, 누르면 팀 현황(3절)으로 간다 |
| `org_count` | 활성 상태(`status='ACTIVE'`)인 HR 조직 수. 화면에는 쓰지 않고 응답에만 남아 있다 |
| `accounts.total` | 전체 계정 수 |
| `accounts.locked` | 그중 상태가 `LOCKED`인 계정 수 |
| `accounts.duplicate_mapping` | 유효한(`VERIFIED`) 직원 연결이 2개 이상인 계정 수(계정 1개가 여러 직원에 연결되는 것을 스키마가 막지 않음) |
| `accounts.needs_review` | `locked`이거나 `duplicate_mapping`인 계정의 합(중복 집계 없이) |
| `connectors.*` | 연결 서비스 상태(`CONNECTED`/`EXPIRED`/`ERROR`)별 건수 |
| `invites.pending` | 아직 만료되지 않은 대기 중 초대 수 |
| `invites.expiring_today` | 그중 오늘 만료 예정인 수 |
| `recent_activity` | 최근 감사 로그 5건(수행자 이름·이메일 포함) |

"오늘 확인할 일" 카드는 `accounts.needs_review`, `connectors.expired + connectors.error`, `invites.expiring_today` 값이 각각 0보다 클 때만 하나씩 생성되고, 셋 다 0이면 "확인이 필요한 항목이 없습니다."를 표시한다. 카드에는 건수와 이동 링크만 있고 조직명·직원 ID 같은 세부 항목은 포함하지 않는다.

계정·연결 서비스 총합이 0일 때는 비율 계산에서 0으로 나누지 않도록 처리해 그래프가 항상 0%로 표시되며, `accounts.total`/`connectors.total`이 0이면 막대그래프 대신 "등록된 계정이 없습니다."/"연결된 서비스가 없습니다." 문구를 보여준다.

## 3. 섹션 3 — 팀 현황

> **2026-07-31 교체.** 이 자리에는 `연결 조직 현황`(`GET /api/ops/organizations/`, 조직 트리)이 있었으나 삭제됐다. 우리 플랫폼을 쓰는 단위가 회사가 아니라 **회사 안의 팀**으로 확정되면서(팀은 팀장이 온보딩에서 팀명을 적어 직접 만든다 — [[HR_어댑터와_테넌트_경계]]), 조직도는 고객사 HR 내부 사정이 되어 운영자가 열람할 자리가 아니게 됐다.

### 3.1 `GET /api/ops/teams/`

읽기 전용, 입력값 없음. 인증 실패 응답은 1.2절과 동일하다.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰, 팀이 1개 이상 존재 | 200 | 아래 3.2절 응답 구조 |
| 10 | 정상 토큰, 팀이 0개 | 200 | 빈 배열(`[]`) — 오류가 아니라 정상적인 빈 목록으로 처리 |
| 11 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

운영자에게는 **팀 생성 API가 없다.** 팀은 팀장이 온보딩에서 만든다(원칙 3 — 운영자는 원본 데이터를 만들지 않는다). 다만 오래 조회 전용이었던 이 섹션에 3.5·3.6이 붙었다 — **팀장이 나가면 그 팀을 아무도 손댈 수 없었고**, 「에이전트가 이상해요」라는 문의에 운영자가 볼 것이 하나도 없었다(2026-08-13). 만드는 것과 이미 있는 것을 고치는 것은 다른 권한이다.

### 3.2 응답 구조

```json
[
  {
    "team_id": "TE001", "name": "개발팀",
    "owner_account_id": "AC001", "owner_email": "lead@example.com",
    "owner_display_name": "홍길동",
    "src_org_id": "A002", "src_org_name": "개발팀",
    "member_count": 5, "account_count": 3, "unregistered_count": 2,
    "locked_count": 0, "pending_invite_count": 1,
    "created_at": "2026-07-31T09:12:44+09:00"
  }
]
```

각 필드의 산출 방식:

| 필드 | 산출 방식 |
|---|---|
| `team_id`/`name`/`owner_account_id`/`src_org_id`/`created_at` | `team` 원본 정보. 최근 생성 순으로 정렬한다 |
| `owner_email`/`owner_display_name` | 팀장 계정(`user_account`) 정보. 계정이 지워졌으면 `null` |
| `src_org_name` | 팀을 만들 때 팀장이 속해 있던 HR 조직의 이름. **참고 표시일 뿐 팀 경계가 아니다** — 경계는 `team_member` 명단이다. HR 어댑터(`hr.lookup_orgs`)로 조회하므로 조직이 없으면 `null` |
| `member_count` | `team_member` 행 수 — 팀에 담긴 사람(PERSON) 수 |
| `account_count` | `user_account.team_id`가 이 팀인 계정 수 — 실제로 가입까지 마친 수 |
| `unregistered_count` | `member_count - account_count`(음수면 0). 팀원인데 아직 계정을 안 만든 사람이다 |
| `locked_count` | 이 팀 계정 중 `account_status='LOCKED'`인 수 |
| `pending_invite_count` | 이 팀의 초대 중 `status='PENDING'`이면서 아직 만료되지 않은(`expires_at > now()`) 수 |

`member_count`는 조직도 인원이 아니라 **팀장이 고른 명단**이다. 그래서 이전 `연결 조직 현황`의 `total_member_count`(하위 조직까지 재귀 집계)에 해당하는 값이 없다 — 팀은 계층이 아니라 평면 명단이다.

HR(팀장·조직 이름)은 어댑터로, 플랫폼(팀·계정·초대)은 SQL로 읽어 파이썬에서 합친다. 두 계층을 조인하지 않는 이유는 [[HR_어댑터와_테넌트_경계]]에 있다. 조인이 없으므로 HR 쪽 데이터가 없어도 이름만 `null`이 되고 목록 조회는 정상 동작한다.

### 3.3 화면 처리

행을 클릭하면 `/ops/accounts?team=<team_id>`로 이동해 **그 팀의 계정만** 필터링해서 보여준다. 팀에서 계정으로 내려가는 동선이라 두 화면이 같은 목록을 중복해서 갖지 않는다. 필터가 화면 상태가 아니라 URL 쿼리에 있어서 링크를 그대로 공유할 수 있다.

- `상태`는 `locked_count > 0` 또는 `unregistered_count > 0`이면 `확인 필요`, 아니면 `정상`이다. 후자를 포함시킨 이유는 "초대가 안 갔거나 초대 코드가 방치된" 상태가 운영자가 볼 이유가 되기 때문이다.
- 검색은 팀 이름·팀장 이메일·출처 조직 이름을 대상으로 한다. **팀 번호로는 검색하지 않는다** — 화면에 번호를 표시하지 않으므로 사용자가 입력할 수 없는 값이다.
- 팀이 하나도 없으면 "아직 만들어진 팀이 없습니다."와 함께 "팀은 팀장이 온보딩에서 직접 만듭니다"라는 안내를 띄운다. 검색 결과만 없으면 "조건에 맞는 팀이 없습니다."로 구분한다.
- 상단 요약에 팀 수·가입 계정 합계·확인 필요 팀 수를 보여준다. 확인 필요가 0이면 "확인 필요 없음"으로 표시한다.
- 조회에 실패하면 오류 메시지와 "다시 시도" 버튼을 보여주고, 인증이 만료된 경우(401)에는 운영자 로그인 화면으로 이동시킨다.

### 3.4 화면에 내부 식별자를 표시하지 않는다 (전 섹션 공통)

같은 날 콘솔 전 화면에서 고유 번호(`account_id`·`person_id`·`org_id`·`conn_id`·`invite_id`·`snapshot_id` 등)를 **표시에서** 뺐다. 운영자가 판단에 쓰는 값이 아니고, 고객사 직원 번호를 노출할 이유도 없다.

| 화면 | 전 | 후 |
|---|---|---|
| 계정 관리 | `직원 ID` 열 | `연결된 직원`(이름) · `팀` · `HR 조직` 3열 |
| 계정 연결·초대 | `초대 기록 ID` + `직원 ID` 2열 | `초대받은 직원`(이름) 1열 |
| 계정 연결·초대 상세 | `연결된 계정 AC001` | `연결된 계정 <이메일>` |
| 연결 서비스 | `연결 번호` 열 | 삭제 |
| 감사 로그 상세 | 대상 ID·스냅샷 ID 문구 | 삭제 |

**API 응답과 라우팅에는 식별자가 그대로 남는다.** 화면 이동(`?team=`), 행 선택(`key`), 상태 변경 요청이 전부 식별자를 쓰기 때문이다. 바뀐 것은 사람이 읽는 자리뿐이다. 검색 대상에서도 빠졌다 — 보이지 않는 값으로는 검색할 수 없어야 앞뒤가 맞는다.

### 3.5 `GET /api/ops/teams/{team_id}/content/`

이 팀이 들고 있는 것과 실제로 있었던 일. 입력값 없음.

응답은 `{"agents": [...], "runs": [...]}` 두 갈래다. `agents`는 팀이 만든 에이전트의 이름·상태·모델·도구·지시문, `runs`는 최근 50건의 실행(상태·반복 수·토큰·도구 호출 수·**실패한 도구와 그 사유**)이다.

**경계가 있다.** 대화 내용과 문서 원문은 주지 않는다 — 그건 고객의 업무 내용이고 열람을 통제할 장치가 아직 없다. 실행 기록은 애초에 내용을 안 담게 설계돼 있어(`tool_call.input_summary`가 원본 인자가 아니라 요약을 남긴다) 그 경계를 이미 지킨다. 지시문은 예외적으로 준다 — 답이 근거 없이 나온다는 문의는 대개 거기서 갈리기 때문이다.

**우리가 넣은 것(`is_prebuilt`)은 양쪽 모두에서 빠진다.** 팀 화면도 그것을 걸러 보여주므로, 섞어 주면 고객은 존재도 모르는 줄을 운영자만 보게 된다. 그 대신 채팅에서 난 일은 이 표에 안 남는다.

### 3.6 `GET`/`POST /api/ops/teams/{team_id}/owner/`

`GET`은 넘길 수 있는 후보를, `POST`는 이전을 수행한다. `POST` 본문은 `account_id`(필수)와 `reason`(선택).

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하지 않는 `team_id` | 404 | `존재하지 않는 팀입니다: {team_id}` |
| 10 | 그 팀 소속이 아닌 계정으로 이전 | 403 | `이 팀에 속한 계정에게만 넘길 수 있습니다.` — 테넌트 경계가 그 자리에서 무너진다 |
| 11 | 이미 그 팀의 소유자 | 400 | `이미 이 계정이 소유자입니다.` |
| 12 | 정상 처리 | 200 | `{"team_id": "...", "owner_account_id": "...", "moved_models": N}` — 감사 로그(`OPS_TEAM_OWNER_TRANSFER`) |

**후보는 그 팀의 살아 있는 계정만이다.** 계정 전체에서 고르게 하면 남의 팀 사람을 고를 수 있고, 서버가 거절하더라도 고를 수 있게 보여 주는 것 자체가 잘못된 안내다. 소속 검사는 화면이 아니라 트랜잭션 안에서 한다.

**그 팀에 등록된 모델도 함께 옮긴다**(`moved_models`). `connector_conn`에는 팀 칸이 없고 모델은 `team.owner_account_id`에 매달려 있어서, 소유자만 바꾸면 등록 모델이 떠난 사람에게 남는다.

## 4. 섹션 4 — 계정 관리

### 4.1 `GET /api/ops/accounts/`

읽기 전용, 입력값 없음. 인증 실패·DB 연결 실패 응답은 1.2절·3.1절과 동일하다.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰 | 200 | 아래 4.5절 응답 구조 |
| 10 | 계정이 0개(이론상 불가하지만) | 200 | 빈 배열(`[]`) |
| 11 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

### 4.1-2 `GET /api/ops/accounts/{account_id}/`

계정 한 건. 상세가 별도 페이지가 되면서 생긴 경로다(주소로 바로 들어올 수 있어야 한다). 목록과 **같은 SQL**을 쓴다 — 상세용 쿼리를 따로 쓰면 중복 연결 판정 같은 계산이 두 벌이 되고, 언젠가 한쪽만 고쳐져 목록과 상세가 다른 말을 한다.

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하는 `account_id` | 200 | 4.5절 응답 구조에서 객체 하나 |
| 10 | 존재하지 않는 `account_id` | 404 | `존재하지 않는 계정입니다: {account_id}` |
| 11 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

### 4.2 `POST /api/ops/accounts/{account_id}/lock/`, `POST /api/ops/accounts/{account_id}/unlock/`

본문은 `reason`(선택, 빈 문자열 허용) 하나. 대상은 URL의 `account_id`다. 사유는 감사 로그 payload에 함께 들어간다 — 무엇을 했는지는 로그가 이미 남기지만 **왜 했는지는 그때 그 사람 머릿속에만 있다**(2026-08-13에 넓혔다). 본문을 안 보내도 빈 사유로 통과한다 — 급할 때 사유 때문에 조치를 못 하면 그게 더 나쁘다.

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하지 않는 `account_id` | 404 | `존재하지 않는 계정입니다: {account_id}` |
| 10 | 대상 계정 상태가 `WITHDRAWN` | 400 | `탈퇴한 계정은 상태를 변경할 수 없습니다.` |
| 11 | `lock`을 자기 자신의 계정에 호출 | 403 | `본인 계정은 잠글 수 없습니다.` |
| 12 | 이미 목표 상태와 같음(예: `ACTIVE`인데 `unlock` 호출) | 400 | `이미 처리된 상태입니다.` |
| 13 | 정상 처리 | 200 | `{"account_id": "...", "account_status": "LOCKED"/"ACTIVE"}` — 변경 전/후 상태를 감사 로그(`ACCOUNT_LOCK`/`ACCOUNT_UNLOCK`)에 함께 기록 |
| 14 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

동시에 들어온 잠금/해제 요청이 서로 낡은 상태를 덮어쓰지 않도록, 대상 계정 행을 잠근(`SELECT ... FOR UPDATE`) 상태에서 상태를 확인·변경한다 — 같은 계정에 대한 `lock` 요청 두 개가 동시에 들어와도 하나만 적용되고 나머지는 `이미 처리된 상태입니다`(400)로 정리되며, 감사 로그도 정확히 한 건만 남는다.

운영자 자신의 계정이 잠기면(다른 운영자가 잠갔거나, DB에서 직접 상태를 바꾼 경우) 그 즉시 본인 토큰의 운영자 인증 자체가 실패하므로(0장의 매 요청 재확인 규칙), **본인 계정을 스스로 `unlock`할 방법이 없다** — 다른 운영자가 풀어주거나 DB를 직접 고쳐야 한다.

### 4.3 `POST /api/ops/accounts/{account_id}/unlink-person/`

본문은 `reason`(선택, 4.2절과 같은 규칙). 해당 계정에 연결된 모든 유효(`VERIFIED`) 직원 연결을 해제(`REVOKED`)한다 — 하나만 있든 중복으로 여러 개 있든 전부 해제한다.

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하지 않는 `account_id` | 404 | `존재하지 않는 계정입니다: {account_id}` |
| 10 | 연결된 직원이 하나도 없는 계정 | 404 | `연결된 직원 정보가 없습니다.` |
| 11 | 링크가 있지만 전부 이미 해제(`REVOKED`) 상태인 계정 | 404 | `연결된 직원 정보가 없습니다.` — 10과 동일하게 취급(다시 해제할 유효 링크가 없음) |
| 12 | 연결된 직원이 1개 이상 있는 계정 | 200 | `{"account_id": "...", "revoked_person_ids": ["PB001", ...]}` — 해제된 직원 ID 전부를 감사 로그(`ACCOUNT_UNLINK_PERSON`)에 함께 기록 |
| 13 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

`account_id` 조건으로 해당 계정의 링크만 골라 해제하므로, 다른 계정에 연결된 직원 정보는 영향받지 않는다.

### 4.4 `POST /api/ops/accounts/{account_id}/admin/`

본문은 `is_admin`(필수, boolean)과 `reason`(선택). 켤지 끌지를 본문으로 받는 이유는 같은 경로로 부여와 회수를 다 하기 때문이다.

원래 이 조치는 **API로 할 수 없었다** — 호스트에서 `backend/services/createDB/grant_admin.py`를 돌려야만 바뀌었다. 담당이 바뀔 때마다 DB 앞에 앉을 사람이 필요해서 콘솔로 열었다(2026-08-13). 첫 운영자만 여전히 그 스크립트로 만든다(아무도 없으면 콘솔에 들어갈 수 없다).

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하지 않는 `account_id` | 404 | `존재하지 않는 계정입니다: {account_id}` |
| 10 | 대상 계정 상태가 `WITHDRAWN` | 400 | `탈퇴한 계정에는 운영자 권한을 줄 수 없습니다.` |
| 11 | 이미 그 상태(운영자에게 부여, 비운영자에게서 회수) | 400 | `이미 처리된 상태입니다.` |
| 12 | 자기 자신의 권한 회수 | 403 | `본인의 운영자 권한은 내릴 수 없습니다. 다른 운영자에게 요청하세요.` |
| 13 | 남는 운영자가 없어지는 회수 | 400 | `마지막 운영자입니다. 권한을 내리면 콘솔에 아무도 들어갈 수 없습니다.` |
| 14 | 정상 처리 | 200 | `{"account_id": "...", "is_admin": true/false}` — 변경 전/후와 사유를 감사 로그(`OPS_ADMIN_GRANT`/`OPS_ADMIN_REVOKE`)에 기록 |
| 15 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

**두 안전장치는 화면이 아니라 트랜잭션 안에 있다.** 대상 계정 행을 잠근 뒤(`SELECT ... FOR UPDATE`) 확인하므로, 마지막 두 운영자가 서로를 동시에 내려 콘솔이 잠기는 일이 생기지 않는다. 마지막 운영자 판정은 「몇 명 남았나」가 아니라 **「이 사람 말고 살아 있는 운영자가 또 있나」**(`is_admin AND account_status='ACTIVE' AND account_id <> 대상`)로 본다.

### 4.5 응답 구조(`GET /api/ops/accounts/`)

```json
[
  {
    "account_id": "UA002", "email": "acct-test@halil.com", "display_name": "테스트대상",
    "account_status": "ACTIVE", "is_admin": false, "team_id": "TE001", "team_name": "개발팀",
    "mapping_status": "DUPLICATE", "link_count": 2,
    "person": { "person_id": "PB001", "name": "박승우", "org_id": "A003", "org_name": "백엔드파트" },
    "services": ["GOOGLE_DRIVE", "JIRA"]
  }
]
```

각 필드의 산출 방식:

| 필드 | 산출 방식 |
|---|---|
| `account_id`/`email`/`display_name`/`account_status` | 계정 원본 정보. `WITHDRAWN` 계정도 포함해 전체 계정을 반환 |
| `is_admin`/`team_id`/`team_name` | 계정 원본 정보. `team_id`가 없으면(팀 미배정) `team_name`도 `null`. 4.7절 `?team=<team_id>` 필터가 클라이언트에서 걸러낼 수 있는 것도 이 필드 덕분이다 |
| `link_count` | 그 계정에 연결된 유효(`VERIFIED`) 직원 링크 수 |
| `mapping_status` | `link_count`로부터 계산 — 0이면 `UNMAPPED`, 1이면 `LINKED`, 2 이상이면 `DUPLICATE`(2.2절 `duplicate_mapping`과 같은 정의) |
| `person` | 대표로 보여줄 직원 1명(가장 먼저 연결된 링크). 링크가 없으면 `null` |
| `services` | 그 계정의 연결 서비스 중 `auth_status='CONNECTED'`인 것만 유형별로 나열(만료·오류 상태는 제외). People DB는 본인 확인용 내부 커넥터라 "연결 서비스"로 세지 않고 항상 빠진다(6.4절과 같은 정의) |

`person.person_id`는 링크(`user_person_link`) 자체가 있는지로만 결정되고, `person.name`/`person.org_id`/`person.org_name`은 그 직원 레코드를 실제로 찾았는지로 결정된다 — 그래서 링크는 있는데 가리키는 직원 레코드가 없는 경우(참조 무결성이 DB 제약으로 강제되지 않음)에도 `person`이 통째로 `null`이 되지 않고, `person_id`만 채워지고 나머지가 `null`인 상태로 나온다.

### 4.6 `account_id` 처리

URL의 `{account_id}`는 그대로 파라미터 바인딩되어 SQL에 문자열로만 비교되므로, 어떤 값이 들어와도 안전하다.

- 존재하지 않는 값, SQL 구문처럼 보이는 문자열, 컬럼 길이(`VARCHAR(5)`)보다 긴 문자열: 전부 동일하게 `404 존재하지 않는 계정입니다: {입력값}`으로 처리되고 서버 오류가 나지 않는다.
- `/`가 포함된 값(예: URL 인코딩된 `%2F`)은 URL 라우팅 단계에서 아예 그 경로와 일치하는 패턴이 없어 Django 기본 404 페이지로 응답한다 — 이 프로젝트의 다른 모든 API(`invites/{id}`, `projects/{id}` 등)도 동일한 라우팅 규칙을 쓰므로 이 화면만의 특이 동작은 아니고, 실제 `account_id`는 하이픈·슬래시 없는 5자리 코드로만 발급되어 정상 경로에서는 발생하지 않는다.

### 4.7 화면 처리

- 계정 상태 필터는 `전체`/`확인 필요`(매핑이 `LINKED`가 아니거나 상태가 `LOCKED`)/`정상`/`잠김`/`탈퇴` 다섯 가지를 실제 값 기준으로 구분한다.
- URL에 `?team=<team_id>`가 붙어 있으면 그 팀 계정만 남긴다(팀 현황에서 넘어온 경우 — 3.3절). 상태 필터와 함께 걸린다.
- 검색은 계정 이메일과 직원 이름을 대상으로 한다. 계정 번호·직원 번호로는 검색하지 않는다(3.4절).
- 상세 패널의 작업 버튼은 서버가 거부할 게 뻔한 조작을 애초에 보여주지 않는다: 이미 `LOCKED`면 "계정 정지" 대신 "계정 재활성"만, 상태가 `WITHDRAWN`이면 두 버튼 다 감추고 안내 문구만, 본인 계정이면 "계정 정지" 버튼 자체를 감춘다. "직원 연결 해제"는 `mapping_status`가 `DUPLICATE`일 때만 노출한다.
- 작업 확인 모달은 처리 중에는 버튼을 비활성화해 중복 제출을 막고, 처리 결과와 무관하게 성공하면 최신 목록을 다시 불러온다.
- 계정이 0개면 "등록된 계정이 없습니다."를, 검색·필터 결과가 없으면 "조건에 맞는 계정이 없습니다."를 표시한다.
- 조회에 실패하면 오류 메시지와 "다시 시도" 버튼을, 조작 중 오류가 나면 서버가 응답한 문구를 그대로 토스트로 보여준다. 인증이 만료된 경우(401)에는 운영자 로그인 화면으로 이동시킨다.

## 5. 섹션 5 — 계정 연결·초대 현황

### 5.1 `GET /api/ops/invites/`

읽기 전용, 입력값 없음. 인증 실패·DB 연결 실패 응답은 1.2절·3.1절과 동일하다.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰 | 200 | 아래 5.4절 응답 구조 |
| 10 | 발급된 초대가 0건 | 200 | 빈 배열(`[]`) |
| 11 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

### 5.1-2 `GET /api/ops/invites/{invite_id}/`

초대 한 건. 상세가 별도 페이지가 되면서 생긴 경로다. 목록과 **같은 SQL**을 쓴다 — 만료 판정(`PENDING`인데 기한이 지났으면 `EXPIRED`)과 중복 연결 판정이 두 벌이 되면 언젠가 한쪽만 고쳐진다.

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하는 `invite_id` | 200 | 5.4절 응답 구조에서 객체 하나 |
| 10 | 존재하지 않는 `invite_id` | 404 | `존재하지 않는 초대입니다: {invite_id}` |
| 11 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

### 5.2 `POST /api/ops/invites/{invite_id}/discard/`

본문은 `reason`(선택, 4.2절과 같은 규칙). 대기 중(`PENDING`, 화면에 `만료`로 보이는 것 포함)인 초대만 폐기(`REVOKED`)한다 — 이미 수락됐거나, 이미 취소됐거나, 존재하지 않는 초대는 전부 같은 메시지로 거부한다(어느 쪽인지 구분해서 알려주지 않음).

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하지 않는 `invite_id` | 404 | `폐기할 수 있는 초대가 아닙니다.` |
| 10 | 이미 수락된(`ACCEPTED`) 초대 | 404 | `폐기할 수 있는 초대가 아닙니다.` |
| 11 | 이미 폐기된(`REVOKED`) 초대 | 404 | `폐기할 수 있는 초대가 아닙니다.` |
| 12 | 대기 중이지만 만료 시각이 지난 초대(화면엔 `만료`로 표시) | 200 | 폐기 가능 — DB에는 여전히 `PENDING`으로 남아있는 상태라, 아직 정리되지 않은 만료 건도 폐기할 수 있다 |
| 13 | 만료 전 대기 중인 초대 | 200 | `{"invite_id": "...", "status": "REVOKED"}` — 감사 로그(`INVITE_DISCARD`)에 대상 직원 ID 기록 |
| 14 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

같은 초대에 폐기 요청이 동시에 여러 번 들어와도, `UPDATE ... WHERE status = 'PENDING' ... RETURNING`이 단일 SQL 문으로 원자적으로 처리되어 하나만 적용되고 나머지는 9번 행(404)으로 정리된다 — 감사 로그도 정확히 한 건만 남는다.

### 5.3 `POST /api/ops/invites/{invite_id}/unlink/`

본문은 `reason`(선택, 4.2절과 같은 규칙). 이 초대의 직원(`person_id`)이 현재 연결된 계정을 찾아, **그 계정에 연결된 직원 링크 전부**를 해제한다(4.3절의 `unlink_all()`을 그대로 재사용 — 계정 1개가 이 초대 말고 다른 초대로도 중복 연결돼 있으면 그것까지 함께 해제된다).

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하지 않는 `invite_id` | 404 | `존재하지 않는 초대입니다: {invite_id}` |
| 10 | 아직 수락된 적 없는(연결이 생긴 적 없는) 초대 | 404 | `이미 연결이 해제됐거나 연결된 적이 없는 초대입니다.` |
| 11 | 이미 다른 경로로 연결이 해제된 초대 | 404 | 〃 |
| 12 | 연결이 남아있는 초대 | 200 | `{"invite_id": "...", "account_id": "...", "revoked_person_ids": [...]}` — 그 계정에 연결돼 있던 직원 전부의 ID를 포함(1명이든 중복 연결된 여러 명이든), 감사 로그(`ACCOUNT_UNLINK_PERSON`)에 기록 |
| 13 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

한 계정에 중복 연결된 두 직원을 서로 다른 초대로 각각 연결 해제 요청해도(둘 다 같은 계정을 가리키므로), 먼저 처리된 요청이 그 계정의 링크를 전부 해제하고 나중 요청은 10번 행(404)으로 정리된다 — 계정 링크를 두 번 해제하거나 감사 로그가 중복 기록되지 않는다.

`team_org_id`/`invited_by`가 가리키는 조직·계정이 존재하지 않거나(참조 무결성이 DB 제약으로 강제되지 않음), `person_id`가 가리키는 직원 레코드가 없어도 오류 없이 처리된다 — 해당하는 `org_name`/`inviter_email`/`person_name`/`person_email`이 `null`로 나올 뿐, 조회·폐기·연결 해제 자체는 정상 동작한다.

### 5.4 응답 구조(`GET /api/ops/invites/`)

```json
[
  {
    "invite_id": "MI003", "person_id": "PB005", "person_name": "서지호", "person_email": "user007@halil.com",
    "org_id": "A003", "org_name": "백엔드파트", "invited_by": "UA001", "inviter_email": "rhksflwk@halil.com",
    "status": "ACCEPTED", "expires_at": "2026-08-06T07:34:03Z", "accepted_at": null, "created_at": "2026-07-30T07:34:03Z",
    "linked_account_id": "UA002", "linked_account_email": "acct-test@halil.com", "linked_account_duplicate": true
  }
]
```

각 필드의 산출 방식:

| 필드 | 산출 방식 |
|---|---|
| `invite_id`/`person_id`/`invited_by`/`expires_at`/`accepted_at`/`created_at` | 초대 원본 정보 |
| `person_name`/`person_email`/`org_id`/`org_name` | 초대 대상 직원과 그 소속 조직 정보 |
| `inviter_email` | 초대자(`invited_by`) 계정의 이메일 |
| `status` | 대기 중(`PENDING`)인데 만료 시각이 지났으면 `EXPIRED`로 바꿔 보여주고, 그 외에는 원본 상태(`PENDING`/`ACCEPTED`/`REVOKED`) 그대로 |
| `linked_account_id` | 이 초대 대상 직원이 현재 유효하게 연결된 계정 ID. 아직 연결이 없으면 `null` |
| `linked_account_email` | 그 계정(`linked_account_id`)의 이메일. 연결이 없으면 `null` — 3.4절 "연결된 계정 <이메일>" 문구가 이 값을 쓴다 |
| `linked_account_duplicate` | 그 계정이 이 직원 말고 다른 직원과도 중복 연결돼 있는지(4.5절 `mapping_status`의 `DUPLICATE`와 같은 정의) |

### 5.5 화면 처리

- 초대 상태 필터(`수락 대기`/`수락 완료`/`만료`/`취소됨`)와 연결 팀·조직 필터는 실제로 조회된 데이터에 있는 값만으로 구성한다 — 특정 팀 이름을 미리 정해두지 않는다.
- 검색은 초대받은 직원 이름과 초대자 이메일을 대상으로 한다. 초대 기록 번호·직원 번호로는 검색하지 않는다(3.4절).
- "이상 초대 폐기" 버튼은 상태가 `수락 대기` 또는 `만료`일 때만 노출한다(둘 다 대기 중 상태를 뜻하고, 5.2절 규칙대로 실제 폐기가 가능한 상태). "중복 직원 연결 해제" 버튼은 `linked_account_duplicate`가 참일 때만 노출한다 — 계정 관리 화면과 동일하게, 정상적으로 1명만 연결된 초대는 연결 해제 대상으로 노출하지 않는다.
- 연결 해제는 이 초대의 직원 한 명이 아니라 **그 계정에 연결된 모든 직원**을 해제하므로, 같은 계정을 가리키는 다른 초대를 나중에 다시 조회하면 이미 함께 해제되어 대상이 없다는 결과가 나올 수 있다(4.3절과 동일한 재사용 동작).
- 발급된 초대가 하나도 없으면 "발급된 초대 기록이 없습니다."를, 검색·필터 결과가 없으면 "조건에 맞는 초대 기록이 없습니다."를 표시한다.
- 조회에 실패하면 오류 메시지와 "다시 시도" 버튼을, 조작 중 오류가 나면 서버가 응답한 문구를 그대로 토스트로 보여준다. 인증이 만료된 경우(401)에는 운영자 로그인 화면으로 이동시킨다.

## 6. 섹션 6 — 연결 서비스 현황

**연결하는 쪽은 이 콘솔의 일이 아니다** — 재연결은 계정 소유자가 설정 화면에서 한다. 다만 **끊는 쪽은 여기에만 있다**(2026-08-13). 토큰이 샜거나 엉뚱한 계정으로 연결된 것을 즉시 끊을 방법이 제품 어디에도 없었고(고객도 못 끊는다), 그것을 6.3절로 열었다.

대상은 Drive/Jira 연결뿐이다. People DB 연결(본인 확인용 내부 커넥터)은 운영자가 상태를 점검해야 할 외부 데이터 소스가 아니라서 빠지고(4.5절 `services`와 같은 정의), 팀에 등록한 모델(`MODEL_API`)도 빠진다 — 스키마를 안 바꾸려고 `connector_conn`을 빌려 쓴 것이지 「연결 서비스」가 아니다(모델은 섹션 9의 것이다). 걸러지지 않아 `MODEL_API` 행이 이 화면에 새고 있던 것을 같은 날 고쳤다.

### 6.1 `GET /api/ops/connectors/`

입력값 없음.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰, 연결이 1건 이상 존재 | 200 | 아래 6.4절 응답 구조 |
| 10 | 정상 토큰, 연결이 0건 | 200 | 빈 배열(`[]`) |
| 11 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

### 6.2 `GET /api/ops/connectors/<conn_id>/`

상세가 별도 페이지가 되면서 생긴 경로(주소로 바로 들어올 수 있어야 한다). 목록과 **같은 SQL**을 쓴다 — 따로 쓰면 언젠가 한쪽만 고쳐진다.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하는 Drive/Jira 연결 | 200 | 6.4절 구조에서 객체 하나 |
| 10 | 없는 `conn_id`, 또는 People DB·`MODEL_API` 연결 | 404 | `존재하지 않는 연결입니다: {conn_id}` — 목록에 없는 것은 상세로도 못 연다 |

### 6.3 `POST /api/ops/connectors/<conn_id>/revoke/`

입력값은 `reason`(선택, 빈 문자열 허용) 하나다. 대상은 경로에 있다.

**행을 지우지 않고 자격증명만 지운다.** `encrypted_credential_ref`를 `NULL`로 만들고 `auth_status`를 `REVOKED`로 바꾼다. 지우지 않는 이유는 재연결이 같은 행을 다시 쓰기 때문이다 — `ConnectorRepository._upsert`가 (account_id, connector_type)으로 UPDATE를 먼저 시도하므로 `conn_id`가 유지된다. 행을 지우면 재연결이 새 `conn_id`를 받고, 그것을 가리키던 `team_folder`·`proj_source`는 FK가 없어 죽은 값을 든 채 남는다(고객이 폴더와 Jira 연결을 전부 다시 골라야 한다). 목적은 자격증명을 못 쓰게 하는 것이지 배선을 끊는 것이 아니다.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 연결됨/만료/오류 상태의 Drive·Jira 연결 | 200 | `{"conn_id","connector_type","auth_status":"REVOKED","affected_sources"}` |
| 10 | 없는 `conn_id` | 404 | `존재하지 않는 연결입니다: {conn_id}` |
| 11 | People DB·`MODEL_API` 연결 | 400 | `구글 드라이브·Jira 연결만 해제할 수 있습니다.` — 화면이 이미 거르지만 규칙은 트랜잭션 안에 있다 |
| 12 | 이미 `REVOKED`인 연결 | 400 | `이미 해제된 연결입니다.` |
| 13 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

`affected_sources`는 이 연결로 읽고 있던 것의 수다 — Drive면 `team_folder`, Jira면 `proj_source` 행 수. 끊는 것은 한 번에 되지만 그 팀의 문서 수집이나 Jira 동기화가 같이 서므로, 무엇이 멈추는지 화면이 말할 수 있어야 한다. `audit_log`에 `OPS_CONNECTOR_REVOKE`(target_type `CONNECTOR`)로 남고 payload에 유형·소유 계정·이전 상태·`affected_sources`·사유가 들어간다.

해제된 뒤 고객이 그 커넥터를 쓰면 `ConnectorRepository.get_credential`이 `운영자가 이 연결을 해제했습니다. 설정에서 다시 연결해 주세요.`로 답한다 — 자격증명이 없다는 이유로 「연결되지 않은 서비스입니다」가 나가면 무슨 일이 있었는지 알 수 없다.

### 6.4 응답 구조

```json
[
  {
    "conn_id": "CN001", "account_id": "UA002", "owner_email": "conn-test@halil.com",
    "connector_type": "GOOGLE_DRIVE", "auth_status": "EXPIRED", "connected_at": "2026-07-29T08:00:27Z",
    "person": { "person_id": "PB002", "name": "윤유진", "org_id": "A003", "org_name": "백엔드파트" },
    "diagnosis": "인증이 만료됐습니다.", "next_action": "계정 소유자가 설정에서 재연결"
  }
]
```

각 필드의 산출 방식:

| 필드 | 산출 방식 |
|---|---|
| `conn_id`/`account_id`/`connector_type`/`auth_status`/`connected_at` | 연결 원본 정보. Drive·Jira 연결만 포함하고(People DB·`MODEL_API` 제외) 상태로는 거르지 않는다 — 만료·오류·해제도 그대로 나온다 |
| `owner_email` | 그 연결을 소유한 계정의 이메일. 계정 자체가 존재하지 않으면(참조 무결성이 DB 제약으로 강제되지 않음) `null` |
| `person` | 소유 계정에 대표로 연결된 직원 1명(4.5절 `person`과 같은 규칙 — 가장 먼저 연결된 링크). 연결된 직원이 없으면 `null` |
| `diagnosis`/`next_action` | `auth_status` 값으로부터 만드는 안내 문구. `CONNECTED`→"정상"/"조치 없음", `EXPIRED`→"인증이 만료됐습니다."/"계정 소유자가 설정에서 재연결", `ERROR`→"연결 중 오류가 발생했습니다."/"계정 소유자가 설정에서 연결 재시도", `REVOKED`→"운영자가 연결을 해제했습니다."/"계정 소유자가 설정에서 다시 연결". 이 네 값 외의 상태가 들어오면(`auth_status`는 DB에 CHECK 제약이 없는 컬럼) "알 수 없는 연결 상태입니다: {값}"과 "계정 소유자에게 연결 상태 확인 요청"으로 대체해 오류 없이 응답한다 |

연결을 소유한 계정 자체가 존재하지 않는 경우(`owner_email`이 `null`인 경우)에도 그 연결 자체는 목록에서 빠지지 않고 그대로 나온다 — 소유자를 알 수 없다는 사실 자체가 운영자가 확인해야 할 정보이기 때문에, 소유 계정 존재 여부로 걸러내지 않는다.

`person`도 4.5절과 같은 규칙으로, 링크는 있지만 그 직원 레코드가 없는 경우 `person_id`만 채워지고 `name`/`org_id`/`org_name`은 `null`로 나온다(통째로 `null`이 되지 않음).

### 6.5 화면 처리

- 목록은 「무엇이 연결돼 있는가」만 맡고 조치는 상세 페이지(`/ops/connectors/:connId`)에 있다. 계정·초대·팀과 같은 규칙이다 — 목록의 「작업」 열은 `상세 보기` 하나이고 행을 눌러도 같은 곳으로 간다. 조치가 생기기 전에는 목록 아래 패널에 상세를 폈다.
- 유형(`구글 드라이브`/`Jira`)과 상태(`연결됨`/`만료됨`/`오류`) 필터는 알려진 값 기준으로 고정 목록을 쓴다(People DB는 API 응답 자체에 없으므로 필터에도 없음). 요약 카드의 유형별 건수·상태 분포는 전부 조회된 데이터에서 그때그때 집계한다. `해제됨`은 필터에 없다 — 운영자가 끊은 것을 다시 찾아 나설 일이 없기 때문이고, 표에는 상태 뱃지로 그대로 보인다.
- 상세에는 소유 계정 이메일과 연결 조직만 표시하고, 연결된 직원의 실명과 토큰 원문은 표시하지 않는다 — 운영자가 필요한 건 "무엇이 문제인지"이지 "누구인지"가 아니고, 끊는 것과 보는 것은 다른 권한이다.
- 강제 해제는 확인 모달을 거치고 사유(선택)를 받는다. 모달은 **무엇이 멈추는지 먼저 말하고**, 해제 후 토스트가 함께 멈추는 폴더·프로젝트 수(`affected_sources`)를 알린다. 이미 해제된 연결에는 버튼 대신 "다시 연결하는 것은 계정 소유자가 설정 화면에서 합니다"를 보여준다.
- 연결이 하나도 없으면 "연결된 서비스가 없습니다."를, 검색·필터 결과가 없으면 "조건에 맞는 연결 서비스가 없습니다."를 표시한다.
- 조회에 실패하면 오류 메시지와 "다시 시도" 버튼을 보여주고, 인증이 만료된 경우(401)에는 운영자 로그인 화면으로 이동시킨다.

## 7. 섹션 7 — 감사 로그

읽기 전용 GET 엔드포인트 하나. 입력값은 없다.

**한 번은 다섯이었다.** 배정 실행 → 추천 결과 → 검증 결과 → PM 결정으로 이어지는 「분석·결정 기록」 4종을 함께 읽었는데, 그 테이블(`assign_run`/`reco_result`/`valid_result`/`decision_rec`)에 쓰는 파이프라인이 이 저장소에 없어 **넷 다 항상 빈 배열**이었다. "나중에 파이프라인이 쓰기 시작하면 코드 변경 없이 채워진다"고 두었지만, 제품이 업무 배정 추천에서 물러나면서 그 나중이 오지 않는다 — 엔드포인트·SQL·화면을 함께 걷었다(2026-08-13). 되살릴 일이 생기면 git 이력에 있다. 테이블 자체(`assign_run`)는 그대로 뒀다. `POST /api/projects/<id>/assignment-runs/`(배정 실행 생성)는 애초에 이 섹션이 걷은 것이 아니었지만, 지금은 그 엔드포인트 자체도 없다 — `apps/projects/api_urls.py`에 더 이상 등록돼 있지 않다.

### 7.2 `GET /api/ops/audit/operations/` — 운영 활동

`audit_log` 최신 200건(수행자 이름·이메일 조인). 운영자 콘솔 자체의 조치(운영자 로그인·로그아웃, 계정 잠금/해제,
직원 연결 해제, 초대 폐기, 전역 정책 변경)뿐 아니라 일반 사용자(팀장·팀원)의 로그인·회원가입·비밀번호 재설정·
커넥터 연결(`LOGIN`/`SIGNUP`/`PASSWORD_RESET`/`CONNECTOR_CONNECT`, `apps/accounts`·`apps/connectors`에서 기록)도
여기 함께 쌓인다 — 이 화면의 전부다.

팀원 초대 발급·수락은 의도적으로 여기 넣지 않는다. `member_invite.created_at`/`accepted_at`이 이미 자체 이력을
갖고 있어서(§5 참고) 같은 정보를 중복 기록하지 않는다. 반대로 로그인·커넥터 연결은 `user_account.last_login_at`/`connector_conn.connected_at`이
최신 값만 덮어쓰는 컬럼이라 과거 이력이 원본 테이블에 남지 않으므로, 감사 로그가 유일한 이력 보존 수단이다.

```json
{
  "audit_id": "AL093", "actor_account_id": "UA001", "actor_display_name": "관리자", "actor_email": "rhksflwk@halil.com",
  "action": "ACCOUNT_LOCK", "proj_id": null, "target_type": "ACCOUNT", "target_id": "UA002",
  "payload": { "before": "ACTIVE", "after": "LOCKED" }, "occurred_at": "2026-07-30T08:05:20Z"
}
```

`actor_account_id`가 가리키는 계정이 존재하지 않으면(참조 무결성이 DB 제약으로 강제되지 않음) `actor_display_name`/
`actor_email`만 `null`이 되고, `actor_account_id` 원본 값과 기록 자체는 그대로 남는다.

### 7.3 화면 처리

- 갈래가 하나뿐이라 탭이 없다. 예전에는 "운영 활동"과 "분석·결정 기록"(4개 하위 탭)을 고르는 2단 탭 구조였다 —
  **탭이 하나면 탭이 아니다.**
- 작업 종류 필터는 실제로 조회된 데이터에 있는 `action` 값만으로 구성한다. 보이는 것은 한글 라벨이고 고르는 값은
  원본 코드다 — 라벨을 값으로 쓰면 표의 `action`과 안 맞아 아무것도 안 걸린다.
- 표에서는 기록 ID 같은 고유 번호를 뺐고(3.4절), 대신 사람이 읽는 값(시각, 수행자, 작업, 대상)을 보여준다.
  검색도 그 값들만 대상으로 한다.
- CSV 내보내기(현재 목록만)는 클라이언트에서 직접 만든다 — 서버 API를 추가로 부르지 않는다.
  **CSV에는 기록 ID를 그대로 남긴다.** 화면과 달리 CSV는 나중에 DB 기록과 대조하기 위해 뽑는 것이라, 번호가 없으면
  용도 자체가 사라진다.
- 조회에 실패하면 오류 메시지와 "다시 시도" 버튼을 보여주고, 인증이 만료된 경우(401)에는 운영자 로그인 화면으로 이동시킨다.

## 8. 섹션 8 — 전역 정책

초대 코드 만료 기간 하나와 시스템 공지 CRUD, 그리고 이 둘의 변경 이력 조회로 구성된다. 변경 이력은 별도
테이블 없이 `audit_log`를 `action` 값으로 필터링해 재사용한다(`POLICY_INVITE_TTL_CHANGE`/`NOTICE_CREATE`/
`NOTICE_UPDATE`/`NOTICE_DELETE`).

### 8.1 `GET/PUT /api/ops/policies/invite-ttl/`

초대 코드 만료 기간(`sys_setting.INVITE_EXPIRE_DAYS`)을 조회·변경한다. 이 값은 `apps/accounts`의
`MemberInviteRepository.create()`가 신규 초대를 발급할 때마다 읽어 만료 시각을 계산하는 데 쓰인다 — 운영자
콘솔 밖에서도 실제로 쓰이는 유일한 설정값이다.

| # | 입력·상황 | HTTP | 응답 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | `GET`, 정상 토큰 | 200 | `{"days": 14}` |
| 10 | 설정 행이 아직 없는 상태에서 `GET`(볼륨을 비우지 않고 수동으로 스키마만 반영한 경우) | 200 | 기본값 `{"days": 14}`로 안전하게 대체 — 이 값이 없으면 신규 초대 발급 전체가 막히므로, 조회 실패 대신 기본값으로 응답한다 |
| 11 | `PUT`, `days`가 정수가 아님(문자열 등) | 400 | `{"days": ["유효한 정수를 입력하세요."]}` |
| 12 | `PUT`, `days` 필드 자체가 없음 | 400 | `{"days": ["이 필드는 필수 항목입니다."]}` |
| 13 | `PUT`, `days`가 0 이하 또는 91 이상 | 400 | `초대 만료 기간은 1일에서 90일 사이로 입력해 주세요.` |
| 14 | `PUT`, `days`가 현재 값과 동일 | 400 | `변경된 초대 정책이 없습니다.` |
| 15 | `PUT`, 1~90 범위의 새로운 값(+ 선택적 `reason`) | 200 | `{"days": 30}` — 감사 로그(`POLICY_INVITE_TTL_CHANGE`)에 `before`/`after`/`reason` 기록 |
| 16 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

같은 값으로 동시에 여러 `PUT` 요청이 들어와도, 설정 행을 잠근(`SELECT ... FOR UPDATE`) 상태에서 현재 값과
비교하므로 하나만 실제로 반영되고 나머지는 14번 행(`변경된 초대 정책이 없습니다.`)으로 정리된다 — 계정
잠금/해제(4.2절)와 같은 방식의 동시성 처리다.

### 8.2 `GET/POST /api/ops/policies/notices/`

시스템 공지 목록 조회와 신규 생성.

| # | 입력·상황 | HTTP | 응답 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | `GET`, 정상 토큰 | 200 | 아래 응답 구조. 등록된 공지가 없으면 빈 배열(`[]`) |
| 10 | `POST`, 제목·내용 중 하나라도 공백 | 400 | `공지 제목과 내용을 입력해 주세요.` |
| 11 | `POST`, 날짜·시간 중 하나라도 누락 | 400 | `공지 날짜와 시간을 선택해 주세요.` |
| 12 | `POST`, `status`가 `PUBLISHED`/`SCHEDULED`/`ENDED` 외의 값 | 400 | `{"status": ["\"...\"은 유효하지 않은 선택입니다."]}` |
| 13 | `POST`, `schedule_mode`가 `FROM`/`UNTIL` 외의 값 | 400 | `{"schedule_mode": ["\"...\"은 유효하지 않은 선택입니다."]}` |

`schedule_date`(날짜)와 `schedule_time`(시간)은 요청에서 따로 받아 서버에서 프로젝트 표준시(`Asia/Seoul`)
기준의 타임존 인지 시각으로 합친 뒤 `sys_notice.schedule_at`(TIMESTAMPTZ) 한 컬럼에 저장한다.

### 8.3 `PUT/DELETE /api/ops/policies/notices/{notice_id}/`

기존 공지 수정·삭제. 검증 규칙은 8.2절 생성과 동일하다.

| # | 입력·상황 | HTTP | 응답 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하지 않는 `notice_id`(수정·삭제 공통) | 404 | `존재하지 않는 공지입니다.` |

| 11 | `PUT`, 필수 조건을 모두 만족(+ 선택적 `reason`) | 200 | 수정된 공지 — 감사 로그(`NOTICE_UPDATE`)에 `before`/`after`/`reason` 기록 |
| 12 | `DELETE`, 존재하는 `notice_id`(+ 선택적 `reason`) | 204 | 본문 없음 — 감사 로그(`NOTICE_DELETE`)에 `before`/`reason` 기록 |
| 13 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

같은 `notice_id`에 삭제 요청이 동시에 여러 번 들어와도, 단일 `DELETE ... RETURNING`이 원자적으로 처리되어
하나만 적용되고 나머지는 9번 행(404)으로 정리된다.

### 8.4 응답 구조(`GET /api/ops/policies/notices/`)

```json
[
  {
    "notice_id": "NT001", "title": "점검 안내", "content": "정기 점검 진행중",
    "status": "PUBLISHED", "schedule_at": "2026-08-01T09:00:00Z", "schedule_mode": "UNTIL",
    "created_by": "UA001", "created_by_name": "관리자",
    "created_at": "2026-07-30T09:04:52Z", "updated_at": "2026-07-30T09:05:13Z"
  }
]
```

`created_by`가 가리키는 계정이 존재하지 않으면(참조 무결성이 DB 제약으로 강제되지 않음) `created_by_name`만
`null`이 되고, `created_by` 원본 값과 공지 자체는 그대로 남는다. 생성 직후 응답에서는 `created_by_name`을
다시 조회하지 않고 `null`로 내려준다(목록 조회 시에만 조인해서 채운다).

### 8.5 `GET /api/ops/policies/changes/` — 정책 변경 이력

`audit_log`에서 `action`이 `POLICY_INVITE_TTL_CHANGE`/`NOTICE_CREATE`/`NOTICE_UPDATE`/`NOTICE_DELETE`인
행만 최신순으로 반환한다. 입력값은 없다.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰 | 200 | 7.2절과 같은 구조(`actor_display_name`/`actor_email` 조인 포함) + `payload`에 `before`/`after`/`reason` |
| 10 | 정책 변경 이력이 0건 | 200 | 빈 배열(`[]`) |
| 11 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

`POLICY_INVITE_TTL_CHANGE`는 `sys_setting`이 단일 설정 행이라 `target_id`를 채울 5자 이내의 자연스러운 ID가
없으므로 `target_id`는 항상 `null`이고, `target_type`(`SYS_SETTING`)만으로 구분한다. 공지 관련 세 액션은
`target_id`에 `notice_id`가 그대로 들어간다.

### 8.6 화면 처리

- 초대 정책 저장 버튼은 값이 1~90 범위를 벗어나거나 현재 값과 같으면 서버가 그대로 거부하므로, 화면에서도
  동일한 조건을 먼저 검사해 같은 문구를 보여준 뒤에만 실제 요청을 보낸다.
- 공지 목록은 상태별 배지(`게시 중`/`게시 예정`/`종료`)와 게시 일정(`MM.DD HH:mm 부터`/`까지`)을 함께 보여주고,
  상세 모달에서 수정·삭제로 진입한다. 등록된 공지가 없으면 "등록된 공지가 없습니다."를 표시한다.
- "정책 변경 이력" 목록은 각 행 앞에 변경 유형 배지(초대 정책 변경/공지 생성/공지 수정/공지 삭제, 색으로 구분)를
  붙여 어떤 종류의 변경인지 한눈에 훑어볼 수 있게 하고, 화면에는 최신 5건만 미리 보여주고, 항목을 고르면 하단에
  변경 전/후, 변경 시각, 변경 사유(입력하지 않았으면 "입력된 사유 없음"), 변경자를 보여준다. 이력이 없으면
  "정책 변경 이력이 없습니다."를 표시하고, 이 경우 "전체 보기" 버튼 자체를 숨긴다.
- "전체 보기"를 누르면 전체 이력을 변경 유형(전체/초대 정책 변경/공지 생성/공지 수정/공지 삭제) select와 제목·
  변경자 검색으로 걸러볼 수 있는 목록을 모달로 띄운다. 목록은 세로 스크롤로 제한 높이 안에서 내려 보고,
  필터·검색 조건 둘 다 실제로 조회된 데이터 안에서만 걸러낸다(서버에 별도 요청 없이 클라이언트에서 필터링).
  조건에 맞는 이력이 없으면 "조건에 맞는 정책 변경 이력이 없습니다."를 표시한다. 목록에서 항목을 고르면 모달이
  닫히고 화면 하단의 상세(변경 전/후 등)가 그 항목으로 바뀐다.
- 조회에 실패하면 오류 메시지와 "다시 시도" 버튼을 보여주고, 저장·생성·수정·삭제 중 오류가 나면 서버가 응답한
  문구를 그대로 토스트로 보여준다. 인증이 만료된 경우(401)에는 운영자 로그인 화면으로 이동시킨다.

## 9. 섹션 9 — 커스텀 모델 등록

**팀이 스스로 등록하지 않는다.** 회사가 요청하면 운영자가 등록한다(2026-08-13 멘토링). 설정 화면의 등록 폼은
없앴다 — 등록하려면 OpenAI 호환 주소와 키와 모델 식별자를 알아야 하는데, 그건 「코딩 없이」를 내세운 제품이
비개발자에게 요구할 일이 아니다. 실제로 Google 호환 주소는 AI Studio 화면에 없어서 문서를 뒤져야 나왔다.

**권한 범위는 여전히 팀이다.** 등록하는 사람만 운영자로 바뀔 뿐, 그 모델을 고르고 실행에 쓰는 것은 그 팀뿐이다
(`CustomModelRepository._rows`가 `user_account.team_id`로 거른다). 조직 단위로 넓히는 것은 하지 않기로
했다(2026-08-13 PM 결정).

`connector_conn` 테이블을 그대로 쓴다(`connector_type = 'MODEL_API'`) — 스키마에 칸을 새로 만들면 팀원 전원이
ALTER를 돌려야 하는데, 이 테이블이 이미 「팀의 암호화된 자격증명」이라 그럴 이유가 없다. 같은 테이블을 쓰지만
「연결 서비스」가 아니라서 6절의 화면·API와는 분리돼 있고, 6절 목록·상세·해제 어디에도 `MODEL_API` 행은 섞이지
않는다(6절 참고).

### 9.1 `GET/POST /api/ops/models/`

`GET`은 모든 팀의 등록분을 반환한다(9.4절 응답 구조). `POST` 본문은 `team_id`(필수)·`label`(필수)·
`base_url`(필수)·`api_key`(필수)·`model`(필수)이다.

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | `GET`, 정상 토큰 | 200 | 9.4절 응답 구조(등록분이 없으면 빈 배열) |
| 10 | `POST`, 필수 필드 누락 | 400 | `{"필드명": ["이 필드는 필수 항목입니다."]}` |
| 11 | `POST`, `model`이 기본 제공 모델(`AGENT_MODELS`)과 이름이 같음 | 400 | `{"model": ["{model} 는 이미 기본 제공하는 모델입니다. 다른 모델을 고르세요."]}` |
| 12 | `POST`, 존재하지 않는 `team_id` | 404 | `없는 팀입니다: {team_id}` |
| 13 | `POST`, `model`이 그 팀에 이미 등록돼 있음(사전 검사에서 걸림) | 400 | `{model} 은 이 팀에 이미 등록돼 있습니다.` |
| 14 | `POST`, 등록 직전 실호출 검증 실패 | 400 | `이 주소와 모델로 답을 받지 못했습니다. 주소·키·모델 이름을 확인해 주세요.` |
| 15 | `POST`, 사전 검사 통과 뒤 검증 호출(최대 25초) 도중 같은 이름이 다른 요청으로 먼저 등록됨 | 409 | `{model} 은 이 팀에 이미 등록돼 있습니다.` — `add_for_team` 트랜잭션 내부의 두 번째 검사 |
| 16 | `POST`, 정상 등록 | 201 | `{"team_id": "...", "model": "..."}` — 감사 로그(`OPS_MODEL_REGISTER`)에 `model`/`label`/`base_url` 기록(키는 남기지 않는다) |
| 17 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

**등록 전에 한 번 써 본다.** 목록 조회(9.2절)만 되고 실제 호출은 안 되는 엔드포인트가 흔해서, 안 되는 것을
등록해 두면 그 팀의 대화가 조용히 실패하고 팀은 운영자가 등록해 줬으니 되는 줄 안다. 그래서 등록 직전에 실제로
`client.chat.completions.create()`를 한 번 불러 답이 오는지 확인한다.

**같은 이름을 두 번 두지 않는다.** 실행 경로가 모델 이름 하나로 정해지므로(`CustomModelRepository.for_model`),
같은 팀에 같은 이름이 겹치면 실행은 먼저 등록한 것으로 고정되는데 목록에는 둘로 보여 어느 것으로 도는지 아무도
모르게 된다. 뷰의 사전 검사와 `add_for_team`의 트랜잭션 내부 검사, 두 번 본다 — 그 사이에 최대 25초짜리 검증
호출이 끼어 있어서, 그 틈에 들어온 다른 요청과 겹칠 수 있기 때문이다.

**목록을 응답에 다시 담지 않는다.** 등록에 성공한 뒤 목록을 다시 만들다 실패하면 이미 끝난 등록이 실패로
보고되고, 운영자는 안 됐다고 믿고 다시 누른다(2026-08-13 검토). 목록은 화면이 따로 받아 간다.

### 9.2 `POST /api/ops/models/probe/`

입력은 `base_url`(필수)·`api_key`(필수) 둘뿐이다. 등록 전에 그 주소가 가진 모델 이름을 미리 보여줘, 운영자가
이름을 외워 적지 않게 한다 — 오타 하나가 실행 시점 404가 되고, 그때는 등록해 준 운영자가 아니라 그 팀의 대화가
죽는다.

| # | 입력·상황 | HTTP | 응답 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | `base_url`·`api_key` 중 하나라도 빈 값 | 400 | `{"detail": "주소와 키가 필요합니다."}` |
| 10 | 주소·키는 있지만 호출 자체가 실패(인증 실패·주소 오류 등) | 200 | `{"models": [], "detail": "이 주소에서 모델 목록을 받지 못했습니다. 주소와 키를 확인해 주세요."}` — 목록 조회가 막힌 것뿐이라 오류가 아니라 200으로 응답한다 |
| 11 | 호출은 되지만 모델 목록이 비어 있음(예: Anthropic 호환 경로) | 200 | `{"models": [], "detail": "이 주소가 쓸 수 있는 모델을 알려주지 않았습니다."}` |
| 12 | 정상 조회 | 200 | `{"models": ["...", ...], "detail": null}` — 이름 오름차순 정렬 |

**목록을 안 주는 구현도 흔하다.** Anthropic 호환 경로는 이 호출 자체가 401로 거절된다. 그럴 때는 빈 목록과
이유를 주고, 화면이 직접 입력으로 넘어간다 — 이 API가 실패해도 등록(9.1절)까지 막지는 않는다.

### 9.3 `DELETE /api/ops/models/{conn_id}/`

입력값 없음. 대상은 경로에 있다. **팀 경계를 안 본다** — 콘솔은 모든 팀을 다루는 자리다(팀 쪽에는 삭제 경로
자체가 없다. 등록이 운영자 몫이라 삭제도 그렇다).

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 없는 `conn_id`, 또는 `MODEL_API`가 아닌 연결 | 404 | `등록되지 않은 모델 API 입니다: {conn_id}` |
| 10 | 그 모델을 쓰는(`ARCHIVED`가 아닌) 에이전트가 있음 | 409 | `이 모델을 쓰는 에이전트가 있습니다: {이름, ...}. 그 에이전트의 모델을 먼저 바꿔 주세요.` |
| 11 | 쓰는 에이전트가 없음 | 204 | 본문 없음 — 감사 로그(`OPS_MODEL_REMOVE`)에 `conn_id`·`model`·`label`·`base_url` 기록 |
| 12 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

**지우기 전에 쓰는 곳부터 본다.** 지우면 그 모델을 쓰던 에이전트는 실행 시점에 우리 키로 없는 모델을 부르다
죽는다 — 저장은 멀쩡해 보이는데 대화만 실패하는, 이 프로젝트가 계속 겪어 온 모양이다. 자격증명을 못 읽는 깨진
행은 예외다 — 어차피 아무도 못 쓰므로 쓰는 곳을 묻지 않고 지운다.

**지운 내용을 감사 로그에 그대로 남긴다.** 행을 지우고 나면 `conn_id`는 아무것도 가리키지 않아서, 그 값만
남기면 나중에 「어느 팀의 무슨 모델이 없어졌나」를 아무도 복원할 수 없다(2026-08-13 검토). 등록 쪽(9.1절)과
같은 모양으로 맞춘다.

### 9.4 응답 구조(`GET /api/ops/models/`)

```json
[
  {
    "conn_id": "CN010", "team_id": "TE001", "team_name": "개발팀",
    "label": "사내 vLLM", "base_url": "https://vllm.example.com/v1",
    "model": "llama-3-70b", "connected_at": "2026-08-13T02:11:04Z"
  }
]
```

각 필드의 산출 방식:

| 필드 | 산출 방식 |
|---|---|
| `conn_id`/`connected_at` | `connector_conn` 원본 정보 |
| `team_id`/`team_name` | 등록할 때 매단 팀장 계정(`user_account.team_id`)이 속한 팀. 팀이 지워졌으면(참조 무결성이 DB 제약으로 강제되지 않음) `team_name`만 `null` |
| `label`/`base_url`/`model` | 암호화된 payload를 복호화해서 꺼낸 값 |

**키(`api_key`)는 이 응답에 없다.** 등록한 사람이 운영자여도 마찬가지다 — 운영자 콘솔도 예외가 아니다.

**복호화에 실패한 행도 목록에서 빠지지 않는다.** 팀 쪽 목록(`CustomModelRepository.list_for_account`)은 못
읽는 행을 건너뛰지만, 이 목록은 그 행도 보여준다 — 치울 사람이 운영자라, 숨기면 아무도 모르는 채로 영영 남기
때문이다. 그럴 때 `label`은 `"읽을 수 없음"`으로, `base_url`·`model`은 빈 문자열로 나온다.
