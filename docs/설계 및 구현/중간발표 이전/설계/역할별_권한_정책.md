# 역할별 권한 정책 (운영자 / 팀장 / 팀원)

## 배경

설정·마이페이지·대시보드 화면을 설계하기 전에, 운영자·팀장·팀원 세 역할이 각각 무엇을 **조회**할 수 있고, 무엇을 **수정**할 수 있고, 무엇을 **설정**할 수 있는지부터 정리한다. 화면 레이아웃은 이 문서의 범위가 아니다.

## 핵심 원칙

1. **People DB(조직·인력)의 원천은 HR Connector다.** 어떤 역할도 `org`/`person` 데이터를 직접 수정하지 않는다 — 운영자를 포함해 전 역할이 조회만 가능하다. HR 쪽과 어긋나는 걸 막기 위함이다. 2026-07-31부터 이 8개 테이블은 `mock_hr` 스키마에 있고 `backend/services/hr/` 어댑터만 읽는다. 애플리케이션 코드에 쓰기 경로가 아예 없다.
2. **운영자는 새로운 회원 역할이 아니라 플랫폼을 개발·운영하는 팀 본인이다.** 별도 권한 테이블은 두지 않고 `user_account.is_admin BOOLEAN NOT NULL DEFAULT false` 플래그 하나로 식별한다(`DB/schema.sql:44`). **첫 운영자**는 `backend/services/createDB/grant_admin.py`로만 켠다(아무도 없으면 콘솔에 들어갈 수 없다). 그 뒤로는 운영자가 콘솔에서 다른 계정에 부여·회수할 수 있다(2026-08-13, `POST /api/ops/accounts/{account_id}/admin/`). **자기 자신은 못 내리고, 마지막 운영자도 못 내린다** — 둘 다 콘솔이 잠기는 경로다.
   > ⚠ **2026-08-05 정정 — 「이메일 하드코딩 allowlist」가 아니다.** 컬럼 주석이 "이메일 패턴 매칭이 아니라 이 플래그로만 관리자를 판별한다"고 명시한다. allowlist 방식으로 알고 접근하면 존재하지 않는 경로를 찾게 된다.
3. **팀장/팀원 구분은 가입 경로로 판단한다.** 초대 코드로 가입해 `user_person_link.match_method='TEAM_INVITATION'`으로 연결된 계정만 팀원이며, 그 외 직접 가입 계정은 팀장으로 본다. HR 시스템 연결 권한이 회사에서 팀장에게만 주어진다는 전제에 따른 정책이다. `org.mgr_id`는 조직의 관리자 정보일 뿐 로그인 역할 판정에는 사용하지 않는다.
4. **운영자 페이지의 보안 경계는 URL이 아니라 별도 로그인이다.** 관리자 페이지는 팀장·팀원이 쓰는 일반 이메일·비밀번호 로그인과 별개로 자체 로그인(`/ops/login` 등)을 두고, **`user_account`의 이메일·비밀번호가 맞으면서 `is_admin=true`이고 상태가 `ACTIVE`인지** 확인한다(2026-08-05 정정 — "환경변수에 등록된 운영자 자격 증명과 대조한다"였으나 운영자 자격 증명용 환경변수는 `config/settings/base.py`에 없다). URL을 내비게이션에 노출하지 않는 것은 일반 사용자 혼란을 줄이는 부가 조치일 뿐, 그 자체를 보안 경계로 삼지 않는다.

### 팀장/팀원 판정과 HR 매핑

| 구분 | 직접 가입(팀장) | 초대 코드 가입(팀원) |
|---|---|---|
| 역할 판정 근거 | 초대 코드 없이 가입 | 유효한 `member_invite`를 사용해 가입 |
| `user_person_link.match_method` | People DB 연결 시 `SELF_EMAIL` | 가입 시 `TEAM_INVITATION` |
| HR 매핑 시점 | 가입 직후가 아니라 People DB 커넥터에서 본인 확인을 완료한 시점 | 초대 코드 수락과 가입이 완료된 시점 |
| HR 매칭 실패 | People DB 온보딩이 중단되므로 팀원 조회·초대 권한이 열리지 않음 | 초대 코드가 연결한 `PERSON`을 사용하므로 이메일 자동 매칭하지 않음 |

서버는 별도 `role` 컬럼을 저장하지 않고 현재 활성 매핑의 `match_method`로 응답 역할을 계산한다. 직접 가입자가 아직 People DB를 연결하지 않았더라도 계정 역할은 팀장이지만, `person` 연결과 `scope_org_ids`가 없으므로 실제 HR 기반 조회·초대 기능은 사용할 수 없다.

초대 화면의 **기본 표시 범위**와 **권한 범위**는 구분한다.

- 기본 표시: 본인의 `person.org_id`와 같은 조직의 구성원
- 권한 범위: 본인 조직과 `org.up_org_id` 재귀로 연결된 모든 하위 조직
- 하위 조직은 화면에서 기본적으로 접어 두며, 사용자가 펼쳐야 선택할 수 있다.

## 화면 배치 원칙

매트릭스의 "조회/수정" 항목이 실제로 어느 화면에 놓이는지는 아래 기준을 따른다.

- **조회 → 역할별 대시보드.** 팀장 대시보드와 팀원 대시보드는 서로 다른 화면이다(팀장은 조직·팀 워크로드 중심, 팀원은 본인 배정 업무 중심). 운영자의 조회 화면은 관리자 페이지 내부에 있다.
- **수정은 두 종류로 나뉜다.**
  - **업무 처리(워크플로우성 수정)**: 업무 배정 후보 수정·최종 승인, 팀원 초대 발급/취소 같은 행위는 그 일이 실제로 일어나는 기존 업무 흐름 화면(추천 결과 화면, 초대 플로우 등)에서 처리한다. 별도 "설정" 메뉴로 옮기지 않는다.
  - **환경설정성 수정**: Connector 연동, 팀 업무 배정 기준처럼 반복적으로 안 바뀌는 구성 값만 설정 페이지에 둔다. 팀원 프로젝트 접근 권한처럼 프로젝트 단위로 스코프가 다른 값은 설정 페이지가 아니라 해당 프로젝트 화면에 둔다. PASS/CONDITIONAL/REJECT 판정 로직 자체는 "결정론적 계산 코드"이지 팀장이 바꾸는 설정이 아니므로 설정 화면에 노출하지 않는다.
- **설정 페이지도 역할별로 분리**: 팀장 설정 / 팀원 설정(=팀원 마이페이지와 통합) / 운영자 설정(=관리자 페이지 내부).

## 팀장 전용 쓰기는 서버가 막는다 (2026-08-13)

**화면이 버튼을 감추는 것은 문지기가 아니다.** 설정 「권한」 탭이 「팀장만」이라고
선언한 넷 중 실제로 서버가 막던 것은 **커넥터 연결 하나뿐**이었고, 나머지 셋은 API 를
직접 부르면 그대로 통과했다. 표가 지켜지지 않는 약속을 하고 있었던 것이라 문지기를
세웠다.

`apps/accounts/permissions.py` 의 `require_leader(account_id, detail)` 하나를 쓴다.
팀장이 아니면 403 응답을, 팀장이면 `None` 을 돌려준다 — 호출부는
`if denied := require_leader(...): return denied` 다. 역할 판정은 여전히
`account_role`(가입 경로) 하나뿐이다.

| 막는 것 | 경로 |
|---|---|
| 팀원 초대 | `POST /api/invites/`, `POST /api/invites/{id}/revoke/` |
| 팀 명부 | `POST /api/teams/members/`, `DELETE /api/teams/members/{person_id}/` |
| 팀 업무량 기준 | `PUT /api/teams/settings/` |
| 읽을 Drive 폴더 | `PUT /api/team/folders/` |
| 커넥터 연결 | `apps/connectors` 5곳 — 검사 뒤 `profile` 을 계속 쓰므로 그쪽은 자기 자리에서 본다 |

**조회는 막지 않는다.** 팀원도 명부·팀 기준·메인 모델을 본다 — 막는 것은 쓰기뿐이다.

**커스텀 도구(옛 MCP)은 이 표에서 빠졌다**(2026-08-18). 팀장 전용이 아니라
**팀에 아예 없다** — 등록·수정·삭제·연결 확인이 운영자 콘솔로 갔다
(`apps/ops/views/mcp.py`). **설정 탭 자체를 걷었다** — 팀이 붙일 수 없게 된 뒤로는
볼 수만 있는 탭이었고, 그 서버의 도구를 고르는 자리는 에이전트 편집이다.
조회 API(`GET /api/mcp/servers/`)는 남는다 — 도구 선택 팝업이 쓴다.

**팀 메인 모델도 같은 이유로 빠졌다**(2026-08-18). 기본 채팅 모델은 운영자가
**팀별로** 정한다(`/api/ops/models/teams/<team_id>/default/`). 에이전트별 모델은
빌더에 그대로 있다 — 옮긴 것은 「아무것도 안 고르고 말을 걸었을 때 도는 모델」
하나뿐이다.

**화면에는 이 표를 두지 않는다.** 설정에 「권한」 탭이 있었지만 걷었다(2026-08-13) —
역할이 가입 경로로 정해져 바꿀 수 없으니 **설정할 수 없는 설정**이었고, 서버 규칙을
손으로 베낀 표라 넷 중 셋이 안 지켜지는 동안 아무도 몰랐다. 같은 것을 두 곳에 두면
또 어긋난다. 팀원에게 「팀장만 …할 수 있습니다」를 말하는 것은 **그 일을 하려는
화면**(Connector 탭)의 몫이고, 정본은 이 문서와 아래 테스트다.

새 쓰기 엔드포인트를 만들 때 이 표에 줄이 늘어야 한다. `tests/test_accounts.py`
`LeaderOnlyGuardTests` 가 여섯 경로에 대해 「팀원이 부르면 403」을 고정한다 — 문지기가
조용히 풀리는 것을 막는 유일한 수단이다.

## 현재 구현의 제약

- **프로젝트 조회는 팀 기준이다.** `GET /api/projects/`가 `ProjectRepository.list_for_team`
  (`backend/db/repositories.py:132`)을 쓴다. 하위 쓰기는 `_require_team_project`가 검사한다.

  > ⚠ **2026-08-05 정정 — 이 절은 "소유자 기준이다. `owner_account_id`로만 필터한다"고
  > 적고 있었다.** 2026-08-04에 팀 기준으로 바뀌었다. 테넌트 경계가 팀이므로 팀원도 팀의
  > 프로젝트를 봐야 하고, 소유자로 거르면 **팀장이 등록한 문서를 팀원이 못 여는** 상태가
  > 되어 경계 정의와 어긋난다. 보안 경계를 반대로 적어 둔 것이라 특히 위험했다 — 이
  > 문서를 근거로 소유자 검사를 새로 넣으면 팀 기능이 조용히 깨진다.
