## 1. 전체 레이어

```
[Chat / Builder / Settings / Admin]          frontend (React+Vite)
        │ HTTP/JSON + 스트리밍
        ▼
[Agent Harness]                              ★ 신규 — 이번 프로젝트의 기술 핵심
  Agent Loop · Tool Registry/Execution · Context 관리 · Permission · 실행 로그
        │                │                  │
        ▼                ▼                  ▼
[Pre-built Agent]   [MCP Client]       [Retrieval]
  업무 추출(재구성)     외부 MCP Server      Vector 검색 (기존)
  업무 분배(재구성)     (Jira 등)
  리포트 생성(신규)
        │                                   │
        ▼                                   ▼
[Data Layer — 기존 그대로]
  Connector(Drive·Jira·HR) → 문서 저장소 → RunPod 파싱·청킹·임베딩
  → PostgreSQL 17 + pgvector (doc_block / chunk / vec_idx)
```

Django + DRF + psycopg 직접 SQL, RunPod Serverless 분리, "RunPod은 우리 DB에
접근하지 않는다" 경계는 전부 유지한다.

### `analysis_run_service.py`의 Harness 일반화 가능성 — **없음**

파일 전체가 `AnalysisRunRepository.create(**kwargs)` 호출 한 줄이다. docstring이
스스로 밝히듯 과거 Django ORM Service를 걷어낸 뒤 남은 **자리 표시자**이고,
"각 기능이 구현될 때 이 모듈에서 Repository 호출을 조합한다"는 계획만 적혀 있다.
Loop·상태 전이·재시도·컨텍스트 같은 실행 관리 코드는 한 줄도 없다.

**결론: Harness는 사실상 신규 작성이다.** §2 표의 "실행 관리 로직을 일반화하며
흡수"는 과대평가였다. 대신 흩어져 있는 아래 세 자산을 모아 쓴다.

| 재사용 자산 | 위치 | Harness에서의 쓰임 |
|---|---|---|
| NDJSON 이벤트 규약 | `apps/projects/api_views.py:1070-1092` | 검사를 모두 끝낸 뒤 스트림을 열고, 실패는 마지막 줄 `{"type":"error"}`로 알린다 — Agent Loop 이벤트에 그대로 적용 |
| 진행 이벤트 타입 | `services/task_extraction/service.py:222-293` | `stage` / `queries` / `stage_done` → Harness의 `step` / `tool_call` / `tool_result`로 일반화 |
| 실행 레코드 패턴 | ~~`AnalysisRunRepository` (`repositories.py:1331`)~~ → 삭제됨(2026-08-13, 죽은 코드 스윕) | 참조 무결성 선검사 + `next_short_code`로 짧은 run_id 발급 패턴을 재사용하기로 했으나, 소스 자체가 걷히면서 `agent_run` 적재는 별도의 `AgentRunRepository`(`backend/db/agent_platform.py:436`)로 새로 구현됐다 |

`task_extraction`의 루프는 **단계가 상수 배열(`STAGES`)로 고정**돼 있다. Harness의
Loop는 이 배열 자리에 모델의 Tool 선택이 들어가는 형태 — 골격은 닮았지만 제어
주체가 코드에서 모델로 넘어가므로 재작성이 맞다.

## 3. Agent Harness — 설계 골자

멘토링 §6의 6개 항목별 우리 범위. "반드시 동작 / 구조만 설계"를 구분한다
(멘토링 §17의 범위 계층).

| 항목 | 8월 범위 | 비고 |
|---|---|---|
| Agent Loop | **동작** — 요청 분석 → Tool 선택 → 실행 → 결과 확인 → 반복/종료 | 기존 추출은 단계 고정이었다. 범용 loop가 신규 개발의 중심 |
| Tool Execution | **동작** — Tool Registry(내장 Tool + MCP Tool), Agent별 허용 목록 | Tool Description이 선택 품질을 좌우 (멘토링 §5 Description 강조와 동일 원리) |
| Context 관리 | 단기 **동작**(대화 이력 + Retrieval 주입), Compaction·장기 Memory는 **구조만** | Harness 조사 결과(Deep Agents의 Offloading 패턴) 반영해 확정 |
| Agent-to-Agent | **여지만** — Agent가 다른 Agent를 Tool처럼 호출할 수 있는 인터페이스 자리 | 완성 목표 아님 (멘토링 §6-4) |
| Permission | **구조 설계 + 최소 동작** — Agent 사용/생성 권한, Agent별 Tool 허용 | 기존 팀 경계(`_require_team`) 위에 얹는다 |
| Observability | **최소 동작** — agent_run·tool_call 로그 적재. 대시보드는 여력 | Langfuse 등 연결은 검토 항목 (멘토링 §6-6) |

### 스키마 초안 (팀 논의 후 확정 — `DB/schema.sql` 수동 관리 방식 유지)

```
agent          팀의 Agent 정의: name, description, instruction, model, is_prebuilt
agent_tool     Agent별 허용 Tool (내장 Tool 식별자 또는 mcp_tool 참조)
mcp_server     팀이 등록한 MCP Server: url, 인증 정보, 상태
chat_session   대화 세션 (팀 · 사용자 · 선택 Agent · 프로젝트 컨텍스트?)
chat_message   메시지 (role, content, 스트리밍 완료 여부)
agent_run      실행 단위: 세션, Agent, 상태, 토큰 사용량, 시작·종료
tool_call      실행 로그: run, tool, 입력 요약, 성공/실패, 소요 시간
```

### 3.1 — 8/11 팀 회의 확정 (공통구조 회의자료 안건 5 + 문서 처리)

1. **에이전트 선택 = 사용자 수동 선택기** (Chat 선택기, Figma 확정안 그대로).
   자동 라우팅(description 임베딩 매칭)은 Future Work.
2. **Loop 하드 상한 기본 10** — `agent.max_iterations` 컬럼으로 에이전트별
   조정. 소프트(스캐폴드 문장)+하드 2겹.
   > ⚠ **실측(8/11): 「10」이 실제로 쓰이는 경로가 없다.** `DB/schema.sql:770`의
   > `DEFAULT 10`은 컬럼 기본값일 뿐이고, `apps/agents/serializers.py:27`이
   > `default=6`(min 2·max 20)이라 **API로 만드는 모든 에이전트가 6**이다. 화면도
   > `AgentEditPage`의 `useState(6)`이고 입력 UI는 없다. 시드 2종은 6·4다
   > (`backend/services/createDB/seed_agents.py`). 확정값을 6으로 내릴지, 10을
   > 실제 기본으로 되돌릴지 정할 것 — `작업목록.md` 작업 5-4에서 함께 처리한다.
3. **권한 v1 = Agent별 허용 도구 목록 + side-effect 승인 게이트(확인 카드)**만.
   Claw Code식 모드 체계는 권한 탭 Future 행.
4. **추출 결과 저장 = chat_message 1차 + Jira 등록 성공분만 task 적재.**
5. **스키마 8테이블 컬럼 확정** — agent(+max_iterations)·agent_tool·mcp_server·
   mcp_tool·chat_session(proj_id nullable)·chat_message·agent_run(parent_run_id
   예약)·tool_call(error_code). + 문서 메타용 `doc_meta`(§5).
6. **문서 처리 = A안 채택** — coarse는 요약 임베딩만으로 시작하고 **요약 품질을
   문서 단위 Recall 지표로 검증**, 미달 시 전문 검색 하이브리드(A′,
   12_문서처리 §5)로 확장. Q1(구현 방식)도 세 분석 수렴으로 **직접 구현+구조
   차용 확정**.

이 확정으로 §3 표의 "미확정" 항목은 전부 해소됐다. 상세 근거는
`3_Harness_조사/공통구조_비교_회의자료.md`.

## 4. MCP 실행 구조 (Priority 4 — 최소 범위)

```
Settings: MCP Server 등록(url·인증) → tool 목록 조회·저장
   ↓
Builder: Agent에 MCP Tool 체크
   ↓
Runtime: Harness가 Agent의 Tool 목록에 MCP Tool을 포함해 노출
   → 모델이 선택하면 MCP Client가 호출 → 결과를 Loop에 반환 → tool_call 적재
```

- 대표 시나리오는 **Jira**: 추출 결과 확인 후 Project/Issue 생성 (멘토링 §11).
- 기존 Jira 연동은 Connector(REST 직접 호출)로 이미 있다. **MCP 경로와
  Connector 경로를 당분간 병행**하고, 공식 Jira MCP에 필요 Tool이 없으면 Jira
  REST를 감싼 Custom MCP Server를 우리가 만든다(멘토링 §11) — 이 판단은 MCP
  Server 후보 조사 후.
- 확장(여력): Tool 목록 UI 노출, Agent별 Tool 선택, 관리자 승인, 사용량.

## 5. 문서 처리 — 2단계 검색 (메타데이터 coarse → 온디맨드 fine) — 8/11 전환

> **8/11 결정(PM)**: v1 초안의 "사전 인덱싱 유지·온디맨드 제외" 제안을 폐기하고
> 멘토링 §12 방향으로 전환한다. 콜드 스타트는 아키텍처 제약이 아니라 별도 해결할
> 인프라 과제다.

**등록 시 (폴더 지정하면 자동, 저비용)** — Drive 메타(파일명·경로·수정일) +
가벼운 텍스트 추출(PDF 텍스트 레이어는 CPU로 처리, GPU 파이프라인 불필요) →
LLM 1회로 요약·주제·키워드·문서 유형 생성 → **문서 단위 요약 임베딩 1개** 저장.

**사용 시** — 질의 → 요약 임베딩으로 후보 문서 탐색(coarse) → 상위 후보만 풀
파이프라인(파싱·청킹·임베딩) 온디맨드 처리, **적재는 캐시로 유지** → 청크 검색으로
문단 단위 근거 발췌(fine, E1~E20 품질 그대로). 기준 문서는 선택 시점에 즉시
처리 시작 — 추출이 이미 분 단위 작업이므로 첫 파싱은 진행 카드("문서를 읽는 중")에
흡수된다.

- AS-IS §6이 기각한 것은 "파일명만"의 검색 — 요약 기반 메타는 그 반박에 안 걸린다.
- 리스크: 요약이 담지 못한 세부를 가진 문서의 coarse 누락 → 평가에 **문서 단위
Recall(coarse)** 지표 추가로 검증 (4_평가 §2). hwp·스캔본은 텍스트 추출 실패 시
메타 빈약 → 상태 표기.
- 문서 관리 화면은 "선택 등록 UI"에서 **"메타데이터 목록 + 처리 상태(준비됨/
미처리/실패 재처리)"로 재정의** — 팀 범위 유지(9_Figma_검증 v3의 테넌트 경계
충돌도 함께 해소). 데모 문서는 사전 처리해 둠.

**콜드 스타트 = 인프라 백로그로 분리**: 현재 원인은 모델이 이미지에 안 구워져
매번 수 GB 재다운로드([[runpod-worker-infra]] 참조). 해결 옵션: 모델 이미지 베이킹,
리전 일치 네트워크 볼륨, 필요 시 min worker 1(비용). 데모는 워밍업 체크리스트 유지.
