# Harness 공통 구조 비교 — 아키텍처 v2 확정 회의 자료 (v2 · 설명 보강판)

> **세 분석을 안 읽었어도 이 문서만으로 회의할 수 있게** 항목마다 설명을 붙였다.
> 흐름: §2 용어 → §3 항목별 비교 → §4 이미 합의된 것 → §5 오늘 정할 것 5개.

## 1. 배경 한 단락

우리가 만들 Harness는 "에이전트(=Builder에서 저장한 업무 지시서)를 실제로
일하게 만드는 실행 시스템"이다. 셋이 각자 잘 만들어진 Agent 제품 하나씩을
뜯어봤고, **세 명 모두 같은 결론**에 도착했다: 남의 프레임워크를 통째로
가져오지 말고, 그 제품들이 공통으로 쓰는 **구조(역할 분리)**만 배워서 직접
만들자. 이 문서는 그 공통 구조가 무엇인지, 그리고 아직 안 정해진 5가지가
무엇인지 정리한 것이다.

## 2. 용어 30초 정리

- **Loop** — 에이전트가 일하는 방식: 모델이 판단 → 도구 실행 → 결과 확인 →
  또 판단 → … → 끝. "한 번 묻고 한 번 답하기"가 아니라 이 반복이 에이전트다.
- **Session / Run / Tool Call** — 카톡방(대화 전체) / 그 안의 업무 처리
  1건 / 그 업무 중 도구를 쓴 기록 1건. 3단으로 나눠 기록한다.
- **Context 조립** — 매번 모델을 부를 때 "창고(DB)에 있는 것 전부"가 아니라
  "이번 판단에 필요한 것만" 골라 보여주는 담당.
- **Tool Registry** — 에이전트가 쓸 수 있는 도구 목록 관리소. 우리 내장
  도구(문서 검색·리포트)와 외부 MCP 도구가 같은 창구로 등록된다.
- **HITL (Human-in-the-loop)** — 도구가 바깥 세상에 뭔가 만들기 전(Jira 등록
  등) 사람 결재를 받는 것. 우리 화면의 "확인 카드".
- **Sub-agent / A2A** — 에이전트가 다른 에이전트에게 하청 주기.
- **스캐폴드** — 모든 에이전트에 공통으로 적용되는 사규(고정 프롬프트).
  사용자가 쓴 지시문은 그 뒤에 붙는다.

## 3. 항목별 비교 — 세 제품은 어떻게 하고, 우리는 어떻게 할 것인가

각 항목: **이게 왜 중요한가 → 세 제품의 방식 → 우리 채택안과 이유.**

### ① 에이전트란 무엇인가

에이전트를 코드로 짜면 사용자가 못 만든다 — 비개발자 Builder의 성립 조건.
OpenCode는 에이전트를 "실행 코드가 아니라 **설정 레코드**"로 다루고, 셋 다
같은 관점이다. → **우리도 Builder 저장물(agent 테이블) = 실행 정의.** 새
에이전트를 만드는 데 배포가 필요 없어진다.

### ② 실행 기록 3단 (Session / Run / Tool Call)

"어제 그 요청, 어디서 실패했지?"에 답하려면 기록이 계층으로 나뉘어야 한다.
OpenCode가 가장 명확했다: 대화(Session)와 실행(Run)을 분리하고, Run 안에
Tool Call을 남긴다. → **chat_session / agent_run / tool_call 3단 채택.**
이 기록이 그대로 평가 지표(성공률·실패 단계)의 원천이 된다 — 별도 측정
코드를 만들 필요가 없다.

### ③ 선기록 (먼저 쓰고 실행)

OpenCode는 "Jira 이슈를 만들려 한다"를 **먼저 기록하고 나서** 실제 호출한다.
실패해도 "무엇을 하려다 실패했는지"가 남는다. → **채택.** 부분 실패
화면("17/20 등록 — 3건 실패")이 정확히 이 기록에서 나온다.

### ④ Loop와 반복 상한

Loop는 모델이 "도구를 더 쓸까, 답을 낼까"를 매번 판단하며 돈다. 문제는
멈추지 않을 때다. 지훈 분석: 프롬프트로 "N번까지만"이라고 지시하는 건
**권고일 뿐**이라 코드가 횟수를 세다 강제 종료하는 **하드 상한**이 따로
필요하다. 주연 분석이 이를 실증한다 — Claw Code CLI는 상한 기능이 있는데
실제로는 안 쓰고 있어서, 도구 호출이 끝날 때까지 무한정 돈다.
→ **상한 2겹 채택** (프롬프트 권고 + 코드 강제). 값은 §5-②에서 결정.

### ⑤ Context — 저장과 제공의 분리

대화가 길어질수록 전부를 모델에게 다시 보여줄 수 없다(비용·한도). OpenCode:
"저장된 것"과 "이번에 보여줄 것"을 분리하는 조립 계층. Deep Agents: 중간
결과를 파일로 내려놓기(Offloading). Claw Code: 커지면 요약. → **조립 계층만
v1 구현**(대화 이력+실행 상태+문서 검색 결과). 요약·Offloading은 자리만
만든다 — 대표 E2E는 도구 2~3회 호출이라 아직 필요 없다.

### ⑥ Memory — 무엇을 기억하나

준억 제안이 이해하기 쉽다: ①대화에서 말한 것(Conversation) ②지금 어디까지
실행했나(Run 상태) ③회사 문서에 뭐가 있나(Knowledge=기존 Data Layer).
→ **3층 채택.** "사용자 성향을 오래 학습하는" 장기 메모리는 셋 다 핵심으로
안 다뤘고 우리도 **비적용** — 격리·최신성·평가 부담 대비 E2E에 안 쓰인다.

### ⑦ Tool Registry와 Permission

주연 분석의 7단계가 표준형이다: 도구 정의 → Registry 등록 → 모델에 노출 →
모델이 호출 결정 → **권한 검사** → 실행 → 결과 반환. Claw Code는 권한을
"전체 모드 × 도구별 요구 권한 × 사용자 규칙"의 조합으로 판정하는 정교한
체계를 갖고 있다. → **Registry 7단계는 그대로 채택.** 권한은 v1에선 단순화
— Agent별 허용 목록 + 바깥에 쓰는 도구는 확인 카드(§5-③에서 확정).

### ⑧ MCP 연결

준억 분석: MCP는 Harness 내부가 아니라 **외부에서 도구를 공급받는 경로**이고,
접점은 Registry 하나면 된다. → 이미 `11_MCP_설계.md`로 확정 진행 중(커스텀
서버 수용이 핵심 증명, 특권 경로 금지). 이 회의에서 재론 불필요.

### ⑨ Sub-agent (하청)

셋 다 결론이 같다: 호출 자체는 쉽지만 **운영(권한 상속·비용 배분·순환 방지·
평가)이 본체**라 지금 만들면 리스크만 얹는다. → **인터페이스 여지만**:
Loop를 대화 화면에 종속되지 않는 순수 함수로 짜두고, agent_run에
parent_run_id 컬럼 자리만 예약. 나중에 델리게이션 도구 하나로 이어붙일 수
있다.

## 4. 이미 합의된 것 (3/3 일치 — 오늘 재논의 불필요)

직접 구현+구조 차용 / 실행 기록 3단+선기록 / 상한 2겹 / HITL 필수 /
장기 메모리 비적용 / Sub-agent 여지만 / Registry 단일 창구.

## 5. 오늘 결정할 것 5개

**① 에이전트 선택 방식** — 사용자가 요청할 때 어느 에이전트가 일할지 누가
정하나. (A) 사용자가 화면에서 직접 선택 — 지금 Figma가 이 모양. 확실하지만
에이전트가 많아지면 번거로움. (B) 시스템이 요청 내용을 보고 자동 매칭 —
편하지만 "잘못 매칭되면?"이라는 평가·데모 리스크가 생김. (C) 수동 기본 +
자동 제안. **제안: A로 v1 확정.** 자동 매칭은 지금 있는 pgvector 검색을
에이전트 설명에 걸면 되는 가벼운 확장이라 Future Work로 자연스럽다.

**② 하드 상한 기본값** — Loop 강제 종료 횟수. 대표 E2E가 정상 2~3회
호출이므로 여유를 둬서 **제안: 기본 10회, agent 테이블에 컬럼을 둬서 에이전트별
조정 가능.**

**③ 권한 수준** — Claw Code식 모드 체계(읽기 전용/작업 쓰기/전체 허용…)까지
갈 것인가. **제안: v1은 "Agent별 허용 도구 목록 + 바깥에 쓰는 도구는 확인
카드" 두 가지만.** 모드 체계는 권한 탭에 Future 행으로만.

**④ 추출 결과 저장** — 지금은 추출 결과가 응답에만 있어 새로고침하면
사라진다(AS-IS의 알려진 문제). **제안: 대화 기록(chat_message)에 저장되는
것으로 1차 해결 + Jira 등록에 성공한 업무만 task 테이블에 정식 적재.**
세 제품 모두 Session 기록 중심이라 이 방식과 부합한다.

**⑤ 스키마 확정** — 신규 8테이블(agent, agent_tool, mcp_server, mcp_tool,
chat_session(proj_id 포함), chat_message, agent_run(parent_run_id 예약),
tool_call(error_code 포함)) 컬럼을 이대로 확정할지. 확정되면 멘토링 후
마이그레이션 작성.
