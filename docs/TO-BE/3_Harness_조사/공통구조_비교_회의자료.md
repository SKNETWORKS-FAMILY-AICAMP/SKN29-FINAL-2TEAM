# Harness 공통 구조 비교 — 아키텍처 v2 확정 회의 자료

> 2026-08-11. 세 분석(준억 OpenCode 2,082줄 · 지훈 Deep Agents 108+347줄 ·
> 주연 Claw Code 1,025줄) 수합본. **이 문서로 회의 → 결정 → 아키텍처 v2 반영.**
> §3(수렴)은 재논의 불필요, §5(안건)만 결정하면 된다.

## 1. 세 줄 요약

1. **3/3 수렴: 프레임워크 통째 도입이 아니라 직접 구현 + 구조 차용.** 가져올
   것은 코드가 아니라 책임 분리다 — Q1은 사실상 답이 나왔다.
2. 세 제품이 공통으로 가진 뼈대가 우리 스키마 초안(chat_session·agent_run·
   tool_call)과 이미 맞는다 — 방향 수정 없이 구체화만 하면 된다.
3. 결정이 필요한 것은 5건(§5). 그중 실질 쟁점은 **에이전트 선택 방식** 하나다.

## 2. 공통 구조 비교표

| 항목 | OpenCode (준억) | Deep Agents (지훈) | Claw Code (주연) | → 우리 채택안 |
|---|---|---|---|---|
| Agent 정의 | 실행 코드가 아니라 **설정(레코드)** | create_agent에 모델·프롬프트 주입 | Runtime이 설정을 읽어 실행 | Builder 저장물 = 실행 정의 (`agent` 테이블) |
| 실행 단위 | **Session ≠ Run 분리**, Runner가 실행 | thread 단위 State | Session 파일 + Runtime | `chat_session` / `agent_run` / `tool_call` 3단 |
| Loop | LLM→Tool→Result→반복, 종료는 모델 판단 | ReAct + 계획 되뇌기(recitation) | Tool 호출 없는 응답 = 최종 답변. **상한 미사용 주의** | 동일 Loop + **상한 2겹(소프트 프롬프트+하드 max_iterations)** — Claw Code의 "상한 없음"은 반면교사 |
| Context | **저장 vs 이번 턴 제공 분리**, 조립 계층 | 파일시스템 Offloading | System Prompt+대화 기록, 커지면 요약 | Context Manager 조립(대화 이력+Run 상태+Retrieval). Compaction·Offloading은 구조만 |
| Memory | 3층(대화/실행 상태/회사 지식) | 세션 간 기억은 선택 확장 → **비적용** | Session 파일·프로젝트 지시 파일 → **복제 안 함** | 3층 채택. 장기 Memory 비적용 (3/3 일치) |
| Tool Registry | 허용 목록·Schema·실행을 한 경계에서 | Tool 위임도 하나의 Tool | Spec 등록→노출→Call→**Permission 검사**→실행 | Registry 단일 경계 + 내장/MCP 동일 인터페이스 |
| Permission | "사용 가능"과 "지금 실행 승인" 2단 | HITL 필수 | **모드(ReadOnly~FullAccess)+규칙 종합 판정** | v1: Agent별 허용 목록 + side-effect 승인 게이트. Claw Code식 모드 체계는 구조만 (§5-③) |
| MCP | **외부 Tool 공급 경로**, Client/Adapter | Registry에 얹힐 자리 확인 | (해당 절 없음 — 자체 Tool 중심) | 11_MCP_설계 확정안 그대로 |
| Model 연결 | Provider/Resolver 분리 | model-agnostic 문자열 교체 | Model Interface 분리 | `agent.model` + Resolver. 단계별 분리(luna/sol)는 기존 자산 |
| Sub-agent | Child Session — 제외 | task() Tool — **Loop 순수 함수화만** | (Worker 상태 머신 — 단계적) | 인터페이스 여지만 (3/3 일치): Loop를 chat 비종속 순수 함수로 + `parent_run_id` 자리 |
| 실행 기록 | **side effect 선기록**→실행→결과 | — | 실행 전 검사 단계 존재 | tool_call 선기록 패턴 채택 (평가 실패 단계 분포의 원천) |
| Sandbox/실행 격리 | 멀티노드 등 제외 | Shell 비적용 | 실행 전 검사+격리 — **필요 확인 후 단계적** | v1 비적용 — 우리 Tool은 코드 실행이 아니라 API 호출 |

## 3. 수렴 — 회의에서 재논의 불필요 (3/3 일치)

- 직접 구현 + 책임 분리 차용 (Runtime/Session/Context/Registry/Permission/Model 분리)
- HITL 승인은 필수, side-effect 전 게이트
- 장기(세션 간) Memory 비적용
- Sub-agent는 여지만 — Loop 순수 함수화 + parent_run_id 컬럼 자리
- Tool Registry가 내장·MCP를 같은 인터페이스로

## 4. 각 분석의 고유 기여 (v2에 개별 반영)

- **준억**: Session/Run 분리 도식(스키마와 1:1), 선기록 trace, Memory 3층 명명,
  Jira Connector+MCP 병행 논거
- **지훈**: 공통 스캐폴드+instruction 합성(코드 내 템플릿 — 전 에이전트 즉시
  반영), 상한 2겹 논거, A2A "안 만드는 진짜 이유"(운영 요소 목록), MCP 보안
  경계 제기(→11_MCP_설계 §4로 답함), 라우팅은 Deep이 아니다(pgvector 재활용)
- **주연**: Loop 순서도(구현 시 그대로 옮길 수 있는 수준), Permission을
  "모드×Tool 요구 권한×규칙"으로 판정하는 모델, Tool Spec→Registry→노출→검사→
  실행 7단계, "상한 미사용" 실제품의 위험 사례
