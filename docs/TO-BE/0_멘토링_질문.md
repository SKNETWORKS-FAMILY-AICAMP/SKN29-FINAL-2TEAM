# 8/12 온라인 멘토링 — 질문 종합

> TO-BE 문서 5종(전부 v1)에 흩어진 미결정 사항을 한 장으로 모았다. 각 질문에
> **우리 제안**을 붙였다 — "어떻게 할까요"가 아니라 "이렇게 하려는데 맞는지"로
> 물어야 멘토링 시간이 판단에 쓰인다. 출처 표기: [IA] [아키] [평가] [E2E].

## 핵심 3 — 범위를 가르는 질문 (여기서 시간의 절반)

**Q1. [결정 보고] Harness = 직접 구현 + 구조 차용 — 검증 요청** [아키 §3.1·§6]
세 분석(OpenCode·Deep Agents·Claw Code)이 전부 같은 결론으로 수렴해 8/11
팀 회의에서 확정했다. 전제: 기존 orchestration은 12줄 스텁이라 어차피 신규
작성(재사용은 NDJSON 규약·이벤트 타입·실행 레코드 3종). 차용 구조:
Session/Run 분리·선기록 trace·스캐폴드+instruction·상한 2겹(기본 10)·
Registry·Loop 순수 함수화. 함께 확정: 에이전트 선택은 수동 선택기(자동
라우팅은 Future). **멘토님께**: 이 결정이 3주 일정·학습 목표 관점에서 타당한지,
빠진 위험 요소가 있는지 검증 요청.

**Q2. 업무 분배(STEP 5)를 v1 데모에서 제외** [E2E §4-1]
분배 로직은 중간발표 시점 미완(화면만 존재). 제안: E2E는 "추출→확인→Jira
등록"으로 확정하고 분배는 Future Work. 빼도 Connector·문서처리·Agent·MCP·Tool
Calling을 전부 시연할 수 있다.

**Q3. [결정 보고] 문서 처리 = 2단계 검색(A안) + 요약 품질 검증 게이트** [아키 §5, 12_문서처리]
8/11 확정: 폴더 지정 시 메타+요약 임베딩만 자동 등록(CPU 저비용), 사용 시 후보
문서만 온디맨드 풀 처리(캐시 유지) 후 청크 검색. 팀 반론("긴 문서는 요약으로
못 찾는다")을 반영해 **요약 품질을 문서 단위 Recall로 실측 검증하고, 미달 시
추출 원문의 전문 검색(tsvector) 하이브리드로 확장**하는 예비안까지 준비됨
(업계 조사: 전량 인덱싱·요약 계층·무인덱스 3갈래 실존). 콜드 스타트는 인프라
과제로 분리. **멘토님께**: 이 단계적 접근(A → 검증 → A′)이 타당한지 확인 요청.

## 구조 — 판단 확인

**Q4. Chat과 Project의 관계** [IA §4-1, 아키 §3]
대화가 프로젝트에 귀속되는가(프로젝트별 Chat), 팀 Chat에서 프로젝트를 컨텍스트로
선택하는가. 제안: **팀 Chat + 프로젝트 컨텍스트 선택** — 검색 경계=팀이라는 기존
결정과 맞고, `chat_session`에 nullable `proj_id`로 구현 부담도 작다.

**Q5. 추출 결과 영속화** [아키 §3, E2E §2-3]
기존에 `task` 테이블 0행(응답으로만 존재). 제안: v1은 `chat_message`에 남는
것으로 1차 해결, `task` 정식 영속화는 Jira 등록 성공 시점에만. 매 추출을 다
적재하면 확인 전 데이터가 쌓인다.

**Q6. Jira 생성 단위** [E2E §4-2]
매번 Project 신규 생성 vs 기존 Project에 Issue 추가. 데모 임팩트는 전자,
권한·정리 부담은 후자가 작다. 제안: 데모는 Project 생성까지, 실사용 기본값은
Issue 추가.

**Q7. 확인 스텝 UX** [E2E §4-3]
전체 일괄 승인 vs 업무별 체크박스. 제안: 업무별 체크(정직성) + "전체 선택"
기본값(데모 템포).

## 평가 — 근거의 강도

**Q8. 골든셋 규모** [평가 §8-1]
G-DOC 5~8문서, G-QUERY 20~30질의(2인 라벨), G-TASK 기준 문서 1~2건 팀 합의,
G-PROMPT 15~20(Tool 불필요 1/3). 이 규모가 발표 근거로 서는지, 어디를 늘려야
하는지.

**Q9. LLM-as-judge 허용 여부** [평가 §8-2]
근거 적합성·업무 매칭을 사람 평정 대신 LLM 채점으로 자동화해도 되는지.
허용되면 반복 측정이 가능해지고, 안 되면 수작업 평정을 1회로 제한해야 한다.

**Q10. 현업 효과 제시 방식** [평가 §8-3]
"기존 수작업 X분 → Agent Y분, 표본 1건 명시" 형태가 PoC 보고 관점에서
적절한지.

## 기타 (시간 남으면)

**Q11.** `/onboarding/jira-project`의 위치 — Connector 설정인가 Project 생성
플로우인가 [IA §4-2]. 제안: Connector 설정으로 이동, 온보딩 필수에서 제외.
**Q12.** Agent 편집 권한 — 팀 공유 vs 작성자만 [IA §4-3]. 제안: v1은 팀 전체
공유(Permission 구조는 설계만).
**Q13.** 기존 대시보드 화면을 리포트 뷰어로 재활용 vs 완전 제거 [IA §4-4].
제안: 재활용 — "부하 리포트 생성" Tool의 출력 화면으로.
**Q14.** 시연 영상 백업 제작 여부 [E2E §4-4]. 제안: 제작(중간발표 경험 재활용).
**Q15.** Figma 화면이 문서보다 앞서간 3건 일괄 확정 [9_Figma_검증 D] — 기본 에이전트 「복제」 / 공개 범위 「나만 보기」 / 확인 카드 「다시 정리해줘」 재실행. 셋 다 화면은 좋지만 구현 범위가 늘어난다 — Figma에 빨간 「멘토링 확정 필요」 주석으로 마킹되어 있음.
**Q16.** MCP 데모의 증명 포인트 확인 [11_MCP_설계 §0~1] — 우리 프레임: 핵심은 "처음 보는 커스텀 MCP 서버를 붙일 수 있느냐"(등록→tool 자동 발견→Builder→실행의 일반 경로, 특권 경로 금지). 데모 대표 서버는 기존 Jira REST를 감싼 자체 MCP를 "고객사 커스텀 MCP의 대역"으로 사용(인증 재사용·부분 실패 통제, 공식 Atlassian은 여력 검증). 이 프레임과 "여력 시 라이브 등록 시연"이 플랫폼 주장으로 충분한지.
