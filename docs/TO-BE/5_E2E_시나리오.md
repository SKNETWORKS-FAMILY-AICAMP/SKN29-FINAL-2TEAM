## 1. 단계별 상세 — 컴포넌트·실패 모드·처리

| STEP | 하는 일 | 컴포넌트 (기존/신규) | 실패 모드 | 처리 |
|---|---|---|---|---|
| 1 | 요청 분석 — Agent가 "추출→확인→Jira 등록" 계획 수립 | **신규** Harness Loop | 의도 오해석 (Tool 불필요로 판단) | Tool Selection 평가(G-PROMPT)로 사전 검증. 데모 발화는 리허설로 고정 |
| 2 | 관련 문서 검색 — 프로젝트 컨텍스트에서 기준 문서 확인 | 기존 Retrieval + doc | 기준 문서 미지정 | Agent가 후보 문서를 제시하고 사용자가 고르는 되묻기 스텝 (기존 `/tasks/distribution/documents`의 선택 UI 흡수) |
| 3 | Retrieval — coarse(요약 임베딩으로 후보 문서) → 미처리 후보는 온디맨드 처리(진행 카드 "문서를 읽는 중") → fine(청크 검색) | 기존 pgvector + **신규 메타 임베딩** | 관련 청크 0건 / coarse 누락 / 후보 처리 실패 | "근거를 찾지 못했다" 정직 반환. 처리 실패 문서는 사유와 함께 제외 표기(표-제외 철학) |
| 4 | Task Extraction Agent 실행 (5단계 파이프라인) | 기존 task_extraction → Pre-built Agent 재구성 | OpenAI 오류·타임아웃 / 근거 확인 안 된 업무 | NDJSON 스트리밍으로 단계 표시(기존 그대로). 근거 없는 업무는 생성 안 함(기존 규칙). 스트림 중 실패는 마지막 줄 `error`(기존) |
| 5 | (필요 시) 업무 분배 Agent | 기존 workload + recommendation | 분배 로직 미완(AS-IS §8) | **v1 데모 범위에서 제외 검토** — §3 미결정 1 |
| 6 | 사용자 확인 — 업무 목록+근거 열람, 수정/제외 | 기존 `/tasks/extraction` UI를 Chat 스텝으로 이식 | 사용자가 일부만 승인 | 선택된 업무만 STEP 7로. 확인 대기 시간은 E2E 시간 지표에서 제외(평가 §5) |
| 7 | Jira MCP Tool 호출 | **신규** MCP Client | MCP Server 연결 실패 / 인증 만료 | 호출 전 연결 상태 점검(설정 화면의 상태 표시 재사용). 실패 시 업무 목록은 보존하고 재시도 버튼 |
| 8 | Jira Project/Issue 생성 | Jira 측 | **일부 이슈만 생성 실패** (rate limit·필수 필드) | ★ PARTIAL_RESULT 핵심 구간 — §2 |
| 9 | 완료 결과·근거 반환 | Harness | — | 생성된 이슈 링크 + 업무별 근거(E번호→원문) + 실패분 목록 |

## 2. PARTIAL_RESULT 정책 (P0 미확정이던 것 — 확정안 제안)

원칙은 파싱 파이프라인의 기존 철학과 동일하다: **"표 한 줄 때문에 본문 수백
블록을 잃지 않는다"** (AS-IS §4). 부분 실패는 전체 실패로 승격하지 않고, 무엇이
빠졌는지 드러낸다.

1. **성공분은 롤백하지 않는다.** 업무 20건 중 17건이 Jira에 생성되고 3건이
   실패하면, 17건은 남기고 실패 3건과 사유를 목록으로 반환한다. 롤백하면
   사용자가 다시 처음부터 해야 하고, Jira에 이미 생성된 이슈 삭제는 더 위험하다.
2. **실패분은 재시도 가능한 단위로 보존한다.** 실패한 업무 3건만 담은 재시도
   버튼 — 전체 재실행이 아니다.
3. **단계 실패의 결과물도 보존한다.** STEP 7~8이 전부 실패해도 STEP 4~6의 업무
   목록·근거는 Chat에 남는다 (추출 결과 영속화 문제 — 아키텍처 §3 미결과 연결.
   최소한 `chat_message`에 남는 것으로 1차 해결).
4. **화면 표기**: "17/20 등록 완료 — 3건 실패 (사유)" 형태. 성공처럼 보이게
   뭉개지 않는다. `missing_fields` 철학의 연장.

## 4. 확정 (2026-08-11 · 팀 결정 — 멘토링에 올리지 않는다)

1. **STEP 5(업무 분배) — 넣는다. 단 하드코딩 기능이 아니라 「기본 제공 에이전트」로.**
   필요한 도구가 이미 전부 Registry에 있다 — `task_extraction`(업무+근거) ·
   `people_list`(팀원·스킬, 5차 단계 1) · `workload_report`(주간 부하·여유,
   화면과 **같은 계산기**) · `jira_create_issues`(`assignee_account_id` 필드 보유,
   `apps/connectors/clients.py:579-582`가 Jira `fields.assignee` 로 매핑).

   > ⚠ **「도구가 이미 전부 있다」는 정확하지 않았다 (2026-08-12).** 도구는 있었지만
   > `task_extraction` 이 모델에게 **건수만** 돌려줘서, 아래 instruction 이 맞출
   > `required_role` 이 모델 컨텍스트에 아예 없었다. 실제로 "이 결과를 등록해 줘"에
   > 「추출 결과가 확인되지 않습니다」라고 답했다. 반환값을 넓혀 고쳤다(`8025981`).
   >
   > **등록 순서도 바뀌었다.** Jira 가 아니라 **우리 플랫폼이 먼저다** —
   > `task_register` 신설(`task` 테이블). 지금까지 추출 결과는 어디에도 저장되지
   > 않아 Jira 를 안 쓰는 팀은 결과를 가질 방법이 없었다. STEP 은
   > 「추출 → 확인 → **우리 등록** → (원하면) Jira 등록」이 된다.
   >
   > 시드는 1종 추가가 아니라 **기존 2종을 「기본 에이전트」 하나로 합쳤다.**

   그래서 분배 「로직」은 신규 코드가 아니라 **instruction 한 덩어리**다 —
   "추출된 업무의 `required_role` 을 팀원 스킬과 맞추고, 남은 여유가 적은 사람은
   피하고, 근거가 없으면 미지정으로 남겨라."

## 5. 평가와의 연결

이 시나리오가 곧 평가 대상이다: E2E 성공률·시간·실패 단계 분포는
`4_평가_설계.md` §5, 확인 대기 제외 규칙 동일. G-TASK 골든셋 문서 = 데모 기준
문서로 통일해 정답셋 구축과 데모 준비를 한 번에 한다.
