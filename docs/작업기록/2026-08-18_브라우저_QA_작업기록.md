# 2026-08-18 — 배포본 브라우저 QA

> **결함 11건을 찾아 10건을 고쳤다.** 그중 **셋은 단위 테스트로 원리적으로 못
> 잡는 것**이었고, **둘은 내가 같은 날 오전에 넣은 것**이었다.
>
> 밟은 대상은 로컬이 아니라 **배포본(https://halil-ai.site)** 이다. 이 문서의 값은
> 「무엇이 고쳐졌나」가 아니라 **「왜 그때까지 아무도 몰랐나」**에 있다.

## 0. 왜 이 QA 가 필요했나

오전에 `jihun` 12커밋을 `main` 에 병합하고 배포했다. 테스트는 700개가 돌고 있었고
`--check` 로 스키마도 맞췄다. **그 상태에서 화면을 열자 첫 질문부터 깨졌다.**

이 문서에 적힌 결함 중 **테스트가 잡을 수 있었던 것은 하나도 없다.** 전부
「돌기는 도는데 틀린 것을 말한다」 부류다.

## 1. 서버가 30초에 채팅을 죽이고 있었다 (`0020e67`)

문서 질문을 하면 `document_search` 가 돌다가 **「요청을 보내지 못했습니다」**로
끝났다. 브라우저 콘솔은 `ERR_HTTP2_PROTOCOL_ERROR` 뿐이라 원인이 안 보였다.
서버 로그에 답이 있었다 —

```
[CRITICAL] WORKER TIMEOUT (pid:8)
[ERROR] Worker (pid:8) was sent SIGKILL! Perhaps out of memory?
```

`Dockerfile` 의 gunicorn 에 `--timeout` 이 없어 **기본값 30초**였다. 문서 승격
(RunPod 파싱·임베딩)은 몇 분이 걸린다. 짧은 인사말은 되고 문서 질문만 죽어서
「검색이 고장났다」로 보이지만, 실제로는 **서버가 스트리밍 중인 워커를 죽인 것**
이다.

> ⚠ **작업목록의 「서버 상한 600초」는 사실이 아니었다.** 8/15 에 클라이언트를
> 90초로 맞춰 뒀는데 서버는 그 전에 30초에 죽는다.

**`gthread` 로 함께 바꿨다.** sync 워커는 한 요청이 워커를 통째로 잡는데 워커가
2개뿐이라, 타임아웃만 늘리면 긴 문서 질문 **둘이 겹치는 순간 로그인·화면 로딩까지
전부 멈춘다**(시연 중 두 사람이 동시에 물으면 그대로 멈춘다). 스트리밍은 대부분
응답 대기(I/O)라 스레드가 맞고, DB 연결은 요청마다 새로 열리므로 스레드 안전
문제도 없다. 2 워커 × 8 스레드 = 동시 16.

## 2. 「내 파일」 검색이 배포 이래 한 번도 안 됐다 (`e3aaea6` · `afbd4a3`)

**이번 QA 의 가장 큰 건이다.**

파일을 올려 **검색에 사용을 켜고** 물었는데 「확인할 수 있는 팀 문서가 없어…」로
답했다. DB 를 직접 불러 좁혔다 —

```
coarse_search(account_id=None)   -> []
coarse_search(account_id=UA002)  -> [DC003 QA_반려동물_정책.md]   ← SQL 은 멀쩡
```

`_injected()` 가 `document_search` 에 **`team_id` 만** 주입하고 있었다.
`account_id` 가 없으면 두 가지가 한꺼번에 죽는다 —

1. `coarse_search` 가 `owner_account_id` 조건을 못 걸어 **내가 켠 내 파일이
   후보에 안 들어온다**(M④)
2. `registry` 의 `not_indexed[:PROMOTE_TOP_N] if account_id else []` 가 빈
   리스트가 되어 **온디맨드 승격이 통째로 꺼진다** — 팀 문서도 본문 색인이
   영영 안 된다

**오류가 아니라 「문서가 없습니다」로 끝나서 기능이 없는 것처럼 보인다.**

### 이 부류가 왜 안 잡혔나

승격은 2026-08-15(`efbf54f`)에 **이 값이 온다는 전제로** 만들어졌는데, 주입하는
자리는 2026-08-12 이후 그대로였다. 그리고 —

- **두 런타임 모두에 있었다.** 새 런타임(`adapters.py`)이 주석에 「`runner.py` 의
  `_injected()` **실측 이관**」이라고 적어 두고 **빠뜨림까지 옮겨 왔다.**
- **테스트가 그 버그를 정답으로 고정하고 있었다.**
  `EXPECTED_INJECTED_CONTEXT["document_search"] = ("team_id",)` 는 「레거시와
  같아야 한다」는 뜻이었는데, 레거시가 틀렸으니 테스트도 함께 틀렸다 —
  **옮긴 값이 맞는지는 쟀지만 그 값이 옳은지는 아무도 묻지 않았다.**

`ToolWiringTests` 에 두 건을 더했다. 이 부류는 **실행하지 않으면 오류가 안 나서**
단위 테스트가 유일한 방어선이다 — `document_list` 가 한 번도 동작한 적 없던 것을
잡은 그 테스트와 같은 자리다.

## 3. 도구가 말한 사유를 새 런타임이 버렸다 (`73bc79c`)

「기준 문서에서 업무 뽑아줘」에 화면은 **「요청을 끝내지 못했습니다」**만 띄웠다.
서버 로그를 보니 도구는 정확히 말하고 있었다 —

```
ToolInputError: 어느 프로젝트의 업무를 뽑을지 정해지지 않았습니다.
                프로젝트를 먼저 고르세요.
```

**QA 체크리스트가 기대한 바로 그 문장인데 화면까지 오지 못했다.**
`factory._run()` 이 도구 예외를 잡지 않아 LangGraph `ToolNode` 가 그대로 다시
던지고 실행이 통째로 죽는다 — **제품이 이유를 알고 있는데 사용자에게 말하지 않는
상태**였다.

레거시는 이미 정책을 갖고 있었다: `_SPEAKABLE_ERRORS = (ToolInputError,
RepositoryError, OAuthError)` — 「문자열을 그대로 응답에 싣는다. 화면에만 감출
이유가 없다」. 새 엔진이 **같은 목록**을 쓰게 했다(밑줄을 떼 공개). 두 엔진이 다른
목록을 들면 같은 실패가 한쪽에서만 설명된다.

**그 밖의 예외는 그대로 올린다** — 라이브러리 예외 문자열에는 쿼리·문서 원문·
토큰이 섞일 수 있고, 삼키면 진짜 장애가 「도구가 뭐라고 했다」로 둔갑한다.

고친 뒤: 오류 카드 대신 **「어느 프로젝트의 기준 문서에서 업무를 뽑을까요?
프로젝트명을 알려주세요.」** 로 되묻는다.

## 4. 기본 챗 에이전트에 도구가 0개였다 (`81151bd`)

오전에 백필로 만든 기본 챗(AG003·AG004)이 도구를 하나도 안 들고 있었다. 정식
경로 `provision_default_chat_agent()` 가 원래 안 붙인다. 그 결과 **기본 상태에서
제품의 대표 발화가 전부 실패**했다 —

| 물어본 것 | 기대(§B-0) | 실제 |
|---|---|---|
| 기준 문서에서 업무 뽑아줘 | 「프로젝트를 먼저 고르세요」 | 「기준 문서가 대화에 **첨부**되어 있지 않습니다. 문서를 **업로드**하거나 내용을 **붙여** 주세요」 |
| 우리 팀원 누구누구야? | 팀원 목록 | 「연결된 업무·인사 도구에서 조회할 수 없다」 |

첫 줄이 특히 나쁘다 — **이 제품에 없는 방식**으로 사용자를 보낸다.

Chat 의 「+」로 붙이면 동작한다. 하지만 §B-0 는 **기본 상태**를 재는 게이트이고,
처음 쓰는 사람은 그 버튼을 눌러야 한다는 것을 모른다. 옛 「코파일럿」은 14종을
들고 있었으니 새 기본 챗이 0종인 것은 그 대비 후퇴다.

**읽기 도구만 붙인다**(PM 결정 · 10종). 기본값이 남의 Jira 에 이슈를 만들거나
업무를 고칠 수 있으면 안 된다. 목록을 박지 않고 **`side_effect` 플래그**에서
끌어온다 — 그게 「밖을 바꾸는가」의 정본이라, 새 도구가 늘어도 읽기면 자동으로
붙고 쓰기면 자동으로 빠진다.

이미 만들어진 두 팀은 **새 버전을 발행하지 않고** 현재 버전에 빠진 것만 더했다 —
발행하면 `agent_version_id` 가 바뀌어 기존 대화의 고정이 끊긴다.

## 5. 화면이 없는 기능을 광고했다 (`5cef263`)

「지금 어떤 도구를 쓸 수 있나요?」에 **「파일 탐색 · 파일 읽기·수정 · 새 파일 작성 ·
서브 에이전트 실행」**이라고 답했다. deepagents 의 **가상 파일 도구**를 자기
능력으로 읽은 것이다(`DEFAULT_EXCLUDED_BUILTIN_TOOLS` 가 `delete` 하나만 뺀다).

**도구를 걷지 않고 프롬프트로 막았다** — `read_file` 은 `FilesystemMiddleware` 가
필수로 요구하고(없으면 ValueError), 장기 메모리가 그 파일 공간에 읽고 쓴다.
걷으면 메모리 설계가 같이 무너진다. 대신 **「그것들은 작업용 임시 공간이지
사용자에게 주는 기능이 아니다」**를 못박고, 할 수 있는 일은 붙어 있는 업무 도구로
말하게 했다.

고친 뒤: 「현재 연결된 업무용 외부 도구는 없습니다. 따라서 문서 검색, 업무 관리,
프로젝트 관리, 사람 조회, 외부 서비스 연동 같은 작업은 직접 수행할 수 없습니다.」

같은 커밋에서 함께 —

- **진행 카드가 답변 뒤에도 「몇 분 걸립니다」라고 했다.** 단계 아이콘은 `running`
  을 보고 회전을 멈추는데 **하단 한 줄만 무조건 그려지고 있었다.**
- **「본문 추출 실패」가 틀린 방향을 가리켰다.** 「텍스트가 들어 있는 파일로 다시
  올려 주세요」였는데, 실제로 제일 흔한 실패는 **본문이 200자보다 짧은 것**이다
  (185자 파일이 이 문구를 받았다). 추출기는 사유를 다섯 갈래로 갈라 만드는데
  `doc_meta` 에 담을 칸이 없어 `as_row()` 가 버린다.

## 6. 내가 같은 날 오전에 넣은 것 둘

**① 같은 카드에 「사용 중지」가 둘이었다** (`3e4412d`)

전날 문구를 통일하며 `remove` 의 「내리기」를 「사용 중지」로 바꿨는데, 그 카드에는
이미 `disable` 의 「사용 중지」가 있었다. **둘은 다른 동작이다** —

| 버튼 | API | 결과 |
|---|---|---|
| disable | `POST /agents/<id>/disable/` | `DISABLED` — 「다시 활성화」로 되돌린다 |
| remove | `DELETE /agents/<id>/` | 서버가 `ARCHIVED` 로 내린다. 목록에서 사라지고 되돌리는 화면이 없다 |

토스트가 양쪽 다 「비활성화했습니다」라 같은 일로 착각했다. **화면에서 두 버튼이
나란히 보이는 것을 봐야 잡히는 종류다** — 문자열만 훑어서는 안 나온다.

**② 수정 성공 메시지가 한 번도 안 떴다** (`f430e2e`)

`save()` 가 `setNote()` 로 띄운 직후 `cancelEdit()` 를 부르는데 그 안에
`setNote('')` 가 있었다. **주소를 바꿨을 때의 「도구를 다시 읽어야 합니다」 경고까지
함께 사라지던 것이 진짜 문제**다 — 못 보면 운영자는 도구가 비워진 줄 모른다.

## 7. 모델에게 쓴 지시문이 화면에 나왔다 (`448a1f1`)

「…로 뭉뚱그리지 않는다」 같은 명령문이 비개발자 화면에 그대로 있었고, 백틱·별표도

함께 — 서브 에이전트 안내의 `**지금 발행된 버전**` 별표, 확인창 제목 둘의

| `/ops/connectors` 의 「상세 보기」가 글씨처럼 보인다 | `.tableWrap button` 문제의 실제 사례. `data-button` 이 안 붙은 표가 더 있다 |

## 9. 밟은 범위

**1순위 — 내가 문구를 바꾼 화면 10개.** `/agents` · `/agents/versions` ·
`/agents/:id/edit` · `/settings/my-files` · `/projects` · `/projects/:id` ·
`/ops/models` · `/ops/connectors/:id` · `/ops/mcp` · 채팅.

**2순위 — 에이전트 빌더·버전 관리(지훈 소관).** 만들기 → 도구 선택 → 저장(v1
발행) → 활성화 → 팀 공유 → 즐겨찾기 → Chat 드롭다운 → 실행 → 새 버전 수정(v2) →
삭제. **흐름은 전부 정상이었고 문구만 걸렸다.** `agent_favorites`(오늘 적용한
마이그레이션)도 실제로 돈다.

**3순위 — QA 체크리스트 §B-0.**

| | 항목 | 결과 |
|---|---|---|
| ① | 「+ 새 대화」 → 프로젝트 펼침, 첫 항목 「팀 전체 문서」 | ✅ |
| ② | 추출 발화 → 「프로젝트를 먼저 고르세요」 | ✅ (§3·§4 로 고침) |

## 10. 남길 교훈

**「테스트가 전부 통과했다」가 「돈다」를 뜻하지 않는다.** 이 문서의 결함 11건 중
단위 테스트가 잡을 수 있었던 것은 **하나도 없다.** 갈래는 셋이었다 —

1. **배선이 끊긴 채로 조용히 반쪽이 된 것**(§2) — 오류가 안 나고 「없습니다」로
   끝나서 기능이 없는 것처럼 보인다.
2. **말할 수 있는 것을 말하지 않은 것**(§3·§5·§7) — 제품이 이유를 알고 있는데
   화면이 안 옮기거나, 모델에게 쓴 말을 사람에게 그대로 보여준다.
3. **화면에서 나란히 봐야만 보이는 것**(§6①) — 같은 카드에 같은 이름의 버튼이
   둘이라는 것은 코드를 읽어서는 안 나온다.

**그리고 테스트가 버그를 정답으로 고정할 수 있다**(§2). 「레거시와 같은가」를
재는 테스트는 레거시가 틀렸을 때 함께 틀린다 — **옮긴 값이 맞는지**와 **그 값이
옳은지**는 다른 질문이다.

## 11. 승인 게이트가 대화를 조용히 끊던 것 (⑪⑫)

쓰기 도구(`task_register`)를 붙이고 등록을 요청하니 **화면에 아무것도 안 나왔다.**
서버는 200 으로 정상 응답했는데도 그랬다. 스트림을 직접 열어 보니 —

```
agent_started → tool_started(task_register) → (끝)
```

승인 게이트가 그래프를 멈췄는데 **「멈췄다」는 이벤트를 아무도 안 보냈다.**

### 원인

LangGraph 는 인터럽트를 `{"__interrupt__": (Interrupt(...),)}` 로 내보낸다.
그런데 `events.py` 의 `convert()` 는 `updates` 페이로드를 `node_name -> dict` 로
순회하면서 `isinstance(node_output, dict)` 를 검사한다 — **인터럽트의 값은 dict 가
아니라 tuple** 이라 거기서 걸러져 조용히 버려졌다.

배선이 반쪽이었다: `interrupt_on`(멈추는 쪽)은 8/18 Phase 7 에 붙었는데, 알리는
쪽·재개하는 쪽이 없었다. `prompts.py` 의 「승인 카드는 아직 구현되지 않았다」가
그 흔적이다.

| | 레거시 harness | 새 agent_runtime (고치기 전) |
|---|---|---|
| 게이트가 멈춤 | ✅ | ✅ |
| 「승인 대기」 이벤트 | ✅ | ❌ |
| 승인 카드 | ✅ | ❌ |
| 재개 경로 | ✅ | ❌ |

**안전 쪽으로는 다행이었다** — 게이트가 실행은 막았고 `task` 는 0행이었다.
조용히 등록되지는 않았다.

### 고친 것 (3dcbb49 · 9912beb)

- `events.py` — `__interrupt__` → `awaiting_confirmation`. **레거시와 같은 모양**
  (`tool_ref`/`tool_name`/`arguments`/`resume`)으로 냈다. 화면의 확인 카드와
  저장(`_persist`)이 이미 그 모양을 읽고 있어서 **양쪽 다 안 고쳤다.**
- `stream_adapter`/`executor` — `Command(resume=...)` 로 멈춘 자리를 잇는다.
  새 발화를 넣지 않는다: 멈춘 대화는 Checkpointer(RDS)에 그대로 있다.
- `api_views` — 확인 API 가 엔진에 따라 갈라진다. 레거시는 대화 전체를 되돌려
  받아 다시 돌지만, 새 엔진은 **「무엇을 승인했는가」만** 넘기면 된다.
- `prompts.py` — 「HITL 은 없다」가 이제 거짓이라 고치고, 레거시의 [외부 변경]
  문구를 되살렸다. 게이트를 모르면 모델이 카드가 이미 묻는 것을 말로 한 번 더
  묻고, 승인 전에 「등록했습니다」라고 말한다.
- `ChatPage.tsx` — **고를 목록이 없는 카드의 「승인」이 0건 등록이 되던 것.**
  그 카드의 승인은 「전부 승인」인데 화면이 빈 배열을 보내서 서버가 「0건만 남겨
  달라」로 읽었다. 승인은 성공처럼 보이고 결과는 비는 최악의 조합이다 —
  게이트가 실제로 뜨면서 비로소 닿을 수 있게 된 경로다.

### 확인

- `task` **0행 → 15행**(TK001~TK015, `src_type=EXTRACTED`, `status=PROPOSED`).
- 승인 카드가 **새로고침 뒤에도 복원**된다(저장된 `awaiting_confirmation` 에서).
- 답변이 **문장으로** 나온다 — 표가 글자로 깨지던 것(9da8b29)도 함께 확인됐다.
- 전체 테스트 859건 중 실패 4건, **전부 커넥터의 개발용 URL 불일치**(운영
  컨테이너에서 돌린 탓)로 이 변경과 무관하다.

### 아직 안 밟은 것

**부분 선택(체크를 풀고 일부만 등록)은 끝까지 밟지 못했다.** 체크박스가 있는
카드는 추출과 등록이 **같은 턴**일 때만 뜨는데, 이번 시험은 추출이 이전 턴이라
목록 없는 대체 카드로 갔다. 선택을 인자에 반영하는 규칙(`_decisions_for` →
`edit` 결정)은 단위로 확인했지만, **`Command(resume=...)` 의 `edit` 가 실제로
줄어든 인자로 실행되는지는 화면에서 확인하지 않았다.**

밟으려면 한 대화에서 추출부터 등록까지 이어서 하고 체크를 몇 개 풀면 된다 —
다만 `task` 행이 더 쌓인다.

### 덧붙여 눈에 띈 것

- 모델이 「투입공수를 **0시간으로 등록했습니다**」라고 했는데 DB 의 `effort` 는
  `NULL` 이다. 안 넣은 것을 넣었다고 말한 셈이라 정직 표기에 어긋난다.
- 생각 과정이 여전히 **영어**다(기존에 지훈님께 넘긴 건과 같은 것).
- 목록 없는 확인 카드가 「업무 0건」이라고 머리에 적는다 — 실제로는 15건이
  대상이라 서로 어긋나 보인다.

### ⑨ — 처음엔 실패했다

도구 설명은 이미 「Jira 이슈가 아니다 — Jira 쪽은 jira_get_issues 다」까지
말하고 있었다. 없던 것은 **「비어 있는 결과는 결론이 아니다」**였다. 그 자리에
한 줄을 더했다(a4377ef).

고친 뒤 같은 문장으로 다시 물으니 —

- Jira 현황 카드가 뜬다. 제목 「**AI Platform** 업무 현황」(`AIP` 키가 아님),
  전체 15건, 지난 마감이 빨갛다.
- 답변이 **둘 다** 말한다: 「등록된 우리 업무: 없음 / Jira 업무: 총 15건」
- 근거도 둘 다 밝힌다: 「팀 업무 등록 목록과 Jira 프로젝트 AIP 조회 결과」

> 이 결함은 **오늘 만든 것**이다. 아침까지 기본 대화 에이전트는 도구가 0개라
> 이 경로에 닿을 수 없었다. 읽기 도구를 붙이자 `task_list` 와 `jira_get_issues`
> 가 같은 물음을 두고 경쟁하기 시작했다 — **기능을 늘리면 판단할 거리도 는다.**

### ⑪ 부분 선택 — 계약까지만 확인했다

체크박스가 있는 카드는 추출과 등록이 **같은 턴**일 때만 뜬다. AI Platform 은
기준 문서가 없어서(제품이 그렇게 답했다) 그 경로를 열 수 없었고, ERP
프로젝트로 밟으면 **데모 데이터에 업무 행이 더 쌓인다.**

대신 설치된 `human_in_the_loop.py` 소스로 계약을 맞춰 두었다 —

```
if decision["type"] == "edit" and "edit" in allowed_decisions:
    edited_action = decision["edited_action"]
    return ToolCall(name=edited_action["name"], args=edited_action["args"], id=tool_call["id"]), None
```

`_decisions_for()` 가 만드는 모양(`{"type": "edit", "edited_action": {"name", "args"}}`)과
정확히 같고, `allowed_decisions` 에 `edit` 가 들어 있는 것도 실제 인터럽트
값에서 확인했다. **다만 클릭으로 끝까지 밟지는 않았다.**
