## 0. 작업 전제 — 반드시 지킬 것

1. **코드는 한 줄도 고치지 않는다.** `DB/`·`apps/`·`services/`·`backend/`·`frontend/`·`runpod_worker/`·`config/` 전부 금지. 정본은 코드이고 문서를 코드에 맞추는 작업이다. 8/6 발표를 앞두고 실행 검증이 끝난 코드다.
2. **정본 문서는 `docs/AS-IS/시스템_전체_설계.md`** (274줄). 다른 문서와 어긋나면 이쪽이 맞다. 스키마 정본은 `DB/schema.sql`.
3. **외과적 수정만.** 틀린 문장·표 셀·수식·숫자만 바꾼다. 문서 전체 재작성 금지, 문체·구조 유지.
4. **과거 기록은 본문을 고치지 않는다.** `docs/회의록/`, `docs/작업기록/`의 날짜 붙은 문서는 상단 배너만 단다. 단 `Jira_부하계산_ToDo.md`와 `2026-08-03_부하계산_작업지시서.md`는 지금도 실행 지침으로 읽히므로 예외 — 본문을 고치고 `(2026-08-05 정정)`을 붙인다.
5. **줄바꿈은 CRLF다.** 편집 도구가 LF로 바꾸지 않도록 주의. 확인: `grep -c $'\r' <파일>`이 `wc -l`과 같아야 한다.
6. 검증은 `git diff --ignore-all-space`로 본다 — 이 저장소는 CRLF churn 때문에 `git status`에 350개 넘게 뜬다.

### 이 패치에서 가장 중요한 한 줄

`DB_시작_가이드.md` §4.3의

```sql
UPDATE doc SET proj_id = NULL WHERE proj_id IS NOT NULL;
```

이 **비멱등인데 108줄이 "모두 멱등이라 여러 번 실행해도 안전하다"고 단언한다.** 재실행한 팀원은 모든 프로젝트의 기준 문서 지정을 잃고, `doc_role='PRIMARY' AND proj_id IS NULL`인 고아 행이 남는다. 부분 유니크 인덱스가 NULL을 서로 다르게 보므로 에러도 안 나고, 되돌리는 코드 경로도 없다. **내일 발표 전에 팀원 4명이 이 블록을 다시 돌릴 가능성이 높다.**

패치는 조건을 이렇게 좁힌다:

```sql
UPDATE doc SET proj_id = NULL WHERE proj_id IS NOT NULL AND doc_role IS DISTINCT FROM 'PRIMARY';
```

- `AND doc_role IS NULL`로는 안 된다. 그 시점 옛 문서는 `doc_role`이 `'PLAN'`·`'MEETING_NOTE'` 등이고 이를 비우는 UPDATE는 **226줄, 즉 189줄보다 뒤**에 있다. `IS NULL`로 좁히면 정작 정리해야 할 행이 전부 빠진다.
- 줄 삭제도 안 된다. 아직 한 번도 안 돌린 팀원의 볼륨에는 근거 없는 `proj_id`가 남아 있고 그걸 비우는 게 원래 목적이다.
- 새 모델에서 `proj_id`가 채워진 행은 **항상** `doc_role='PRIMARY'`와 짝이다(`document_pipeline.py:172`, `repositories.py:334`가 두 컬럼을 함께 세팅/해제). 그래서 이 조건이 레거시 행만 정확히 겨냥한다.

**패치 적용 후 이 한 줄은 반드시 눈으로 확인할 것.**

#### D-5. **사람이 정해야 하는 것 — 고치지 말 것**

`docs/AS-IS/설계/업무량_계산_MVP_계약.md`은 **계약서**라 방향이 반대일 수 있다. 아래 2건은 문서가 맞고 **코드가 틀렸을 가능성**이 있다.

**(1) §2③ 할당 조건 — 78줄**

```
문서: and (due_at < period_end  OR  status_category = 'IN_PROGRESS')
코드: due_at이 있으면 due < period_end만 본다 (IN_PROGRESS를 안 봄) — if/else
```

마감이 창 밖인 **진행 중** 업무를 문서는 분자에 넣고 코드는 Backlog로 뺀다. 계약서 머리말(11~14줄)이 드는 2주 창 예시(122.5% → 102.86%)가 정확히 이 경우라, **어느 쪽이 그 숫자를 만드는지 재현해 보고 결정해야 한다.**

**(2) §2 미일정 Backlog 정의 — 88줄**

```
문서 §2:   마감 없고 미시작인 일
문서 머리말 28~29줄:  창 밖 업무는 전부 모인다
코드:      창에 안 들어온 것은 전부 (calculator.py:266-271)
```

**같은 문서 안에서 §2와 머리말이 모순이다.** 코드 주석은 "예전에는 `due_at is None`인 것만 담아서 2주 창에서 팀 잔여 548h 중 346h가 증발했다"고 적는다 — 코드가 맞고 §2 본문이 낡았을 가능성이 높지만, 계약서 본문이라 확인 후 고칠 것.

> **계약서 조항별 준수 판정: 30개 중 26개 지킴 · 3개 어김 · 1개 부분.** 어긴 3개가 위 2건 + §6 마감 위험 신호(이미 구현됐는데 미룬 것으로 적힘)다.
