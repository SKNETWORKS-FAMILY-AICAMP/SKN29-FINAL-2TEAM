# 2026-08-19_02 — LangSmith/Langfuse 1~4단계 구현 + 이메일 마스킹

> `2026-08-19_01_작업계획.md`의 작업 순서 1~4단계를 실제로 구현했다. 실 키는
> 아직 없어서(5단계 대기) 런타임 동작(실제로 대시보드에 trace가 찍히는지)은
> 확인 못 했다 — `py_compile` 통과까지만 검증.

## 1. LangSmith 배선 (`config/settings/base.py`)

`LANGCHAIN_TRACING_V2`/`LANGCHAIN_API_KEY`/`LANGCHAIN_PROJECT`/
`LANGCHAIN_ENDPOINT` 4개를 `env(...)` 패턴으로 추가했다. **우리 코드는 이
값을 다시 참조하지 않는다** — `langchain-core`/`langgraph`가 `os.environ`을
직접 읽고, 이미 파일 맨 위 `environ.Env.read_env(BASE_DIR / ".env")`가 `.env`를
`os.environ`에 채워 두므로 이것만으로 동작한다. 여기 적어 둔 건 이 파일을
"외부 설정 전체 목록"으로 보는 관례를 따르기 위한 문서화용.

## 2. Langfuse 의존성 (`requirements/base.txt`)

`langfuse>=3.0,<4.0` 추가. LangSmith는 `langchain-core`에 이미 내장돼 있어
별도 패키지가 필요 없다.

## 3. `services/agent_runtime/tracing/callbacks.py` 구현

원래 의도적으로 빈 스텁이던 파일을 채웠다.

- `get_langfuse_callback()` — `settings.LANGFUSE_PUBLIC_KEY`/`SECRET_KEY`가
  둘 다 있어야 `CallbackHandler()`를 만들고, 없으면 `None`(`WEB_SEARCH_API_KEY`와
  같은 "키 없으면 그 기능만 조용히 꺼진다" 원칙).
- `_ensure_client_configured()` — 프로세스당 한 번만 `Langfuse(...)` 싱글턴
  클라이언트를 구성한다. env var 이름(`LANGFUSE_HOST` vs `LANGFUSE_BASE_URL`
  등 SDK 버전마다 다를 수 있는 이름)에 기대지 않고 `settings.LANGFUSE_*`를
  명시적으로 넘긴다 — 이 저장소의 "비밀값은 settings를 거친다" 관례.

## 4. `stream_adapter.py`/`executor.py` 콜백 주입

- `stream_adapter.py`의 `stream()`에 `callbacks`/`trace_metadata` 파라미터
  추가 — `stream_kwargs["config"]`에 `callbacks`/`metadata`로 얹는다.
  `thread_id`가 없어서 `config` 키 자체가 아직 없을 수 있어 `setdefault`로
  먼저 만든 뒤 채운다.
- `executor.py`의 `run()`이 매 실행마다 `get_langfuse_callback()`을 불러
  콜백을 얻고, `trace_metadata`에 `langfuse_session_id`(=`context.session_id`)/
  `langfuse_user_id`(=`context.account_id`)/`langfuse_tags`(팀 id, agent id)를
  실어 보낸다 — Langfuse 대시보드에서 세션·계정·팀 단위로 걸러 볼 수 있게.
  콜백이 `None`이면(키 없음) `callbacks=()`, `trace_metadata=None`이라
  `runtime.stream()` 호출 모양이 이전과 완전히 같다.

## 5. 이메일 마스킹 — 지훈 리뷰로 추가

구현을 다 끝낸 뒤 지훈이 "trace에 도구 호출 인자·결과가 통째로 실려서 실제
데이터(Jira, 팀원 이름·업무배정 등)가 외부로 나가는 거 아니냐"고 문제 제기.
조사 결과:

- `langfuse_user_id=context.account_id`는 문제없음 — `account_id`는
  `user_account.account_id VARCHAR(5)`(`UA001` 같은 코드)고, 이메일은 별도
  컬럼이라 여기 안 실린다.
- **`jira_get_issues`/`jira_create_issues`가 담당자 `assignee_email`을 실제
  값 그대로 돌려준다**(`apps/connectors/clients.py`의 `_jira_issue_row()`)—
  이게 유일하게 확인된 이메일 유출 경로. 다른 도구(`people_list`/`task_list`/
  `document_search`/`absence_list`/`workload_report`)엔 이메일 필드가 없다.

**조치**: Langfuse v3 SDK가 정확히 이 용도의 훅(`mask_otel_spans`)을
지원한다(공식 문서 "Redact email addresses" 예제와 동일한 방식) —
`_ensure_client_configured()`에서 `Langfuse(..., mask_otel_spans=_mask_otel_spans)`로
등록. export 직전 span 속성 문자열에서 이메일 패턴(`_EMAIL_PATTERN` 정규식)을
`[REDACTED_EMAIL]`로 치환한다 — 사용자에게 가는 실제 응답이나 우리 DB
(`tool_call.input_summary`)는 그대로 두고, **Langfuse로 나가는 사본만** 가린다.

**LangSmith는 이 마스킹이 없다** — env var만으로 자동 연결되는 별도 경로라
이 훅을 안 거친다. 지훈과 상의해 **LangSmith는 마스킹 방법을 찾기 전까지
당장 끄기로 결정**(`.env`에 `LANGCHAIN_API_KEY`를 채우지 않는다 — 비어
있으면 `LANGCHAIN_TRACING_V2`가 켜져 있어도 실제로는 안 붙는다). 검증
단계(작업 5)는 Langfuse만으로 진행한다.

## 6. 검증

- `python -m py_compile`로 수정한 파일(`config/settings/base.py`,
  `services/agent_runtime/executor.py`, `stream_adapter.py`,
  `tracing/callbacks.py`) 문법 확인 — 통과.
- 실 키가 없어 런타임 확인(실제로 Langfuse 대시보드에 trace가 찍히는지,
  이메일이 정말 마스킹되는지)은 **아직 안 했다** — 작업 5단계(지훈이 실 키
  발급받은 뒤)에서 확인 필요. 특히 마스킹은 `mask_otel_spans`가 받는
  span 속성 키 이름이 실제로 어떻게 나오는지(LangChain 계측이 tool 결과를
  어느 속성 키에 담는지) 실측 전이라, 정규식이 값 전체를 스캔하는 지금
  구현은 이론상 안전해도 실제로 이메일이 지워지는지는 눈으로 봐야 한다.

## 7. 남은 일

  Langfuse에 trace 잡히는지 + 이메일이 실제로 마스킹되는지 같이 확인.

  등) 정해지면 재논의.
