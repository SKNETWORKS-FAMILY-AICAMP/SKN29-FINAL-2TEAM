# 2026-08-19_01 — LangSmith + Langfuse 도입 작업계획

> Deep Agents(services/agent_runtime/) 검증·평가를 위해 LangSmith와 Langfuse를
> 함께 붙이기로 함. **이 문단은 최초 계획 시점의 상태다.** 당시에는 실 계정/키가
> 없었다 — 코드는 `env(..., default="")`
> 패턴이라 키 없이도 먼저 짤 수 있고, 키가 없으면 해당 트레이싱만 조용히
> 꺼진 채로 동작해야 한다(다른 외부 연동과 같은 원칙, WEB_SEARCH_API_KEY 등).
> 이후 실제 키를 사용한 양쪽 서비스 검증과 이메일 마스킹 검증까지 완료했으며,
> 최종 상태는 §8(진행 상태)과 §9(평가 착수 전 배선 점검)를 기준으로 한다.

## 1. 왜 둘 다인가 — 역할 분담

같은 일을 두 번 하는 게 아니라 관심사가 다르다.

- **LangSmith** — Deep Agents가 내부적으로 어떻게 실행됐는가, LangGraph의
  run·node·tool 흐름을 얼마나 잘 재현하는가, 문제를 얼마나 빨리 디버깅할 수
  있는가. `langchain-core`/`langgraph`가 이미 호환되는 트레이싱 훅을 내장하고
  있어서 env var만 켜면 코드 변경 없이 붙는다.
- **Langfuse** — 운영 trace와 평가 결과를 장기적으로 어떻게 축적할 것인가,
  Dataset·Experiment로 변경 전후를 어떻게 비교할 것인가, 비용·데이터
  소유권·셀프호스팅을 어떻게 관리할 것인가. `CallbackHandler`를
  `runtime.stream()` 호출부에 직접 주입해야 해서 코드 변경이 필요하다.

## 2. 셀프호스팅 vs 클라우드 — 클라우드로 결정

Langfuse 셀프호스팅은 Postgres + ClickHouse + Redis/Valkey + S3 호환 오브젝트
스토리지 + 앱 컨테이너 2개(web/worker)가 필요하다. MIT 라이선스 코어가 클라우드
기능과 거의 동일하고(Organization Creators·Instance Management API·UI
커스터마이징 정도만 Enterprise 전용) 데이터 소유권 이점이 있지만, 지금 팀
규모·트래픽에서는 그 인프라(4종 신규 스토리지 컴포넌트)를 새로 운영하는 비용이
클라우드 요금(Hobby 무료 / Core $29 / Pro $199 + 초과사용료)보다 크다고 판단—
**Langfuse Cloud로 간다.** 리전은 JP(`https://jp.cloud.langfuse.com`)로
결정(2026-08-19 정정 — 팀이 한국에 있어 EU/US보다 지연이 짧다). 다른
리전으로 가입하게 되면 US/EU/HIPAA URL로 바꾼다(`LANGFUSE_HOST` env var
하나만 바꾸면 됨 — 코드 변경 없음).

## 3. 작업 순서

1. **LangSmith 배선** — `config/settings/base.py`에 `LANGCHAIN_TRACING_V2`/
   `LANGCHAIN_API_KEY`/`LANGCHAIN_PROJECT`/`LANGCHAIN_ENDPOINT` 문서화(실제
   소비자는 `langchain-core`가 `os.environ`을 직접 읽는 것 — 이미
   `environ.Env.read_env(BASE_DIR / ".env")`가 `.env`를 `os.environ`에 채워
   두므로 코드 쪽에서 별도로 `settings.X`를 참조할 필요는 없다. 여기 적는 건
   이 파일이 "외부 설정 전체 목록"이라는 이 저장소의 관례를 따르기 위함).
2. **Langfuse SDK 의존성 추가** — `requirements/base.txt`에 `langfuse` 핀.
3. **`tracing/callbacks.py` 구현** — 지금은 의도적으로 빈 스텁. 키가 있으면
   `langfuse.langchain.CallbackHandler`를 만들어 주고, 없으면 `None`(호출 쪽이
   조용히 건너뛴다).
4. **`stream_adapter.py`/`executor.py`에 콜백 주입** — `runtime.stream(...)`의
   `config["callbacks"]`에 얹는다. 동시에 `config["metadata"]`에
   `langfuse_session_id`(=`context.session_id`)/`langfuse_user_id`(=
   `context.account_id`)/`langfuse_tags`(팀 id, agent id)도 실어서 Langfuse
   대시보드에서 세션·계정 단위로 걸러 볼 수 있게 한다.
5. **지훈 환경에서 두 대시보드 동시 검증** — 실제 키를 발급받아 `.env`에 채운
   뒤, 챗에서 한 번 돌려서 LangSmith·Langfuse 양쪽에 같은 실행이 잡히는지 확인.
6. **Langfuse Dataset으로 평가 시나리오 등록** — 먼저 로컬의 고정 PDF와
   개인 테스트 Jira를 사용한 개발용 Dataset `v0.1`로 평가 실행기와 채점기를
   검증한다. 이후 프로덕션에서는 같은 시나리오 구조와 공통 안전 규칙을
   재사용하되, 문서명·담당자·기한·Jira 프로젝트처럼 실제 데이터에 종속된
   정답만 팀 데이터에 맞춘 Dataset `v1.0`으로 교체해 다시 평가한다.

1~4는 키 없이 코드만으로 끝낼 수 있다. 5부터는 지훈이 직접 계정을 만들고 키를
`.env`에 넣어야 진행할 수 있다.

## 4. 외부 반출 데이터 — 개인정보 마스킹 (2026-08-19, 지훈 리뷰로 추가)

`CallbackHandler`가 잡는 trace에는 프롬프트·모델 응답뿐 아니라 **도구 호출
인자·결과가 통째로** 실려서 Langfuse/LangSmith 클라우드(둘 다 외부 서드파티
서버)로 나간다. 실제로 확인한 결과:

- `langfuse_user_id=context.account_id`는 문제없다 — `account_id`는
  `user_account.account_id VARCHAR(5)`(`UA001` 같은 짧은 코드)고, 이메일은
  별도 컬럼이라 여기 안 실린다.
- `jira_get_issues`/`jira_create_issues`(services/harness/registry.py,
  `apps/connectors/clients.py`의 `_jira_issue_row()`)가 담당자
  `assignee_email`을 실제 값 그대로 돌려준다 — 이게 유일하게 확인된 이메일
  유출 경로다. 다른 도구(`people_list`/`task_list`/`document_search`/
  `absence_list`/`workload_report`)의 결과에는 이메일 필드가 없다(이름은
  있음).

**정책**: Langfuse는 `tracing/callbacks.py`의 마스킹 훅으로 export 직전
이메일 패턴을 정규식 치환한다(원본 응답·DB에는 영향 없음, Langfuse로
나가는 사본만 가림). **LangSmith는 아직 이 마스킹이 없다** — env var만으로
자동 연결되는 별도 경로라 이 훅을 안 거친다.

**결정(2026-08-19, 뒤집힘 — §6 참고)**: 처음엔 LangSmith는 마스킹 방법을
찾기 전까지 끄기로 했었다. 이후 `hide_inputs`/`hide_outputs` 커스텀
`Client` 방식을 실제로 조사·구현해서, 지금은 **LangSmith도 마스킹된
상태로 켤 수 있다** — 아래 §6 참고.

## 5. 재검토(2026-08-19) — 마스킹 API 실제 SDK와 불일치, 순환 import로 서버 다운

문서·코드가 다 준비된 것처럼 보였지만, `requirements/base.txt`에 핀만 되어
있고 실제로 설치는 안 돼 있던 `langfuse` 패키지를 직접 설치해 실제 API로
검증하니 두 가지 실제 결함이 나왔다.

**① 마스킹 파라미터 이름이 틀렸다.** §4의 `mask_otel_spans`는 실제 설치되는
버전(`langfuse==3.15.0`, 핀 범위 `>=3.0,<4.0` 안)의 `Langfuse.__init__()`에
없는 인자다 — 그대로 부르면 `TypeError`. `MaskOtelSpansResult`/`OtelSpanPatch`
타입도 `langfuse.types`에 없다. 진짜 파라미터는 `mask`이고 모양도 다르다
(`langfuse.types.MaskFunction` — span을 순회하는 게 아니라 관측값 `data`
하나를 받아 마스킹한 값을 그대로 돌려주는 함수). **실 키를 넣는 순간(작업
5) `get_langfuse_callback()`의 넓은 예외 처리가 이 `TypeError`를 삼켜서,
Langfuse 연동 전체가 로그 한 줄 말고는 아무 표시 없이 조용히 안 붙을
뻔했다** — `tracing/callbacks.py`를 실제 API에 맞게 다시 짰다(`mask=
_mask_data`, 문자열/dict/list를 재귀적으로 훑어 이메일만 치환).

**② `executor.py`의 콜백 import가 순환 import를 만들어 서버 자체가 안
떴다.** 모듈 맨 위에서 `from services.agent_runtime.tracing.callbacks
import get_langfuse_callback`을 했더니, `tracing` 패키지 초기화
(`tracing/__init__.py`)가 `backend.db.agent_platform`을 다시 불러오는데,
그 시점에 `agent_platform.py`는 **자기 자신이 아직 다 안 만들어진 채로**
`services.agent_runtime`을 부르던 중이었다(`agent_platform.py` →
`services.agent_runtime.subagents.validation` → 패키지 초기화 →
`executor.py` → `tracing.callbacks` → `tracing/__init__.py` →
`agent_platform.py`, 한 바퀴 돌아 자기 자신). 실제로
`docker compose restart web`을 해보고 나서야 `ImportError: cannot import
name ... from partially initialized module`로 **서버가 아예 기동조차
안 되는 것**을 확인했다 — import를 실제로 쓰는 함수(`AgentExecutor.run()`)
안으로 옮겨 순환을 끊었다.

두 문제 다 실제 SDK 설치 + 서버 재기동 + 백엔드 테스트 878개 + 실제 채팅
메시지 왕복까지 검증 완료. `tests/test_executor.py`의 가짜 스트림 어댑터가
새로 늘어난 `callbacks`/`trace_metadata` 인자를 못 받아 테스트 6개가 깨져
있던 것도 함께 고쳤다(이 리뷰와 별개로 이미 있던 문제).

## 6. LangSmith 마스킹 구현 — "당장 끄기" 결정을 뒤집는다

§4에서 "LangSmith는 마스킹 방법을 찾기 전까지 끈다"고 결정했는데, 실제
설치된 SDK(`langsmith==0.11.0`, `langchain-core`의 의존성으로 이미 깔려
있음)로 직접 조사해 보니 방법이 있었다.

**실제 API(직접 설치·확인)**:
- `langsmith.Client(hide_inputs=..., hide_outputs=...)` — 둘 다
  `Callable[[dict], dict]`을 받는다(공식 시그니처, `Client.__init__`
  docstring 실측). Langfuse의 `mask`와 모양이 같아서 `_mask_data`를 그대로
  재사용한다(`_mask_dict`는 키워드만 맞춘 얇은 래퍼).
- `langchain_core.tracers.LangChainTracer(client=...)` — 우리가 만든
  마스킹 `Client`를 쓰는 tracer를 명시적으로 만들 수 있다.

**"자동 연결(env var)과 충돌하지 않는가"가 핵심 의문이었다.** `LANGCHAIN_
TRACING_V2=true`를 켜 두면 `langchain-core`가 자기 기본 `Client`(마스킹
없음)로 별도 트레이스를 또 보내는 게 아닌가 — 실제 설치된
`langchain_core.tracers.context._get_trace_callbacks()` 소스를 직접 읽어
확인: `callback_manager.handlers`에 **이미 `LangChainTracer`가 있으면
자기 것을 또 안 붙인다**(소스 주석: "If it already has a LangChainTracer,
we don't need to add another one... this would likely mess up the trace
hierarchy"). 그래서 우리가 마스킹된 tracer를 명시적으로 `callbacks`에
얹어 두면, env var는 그대로 켜 둬도 이중·비마스킹 트레이스가 안 생긴다 —
LangFuse처럼 명시 주입 하나로 충분하고, env var를 끌 필요가 없다.

**구현**(`tracing/callbacks.py`): `get_langsmith_callback()` 추가 —
`settings.LANGCHAIN_API_KEY`가 없으면 `None`(Langfuse와 같은 원칙).
있으면 마스킹된 `Client` → `LangChainTracer`를 만들어 돌려준다.
`executor.py`는 `_tracing_callbacks()` 헬퍼로 Langfuse·LangSmith 콜백을
한 리스트로 모아 `run()`/`resume()` 양쪽에 넘긴다.

**검증(가짜 키)**: `python manage.py test`(1017개) 통과, 서버 재기동 정상,
실제 채팅 왕복 정상. `LANGCHAIN_API_KEY`를 가짜 값으로 채운 상태에서
`get_langsmith_callback()`을 직접 호출해 `LangChainTracer` 인스턴스가
만들어지는 것과, 그 안의 마스킹 함수가 중첩된 dict 안 이메일까지 실제로
가리는 것을 직접 확인했다.

**검증(실 키, 2026-08-19 — 작업 5의 LangSmith 절반)**: 지훈이 실제
`LANGCHAIN_API_KEY`를 `.env`에 채운 뒤, 테스트 에이전트로 이메일
(`kim.jihun@example.com`)이 든 메시지를 실제로 보내고, `langsmith.Client
.list_runs()`로 **LangSmith 서버에 실제로 기록된 원본 데이터**를 직접
조회했다. 결과: 기록된 입력에 `REDACTED_EMAIL`은 있고 원본 이메일
문자열은 어디에도 없음 — 마스킹이 진짜 운영 환경에서 작동하는 것을
서버 쪽 데이터로 직접 확인했다. Langfuse는 아직 실 키가 없어 이 확인이
남아 있다.

## 7. Langfuse 실 키 검증 — 마스킹이 대부분 안 걸리는 버그를 발견·수정

지훈이 `LANGFUSE_PUBLIC_KEY`/`SECRET_KEY`를 `.env`에 채운 뒤, §6의
LangSmith 실키 검증과 같은 방식으로 진행했다: 컨테이너를 띄우고(이미지
자체에 `langfuse` 패키지가 설치돼 있지 않아 `docker compose build web`부터
다시 해야 했다 — `requirements/base.txt`엔 있었지만 이전에 검증용으로
설치·제거를 반복한 게 이미지에 반영 안 된 상태였다), 테스트 에이전트로
이메일(`langfuse.verify.jihun@example.com`)이 든 메시지를 실제로 보내고,
Langfuse REST 조회 API(`langfuse.api.client.FernLangfuse` —
`client.trace.list(session_id=...)`/`client.observations.get_many
(trace_id=...)`)로 **서버에 실제로 기록된 원본 데이터**를 직접 읽었다.

**발견(버그, 실 키로만 드러남)**: 대화 하나당 관측치(observation)가 9개
생기는데, 그중 최상위 trace의 `input` 필드 하나와 `GENERATION`(실제 LLM
호출) 관측치의 `input`만 마스킹돼 있고, 나머지 7개(LangGraph
노드/미들웨어 경계 — `ModelCallLimitMiddleware.after_model`,
`ToolCallLimitMiddleware.after_model`, `TodoListMiddleware.after_model`,
`CHAIN name: model`, `ModelCallLimitMiddleware.before_model`,
`MemoryMiddleware.before_agent`, `PatchToolCallsMiddleware.before_agent`)와
**최상위 trace 자신의 `output`**은 원본 이메일이 그대로 남아 있었다.
`python manage.py test`도, 가짜 키 검증도 이 버그를 못 잡았다 — 실제
LangGraph 실행 구조(멀티 노드, 멀티 미들웨어)를 태우고 서버에 기록된
데이터를 직접 읽어야만 드러나는 종류였다.

**근본 원인(SDK 소스 직접 읽어 확인, `langfuse==3.15.0`)**: 마스킹이
걸리고 안 걸리고의 경계는 "그 시점에 값이 이미 순수 dict/list/str이었는가"
였다.
- `langfuse.langchain.CallbackHandler`가 `on_llm_start`/`on_llm_end`(실제
  LLM 호출)에 넘기는 값은 `_convert_message_to_dict()`를 거쳐 이미 순수
  dict라 우리 `_mask_data`의 dict/list 재귀가 잘 먹혔다.
- 반면 `on_chain_start`/`on_chain_end`(LangGraph 노드·미들웨어 경계)에는
  `kwargs.get("inputs"/"outputs")`를 **변환 없이 그대로** 넘긴다 — 이
  값은 LangGraph state 그 자체라, `messages` 리스트 안에 아직 dict로
  안 바뀐 langchain-core의 `HumanMessage`/`AIMessage` **pydantic 객체**가
  살아 있다. `_mask_data`는 `str`/`dict`/`list`/`tuple`만 재귀해서 돌고
  그 외 타입은 `return data`로 그냥 통과시켰으니, 이 객체들은 마스킹 없이
  그대로 span에 실렸다가 Langfuse SDK 내부에서 나중에(마스킹이 다 끝난
  뒤에) dict로 직렬화됐다 — 그래서 서버에는 dict 모양으로 보이는데
  마스킹만 빠진 상태로 남은 것이다.
- 최상위 trace의 `output`도 같은 이유(LangGraph 최종 state가 원본
  `BaseMessage` 객체를 담고 있음)로 샜다.

**수정**(`services/agent_runtime/tracing/callbacks.py`의 `_mask_data`):
`str`/`dict`/`list`/`tuple` 다음 분기로 `model_dump()`(pydantic v2,
langchain-core 1.x 전제)를 가진 객체면 그것부터 dict로 바꾼 뒤 재귀하는
분기를 추가했다. 되돌아온 dict는 로그 전송용 사본일 뿐이라(mask()의
반환값은 Langfuse가 span attribute를 만드는 데만 쓰고, 그래프 실행
자체에는 다시 안 들어간다) 원본 객체를 안 건드려도 안전하다.

이 수정을 처음 넣었을 때 `LANGCHAIN_TRACING_V2`(env var 자동 연결) 경로
쪽에서 `BaseModel.model_dump() missing 1 required positional argument:
'self'` 에러가 새로 났다 — `_mask_data`가 LangSmith의 `hide_inputs`/
`hide_outputs`와도 공유되는데, 그쪽에서는 (도구 스키마의 `args_schema`
필드처럼) pydantic 모델 **클래스 자체**가 값으로 들어오는 경우가 있어
`data.model_dump`가 언바운드 메서드로 잡혀 `self` 없이 호출된 것.
`isinstance(data, type)` 체크로 클래스는 먼저 걸러내고, 혹시 모를 다른
변형에 대비해 `TypeError`도 한 번 더 방어적으로 잡도록 했다.

**재검증(수정 후, 같은 방식으로 다시 실 데이터 확인)**: 같은 테스트
에이전트로 새 메시지를 보내고 다시 Langfuse REST API로 조회 — 관측치
9개 전부, trace 레벨 input/output 전부 원본 이메일 없음(`leaked
observations: 0/9`). 같은 `_mask_data`를 공유하는 LangSmith 쪽도 회귀가
없는지 `langsmith.Client.list_runs()`로 수정 시점 이후 생성된 최근 실행
24건을 다시 조회해 확인 — 전부 마스킹 정상(`leaked: 0`).

## 9. 평가 착수 전 배선 점검 (2026-08-21)

작업 6(Dataset)에 들어가기 전에 §5~§7의 결과물을 다시 읽고 실제 SDK 소스와
대조했다. 실키 검증(§6·§7)으로 "이메일이 안 나간다"는 확인했지만, **평가
문서의 하드 게이트가 요구하는 범위와 구현 범위가 다르다**는 게 드러나 네
가지를 고쳤다.

### 9.1 `LANGSMITH_*` env 이름 — 마스킹이 통째로 우회되던 경로

설치된 `langsmith/utils.py`의 `get_env_var()`는
`namespaces=("LANGSMITH", "LANGCHAIN")` 순서로 찾는다 — `LANGSMITH_API_KEY`가
있으면 그쪽이 이긴다(`tracing_is_enabled()`도 `TRACING_V2` → `TRACING` 순으로
같은 두 접두사를 본다). 그런데 `config/settings/base.py`는 `LANGCHAIN_*`만
읽고 있었다. 지금 LangSmith 온보딩이 주는 스니펫이 `LANGSMITH_*` 이름이라,
그걸 그대로 `.env`에 붙여 넣으면:

- `settings.LANGCHAIN_API_KEY`가 비어 `get_langsmith_callback()`이 `None`
- 그런데 `langchain-core` 자동 연결은 `LANGSMITH_API_KEY`를 읽어
  **마스킹 없는 기본 `Client`로 멀쩡히 붙는다**

§6에서 확인한 "명시적 tracer가 있으면 자동 연결이 양보한다"는 안전장치가
*tracer가 만들어졌을 때만* 성립한다는 게 핵심이다. settings가 SDK와 같은
우선순위로 두 이름을 모두 읽도록 고쳤고(`_langsmith_env()`), 그래도 이
조합(키 없음 + 트레이싱 켜짐)이 되면 경고 로그를 남긴다.

### 9.2 마스킹 범위를 저장소 단일 출처로 통합

이 저장소에는 이미 `services/agent_runtime/sensitive_text.py`가 있고, 그
docstring이 "무엇을 민감정보로 보는가는 여기 한 곳에서 정한다"고 못박아 뒀다
(메모리 write guard와 채팅 입력 마스킹이 공유). 그런데 `tracing/callbacks.py`는
자체 이메일 정규식 하나만 갖고 있었다 — 정의가 두 벌이었고, 범위도 좁아
RAG 청크·Jira 설명·MCP 결과에 섞인 전화번호나 API 키는 그대로 서드파티로
나갔다. 외부 반출 기준을 "비밀값이나 개인정보 원문 노출"로 잡으면 그대로
파일럿을 돌렸을 때 에이전트 품질이 아니라 관측 배선 결함이 먼저 잡혔을 것이다.

`sensitive_text.py`에 `EMAIL_PATTERN`과 `mask_for_export()`를 추가해 세
사용처가 같은 패턴 목록을 쓰되 조합만 다르게 했다.

| 사용처 | 함수 | 가리는 것 |
| --- | --- | --- |
| 채팅 입력·메모리 write guard | `mask_sensitive()` | credential + PII + 권한 서술 |
| LangSmith·Langfuse export | `mask_for_export()` | credential + PII + **이메일** |

패턴이 1개에서 9개로 늘어 마스킹 비용도 늘었다 — 66KB 문자열 기준 2.1ms →
9.3ms(실측). 관측치 하나가 그 정도로 크지도 않고 LLM 왕복 시간에 비하면
무시할 수준이라 그대로 간다. 다만 Langfuse의 `mask`는 span을 닫는 요청
스레드에서 도는 코드라, 나중에 trace 페이로드가 커지면 여기부터 본다.

이메일을 `PII_PATTERNS`에 넣지 않은 건 의도적이다 — 채팅 입력에서 이메일을
가리면 "박서준한테 메일로 공유해줘" 같은 정상 업무가 망가진다. 반대로 권한
서술(`AUTHORITY_KEYWORDS`)을 trace에서 지우면 에이전트가 왜 그렇게 판단했는지
디버깅할 수 없어 export 쪽에서는 뺐다.

### 9.3 LangSmith `Client`를 프로세스당 하나로

`get_langsmith_callback()`이 실행(`run()`/`resume()`)마다 `Client(...)`를 새로
만들고 있었다. 설치된 `langsmith/client.py`를 읽어 보니 생성자가 매번
① `atexit.register()`로 세션 close 핸들러를 등록하고 ② `auto_batch_tracing`
기본값 때문에 배치 전송 스레드를 하나 띄운다. 장수명 web 워커에서 메시지마다
새로 만들면 atexit 핸들러가 프로세스가 죽을 때까지 무한히 쌓인다. Langfuse
쪽(`_ensure_client_configured()`)은 이미 싱글턴이었는데 LangSmith만 비대칭이던
것 — 클라이언트는 캐시하고 `LangChainTracer`만 실행마다 만든다.

### 9.4 마스킹 함수는 어떤 값이 와도 던지지 않는다

`_mask_data`가 `type(data)(masked)`로 시퀀스를 복원하고 있었는데, namedtuple은
생성자가 이터러블 하나가 아니라 필드별 위치 인자를 받아 `TypeError`가 난다.
`model_dump()` 쪽도 `TypeError`만 잡고 있어서 직렬화 실패 같은 다른 예외는
그대로 올라갔다. 예외가 나면 Langfuse는 그 관측치를 통째로
`"<fully masked due to failed mask function>"`으로 바꿔 버리고(`span.py`의
`_mask_attribute`), LangSmith `_hide_run_inputs`에는 그런 폴백조차 없다.
둘 다 방어했다 — 마스킹에 실패하면 원본 대신 문자열로 눌러서 다시 마스킹한다.
