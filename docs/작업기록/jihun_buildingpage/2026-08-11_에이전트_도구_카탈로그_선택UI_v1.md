# 작업기록 v1 — 에이전트 내장 도구 확장과 도구 선택 UI 팝업화 (2026-08-11)

> Cowork 세션에서 진행. 범위: (1) 내장 도구 8종 체계(5종 → 8종 + `category` 필드) 확정·구현, (2) 에이전트 편집 화면의 도구 선택을 인라인 체크리스트에서 3탭 팝업으로 재설계·구현.
> 제외: 「빌더 에이전트」(자연어 4입력 → LLM이 지시문을 다듬고 확인 화면을 보여주는 흐름, `빌더_에이전트_구체화.md`) 자체의 설계·구현 — 이 문서가 다루는 것은 그 앞 단계인 "지금 있는 수동 편집 화면(`AgentEditPage.tsx`)에서 도구를 어떻게 고르게 할 것인가"이며, 빌더 흐름과의 관계는 여전히 미정으로 남아 있다(§5).

## 1. 배경 — 왜 지금 손댔나

에이전트 편집 화면(`AgentEditPage.tsx`)은 원래 내장 도구 5종 + 팀이 연결한 MCP 도구를 한 줄짜리 플랫 체크리스트로 보여주고 있었다. 도구가 5~10개일 때는 문제가 없지만, 팀이 MCP 서버를 여러 개 연결하기 시작하면 그 목록이 계속 늘어난다. 이 상태에서 "우리 플랫폼이 기본으로 어떤 도구를 줘야 하는가"를 먼저 정리했다.

처음에는 "문서/업무/사람·부하/외부도구/보고/위험감지" 6개 카테고리, 11개 도구를 브레인스토밍했지만, 검토 과정에서 방향을 좁혔다. 기준은 "이 데이터는 정말 별도 조회 도구가 있어야 모델이 쓸 수 있는가(진짜 원자적 데이터 접근)"와 "이미 있는 도구 2~3개를 지시문으로 조합하면 모델이 스스로 만들어낼 수 있는 결과인가(파생 능력)"를 나누는 것이었다. 후자는 새 도구를 만들지 않기로 하고, 전자에 해당하는 것만 추렸다 — 결과가 아래 3종이다.

동시에 "MCP 서버만 선택하게 하고 개별 도구 선택은 없애자"는 아이디어도 검토했다. 결론은 반대로, 지금 DB가 `agent_tool`에 개별 MCP 도구(`mcp:<mcp_tool_id>`)를 저장하는 구조라 서버 단위 저장으로 바꾸려면 스키마 변경이 필요하고, 이미 모든 MCP 도구를 "실행 전 사람 승인 필요"로 취급하고 있어 선택 단계에서 세밀하게 골라도 실행 시점 안전성에 크게 보태는 게 없다는 점, 반대로 서버 단위로 켜면 그 서버에 나중에 추가되는 도구가 조용히 함께 켜진다는 점을 근거로 **개별 도구 선택을 유지**하기로 했다(§4).

## 2. 신규 내장 도구 3종

기존 5종(`document_search`, `workload_report`, `task_extraction`, `jira_create_issues`, `jira_get_issues`)에 아래 3종을 추가해 총 8종이 됐다. 전부 `services/harness/registry.py`의 `BUILTIN_TOOLS`에 등록된다.

| tool_ref | 이름 | category | side_effect | 무엇을 하는가 | 근거 |
|---|---|---|---|---|---|
| `task_status` | 업무 현황 조회 | 업무 | false | 팀의 Jira 연동 업무를 담당자명·상태·상태분류·마감일·공수(estimate/remaining/spent)·프로젝트 정보와 함께 목록으로 돌려준다. | `workload_report`는 부하 "계산" 결과만 주지 개별 업무 목록을 안 준다. "지금 막힌 업무가 뭐야" 같은 질문에는 계산기가 아니라 원천 목록이 필요해서 별도 도구로 뺐다. |
| `team_member_info` | 팀원 정보 조회 | 사람·부하 | false | 팀원의 이름·직무·소속 조직·보유 스킬·오늘 부재 여부를 목록으로 돌려준다. | HR 데이터(이름, 스킬, 부재)는 기존 8종 어떤 도구로도 조합해서 만들 수 없는 원자적 데이터라 별도 도구가 필요했다. |
| `jira_update_issue` | Jira 이슈 수정 | Jira연동 | **true(승인 필요)** | 기존 Jira 이슈 한 건의 제목·설명·담당자·마감일을 바꾼다. 상태 전이(예: "진행중"으로 옮기기)는 지원하지 않는다. | `jira_create_issues`(생성)만 있고 수정이 없었다 — "이미 등록된 이슈를 고쳐줘" 요청에 대응할 수 없었다. 상태 전이는 Jira 워크플로마다 허용되는 전이가 달라 별도 조회·검증이 필요해 이번 범위에서 뺐다. |

### 2.1 `task_status` 구현 상세

`ExistTaskRepository.list_for_team(account_id)`(Jira 싱크 테이블, `/api/teams/workload`와 같은 원천)를 그대로 읽고, 담당자 `person_id` 목록을 모아 `backend.services.hr.lookup_persons`로 이름을 붙인 뒤 반환한다. 부하 계산(`workload_report`)과 달리 재계산을 하지 않는다 — 같은 원천을 두 도구가 각자 다르게 가공하면 화면이 말하는 숫자와 에이전트가 말하는 숫자가 갈릴 위험이 있어, 이 도구는 원천을 그대로 노출하는 역할로 좁혔다.

### 2.2 `team_member_info` 구현 상세

팀 경계는 `workload_report`와 같은 방식(`TeamRepository.member_person_ids`)으로 잡는다. `backend.services.hr.list_persons(person_ids=...)`로 팀원 명부를 받고, 스킬은 `list_person_skills`가 사람 단위 조회만 지원해서 인원수만큼 반복 호출한다(팀 규모가 수십 명 수준이라 문제 되지 않는다고 판단). 오늘 날짜 기준 `list_absences`로 부재 여부를 붙인다.

### 2.3 `jira_update_issue` 구현 상세

`apps/connectors/clients.py`에 `update_jira_issue(*, account_id, issue_key, changes)`를 신규 작성했다. `create_jira_issues`와 같은 인증·에러 처리 패턴(Bearer 토큰, cloud_id 조회, 401/403/404/429/400 개별 처리)을 따른다. 바꿀 수 있는 필드를 `_JIRA_UPDATABLE_FIELDS = ("title", "description", "assignee_account_id", "duedate")`로 화이트리스트해, 모델이 임의의 Jira 필드명을 지어내 보내는 사고를 막았다. `PUT /rest/api/3/issue/{issueKey}`는 성공 시 204(본문 없음)를 돌려주므로, 성공 응답에서는 우리가 보낸 `changes`를 그대로 되돌려준다.

Registry 쪽 `_jira_update_issue` 핸들러는 이 함수를 얇게 감싸기만 한다. `side_effect=True`라 실행 전 사람 승인을 받고, `services/harness/runner.py`의 `_ACCOUNT_SCOPED_TOOLS`에 추가해 서버가 호출자 계정으로 자격 증명을 주입하게 했다(모델이 `account_id`를 스스로 정하면 남의 Jira를 건드릴 수 있어 반드시 서버 주입이어야 한다).

`task_status`, `team_member_info`도 같은 이유로 `_ACCOUNT_SCOPED_TOOLS`에 추가했다 — 둘 다 `account_id`만 서버가 주입받는 유일한 인자다.

## 3. `category` 필드

`Tool` dataclass(`services/harness/registry.py`)에 `category: str` 필드를 추가했다(기본값 없는 필수 필드, `side_effect` 앞에 위치해 dataclass 필드 순서 규칙을 지킴). 기존 5종에도 값을 채웠다: `document_search`→문서, `workload_report`/`team_member_info`→사람·부하, `task_extraction`/`task_status`→업무, `jira_create_issues`/`jira_get_issues`/`jira_update_issue`→Jira연동.

**지금 화면에서는 이 값을 쓰지 않는다.** 도구가 8개뿐이라 카테고리별로 묶어 보여줄 필요가 아직 없다고 판단했고, 대신 도구가 늘었을 때 나중에 다시 분류하지 않도록 데이터만 먼저 실어 둔 것이다. API 응답(`apps/agents/serializers.py::builtin_tool_response`)과 프론트 타입(`frontend/src/api/agents.ts::ToolChoice.category`, optional)에도 노출은 해 뒀다.

## 4. 도구 선택 UI — 인라인 체크리스트에서 팝업으로

### 4.1 이전 상태

`AgentEditPage.tsx`의 "참고 데이터 · 도구" 카드 안에, `listToolChoices()`(내장 도구 + 팀 MCP 도구를 합친 flat 배열)를 순회하며 체크박스 목록을 그대로 렌더링했다. 항목마다 이름·설명·승인 필요 여부·출처(`기본 제공` / `MCP · <서버명>`)를 한 줄에 표시했다.

### 4.2 요청과 결정한 구조

사용자 요청: 도구를 고르면 새 팝업이 뜨고, 그 팝업 안에서 **툴 선택 / MCP서버 선택 / 툴 생성** 세 갈래로 나뉘어야 한다.

MCP서버 선택 탭의 단위를 두고 두 안을 비교했다(§1에서 이미 요약).

| 안 | 장점 | 단점 |
|---|---|---|
| 서버 단위로 전체 켜기 | 클릭이 적고 화면이 단순함 | 서버에 도구가 추가되면 이미 켜둔 에이전트에 조용히 권한이 늘어남. `agent_tool`이 개별 도구 단위로 저장하는 지금 스키마와 안 맞아 저장 방식을 새로 설계해야 함 |
| 서버 고른 뒤 도구를 개별 선택(채택) | 어떤 도구가 켜져 있는지 정확함. 새 도구가 추가돼도 자동으로 켜지지 않음. 지금 DB 저장 방식과 그대로 맞음 | 도구가 많은 서버는 체크할 게 늘어남(단, 모든 MCP 도구가 이미 실행 전 승인 게이트를 타므로 실제 위험 차이는 크지 않음) |

**개별 선택 안을 채택.** 이유는 표에 정리된 대로 기존 스키마 변경이 불필요하고 권한이 명확하기 때문이다.

툴 생성 탭은 "3개 탭 구조는 지금 만들되, '새 도구 만들기' 자체는 아직 아무 기능도 없게" 하기로 결정했다 — 팀이 직접 도구를 만드는 기능은 설계·백엔드가 전혀 없는 상태라, 이번 범위에서는 안내 문구와 비활성화된 버튼만 두는 스텁으로 좁혔다.

### 4.3 구현

**신규 파일**

- `frontend/src/pages/AgentEditPage/ToolPickerModal.tsx` — 팝업 본체. 공용 `Modal` 컴포넌트 위에 자체 탭 상태(`useState<'builtin' | 'mcp' | 'create'>`)를 얹었다.
  - **툴 선택 탭**: `builtinTools`(부모가 넘겨주는, `tool_ref`가 `mcp:`로 시작하지 않는 항목만) 를 기존과 같은 체크리스트 스타일로 보여준다.
  - **MCP서버 선택 탭**: `listMcpServers()` 응답(`McpServer[]`, 서버마다 `tools: McpTool[]` 내장)을 서버별 카드로 그룹핑한다. 서버 상태 배지(연결됨/미확인/연결 실패)를 보여주고, `CONNECTED`가 아닌 서버는 도구 목록 대신 안내 문구("설정에서 연결을 확인해야 도구를 고를 수 있습니다" 등)를 띄운다. 개별 도구 체크박스는 `mcp:${tool.mcp_tool_id}`를 `tool_ref`로 써서 토글하며, `tool.enabled === false`인 도구는 체크박스를 비활성화한다(백엔드 `_check_tool_refs`가 `enabled = true`인 도구만 유효하다고 검증하는 것과 맞춘 것). 하단에 "MCP 서버 관리로 이동" 링크를 둬 설정 화면(`PATHS.settingsMcp`)으로 바로 갈 수 있게 했다.
  - **툴 생성 탭**: 안내 문구("팀에서 직접 도구를 만드는 기능은 아직 준비 중입니다…")와 `disabled` 처리된 "새 도구 만들기 (준비 중)" 버튼만 있다. 클릭 핸들러 자체가 없다.
- `frontend/src/pages/AgentEditPage/ToolPickerModal.module.css` — 탭 바(`.tabs`/`.tab`/`.tabOn`), 서버 카드(`.serverList`/`.serverGroup`/`.serverHead`/`.serverName`), 설정 이동 링크(`.settingsLink`), 툴 생성 탭(`.createTab`) 스타일. 도구 한 줄(체크박스+이름+설명) 스타일은 새로 안 만들고 `AgentEditPage.module.css`의 기존 `.toolRow`/`.toolRowOn`/`.toolText`/`.gate`/`.help` 클래스를 그대로 import해 재사용했다(중복 스타일 방지).

**`AgentEditPage.tsx` 변경**

- 기존 인라인 체크리스트 블록을 제거하고, 선택된 도구를 칩(chip) 형태로 요약 표시하도록 바꿨다. 칩에는 도구 이름과 X 버튼이 있어 팝업을 열지 않고도 바로 뺄 수 있다.
- "도구 선택" 버튼(`variant="outline" size="sm"`)을 눌러야 `ToolPickerModal`이 열린다(`pickerOpen` 상태).
- `mcpServers` 상태를 신규로 추가해 화면 진입 시 `listMcpServers()`로 한 번 받아 둔다(팝업을 열 때마다 다시 부르지 않음 — 팀당 MCP 서버 수가 아직 적은 단계라 이렇게 단순화했다).
- `toolLabel(ref)` 헬퍼: 칩에 표시할 이름을 찾는다. 먼저 `/agents/tools/` 카탈로그(`tools`)에서 찾고, 없으면(`mcp:` 접두사이면서 아직 카탈로그에 안 실린 경우) `mcpServers`를 순회해 한 번 더 찾는다.
- 도구 토글 함수(`toggleTool`)와 저장 로직(`handleSave`)은 바꾸지 않았다 — 팝업은 선택 UI만 감싼 것이고, 상태 관리와 저장 방식은 그대로다.

**CSS 추가** — `AgentEditPage.module.css`에 `.toolSummary`(칩을 감싸는 flex 컨테이너)와 `.toolChip`(칩 하나, 안에 X 버튼 포함) 신규.

## 5. 검증

- 백엔드: `python -m py_compile apps/connectors/clients.py services/harness/registry.py services/harness/runner.py apps/agents/serializers.py tests/test_harness.py` 통과.
- 프론트: `npx tsc -b --noEmit` 통과 (도구 3종 구현 직후 1회, 팝업 UI 구현 직후 1회 — 총 2회 확인).
- 실제 Django 테스트 스위트는 이번에도 실행하지 못했다(샌드박스 Python 3.10, 프로젝트는 `datetime.UTC` 등 3.11+ 문법 사용 — 이 세션 이전부터 있던 환경 제약). `tests/test_harness.py`의 `echo_tool` 헬퍼는 `Tool`에 새 필수 필드가 생겨서 함께 고쳤지만, 실행 확인은 못 했다.

## 6. 이 문서 범위 밖 — 다음에 다룰 것

- **도구 선택 + 프롬프트 작성 다음에 무슨 일이 일어나는가**: 이 세션에서 "제출 → 빌더 에이전트 검토(지시문 다듬기 + 경고 판정) → 확인 화면 → 저장" 4단계까지는 구두로 정리했지만, 확인 화면을 실제로 어떻게 그릴지는 논의를 시작만 하고 문서화하지 않았다. `빌더_에이전트_구체화.md` §6에 이미 열린 항목으로 남아 있다.
- **빌더 흐름과 `AgentEditPage.tsx`(이번에 손댄 수동 생성·편집 폼)의 관계**: 빌더가 이 폼을 대체하는지, 생성 경로만 추가되고 수정은 지금 폼으로 남는지 — 여전히 미정(`빌더_에이전트_구체화.md` §6).
- **툴 생성 탭의 실제 기능**: 팀이 직접 커스텀 도구를 만드는 기능은 설계 자체가 없다. 지금은 스텁만 존재.
- **MCP 도구의 `enabled` 토글**: 체크박스 비활성화 처리는 넣었지만, `mcp_tool.enabled`를 사람이 직접 켜고 끄는 화면은 어디에도 없다(Settings > MCP 탭 포함). 지금은 서버 도구 목록을 새로 읽어올 때(`initialize_and_list_tools`) 전부 `enabled=true`로 저장되는 것으로 보인다 — 확인만 했고 바꾸지 않았다.
