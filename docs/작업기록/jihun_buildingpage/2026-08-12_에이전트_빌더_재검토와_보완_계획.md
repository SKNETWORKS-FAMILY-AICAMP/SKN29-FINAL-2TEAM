# 에이전트 빌더 재검토와 보완 계획

> 작성일: 2026-08-12  
> 문서 성격: 구현 완료 기록이 아니라, 현재 Builder 코드를 다시 검토한 뒤 확정한 **보완 작업 계획**  
> 관련 범위: 검증 단계 전환, Tool 입력 검증, MCP `input_schema` 전달, Builder 자동 테스트  
> 관련 구현: `frontend/src/pages/AgentEditPage/`, `apps/agents/`, `backend/db/agent_platform.py`, `services/harness/`, `tests/`

## 1. 재검토 결론

현재 Builder는 이름·설명·지시문·Tool을 조합하고, 의미 검증과 초안 대화 테스트를
거쳐 DRAFT를 ACTIVE로 전환하는 기본 구조가 구현돼 있다. 저장 전 시험 실행은
`run_ephemeral()`을 사용해 평가 로그를 오염시키지 않고, 승인 필요 Tool은
`dry_run=True`에서 실제 실행하지 않는 안전 경계도 갖췄다.

프런트 프로덕션 빌드도 통과한다. 다만 현재 코드를 다시 검토한 결과, 기능을 더
추가하기 전에 아래 세 항목을 보완해야 한다.

1. 상단 탭을 통해 1단계 검증을 우회하고 대화 테스트로 들어갈 수 있다.
2. 개별 Tool 확인 화면이 잘못된 숫자·JSON 입력을 조용히 요청에서 제거한다.
3. Builder 신규 API와 생명주기를 보호하는 자동 테스트가 없고, 기존 Harness 테스트
   2건은 위임 Agent 조회 mock 누락으로 실패한다.

작업 순서는 **현재 테스트 기준선 확인 → 기존 테스트 복구 → 검증 우회 차단 → Tool
입력 검증 및 MCP Schema 배선 → Builder API 테스트 추가 → 통합 검증**으로 확정한다.

## 2. 작업 1 — 검증 단계 우회 차단

### 2.1 현재 상태

`TestRunModal.tsx` 하단의 `다음 단계: 대화 테스트` 버튼은 이미 올바른 게이트를
갖고 있다.

- `disabled={!canProceed}`로 검증 미완료·`reject` 상태를 막는다.
- 검증 화면에서 확정한 설명과 지시문을 `onApplyDescription()`과
  `onApplyInstruction()`으로 부모 폼에 반영한다.
- 반영 후 `setStage('chat')`으로 2단계에 진입한다.

따라서 새로운 흐름을 설계할 필요는 없다. 실제 구멍은 상단 탭의 다음 코드 하나다.

```tsx
onClick={() => setStage(s.key)}
```

이 코드는 `canProceed`와 설명·지시문 반영 로직을 모두 건너뛴다. 검증 중이거나
`reject` 결과여도 사용자가 `2. 대화 테스트` 탭을 직접 누르면 진입할 수 있다.

### 2.2 수정 방식

하단 버튼에 이미 있는 전환 로직을 함수로 추출하고 상단 탭과 하단 버튼이 같은
함수를 사용하게 한다.

```tsx
function moveToChatStage() {
  if (!canProceed) return;

  onApplyDescription(checkedDescription);
  onApplyInstruction(checkedInstruction);
  setStage('chat');
}

function moveToStage(next: Stage) {
  if (next === 'check') {
    setStage('check');
    return;
  }
  moveToChatStage();
}
```

`chat` 탭은 `canProceed` 전까지 실제 `disabled` 상태로 둔다. 시각적으로도 비활성
상태가 드러나도록 기존 탭 CSS에 `:disabled` 스타일을 추가한다.

```tsx
const disabled = s.key === 'chat' && !canProceed;

<button
  disabled={disabled}
  aria-disabled={disabled}
  onClick={() => moveToStage(s.key)}
>
```

### 2.3 `checkedInstruction` 사용 여부

현재 정상 경로에서는 단계 전환 시 부모 상태가 먼저 갱신되고, 사용자가 실행 버튼을
누를 때는 갱신된 `instruction` prop이 다시 들어온다. 따라서 `run()`이 부모의
`instruction`을 사용하는 것이 현재 정상 경로의 실제 버그는 아니다.

다만 대화 테스트가 “검증 모달에서 사용자가 확정한 지시문”을 사용한다는 계약을
코드에 직접 드러내기 위해 다음과 같이 `checkedInstruction`을 전달하는 것을
방어적 보완으로 포함한다.

```tsx
instruction: checkedInstruction,
```

이는 우회 차단의 필수 조건은 아니지만, 상태 동기화 순서에 대한 암묵적 의존을 줄인다.

### 2.4 완료 조건

- 검증 중에는 `2. 대화 테스트` 탭을 누를 수 없다.
- 검증 API 실패 또는 `reject` 결과에서도 2단계로 들어갈 수 없다.
- 보정안이 있는데 적용/유지 결정을 하지 않은 상태에서는 들어갈 수 없다.
- `pass` 또는 `warn`이고 사용자 결정이 끝나면 상단 탭과 하단 버튼 모두 활성화된다.
- 두 진입 경로가 동일하게 설명·지시문을 부모 폼에 반영한다.
- 대화 테스트는 검증 모달에서 확정한 지시문으로 실행된다.

예상 작업량은 15~30분이다.

## 3. 작업 2 — Tool 입력값 검증과 MCP Schema 배선

### 3.1 현재 문제

`ToolCheckPanel.tsx`는 Tool의 `input_schema.properties`를 읽어 입력 폼을 만든다.
그러나 숫자 변환 실패나 JSON 파싱 실패가 발생하면 오류를 표시하지 않고 해당 값을
요청 인자에서 제외한다.

```tsx
try {
  built[prop] = JSON.parse(raw);
} catch {
  // 잘못된 JSON은 그냥 뺀다.
}
```

이 때문에 사용자는 값을 입력했는데도 백엔드에서는 필수 인자가 누락된 요청으로
보게 된다. 입력 오류와 Tool 실행 오류가 섞여 원인을 판단하기 어렵다.

### 3.2 프런트 검증 규칙

인자 조립을 `buildArguments()` 같은 순수 함수로 분리하고, 조립 결과와 필드별
오류를 함께 반환한다.

```tsx
type BuildArgumentsResult = {
  argumentsByRef: Record<string, Record<string, unknown>>;
  errors: Record<string, string>;
};
```

검증 규칙은 다음과 같다.

| 입력 조건 | 처리 |
|---|---|
| `required` 필드가 비어 있음 | `필수 입력입니다.` 표시 |
| number/integer를 숫자로 변환할 수 없음 | `숫자로 입력해 주세요.` 표시 |
| JSON 파싱 실패 | `올바른 JSON 형식으로 입력해 주세요.` 표시 |
| Schema가 `array`인데 JSON 배열이 아님 | 배열 형식 오류 표시 |
| Schema가 `object`인데 JSON 객체가 아님 | 객체 형식 오류 표시 |

오류가 하나라도 있으면 `/agents/build/check-tools/` API를 호출하지 않는다. 잘못된
입력을 조용히 버리는 경로는 제거한다. 사용자가 값을 수정하면 해당 필드 오류가
사라져야 한다.

### 3.3 MCP `input_schema` 전달 경로

MCP Tool의 입력 폼을 만들려면 Serializer만 수정해서는 안 된다. 현재
`AgentCrudRepository.team_tool_refs()` SQL이 `mcp_tool.input_schema`를 조회하지
않기 때문이다. DB 컬럼은 이미 존재하지만 API까지 배선되지 않은 상태다.

수정 경로는 다음 세 층이다.

```text
mcp_tool.input_schema (JSONB)
    ↓
AgentCrudRepository.team_tool_refs() SELECT
    ↓
mcp_tool_response()
    ↓
ToolChoice.input_schema
    ↓
ToolCheckPanel 입력 폼
```

따라서 아래 파일을 함께 수정한다.

1. `backend/db/agent_platform.py`
   - `team_tool_refs()` SQL에 `t.input_schema`를 추가한다.
2. `apps/agents/serializers.py`
   - `mcp_tool_response()`에 `input_schema`를 포함한다.
3. `frontend/src/api/agents.ts`
   - `ToolChoice.input_schema` 타입이 MCP 응답도 수용하는지 확인하고 필요하면 보완한다.
4. `frontend/src/pages/AgentEditPage/ToolCheckPanel.tsx`
   - 동일 Schema로 내장 Tool과 MCP Tool 입력을 검증한다.

API 응답은 Schema가 비어 있을 경우 최소 객체 Schema를 반환한다.

```python
"input_schema": row.get("input_schema") or {
    "type": "object",
    "properties": {},
},
```

### 3.4 MCP Tool 확인의 안전 경계

MCP `tools/list` 결과만으로 읽기 전용인지 쓰기 작업인지 확정할 수 없으므로 현재처럼
MCP Tool은 전부 `side_effect=True`로 본다. Builder의 개별 Tool 확인에서는 실제
호출하지 않고 `SIMULATED`로 최종 호출 인자만 보여준다.

따라서 MCP에 대해 Builder가 보장하는 것은 다음까지다.

- 저장된 Input Schema에 맞게 인자를 입력했는가
- 필수값과 타입이 맞는가
- 어떤 인자로 호출하려 했는가
- 연결된 서버와 Tool이 현재 카탈로그에 존재하는가

실제 외부 변경은 ACTIVE Agent 실행 중 사용자 승인 뒤에만 수행한다. 화면 문구도
필요하면 MCP Tool에 한해 `실행 확인`보다 `호출 계획 확인`에 가깝게 조정한다.

### 3.5 완료 조건

- 필수 입력 누락 시 API를 호출하지 않는다.
- 잘못된 숫자·JSON 입력을 해당 필드 아래에서 설명한다.
- 잘못된 입력이 요청에서 조용히 사라지지 않는다.
- 입력을 수정하면 오류가 해제되고 유효한 값만 서버로 전달된다.
- MCP Tool도 저장된 `input_schema`에 따라 입력 폼을 생성한다.
- 승인 필요 Tool과 MCP Tool은 계속 실제 실행하지 않고 `SIMULATED`로 처리한다.

예상 작업량은 1~2시간이다.

## 4. 작업 3 — Builder 자동 테스트 추가와 기존 Harness 테스트 복구

### 4.1 구현 전 기준선 확인

기능 수정 전에 Harness 테스트만 독립 실행해 현재 실패 기준선을 다시 확인한다.

```powershell
.\.venv\Scripts\python.exe manage.py test `
  tests.test_harness `
  --settings=config.settings.local
```

현재 확인된 실패는 `RegistryTests`의 2건이다. 두 테스트가
`registry.load_for_agent(..., depth=1)`를 호출하고, `depth < MAX_AGENT_DEPTH`라
새 위임 Agent 조회 분기로 들어가지만 `AgentRepository.callable_agents()`를 mock하지
않아 실제 DB 연결을 시도한다.

### 4.2 기존 테스트 2건 복구

해당 테스트에 아래 mock을 추가한다.

```python
@patch(
    "services.harness.registry.AgentRepository.callable_agents",
    return_value=[],
)
```

복구 후 `tests.test_harness`를 다시 실행해 기존 테스트가 외부 DB 없이 전부 통과하는지
확인한 다음 신규 Builder 테스트를 작성한다.

### 4.3 중복해서 만들지 않을 위임 테스트

`tests/test_harness.py`의 `AgentToolLoadTests`에는 이미 다음 동작을 검증하는 테스트가
있다.

- wildcard가 팀 Agent Tool로 동적 확장되는가
- 깊이 상한에 도달하면 위임 Tool을 제거하는가
- wildcard가 없으면 명시적으로 허용하지 않은 Agent에 위임할 수 없는가

따라서 이번 작업에서는 같은 내용을 다시 작성하지 않는다.

### 4.4 이번 범위에서 제외할 SQL 통합 테스트

`AgentRepository.callable_agents()`의 다음 조건은 Registry 로직이 아니라 SQL
Repository의 책임이다.

- 같은 `team_id`만 조회
- 자기 자신(`agent_id`) 제외
- `status = 'ACTIVE'`만 조회

현재 프로젝트 테스트는 PostgreSQL 테스트 DB를 사용하지 않는 `SimpleTestCase`와
Repository mock 중심이다. Registry 테스트에서 `callable_agents()` 자체를 mock하므로
이 SQL의 WHERE 조건을 실제로 검증할 수 없다.

SQL 문자열을 mock cursor로 검사하는 방식은 구현 세부사항에 강하게 결합되고 실제
PostgreSQL 동작도 보장하지 않으므로 이번 범위에 넣지 않는다. 아래 후속 작업으로
남긴다.

> 후속: PostgreSQL 기반 Repository 통합 테스트 환경을 도입할 때
> `callable_agents()`의 team/status/self-exclusion 조건을 실제 DB 행으로 검증한다.

### 4.5 신규 Builder 테스트 파일

CRUD 테스트와 Builder 검증·실행 테스트가 섞이지 않도록
`tests/test_agent_builder.py`를 새로 만든다.

우선 구현할 필수 테스트는 다음과 같다.

#### 검증 API — `POST /api/agents/build/check/`

- 인증 없으면 401
- 알 수 없는 Tool이면 LLM을 호출하지 않고 `reject`
- 중복 Tool이면 LLM을 호출하지 않고 `reject`
- LLM `pass` / `warn` / `reject` 응답을 API 계약으로 변환
- 검증 설정 누락은 503
- 모델 구조화 응답 실패는 502

#### 지시문 재검증 — `POST /api/agents/build/recheck-instruction/`

- 빈 지시문은 400
- 설명 검증을 다시 수행하지 않음
- 지시문과 Tool 정합성은 다시 검사
- 알 수 없는 Tool은 `reject`

#### 초안 대화 테스트 — `POST /api/agents/build/test/`

- NDJSON 스트림 반환
- 초안의 model/reasoning/max_iterations/tool_refs를 Harness에 전달
- 실제 `agent_run`·`tool_call` Repository를 사용하지 않고 ephemeral trace 사용
- `side_effect=True` Tool은 `SIMULATED` 이벤트를 반환하고 handler를 호출하지 않음
- 일반 읽기 Tool은 실행 가능
- 스트림 중 예외는 마지막 `error` 이벤트로 반환
- 반복 상한 도달은 `complete=false`로 반환

#### 개별 Tool 확인 — `POST /api/agents/build/check-tools/`

- 일반 Tool 성공
- Tool 하나가 실패해도 다음 Tool을 계속 확인
- 승인 필요 Tool은 `SIMULATED`
- `task_extraction`은 `SKIPPED`
- 서버가 주입하는 `team_id`·`account_id`가 사용자 arguments보다 우선
- 알 수 없는 Tool은 실패 결과로 반환
- 시험 실행 로그를 DB에 남기지 않음

#### 생명주기

- 새 Agent는 DRAFT로 생성
- DRAFT 활성화 성공
- 검증 `reject` 시 409이며 DRAFT 유지
- ACTIVE → DISABLED
- DISABLED → ACTIVE
- 기본 제공 Agent 수정 차단
- 다른 팀 Agent 접근 차단

### 4.6 프런트 자동 테스트 범위

현재 프런트에는 Vitest/Testing Library 환경이 없다. 이번 세 항목을 고치기 위해
테스트 프레임워크까지 새로 도입하면 범위가 커지므로, 이번 작업에서는 다음으로
검증한다.

- TypeScript + Vite 프로덕션 빌드
- Builder 백엔드 단위 테스트
- 로그인된 브라우저에서 수동 체크리스트 실행

프런트 자동 테스트 도입은 후속 작업으로 둔다. 도입 시 최우선 테스트 대상은
`chat` 탭 비활성화, 보정 지시문 적용, 필드별 Tool 입력 오류다.

## 5. 확정 작업 순서

1. `tests.test_harness`만 실행해 현재 실패 기준선을 확인한다.
2. `RegistryTests` 2건에 `callable_agents()` mock을 추가한다.
3. `tests.test_harness`를 다시 실행해 기존 테스트를 복구한다.
4. `TestRunModal.tsx`의 단계 전환 함수를 통일한다.
5. 상단 `chat` 탭을 `canProceed` 전까지 비활성화한다.
6. 대화 테스트 입력에 `checkedInstruction`을 사용한다.
7. `team_tool_refs()` SQL에 `input_schema` 조회를 추가한다.
8. MCP Tool API 응답에 `input_schema`를 추가한다.

## 7. 브라우저 체크리스트

1. 빈 이름·설명·지시문으로 검증을 시작한다.
2. 검증 중 `2. 대화 테스트` 탭이 비활성인지 확인한다.
3. `reject` 결과 후에도 탭이 비활성인지 확인한다.
4. `warn` 결과는 사용자 확인 후 진행 가능한지 확인한다.
5. 보정안 적용 시 부모 Builder 폼의 지시문이 바뀌는지 확인한다.
6. `내 지시문 유지` 경로도 정상인지 확인한다.
7. 잘못된 숫자·JSON 입력에서 Tool 확인 요청이 나가지 않는지 확인한다.
8. 필드별 오류가 표시되고 수정 후 해제되는지 확인한다.
9. MCP Tool의 저장된 Schema로 입력 폼이 생성되는지 확인한다.
10. Jira/MCP 등 승인 필요 Tool이 `SIMULATED`인지 확인한다.
11. 임시 저장 후 URL이 생성된 Agent ID 편집 경로로 바뀌는지 확인한다.
12. 활성화 후 Chat으로 이동하고 위임 대상에 포함되는지 확인한다.
13. 비활성화 후 Chat 위임 대상에서 제외되는지 확인한다.

## 8. 완료 기준

이번 작업은 단순히 빌드가 성공하는 것으로 끝내지 않는다. 다음 네 조건을 모두
만족해야 완료다.

1. 1단계 검증을 통과하지 않고 2단계 대화 테스트로 들어갈 수 없다.
2. 잘못된 Tool 입력이 조용히 사라지지 않고 사용자에게 필드별로 드러난다.
3. 저장 전 시험에서 외부 변경 Tool이 실제 실행되지 않는다.
4. Builder 관련 테스트가 외부 PostgreSQL 접속 없이 모두 통과한다.

## 9. 최종 판단

이번 보완은 Builder 기능을 확장하는 작업이 아니라, 이미 구현된
`검증 → 대화 테스트 → DRAFT/ACTIVE 생명주기`의 끊어진 경계를 닫는 작업이다.

- 검증 단계 전환은 기존 하단 버튼의 올바른 로직을 상단 탭에도 재사용한다.
- Tool 입력 검증은 실패 값을 버리지 않고 입력 오류와 실행 오류를 분리한다.
- MCP Schema는 DB에 이미 있으므로 Repository SQL부터 API·프런트까지 배선한다.
- 자동 테스트는 기존 위임 테스트를 중복하지 않고 Builder의 새 API와 안전 경계에
  집중한다.
- 실제 PostgreSQL이 필요한 SQL 조건 검증은 테스트 인프라가 마련될 때까지 후속으로
  명시한다.

이 범위가 끝나면 Builder는 기능 시연뿐 아니라 실패 경로와 안전 정책까지 설명할 수
있는 상태가 된다.
