# 빌더 에이전트 구체화

> 2026-08-11. Cowork 세션에서 나눈 대화 정리.
> 콜드 스타트에서 가장 먼저 작동하는 빌더 에이전트 — 사용자가 4개 필드에
> 자연어로 입력하면 그걸 실제 에이전트(agent 레코드)로 만들어주는 과정을
> 구체화한 것. 이 세션 안에서만 정리한 초안이며 다른 문서에는 반영하지 않음.

## 0. 입력

```
BuilderInput
├── name          (사용자 직접 입력)
├── description   (사용자 직접 입력)
├── tools         (Tool 카탈로그에서 체크박스로 선택한 id 목록)
├── behavior      (자연어 문단)
└── (세션에서 자동) team_id, user_id
```

> `model`·`reasoning_effort`는 입력에 없다. 사용자에게 받지 않고 플랫폼
> 기본값을 자동으로 채운다 — §4 참고.

## 1. 빌더 에이전트 LLM 호출 — 구조화 출력

"behavior를 instruction으로 다듬는다"를 자유 텍스트 생성으로 두면 검증과
다듬기가 한 응답에 섞여서 실패 시 원인을 파싱하기 어렵다. 하나의 구조화
출력으로 묶는다.

```
BuilderCheckResult
├── refined_instruction        # behavior를 다듬은 최종 instruction
├── description_check
│   └── note                   # 애매하면 사유, 명확하면 null
├── tool_match_check
│   ├── missing_tools          # behavior상 필요해 보이는데 선택 안 된 tool
│   └── unused_tools           # 선택했는데 behavior에서 안 쓰일 것 같은 tool
└── overall                    # pass / warn
```

> `passed: bool`, `fail` 상태는 두지 않는다 — §3 참고. warn이어도 항상
> 저장은 허용되므로 통과 여부를 별도 boolean으로 가를 필요가 없고, 경고
> 사유 텍스트만 있으면 된다.

## 2. 세 판단 각각의 기준

| 체크 | 무엇을 보는가 | 왜 필요한가 |
|---|---|---|
| behavior→instruction 다듬기 | 문장 정리 + 스캐폴드와 중복되는 지시(근거 원칙·확인 후 진행 등)는 제거 — 스캐폴드가 이미 모든 에이전트에 공통 적용되므로 여기 또 적으면 중복·충돌 소지 | instruction이 스캐폴드와 겹치면 프롬프트 낭비이자, 나중에 스캐폴드 문구를 바꿔도 개별 에이전트 instruction은 안 바뀌는 불일치가 생김 |
| description 명확성 | 동사(뭘 하는지)+대상(뭐에 대해)+산출물(뭘 내는지) 세 요소가 있는지 — 자동 라우팅을 채택할 경우 이 description이 임베딩 매칭의 유일한 근거가 됨 | "문서 도우미" 같은 모호한 설명은 라우팅 시 다른 에이전트와 구분이 안 됨 |
| behavior-tools 매칭 | behavior 텍스트에서 언급된 행위 키워드(예: "Jira 등록")와 선택된 tool description을 대조해 커버 여부 판단 | behavior가 Jira 등록을 요구하는데 tool 목록에 `create_jira_issue`가 없으면 실행 중 CallingModel이 낼 수 있는 tool_call이 아예 없어 매 턴 실패함 |

## 3. 검증 결과 처리 — warn도 항상 등록 허용

- `pass` → 바로 배포 전 확인 화면으로, 경고 없음.
- `warn`(description 애매함, missing_tools/unused_tools 존재 등) → 확인
  화면에 경고 배너로 사유를 띄우되, **저장을 막지 않는다.** 사용자가 그대로
  무시하고 등록 버튼을 누르면 그대로 `agent`/`agent_tool` 레코드가 생성된다.
- **저장 자체를 막는 hard fail 상태는 두지 않는다.** 빌더 에이전트의 역할은
  게이트키퍼가 아니라 "확인 화면에 띄울 경고 문구를 만들어주는 것"으로
  좁힌다 — 구현 범위가 줄어드는 방향의 선택.
- **이 "hard fail 없음" 원칙은 빌더 LLM이 내리는 판단(설명 애매함, tool
  불일치)에만 적용된다.** 존재하지 않는 tool_ref를 선택하는 것 같은 진짜
  무결성 오류는 해당하지 않는다 — `AgentCrudRepository.create`의
  `_check_tool_refs`가 이미 그런 tool_ref를 409로 거부하고 있고, 이 하드
  검증은 빌더를 붙여도 그대로 유지한다. 빌더가 손대는 건 "저장은 되지만
  경고가 필요한" 애매한 영역이지, "저장 자체가 불가능한" 무결성 오류가 아니다.

## 4. 백엔드가 자동으로 채우는 값

(`Agent_정의와_실행_계약.md` §1-2, §1-3과 동일한 원칙 — 단 model 선택 방식은
§1-3에서 아직 미결로 남겨둔 항목이라, 여기서는 "당장은 고정값을 쓴다"는
결정만 추가한다.)

- `team_id` — 세션에서 주입
- `model` / `reasoning_effort` — 사용자 입력을 받지 않고 플랫폼 기본값을
  쓴다. 기존 수동 생성 폼(`AgentWriteSerializer`)과 같은 값
  (`gpt-5.6-luna` / `low`)으로 맞춘다 — 같은 화면 계열에서 생성 경로에 따라
  기본값이 다르면 안 된다. 모델을 behavior 복잡도로 자동 판단하게 할지는
  여전히 미결(§1-3)이고, 지금은 그냥 고정값이다.
- `max_iterations` — **6**. `공통구조_비교_회의자료.md` §5-②의 8/11 확정값과
  DB 컬럼 기본값(`agent.max_iterations DEFAULT 10`)은 10이지만, 실제 배포된
  수동 생성 폼(`AgentWriteSerializer.max_iterations`, min 2 / max 20)은 이미
  6을 쓰고 있다. 빌더도 그 폼과 같은 값을 써야 두 생성 경로의 동작이 갈리지
  않는다 — 10으로 되돌릴지는 이 문서가 아니라 수동 폼 쪽에서 따로 결정할
  문제로 남긴다.
- Retrieval 범위 — 별도 설정 없이 team_id 스코프가 자동 적용

## 5. 최종 저장 — AgentDefinition 매핑

`Agent_Runtime_단계별_설계.md` §10.3 AgentDefinition 스키마 기준. 단 §10.3의
`instruction.system_prompt_ref`는 버저닝된 프롬프트 저장소를 가리키는
**참조**(`prompt://.../1.3.0`)를 전제하는데, 이 프로젝트에는 그런 저장소가
없고 `agent.instruction`에 텍스트를 그대로 저장한다 — 아래 표의 필드명은
§10.3과 이름만 맞춘 것이고, 실제로는 참조가 아니라 원문 텍스트가 들어간다.

| 빌더 산출물 | AgentDefinition 필드 | 비고 |
|---|---|---|
| name | identity.name | |
| description | identity.description | 검증(§1-2)만 하고 다듬지 않는다 — 사용자가 입력한 원문 그대로 저장. LLM이 다듬는 건 instruction뿐이다 |
| refined_instruction | instruction.system_prompt_ref | 참조가 아니라 텍스트 자체가 `agent.instruction`에 들어간다(위 설명 참고) |
| tools | capabilities.tools.allow | |
| (백엔드) model / reasoning_effort | model.* | §4 — 플랫폼 기본값 고정, 빌더가 판단하지 않는다 |
| (백엔드) max_iterations | runtime.max_iterations | §4 — 6 |
| (백엔드) team_id | Definition이 아니라 Run Contract의 principal.tenant_id로 들어감 | 이 프로젝트엔 Run Contract가 없고 `agent.team_id` 컬럼에 그대로 들어간다 — §10.3은 미래 아키텍처를 전제한 이름이라는 점에 유의 |

## 6. 아직 안 정한 것

- 자동 라우팅을 실제로 채택할지에 따라 description_check의 실효성이 달라짐
  (수동 선택이면 이 체크의 가치가 낮아짐) — 에이전트 선택 방식 자체가 미결.
- warn 사유를 확인 화면에서 어떤 문구/UI로 보여줄지 (배너 vs 필드별 인라인
  경고 등) 화면 설계 필요.
- 이 빌더 흐름이 기존 수동 생성·수정 폼(`AgentEditPage.tsx` — instruction을
  textarea에 직접 타이핑하는 지금 화면)을 대체하는지, 아니면 "생성"에만
  별도 경로로 추가되고 "수정"은 지금처럼 직접 편집으로 남는지. 지금 화면엔
  이 빌더 흐름이 전혀 없어서, 기존 폼과의 관계를 먼저 정해야 구현 범위가
  나온다.
