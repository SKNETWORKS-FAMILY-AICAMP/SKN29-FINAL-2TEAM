# Deep Agent형 에이전트 빌더 개편 설계

## 1. 문서 목적

현재 에이전트 빌드 페이지를 프롬프트 품질 검증 중심 구조에서 Deep Agents 기반의 에이전트 구성 중심 구조로 개편한다.

> **구현 계약 정본:** 실제 분업과 구현에 사용하는 타입, 버전, 검증, 실행 및 이벤트 계약은 [2026-08-13_02_Deep-Agent_런타임_공통_계약_v1.md](./2026-08-13_02_Deep-Agent_런타임_공통_계약_v1.md)를 따른다. 두 문서가 충돌할 경우 `02` 공통 계약서가 우선한다.
>
> **정합 수정 (2026-08-13, 같은 날 저녁):** 최초 작성 당시 §10이 "버전제는 나중에
> 도입"을 전제로 비버전 데이터 모델을 스케치했는데, 이후 확정된 `02`가 처음부터
> 버전 모델(불변 `agent_versions`, 세션·서브에이전트 관계의 버전 고정)을 MVP
> 전제로 삼으면서 두 문서가 어긋나 있었다. §7-1·§9·§10을 `02`에 맞게 고쳤다 — 폐기된
> 원문은 §10에 접이식으로 남긴다.

첫 구현에서는 Deep Agents의 모든 기능을 완성하지 않는다. 기본 에이전트와 한 단계 서브 에이전트를 생성하고 실행할 수 있는 최소 구조를 먼저 만든다. 이후 Deep Agents를 학습하고 실제 사용 결과를 확인하면서 Memory, Middleware, TODO, Checkpointer, HITL 등을 단계적으로 추가한다.

## 2. 합의된 핵심 결정

1. 현재 빌더의 LLM 기반 프롬프트 검증 기능을 제거한다.
2. 에이전트 생성 화면에 서브 에이전트 선택 기능을 추가한다.
3. 빌더에서 저장한 설정으로 Deep Agent를 동적으로 조립한다.
4. MVP에서는 한 단계 위임만 허용한다.
5. Memory, 커스텀 Middleware, TODO 등은 초기 범위에서 제외하고 이후 확장한다.
6. 테스트 실행은 필수 검증 단계가 아닌 선택형 미리보기 기능으로 유지한다.
7. 빌더 테스트 실행과 실제 Chat 실행은 동일한 런타임 조립 코드를 사용한다.

## 3. 제거할 기존 검증 기능

현재 `services/agent_builder`와 빌더 화면에서 제공하는 다음 LLM 기반 검증 흐름을 제거한다.

- 설명이 충분한지 평가하는 기능
- 시스템 프롬프트 또는 지시문의 품질 평가
- 지시문 자동 개선
- 선택한 도구와 지시문의 적합성 평가
- `pass`, `warn`, `reject` 기반 발행 차단
- 활성화 시 `review_builder_input()`을 호출하는 흐름
- 단계별 검증 결과를 보여주는 현재 검증 UI

사용자가 작성한 프롬프트의 품질을 LLM이 심사해 저장이나 활성화를 막지 않는다.

## 4. 제거하면 안 되는 시스템 검증

LLM 기반 내용 검증은 제거하지만, 실행 가능한 구성과 보안 경계를 보장하는 구조 검증은 서버에 남긴다.

- 이름 및 시스템 프롬프트 필수값 검사
- 선택한 모델의 사용 가능 여부 확인
- 선택한 내장 도구의 존재 여부 확인
- 선택한 MCP 도구와 서버의 존재 및 사용 가능 여부 확인
- 현재 사용자와 팀의 도구 사용 권한 확인
- 선택한 서브 에이전트의 존재 여부 및 활성 상태 확인
- 서브 에이전트 실행 권한 확인
- 자기 자신을 서브 에이전트로 선택하는 구성 차단
- 동일한 서브 에이전트의 중복 등록 차단
- 에이전트 순환 참조 차단
- MVP의 한 단계 위임 제한 확인

이 검증은 별도의 큰 검증 페이지에서 수행하지 않는다. 저장 또는 활성화 API가 검사하고, 실패한 항목을 해당 입력 영역과 버튼 주변에 명확하게 표시한다.

## 5. 새로운 빌더 화면 구성

### 5.1 기본 정보

- 에이전트 이름
- 설명
- 시스템 프롬프트

기존 DB와 API의 `instruction` 필드는 초기에는 유지할 수 있다. 다만 사용자 화면에서는 의미가 명확하도록 `시스템 프롬프트`로 표시한다.

### 5.2 모델 및 실행 설정

- 모델
- Reasoning effort
- 최대 반복 횟수

최대 반복 횟수는 초기에는 기존 숫자 입력을 유지할 수 있다. 추후 사용자 친화적인 실행 강도 프리셋으로 변경할 수 있다.

### 5.3 도구

- 서버에 등록된 내장 도구
- 팀에서 사용할 수 있는 MCP 도구
- 각 도구의 설명
- 외부 변경을 발생시키는 도구 표시
- 추후 HITL이 적용될 도구 표시

현재 `ToolPickerModal`과 도구 카탈로그 API는 가능한 범위에서 재사용한다.

### 5.4 서브 에이전트

기존 검증 영역을 제거하고 `서브 에이전트` 영역을 추가한다.

사용자는 `서브 에이전트 추가` 버튼으로 선택 모달을 열 수 있다. 모달에는 다음 정보를 표시한다.

- 에이전트 이름과 설명
- 작성자
- 활성 상태
- 에이전트가 가진 주요 도구
- 선택 가능 여부와 선택 불가 사유

선택한 서브 에이전트마다 다음 설정을 저장한다.

- 자식 에이전트 ID
- 부모에게 노출할 별칭
- 위임 역할 설명
- 추후 버전제 도입 시 자식 에이전트 버전 ID

예시는 다음과 같다.

```text
서브 에이전트: Jira 등록 에이전트
별칭: jira_writer
위임 설명: 사용자가 Jira 이슈 생성을 요청했을 때 사용한다.
```

위임 역할 설명은 부모 에이전트가 어떤 서브 에이전트에 작업을 맡길지 판단하는 핵심 정보이므로 필수값으로 취급한다.

### 5.5 테스트 실행

현재 검증 모달은 선택형 `테스트 실행` 또는 `미리 실행` 기능으로 단순화한다.

테스트 결과에는 가능한 범위에서 다음 정보를 표시한다.

- 부모 에이전트의 응답
- 선택된 서브 에이전트
- 서브 에이전트에 전달한 작업
- 서브 에이전트 응답
- 호출한 도구
- 실행 오류
- 추후 승인 요청 및 재개 상태

테스트 실행을 완료하지 않아도 저장과 활성화는 가능하다.

## 6. MVP 사용자 흐름

```text
기본 정보 작성
→ 모델 설정
→ 도구 선택
→ 서브 에이전트 선택 및 역할 설명
→ 선택적으로 테스트 실행
→ 임시 저장
→ 구조 검증
→ 활성화
```

구조 검증에 실패하면 활성화하지 않고 수정 가능한 상태를 유지한다.

## 7. 기본 Deep Agents 런타임 범위

첫 번째 버전에서는 다음 조립 과정만 지원한다.

1. 저장된 **특정 `agent_version_id`**의 에이전트 정의를 조회한다(02 §5.2 — `agent_id`만으로는
   조회하지 않는다. "현재 버전"이라는 암묵적 개념을 실행 경로에 두지 않는다).
2. 선택한 모델을 생성한다.
3. 허용된 내장 도구와 MCP 도구를 불러온다.
4. 명시적으로 선택한 서브 에이전트를 불러온다.
5. 서브 에이전트를 각각 실행 가능한 Deep Agent로 조립한다.
6. 부모 Deep Agent에 도구와 서브 에이전트를 전달한다.
7. 사용자 메시지를 실행한다.
8. 응답과 실행 이벤트를 UI에 스트리밍한다.

개념적인 초기 형태는 다음과 같다.

```python
agent = create_deep_agent(
    model=model,
    system_prompt=system_prompt,
    tools=selected_tools,
    subagents=selected_subagents,
)
```

실제 API 뷰에서 `create_deep_agent()`를 직접 호출하지 않는다. 모든 실행 경로가 공통 런타임 팩토리를 통하도록 한다.

```text
Builder Test API ─┐
                  ├─→ AgentRuntimeFactory → Deep Agent
Chat API ─────────┘
```

## 8. 런타임 조립기의 기본 구조

초기부터 확장 지점을 분리하되, 아직 지원하지 않는 기능은 빈 구현으로 둔다.

### 8.1 Deep Agent 관련 폴더 구조

Deep Agent 런타임 관련 코드는 `services/agent_runtime` 아래에 모은다. 초기 MVP에서 바로 사용하는 코드와 이후 학습하면서 추가할 Memory, Middleware, TODO, Checkpointer 등의 확장 위치를 처음부터 함께 만든다.

```text
services/
└─ agent_runtime/                    # Deep Agent의 조립·실행·확장 기능을 모으는 런타임 패키지
   ├─ __init__.py                    # 외부에 run_agent 등 최소 공개 인터페이스만 노출
   ├─ definitions.py                 # 부모·서브 에이전트의 런타임 데이터 구조 정의
   ├─ loader.py                      # DB 또는 빌더 초안에서 에이전트 설정을 읽어 정의 객체로 변환
   ├─ factory.py                     # 모델·도구·서브 에이전트·확장 기능을 조합해 Deep Agent 생성
   ├─ executor.py                    # Deep Agent 실행과 스트리밍의 단일 진입점
   ├─ events.py                      # Deep Agents 내부 이벤트를 프런트용 공통 이벤트로 변환
   ├─ context.py                     # 사용자·팀·세션·프로젝트 등 서버가 주입할 실행 문맥 정의
   ├─ exceptions.py                  # 런타임 조립·실행 중 발생하는 공통 예외 정의
   │
   ├─ models/                        # 저장된 모델 설정을 실제 LLM 객체로 만드는 영역
   │  ├─ __init__.py                 # 모델 패키지의 공개 인터페이스 정의
   │  └─ factory.py                  # 모델명·Reasoning 설정을 이용해 실제 모델 클라이언트 생성
   │
   ├─ tools/                         # 부모와 자식에게 허용된 도구를 로딩하고 변환하는 영역
   │  ├─ __init__.py                 # 도구 패키지의 공개 인터페이스 정의
   │  ├─ loader.py                   # tool_ref를 기준으로 내장 도구와 MCP 도구를 선택적으로 로딩
   │  └─ adapters.py                 # 기존 Tool Registry 도구를 Deep Agents 호환 형식으로 변환
   │
   ├─ subagents/                     # 선택된 서브 에이전트의 검사와 런타임 조립을 담당하는 영역
   │  ├─ __init__.py                 # 서브 에이전트 패키지의 공개 인터페이스 정의
   │  ├─ builder.py                  # 자식 정의를 실행 가능한 Deep Agent 서브 에이전트로 생성
   │  └─ validation.py               # 자기 참조·중복·순환 참조·최대 위임 깊이 검사
   │
   ├─ memory/                        # 대화 기억과 장기 기억을 이후 단계에서 추가할 확장 영역
   │  ├─ __init__.py                 # Memory 기능의 활성화 여부와 공개 인터페이스 정의
   │  ├─ short_term.py               # 세션 메시지와 실행 상태 등 단기 대화 기억 담당
   │  └─ long_term.py                # 사용자·팀·에이전트 Namespace 기반 장기 기억 담당
   │
   ├─ middleware/                    # Deep Agent 실행 전후에 공통 정책을 삽입하는 확장 영역
   │  ├─ __init__.py                 # Middleware 패키지의 공개 인터페이스 정의
   │  ├─ factory.py                  # 설정과 실행 문맥에 맞는 Middleware 목록 조립
   │  ├─ permissions.py              # 사용자·팀·도구·데이터 접근 권한 검사
   │  └─ hitl.py                     # 위험 도구 실행 전 사람 승인과 실행 재개 처리
   │
   ├─ planning/                      # TODO와 작업 계획 기능을 이후 단계에서 추가할 영역
   │  ├─ __init__.py                 # Planning 기능의 공개 인터페이스 정의
   │  └─ todo.py                     # 작업 목록 생성·수정·완료 상태 관리
   │
   ├─ checkpoint/                    # 실행 상태 저장과 중단 후 재개를 담당할 확장 영역
   │  ├─ __init__.py                 # Checkpoint 기능의 공개 인터페이스 정의
   │  └─ checkpointer.py             # LangGraph Checkpointer 생성과 저장소 연결 담당
   │
   └─ tracing/                       # 부모·자식·도구 실행을 추적하고 관측하는 영역
      ├─ __init__.py                 # Tracing 패키지의 공개 인터페이스 정의
      └─ callbacks.py                # 실행 이벤트·시간·오류·위임 관계를 로그로 기록
```

### 8.2 핵심 파일의 책임

| 경로 | 책임 |
| --- | --- |
| `definitions.py` | 부모와 서브 에이전트의 런타임 정의 |
| `context.py` | 사용자, 팀, 세션, 프로젝트 등 실행 컨텍스트 |
| `loader.py` | DB 또는 빌더 초안에서 에이전트 정의 로딩 |
| `factory.py` | 모델, 도구, 서브 에이전트와 확장 기능을 조합하여 Deep Agent 생성 |
| `executor.py` | 생성된 Deep Agent 실행과 스트리밍 진입점 |
| `events.py` | Deep Agents 내부 이벤트를 애플리케이션 공통 이벤트로 변환 |
| `exceptions.py` | 런타임 조립 및 실행에서 사용하는 공통 예외 |
| `models/factory.py` | 저장된 모델 설정을 실제 모델 객체로 변환 |
| `tools/loader.py` | 허용된 내장 도구와 MCP 도구 로딩 |
| `tools/adapters.py` | 기존 Tool Registry의 도구를 Deep Agents 형식으로 변환 |
| `subagents/builder.py` | 선택된 자식 정의를 실행 가능한 서브 에이전트로 조립 |
| `subagents/validation.py` | 자기 참조, 중복, 순환 및 위임 깊이 검사 |

### 8.3 초기 구현과 확장 예약 구분

첫 번째 MVP에서 실제로 동작하도록 구현하는 영역은 다음과 같다.

- `definitions.py`
- `context.py`
- `loader.py`
- `models/factory.py`
- `tools/loader.py`
- `tools/adapters.py`
- `subagents/builder.py`
- `subagents/validation.py`
- `factory.py`
- `executor.py`
- `events.py`

다음 영역은 폴더와 최소 인터페이스를 먼저 만들되 초기에는 비활성 상태로 둔다.

- `memory`
- `middleware`
- `planning`
- `checkpoint`
- `tracing`

빈 확장 영역에는 복잡한 추상화나 동작을 미리 구현하지 않는다. 현재 상태와 도입 조건을 모듈 주석으로 기록하고, 런타임에는 `None` 또는 빈 목록을 반환한다.

```python
# middleware/factory.py
def build(definition, context):
    return []


# checkpoint/checkpointer.py
def build(definition, context):
    return None
```

### 8.4 런타임 내부 의존 흐름

```text
executor
  ├─ loader
  │   └─ definitions
  │
  ├─ factory
  │   ├─ models
  │   ├─ tools
  │   ├─ subagents
  │   ├─ memory
  │   ├─ middleware
  │   ├─ planning
  │   └─ checkpoint
  │
  └─ events
      └─ tracing
```

`apps/agents`와 `apps/chat`은 Deep Agents를 직접 조립하지 않는다. 빌더 테스트와 실제 Chat은 모두 `agent_runtime.executor`를 통해 실행한다.

### 8.5 런타임 팩토리 확장 원칙

```python
class AgentRuntimeFactory:
    def build(self, definition, context):
        model = self.build_model(definition)
        tools = self.build_tools(definition, context)
        subagents = self.build_subagents(definition, context)
        middleware = self.build_middleware(definition, context)

        return create_deep_agent(
            model=model,
            system_prompt=definition.system_prompt,
            tools=tools,
            subagents=subagents,
            middleware=middleware,
        )

    def build_middleware(self, definition, context):
        return []
```

Memory, Middleware, TODO, Checkpointer가 아직 구현되지 않았더라도 `factory.py`가 해당 확장 지점을 거치는 형태는 처음부터 유지한다. 이후 기능 추가 시 API나 실행 진입점을 변경하지 않고 각 하위 모듈의 구현을 교체하는 것을 목표로 한다.

런타임 컨텍스트에는 최소한 다음 정보가 포함되어야 한다.

- 요청 사용자 ID
- 팀 ID
- 세션 ID
- 프로젝트 ID
- MCP 자격 증명 해석에 필요한 실행 주체

사용자와 팀 정보는 모델이 전달하는 인자를 신뢰하지 않고 서버 런타임 컨텍스트에서 주입한다.

## 9. 서브 에이전트 MVP 정책

초기 버전에서는 다음 규칙을 적용한다.

- 빌더에서 명시적으로 선택한 에이전트만 부모에게 제공한다.
- 활성 상태인 에이전트만 선택할 수 있다.
- 자기 자신은 선택할 수 없다.
- 같은 에이전트를 중복 선택할 수 없다.
- 위임 역할 설명은 필수다.
- 부모에서 자식으로 한 단계만 위임할 수 있다.
- 자식의 서브 에이전트는 실행 시 로딩하지 않는다.
- 순환 참조가 확인되면 저장 또는 활성화를 거부한다.
- **선택한 자식은 특정 버전(`child_version_id`)에 고정된다** — 부모 버전을 발행한 뒤
  자식이 새 버전을 내도 이 부모는 발행 시점의 자식 버전을 계속 쓴다(02 §5.4). "자식을
  고치면 모든 부모에 즉시 반영"은 이 모델에서 발생하지 않는다.

MVP에서는 다음 구성을 허용한다.

```text
Main Agent → Subagent
```

다음 구성은 허용하지 않는다.

```text
Main Agent → Subagent → Subagent
```

다단계 위임은 승인 재개, 실행량 제한, 스트리밍 계층 표현, 장애 전파 정책을 설계한 뒤 확장한다.

## 13. Memory 도입 원칙

Memory는 하나의 기능으로 묶지 않고 다음 두 종류로 분리한다.

### 대화 기억

- 동일 세션의 이전 메시지
- 실행 중인 그래프 상태
- 도구 승인 후 재개 정보

초기에는 현재처럼 저장된 메시지 히스토리를 다시 주입하는 방식으로 시작할 수 있다. 이후 Checkpointer로 전환한다.

### 장기 기억

- 사용자 선호
- 팀 공용 지식
- 에이전트가 저장한 재사용 정보

장기 기억은 다음 Namespace와 접근 정책을 정의한 후 도입한다.

```text
team / user / agent
```

누가 저장할 수 있고 누가 읽을 수 있는지 정하지 않은 상태에서는 장기 Memory를 도입하지 않는다.

## 14. 실행 로그와 관측성

Memory나 고급 Middleware가 없어도 초기부터 다음 실행 정보는 남긴다.

- 실행한 부모 에이전트
- 선택한 서브 에이전트
- 서브 에이전트에 위임한 작업
- 호출한 도구
- 부모 실행 ID와 자식 실행 ID의 관계
- 실행 성공 또는 실패 상태
- 실행 시간
- 모델 및 도구 오류 코드

이를 통해 부모가 어떤 이유로 자식을 선택했고 어느 단계에서 실패했는지 추적할 수 있어야 한다.

## 15. 구현 시 주의사항

### 테스트 실행과 실제 실행의 차이 방지

테스트 실행과 Chat이 서로 다른 조립 코드를 사용하면 테스트에서는 성공하지만 실제 대화에서는 실패할 수 있다. 두 경로는 반드시 동일한 `AgentRuntimeFactory`를 사용한다.

### 전체 활성 에이전트 자동 노출 금지

팀의 모든 활성 에이전트를 자동으로 부모의 서브 에이전트로 등록하지 않는다. 빌더에서 사용자가 명시적으로 선택한 자식만 런타임에 전달한다.

### 활성화 검증의 실패 정책

구조와 권한 검증은 실패 시 활성화를 차단한다. 외부 LLM을 이용한 프롬프트 품질 검사는 활성화 조건으로 사용하지 않는다.

### 기존 시스템과의 관계

현재 시스템은 정문 에이전트가 `agent:*` 도구를 통해 다른 에이전트에 위임하는 구조를 일부 갖고 있다. 새 빌더에서는 이 위임 대상을 자동으로 결정하지 않고 부모와 자식의 명시적인 관계로 저장하는 방향으로 전환한다.

## 16. 첫 번째 완료 기준

다음 흐름이 끝까지 동작하면 첫 번째 Deep Agent형 빌더 구현이 완료된 것으로 본다.

```text
새 에이전트 작성
→ 시스템 프롬프트와 모델 저장
→ 내장 도구 또는 MCP 도구 선택
→ 활성 에이전트 한 개를 서브 에이전트로 추가
→ 위임 역할 설명 저장
→ 구조 검증 후 활성화
→ Chat 또는 테스트 실행에서 부모 Deep Agent 실행
→ 부모가 선택한 자식에게 작업 위임
→ 자식 결과를 부모가 받아 최종 응답 생성
→ 부모·자식·도구 실행 로그 확인
```

이 시점에는 Memory, TODO, 커스텀 Middleware가 없어도 된다. 핵심은 빌더에서 저장한 구성이 공통 런타임 조립기를 통해 실제 부모·서브 에이전트 실행으로 이어지는 것이다.
