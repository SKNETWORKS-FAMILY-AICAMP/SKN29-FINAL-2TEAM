# 10. 병렬 실행과 timeout

## 한 줄 정리

LLM이 한 응답에서 여러 도구 또는 `task` 호출을 만들면 LangGraph가 동시에 실행하며, 우리 서비스는 동시 실행 수를 4로 제한하고 일부 쓰기 작업만 잠금으로 직렬화한다.

## Deep Agents 기본 설계

기본 `SubAgentMiddleware.task`는 한 호출 안에서 서브에이전트 하나를 실행한다. 하지만 LLM이 한 AIMessage에 여러 tool call을 만들면 LangGraph ToolNode가 같은 super-step에서 병렬 실행할 수 있다. 이것은 `AsyncSubAgentMiddleware` 없이도 가능하다.

`AsyncSubAgentMiddleware`는 원격 Agent Protocol 작업을 백그라운드로 시작하고 상태 조회·수정·취소하는 별도 기능이며, 단순 병렬 호출용 필수 요소가 아니다.

## 우리 설계

- `max_concurrency=4`를 LangGraph 실행 config에 전달한다.
- LLM이 독립 작업을 여러 `task`로 동시에 호출하도록 도구 설명에서 안내한다.
- Root의 병렬 호출 안에서 Child도 병렬 도구 호출을 만들 수 있어 이론상 최대 4×4 실행이 가능하다.
- 같은 프로젝트의 `task_register`, `task_update`, `jira_create_issues`는 잠금으로 직렬화한다.
- MCP 호출은 기본 480초, 최대 540초의 런타임 timeout 정책을 가진다.
- 실제 HTTP MCP 클라이언트에는 별도의 연결·읽기 timeout이 있다.

## 설계 이유

읽기·조사 작업은 빠르게 처리하면서 쓰기 경합과 무제한 동시 실행으로 인한 서버 고갈을 막기 위해서다.

## 좋은 부분

- 병렬 여부는 요청마다 LLM이 판단하고 플랫폼은 안전한 상한을 적용한다.
- 독립 작업은 병렬, 충돌 가능성이 있는 일부 쓰기는 직렬로 처리한다.
- AsyncSubAgent 인프라 없이 현재 요청 안의 병렬 처리 효과를 얻는다.
- 동시 실행 상한이 Root와 재개 경로에도 적용된다.

## 문제점

- 기본값 4는 부하 테스트로 확정한 값이 아니다.
- 중첩 병렬성으로 한 요청이 최대 16개의 작업을 동시에 만들 수 있다.
- 사용자 MCP의 rate limit, 동시성 허용 여부, 읽기·쓰기 성격을 플랫폼이 알 수 없다.
- 런타임 480초 정책과 HTTP read timeout 약 30초가 서로 달라 실제 동작 설명이 혼란스럽다.
- ThreadPool timeout은 기다림을 중단할 뿐 실행 중인 Python 스레드나 외부 요청을 강제 취소하지 못할 수 있다.

## 현재 판단

현재 방식은 첫 단계로 적절하다. AsyncSubAgentMiddleware를 바로 도입하기보다 동시성 계측, MCP별 실패율, 대기 시간, 중첩 실행 수를 먼저 측정하는 편이 좋다.

## 즉시 수정이 필요한 치명적 문제

쓰기 MCP가 timeout된 뒤 백그라운드에서 성공할 수 있는데 시스템은 실패처럼 보일 수 있다. 이 상태에서 자동 재시도하면 중복 변경이 발생한다. timeout 후 상태를 `실패`가 아니라 `결과 불명확`으로 구분하고 자동 재시도를 금지해야 한다.
