# 07. 장기 메모리와 대화 상태

## 한 줄 정리

Deep Agents의 파일 기반 MemoryMiddleware를 사용하되, 장기 저장은 계정별 개인 선호 파일 하나로 좁히고 나머지 파일은 대화 스레드 상태로만 유지한다.

## Deep Agents 기본 설계

Deep Agents는 backend와 store를 연결하면 파일 도구와 MemoryMiddleware를 통해 메모리 파일을 읽고 쓸 수 있다. 어떤 경로를 장기 저장할지는 애플리케이션이 backend 라우팅으로 결정한다.

## 우리 설계

- `/memories/users/preferences.md`만 PostgresStore에 장기 저장한다.
- 저장 namespace에 계정 ID를 사용해 사용자별로 격리한다.
- 팀·프로젝트 공유 장기 메모리는 제거했다.
- 다른 파일은 StateBackend에 두며 같은 대화에서는 Checkpointer로 이어지지만 다른 대화에는 자동 공유하지 않는다.
- 개인 메모리는 매 턴 시스템 프롬프트에 주입한다.
- Root의 메모리 쓰기에는 `MemoryWriteGuardMiddleware`를 붙여 credential, 개인정보, 권한·보안 관련 텍스트를 차단한다.
- 저장된 메모리는 명령이 아니라 데이터로 취급하라는 메모리 전용 지침이 있다.

## 설계 이유

팀 공유 메모리의 잘못된 정보 전파와 권한 문제를 줄이고, 사용자에게 장기간 유효한 선호만 재사용하기 위해서다.

## 좋은 부분

- 사용자별 namespace 격리가 명확하다.
- 프로젝트 한정 사실이 모든 미래 대화에 섞이는 것을 줄였다.
- 민감정보 저장을 프롬프트뿐 아니라 코드 패턴 검사로 한 번 더 막는다.
- 대화 상태와 장기 기억의 의미를 분리했다.

## 문제점

- `preferences.md`가 매 턴 들어가므로 길어지면 토큰 비용과 오래된 정보의 영향이 커진다.
- 패턴 기반 write guard는 여러 번 나눠 쓰거나 변형한 민감정보를 놓칠 수 있다.
- 반대로 정상 전화번호 같은 내용을 과잉 차단할 수 있다.
- 모델이 판단한 잘못된 선호가 저장되면 이후 모든 대화에 반복 주입될 수 있다.
- PostgresStore 연결은 프로세스 단위 singleton이며 명시적인 종료 처리가 없다.

## 현재 판단

개인 선호만 장기 저장하는 방향은 안전하고 이해하기 쉽다. 메모리 크기 제한, 갱신 이력, 사용자 확인·삭제 UI가 함께 있어야 완성된다.

## 즉시 수정이 필요한 치명적 문제

민감정보 guard를 완전한 보안 경계로 간주하면 안 된다. 실제 메모리 읽기·쓰기 권한이 account namespace에서 확실히 격리되는 통합 테스트와 사용자 삭제 기능은 공개 운영 전에 반드시 확인해야 한다.
