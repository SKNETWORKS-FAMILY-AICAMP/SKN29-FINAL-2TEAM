# 02. 모델 해석과 생성

## 한 줄 정리

Deep Agents에 모델 이름을 바로 넘기지 않고, 팀 설정과 provider를 먼저 해석해 완성된
LangChain 모델 객체를 전달한다.

## Deep Agents 기본 설계

`create_deep_agent()`는 모델 문자열이나 모델 객체를 직접 받는다.

```python
create_deep_agent(model="openai:gpt-5")
```

또는:

```python
create_deep_agent(model=ChatOpenAI(...))
```

`model=None`도 가능하지만 0.7.5에서 deprecated 상태다.

## 우리 프로덕트 설계

```text
agent_versions.model
  → ModelConfigResolver
  → ResolvedModelConfig
  → ModelFactory
  → ChatOpenAI 또는 ChatAnthropic
  → create_deep_agent(model=모델 객체)
```

지원 경로:

- Anthropic
- OpenAI 공식 API
- 팀이 등록한 OpenAI-compatible endpoint

OpenAI 공식 API는 Responses API와 reasoning summary를 사용한다. OpenAI-compatible
서버에는 호환성을 보장할 수 없어 Responses API와 provider 전용 reasoning 설정을
강제하지 않는다.

Root와 Child는 서로 다른 모델을 가질 수 있다.

주요 코드:

- `services/agent_runtime/models/factory.py`
- `services/agent_runtime/factory.py`

## 이렇게 설계한 이유

- 팀별 커스텀 모델 endpoint를 지원해야 한다.
- API Key를 Agent 정의나 프롬프트에 저장하면 안 된다.
- OpenAI와 Anthropic의 reasoning 설정 방식이 다르다.
- 실제 실행에 사용된 provider와 endpoint 변경 여부를 로그로 남겨야 한다.

## 좋은 부분

- 팀마다 다른 모델 서버를 사용할 수 있다.
- Root는 빠른 모델, Child는 강한 모델처럼 역할별 선택이 가능하다.
- provider별 옵션을 구분해서 전달한다.
- Deep Agents의 모델 문자열 해석 변화에 덜 영향을 받는다.
- endpoint 원문 대신 hash를 기록해 내부 주소 노출을 줄인다.

## 문제점

- provider를 일부 모델 이름 패턴으로 판단한다.
- 새로운 provider를 추가할 때 Resolver와 Factory 코드를 수정해야 한다.
- OpenAI-compatible 서버가 tool calling, streaming, 병렬 Tool call을 실제로
  지원하는지는 모델 생성만으로 확인할 수 없다.
- reasoning effort 허용값이 provider마다 다를 수 있다.
- 실행 전에 사용하지 않을 Child 모델과 그래프도 모두 준비하므로 Child 수가 많으면
  조립 비용이 커질 수 있다.
- endpoint hash는 같은 서버인지 비교할 수 있지만 과거 URL을 복원할 수는 없다.

## 현재 판단

구조는 적절하다. 특히 팀별 endpoint와 provider별 옵션을 지원하려면 모델 객체를 먼저
만들어 Deep Agents에 넘기는 방식이 필요하다.

장기적으로는 모델 이름에서 provider를 추측하지 말고 모델 등록 정보에 provider와
capability를 명시하는 편이 안전하다.

## 즉시 수정이 필요한 치명적 문제

현재 기본 OpenAI·Anthropic 모델만 사용하는 범위에서는 확인된 치명적 문제는 없다.

하지만 불특정 사용자가 커스텀 모델을 등록할 수 있는 운영 환경이라면 capability 검증
없이 활성화하는 것은 위험하다. 최소한 다음 테스트를 통과한 모델만 Deep Agent용으로
활성화해야 한다.

- 단일 Tool call
- Tool 결과를 받은 뒤 최종 응답
- streaming
- 복수 Tool call 또는 병렬 Tool call 지원 여부
