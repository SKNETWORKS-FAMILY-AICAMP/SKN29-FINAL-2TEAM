# 08. 체크포인트와 사람 승인(HITL)

## 한 줄 정리

Postgres Checkpointer로 대화와 중단 상태를 저장하고, 부수효과 도구는 HumanInTheLoopMiddleware에서 멈춘 뒤 사용자의 승인·수정·거부로 재개한다.

## Deep Agents 기본 설계

Deep Agents는 LangGraph checkpointer를 받을 수 있고, `interrupt_on`을 주면 HumanInTheLoopMiddleware를 자동 연결한다. 중단된 실행은 같은 `thread_id`와 `Command(resume=...)`로 재개한다.

## 우리 설계

- `session_id`를 LangGraph `thread_id`로 사용한다.
- PostgresSaver를 프로세스별로 한 번 열어 재사용한다.
- `side_effect=True`이면서 현재 역할에 허용된 도구 전체를 `interrupt_on`에 넣는다.
- 한 모델 응답에 여러 쓰기 호출이 있으면 하나의 승인 묶음으로 화면에 표시한다.
- 승인 전 run은 실패가 아니라 `PENDING`으로 기록한다.
- 재개할 때 기존 run_id와 thread_id를 사용하며 새 사용자 메시지를 넣지 않는다.
- 같은 tool_call이 이미 성공했다면 다시 실행하지 않는 내부 멱등성 방어가 있다.

## 설계 이유

외부 시스템 변경 전에 사람이 최종 결정을 내리게 하고, 웹 요청이 끊겨도 실행 상태를 이어가기 위해서다.

## 좋은 부분

- 승인 전에는 실제 쓰기가 실행되지 않는다.
- 승인 대기 상태와 실패 상태를 구분한다.
- 재개가 대화 기록 재전송이 아니라 체크포인트 상태를 기준으로 동작한다.
- 중복 재개에 대한 1차 멱등성 방어가 있다.

## 문제점

- leader와 member 모두 모든 side-effect 도구를 자기 승인으로 실행할 수 있다. 도구별 권한 구분이 없다.
- MCP는 읽기 도구도 전부 side-effect로 분류되어 불필요한 승인 카드가 뜬다.
- 여러 쓰기 호출을 한 묶음으로 승인하면 사용자가 개별 호출의 영향과 부분 실패를 이해하기 어렵다.
- Checkpointer 테이블의 보존 기간과 정리 정책이 명확하지 않으면 대화·도구 인자가 장기간 남는다.
- 내부 멱등성은 외부 MCP 서버가 요청을 처리한 뒤 응답만 유실한 경우까지 해결하지 못한다.

## 현재 판단

HITL 연결 자체는 잘 되어 있다. 앞으로는 도구별 위험도와 조직 권한에 따라 승인 정책을 세분화해야 한다.

## 즉시 수정이 필요한 치명적 문제

임의 MCP 쓰기 도구에 대해 timeout·연결 끊김 후 상태가 불명확한데 사용자가 다시 승인하면 외부 작업이 중복될 수 있다. 외부 idempotency key, 실행 상태 조회, 또는 “결과 불명확” 상태에서 자동 재시도 금지가 필요하다.
