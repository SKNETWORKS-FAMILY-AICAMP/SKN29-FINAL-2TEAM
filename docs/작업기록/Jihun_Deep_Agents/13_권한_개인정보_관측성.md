# 13. 권한, 개인정보와 관측성

## 한 줄 정리

Deep Agents 바깥에 팀 실행 문맥, 도구 실행 권한, 개인정보 마스킹, Langfuse·LangSmith 추적을 추가해 멀티테넌트 제품으로 확장했다.

## Deep Agents 기본 설계

Deep Agents는 호출자가 넘긴 도구와 문맥을 실행한다. 우리 서비스의 팀·계정 권한, DB run 기록, 외부 관측 서비스 마스킹 정책은 알지 못한다.

## 우리 설계

- `RuntimeContext`에 account, team, session, project, run 정보를 담아 서버에서 도구에 주입한다.
- 모델이 account_id나 team_id를 임의로 인자로 만들지 못하게 숨긴다.
- side-effect 도구는 실행 직전에 계정 역할을 다시 검사한다.
- 현재 기본 정책에서는 leader와 member 모두 side-effect 도구를 사용할 수 있지만 HITL 승인을 거친다.
- 채팅 입력과 외부 tracing 사본에서 이메일, credential, 주민번호, 카드, 전화번호 패턴 등을 마스킹한다.
- 내부 이벤트 DB 기록과 Langfuse·LangSmith callback을 함께 사용한다.
- 외부 관측 서비스가 실패해도 에이전트 실행은 계속한다.

## 설계 이유

한 팀의 도구와 데이터가 다른 팀으로 섞이지 않게 하고, 운영 문제를 추적하면서 외부 로그로 민감정보가 나가는 위험을 줄이기 위해서다.

## 좋은 부분

- 권한 문맥을 모델 입력이 아니라 서버가 주입한다.
- 도구 노출과 실제 실행 권한을 분리해 “기능 없음”과 “권한 없음”을 구분한다.
- tracing 장애가 본 서비스 장애로 번지지 않는다.
- 두 관측 시스템에 같은 마스킹 정의를 재사용한다.

## 문제점

- 문자열 패턴 마스킹은 모든 비밀과 개인정보를 찾지 못하며 오탐도 발생한다.
- leader/member가 동일한 쓰기 권한이라 조직 RBAC가 사실상 세분화되지 않았다.
- 외부 MCP 결과와 도구 설명이 tracing에 어느 범위까지 남는지 데이터 보존·국외 전송 정책이 필요하다.
- 도구를 모델에게 보인 뒤 실행 시점에 막는 방식은 불필요한 호출과 오류 턴을 만들 수 있다.
- 마스킹 실패 시 일부 객체는 문자열 표현으로 처리되므로 새로운 payload 타입에 대한 테스트가 필요하다.

## 현재 판단

멀티테넌트 안전성의 기본 골격은 있다. 그러나 패턴 마스킹을 데이터 보호의 유일한 수단으로 사용해서는 안 된다.

## 즉시 수정이 필요한 치명적 문제

팀 간 데이터 격리는 프롬프트나 마스킹이 아니라 모든 Repository와 MCP credential 조회의 서버측 조건으로 보장되어야 한다. account/team 교차 접근 통합 테스트가 없다면 공개 전에 가장 먼저 추가해야 한다.
