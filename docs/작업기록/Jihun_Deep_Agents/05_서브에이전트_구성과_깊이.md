# 05. 서브에이전트 구성과 위임 깊이

## 한 줄 정리

기본 Deep Agents의 서브에이전트 기능을 사용하지만, 사용자가 DB에서 선택한 에이전트를 실행 시점에 `CompiledSubAgent`로 만들고 위임을 1단계로 제한했다.

## Deep Agents 기본 설계

Deep Agents는 서브에이전트 설정에 이름, 설명, 프롬프트, 도구 또는 미리 컴파일한 그래프를 받을 수 있다. Root는 `task` 도구로 해당 에이전트를 호출한다. 서브에이전트는 호출자의 전체 대화 상태를 자동으로 받지 않고 위임문을 입력으로 받는다.

## 우리 설계

- Builder에서 선택한 Child의 특정 발행 버전을 DB에서 읽는다.
- Child마다 별도 모델, 프롬프트, 도구, 호출 상한을 적용해 그래프를 미리 컴파일한다.
- 사용자가 정한 `alias`가 `subagent_type`이 되고, `delegation_description`이 Root가 보는 설명이 된다.
- 같은 Child 중복, alias 중복, 자기 참조, 비활성·권한 없음, 순환 참조를 검사한다.
- Child가 또 다른 Child를 가지는 2단계 위임은 저장·테스트 실행·런타임에서 모두 막는다.
- Root마다 읽기 전용 general-purpose도 명시적으로 추가한다.

## 설계 이유

사용자가 만든 에이전트를 안전하게 조합하면서 무한 위임, 순환 호출, 권한 우회를 막기 위해서다. 1단계 제한은 실행 비용과 실패 경로를 예측하기 쉽게 만든다.

## 좋은 부분

- Child가 어느 버전과 모델로 실행됐는지 고정하고 기록할 수 있다.
- 저장 경로뿐 아니라 Builder Test Run도 같은 깊이 검사를 받는다.
- Child별 역할과 도구가 분리된다.
- 순환과 자기 참조를 실행 전에 발견한다.

## 문제점

- Root를 만들 때 모든 Child 그래프를 먼저 컴파일하므로 Child 수가 커지면 첫 응답 지연과 메모리 사용량이 증가한다.
- 1단계 제한은 안전하지만 전문 에이전트를 여러 단계로 조합하는 기능을 막는다.
- alias와 설명의 품질을 사용자가 결정하므로 모호한 설명이면 LLM이 잘못 위임할 수 있다.
- 현재 `CompiledSubAgent`는 요청 안에서 끝나는 동기식 실행이다. 원격 백그라운드 작업의 시작·조회·취소 기능은 없다.

## 현재 판단

MVP에는 적절하다. 에이전트 수가 늘면 모든 Child를 선컴파일하지 말고 선택된 Child를 지연 생성하거나 캐시하는 구조를 검토해야 한다.

## 즉시 수정이 필요한 치명적 문제

현재 확인된 즉시 장애급 문제는 없다. 다만 Child 수 증가 전 부하 테스트 없이 그대로 확장하면 그래프 조립 비용이 병목이 될 수 있다.
