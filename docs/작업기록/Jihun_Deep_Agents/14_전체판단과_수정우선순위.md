# 14. 전체 판단과 수정 우선순위

## 우리 Deep Agents 설계의 성격

우리 제품은 Deep Agents를 그대로 호출하는 챗봇이 아니다. Deep Agents와 LangGraph를 실행 엔진으로 사용하고 그 위에 다음 제품 계층을 추가한 Agent Platform이다.

- DB 기반 에이전트 Builder와 발행 버전
- 팀·계정·프로젝트 실행 문맥
- 사용자 연결 MCP와 내장 업무 도구
- Root·전용 Child·읽기 전용 GP
- 공통 프롬프트와 위임 규칙
- 호출 상한, 병렬성 제한, timeout, 쓰기 잠금
- 개인 장기 메모리와 Postgres Checkpointer
- HITL 승인과 중단·재개
- 제품용 스트리밍 이벤트와 실행 추적
- 개인정보 마스킹과 외부 observability

## 전체적으로 좋은 부분

- 라이브러리 버전을 고정하고 호환 계층을 만들었다.
- 권한·승인·호출 상한을 프롬프트가 아닌 코드로 강제한다.
- 사용자가 만든 에이전트와 MCP를 런타임에 조립할 수 있다.
- Child 깊이, 순환, 권한을 실행 전에 검사한다.
- 병렬 실행은 허용하되 전체 동시성 상한을 둔다.
- 쓰기 작업은 HITL과 일부 잠금·멱등성 방어를 거친다.
- 대화 상태, 장기 기억, 팀 업무의 의미를 구분했다.
- 내부 라이브러리 이벤트를 제품 이벤트 계약으로 변환한다.

## 바로 수정해야 할 1순위

### 1. MCP SSRF 방어 완성

현재 URL 사전 검증이 있어도 HTTP redirect를 따라가면 공개 주소에서 내부 주소로 우회될 수 있다. 요청에서 redirect를 금지하고, DNS rebinding까지 고려한 네트워크 egress 방화벽 또는 전용 proxy로 내부 CIDR과 metadata 주소를 차단해야 한다.

### 2. MCP timeout 후 결과 불명확 상태 처리

Thread timeout은 실제 외부 실행을 취소하지 못할 수 있다. 쓰기 요청은 timeout 후 `FAILED`로 단정하거나 자동 재시도하지 말고 `UNKNOWN` 또는 `TIMED_OUT_UNCERTAIN` 상태로 기록해야 한다. 가능하면 외부 idempotency key와 상태 조회 기능을 사용한다.

### 3. 외부 데이터 프롬프트 인젝션 방어

MCP·문서·이슈 본문은 명령이 아니라 데이터로 취급하도록 공통 지침을 복구한다. 동시에 읽기·쓰기 권한 분리, 민감 데이터 최소 노출, 결과 크기 제한, 승인과 감사 로그를 유지한다. 프롬프트 문장만으로 해결됐다고 판단하면 안 된다.

### 4. 사용자 에이전트 프롬프트와 플랫폼 정책 충돌

Builder 프롬프트가 공통 Scaffold 뒤에 붙는다. 충돌 시 플랫폼 정책이 우선한다고 명시하고, 명백한 정책 무시 문구를 검사한다. 보안 경계는 계속 코드에 둔다.

## 공개 운영 전 2순위

- MCP 도구 설명·JSON Schema·도구 수·LLM에 전달하는 결과 크기 제한
- team/account 교차 접근 통합 테스트
- 체크포인트·메모리·tracing 데이터의 보존 및 삭제 정책
- 도구별 RBAC와 위험도별 HITL 정책
- 런타임 480초와 실제 MCP HTTP timeout의 정책 일치
- 병렬성 4와 중첩 최대 16에 대한 부하 테스트
- 호출 수·비용·대기 시간·timeout·부분 실패 모니터링과 경보
- 실행 snapshot에 runtime 정책 버전 기록

## 확장 시 3순위

- Child 그래프 지연 생성 또는 캐시
- 1단계보다 깊은 위임이 정말 필요한지 실제 사례로 재검토
- MCP capability를 사용자가 선택적으로 선언하고 운영 중 관측으로 보정하는 구조
- 장시간 작업에 한해 AsyncSubAgent·worker·background 실행 도입
- UI가 지원할 때 에이전트별 표·코드블록 출력 허용
- GP에 검증된 read-only MCP만 선택적으로 허용

## 최종 결론

현재 설계는 MVP 실행 엔진으로는 탄탄한 편이며 전면 재작성할 이유는 없다. 문제의 중심은 Deep Agents 자체보다 “사용자가 임의의 MCP와 프롬프트를 연결하는 플랫폼”에서 생기는 신뢰 경계다.

따라서 AsyncSubAgentMiddleware를 먼저 추가하거나 모든 실행을 비동기로 바꾸는 것보다, SSRF·timeout 불확실성·프롬프트 인젝션·권한 격리를 먼저 해결하는 것이 맞다. 이후 실제 운영 지표에서 오래 걸리는 작업과 병렬 병목이 확인되면 그때 background worker와 AsyncSubAgent를 선택적으로 추가하면 된다.
