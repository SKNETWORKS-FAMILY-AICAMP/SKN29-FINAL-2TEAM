### 1.1 토큰을 어디서 세는가 — `events.py` 인 이유

`agent_run.iterations`/`token_in`/`token_out` 이 새 엔진에서 **0 / NULL / NULL
고정**이었다(레거시 harness 만 재고 있었다). 이제 `EventMapper._count_model_call()`
이 모델 노드 update 마다 `usage_metadata` 를 누적해 **끝나는 이벤트**(`result` ·
`subagent_completed` · `error`)에 실어 보내고, `tracing/` 의 `_usage_of()` 가
옮겨 적는다.

**왜 `tracing/` 에서 직접 안 세나** — 그 모듈은 변환된 이벤트만 보므로 원시
`AIMessage.usage_metadata` 에 닿지 못한다. 전용 이벤트를 새로 내면
`apps/chat` 의 `_relay()` 가 종류를 안 가리고 브라우저까지 흘려보낸다.
그래서 누계는 저쪽에서 세고 이쪽은 적기만 한다.

### 1.2 실측으로 발견한 것 둘

**① `openai_compatible` 은 토큰이 아예 안 왔다.** `langchain_openai`(1.3.0
소스 확인)는 `base_url` 이 있으면 `stream_usage` 자동 활성화 조건에서 뺀다 —
이 경로는 정의상 항상 `base_url` 이 있다. 팀에 실제로 등록된 것이 **Gemini 의
OpenAI 호환 주소**라 주력 경로가 통째로 NULL 이었다.

`stream_options` 를 거부하는 호환 서버가 있을 수 있어 **그 주소로 직접 확인하고**
`stream_usage=True` 를 켰다(정상 응답, usage 를 준다).

> ⚠ 새 엔드포인트를 등록할 때 이 옵션을 거부하는 서버를 만나면 **실제 대화에서
> 처음 드러난다.** `/ops/models` 의 「연결 확인」은 스트리밍이 아니라 못 잡는다.

**② Gemini 는 thinking 토큰을 `total_tokens` 에만 넣는다.** 실제 응답이
`prompt 6 · completion 1 · total 149` 였고 `completion_tokens_details` 는 `null`
이다. 있는 그대로 적으면 Usage 합계가 149 대신 7 — 한 자릿수로 틀린다.
**설명되지 않는 나머지를 출력 쪽에 얹는다.** 총합이 딱 맞는 제공자(OpenAI
11+5=16)는 나머지가 0 이라 그대로다.

별도 칸으로 나누려면 컬럼을 더해야 하고 그건 팀원 전원이 ALTER 를 돌려야 하는
변경이라, 필요해지면 그때 나눈다.

### 1.3 조회 문서는 식별자만 담는다

`tool_call.retrieved_doc_ids TEXT[]`(+ GIN). 도구별로 분기하지 않고 결과 JSON 의
`doc_id` 키를 재귀로 모은다 — 핸들러가 dict 를 돌려주면 langchain-core 의
`_stringify()` 가 `json.dumps` 로 만들어서 되읽을 수 있다.

**본문은 안 담는다.** 원문을 남기면 감사 로그가 문서 사본이 된다
(`input_summary` 가 자격증명을 안 남기는 것과 같은 원칙). 접근 감사가 묻는 것은
「어느 문서를 봤나」이지 「무엇이라고 쓰여 있었나」가 아니다.

GIN 을 건 이유는 역추적이 주 용도라서다 —
`WHERE 'DC001' = ANY(retrieved_doc_ids)`.

### 1.4 요약 화면은 왜 우리가 만들었나

시중 제품 조사(오늘) 결과 관측성을 **요약 → 목록 → 상세** 세 층으로 나눈다.

- **목록/상세**: 실행 하나를 따라가는 트레이스 → **아무도 직접 안 만든다.**
  watsonx Orchestrate 는 Langfuse + IBM Telemetry, Azure AI Foundry 는

그래서 `/ops/usage` 는 요약만 만들고 상세는 Langfuse 로 보낸다(§4).

## 3. ⚠ 넘기는 결함 — 승인 도구가 전부 「실패」로 기록된다

`/ops/usage` 를 켜자마자 잡혔다. **`task_register` 8회 0% · `jira_create_issues`
3회 0%** — 0% 인 것이 정확히 **승인 게이트가 걸린 쓰기 도구 둘**이다.

### 3.1 실패한 적이 없다. 기록이 틀렸다

```
모델이 도구 호출 결정
  → tool_started 이벤트                ← tool_call 행이 PENDING 으로 열린다
  → HITL 미들웨어가 interrupt           ← 승인 카드를 띄우고 스트림 종료
  → finally: _close_orphans()
       안 닫힌 tool_call 을 FAILED / STREAM_CLOSED 로 정리   ❌
  → 사용자가 승인 → 재개                ← 도구는 실제로 성공
       재개는 새 스트림이라 open_tool_calls 가 비어 있고,
       _end_tool_call() 이 짝을 못 찾아 조용히 반환           ❌ 성공이 안 남는다
```

**증거(프로덕션):** 도구는 FAILED 인데 실행은 DONE 이거나 PENDING 이다. 소요
6~8ms 로 실제로 돌지도 않았다.

```
jira_create_issues  8/20 10:26  FAILED / STREAM_CLOSED   run_status = DONE
jira_create_issues  8/20 07:37  FAILED / STREAM_CLOSED   run_status = PENDING
task_register       8/20 07:36  FAILED / STREAM_CLOSED   run_status = PENDING
```

### 3.2 이미 한 번 만난 함정이다

`tracing/__init__.py` 의 `_suspend_run()` 주석이 **똑같은 버그를 설명하고 있다.**
2026-08-19 에 고쳤는데 **`agent_run` 만 고치고 `tool_call` 은 빠뜨렸다.**

> "interrupt로 멈춘 실행은 `EVENT_RESULT`/`EVENT_ERROR` 없이 스트림이 그냥
> 끝나고, `finally` 의 `_close_orphans()` 가 이 run 을 `FAILED` 로 정리해
> 버린다 — 승인 대기 중일 뿐인 실행이 실패로 잘못 기록된다."

### 3.3 고칠 곳 둘

**① 작다 — 거짓 실패를 없앤다.** `_suspend_run()` 이 `open_run_ids` 에서 run 을
빼듯, 그 run 에 속한 `open_tool_calls` 항목도 빼서 `PENDING` 으로 남긴다.
이것만 해도 성공률 표가 거짓말을 멈춘다. 대신 승인 대기 행이 `PENDING` 으로
쌓여 「안 닫힌 호출」 칸에 잡히는데, **그건 사실이라 정직한 표시다.**

**② 크다 — 승인 후 실제 결과를 그 행에 적는다.** 재개 스트림이 그 run 의
`PENDING` 행을 미리 열어야 짝이 맞는다(`known_run_ids` 와 같은 방식으로
`known_tool_calls`). **여기가 지훈 판단이 필요한 자리다** — `tool_call` 에
langchain 의 `tool_call_id` 를 안 남겨서 `tool_ref` 로 짝지어야 하고,
**병렬 승인으로 같은 도구를 여러 건 부르면 어느 것인지 애매하다.**

`2026-08-21_05_병렬_side-effect_부분실패_보고.md` 와 맞닿아 있다. 그 문서는
**이벤트 층**(모델·화면에 `tool_call_id` 별로 전달)을 다루는데, 이건 **DB 적재
층**이라 아직 아무도 안 본 자리다. 참고로 `tool_call_idempotency` 는
`langchain_tool_call_id` 를 갖고 있어 ②의 실마리가 될 수 있다.

## 4. 요청 — Langfuse 키를 운영 `.env` 에 넣어 달라

**검증은 이미 끝나 있다.** `LangSmith_LangFuse/2026-08-19_01_작업계획.md` §7 이
「작업 5는 LangSmith·Langfuse 둘 다 실 키로 검증 완료」라고 적고 있고, 마스킹도
서버에 실제로 기록된 24건을 다시 조회해 `leaked: 0` 으로 확인했다.

**그런데 그 키가 운영에 안 들어가 있다.** 2026-08-21 확인 —

```
운영 서버 .env :  LANGFUSE_PUBLIC_KEY 비어있음 · LANGFUSE_SECRET_KEY 비어있음
```

키가 없으면 `get_langfuse_callback()` 이 `None` 을 돌려주고 콜백 목록에서 그냥
빠진다 — **에이전트 실행에는 아무 영향이 없고, 대신 트레이스가 하나도 안 쌓인다.**
지금 상태가 그거다.

- 검증에 썼던 키를 운영 서버 `.env` 의 `LANGFUSE_PUBLIC_KEY` ·
  `LANGFUSE_SECRET_KEY` 에 넣는다(`LANGFUSE_HOST` 는 리전이 다르면 함께).
- **`.env` 는 바꾸면 재시작이 아니라 재생성이다** — `up -d --force-recreate web`.
- LangSmith 는 계속 꺼 둔다(`LANGCHAIN_API_KEY` 를 안 채운다).

이게 채워지면 관측성 「상세 트레이스」 층이 생겨서, 도구 호출·조회 문서·토큰이
따로 화면을 만들지 않아도 보인다. 발표 시연에도 이쪽이 제일 잘 보인다.

## 5. 스킬 — 설계가 맞아떨어진다

지훈의 `Deep_Agents/2026-08-20_16_Skill_Middleware_설계.md` 와 어제 만든
설정 「스킬」 탭이 같은 그림이다 — progressive disclosure 그대로 사용 · 개인/팀 ·
조직 제외 · 팀은 팀장 승인.

**다만 화면은 개인만 만들었다.** 공유 범위가 정해지기 전에 화면이 먼저 주장하게
두지 않으려는 것이고, 팀 단위가 확정되면 「내 파일」 탭의 안쪽 탭
(`Inner = 'mine' | 'shared'`)을 그대로 옮기면 된다.

API 계약은 `frontend/src/api/skills.ts` 에 `/me/skills/` 넷(GET·POST·PATCH·
DELETE)으로 정의해 뒀다. **서버가 없어 지금은 404 이고 화면이 「준비 중」으로
그린다** — 엔드포인트가 붙는 순간 코드 변경 없이 산다. 칸은 셋뿐이다
(`name`·`description`·`body`) — `SkillsMiddleware` 가 frontmatter 의
`name`/`description` 만 읽고 본문은 고른 뒤 읽으므로, 그 밖의 값을 받아 두면
화면에만 있는 값이 된다.

> ⚠ 지훈 설계 §4.0 의 **「등록 실행도 HITL 확인 카드를 거친다」**는 §3 의 버그를
