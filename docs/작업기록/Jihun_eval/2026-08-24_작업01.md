- 작업일: 2026-08-24
- 작업 범위: 평가 실행 전 P0 문제 수정, 회귀 검증, Codex 작업 환경 준비
- 관련 설계 문서: `2026-08-24_Deep_Agent_평가도구_비교와_도입전략.md`

## 1. 작업 배경

Deep Agent 평가를 실행하기 전에 기존 `agent_run`·`tool_call` 추적 흐름을 점검했다.
그 결과 HITL(Human-in-the-loop) 승인 대기 구간에서 실제 실패가 아닌 도구 호출이
`FAILED / STREAM_CLOSED`로 기록될 수 있는 문제를 확인했다.

기존 추적기는 LangChain의 도구 호출 ID와 DB의 `tool_call_id` 관계를 현재 Python
스트림의 메모리에만 보관했다. 승인 요청으로 첫 스트림이 종료되면 이 관계가
사라졌고, 다음 resume 스트림에서는 원래 `PENDING` 행을 찾을 수 없었다. 또한
첫 스트림의 종료 정리 로직이 승인 대기 중인 루트·서브에이전트 실행과 도구 호출을
실패로 오인할 수 있었다.

이 상태로 평가를 시작하면 다음과 같은 왜곡이 발생한다.

- 승인 대기 호출이 실행 실패로 집계된다.
- 승인 후 성공한 호출이 기존 `PENDING` 행을 정상적으로 닫지 못한다.
- 사용자가 거절하여 실행되지 않은 호출이 성공 또는 실패로 잘못 집계될 수 있다.
- 도구 성공률과 평가 기준선의 신뢰도가 떨어진다.

## 2. 구현한 내용

### 2.1 DB 상관관계 키 추가

`tool_call` 테이블에 nullable `langchain_tool_call_id VARCHAR(64)` 컬럼을 추가했다.
동일한 실행에서 동일한 LangChain 호출이 중복 기록되지 않도록 다음 부분 UNIQUE
인덱스도 추가했다.

```sql
CREATE UNIQUE INDEX ux_tool_call_run_langchain_id
    ON tool_call (run_id, langchain_tool_call_id)
    WHERE langchain_tool_call_id IS NOT NULL;
```

관련 파일:

- `DB/schema.sql`
- `DB/migrations/2026-08-24_tool_call_hitl_lifecycle.sql`
- `backend/db/agent_platform.py`

레거시 Harness는 LangChain 호출 ID가 없으므로 저장소 인자를 선택값으로 유지했다.
따라서 기존 호출 경로는 예전처럼 새 행을 기록하고, Deep Agent 경로만 영속
상관관계 키를 사용한다.

### 2.2 승인 대기 상태 보존

HITL interrupt가 발생하면 현재 스트림에서 열린 루트 실행뿐 아니라 서브에이전트
실행도 함께 `PENDING`으로 유지하도록 변경했다. 열려 있던 도구 호출 역시 DB에서는
`PENDING` 상태를 유지하고, 현재 스트림의 orphan 정리 대상에서만 제거한다.

승인 카드에는 resume에 필요한 최소 추적 상태를 저장한다.

- 대기 중인 서브에이전트 정보
- namespace와 서브에이전트 실행의 대응 관계
- 대기 중인 직접 도구 호출 정보
- `action_index`와 `(run_id, tool_call_id)`의 대응 관계
- 중단 시점에 열려 있던 실행 ID 목록

관련 파일:

- `services/agent_runtime/events.py`
- `services/agent_runtime/executor.py`
- `services/agent_runtime/tracing/__init__.py`

### 2.3 resume 완료 처리

resume 스트림에는 첫 스트림의 메모리상 DB UUID 매핑이 없다. 따라서 도구 완료
이벤트가 오면 `(run_id, langchain_tool_call_id)`로 기존 `PENDING` 행을 찾아
`OK` 또는 `FAILED`로 갱신하도록 변경했다.

resume 시점에는 실제 도구 시작 시각을 알 수 없으므로 사람의 승인 대기 시간을
도구 실행 시간으로 잘못 포함하지 않도록 `duration_ms`는 `NULL`로 유지한다.

### 2.4 사용자 거절 상태 분리

사용자가 거절한 호출은 실제 handler가 실행되지 않는다. 이를 실행 실패와 구분하기
위해 `tool_call.status`에 `REJECTED` 상태를 사용하고, `error_code`에는
`HITL_REJECTED`를 기록하도록 변경했다.

resume 이후 미들웨어가 거절 결과를 정상 `ToolMessage`로 반환하더라도 저장소의
`status = 'PENDING'` 조건 때문에 `REJECTED` 행이 `OK`로 덮이지 않는다.

관련 파일:

- `apps/chat/api_views.py`
- `backend/db/agent_platform.py`

### 2.5 운영 지표 보정

도구 성공률의 분모를 실제 실행이 완료된 호출로 제한했다.

```text
도구 성공률 = OK / (OK + FAILED)
```

`PENDING`은 승인 대기 또는 실행 중인 호출이고, `REJECTED`는 사용자가 실행하지
않기로 결정한 호출이므로 성공률 분모에서 제외한다. 운영 화면에는 두 상태를 별도
열로 표시한다.

관련 파일:

- `backend/db/repositories.py`
- `frontend/src/api/opsUsage.ts`
- `frontend/src/pages/OpsUsagePage/OpsUsagePage.tsx`

## 3. 추가한 회귀 검증

다음 시나리오를 테스트에 반영했다.

- 도구 시작 시 LangChain 호출 ID가 DB 저장소로 전달되는지
- 승인 대기 시 열린 도구 호출이 실패로 닫히지 않는지
- 서브에이전트 실행과 그 내부 도구 호출도 함께 보류되는지
- resume 스트림이 원래 `PENDING` 행을 성공 또는 실패로 닫는지
- 동일한 병렬 호출이 원래 순서대로 승인 요청과 대응되는지
- resume 시 서브에이전트 namespace/run 매핑이 복원되는지
- 사용자 거절이 `REJECTED`로 기록되는지
- 기존 레거시 Harness 호출이 계속 동작하는지
- 운영 집계 응답에 `PENDING`과 `REJECTED`가 구분되는지

테스트 중 로컬에 없는 DB 호스트와 LangSmith 연결을 시도하는 로그가 출력됐지만,

인덱스 검사 대상은 `tool_call.ux_tool_call_run_langchain_id`이며 PostgreSQL 카탈로그의

### 5.2 실제 DB 마이그레이션 적용 — 로컬 DB 완료

적용 전에는 새 컬럼과 인덱스 2개가 누락된 것으로 확인됐고, 적용 후에는 확인 항목

첫 적용 시 SQL 문자열 안의 세미콜론을 문장 구분자로 오인하는 `_split_statements`
버그를 발견했다. 트랜잭션은 롤백됐고, 재현 테스트를 추가한 뒤 따옴표 밖의
세미콜론만 구분하도록 수정하여 재적용했다.

### 5.3 수동 HITL QA — 루트 호출 완료

DB 반영 후 실제 채팅에서 루트 에이전트의 승인·거절 흐름을 검증했다.

- 승인 전: 대상 `tool_call` 행이 `PENDING`으로 유지됨
- 승인 후: 같은 행이 `OK`로 종료되고 중복 행이 생기지 않음
- 거절 후: 같은 행이 `REJECTED / HITL_REJECTED`로 종료됨
- 승인·거절 카드가 각각 표시되고 종료 후 다시 대기 카드로 선택되지 않음
- 연속 클릭으로 동일 확인 요청이 중복 전송되지 않도록 프런트에 즉시 잠금을 추가함
- 도구 실제 완료 이벤트를 기준으로 서버가 완료 메시지를 확정하여, 모델의 승인 안내 문구가 최종 결과를 덮지 않음

남은 수동 검증은 서브에이전트 내부 승인 대기 → 승인 → 도구 성공 흐름이다.

최종 완료 기준은 다음과 같다.

- 승인 전: 대상 `tool_call.status = 'PENDING'`
- 승인 후 성공: 같은 행이 `OK`
- 거절 후: 같은 행이 `REJECTED`, `error_code = 'HITL_REJECTED'`
- 승인 대기 중인 호출이 `FAILED / STREAM_CLOSED`로 기록되지 않음
- 같은 `(run_id, langchain_tool_call_id)`에 중복 행이 생기지 않음
