## 1. 범위 — 장기 메모리만 새로 만든다, 단기는 이미 있다

deepagents 공식 문서(docs.langchain.com/oss/python/deepagents/memory) 기준으로
"단기"와 "장기"는 서로 다른 메커니즘이다. 단기(short-term)는 한 세션 안의 대화
이력이나 스크래치 공간을 말하고, deepagents는 이걸 LangGraph의 checkpointer로
스레드 단위로 관리한다. 장기(long-term)는 세션을 넘어 남는 것이고,
`memory=`(파일 경로)와 `backend=StoreBackend(...)`, `store=`(실제 저장소)를
조합해서 관리한다.

이 앱은 단기 메모리를 이미 다른 방식으로 갖고 있다. `chat_message` 테이블에
대화를 저장해 두고, `apps/chat/api_views.py`가 매 요청마다 이전 메시지를 다시
실어 `executor.run()`에 넘기는 구조다(LangGraph의 thread_id/checkpointer
방식이 아니라 이 저장소 자체 방식이다 — `tests/test_chat.py`의
`conversation_history_is_threaded_through` 참고). deepagents가 기본
제공하는 `StateBackend`(단일 실행 안의 파일 스크래치 공간)도 손대지 않아도 이미
붙어 있다. 그래서 이 작업은 **장기 메모리만** 새로 만들었다.

## 2. 현재 구조 — 개인 메모리 하나만 장기 저장(Store)으로 간다

원래는 팀·에이전트가 공유하는 메모리(`/memories/AGENTS.md`)와 개인 메모리
(`/memories/users/preferences.md`) 두 route를 같이 뒀다. 하지만 팀원 아무나
"우리 팀은 앞으로 이렇게 할 거야"라고 한마디만 하면 그 내용이 다른 팀원
전체의 대화에 동의 없이 끼어드는 문제가 있었고, 역할(leader)만 쓸 수 있게
제한하는 방안도 검토했지만 결국 **공유 메모리 자체를 없애고 개인 메모리만
쓰는 쪽으로 결정했다**(근거는 위 개정 이력 표의 2026-08-19_03 문서).

**남은 route는 하나뿐이다.**

- **개인 메모리**: `/memories/users/preferences.md`. namespace는 `(team_id,
  agent_id, account_id)` — 계정이 다르면 완전히 다른 저장 공간을 보고,
  같은 계정이라도 팀·에이전트가 다르면 역시 다른 공간을 본다.
- 이 경로 하나만 매 턴 시스템 프롬프트에 자동 주입된다 — "항상 알아야 할
  배경지식을 매번 다시 안 물어봐도 되게" 하려는 목적은 예전 `AGENTS.md`와
  같고, 그 자리를 이제 개인 선호가 대신한다. 매 턴 실리므로 짧게 유지해야
  한다는 제약도 그대로 있다.
- 그 외 경로(`/memories/users/`가 아닌 나머지 전부 — 예전 `AGENTS.md`나
  `/memories/projects/*.md`에 해당했을 경로 포함)는 전부 `CompositeBackend`의
  기본값인 `StateBackend`로 떨어진다. 경로별로 따로 분기하거나 새 예외를
  만들 필요가 없다 — route가 하나뿐이라 나머지는 자동으로 그리로 간다.

**`StateBackend`를 "휘발성"이라고 부르는 건 부정확하다.** 이 프로젝트는
checkpointer(`PostgresSaver`)가 `memory_provider`와 항상 같이 켜져 있어서,
`StateBackend`의 `files` 채널도 매 스텝 뒤 체크포인트로 Postgres에 실제
저장된다(`StateBackend` 자체 docstring: "State is automatically checkpointed
after each agent step"). 즉 **"대화가 끝나면 사라진다"는 표현은 틀렸다** —
같은 대화 스레드(`thread_id`=`session_id`)를 나중에 다시 이어가면 그 데이터가
다시 보인다. 정확한 표현은 "장기 메모리 Store에 영속화되지 않는다"다:
다른 스레드(다른 프로젝트 대화 포함)에서는 구조적으로 안 보이고, 장기
메모리처럼 매 턴 자동 주입되지도 않는다는 뜻이지, 그 스레드 자체에서
완전히 삭제된다는 뜻이 아니다.

Store는 `langgraph.store.postgres.PostgresStore`를 쓰는데, 이 앱이 이미
쓰는 같은 Postgres(`settings.RAW_DATABASE_URL`)에 그대로 붙는다. `store`,
`store_migrations` 같은 자기 테이블은 `store.setup()`이 알아서 만든다 —
`DB/schema.sql`이 관리하는 다른 테이블과 달리 langgraph 라이브러리가 스스로
관리한다.

메모리는 Root 그래프에만 붙는다. Child(서브에이전트)는 메모리 없이 그대로
둔다 — `create_child_graph`가 애초에 backend를 안 넘기고 deepagents 기본값인
새 `StateBackend()`만 받는다. 이 인스턴스는 Root가 쓰는 backend와 아예 다른
객체라, `/memories/...` 경로에 뭘 해도 그 Child 실행 안에서는 항상 빈 파일
취급이고, 다른 세션이나 계정의 메모리에 닿을 방법 자체가 없다.

## 3. deepagents `middleware=`는 대체가 아니라 병합이다

작업 도중 헷갈리기 쉬운 부분이 하나 있어서 정리해 둔다. `middleware=`에
넘긴 리스트가 deepagents 기본 스택을 통째로 대체한다고 생각하기 쉬운데, 그건
틀렸다. 공식 문서(docs.langchain.com/oss/python/deepagents/customization
"Middleware" 절)에 따르면 각 미들웨어 인스턴스는 `.name`을 기준으로 기존
스택과 **병합**된다 — 이름이 겹치면 그 자리를 교체하고, 안 겹치면
`PatchToolCallsMiddleware` 뒤에 끼워 넣는다.

그래서 `FilesystemMiddleware`, `SubAgentMiddleware`,
`SummarizationMiddleware`, `PatchToolCallsMiddleware`, prompt caching 같은
deepagents 기본 스택은 무엇을 넘기든 항상 그대로 살아 있다. 우리가 넘기는
`ModelCallLimitMiddleware`/`ToolCallLimitMiddleware` 같은 것들은 그 뒤에
추가되는 것뿐이다.

`TodoListMiddleware`가 자동으로 안 붙는 것도 같은 이유다 — deepagents 기본
스택 목록에 애초에 없는 항목이라 쓰려면 명시적으로 `middleware=[
TodoListMiddleware(...)]`로 넣어야 한다. `MemoryMiddleware`도 원리는 같다 —
공식 문서 표현으로 "Only when you pass `memory`"라, `middleware/factory.py`를
안 건드리고 `factory.py`의 `build()`가 `create_root_graph(memory=...)`로
따로 넘기기만 해도 자동으로 붙는다.

## 4. 무엇을 개인 메모리에 저장해도 되는가 — 라우팅 기준

`preferences.md`는 매 턴 시스템 프롬프트에 실려서 **이 사용자의 다른 모든
미래 대화**에도 매번 끼어든다. 그래서 "기억할 가치가 있는가"라는 느슨한
기준이 아니라 **"이 사용자에 대해 어느 프로젝트·어느 대화를 하든 항상
참인가"**를 명시적으로 묻게 했다(`_MEMORY_ROUTING_PROMPT`,
`memory/backend.py`).

**써도 되는 것** — 지속적인 개인 선호·습관·응대 방식. 예: "한국어로 답해줘",
"짧게 답하는 걸 선호한다", "읽기 전용 동작엔 확인창 필요 없다".

**쓰면 안 되는 것** — 당장은 기억할 가치가 있어 보여도, 이 사용자에 대해
항상 참인 게 아니라면 안 된다.

- 프로젝트 한정 사실·결정("이번 프로젝트는 Jira 대신 DB를 썼다", "지난번엔
  A 방식으로 처리했다") — 그 프로젝트 맥락에서만 참이라, 무관한 미래
  대화에마다 계속 끼어들게 된다.
- 1회성 작업 결과, 특정 세션에만 해당하는 내용.
- 모델이 대화 흐름을 보고 스스로 추론한 것 — 사용자가 실제로 말한 게
  확실하지 않으면 적지 않는다.
- 저장 의도 없이 지나가듯 한 말.

판단이 애매하면 적지 않는 쪽을 택한다 — 안 적어서 나중에 한 번 더
설명해야 하는 비용보다, 잘못 저장된 내용이 누군가 알아채고 지울 때까지
매번 끼어드는 비용이 더 크다.

## 5. 쓰기 내용 방어(write_guard) — 설계만 있고 아직 코드에 없다

라우팅 지침(4장)은 전부 모델에게 주는 프롬프트 지시일 뿐이다. 코드가
`write_file`/`edit_file` 인자를 실제로 검사하지 않으면, 모델이 비밀번호나
개인정보를 실수로 적어도 막을 방법이 없다. 메모리 쓰기는 `side_effect=True`
도구가 아니라서 HITL 대상도 아니다.

**틀 — "금칙어를 막는다"가 아니라 "저장 가능한 정보의 종류를 좁힌다".**
예를 들어 "이 사용자는 관리자 권한을 가지고 있다"는 문장이 사용자가 실제로
말한 사실인지, 모델이 대화 맥락을 잘못 추론해 지어낸 것인지는 문자열만
봐서는 코드가 구분할 수 없다. 그래서 "위험한 단어가 들어갔는가"가 아니라
"이게 애초에 저장해도 되는 종류의 정보인가"를 기준으로 삼는다 — 진위와
무관하게 카테고리 자체가 저장 대상이 아니면 막는다.

| 카테고리 | 예시 | 처리 | 강제 위치 |
|---|---|---|---|
| credential / secret | API 키, 비밀번호, 토큰 | 차단 | 코드(정규식) |
| 개인정보 | 주민등록번호, 카드번호, 전화번호 패턴 | 차단 | 코드(정규식) |
| 권한/보안 관련 사실 | "관리자 권한이 있다", "루트 계정을 쓴다" | 진위와 무관하게 보수적으로 차단 | 코드(키워드, 카테고리 전체 차단) |
| 모델이 추론한 사실 | 사용자가 직접 말하지 않은 걸 모델이 짐작 | 저장 금지 | 프롬프트만(4장) |
| 단순 대화 내용 | 저장 의도 없는 잡담 | 저장 금지 | 프롬프트만(4장) |
| 프로젝트 한정 사실/1회성 결과 | "이번엔 DB를 썼다" | 저장 금지 | 프롬프트만(4장) |
| 지속적 개인 선호·습관 | "한국어로 답해줘" | 저장 허용 | — |

앞 세 카테고리는 값의 **형태**(키 형식, 자릿수, 특정 단어 포함 여부)만
보면 되므로 코드로 신뢰성 있게 걸러낼 수 있다. 뒤 세 카테고리는 판단
대상이 **문장이 생겨난 맥락**(사용자가 직접 말했는지, 이 프로젝트에만
해당하는지)이라 정규식으로 답할 수 있는 질문이 아니다 — 이 부분은 코드가
아니라 4장의 프롬프트 지침에 맡긴다는 걸 인정하고 간다. 코드로 억지로
잡으려 하면 오탐만 늘고 실제로는 못 잡는다.

**구현 계획**(미착수): `memory/write_guard.py`에 `wrap_tool_call` 훅으로
새 미들웨어를 추가해, `/memories/users/`로 시작하는 `write_file`/`edit_file`
호출의 인자(`content`/`new_string`)를 handler 실행 전에 검사한다. 걸리면
실행하지 않고 거부 사유를 `ToolMessage(status="error")`로 돌려줘서, 모델이
사유를 보고 다시 시도할 기회는 남긴다. 카테고리·근거는
`2026-08-19_02_메모리_기본에이전트_분리_및_쓰기_방어_설계.md` §2 참고, 실제
`deepagents`/`langchain` 설치 소스로 검증한 클래스·함수 시그니처·정규식
목록·`factory.py` 배선 지점·테스트 계획까지 코드 반영 직전 수준으로 구체화한
설계는 `2026-08-19_04_write_guard_구현설계.md` 참고.

## 6. 구현

새 패키지 `services/agent_runtime/memory/`에 세 모듈이 있다.

- `store.py` — `get_memory_store()`. 프로세스 전역 `PostgresStore` 하나를
  최초 호출에서 열고 계속 재사용한다. 이 패키지의 "호출마다 새로 조립한다"는
  원칙(`bootstrap.py` docstring)의 유일한 예외다 — Postgres 연결 풀을 매
  요청마다 열고 닫을 수는 없어서다. 모듈 docstring에 이 예외를 명시해 뒀다.
- `backend.py` — `build_memory_backend(team_id, agent_id, account_id)`와
  `memory_paths()`. `/memories/users/` route 하나만 담은 `CompositeBackend`를
  만들고, 나머지는 `StateBackend`(2장 참고)로 둔다.
  `MemoryMiddleware.system_prompt`에 이어붙일 라우팅 안내
  (`_MEMORY_ROUTING_PROMPT`, 4장 기준)도 여기 있다.
- `provider.py` — `MemoryProvider`. `AgentRuntimeFactory`가 다른 협력자들
  (`ModelFactory`, `ToolLoader` 등)과 같은 방식으로 생성자 주입받는다.

연결 지점은 세 군데다. `compat/deepagents_v075.py`의 `create_root_graph()`에
`memory`/`backend`/`store` 파라미터를 추가했는데, 넷 다 기본값이 없거나 빈
값이면 deepagents 기본 동작 그대로다(하위 호환). `factory.py`의
`AgentRuntimeFactory.__init__`에는 `memory_provider: MemoryProvider | None =
None`을 추가해서, `None`이면(기존 테스트 등) 예전과 완전히 동일하게 동작하고
`build()`가 Root 분기에서만 관련 인자를 채운다. `bootstrap.py`의
`build_default_executor()`가 `MemoryProvider()`를 만들어 넘기는데, 이 생성
자체는 I/O가 없다 — 실제 연결은 `get_memory_store()`가 처음 쓰일 때 연다.

DB 쪽엔 새 테이블을 `DB/schema.sql`에 만들지 않았다 — `PostgresStore.setup()`
이 자기 테이블을 스스로, 멱등하게 관리한다. 대신 `requirements/base.txt`에
`langgraph-checkpoint-postgres`(`PostgresStore`가 들어있는 패키지)와
`psycopg[pool]` extra를 추가했다.

**`middleware/permissions.py`(프로젝트별 메모리 파일 접근 제어)는 이제 죽은
코드다.** 공유 메모리가 있던 시절, 같은 팀·에이전트의 다른 프로젝트 대화가
서로의 프로젝트 메모리 파일에 접근하지 못하게 막던 장치였는데, 그 경로
(`/memories/projects/*.md`) 자체가 이제 장기 Store에 안 가고 `StateBackend`로
떨어져서 격리할 대상 자체가 없어졌다. `factory.py`에서 이 배선만 끊었고
(`permissions=...` 호출 제거), 함수·테스트 코드 자체는 재사용 대비 남겨
뒀다.

<details>
<summary>참고 — 지나간 버그: <code>{project_id}</code> 이스케이프 누락(2026-08-15, 이미 해결)</summary>

옛 `_MEMORY_ROUTING_PROMPT`(공유+개인 2-route 시절)에 프로젝트별 메모리 경로
예시로 `/memories/projects/{project_id}.md`를 이스케이프 없이 적었다가,
`MemoryMiddleware._format_agent_memory()`가 문자열 전체를
`str.format(agent_memory=...)`로 처리하는 과정에서 `KeyError: 'project_id'`로
죽는 버그가 있었다. `{{project_id}}`로 고쳤고, 이 회귀를 잡는 테스트
(`test_survives_actual_format_agent_memory_call`, `tests/test_memory_backend.py`)
를 추가했다. 지금 `_MEMORY_ROUTING_PROMPT`는 이 경로 예시 자체가 없어졌지만,
비슷한 실수를 다시 하지 않도록 그 테스트는 계속 남겨 뒀다.

## 7. 검증

로컬 Postgres와 `requirements/base.txt` 전체를 설치한 환경에서 실제 Django
테스트 스위트로 확인했다.

- 계정이 다르면 개인 namespace가 다른지, 같은 계정이라도 팀이 다르면
  namespace가 다른지(`tests/test_memory_backend.py`) — 전부 통과.
- `_MEMORY_ROUTING_PROMPT`가 실제 `MemoryMiddleware`의 포맷팅을 통과하는지,
  공유 메모리 관련 문구(`AGENTS.md`, `/memories/projects/`, `SHARED`,
  `## 정책`)가 완전히 빠졌는지, 저장된 메모리 vs 도구 조회 결과·사용자의
  현재 요청 사이 충돌 판단 기준이 실제 포맷 결과에 남아 있는지 — 전부 통과.
- 개인 전용 구조로 바뀐 뒤 관련 테스트 109개(`test_memory_backend`,
  `test_memory_provider`, `test_factory`, `test_middleware_permissions`,
  `test_deepagents_compat`)를 다시 돌려 회귀가 없는지 확인 — 전부 통과.
  전체 스위트(870개) 기준 실패 25건·에러 6건은 이번 변경과 무관한 기존
  실패다(`test_accounts`·`test_document_download`·`test_harness`·
  `test_hr_tenant`·`test_projects`의 503 관련, `test_document_pipeline`
  import 에러).

**아직 확인 못 한 것**: 실제 대화에서 "이거 기억해줘" 같은 요청을 했을 때
`PostgresStore`에 실제로 행이 쓰이는지, 그리고 같은 팀·같은 에이전트로 새
세션을 열었을 때 그 내용을 실제로 반영해서 답하는지는 여전히 라이브로
확인하지 못했다. 이건 실제 모델 호출이 필요한 항목이라 구조적 테스트로는
대신할 수 없다.
