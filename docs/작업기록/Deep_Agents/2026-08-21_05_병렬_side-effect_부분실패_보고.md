# 2026-08-21_05 — 병렬 side-effect 부분 실패: 되돌리기 대신 정확한 보고

## 1. 이 문서의 결론

`2026-08-20_02_에이전트_병렬실행_설계.md` §7("fail-late + 부분 결과
허용")은 여러 side-effect 호출을 병렬로 승인했다가 일부만 성공하는
경우에 "이미 성공한 걸 어떻게 할지"를 정하지 않고 있었다.

1. **자동 되돌리기(rollback/보정)는 하지 않는다.** 사용자가 자유롭게
   연결하는 MCP 도구는 되돌리는 방법(취소 API 존재 여부, 되돌리기가
   의미 있는지)을 우리가 알 방법이 없고, 이메일 발송처럼 원천적으로
   되돌릴 수 없는 동작도 있다. 이 프로젝트가 지금까지 유지해 온 전제
   ("도구별 추가 메타데이터를 요구하지 않는다", `2026-08-20_01` §4)와도
   맞지 않는다.
2. **대신 "무엇이 실제로 일어났는지"를 절대 뭉개지 않고 항목별로
   정확히 전달하는 것**을 보장한다. 병렬로 승인된 side-effect 호출들의
   결과를 하나로 요약하지 않고, tool_call_id 단위로 성공/실패를 모델과
   사용자 화면 양쪽에 그대로 남긴다.
3. 이건 새로운 저장/추적 장치가 아니다 — 이미 있는 `tool_call_id` 기반
   추적(§9)과 idempotency 결과 기록(`2026-08-21_03`)을 "요약해서
   뭉개지 않는다"는 규칙으로 강제하는 것에 가깝다.

## 2. 왜 되돌리기를 포기하는가

지라 이슈 생성 2건 + 이메일 발송 1건을 한 카드로 승인했는데 이메일만
실패했다고 하자. "이미 만든 지라 이슈 2건을 자동으로 지울까"를 생각해
볼 수 있지만:

- 이메일은 발송하면 되돌릴 방법이 없다 — 애초에 "실패한 것" 자체는
  되돌릴 게 없는 경우도 많다.
- 지라 이슈를 자동으로 지우려면 "생성의 반대 동작(취소)"이 뭔지 알아야
  하는데, 이건 도구마다 다르고 사용자가 연결한 임의의 MCP 서버가 그런
  기능을 제공하는지조차 우리가 모른다.
- 설령 안다 해도, 취소 자체가 또 하나의 side-effect 호출이라 똑같이
  실패할 수 있고, 실패하면 또 무슨 상태인지 애매해진다 — 문제를
  풀지 않고 한 단계 미룰 뿐이다.

이 프로젝트는 이미 같은 이유로 "도구별 메타데이터를 요구하지 않는다"는
원칙을 여러 번 지켜왔다(`2026-08-20_01` §4, `2026-08-21_04` §2). 되돌리기
기능은 정확히 이 원칙과 충돌하는 요구라서, 일반적인 자동 되돌리기는
설계하지 않는다.

## 3. 대신 보장하는 것 — 결과를 뭉개지 않는다

### 3.1 모델에게 가는 결과

병렬로 승인된 side-effect 호출들이 끝나면, Root가 받는 결과는 하나로
요약된 문장이 아니라 **tool_call_id별로 분리된 결과 목록**이어야 한다.

```text
잘못된 예 (뭉개짐):
  "요청하신 작업 중 일부가 실패했습니다."

지켜야 할 예 (항목별):
  tool_call_id=abc123  jira_create_issues(title="로그인 버그")   → 성공
  tool_call_id=def456  jira_create_issues(title="결제 오류")     → 성공
  tool_call_id=ghi789  send_email(to="team@..")                 → 실패(timeout)
```

이건 이미 `2026-08-20_02` §9가 "모든 병렬 단위는 tool_call_id를 기준으로
연결한다"고 정해 둔 것과 같은 방향이다 — 지금까지는 Child 단위(task
위임)에 적용됐는데, 이 문서는 **같은 규칙을 한 카드로 병렬 승인된
side-effect tool_call 각각에도 적용**한다.

### 3.2 사용자 화면

승인 카드가 여러 항목을 담을 수 있게 되는 것(§8, `2026-08-21_02`가
앞당긴 Phase 2)과 짝을 맞춰, **실행 결과 화면도 항목별로 보여준다.**
"일부 실패"라는 뭉뚱그린 문구 하나로 끝내지 않는다.

```text
✅ 지라 이슈 "로그인 버그" 생성됨
✅ 지라 이슈 "결제 오류" 생성됨
❌ 이메일 발송 실패 — 자동 재시도 안 함
```

이렇게 하면 사용자가 "이미 실제로 일어난 일"을 정확히 알고 다음 행동을
정할 수 있다 — 특히 `2026-08-21_03`이 다룬 "실행 여부를 모른 채 재시도해
중복이 나는" 위험을 사용자 쪽에서도 줄여준다. 되돌리기는 못 해도,
"뭐가 됐는지 정확히 아는 것"까지는 확실히 보장할 수 있다.

## 4. `2026-08-20_02`에 반영할 내용

§7("실패 처리")에 다음을 추가한다 — 정책 자체(fail-late + 부분 결과
허용)는 바뀌지 않고, "부분 결과"가 무엇을 뜻하는지를 명확히 한다.

- 부분 결과는 tool_call_id별로 분리된 성공/실패 목록이어야 하며, 하나의
  요약 문장으로 대체할 수 없다.
- 이미 성공한 side-effect 호출은 자동으로 되돌리지 않는다 — 그 이유는
  이 문서 §2.
- 사용자 화면도 §3.2와 같이 항목별로 표시한다.

## 5. 이 설계가 풀지 않는 것

- 특정 도구(우리가 직접 만든 내장 도구 중 일부)에 한해 되돌리기를
  지원할지는 이 문서에서 결정하지 않는다 — 일반적인 해법이 아니라
  도구별 개별 판단이 필요해 범위 밖으로 둔다.
- 항목별 결과를 사용자가 보고 "그럼 이메일만 다시 보내줘"라고 요청하는
  흐름 자체는 이미 `2026-08-21_03`(재시도 안전성)이 다루는 영역과
  이어진다.

## 6. 여기까지 — A/B 카테고리 정리 마무리

`2026-08-20_01`/`2026-08-20_02` 검토에서 나온 A(문서-구현 충돌) 3건,
B(설계 자체 위험) 3건을 모두 다뤘다.

```text
A-1 Tool timeout 삭제           → 2026-08-21_01 (재설계)
A-2 MCP 승인 범위 확대           → 2026-08-21_02 (문서 반영 + Phase 순서 변경)
A-3 idempotency 절반만 해결      → 2026-08-21_03 (재시도 안전성 설계)
B-1 MCP lock의 DB 커넥션 문제    → 2026-08-21_04 (직렬화 폐기, 경고로 대체)
B-2 읽기 MCP도 줄 세우던 문제    → 2026-08-21_04에서 부수적으로 해결
B-3 병렬 부분 실패 뒷정리 없음   → 2026-08-21_05 (이 문서)
```
