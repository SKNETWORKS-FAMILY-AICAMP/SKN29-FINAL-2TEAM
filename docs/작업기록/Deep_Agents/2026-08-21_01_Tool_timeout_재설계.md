# 2026-08-21_01 — Tool timeout 재설계

## 1. 이 문서의 결론

`2026-08-19_10`(전역 300초 timeout)은 `17e8c62`에서 되돌려졌고, 그 상세 기록
문서는 저장소에 커밋된 적이 없다. 남은 근거는 커밋 메시지 한 줄뿐이다.

> Tool별 timeout 미들웨어 되돌림 — 사용자 재판단으로 일괄 300초 기본값이
> 안 맞다고 결론, tool_timeout.py 삭제 및 middleware/factory.py 배선 제거.

이번 재설계에서는 다음을 결정했다.

1. 되돌려진 건 "hard timeout이라는 아이디어"가 아니라 "모든 도구에 똑같이
   건 300초"다. 넘기면 모델에게 `ToolMessage(status="error")`로 알리는
   기존 동작 자체는 문제 삼은 적이 없다.
2. 내장(harness) 도구와 MCP 도구를 같은 틀로 묶지 않는다. 내장 도구는
   우리가 코드를 직접 쓰므로 필요하면 도구 작성자가 그 도구에만 맞는
   timeout을 직접 건다(`FilesystemMiddleware`의 `execute`가 이미 그렇게
   하고 있다, `max_execute_timeout` 기본 3600초). 이 재설계가 만드는
   공통 미들웨어의 적용 대상에서 내장 도구는 뺀다.
3. MCP 도구는 "이 도구가 정상적으로 몇 초 걸리는가"를 우리가 알 방법이
   없다는 걸 인정한다. 그 질문에 답하려던 게 지난 실패 원인이므로, 이번엔
   그 질문 자체를 피해간다.
4. 대신 우리가 확실히 아는 값 — gunicorn이 요청 하나를 600초 넘기면
   프로세스를 강제로 죽인다는 사실(`Dockerfile`) — 을 근거로 삼는다. MCP
   도구에 거는 값은 "이 정도가 정상"이라는 추측이 아니라 "이 시점부터는
   살아있어도 어차피 gunicorn이 죽이니, 그 전에 우리가 먼저 곱게 끊어서
   최소한 에러 메시지는 남긴다"는 순수 방어용 상한이다.
5. 도구별 예외(`tool_call_timeout_overrides`)는 이전 설계에 이미 있던
   틀을 그대로 살린다. 처음엔 빈 채로 시작하고, 특정 MCP 도구가 실제로
   문제로 확인되면(사용자 신고·관측 데이터) 그때 그 도구만 예외를 준다 —
   출시 전에 모든 MCP 도구를 미리 추측해서 분류하지 않는다.
6. 정확한 기본값 초 단위는 이 문서에서 확정하되, 실측 후 조정 가능한
   값으로 취급한다(아래 §4).
7. **(2026-08-21 추가)** `17e8c62`가 `tool_timeout.py`를 지우면서 이걸
   테스트하던 4개 파일을 안 지웠다 — 지금 이 브랜치는 이미 그 지점에서
   테스트가 깨져 있다. 착수 전 선행 조건으로 §8에 남긴다.

이 문서는 설계 판단만 기록한다. 코드에는 아직 반영하지 않았다.

## 2. 배경 — 왜 다시 설계가 필요한가

`2026-08-20_01_MCP_실행시간과_백그라운드_실행_검토.md` §4는 "모든 MCP
호출에 적용할 플랫폼 공통 방어" 1순위로 "실행 hard timeout"을 꼽았다. 그
문서를 검토하던 시점엔 `runtime_policy.py`에 `DEFAULT_TOOL_CALL_TIMEOUT_
SECONDS = 300`과 이를 강제하는 `ToolCallTimeoutMiddleware`가 실제로 있었다.

이후 `main`을 병합하며 들어온 `17e8c62`가 이 미들웨어와 관련 필드
(`tool_call_timeout_seconds`, `tool_call_timeout_overrides`,
`timeout_for_tool()`)를 전부 삭제했다. 병합 이후 코드베이스에는 tool 호출
timeout이 하나도 없다 — `2026-08-20_01` §4가 "이미 있다"고 전제한 방어선이
지금은 존재하지 않는다.

동시에 이 상태는 `2026-08-20_02_에이전트_병렬실행_설계.md` §5.2가 제안한
"같은 MCP 서버 호출을 advisory lock으로 직렬화"와 맞물리면 위험이 커진다.
timeout이 없으면 MCP 호출이 무한정 걸릴 수 있고, lock을 쥔 채 기다리는
전용 DB 커넥션도 그만큼 오래 열려 있게 된다. 이 문서가 정하는 상한은
그 최악의 경우에도 유한한 값을 보장하는 역할을 겸한다.

## 3. 내장 도구와 MCP 도구를 분리하는 이유

내장 도구는 이 저장소 안에 코드가 있고, 우리가 실제로 실행시간을 알거나
통제할 수 있다. `services/harness/registry.py`의 도구들이 여기 해당한다.
이미 `FilesystemMiddleware`의 `execute`처럼 필요한 도구는 자체 timeout을
갖고 있다 — 이는 도구 작성자가 그 도구의 실제 특성을 알고 정한 값이라
정확하다. 이런 도구에 플랫폼 공통 미들웨어가 또 다른 값을 얹으면 두 값이
어긋날 뿐 얻는 게 없다.

MCP 도구는 반대다. 사용자가 자유롭게 연결하는 임의의 외부 서버라
`tools/list` 응답만으로는 정상 실행시간을 알 수 없다
(`2026-08-20_01` §3). 여기서는 "적당한 값을 추측"하는 대신 "넘기면
확실히 문제인 값"을 쓴다.

```text
내장 도구  → 이 미들웨어의 대상 아님. 필요하면 도구 자신이 timeout을 가진다.
MCP 도구   → 이 미들웨어가 공통 상한을 건다. 값의 근거는 도구 특성이 아니라
             gunicorn worker timeout이다.
```

구분 기준은 `tool_ref`다. `services/agent_runtime/tools/adapters.py`가
MCP 도구를 `mcp:` 접두사로 만들므로(`adapt_mcp_tools()`), 미들웨어는
`tool_ref.startswith("mcp:")`인 호출에만 적용한다.

## 4. 값의 근거 — gunicorn worker timeout

`Dockerfile`은 이미 이 값을 정해 놓았다.

```text
CMD ["gunicorn", ..., "--timeout", "600", ...]
```

같은 파일의 주석은 이 값을 뺐을 때 실제로 겪은 장애를 기록하고 있다
(2026-08-18 QA) — timeout 없이 요청이 오래 걸리면 스트리밍 중인 워커가
그대로 SIGKILL되고, 브라우저에는 `ERR_HTTP2_PROTOCOL_ERROR`만 남고 원인은
어디에도 남지 않는다.

이 600초는 이미 이 프로젝트가 근거를 들어 정한 값이므로, 새로 숫자를
만들어내는 대신 이 값에서 역산한다. MCP 도구 하나의 상한은 600초보다
확실히 작아야 한다 — 모델 응답 조립, 스트리밍 오버헤드 등 tool 호출 외
시간도 같은 600초 예산 안에 있기 때문이다.

**기본값: 480초(8분), 여유 120초.** 이 값은 "MCP 도구가 보통 이 정도
걸린다"는 주장이 아니라 "이 미들웨어가 못 끊으면 gunicorn이 대신 끊는데,
그 방식이 훨씬 나쁘다"는 안전마진이다. 도구가 실제로 몇 초 걸리는지에
대한 실측 데이터가 아니라 gunicorn 설정에서 그대로 도출한 값이므로,
gunicorn `--timeout` 값이 바뀌면 이 값도 같이 검토해야 한다.

## 5. 도구별 예외

이전 설계의 `tool_call_timeout_overrides: dict[str, int]`를 그대로
되살린다. 기본은 빈 dict — 모든 MCP 도구가 §4의 기본값을 쓴다.

특정 MCP 도구가 실제로 이 기본값 때문에 정상 작업이 끊긴다는 게 확인되면
(사용자 신고, 또는 `2026-08-20_01` §4가 제안한 `(team_id, mcp_server_id,
tool_name)` 단위 관측 데이터), 그 도구의 `tool_ref`만 override에 추가한다.
480초보다 크게 잡더라도 600초(gunicorn 한도)는 넘지 않아야 한다 — 넘기면
이 미들웨어가 있으나 마나이므로, override 값 자체에도 상한 검증을 둔다.

```text
override 없음      → 기본값(480초) 적용
override 있음       → override 값 적용, 단 gunicorn timeout(600초) 미만으로 제한
```

미리 모든 MCP 도구를 "빠름/느림"으로 분류하지 않는다 — 실제로 문제가
확인된 것만, 확인된 뒤에 예외를 준다.

## 6. 넘겼을 때의 동작 — "실행 여부 불명"을 명시한다

이전 `ToolCallTimeoutMiddleware`의 기본 동작(그래프를 죽이지 않고 해당
tool_call만 `ToolMessage(status="error")`로 되돌려 모델이 스스로 다시
판단하게 한다)은 그대로 가져오되, `2026-08-21_03_외부_Write_Tool_재시도_
안전성.md`에서 다룬 이유로 메시지 내용을 바꾼다.

`concurrent.futures.ThreadPoolExecutor` + `future.result(timeout=...)`는
"기다리기를 포기"할 뿐 실행 중인 스레드를 강제로 죽이지 못한다 — timeout
후에도 handler는 백그라운드에서 계속 돌다가 나중에 끝난다. 즉 timeout이
났다는 건 "실패했다"가 아니라 "결과를 모른다"는 뜻이다.

**`tool.side_effect`로 분기하지 않는다(2026-08-21 정정)**: 이 미들웨어는
§3에서 이미 MCP 도구(`mcp:` 접두사)로만 적용 범위를 좁혔고, MCP 도구는
`tools/adapters.py`가 무조건 `side_effect=True`로 고정한다. 즉 이
미들웨어가 다루는 도구는 항상 side-effect라 분기할 대상 자체가 없다 —
메시지는 하나만 쓴다.

```text
timeout 초과 (MCP 도구, 항상 side_effect=True)
  → future.result(timeout=...)가 TimeoutError
  → ToolMessage(status="error", content="~초를 넘어 응답을 기다리지
    않고 중단했습니다. 실제로 실행됐는지 확인되지 않았습니다 — 자동으로
    다시 시도하지 말고, 필요하면 사용자에게 재시도 여부를 확인하세요.")
  → 그래프는 계속 진행, 모델이 (안내에 따라) 재시도·다른 방법·사용자 확인 중 택함
```

이건 프롬프트 수준 방어일 뿐 강제는 아니다 — 모델이 메시지를 무시하고
새 tool_call로 재시도해도 서버가 막지는 않는다. 실제 방어는 §7에서 밝힌
대로 이미 있는 HITL 승인 단계와 `2026-08-21_03`의 승인 카드 경고 표시가
맡는다.

진짜 취소 전파(스레드를 강제로 죽이는 것)는 여전히 이 미들웨어의 범위
밖이며, `2026-08-13_04` 7순위(Run 전체 wall-clock timeout + 취소 전파)로
남겨둔다.

## 7. 이 재설계가 풀지 않는 것

- MCP 서버별 직렬화(lock)가 이 timeout이 도는 동안 DB 커넥션을 쥐고
  있는 문제(`2026-08-20_02` §5.2) — 최악의 경우가 "무한"에서 "480~600초"로
  줄어들 뿐, 커넥션을 오래 쥐는 설계 자체는 별도로 다뤄야 한다.
- Run 전체 wall-clock timeout과 진짜 취소 전파 — §6에서 밝힌 대로 범위
  밖이다.
- 팀·계정별 timeout 차등 — 지금은 전 팀 공통 기본값 하나만 둔다.
