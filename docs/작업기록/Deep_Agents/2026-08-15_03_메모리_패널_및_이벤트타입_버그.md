# 2026-08-15_03 — Chat 오른쪽 장기 메모리 패널 + 이벤트 타입 불일치 버그

> `2026-08-15_02_장기메모리_설계.md`의 후속. 지훈 요청: "장기 메모리에 어떤
> 순서로 저장되는지 채팅 페이지 오른쪽에서 보고 싶다(read_file/write_file 등)".

## 1. 구현 도중 발견한 버그 — 도구 호출 진행 표시가 전부 죽어 있었다

`frontend/src/api/chat.ts`의 `ChatEvent` 타입은 **레거시 Harness**
(`services/harness/runner.py`)가 내는 이름(`tool_call_started`/
`tool_call_finished`)만 알고 있었다. 그런데 `apps/chat/api_views.py`의
`_run_deep_agent()`가 "2026-08-14부터 전부 이 경로"라고 스스로 문서화한 대로
**새 엔진**(`services/agent_runtime/events.py`)이 이미 유일한 실행 경로였고,
새 엔진이 실제로 내보내는 타입은 `tool_started`/`tool_completed`/
`subagent_started`/`subagent_completed`/`tool_progress`로 **다른 문자열**이다
(`_relay()`가 이벤트를 그대로 `json.dumps`해 NDJSON으로 흘려보낸다 — 가로채
바꾸는 코드가 없다, `apps/chat/api_views.py:449` 확인).

`frontend/src/pages/ChatPage/liveChat.ts`의 `reduce()`는 모르는 `type`을
`default: return state`로 조용히 버린다. 즉 **2026-08-14 이후 모든 Chat
대화에서 도구 진행 표시(`toolName`, 실패 사유 등)가 화면에 전혀 반영되지
않고 있었다** — 에러도 안 나고 그냥 아무 일도 안 일어나는 채로.

이번 작업으로 `chat.ts`에 새 타입 5종을 추가하고 `liveChat.ts`에
`tool_started`/`tool_completed` 케이스를 추가해 고쳤다. 레거시 두 케이스는
**지우지 않았다** — 2026-08-14 이전에 저장된 `chat_message.content.events`가
옛 타입 그대로 DB에 남아 있어(재생 시 `toTurns()`가 그 값을 다시 `reduce`에
먹인다), 지우면 과거 대화 복원이 깨진다.

## 2. 오른쪽 패널

`liveChat.ts`:
- `ToolCallEntry`(seq/toolCallId/toolRef/status/arguments), `LiveChat.toolCalls`
  추가. `tool_started`(부모 직접 호출, `subagent_alias == null`인 것만)가
  새 항목을 `RUNNING`으로 밀어 넣고, `tool_completed`가 `tool_call_id`로
  찾아 상태만 바꾼다. **서브 에이전트 내부 호출은 안 담는다** — Child에는
  메모리가 없어서(`_02_` 문서 §4) 이 패널과 무관하다.
- `memoryFilePath(args)` — 도구 인자에서 `/memories/`로 시작하는 경로를
  찾는다. `file_path`/`path` 키를 먼저 보고, 없으면 값 전체를 훑는다.

`ChatPage.tsx`:
- `memoryOps` — 이 대화의 모든 턴에서 `memoryFilePath`가 잡히는 도구 호출만
  시간순으로 편 배열(`useMemo`).
- `.main` 옆에 고정 폭(260px) `<aside>` 패널을 추가해 순서 번호·동작
  (읽기/쓰기/수정)·경로·상태(진행 중/완료/실패)를 나열한다. 접었다 펴는
  기능은 안 만들었다 — 지금 목적이 "팀에 실제로 이렇게 돈다"를 보여주는
  데모라 숨기면 목적에 안 맞는다.

## 3. 확인 못 한 것 — `file_path` 인자 키 이름

deepagents 내장 파일 도구(`read_file`/`write_file`/`edit_file`)의 실제 인자
키 이름을 **패키지가 이 샌드박스에 없어서 소스로 확인 못 했다.** Claude
자신의 Read/Write/Edit 도구와 같은 관례(`file_path`)일 것이라는 추정으로
짰고, `memoryFilePath()`가 `path`도 같이 보고 그래도 없으면 인자 값 전체를
훑는 방어적 순서를 쓴 것도 이 불확실성 때문이다.

**남은 확인(지훈 환경에서, `_02_` 문서 §5와 이어서)**: 기본 챗 에이전트에
"내가 짧은 답을 좋아한다고 기억해줘" 같은 요청을 보낸 뒤, 오른쪽 패널에
`쓰기 AGENTS.md`가 실제로 뜨는지 확인. 안 뜨면 `memoryFilePath()`의 키
추정이 틀린 것 — 그때 실제 인자 이름으로 `liveChat.ts`의 `memoryFilePath`를
고치면 된다(패널·이벤트 배선 자체는 안 건드려도 됨).
