## Phase 8 — 외부 Write Tool Idempotency (설계 완료, 미착수)

**문제**: HITL 승인 후 재개하거나, checkpoint 저장 실패 후 같은 super-step이
재실행되면 `jira_create_issues`·`task_register` 같은 외부 side_effect 도구가
같은 요청으로 두 번 실행될 수 있다. LangGraph의 재시도·재개 메커니즘은 이걸
막아주지 않는다(`agent-harness-deepagents-code-benchmark.md` §4 — "Tool의
외부 side effect는 checkpoint와 같은 트랜잭션이 아니다").

**설계**

1. `tool_call` 테이블에 `langchain_tool_call_id VARCHAR(64)` 컬럼을 추가한다
   (nullable — 이 값이 없는 기존/레거시 경로는 그대로 둔다). `(session_id,
   langchain_tool_call_id)` 조합에 partial unique index를 건다
   (`WHERE langchain_tool_call_id IS NOT NULL`).
2. 이 값은 모델이 낸 `AIMessage.tool_calls[i]["id"]`다 — checkpoint에
   그대로 저장돼 재개해도 같은 값으로 남는다(모델이 재시도 때 새로
   짓는 값이 아니다). 지금 `factory.py`의 `_to_langchain_tool()._run()`은
   이 값을 안 받는다 — `langchain_core.tools.InjectedToolCallId`로 도구
   스키마에 주입해서(모델에게는 안 보이고 `ToolNode`가 자동으로 채워 줌,
   실제 설치된 `langchain-core`에 이 클래스가 있는 것까지 확인함) 받아와야
   한다.
3. `_run()`이 `tool.handler(**resolved)`를 부르기 **전에**, `side_effect=True`
   인 도구에 한해 `(session_id, langchain_tool_call_id)`로 이미 `SUCCESS`
   상태인 `tool_call` 행이 있는지 먼저 조회한다. 있으면 handler를 다시
   부르지 않고 그 행에 저장해 둔 결과 텍스트를 그대로 반환한다. 없으면
   평소대로 실행하고 결과를 그 값과 함께 기록한다.
4. 읽기 전용 도구는 대상에서 뺀다 — 다시 불러도 부작용이 없어서 이 보호가
   필요 없다.

`tool_call` 테이블은 이미 "선기록 패턴"(실행 전 PENDING insert)을 쓰고 있어서
3번의 조회·기록 자리를 새로 만들 필요 없이 기존 흐름에 조건 하나만 끼워 넣으면
된다.

**2026-08-19 재판단**: 이 문제는 "재개(resume)가 실제로 일어날 때" 현실화된다.
그런데 지금 새 엔진에는 재개 자체가 안 되는 상태다 — 아래 "다음 순서" 0번
참고. 재개 API가 생기기 전까지는 이 Idempotency 문제가 실제로 발생할 경로
자체가 없다(재개가 안 되니 같은 tool_call이 두 번 실행될 일도 없다). 그래서
착수 순서를 0번 바로 다음으로 옮겼다 — 설계 자체는 그대로 유효하다.

### 5순위 — Tool별 timeout + 병렬 쓰기 락(advisory lock) — 완료(2026-08-19)

**착수 이유(한 줄)**: harness 내장 도구·MCP 도구엔 timeout 개념이 아예 없고,
`StoreBackend`(`/memories/users/`)의 읽기-수정-쓰기는 락도 CAS도 없어 동시
`edit_file` 두 개가 겹치면 먼저 쓴 내용이 조용히 사라진다 — 1순위
`write_guard`와 같은 자리(`wrap_tool_call`)를 셋이 같이 건드려서 함께
설계·구현했다.

**완료.** `ToolCallTimeoutMiddleware`(신규, `middleware/tool_timeout.py`)를

`memory/write_lock.py`)로 `/memories/users/` 쓰기를 Postgres advisory
lock(`pg_advisory_xact_lock`, `backend/db/codes.py`가 이미 쓰는 패턴 재사용)
으로 직렬화했다. 최종 middleware 순서(바깥→안): timeout → write_guard →
write_lock → 실제 handler. 실제 Postgres로 "같은 락 키는 직렬화, 다른
namespace는 안 기다림" 두 시나리오까지 확인했다. 자세한 기록은
`2026-08-19_10_Tool_timeout_병렬쓰기락_구현완료.md`.
