# 작업자 B — Deep Agent 실행 코어 진행 상황 및 다음 계획 (2026-08-13 갱신)

이전 버전(Walking Skeleton 계획 원문)은 §1~§8에 결정 과정과 근거를 길게 남겼습니다. 그 결정들은
전부 이미 코드로 반영·검증됐으므로 여기서는 **아직 유효한 설계 제약만 표로 압축**하고, 나머지는
실측한 현재 상태와 다음 계획으로 채웁니다. 과거 버전 전문은 git 이력에 남아 있습니다.

---

## 1. 한 줄 요약

**저장(에이전트 생성)은 새 스키마로 완전히 동작합니다. 실행(대화·테스트 실행)은 아직 전부 옛
harness 엔진으로만 동작하고, 새 실행 엔진(`AgentExecutor`)은 프로덕션 코드 어디에서도 호출되지
않습니다(테스트에서만 사용).** 즉 사용자가 이름/설명/모델/툴/서브에이전트를 입력해 에이전트를
"만들기"는 지금도 됩니다 — 하지만 그렇게 만든 에이전트를 "실행"할 방법은 아직 없습니다.
근거와 다음 계획은 아래 §3, §5.

## 4. 사용자 질문에 대한 답

### 4-1. "지금 코드로 사용자가 에이전트를 생성할 수 있어?"

**생성(저장)은 됩니다.** `POST/PUT /api/agents/versions/`(`apps/agents/api_views.py`의
`AgentVersionListCreateAPIView`/`AgentVersionDetailAPIView`)가 이름·설명·system_prompt·model·
tool_refs·subagents를 받아 검증(`_check_tool_refs`, `_model_rejection`, `validate_subagents`,
자기 참조 409 등)하고 `AgentVersionCrudRepository.publish()`로 저장합니다. 여기까지는 A의
Repository와 B의 검증 코드가 실제로 맞물려 동작합니다.

**실행은 안 됩니다.** 실행 진입점이 두 곳뿐인데 둘 다 옛 `services.harness.run_agent`만 부릅니다.

```
apps/agents/api_views.py::_builder_test_events()  → run_agent(dry_run=True)   (빌더 "테스트 실행")
apps/chat/api_views.py 138줄, 250줄               → run_agent()               (실제 채팅)
```

`AgentExecutor`/`build_default_executor`(새 엔진)를 실제로 부르는 `apps/*` 코드는 **0곳**입니다
(테스트에서만 사용 — `grep -rl AgentExecutor . | grep -v tests` 실측 결과). 옛 `run_agent`는
`draft`가 `instruction`/`tools`(레거시 registry ref) 같은 옛 스키마를 기대하고 subagents 개념
자체가 없어서, 새 스키마로 만든 에이전트(특히 서브에이전트가 있는 경우)를 넘겨도 제대로 실행되지
않습니다. **결론: "만들기"와 "실행하기"가 서로 다른 두 시스템에 떨어져 있고, 아직 다리가 없습니다.**
이게 §5의 6-12가 남아있는 이유이자, 지금 가장 우선순위 높은 다음 작업입니다.

### 4-2. 하드코딩이나 연결 끊긴 부분

`services/agent_runtime` 안에서 진짜 하드코딩(숫자·문자열을 코드 곳곳에 직접 박아 넣은 것)은
찾지 못했습니다 — 정책 숫자(호출 상한 6/12/20/40 등)는 전부 `runtime_policy.py` 한 곳에 이름을
붙여 모아뒀고(§2), 나머지는 실측 근거가 있는 상수(§17.1 injected_context 표 등)입니다. 대신
아래 두 가지는 "연결이 끊긴 부분"으로 분류하는 게 맞습니다.

1. **실행 경로 단절** — 위 4-1. 이게 가장 큰 단절입니다.
2. **`apps/agents/api_views.py`의 스테일 주석** — 새 스키마 엔드포인트 위 주석이 "services/agent_runtime/이
   미완성 — loader.py가 NotImplementedError"라고 적혀 있는데, 이건 더 이상 사실이 아닙니다
   (`loader.py`/`adapters.py` 완료). 기능엔 영향 없지만 다음에 이 파일 만지는 사람이 오해할
   수 있어 정리 대상입니다.
3. **`runtime_policy.enable_todo`가 죽은 설정값** — 값은 있는데 `middleware/factory.py`가 읽지
   않습니다. Todo를 켜고 싶어도 지금은 이 플래그를 True로 바꿔도 아무 일도 안 일어납니다.

### 4-3. Todo·Memory는 어떻게 되어 있어? Memory는 미들웨어로 부르는 거야?

**둘 다 지금은 완전히 비활성입니다** — `planning/todo.py`, `memory/short_term.py`,
`memory/long_term.py`는 docstring 한 줄짜리 빈 파일입니다.

Todo는 맞습니다, **미들웨어로 붙이는 게 맞는 방향**입니다 — `langchain.agents.middleware`에
이미 `TodoListMiddleware`가 있고(설치된 패키지에서 직접 확인), `middleware/factory.py.build()`가
`ModelCallLimitMiddleware`/`ToolCallLimitMiddleware`를 붙이는 것과 같은 자리에 조건부로 추가하면
됩니다 — `runtime_policy.enable_todo`가 이미 그 스위치로 설계돼 있으니 배선만 하면 됩니다(비용
낮음).

Memory는 조금 다릅니다. deepagents가 제공하는 `MemoryMiddleware`는 파일시스템의 `AGENTS.md`를
읽어 시스템 프롬프트에 얹는 용도(정적 프로젝트 컨텍스트)라, `memory/long_term.py`의 docstring이
말하는 "사용자·팀·Agent 단위 장기 Memory"(DB 기반)와는 목적이 다릅니다 — **가져다 쓸 수 있는
기존 미들웨어가 없고, DB 스키마부터 새로 설계해야 합니다**(비용 높음, 별도 계획 필요).
`memory/short_term.py`(세션 내 대화 상태)는 오히려 `checkpoint/checkpointer.py`(지금 항상
`None` 반환) 쪽 문제에 더 가깝습니다 — LangGraph는 실행 중 상태를 자체적으로 들고 있지만, 그걸
요청 사이에 영속화하려면 실제 Checkpointer 구현이 필요합니다.

### 4-4. 어떤 툴을 부를지는 어디서 결정해?

두 층위가 있습니다.

- **어떤 툴을 "쓸 수 있게" 할지** — 사용자가 에이전트 생성 시 `tool_refs`로 직접 고릅니다
  (`POST /api/agents/versions/`의 `tool_refs` 필드, `_check_tool_refs`가 존재 여부만 검증).
  그 값이 `factory.py`의 `self.tool_loader.load(tool_refs=definition.tool_refs, ...)`로 실제
  Tool 목록이 되고, 이어서 `RuntimeCapabilityPolicy.filter_tools_for_role()`이 계정 역할(member는
  side_effect 도구 제외)로 한 번 더 거릅니다.
- **그 중 실제로 "어떤 걸 지금 부를지"** — 이건 이 코드베이스가 결정하지 않습니다. `factory.py`가
  허용된 Tool들을 LangChain `StructuredTool`로 바꿔 모델에 bind해두면, **모델 자신이** system_prompt와
  각 Tool의 description을 보고 판단합니다. 라우터 코드는 없습니다 — LLM의 tool-calling 자체가
  그 역할입니다.

## 5. 다음 계획 (우선순위 순)

**P0 — ✅ 승인됨(2026-08-15, 지훈/A 확인).** `context.py`의 `role` 필드 추가 — 계약 변경이었지만
승인 완료. 더 이상 대기 항목 아님.

**P1 — 실행 경로 연결 (6-12, 가장 시급).** 순서:
1. 새 스키마용 실행 엔드포인트를 먼저 Builder Test 쪽에 연결 — 기존 `AgentBuilderTestRunAPIView`를
   고치기보다, `agent_versions` draft를 받아 `build_default_executor().run(...)`으로 스트리밍하는
   새 엔드포인트를 옆에 추가하는 쪽을 권장합니다(옛 엔드포인트의 옛 스키마 계약을 안 건드림).
2. 같은 입력으로 옛 harness 결과와 비교해 안정성 확인.
3. Chat API 연결은 feature flag 뒤에서 — **어떤 `agent_id`가 새 스키마에 속하는지 구분하는 로직이
   아직 없습니다**(옛 `agent` 테이블과 새 `agent_versions`가 나란히 존재). 이 판별 방법을 먼저
   정해야 합니다 — 이건 코드보다 설계 결정이라 사용자 확인이 필요합니다.

**P2 — 정리.** `apps/agents/api_views.py`의 스테일 주석(§4-2의 2번) 갱신. 작은 작업이라 P1과
같이 진행 가능.

**P3 — Todo 배선.** `middleware/factory.py.build()`에서 `runtime_policy.enable_todo`가 True일 때
`TodoListMiddleware()`를 추가하도록 배선. 비용 낮음 — MVP에 필요한지만 확인되면 바로 가능.

**P4 — Memory 설계.** DB 기반 장단기 메모리는 스키마 설계부터 필요한 별도 작업입니다. 지금 MVP
스코프에 포함할지부터 결정 필요 — **사용자 확인 필요** (포함한다면 별도 계획 문서로 분리 권장).

**P5 — MCP 도구 연결.** `tools/loader.py`가 `mcp:` 접두사를 명시적으로 거부하는 상태 그대로 둘지,
언제 연결할지는 아직 범위 미정.
