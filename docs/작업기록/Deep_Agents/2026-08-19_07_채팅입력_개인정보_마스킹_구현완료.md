# 채팅 입력 개인정보 마스킹 — 구현 완료 (2026-08-19)

## 이 문서가 왜 필요한가 — 범위 정정 기록

`2026-08-13_04_실행코어_세부계획.md`의 "2순위"는 원래 `2026-08-19_01_실행_안정성_설계.md`
§5(계정 탈퇴 시 `/memories/users/preferences.md`와 checkpoint를 자동 삭제하는
것)를 가리키는 항목으로 적혀 있었다. 이 문서를 쓰기 시작한 시점에는 그
설계대로 "계정 탈퇴 트리거 → 개인정보/checkpoint 삭제" 흐름을 구현하려 했다.

착수 직전 확인 질문(계정 상태 `WITHDRAWN`을 실제로 세팅하는 코드 경로가
있는지)에 대해, 지금 이 프로젝트에는 계정 탈퇴 기능 자체가 없다는 답을
받았다. 그리고 "2순위"로 의도했던 것은 애초에 그 얘기가 아니었다 —
**사용자가 채팅에 직접 입력한 개인정보가 LLM에게 전달되면 안 된다**는
뜻이었다. 계정 탈퇴 시 저장된 데이터를 지우는 것과, 애초에 민감한 값이
모델 호출에 실리지 않게 막는 것은 서로 다른 문제라 구현 방향을 전면
전환했다. 이 문서는 전환 이후 실제로 구현한 내용만 다룬다 — 계정
탈퇴/삭제 자동화 쪽은 착수하지 않았다(필요해지면 별도 항목으로 다시
판단한다).

## 확정된 범위

두 가지를 사용자에게 직접 확인받았다.

- **대상 채널**: 사용자가 채팅에 직접 입력한 내용만. 도구 실행 결과나
  장기 메모리 회상(recall) 내용은 이번 범위에서 제외한다 — 그 두 채널은
  사용자가 직접 타이핑한 게 아니라 시스템이 만들어 낸 값이라 같은 문제가
  아니다.
- **처리 방식**: 매칭된 값만 가리고 나머지 문장은 그대로 모델에게
  전달한다(추천 옵션). 메시지 전체를 거부하지 않는다 — 사용자가 "제
  전화번호는 010-1234-5678인데 이걸로 리마인더 좀 설정해줘" 라고 쓰면
  전화번호만 가려지고 나머지 요청은 그대로 처리된다.

## 설계 — 저장은 원문, 마스킹은 모델 입력에만

`ChatMessageRepository.append()`는 계속 원문 그대로 저장한다. 화면은
사용자 자신이 실제로 입력한 문장을 그대로 보여줘야 한다 — 이건 "모델에게
전달되면 안 된다"는 요구지 "사용자 자신도 못 보게 하라"는 요구가 아니다.

`ChatMessageAPIView.post()`에서 `model_input = mask_sensitive(text)`를
한 번 계산해, 모델로 가는 **세 경로 전부**에 쓴다.

1. 이번 턴 실행 — `_run_deep_agent(..., user_input=model_input, ...)`
2. 제목 생성 — `_relay(..., question=model_input)` → `_name_session()` →
   `suggest_title(question=question, ...)`
3. 이력 재전송 — `_history()`가 저장된(원문) 과거 발화를 매 턴 다시
   모델에게 태우므로, 여기서도 독립적으로 `mask_sensitive()`를 적용한다.
   이걸 빼먹으면 이번 턴만 막고 다음 턴부터 저장된 원문이 그대로
   새어나간다.

## 패턴 공유 — `sensitive_text.py`

1순위(`write_guard.py`)가 이미 credential/개인정보/권한 서술 패턴을 갖고
있었다. 이번 기능도 "무엇을 민감정보로 보는가"를 판단해야 하는데, 두
곳에 따로 정의하면 한쪽만 고쳐지고 다른 쪽은 안 고쳐지는 위험이 생긴다.
그래서 패턴 정의를 `services/agent_runtime/sensitive_text.py`(신규)로
뽑아내고, `write_guard.py`는 이 모듈을 import해서 쓰도록 리팩터했다.

- `CREDENTIAL_PATTERNS` / `PII_PATTERNS` / `AUTHORITY_KEYWORDS` /
  `CATEGORY_LABELS` — write_guard가 쓰던 것을 그대로 옮김(값 변경 없음).
- `match_category(text)` — 첫 매치 카테고리 하나만 필요한 곳(write_guard의
  저장 차단 여부 판단)에 씀. 기존 `write_guard.py`의 로컬 함수를 그대로
  옮긴 것.
- `mask_sensitive(text)` — 이번에 새로 추가. `match_category()`와 달리
  **첫 매치에서 멈추지 않는다** — 한 문장에 여러 종류의 민감정보가
  섞여 있으면 전부 가린다. 매칭된 원문은 반환값 어디에도 남기지 않는다.

`write_guard.py` 리팩터는 동작을 바꾸지 않는다 — 기존 21개 단위
테스트(`test_memory_write_guard.py`)가 그대로 통과하는 것으로 확인했다.

## 한계 — 정직하게 기록

- **범위 밖 채널**: 도구 실행 결과, 장기 메모리 회상 내용은 이번 범위에
  포함하지 않는다(사용자가 명시적으로 제외한 범위). 그 두 채널에도 같은
  문제가 있을 수 있지만, 사용자가 직접 입력한 것과는 발생 경로가 달라
  별도 판단이 필요하다.
- **형태 기반 판단의 한계**: `write_guard.py`와 동일하게, 전화번호
  패턴은 정당한 요청("이 번호로 리마인더 보내줘")도 걸릴 수 있고,
  권한/보안 키워드는 문맥 없이 문자열 포함 여부만 본다. 값을 여러 조각
  으로 쪼개 입력하면(예: 한 턴에 앞자리, 다음 턴에 뒷자리) 개별 조각은
  못 잡는다 — 완전한 방어가 아니라 "명백한 경우를 잡는 안전망"이다.
- **실시간 검증**: `_run_deep_agent()`가 `executor.run(user_input=...)`을
  부르는 지점까지 마스킹된 값이 그대로 전달되는 것은 단위 테스트(HTTP
  요청 → `mock_executor.run.call_args.kwargs["user_input"]` 확인)로
  검증했다. `executor.run()` 내부(실제 `DeepAgentStreamAdapter`가
  모델에게 보내는 메시지 구성)는 순수하게 문자열을 그대로 옮기는
  경로이고 이 기능이 손대는 지점이 아니므로, 1순위(write_guard)에서
  했던 것과 같은 실제 Postgres 대상 종단 검증은 이번에는 별도로 하지
  않았다 — 값이 컨텍스트 안에서 변형 없이 전달되는지만 보면 되는
  범위라 판단했다.
