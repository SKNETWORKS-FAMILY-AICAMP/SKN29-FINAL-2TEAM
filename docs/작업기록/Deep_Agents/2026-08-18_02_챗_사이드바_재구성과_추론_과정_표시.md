## 4. 개인(DRAFT) 에이전트를 Chat에서 테스트할 방법이 없던 문제

**발견**: `AgentVersionEditPage`엔 테스트 실행 기능이 아예 없고(v1 범위

없었다. 이 상태로는 "팀에 아직 안 보여주고 혼자 테스트"가 불가능했다.

**결정**(지훈 확인): Chat이 본인 DRAFT도 고를 수 있게 한다.

**구현**:
- `ChatPage.tsx`: `usable = rows.filter(row => row.status === 'ACTIVE' ||
  row.status === 'DRAFT')` — 서버가 이미 DRAFT를 소유자에게만 내려주므로
  (`list_for_team()`), 여기 뜨는 DRAFT는 항상 내 것이다. 드롭다운 옵션에
  "(개인·미공유)" 표시를 붙임.
- **막혀 있던 진짜 이유**: `backend/db/agent_platform.py`의
  `_resolve_session_agent()`가 "ACTIVE만 대화 가능"을 강제하고 있어서,
  프론트만 풀면 세션 생성이 409로 막혔을 것 — DRAFT면서 `owner_account_id`가
  요청자 본인일 때도 허용하도록 조건을 넓혔다(`account_id` 파라미터 추가).
- **부수적으로 막은 구멍**: 이전에는 `agent_id`만 알면 team_id만 같아도 남의
  DRAFT로 세션을 열 수 있었다(UI엔 안 보였지만 API 직접 호출로는 가능했음).
  이제 소유자만 가능 — `PermissionDenied` 403.

curl로 검증: 소유자 본인은 DRAFT로 세션 생성 성공(201), 소유자 아닌 팀장은
409로 차단.

## 9. 복잡한 대화의 추론 과정 표시

**질문**: "지금은 어떤 식이야?" → 조사해서 답변: **지금은 안 보여준다.**
`services/agent_runtime/events.py`가 `message.text`(텍스트 블록만 남기는
langchain-core 프로퍼티)를 쓰기 때문에 추론 모델(`gpt-5.6-luna`, OpenAI
Responses API)의 reasoning 콘텐츠 블록이 조용히 버려지고 있었다 — 실측
코멘트까지 있던 기존 동작.

**구현**:
- `services/agent_runtime/events.py`: `_extract_reasoning()` 추가, 새
  이벤트 타입 `EVENT_REASONING`("reasoning") 신설. 부모·자식(서브 에이전트)
  네임스페이스 양쪽의 "model" 노드 분기에서 reasoning이 있으면 다른
  이벤트(결과/도구 시작)보다 먼저 낸다.
- **처음에 키 이름을 잘못 짚었다**: `langchain_core`의
  `ReasoningContentBlock.reasoning`(평문 문자열)일 거라 가정하고 짰는데,
  기존 테스트(`test_openai_responses_reasoning_content_blocks_yield_
  plain_text_not_raw_list`)의 실측 픽스처가 `{"type": "reasoning", ...,
  "summary": []}` 모양이라는 걸 이미 갖고 있었다 — 설치된 `langchain_openai`
  소스로 확인해보니 실제 텍스트는 `block["summary"][i]["text"]`(리스트)에
  있다. 기존 테스트 덕분에 이 실수를 커밋 전에 잡았다.
- **더 근본적인 버그**: `models/factory.py`의 `ModelFactory._create_openai()`
  가 `reasoning_effort=` 단독으로 넘기고 있었는데, langchain-openai
  소스(`_construct_responses_api_payload`)를 보면 이건
  `reasoning={"effort": ...}`로만 변환돼 API에 가고 `summary`가 없다 —
  그러면 OpenAI가 reasoning 블록을 **항상 빈 summary로만** 돌려줘서, 이벤트
  코드를 다 만들어도 실제로는 보여줄 텍스트가 없었을 것이다. `reasoning=
  {"effort": ..., "summary": "auto"}`로 직접 요청하도록 고쳤다.
- 프론트: `api/chat.ts`에 `reasoning` 이벤트 타입 추가, `liveChat.ts`가
  턴별로 `reasoningSteps: string[]`에 모으고(서브 에이전트 자신의 추론은
  최상위 표시에 안 담음 — `toolCalls`와 같은 규칙), 새 `ReasoningTrace`
  카드(`ChatCards.tsx`, 접혀서 시작 — "생각 과정 N단계")가 그린다.
- 테스트: `tests/test_events.py`에 5개 케이스 추가(채워진 summary, 여러
  조각 join, 도구 호출 앞의 reasoning, 자식 네임스페이스 reasoning, 빈
  summary는 이벤트 없음), `tests/test_model_factory.py` 기존 테스트 하나를
  새 `reasoning=` 방식에 맞게 수정. 전체 768개 테스트 통과.

**실제 API로 최종 검증**: 기본 챗(gpt-5.6-luna)에 "1~20 소수 세기, 계산
과정 보여줘" 질문 → 결과 전에 실제 영어 reasoning 텍스트("Evaluating prime
numbers in Korean... I identify 8 primes...")가 `reasoning` 이벤트로
정확히 왔다.

## 10. 기본 챗 도구 토글이 이미 열린 대화에는 안 먹히던 문제

**보고**: "팀원 조회 도구 선택해서 물어봤는데 '연결 파일이나 도구에서 확인
불가'라고 나온다." 재현해보니 **새 대화**에서는 도구가 정상 호출됐다 — 즉
문제는 **이미 열려 있던 대화**에서 도구를 켠 경우였다.

**원인**: `chat_session.agent_version_id`는 세션을 만들 때 한 번 고정되고,
`ChatMessageAPIView`는 메시지를 보낼 때마다 그 고정값을 그대로 쓴다
(`agents.current_version_id`를 다시 안 봄) — 버전 불변성 원칙상 다른
에이전트에는 맞는 동작이지만, "+"로 그 자리에서 새 버전을 발행하는 기본
챗에는 안 맞는다. 도구를 켠 시점 이후 대화만 새 버전을 보고, 이미 열려
있던 대화는 계속 옛(도구 없는) 버전으로 돈다.

**후속 질문**: "이미 존재하는 세션에도 바로 반영되게 할 수 없나?" → 가능.

**구현**: `AgentVersionRepository.resolve_live_version_id(agent_id)`
추가 — **기본 챗일 때만** `agents.current_version_id`(지금 발행된 최신
버전)를 돌려준다. `ChatMessageAPIView.post()`가 세션을 읽은 직후, 그
세션의 에이전트가 기본 챗이면 이 값으로 `agent_version_id`를 갈아 끼우고
실행한다 — 다른 에이전트는 이 조회 자체가 `None`을 돌려주므로(=
`is_default_chat`이 아니므로) 원래대로 세션 고정값을 그대로 쓴다.

**검증(curl)**: ① 도구 끄고 새 대화 열기(버전 X에 고정) → ② **그 세션은
안 건드리고** 도구 다시 켜기(버전 X+1 발행) → ③ **①에서 이미 열려 있던**
그 세션에서 메시지 전송 → 이벤트에 `agent_version_id: X+1`(최신)로 찍히고
도구가 정상 호출됨.

## 11. 세션별 도구 override — 에이전트 원본을 안 건드리고 대화별로 켜고 끄기

지훈이 "이게 가능하면, 임의의 에이전트를 고른 상태에서도 원본 에이전트는
안 건드리고 이 대화에서만 도구를 껐다 켰다 할 수 있는 거 아니냐"고 물어서
가능하다고 답한 뒤 바로 구현했다 — §7·§10의 방식(에이전트 자체를 새
버전으로 발행)을 **완전히 대체**한다. 여러 사람이 같은 에이전트(특히 기본
챗)로 동시에 대화할 때, 한 사람이 도구를 껐다고 남의 대화까지 바뀌는 건
지훈이 원한 그림이 아니었다.

**스키마**: `DB/migrations/2026-08-18_chat_session_tool_override.sql`이
`chat_session.tool_refs_override TEXT[]`(nullable, DEFAULT 없음)를 추가.
`NULL` = 이 대화는 커스터마이즈 안 함(에이전트 원래 `tool_refs`를 그대로
씀), 빈 배열(`{}`) = "이 대화에서 도구를 전부 껐다"는 실제 선택 — 이
구분을 유지하려고 DEFAULT를 일부러 안 둔다. `DB/schema.sql`의
`chat_session` 정의도 같이 갱신.

**백엔드**:
- `ChatSessionRepository.set_tool_refs_override()` 신설 — 세션 소유자만
  바꿀 수 있다(`_require_session`은 팀 검사라 남의 대화도 열리지만, 도구
  구성은 실제로 쓰는 사람의 선택이어야 한다).
- `AgentExecutor.run()`에 `tool_refs_override: Sequence[str] | None` 인자
  추가 — 로드된 정의를 `dataclasses.replace()`로 복사해 `tool_refs`만 갈아
  끼운다(원본 `AgentDefinition`은 불변이라 안전하게 사본만 바뀐다). 서브
  에이전트의 도구는 영향 없음 — 이 대화가 직접 부르는 루트만 대상.
- `ChatSessionToolsAPIView`(`PUT /chat/sessions/<id>/tools/`) 신설.
- `ChatMessageAPIView.post()`가 `session.get("tool_refs_override")`를
  읽어 `executor.run()`에 그대로 넘긴다 — §10의 `resolve_live_version_id`
  (기본 챗 버전 재조회)는 그대로 남겨 뒀다(다른 이유로도 여전히 쓸모
  있음), 이번 값은 그 위에 얹힌다.

**프론트**: `ChatPage.tsx`의 "+" 버튼이 이제 **세션이 열려 있으면 어떤
에이전트든** 뜬다(전엔 기본 챗 전용). 켜고 끄기는 더 이상
`publishAgentVersion()`을 안 부르고 `setSessionToolRefs()`(새 API)를
부른다. `sessionToolOverride`(이 세션의 커스터마이즈, null 가능)와
`agentOwnToolRefs`(picker 초기값 계산용, 커스터마이즈 전엔 이걸 보여줌)
두 상태로 나눠 관리 — `openSession()`이 세션을 열 때
`detail.tool_refs_override`를 읽고, `startNew()`는 새 대화니 `null`로
리셋한다.

**검증(curl, 실제 실행까지)**: 도구 `document_search` 하나만 가진 테스트
에이전트로 세션 C를 열고, override 없이 "쓸 수 있는 도구 나열해줘" →
`functions.document_search` 확인. 같은 세션에 `tool_refs=["people_list"]`
override 저장 → **같은 세션, 같은 `agent_version_id`**로 다시 물어보니
`functions.people_list`로 바뀜(에이전트 자체 버전은 그대로 `AV037`).
별개로 만든 세션 B는 override를 안 건드렸으니 계속 `tool_refs_override:
null` — 격리 확인. 에이전트 원본 `tool_refs`는 시종일관 `["document_search"]`
로 안 바뀜. `tests/test_executor.py`에 `ToolRefsOverrideTests` 3개
추가(override 없음/교체/빈 배열로 전부 끄기) — 전체 771개 테스트 통과.
