# 2026-08-18_05 — 장기 메모리 충돌 판단 기준 설계·코드 반영

> `2026-08-15_02_장기메모리_설계.md`(AGENTS.md 공유 메모리, 계정 전용
> `/memories/users/` route)의 후속. 이번 작업은 저장 구조가 아니라 **"팀 규칙·
> 프로젝트 맥락·개인 선호·현재 사용자 지시가 서로 충돌할 때 뭘 우선하는가"**를
> 다룬다.

## 1. 배경

기존 메모리 구조는 "공유(AGENTS.md) vs 개인(users/preferences.md)"만 구분했고,
이 둘과 프로젝트 맥락(`projects/*.md`), 현재 도구 조회 결과, 현재 사용자 지시가
충돌할 때 뭘 우선해야 하는지 정의가 전혀 없었다. `MemoryMiddleware`의 기본
프롬프트("메모리보다 사용자를 신뢰하라")만으로는 "PM 승인 없이 등록해줘"처럼
정책과 충돌하는 요청까지 사용자가 이겨야 하는지가 불명확했다.

## 2. 검토했다가 기각한 대안

- **`MemoryMiddleware(policy=...)` 주입**: 실제 설치된 `deepagents==0.7.5`의
  `MemoryMiddleware.__init__` 시그니처를 직접 읽어 확인 —
  `backend`/`sources`/`add_cache_control`/`system_prompt` 넷뿐, `policy`
  파라미터가 없다. 넣으려면 deepagents 자체를 fork/패치해야 해 기각.
- **메모리 레코드에 scope/priority 메타데이터**: `StoreBackend`가 저장하는
  `FileData` 구조(`content`/`encoding`/`created_at`/`modified_at`)에 그런
  필드가 없다. `_format_agent_memory()`도 파일 전체를 통짜 텍스트로 이어붙이지
  문장 단위로 파싱·스코어링하지 않는다 — "구조화된 메모리 레코드"라는, 지금
  파일 기반 구조에 없는 전제가 필요해 기각.
- **`policy.md` 별도 파일/Store route 분리**: 처음엔 이 방향으로 설계했다가
  철회했다. 파일을 나눠도 충돌 발생 자체를 막지는 못하고(같은 이득을 `AGENTS.md`
  안 `## 정책` 섹션 컨벤션으로도 얻을 수 있음), 둘 다 매 턴 자동 주입할
  계획이라 토큰 비용도 똑같았다. 분리가 정당화되는 유일한 경우("모델이 정책을
  `edit_file`로 직접 못 고치게 코드로 막아야 한다")는 아직 요구되지 않아서
  지금은 `AGENTS.md` 하나 + 내부 섹션 컨벤션으로 정리했다.

새 DB나 priority 필드, 별도 Policy Engine은 만들지 않는다 — 이 판단은 전부 LLM이
프롬프트를 읽고 내리는 것이지, 코드가 검사·강제하지 않는다.

## 3. 채택한 설계 — 충돌 유형별 판단 기준

선형 순위표(`1 > 2 > 3 > ...`)로 정의하지 않는다. 충돌은 성격이 다른 두 축에서
일어난다.

**허용 여부(정책) 축** — 정책은 "무엇을 해도 되는가"만 정한다.
- 정책 vs 사용자의 현재 요청 → 정책. 사용자에게 그 사실을 알린다.
- 정책 vs 그 외 저장된 메모리(팀 일반/프로젝트/개인) → 정책

**사실 확인 축** — 도구 조회 결과는 "지금 무엇이 사실인가"만 정한다. 정책과는
비교 대상이 아니다.
- 저장된 메모리(어느 카테고리든) vs 현재 도구 조회 결과 → 현재 도구 조회 결과

**정책이 아닌 저장된 정보끼리의 충돌** — 적용 범위·최신성·현재 상황과의 일치
여부를 함께 고려한다. 프로젝트에 한정된 구체적인 정보는 일반적인 팀 정보보다
우선할 수 있고, 현재 확인된 사실과 충돌하는 과거 메모리는 쓰지 않는다("팀 >
프로젝트 > 개인" 같은 단순 스코프 순서는 쓰지 않는다 — 구체성이 스코프보다
중요할 수 있어서다).

**정책과 무관한 사안에서 사용자의 현재 요청 vs 저장된 메모리** → 사용자의 현재
요청.

이 판단 기준의 실행 단계 백스톱은 HITL 하나뿐이다. `factory.py`의
`interrupt_on`이 `side_effect=True`로 태깅된 모든 도구(`task_register`/
`task_update`/`jira_create_issues`/MCP 도구 등)에 하드코딩 없이 자동으로 사람
승인을 건다 — 이건 정책 위반을 탐지하는 장치가 아니라, 모델의 판단과 무관하게
부작용 도구 실행 앞에 항상 걸리는 무조건적 게이트다. 도구 실행이 아닌 응답
내용(어투, 언급 여부 등)에는 이 게이트가 적용되지 않고 프롬프트 문구에만
의존한다.

## 5. 검증

### 5-1. 단위 테스트 — 실행 완료, 전부 통과

로컬 Postgres(스키마는 `DB/schema.sql` 그대로 적용, pgvector 미설치로
`VECTOR(768)` 컬럼 테이블 하나만 실패 — 이번 작업과 무관)와 `requirements/base.txt`
전체를 설치한 환경에서 실제로 돌렸다.

```
python manage.py test tests.test_memory_backend -v 2
```
→ 16개 전부 통과(신규 2개 포함).

```
python manage.py test tests.test_factory tests.test_deepagents_compat \
  tests.test_runtime_policy tests.test_middleware_factory \
  tests.test_memory_backend tests.test_memory_provider -v 1
```
→ 131개 전부 통과, 회귀 없음.

1차 실행에서 `test_conflict_priority_guidance_reaches_final_system_message`가
실패했었는데, 원인은 프롬프트 문구가 아니라 테스트 코드 버그였다 —
`_MEMORY_ROUTING_PROMPT` 원문이 가독성 때문에 "현재 도구 조회" / "결과는 현재
상태를..." 사이에서 줄바꿈되는데, `assertIn`에 넣은 기대 문자열은 그 사이에
공백이 있는 한 줄짜리로 썼다. 줄바꿈을 피하는 문자열로 고쳐서 통과시켰다.

### 5-2. HITL 구조 검증 — 실행 완료, 통과

`_hitl_structural_check.py`(신규, 저장소 루트) — 정책 문구를 무시하고 항상
`task_register`를 호출하도록 고정한 가짜 모델로, "모델이 어떤 판단을 내리든
side_effect 도구 실행 자체는 코드가 막아주는가"를 확인했다. 실제 Postgres
checkpointer로 승인 대기 상태까지 만든 뒤 approve/reject 각각 재개:

- 두 케이스 모두 승인 전 handler 호출 0회(먼저 실행되지 않음).
- approve 재개 후 정확히 1회 호출, reject 재개 후 끝까지 0회 호출.

이걸로 "side-effect 도구 호출 시 HITL이 실제로 실행을 막는지"와, 정책·사실이
얽힌 시나리오 중 "모델이 도구를 호출하려 시도해도 HITL이 막는지" 부분까지
구조적으로 확인했다.

### 5-3. 라이브 모델 판단 검증 — 못 함, API 키 필요

아래는 가짜 모델로는 의미가 없다 — "모델이 프롬프트를 읽고 실제로 어떻게
판단하는가" 자체를 확인하는 항목이라 진짜 모델 호출이 필요하다. 실제
`OPENAI_API_KEY`가 있어야 실행할 수 있어서 이번엔 못 했다.

- [ ] 개인 선호 vs 팀 정책 — 모델이 정책을 따르는지
- [ ] 프로젝트 맥락 vs 개인 선호 — 더 구체적인 프로젝트 정보를 우선하는지
- [ ] 과거 메모리 vs 현재 도구 조회 결과 — 최신 조회 결과를 신뢰하는지
- [ ] 정책·사실이 동시에 얽힌 상황에서, 모델이 실제로 정책을 따르겠다고
      답하는지(5-2에서 확인한 건 "따르든 안 따르든 실행은 막힌다"는 것뿐,
      "실제로 따르겠다고 답하는지"는 별개로 확인 필요)

실제 API 키로 이 네 가지를 마저 돌리고 싶으면, 키를 알려주거나 직접
`agent_user_query_tool_check.py` 같은 스크립트로 돌려서 결과를 공유해 달라.
