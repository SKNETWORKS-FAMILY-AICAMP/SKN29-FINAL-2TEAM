# 2026-08-20_02 — 에이전트 병렬 실행 설계

## 1. 결론

이 프로젝트에는 별도 병렬 오케스트레이터를 새로 만들기보다, Deep Agents가 이미
제공하는 복수 `task` tool-call 병렬 실행을 유지하고 그 바깥에 플랫폼 안전장치를
추가한다.

핵심 원칙은 다음과 같다.

1. 어떤 작업을 같이 위임할지는 Root LLM이 판단한다.
2. 실제로 몇 개까지 동시에 실행할지는 서버 정책이 제한한다.
3. 조회 작업은 제한된 병렬 실행을 허용한다.
4. 쓰기 작업은 승인 여부와 쓰기 대상에 따라 다르게 보호한다 — 내장
   도구·개인 메모리는 직렬화하고, MCP는 직렬화 대신 동시 실행 경고를
   승인 카드에 띄운다(2026-08-21 재검토, `2026-08-21_04` 참고).
5. 한 Child의 실패 때문에 이미 성공한 다른 Child 결과를 버리지 않는다.
6. 병렬 실행 단위는 반드시 `tool_call_id`로 추적한다.
7. LLM의 병렬 호출은 제안이지 권한이 아니다. 서버의 권한·HITL·timeout·동시성
   제한을 우회할 수 없다.
8. `AsyncSubAgentMiddleware`는 이 설계의 전제가 아니다.

이 문서는 설계 초안이며 코드와 DB에는 아직 반영하지 않았다. 구체적인 기본 동시
실행 수치는 부하 테스트 전에 확정하지 않는다.

## 2. 현재 이미 되는 것

Root 모델이 한 AIMessage에 여러 `task` 호출을 만들면 LangGraph `ToolNode._func()`가
`get_executor_for_config(config)`의 executor에 모든 tool call을 넘겨 동시에 실행한다.

```text
Root LLM
  → task(researcher, "문서 조사")
  → task(people_analyst, "인력 조회")

ToolNode
  ├─ researcher 실행
  └─ people_analyst 실행

둘 다 완료
  → Root LLM이 결과 종합
```

현재 이벤트 계층도 한 AIMessage의 모든 `tool_calls`를 순회하고,
`subagent_started`/`subagent_completed`를 `tool_call_id`로 연결한다. 따라서
병렬 실행 기능 자체를 새로 구현할 필요는 없다.

## 3. 현재 부족한 것

현재는 병렬 실행을 허용하지만 플랫폼 차원의 동시성 정책이 없다.

### 3.1 동시 실행 수가 명시적으로 제한되지 않는다

한 Root가 Child를 여러 개 부르고, 각 Child가 다시 여러 Tool을 부르면 실제 외부
호출 수가 빠르게 늘어난다.

```text
Root가 Child 4개 동시 실행
  └─ Child마다 Tool 4개 동시 실행
      → 한 Root 요청에서 최대 16개 외부 호출 가능
```

여러 사용자가 동시에 요청하면 이 수가 다시 곱해진다. 기존
`ToolCallLimitMiddleware`는 한 실행에서 호출할 수 있는 **총 횟수**를 제한할 뿐,
한 순간에 실행되는 **동시 개수**를 제한하지 않는다.

### 3.2 MCP는 전부 잠재적 쓰기로 취급된다

MCP `tools/list`에는 read/write를 신뢰성 있게 구분하는 필드가 없다. 현재
`tools/adapters.py`도 이 이유로 모든 MCP 도구에 `side_effect=True`를 고정한다.
따라서 MCP 호출은 승인 허용 역할(`write_tool_allowed_roles`, 2026-08-20부터
leader+member)과 HITL 승인을 거친다. 승인자는 요청자 본인이 될 수 있다
(`is_tool_allowed_for_role()` — `2026-08-21_02_MCP_승인_범위_변경_반영.md`
참고).

승인 후 복수 MCP ToolMessage가 같은 super-step에 풀리면 ToolNode는 이 호출들도
동시에 실행할 수 있다. 알 수 없는 서버의 쓰기 안전성과 동시 처리 능력을 보장할 수
없으므로 그대로 두면 안 된다.

### 3.3 병렬 HITL의 호출별 결정이 없다

Deep Agents/LangChain의 HITL은 여러 `action_requests`와 같은 길이의 `decisions`
목록을 지원한다. 그러나 현재 Chat API는 한 카드의 모든 호출에 같은 승인 또는 거절을
적용한다. 첫 호출의 목록 항목만 부분 선택할 수 있고, 호출별 승인·거절은 할 수 없다.

### 3.4 Child 내부 진행 이벤트 귀속에 휴리스틱이 남아 있다

부모의 `subagent_started`/`subagent_completed`는 `tool_call_id`로 정확히 연결된다.
하지만 동시에 열린 Child namespace의 세부 reasoning/tool progress를 어느 Child에
붙일지는 일부 순서 휴리스틱을 사용한다. 같은 alias를 병렬로 여러 번 호출하거나 완료
순서가 뒤집히면 UI 세부 진행 표시가 잘못 붙을 수 있다.

### 3.5 실패 정책이 제품 규칙으로 명시되지 않았다

병렬 Child 중 하나가 실패했을 때 다음 중 어떤 동작인지 명확해야 한다.

- 전체 즉시 중단
- 다른 Child 완료까지 기다린 후 부분 결과 사용
- 실패한 Child만 재시도

## 4. 병렬화 결정: LLM과 서버의 책임을 분리한다

### 4.1 Root LLM의 책임

Root LLM은 작업 의미를 이해하므로 다음을 판단한다.

- 서로 독립적인 작업인지
- 한 작업의 결과가 다른 작업의 입력인지
- 어떤 Child에 위임할지
- Child에게 어떤 입력과 반환 형식을 요구할지

```text
문서 조사와 인력 조회
→ 서로 독립적이므로 한 응답의 복수 task 호출

문서 조사 결과로 보고서 작성
→ 조사 완료 후 writer 호출
```

사용자가 에이전트와 MCP를 자유롭게 추가하는 플랫폼이므로, 서버가 모든 도메인의
의존성을 미리 코딩하는 것은 불가능하다. 초기 설계에서는 별도 DAG JSON이나 Planner
모델을 강제하지 않는다.

### 4.2 서버의 책임

서버는 작업 의미 대신 안전 경계를 판단한다.

- 동시에 실행 가능한 최대 호출 수
- 요청자와 팀의 권한
- side effect 및 HITL
- timeout
- 동일 자원에 대한 쓰기 충돌
- 팀 전체 자원 상한

Root LLM이 10개의 `task`를 한 번에 내더라도 서버 정책이 3개만 허용하면 3개씩
실행되어야 한다. 호출을 버리는 것이 아니라 대기시킨다.

## 5. 제안하는 3단계 동시성 제한

### 5.1 1단계 — 한 ToolNode super-step의 동시 실행 제한

LangGraph 실행 config의 `max_concurrency`를 사용한다. `stream_adapter.py`가
`runtime.stream(..., config=...)`에 이 값을 넣는 위치다. 같은 AIMessage에 복수
tool call이 있어도 executor가 설정된 수 이상을 동시에 실행하지 않고 나머지를
대기시킨다.

```text
LLM이 task 5개 호출
max_concurrency = N
  → 최대 N개 실행
  → 완료된 자리에 다음 호출 실행
```

이 값은 코드 곳곳에 숫자로 박지 않고 `RuntimeCapabilityPolicy`에 둔다. 정확한 기본값은
실측 전에 확정하지 않는다.

이 제한은 가장 먼저 적용할 최소 안전장치다. 다만 중첩된 각 Child 그래프에도 같은
설정이 전파되므로, 이것만으로 팀 전체 동시 호출 수를 완전히 제한한다고 보지는 않는다.

### 5.2 2단계 — 쓰기 대상 보호: 내장 도구는 직렬화, MCP는 경고

동시에 실행해도 되는 것과 안 되는 것을 나눈다. 다만 "안 되는 것"을 다루는
방식은 대상마다 다르다.

```text
서로 다른 읽기 Tool
→ 제한된 병렬 허용

같은 개인 메모리 파일 쓰기
→ 기존 MemoryWriteLock으로 직렬화 (빠른 로컬 쓰기라 lock을 오래 쥐지 않음)

내장 side-effect Tool
→ 자원 키 기준 직렬화 (역시 우리가 통제하는 코드라 실행시간을 앎)

알 수 없는 MCP Tool
→ 직렬화하지 않는다. 같은 MCP 서버에 동시 실행 중인 다른 호출이 있으면
  승인 카드에 경고를 띄우고, 진행 여부는 승인하는 사람이 정한다.
```

**왜 MCP만 다르게 하는가(2026-08-21 재검토, `2026-08-21_04` 참고)**:
원래는 MCP도 advisory lock을 쥔 채 handler를 부르는 같은 방식으로
직렬화하려 했다. 그런데 그 lock은 즉시 끝나는 로컬 쓰기용으로 만들어진
것이고, MCP 호출은 `2026-08-21_01`이 정한 대로 최대 480~600초까지 걸릴
수 있다 — 대기하는 모든 호출이 그만큼 DB 커넥션을 붙잡게 된다.

더 근본적으로는, MCP 서버를 한 번에 하나씩만 쓰게 만드는 게 기술적으로
필수인 것도 아니다 — MCP 서버는 보통 동시 접속을 문제없이 받는다.
우리가 모르는 건 "동시 접속이 가능한가"가 아니라 "그 요청이 하는 일이
동시에 일어나도 안전한가"이고, 이건 도구 설명만으로는 애초에 알 수 없다
(§3.2). 정보가 없는 채로 기다리게 하는 대신, 아는 사실("동시에 같은
곳에 뭔가 하는 중")만 정직하게 보여주고 판단은 승인하는 사람에게
맡긴다 — `2026-08-21_02`/`2026-08-21_03`이 이미 택한 것과 같은 방향이다.

**내장 side-effect Tool 직렬화는 그대로 유지**한다. 실행을 거부하는 게
아니라 대기시키는 것이고, 우리가 실행시간을 아는 로컬 도구라 lock을
오래 쥘 일이 없다.

```text
내장 write Tool 호출 A, B, C 동시 요청 (같은 자원 키)
  → A 실행
  → B 대기
  → C 대기
  → 순서대로 완료
```

프로세스가 여러 개인 배포에서는 Python `Lock`만으로 충분하지 않다. 메모리 쓰기에 이미
사용 중인 PostgreSQL advisory lock 패턴을 재사용하거나, 실행 슬롯을 관리하는 DB
lease가 필요하다.

**MCP 호출은 직렬화 없이 즉시 실행하되, 경고만 띄운다.**

```text
MCP 호출 A, B 동시 요청 (같은 MCP 서버)
  → 승인 카드를 만들기 직전 "활성 호출 표시판" 조회
  → 서로의 존재를 확인하면 카드에 "다른 요청이 같은 서버에 진행 중"
    경고 표시
  → 사용자가 각각 판단해서 승인/거절
  → 승인되면 둘 다 즉시 실행 (기다리지 않음)
```

세부 스키마와 표시판 lifecycle은 `2026-08-21_04_MCP_동시_쓰기_경고_
설계.md` §3 참고.

### 5.3 3단계 — 팀 전체 실행 슬롯

여러 사용자와 여러 Root 실행을 합친 팀 전체 상한이다.

```text
팀 A 실행 1: Child 3개
팀 A 실행 2: Child 3개
팀 A 실행 3: MCP 2개
```

각 실행만 보면 제한 안쪽이어도 팀 전체로는 외부 호출이 몰릴 수 있다. 운영 단계에서는
`team_id` 기준 실행 슬롯을 두고, 슬롯이 없으면 실패시키지 말고 짧게 대기시킨다.

이 단계는 다중 Django/Worker 프로세스에서도 공유돼야 하므로 process-local semaphore가
아니라 DB 또는 공용 큐가 필요하다. MVP 첫 구현에서는 1·2단계를 우선하고, 실제 동시
사용 부하가 생기기 전에 3단계를 추가한다.

## 6. Tool 종류별 실행 정책

| 호출 종류 | 기본 실행 정책 | 이유 |
|---|---|---|
| `task` 위임 | 제한된 병렬 | 독립 Child의 지연을 줄임 |
| 내장 read Tool | 제한된 병렬 | 상태를 변경하지 않음 |
| 내장 side-effect Tool | HITL 후 자원별 직렬화 | 승인과 중복 쓰기 보호 |
| MCP Tool | HITL 승인 시 동시 실행 경고 (직렬화 안 함) | read/write·동시성 능력을 알 수 없어 판단을 사람에게 넘김 |
| 개인 장기 메모리 쓰기 | 파일·namespace별 직렬화 | 기존 lost update 방지 |
| 같은 Child alias 복수 호출 | 허용하되 call ID별 추적 | 서로 다른 독립 입력일 수 있음 |

## 7. 실패 처리

기본 정책은 **fail-late + 부분 결과 허용**으로 한다.

```text
Child A 성공 ─┐
Child B 실패 ─┼─ 모두 종료 후 Root에 결과 전달
Child C 성공 ─┘
```

Root에는 성공 결과와 함께 Child B가 실패했다는 구조화된 ToolMessage가 전달된다. Root는:

1. 성공한 결과만으로 답할 수 있으면 부분 결과임을 명시하고 답한다.
2. 실패한 결과가 필수라면 사용자에게 완료하지 못했다고 말한다.
3. 같은 호출을 자동으로 무제한 재시도하지 않는다.

다른 Child가 아직 실행 중인데 하나가 실패했다고 전체를 즉시 취소하지 않는다. 외부
도구는 중간 취소가 보장되지 않고, 이미 성공한 비용과 결과를 버릴 이유도 없기 때문이다.

**"부분 결과"가 뜻하는 것(2026-08-21, `2026-08-21_05_병렬_side-effect_
부분실패_보고.md` 참고)**: 한 카드로 병렬 승인된 side-effect 호출들이
섞여 있을 때, 이미 성공한 호출을 자동으로 되돌리지 않는다 — 사용자가
연결하는 임의의 MCP 도구는 되돌리는 방법을 우리가 알 수 없고, 이메일
발송처럼 원천적으로 되돌릴 수 없는 동작도 있다. 대신 결과를 하나의 요약
문장으로 뭉개지 않고, tool_call_id별 성공/실패 목록 그대로 모델과 사용자
화면에 전달한다(§9의 tool_call_id 추적 원칙을 병렬 side-effect 결과에도
그대로 적용). "일부 실패했습니다" 같은 뭉뚱그린 문구로 대체할 수 없다.

재시도는 별도 정책이 생기기 전까지 Root LLM의 새 tool call 또는 사용자의 재요청으로만
수행한다. side-effect Tool은 idempotency가 확인되지 않으면 자동 재시도하지 않는다.

## 8. HITL 병렬 호출

HITL interrupt는 한 턴의 side-effect 요청들을 한 번에 모을 수 있다. UI는 호출별로
다음을 보여줘야 한다.

```text
[승인] Jira 이슈 3건 생성
[거절] 외부 MCP send_email 호출
[승인] 업무 상태 변경
```

API도 단일 `decision` 대신 `tool_call_id` 또는 action index별 decision 목록을 받아야
한다.

```json
{
  "decisions": [
    {"action_index": 0, "type": "approve"},
    {"action_index": 1, "type": "reject"},
    {"action_index": 2, "type": "approve"}
  ]
}
```

승인된 호출만 실행한다. 승인됐다는 이유만으로 서로 동시에 써도 안전하다는 뜻은
아니므로, 내장 side-effect Tool은 실행 시 §5.2의 자원별 직렬화가 다시 적용된다.
MCP Tool은 직렬화 대신 승인 카드 자체에 동시 실행 경고가 이미 표시돼 있으므로
(§5.2, `2026-08-21_04`), 승인한 시점에 이미 그 위험을 알고 판단한 것으로 본다.

호출별 승인 UI/API가 완성되기 전에는 병렬 side-effect 호출을 하나의 전체 승인으로
실행하는 현재 동작을 확대하지 않는다. 안전한 임시 정책은 승인된 side-effect Tool을
직렬 실행하는 것이다.

## 9. 이벤트와 화면

모든 병렬 단위는 배열 순서나 alias가 아니라 `tool_call_id`를 기준으로 연결한다.

```text
delegation_id = parent task tool_call_id
tool_call_id  = Child 내부 Tool 호출 ID
run_id        = Root/Child 실행 ID
parent_run_id = 부모 실행 ID
```

화면은 병렬 Child를 한 줄씩 별도 표시한다.

```text
문서 조사       실행 중
인력 조회       완료
리스크 분석     실패
```

같은 alias를 두 번 호출해도 서로 다른 `tool_call_id`라면 다른 실행으로 표시한다.

현재 namespace 순서 휴리스틱으로는 Child 내부의 세부 진행 이벤트가 잘못 귀속될 수 있다.
정확한 namespace↔delegation ID 연결을 구현하기 전에는 다음 중 하나를 택한다.

1. 병렬 Child의 시작·완료만 정확하게 보여주고 내부 progress는 합쳐서 표시한다.
2. LangGraph namespace에서 안정적으로 얻을 수 있는 실행 ID를 확인해 명시적 매핑을 만든다.

잘못된 상세 정보를 보여주는 것보다 1번을 안전한 초기 동작으로 사용한다.

## 10. 프롬프트

Root 프롬프트에는 다음 원칙을 짧게 추가한다.

```text
서로의 결과에 의존하지 않는 작업은 한 번의 응답에서 여러 task 호출로 위임한다.
한 작업의 결과가 다른 작업의 입력이면 앞 작업을 완료한 뒤 다음 작업을 위임한다.
같은 외부 상태를 변경할 수 있는 작업들은 병렬로 위임하지 않는다.
```

프롬프트는 병렬화를 유도하지만 안전을 보장하지 않는다. 모델이 이 지시를 어겨도 서버의
동시성 제한, HITL, 권한 검사와 쓰기 락이 최종 방어한다.

## 11. 구현 순서

### Phase 1 — 현재 병렬 실행에 상한 추가

1. `RuntimeCapabilityPolicy`에 per-super-step 동시 실행 상한 추가
2. `DeepAgentStreamAdapter`의 run/resume config에 같은 상한 전달
3. 복수 `task`가 상한만큼만 동시에 실행되는 실물 테스트
4. Child 내부 복수 Tool에도 설정이 어떻게 전파되는지 테스트

### Phase 2 — 병렬 HITL

**2026-08-21, `2026-08-21_02_MCP_승인_범위_변경_반영.md`에서 원래 Phase 3이던
이 항목을 Phase 2 자리로 앞당겼다.** MCP 쓰기 도구 승인 허용 역할이
leader 전용에서 leader+member로 넓어져(`2026-08-21_02` 참고), 자기 요청을
자기가 승인할 수 있는 대상 범위가 팀 전체로 커졌다. 지금 승인 카드는
호출별이 아니라 "카드 하나 통째로 승인/거절"만 지원하므로, 팀원이 병렬
쓰기 요청 여러 개를 한 번에 몰아 만들고 실수로 한 번에 승인해 버릴
위험이 이전보다 커졌다고 판단했다. 아래 순서 자체(카드 확장 → API 변경 →
재개 테스트)는 바뀌지 않았고, 이 항목이 Phase 3(쓰기 직렬화)보다 먼저
온다는 순서만 바뀌었다.

1. 확인 카드에 action별 선택 추가
2. serializer/API를 decisions 목록으로 변경
3. approve/reject/edit 혼합 재개 테스트
4. 이 시점엔 Phase 3(내장 도구 쓰기 직렬화)이 아직 없으므로, 개별 승인된
   내장 side-effect 호출들이 여전히 동시에 실행될 수 있다는 걸 인지하고
   진행한다 — 직렬화 보장은 Phase 3에서 다시 검증한다. MCP 호출은 애초에
   직렬화 대상이 아니므로(§5.2, `2026-08-21_04`) 이 항목과 무관하다.

### Phase 3 — 내장 도구 직렬화 + MCP 동시 실행 경고

**2026-08-21, `2026-08-21_04_MCP_동시_쓰기_경고_설계.md`에서 MCP 관련
작업을 lock 방식에서 경고 방식으로 바꿨다.** 이유는 §5.2 참고 — advisory
lock을 쥔 채 최대 480~600초짜리 MCP 호출을 기다리면 DB 커넥션을 그만큼
붙잡게 되고, 애초에 MCP 서버를 직렬화해야 할 기술적 필연성도 없었다.

1. 내장 side-effect Tool의 자원 키 정의
2. 같은 자원 키의 승인된 내장 호출을 직렬화하는 middleware
3. 기존 `MemoryWriteLockMiddleware`와 lock 순서·교착 가능성 검증
4. MCP tool_ref에서 MCP 서버 ID를 확인하는 키 정의(직렬화가 아니라 아래
   활성 호출 표시판 조회에 쓴다)
5. "활성 호출 표시판"(`mcp_active_calls`) 테이블 추가 — `factory.py`의
   `_run()` wrapping 레이어(A-3 idempotency와 같은 자리)에서 시작 시
   삽입, 종료 시(성공·실패·timeout 무관) 삭제(`2026-08-21_04` §3.1)
6. `interrupt_on`을 `dict[str, bool]`에서 `dict[str, InterruptOnConfig]`
   (`description` 콜백 포함)로 바꾸고, HITL 카드 생성 시 ①같은
   `mcp_server_id`의 활성 호출(표시판 조회)과 ②같은 배치(AIMessage)
   안의 다른 MCP tool_call(`state`에서 직접 비교, DB 조회 없음) 둘 다
   확인해 경고를 붙이는 로직 추가(같은 run의 병렬 Child 포함, §3.2·§3.5)
7. 오래된 행을 무시하는 조회 조건(gunicorn timeout 600초 기준) 테스트
8. 같은 배치로 승인 요청된 MCP 쓰기 2개가 서로에게 정확히 경고를
   띄우는지 테스트(§3.2 — 표시판만으로는 못 잡는 케이스)
9. Phase 2에서 개별 승인된 내장 side-effect 호출들이 이제 쓰기 정책에
   따라 직렬화되는지 검증. MCP는 승인 카드에 경고가 정확히 뜨는지와,
   승인 후 직렬화 없이 즉시 실행되는지를 검증한다.

### Phase 4 — 관측성과 팀 상한

1. 병렬 폭, 대기 시간, 실행 시간 기록
2. 팀 전체 동시 실행 슬롯
3. 실행별·팀별 비용 상한
4. 부하 테스트 결과로 기본 동시 실행 수 확정

### Phase 5 — 필요할 때만 명시적 실행 계획

LLM의 병렬 판단이 실제 데이터에서 지나치게 불안정하거나 의존성 오류가 반복될 때만
`depends_on`을 가진 명시적 DAG 실행 계획을 검토한다. 자유 연결 에이전트/MCP 환경에서
초기부터 별도 Planner와 Scheduler를 추가하면 복잡도와 모델 호출 비용이 크게 늘어나므로
측정 없이 먼저 도입하지 않는다.

## 12. 완료 조건

병렬 실행 설계가 완료됐다고 보려면 다음을 만족해야 한다.

- 복수 독립 Child가 실제로 겹쳐 실행된다.
- 설정된 동시 실행 상한을 넘지 않는다.
- 같은 내장 side-effect 자원에 대한 호출은 보수적 기본값으로 직렬화된다.
- 같은 MCP 서버에 동시 실행 중인 다른 호출이 있으면 승인 카드에 정확히
  경고가 뜬다(같은 run의 병렬 Child 포함) — 직렬화는 하지 않는다.
- 병렬 Child 하나가 실패해도 다른 결과가 보존된다.
- 같은 alias를 복수 호출해도 시작·완료가 뒤섞이지 않는다.
- 병렬 side-effect 호출을 사용자가 개별 승인·거절할 수 있다.
- 승인 후에도 내장 도구의 쓰기 직렬화는 유지된다.
- 병렬 side-effect 호출 중 일부만 실패해도, 이미 성공한 호출을 자동으로
  되돌리지 않는다. 결과는 tool_call_id별로 분리돼 모델과 사용자 화면에
  전달되며, 하나의 요약 문장으로 뭉개지지 않는다(`2026-08-21_05`).
- timeout·권한·HITL을 병렬 호출이 우회하지 못한다.
- 팀 전체 부하가 설정된 운영 상한을 넘지 않는다.
