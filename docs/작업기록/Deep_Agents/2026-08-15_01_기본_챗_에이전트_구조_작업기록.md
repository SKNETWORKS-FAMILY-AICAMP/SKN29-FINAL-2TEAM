# 2026-08-15_01 — Chat 재설계: 기본 챗 에이전트 구조 작업기록

> 정본 관계: 이 문서는 계약 문서가 아니라 **작업기록**이다. `2026-08-13_02_Deep-Agent_런타임_공통_계약_v1.md`가
> 여전히 정본이고, 여기는 그 위에서 이번에 새로 결정·구현한 것을 남긴다.

## 1. 배경 — 왜 이 작업을 시작했나

teammate(성주연)의 `699da7f` 커밋으로 실행 코어(`services/agent_runtime/`)와 Chat 연동
(`apps/chat/api_views.py`)이 예상보다 많이 끝나 있는 걸 확인하던 중, Chat이 실제로는
**옛 스키마 "정문" 에이전트 하나에게만 말을 걸고 있고**, 그 정문이 다른 에이전트에게
위임하는 유일한 통로(`agent:*` A2A 와일드카드, `services/harness/registry.py`)가 새
엔진의 `ToolLoader.load()`에서 인식되지 않는다는 걸 발견했다:

- `legacy_bridge.py`의 `draft_from_legacy_agent()`가 정문의 `tool_refs`(그 안의 `agent:*`
  포함)를 필터링 없이 그대로 새 엔진에 넘긴다.
- `ToolLoader.load()`(내장 도구 + MCP 도구만 안다)는 모르는 tool_ref가 하나라도 있으면
  요청 전체를 `ToolUnavailableError`(409)로 막는다.
- 즉 정문이 `agent:*`를 갖고 있으면, 8/14 새 엔진 컷오버 이후로 위임뿐 아니라 정문
  자체가 메시지를 못 받을 가능성이 있다. (실제 DB로 재현은 못 했다 — §5 참고.)

이걸 계기로 지훈과 Chat 재설계 방향을 다시 정했다. 확정된 것(2026-08-15, 지훈 확인):

1. **빌더**에서 서브에이전트로 이미 만든 에이전트를 선택할 수 있다(기존 기능, 유지).
2. **대화 상대 선택**을 사용자가 직접 한다 — Chat 화면 상단 드롭다운(**UI는 이번에
   안 만듦**, §6 참고 — 예전에 "에이전트 선택기는 의도적으로 없앴다"는 PM 결정과
   충돌해서 배경 확인 전까지 보류).
3. **기본 챗 에이전트**(아무것도 안 고르면 떨어지는 곳) — tool·MCP만 붙고 서브에이전트는
   없다. **DB에 실제 저장된 에이전트 행**으로 둔다(코드 고정 설정 아님) — Builder로
   팀이 직접 수정 가능하고, 드롭다운에 다른 에이전트와 같은 모양으로 끼워 넣을 수
   있어서.
4. 옛 정문/`agent:*` A2A는 **이 재설계가 끝나면 함께 제거**한다. 그 전까지는 손대지
   않는다.

이번 작업은 그중 **3번(기본 챗 에이전트)의 백엔드 구조**와, 2번을 나중에 쉽게 붙일 수
있게 하는 준비까지다.

## 2. DB 스키마 — `agents.is_default_chat`

`DB/migrations/2026-08-15_agent_default_chat.sql` (+ `DB/schema.sql` 동기화):

```sql
ALTER TABLE agents ADD COLUMN IF NOT EXISTS is_default_chat BOOLEAN NOT NULL DEFAULT false;

CREATE UNIQUE INDEX IF NOT EXISTS agents_one_default_chat_per_team
    ON agents (team_id)
    WHERE is_default_chat = true;
```

**`is_prebuilt`를 재사용하지 않았다.** `is_prebuilt`는 이미 "우리가 시드로 넣은 것"이라는
다른 뜻으로 쓰이고 있다 — 정문뿐 아니라 복제용 예시 에이전트도 같은 플래그를 쓴다
(`backend/db/agent_platform.py:119-121`의 `AgentRepository.PLATFORM_TOOL` 주석,
`backend/services/createDB/seed_agents.py`). 그래서 그것만으로는 "이게 Chat 기본값이다"를
못 가른다.

**별개로 발견한 것 — 안 고침**: `DB/migrations/2026-08-13_agent_versioning.sql`의
`agents.is_prebuilt` 주석은 "정문 판별용"이라 적혀 있는데, 실제 정문 판별은
`agent:*` tool_ref 보유 여부다. 그 주석은 낡았다. 이번 마이그레이션 파일에 발견
사실만 남겨 뒀다.

삭제·비활성화 금지는 DB 제약이 아니라 애플리케이션 레이어에서 막는다(§4).

## 3. 프로비저닝 — 팀 생성 시 자동 생성 + 기존 팀 백필

`database_connection()`을 안 열고 넘겨받은 커서를 그대로 쓴다** — `backend/db/repositories.py`의

`TeamRepository.create()`에서 지연 import로 호출한다 — `agent_platform.py`가 이미
`repositories.py`의 `_require_team`을 가져다 써서, 모듈 최상단에서 서로 못 붙인다
(순환 참조).

**model을 명시적으로 채운다** — `services.harness.runner`의 `DEFAULT_MODEL`/`DEFAULT_EFFORT`
(`"gpt-5.6-luna"`/`"low"`)를 그대로 재사용한다. 이유는 §5.2 참고.

## 4. 가드 — 기본 에이전트는 못 끈다

`AgentVersionCrudRepository.set_status()`에 체크 추가: `status != 'ACTIVE'`로 바꾸려는
대상이 `is_default_chat=true`면 `RepositoryError("기본 챗 에이전트는 비활성화할 수
없습니다.")`.

`AgentVersionDisableAPIView`의 기존 전제("끄는 쪽은 항상 안전하다")가 기본 챗

삭제 API는 새 스키마에 아직 없어서 여기서만 막으면 충분하다.

## 5.3 실제 검증 중 발견한 버그 — ID 충돌로 새 에이전트가 조용히 가려짐

§5.2를 지훈 로컬 환경(Docker DB)에서 실행해 검증하는 과정에서 실제로 겪었다.

**증상**: `backfill_default_chat_agents.py`가 만든 기본 챗 에이전트(`AG002`)로
세션을 열고 메시지를 보냈더니 응답은 왔지만, 이벤트의 `agent_version_id`가
`None`이었다 — 새 스키마 실행이 아니라 **레거시 실행 경로로 갔다**는 뜻이다.

**원인**: `agents`(새 스키마)와 `agent`(옛 스키마) 두 테이블이 `next_short_code()`로
번호를 각자 따로 매기는데, 우연히 둘 다 `AG002`가 나왔다(팀 TE001에 이미 옛
`agent` 테이블 쪽 `AG002`가 있었음). `_resolve_session_agent()`는 옛 테이블을
**먼저** 보므로, ID가 겹치면 새로 만든 에이전트는 에러 없이 조용히 무시되고
옛 에이전트가 대신 응답한다. `DB/migrations/2026-08-13_agent_versioning.sql`
상단 주석이 이 충돌 가능성을 이미 경고하고 있었는데, 이번에 실제로 재현됐다.

**논의한 대안**: 옛 `agent` 테이블을 아예 지우는 안도 나왔지만, 지금 운영 중인
Chat("정문")·옛 Builder 화면·기존 `chat_session` 전부가 그 테이블에 물려
있어서 지금 지우면 현재 되는 기능이 멈춘다 — 재설계 완료 후(§7의 task #19)로
미룬다.

**고친 것**: `agents.agent_id` 발급 시 옛 `agent` 테이블의 MAX도 같이 보고 더
큰 쪽 다음 번호를 쓰도록 `_next_agents_id()`를 추가했다(`backend/db/agent_platform.py`
— `publish()`·`provision_default_chat_agent()` 둘 다 여기로 통일, `backend/services/createDB/backfill_default_chat_agents.py`도
같은 로직을 복붙해 반영). `next_short_code()`(범용 유틸, 다른 테이블도 씀) 자체는
안 건드렸다 — `agents` 테이블만의 특수 사정이라 여기서만 고쳤다.

**안 고친 것 — 반대 방향 충돌은 남아 있다**: 옛 `agent` 테이블이 새로 발급하는
ID가 기존 새 스키마 에이전트 ID와 겹치는 경우는 안 막았다(`AgentCrudRepository`
쪽 `next_short_code(table="agent", ...)` 호출, 그대로 둠). `_resolve_session_agent()`가
옛 테이블을 먼저 보므로 이 반대 방향도 같은 종류의 문제를 일으킬 수 있지만,
옛 시스템은 재설계 완료 후 통째로 없어질 예정이라 지금 범위에서는 뺐다 — 팀에
공유는 해 둘 것.

**로컬 DB의 기존 잘못된 데이터**: 검증 중 만들어진 충돌 상태의 `AG002`(새 스키마)는
지우고 백필을 다시 돌려 재발급했다.

## 6. 발견했지만 손 안 댄 것

- **`agent_versions.model`이 NULL이면 순수 새 스키마 실행이 깨진다.**
  `loader.py`의 `_definition_from_row()`가 `row["model"]`을 그대로 `AgentDefinition.model`에
  넣고, `models/factory.py`의 `resolve(model: str, ...)`는 이를 필수 인자로 받는다.
  `legacy_bridge.py`는 NULL이면 `DEFAULT_MODEL`로 떨어뜨려 주지만, `agent_id`+
  `agent_version_id`로 직접 도는 순수 새 스키마 경로엔 그런 안전망이 없다. Builder의
  `model` 필드는 nullable이라, 사용자가 모델을 안 고르고 저장하면 이 상태가 된다.
  기본 챗 에이전트는 프로비저닝 시 model을 명시적으로 채워 이 문제를 피했지만,
  팀이 직접 만드는 다른 에이전트는 여전히 노출돼 있다. **팀 공유 필요.**
- `_check_tool_refs` 미보호 호출 옛 엔드포인트 버그(`2026-08-13_03_Repository_저장발행API_작업기록.md`
  §5에서 이미 발견) — 여전히 안 고쳐짐, 여전히 팀 공유 안 함.

## 6.5 Chat 상단 드롭다운 UI — 결국 지금 만듦

§1에서는 "에이전트 선택기를 의도적으로 없앴다"는 예전 PM 결정과 충돌해서 보류했다.
그 뒤 지훈이 옛 Builder 화면을 새 화면으로 완전히 교체하고 싶다고 했는데, 그러면
"새 화면으로 만든 에이전트를 Chat에서 하나도 못 부른다"는 문제가 더 급해졌다 —
교체를 하든 안 하든 팀원에게 지금 흐름을 공유해야 해서, 배경 확인을 더 기다리지
않고 드롭다운을 넣기로 했다(2026-08-15, 지훈 확인 — "일단은 팀 공유용으로 먼저").

**과도기 UI라는 걸 코드에 남겼다** — `ChatPage.tsx` 헤더 주석에 "재설계가 끝나
정문을 걷어낼 때까지"라고 명시. 예전 "선택기는 없앴다" 주석과 정면으로 다른
결정이라, 나중에 코드만 보고 왜 있는지 헷갈리지 않게 이유를 남겼다.

구현:

- `AgentVersionCrudRepository.list_for_team()`·`agent_version_response()`에
  `is_default_chat` 필드 노출(원래 목록에 안 실려 있었음 — Builder 화면은 이
  값이 필요 없었어서).
- `frontend/src/api/agentVersions.ts` — `AgentVersionSummary`에 `is_default_chat` 추가.
- `ChatPage.tsx` — 옛 `listAgents()`/`isPlatformAgent()` 기반 자동 선택을
  `listAgentVersions()` 기반으로 교체. 드롭다운에서 팀의 ACTIVE 에이전트를
  고르면(기본은 `is_default_chat`) 그 에이전트로 **새 대화**가 시작된다 —
  대화 하나는 만들어질 때 고른 에이전트에 고정이라 중간에 못 바꾸므로, 드롭다운을
  바꾸면 `startNew()`를 같이 호출한다.

**안 고친 것**: 옛 방식(정문의 `agent:*` 위임)으로 만들어진 기존 대화를 다시 열면,
그 세션의 `agent_id`가 지금 드롭다운 목록(새 스키마 ACTIVE만)에 없어서 선택값이
비어 보일 수 있다 — 데모·팀 공유 목적이라 지금은 손 안 댔다.

## 6.6 사이드바 "에이전트"를 새 화면으로 교체

§6.5로 Chat이 새 스키마 에이전트를 부를 수 있게 되면서, 옛 Builder 화면을 계속
사용자 동선에 두지 않아도 될 이유가 사라졌다(전에는 "새 화면으로 만든 에이전트를
Chat이 못 부른다"는 이유로 교체를 미뤘음, §6.5 첫 문단). `frontend/src/routes.ts`의
`APP_NAV_ITEMS`에서 "에이전트" 항목이 이제 `PATHS.agentVersions`(새 화면)를 가리킨다
— 옛 화면("테스트 실행" 포함)은 사이드바에서 빠졌다.
