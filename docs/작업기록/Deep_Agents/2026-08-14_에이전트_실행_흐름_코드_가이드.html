Builder에서 질문·Tool·최종 답변까지

저장된 Agent 정의와 사용자 질의가 어디서 합쳐지고, LLM이 Tool을 고른 뒤 결과를 받아 다시 판단하는 과정을 한 흐름으로 정리한다.

0. 먼저 알아야 할 현재 상태

Builder 화면과 새 Deep Agent Runtime이 아직 한 경로로 완전히 통합되지 않았다. 현재 화면은 예전 agent/instruction API를 사용하고 Builder Test Run도 레거시 services.harness.run_agent()를 탄다. 새 실행 코어는 agents/agent_versions/system_prompt를 사용하며, chat_session.agent_version_id가 있는 채팅만 새 Runtime으로 실행된다.

현재 Builder 화면

name, description, instruction, model, reasoning_effort, max_iterations, tool_refs

저장된 Child/Sub-agent 선택 UI가 없다.

AgentEditPage.tsx:55–61, 151–162

새 AgentVersion API / Runtime

name, description, system_prompt, model, reasoning_effort, max_iterations, tool_refs, subagents

저장된 Child 버전을 CompiledSubAgent로 조립한다.

serializers.py:130–167 · factory.py:166–190

따라서 Builder Test Run 결과를 현재 Deep Agent Runtime의 검증 결과로 보면 안 된다. Test Run은 새 Scaffold·Compiled Child·새 Middleware 경로를 검증하지 않는다.

3. 질문을 보내기 전, Runtime Graph를 조립한다

Chat API→ AgentExecutor→ DefinitionLoader→ AgentRuntimeFactory→ create_deep_agent()

① DB 로드·검증

AgentVersion, Tool refs, Child 버전을 로드하고 팀 권한·활성 상태·중복 alias·순환·재위임을 검사한다.

loader.py · validation.py:51–116

② Model 생성

팀 Custom endpoint → claude-* → OpenAI 순서로 provider를 해석한다. API Key는 DB나 Django settings에서 읽고 LLM Prompt에는 넣지 않는다.

models/factory.py:33–131

③ Tool 조립

저장된 tool_refs만 로드 → member에게 외부 write Tool 제거 → LangChain StructuredTool로 변환한다.

factory.py:141–149 · tools/loader.py:58–92

④ Middleware 조립

Root/Child에는 Model 호출 상한과 Tool 호출 상한을 붙인다. GP는 6/12를 쓴다.

middleware/factory.py:30–50

⑤ Child 조립

저장된 Child는 각자 Model·Prompt·Tool·Middleware로 그래프를 만들어 CompiledSubAgent로 연결한다. GP는 별도로 명시 삽입한다.

subagents/builder.py:16–49 · factory.py:166–190

⑥ Deep Agents 그래프

4. 실제 System Prompt는 어떻게 만들어지나

DB에 저장된 것

Builder가 작성한 Agent 전용 지시만 agent_versions.system_prompt에 저장한다.

"너는 Google Drive 문서 수정 전문 에이전트다.
문서를 수정하기 전에 변경 내용을 먼저 요약한다."

Runtime에서 추가되는 것

RuntimePromptAssembler가 공통 Scaffold를 앞에 붙인다. DB의 Prompt를 덮어쓰지 않는다.

RUNTIME_SCAFFOLD
+ "[\uC774 \uC5D0\uC774\uC804\uD2B8\uC758 \uC9C0\uC2DC]"
+ agent_versions.system_prompt
현재 코드의 RUNTIME_SCAFFOLD 전체 
너는 팀의 프로젝트 운영을 돕는 에이전트다.

[실행 원칙]
- 사용자의 요청을 먼저 이해하고, 필요한 경우에만 제공된 도구나 서브 에이전트를 사용한다.
- 같은 도구를 같은 목적으로 불필요하게 반복 호출하지 않는다.
- 도구 결과가 충분하면 추가 호출을 중단하고 답변을 작성한다.
- 요청을 완료할 수 없으면 확인한 내용과 완료하지 못한 내용을 구분한다.

[근거]
- 도구나 문서로 확인한 사실만 확정적으로 말한다.
- 확인하지 못한 내용을 추측해서 채우지 않는다.
- 사실을 설명할 때는 어떤 문서나 도구 결과를 근거로 했는지 밝힌다.

[답변]
- 사용자의 질문에 직접 답한다.
- 불필요한 계획이나 진행 예고를 먼저 나열하지 않는다.
- 필요한 내용만 간결하고 명확하게 전달한다.

6. LLM이 Tool을 고른 뒤의 반복 흐름

1

LLM이 다음 행동을 선택한다

LLM은 노출된 Tool의 이름·설명·입력 schema를 보고 ① 텍스트 답변, ② 일반 Tool Call, ③ task Sub-agent 위임 중 하나를 고른다. 별도의 규 기반 Tool Router는 아직 없다.

2

Tool Call을 반환한다

AIMessage.tool_calls = [{
  "name": "document_search",
  "args": {"query": "진행 상황"},
  "id": "call_123"
}]

여러 Tool Call을 한 응답에 넣을 수 있으며 LangGraph ToolNode가 병렬로 실행할 수 있다.

3

실행 직전 권한과 서버 인자를 적용한다

외부 변경 Tool은 leader만 실행할 수 있다. LLM이 team_id를 임의로 보내도 RuntimeContext의 서버 값으로 덮어쓴다.

factory.py:43–65 · tools/loader.py:27–55

4

Tool handler를 실행하고 ToolMessage를 만든다

handler의 반환값은 현재 LangGraph State의 messages에 Tool Result로 추가된다. 모델 자체에 저장되는 것이 아니다.

5

같은 LLM을 다시 호출한다

System Prompt + 기존 Messages + Tool Call + Tool Result를 보고 다음을 판단한다.

Tool Result 충분→최종 텍스트Tool 추가 필요→다음 Tool Call전문 작업→task(Sub-agent)
6

Sub-agent를 고르면 Root는 결과를 기다린다

task(subagent_type=alias, description=위임 내용) → Child Graph 실행 → Child 최종 결과만 Root의 ToolMessage로 반환 → Root LLM 재호출. 현재는 동기 위임이며 Root가 Child 완료까지 기다린다.

subagents/builder.py · 이벤트 판별: events.py:337–420

7

최종 텍스트를 이벤트와 DB 답변으로 바꾼다

Tool Call이 없는 Root AIMessage의 텍스트를 result 이벤트로 매핑하고 NDJSON으로 화면에 보낸 뒤 chat_message에 저장한다.

events.py:232–254 · apps/chat/api_views.py:430–519

7. Middleware는 어디에 들어가나

Middleware는 순서대로 한 번씩 실행되는 업무 단계가 아니다. LLM 호출 전후·Tool 호출 전후·Agent 시작 전후의 hook으로 들어간다.

구분현재 연결하는 일
우리가 추가활성ModelCallLimitMiddleware: Root/Child는 min(max_iterations, 20), GP는 6회. ToolCallLimitMiddleware: Root/Child 40회, GP 12회.
Filesystem활성기본 StateBackend. 현재 Harness Profile에서 delete만 최종 제외.
SubAgentRoot만 활성GP + 저장된 Compiled Child를 task Tool로 노출. Child는 subagents=[]로 재위임 안 함.
SummarizationDeep Agents 기본Context가 커지면 과거를 요약. 우리 코드에서 임계치를 덮어쓰지 않음.
PatchToolCallsDeep Agents 기본중단 후 Tool Call/Result 쌍이 깨진 메시지를 복구.
Harness Profile활성Deep Agents의 GP 자동 삽입을 끄고, delete Tool을 제외. Factory가 GP를 명시적으로 다시 추가.
Skills / Memory / HITL / Async / Todo비활성현재 Factory가 해당 인자나 Middleware를 전달하지 않음.
Checkpointer / Store미연결대화 상태 재개·장기 Memory가 없음. 대화 영속성은 현재 chat_message 최근 20개 재주입으로 처리.

우리 Middleware: middleware/factory.py · 제외 정책: runtime_policy.py:14–54 · Deep Agents 호출: compat/deepagents_v075.py

8. 각 값은 어디에 저장되는가

PostgreSQL — 영구 저장

Agent 정의: agents, agent_versions, agent_version_tools, agent_version_subagents

대화: chat_session, chat_message

Session은 생성 시의 agent_version_id에 고정된다.

LangGraph State / StateBackend — 이번 실행

현재 턴의 Messages, Tool Call, Tool Result, 요약 상태, 가상 파일이 있다.

Checkpointer가 없어 그래프 실행 후 이 상태를 다음 HTTP 요청에서 재개하지 못한다.

Model Provider / SDK

LLM은 입력을 받고 AIMessage를 반환할 뿐, Agent 정의나 대화 DB를 소유하지 않는다.

API Key는 Django settings 또는 팀 Custom Model 설정에서 읽는다.

9. 실패하면 어디로 가고 Retry는 몇 번인가

조립 중 실패

AgentVersion/Child 권한, 모델, Tool 로딩, 그래프 조립이 실패하면 AgentBuildError 또는 구체적 Runtime 예외로 종료한다.

명시적 자동 Retry: 0회

Stream 실행 중 실패

AgentExecutor가 예외를 잡아 AGENT_EXECUTION_FAILED error 이벤트로 종료한다. Chat API는 이 오류도 최종 Agent 메시지로 DB에 저장한다.

명시적 자동 Retry: 0회

max_iterations는 Retry 횟수가 아니다. 현재는 Model Call 상한으로 사용한다. 상한을 넘으면 exit_behavior="error"로 종료한다.
Model SDK 내부 Retry 횟수는 우리 코드에서 고정하지 않았다. ChatOpenAI와 ChatAnthropic 생성 시 max_retries를 넘기지 않으므로, provider SDK 버전의 기본값에 의존한다. 따라서 “우리 서비스의 보장 Retry 횟수”는 현재 0회이며, SDK 내부 횟수는 코드 계약으로 확정되지 않았다.

executor.py:52–137 · middleware/factory.py:30–50 · models/factory.py:90–131
