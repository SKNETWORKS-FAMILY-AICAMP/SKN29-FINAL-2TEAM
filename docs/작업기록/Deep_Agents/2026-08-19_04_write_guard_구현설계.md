# 2026-08-19_04 — write_guard 구현 설계 (코드 반영 직전 단계)

`2026-08-19_02_메모리_기본에이전트_분리_및_쓰기_방어_설계.md` §2가 정한 틀
("금칙어 차단"이 아니라 "저장 가능한 정보의 종류를 좁힌다", 카테고리 표)을
실제 `deepagents==0.7.5`/`langchain` 설치 소스로 검증하고, 코드로 바로
옮길 수 있는 수준까지 구체화한다.

## 1. 재판단 — 기존 설계는 유효한가

**타당하다.** 카테고리 구분(credential/개인정보/권한·보안 서술은 코드,
나머지는 프롬프트) 자체는 실제 도구 인자 구조를 확인해도 그대로 성립한다.
다만 실제 소스를 확인하는 과정에서 기존 설계 문서에 없던 구체적인 문제
하나를 발견했다 — 아래 §2-3.

**검증한 것** (`/tmp/skn_test_venv`의 실제 설치 소스):

- `write_file(file_path: str, content: str)`, `edit_file(file_path: str,
  old_string: str, new_string: str, replace_all: bool = False)` — 도구
  인자 스키마(`deepagents/middleware/filesystem.py` `WriteFileArgs`/
  `EditFileArgs`, 1130~1155행). 검사 대상은 `write_file`이면 `content`,
  `edit_file`이면 `new_string`(실제로 파일에 남는 값)이면 된다 —
  `old_string`은 검사할 이유가 없다.
- `AgentMiddleware.wrap_tool_call(self, request: ToolCallRequest, handler)`
  (`langchain/agents/middleware/types.py`) — `handler(request)`를 아예
  호출하지 않고 바로 `ToolMessage`를 반환하면, 실제 파일 쓰기(`backend.write`/
  `backend.edit`)가 **일어나기 전에** 막힌다(호출 자체를 안 하니 사후 검사가
  아니라 사전 차단). `2026-08-19_02`가 예시로 든 `ToolErrorMiddleware`
  (`langchain/agents/middleware/tool_error.py`)의
  `ToolMessage(content=..., tool_call_id=request.tool_call["id"],
  name=tool_name, status="error")` 구성이 그대로 재사용 가능한 정확한
  패턴이다.
- `ToolCallRequest.tool_call`은 `{"name", "args", "id"}` 딕셔너리
  (`langchain/agents/middleware/types.py` `ToolCallRequest` docstring) —
  `request.tool_call["args"]["file_path"]`/`["content"]`/`["new_string"]`로
  바로 접근 가능, 별도 파싱 불필요.
- `middleware/factory.py`(`MiddlewareFactory`)가 조립하는
  `custom_middleware` 리스트는 Root와 Child가 **같은 인스턴스**를 공유한다
  (`factory.py` `build()` — `custom_middleware = self.middleware_factory
  .build(...)`가 Child 분기·Root 분기 양쪽에서 그대로 쓰임). write_guard는
  Root에만 필요하다(Child는 애초에 진짜 `StoreBackend`가 없어서
  `/memories/users/`에 뭘 써도 그 Child 실행의 빈 `StateBackend`로 떨어질
  뿐, 실제 저장이 안 된다 — `2026-08-15_02_장기메모리_설계.md` §2). 그래서
  `MiddlewareFactory.build()`가 아니라 **`factory.py`의 Root 분기에서,
  `memory_provider is not None`일 때만** 추가해야 한다 — 메모리 관련
  `root_kwargs`를 채우는 것과 같은 조건.

## 2. 재판단에서 새로 발견한 것 — 원시 경로 문자열 대신 정규화된 경로로 비교해야 한다

기존 설계(`2026-08-19_02` §2)는 "`/memories/users/`로 시작하는 경로"라고만
적었는데, 실제로는 **어느 시점의 경로 문자열**을 기준으로 판단할지가
빠져 있었다.

`wrap_tool_call`은 도구 함수 본문이 실행되기 **전**에 끼어든다. 그런데
경로를 실제로 정규화하는 `validate_path()`(`deepagents/backends/utils.py`,
`.`/`..`/역슬래시 정리, 맨 앞 `/` 보정)는 도구 함수 본문 **안**에서
호출된다(`filesystem.py`의 `write_file`/`edit_file` 클로저 내부, 2003·
2097행 근처). 즉 `wrap_tool_call`이 보는 `request.tool_call["args"]
["file_path"]`는 **모델이 보낸 그대로의, 아직 정규화 전** 문자열이다.

이 상태에서 단순히 `raw_path.startswith("/memories/users/")`로만 비교하면,
`validate_path()`를 거치면 결국 같은 파일로 정규화될 변형된 표기(예:
`"memories/users/preferences.md"`처럼 맨 앞 `/`가 빠진 경우,
`"/memories//users/preferences.md"`처럼 슬래시가 중복된 경우, `"/./
memories/users/preferences.md"`)를 놓칠 수 있다. 반대로 방향의 문제(가짜로
그 prefix처럼 보이게 만들어 실제로는 다른 곳에 쓰는 것)는 걱정할 필요
없다 — `validate_path`가 그런 시도는 그 자체로 `ValueError`를 내서 도구
실행이 실패하므로, write_guard가 놓쳐도 실제 피해로 이어지지 않는다.
문제가 되는 방향은 **"진짜 `/memories/users/`로 정규화될 경로인데
표기가 달라서 감시망을 피해가는" 쪽 하나뿐**이다.

**해결**: 직접 정규화 로직을 새로 짜지 않고(이 프로젝트 원칙 — 프레임워크가
이미 제공하는 걸 재구현하지 않는다), `deepagents.backends.utils
.validate_path()`를 write_guard 안에서 그대로 호출해 정규화된 경로를
얻은 뒤 그 값으로 prefix를 비교한다. `validate_path()`가 `ValueError`를
내면(진짜 잘못된 경로) write_guard는 관여하지 않고 그냥 `handler(request)`
로 넘긴다 — 그 오류는 도구 본문이 어차피 같은 이유로 낼 오류이므로, 여기서
따로 처리할 이유가 없다.

## 3. 확정 설계

### 파일 위치

`services/agent_runtime/memory/write_guard.py` (새 파일) — `/memories/`
관련 파일이라 범용 `middleware/`가 아니라 `memory/` 패키지에 둔다는
`2026-08-19_02`의 판단을 그대로 따른다.

### 패턴 — 코드로 형태 기준 검사가 가능한 세 카테고리만

```python
import re

_GUARDED_TOOLS = {"write_file", "edit_file"}

# credential / secret — 값의 "형태"만으로 판단, 진위 판단 불필요
_CREDENTIAL_PATTERNS = [
    re.compile(r"sk-[A-Za-z0-9]{20,}"),                 # OpenAI/Anthropic류 API 키 형식
    re.compile(r"AKIA[0-9A-Z]{16}"),                     # AWS access key 형식
    re.compile(
        r"(?i)(api[_-]?key|secret|token|password|passwd|pwd)\s*[:=]\s*\S+"
    ),
    re.compile(r"(?i)(aws_secret|db_password|secret_key|private_key)\s*[:=]"),
]

# 개인정보 — 자릿수·형식이 고정된 패턴
_PII_PATTERNS = [
    re.compile(r"\d{6}[-\s]?[1-4]\d{6}"),               # 주민등록번호
    re.compile(r"\d{4}[-\s]?\d{4}[-\s]?\d{4}[-\s]?\d{4}"),  # 카드번호
    re.compile(r"01[016789][-\s]?\d{3,4}[-\s]?\d{4}"),  # 휴대전화번호(§4 한계 참고)
]

# 권한/보안 관련 사실 — 진위와 무관하게 카테고리째 차단
_AUTHORITY_KEYWORDS = [
    "관리자 권한", "관리자 계정", "관리자 비밀번호", "루트 계정", "root 계정",
    "내부 접속 정보", "administrator privilege", "admin password",
    "root access", "superuser",
]

_CATEGORY_LABELS = {
    "credential": "credential/secret로 보이는 값",
    "pii": "개인정보로 보이는 값(주민등록번호·카드번호·전화번호 패턴)",
    "authority": "권한/보안 관련 서술",
}


def _match_category(text: str) -> str | None:
    for pattern in _CREDENTIAL_PATTERNS:
        if pattern.search(text):
            return "credential"
    for pattern in _PII_PATTERNS:
        if pattern.search(text):
            return "pii"
    lowered = text.lower()
    if any(keyword.lower() in lowered for keyword in _AUTHORITY_KEYWORDS):
        return "authority"
    return None
```

### 미들웨어

```python
from langchain.agents.middleware.types import AgentMiddleware
from langchain_core.messages import ToolMessage
from deepagents.backends.utils import validate_path

from services.agent_runtime.memory.backend import MEMORY_USERS_PATH_PREFIX


class MemoryWriteGuardMiddleware(AgentMiddleware):
    """`/memories/users/` 쓰기 전, 코드로 형태 판단이 가능한 세 카테고리
    (credential/개인정보/권한·보안 서술)만 검사한다. "모델이 추론했는가"·
    "프로젝트 한정 사실인가" 같은 맥락 판단은 여기서 하지 않는다 — 그건
    `_MEMORY_ROUTING_PROMPT`(memory/backend.py)의 몫이다. 근거:
    `2026-08-19_02_...` §2, `2026-08-19_04_write_guard_구현설계.md`.
    """

    def __init__(self, *, guarded_prefix: str = MEMORY_USERS_PATH_PREFIX) -> None:
        super().__init__()
        self._guarded_prefix = guarded_prefix

    def wrap_tool_call(self, request, handler):
        name = request.tool_call["name"]
        if name not in _GUARDED_TOOLS:
            return handler(request)

        args = request.tool_call["args"]
        raw_path = args.get("file_path", "")
        try:
            # §2 — 모델이 보낸 원시 경로가 아니라, 실제 도구 본문과 같은
            # 정규화 함수를 재사용해 정규화된 경로로 비교한다.
            normalized_path = validate_path(raw_path)
        except ValueError:
            # 경로 자체가 무효하면 write_guard의 관심사가 아니다 — 도구
            # 본문이 어차피 같은 오류를 낼 것이므로 그대로 넘긴다.
            return handler(request)

        if not normalized_path.startswith(self._guarded_prefix):
            return handler(request)

        text_to_check = (
            args.get("content", "") if name == "write_file" else args.get("new_string", "")
        )
        category = _match_category(text_to_check)
        if category is None:
            return handler(request)

        # 매칭된 원문(비밀번호·주민번호 값 자체)은 오류 메시지에 절대
        # 옮기지 않는다 — ToolMessage는 그대로 대화 기록(메시지 히스토리)에
        # 남으므로, 여기 원문을 넣으면 "저장은 막았지만 대화 로그에는
        # 남는" 모순이 생긴다. 카테고리 이름만 알려준다.
        return ToolMessage(
            content=(
                f"이 내용은 저장하지 않았습니다 — {_CATEGORY_LABELS[category]}"
                "이(가) 포함된 것으로 보입니다. 개인 장기 메모리에는 "
                "credential·개인정보·권한/보안 관련 서술을 저장하지 않습니다. "
                "다른 방식으로 표현해서 다시 시도할 수 있습니다."
            ),
            tool_call_id=request.tool_call["id"],
            name=name,
            status="error",
        )


def build_memory_write_guard(
    *, guarded_prefix: str = MEMORY_USERS_PATH_PREFIX
) -> MemoryWriteGuardMiddleware:
    return MemoryWriteGuardMiddleware(guarded_prefix=guarded_prefix)
```

### 배선 지점 — `factory.py`, Root 분기의 `memory_provider is not None` 조건 안

`MiddlewareFactory.build()`가 반환하는 `custom_middleware`는 Root/Child가
공유하므로 거기 넣지 않는다. 대신 `factory.py`의 `build()`가 이미
"`memory_provider`가 있을 때만 Root에 메모리 관련 kwargs를 채우는" 자리
(`root_kwargs.update(...)` 바로 그 조건문)에 같이 넣는다.

```python
root_kwargs: dict[str, Any] = {}
root_middleware = custom_middleware
if self.memory_provider is not None:
    root_kwargs.update(
        memory=self.memory_provider.paths(),
        backend=self.memory_provider.backend(...),
        store=self.memory_provider.store(),
        memory_system_prompt=self.memory_provider.system_prompt(),
    )
    root_middleware = [*custom_middleware, build_memory_write_guard()]
...
return create_root_graph(
    ...,
    middleware=root_middleware,
    **root_kwargs,
)
```

Child 분기(`create_child_graph`)는 그대로 `custom_middleware`만 쓴다 —
바꾸지 않는다.

## 4. 한계 — 정직하게 남겨 둔다

- **여러 번의 `edit_file`에 걸쳐 쪼개서 넣으면 각 호출은 통과할 수 있다.**
  예를 들어 API 키를 두 번의 `edit_file`로 절반씩 나눠 적으면, 각 호출의
  `new_string`만 보면 패턴에 안 걸린다. 이건 어떤 per-call 패턴 검사로도
  원천적으로 막기 어렵다(파일 전체를 매번 다시 읽어 검사하면 막을 수는
  있지만, 그 경우도 여러 파일에 걸쳐 쪼개면 다시 못 잡는다) — 완전한
  방어가 아니라 "명백한 경우를 잡는 안전망"이라는 `2026-08-19_02`의 원래
  전제를 그대로 유지한다.
- **전화번호 패턴은 오탐 가능성이 있다.** 사용자가 "제 번호는 010-...
  입니다, 이걸로 리마인더 보내주세요" 같은 정당한 요청을 해도 패턴에
  걸릴 수 있다. 개인정보를 카테고리째 보수적으로 막는다는 방향과 일치하는
  선택이지만, 실제로 걸어 보고 오탐이 너무 잦으면 이 패턴만 빼는 것도
  고려할 수 있다.
- **권한/보안 키워드는 문맥 없이 문자열 포함 여부만 본다.** "저는 이
  시스템 관리자입니다"처럼 자기소개성 문장도 걸릴 수 있다 — 카테고리
  자체를 진위와 무관하게 막기로 한 결정(`2026-08-19_02`)의 의도된 결과다.
- **모델이 추론한 사실·프로젝트 한정 사실·1회성 결과는 이 미들웨어가
  전혀 못 잡는다.** 문자열 형태로 판단할 수 있는 범위 밖이라 처음부터
  이 미들웨어의 대상이 아니다 — `_MEMORY_ROUTING_PROMPT`(이미 코드 반영·
  테스트 완료, `2026-08-19_03` §8-(1))가 그 몫을 담당한다.

## 5. 테스트 계획

`tests/test_memory_write_guard.py`(신규). `Mock`으로 `request`/`handler`를
만드는 패턴은 `test_memory_backend.py`가 이미 쓰는 방식을 재사용한다.

- 대상 도구가 아니면(`read_file`, `ls` 등) 검사 없이 `handler(request)`를
  그대로 호출·반환하는지.
- `/memories/users/` 밖 경로(`/memories/users/`가 아닌 임의 경로)면
  통과하는지.
- 경로 표기가 다르지만 정규화하면 `/memories/users/`로 떨어지는 경우
  (`"memories/users/preferences.md"`, `"/memories//users/preferences.md"`)
  도 걸리는지 — §2에서 발견한 문제의 회귀 테스트.
- `validate_path`가 `ValueError`를 내는 경로(`"../etc/passwd"`류)는
  write_guard가 관여하지 않고 `handler(request)`로 넘기는지.
- `write_file`의 `content`에 API 키 형식이 있으면 `handler`를 **호출하지
  않고** `ToolMessage(status="error")`를 바로 반환하는지(호출 여부는
  `handler` mock의 `assert_not_called()`로 확인).
- `edit_file`의 `new_string`에 주민등록번호 패턴이 있으면 막히는지 —
  `old_string`에만 있고 `new_string`에는 없으면 통과하는지(의도된 동작 —
  §1 근거).
- "관리자 권한이 있다"류 문장이 사실 여부와 무관하게 막히는지.
- 정상적인 개인 선호 문장("한국어로 답해줘")은 통과하는지.
- 거부 사유 `ToolMessage.content`에 매칭된 원문 값이 그대로 노출되지
  않는지(카테고리 이름만 있는지) — §3 코드 주석의 의도가 실제로 지켜지는지
  확인하는 회귀 테스트.
- Root 그래프 조립 시(`factory.py`) `memory_provider`가 있을 때만
  `MemoryWriteGuardMiddleware`가 middleware 목록에 포함되고, 없을 때나
  Child 그래프에는 포함되지 않는지.
