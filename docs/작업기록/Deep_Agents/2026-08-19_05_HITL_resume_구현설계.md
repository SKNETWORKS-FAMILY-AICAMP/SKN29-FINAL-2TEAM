# HITL resume API — 새 엔진 자기 승인 재개, 설계와 구현 (2026-08-19)

> 이 문서는 `2026-08-13_04_작업자B_실행코어_세부계획.md`의 "0순위"를 구현하며
> 쓴 기록이다. `services/agent_runtime/events.py`의 interrupt 처리 코드가
> 이 문서 이름을 그대로 가리키고 있다.

## 0. 요약

새 엔진(`services.agent_runtime`)에서 side_effect 도구(`task_register` 등)를
모델이 호출하면 `HumanInTheLoopMiddleware`가 그래프를 멈추고 사람 승인을
기다린다. 이 기능 자체는 이미 있었다(`_hitl_structural_check.py`가 그래프
레벨에서 검증). 문제는 **그 위에서 실제로 재개할 방법이 코드에 없었다는
것** — 승인 대기 이벤트를 화면에 전달하는 경로도, 재개를 요청하는 API도,
멈춘 실행을 다시 여는 그래프 조립 경로도 전부 없었다. 승인 대기 상태로
멈춘 실행은 스트림이 조용히 끝나고, 그 실행은 영원히 그 상태로 남았다.

이번 작업으로 이 경로를 전부 채웠다: interrupt를 이벤트로 바꾸는 코드,
재개를 요청하는 `executor.resume()`, 그걸 부르는 API 엔드포인트, 그리고
멈춘 실행의 DB 상태(`agent_run.status`)를 정확히 추적하는 로깅까지.

## 1. 왜 깨져 있었는가 (근거)

LangGraph의 `interrupt()` 메커니즘을 실제 설치된 소스로 추적했다.

- `map_output_updates()`(`langgraph/pregel/_io.py`)는 `INTERRUPT` 채널에
  쓴 값을 이 함수가 만드는 일반 "updates" 청크에서 **애초에 걸러낸다.**
- 대신 `output_writes()`(`langgraph/pregel/_loop.py`, 약 1416-1447행)가
  `self._emit("updates", lambda: iter([{INTERRUPT: interrupts}]))`로
  **완전히 분리된 자기만의 청크**를 낸다.
- 즉 interrupt가 나는 턴의 "updates" 이벤트는 `{"__interrupt__": (Interrupt(...),)}`
  모양이지, 다른 노드 이름과 같은 딕셔너리에 섞이지 않는다.

우리 `EventMapper.convert()`의 기존 루프는 `node_output`이 dict가 아니면
(interrupt 값은 `tuple[Interrupt, ...]`) 건너뛰는 구조였다 — 이 키를 아예
모르니 빈 리스트만 반환하고 스트림은 그대로 끝났다. 화면에는 카드도 오류도
없이 아무 일도 없었던 것처럼 보였지만, 실제로는
`HumanInTheLoopMiddleware`가 그래프를 멈춰 둔 채였다. 재개할 API 자체도
없었으니 그 실행은 그 상태로 영원히 멈춰 있었다.

`HumanInTheLoopMiddleware.after_model()`(설치된 `langchain` 소스,
`langchain/agents/middleware/human_in_the_loop.py` 399-486행)를 읽고 재개
계약을 확인했다:

- 모델 노드 1턴에 걸린 side_effect tool_call **전부**를 한 번에 모아
  `interrupt(hitl_request)`를 **딱 한 번만** 부른다 — tool_call마다 따로
  interrupt하지 않는다.
- `hitl_request = {"action_requests": [...], "review_configs": [...]}`.
- `decisions = interrupt(hitl_request)["decisions"]` — 재개 값은
  `{"decisions": [...]}` 모양이어야 하고, `len(decisions)`이 그 턴의
  `action_requests` 개수와 정확히 같아야 한다. 다르면 `ValueError`.
- `Decision`은 `{"type": "approve"}` / `{"type": "reject", "message": ...}` /
  edit / respond 넷 중 하나다.

## 2. 설계

### 2.1 범위(MVP)

- **자기 승인만.** 팀장이 자기 요청을 자기가 승인하는 경우만 다룬다.
  "팀원이 요청 → 팀장이 승인"하는 교차 역할 라우팅은 별도의 제품 결정이
  필요해 범위 밖으로 미뤘다.
- **approve/reject만.** `edit`/`respond`는 다루지 않는다 — 지금 화면에
  그 결정을 입력할 UI가 없다.
- **턴 전체에 같은 결정.** 한 턴에 side_effect tool_call이 여러 개면(모델이
  병렬로 부르면) 전부에 같은 결정을 적용한다. 항목별 부분 승인(레거시
  확인 카드의 `selected`처럼)은 아직 없다 — §5 한계 참고.

### 2.2 이벤트 규격

`EVENT_AWAITING_CONFIRMATION = "awaiting_confirmation"` — 레거시
`services.harness.runner`의 동명 상수와 **의도적으로 같은 문자열**이다.
`EVENT_ERROR`/`EVENT_RESULT`가 이미 이렇게 하고 있는 것과 같은 이유:
`ChatMessageRepository.latest_pending_confirmation()`과
`apps/chat/api_views.py`의 `_history()`/`_relay()`가 이 문자열 하나로 두
엔진을 가리지 않고 같은 분기를 타야 하기 때문이다. import로 상수를
공유하지 않고 값만 맞춘다 — 레거시와 새 엔진은 서로의 내부 구현을 몰라도
되게 분리하되, 화면·DB로 나가는 문자열 계약만 맞춘다.

```
{
    "type": "awaiting_confirmation",
    "run_id": ...,
    "agent_id": ...,
    "agent_version_id": ...,
    "interrupt_id": ...,       # 지금은 턴에 하나뿐이라 안 써도 되지만,
                                # 나중에 병렬 interrupt를 지원하면 필요해진다
    "action_requests": [...],  # 화면이 확인 카드를 그리는 데 필요한 전부
    "complete": False,
}
```

### 2.3 재개 API

`executor.resume(agent_id, agent_version_id, context, decisions, draft=None,
tool_refs_override=None)` — `run()`과 조립 규칙(로더, `tool_refs_override`
적용, factory 조립)은 완전히 같다. 다른 점 셋:

1. `context.run_id`가 **이미 있어야 한다**(멈췄던 그 실행의 run_id) — 없으면
   `ValueError`. 새로 발급하면 그 run_id로 이미 열어 둔 `agent_run` 행을
   못 찾는다.
2. `EVENT_AGENT_STARTED`를 안 낸다 — "새로 시작"이 아니라 "이어서 진행"이라
   새 `agent_run` 행을 또 만들면 안 된다(run_id PK 충돌).
3. `stream_adapter.stream(resume={"decisions": [...]}, thread_id=...)`을
   부른다 — `user_input`/`conversation_messages`는 무시된다.

`DeepAgentStreamAdapter.stream()`은 `resume` 파라미터가 있으면
`Command(resume=resume)`을 입력으로 그래프에 보낸다(langgraph 자신의
`interrupt()` docstring 예제와 같은 방식). `thread_id` 없이 재개하는 건
의미가 없어 `ValueError`로 막는다 — langgraph 자신도 checkpointer 없는
`Command(resume=...)`을 같은 이유로 막는다(`pregel/_loop.py` `_first()`,
"Cannot use Command(resume=...) without checkpointer").

### 2.4 DB 상태 — `agent_run.status`에 `PENDING` 추가

interrupt로 멈춘 실행은 끝난 게 아니라 재개를 기다리는 것뿐이다 —
`FAILED`로 잘못 기록하면 평가 로그가 실패로 센다. `agent_run.status`는
`VARCHAR(20) NOT NULL DEFAULT 'RUNNING'`이고 CHECK 제약이 없다(`DB/schema.sql`
확인) — 마이그레이션 없이 새 값을 추가할 수 있다. `tool_call.status`가
이미 같은 뜻으로 `'PENDING'`을 쓰고 있어(선기록 패턴) 새 어휘를 만들지
않고 그 값을 재사용했다.

`AgentRunRepository.suspend(run_id)` — `finish()`와 다르게 `ended_at`을
안 채운다. `_suspend_run()`이 `EVENT_AWAITING_CONFIRMATION`을 보면 이걸
부르고, 그 스트림의 `open_run_ids`에서도 뺀다(이 스트림 기준으로는 더
"열려" 있지 않다 — `finally`의 `_close_orphans()`가 이걸 `FAILED`로 잘못
정리하면 안 된다).

### 2.5 `trace_events()`의 재개-스트림 문제와 `known_run_ids`

`trace_events()`를 부를 때마다 `open_run_ids = set()`으로 새로 시작한다 —
호출 하나에 국한된 메모리 상태다. 재개 스트림은 `EVENT_AGENT_STARTED`를
다시 안 내므로(§2.3), 이 새 호출은 멈췄던 실행의 run_id를 전혀 모른 채
시작한다 — `EVENT_RESULT`/`EVENT_ERROR`가 와도 `_finish_root_run()`이
"내가 시작한 run이 아니다"로 보고 그 `agent_run` 행을 닫지 못한다. 그
행은 interrupt 시점에 `PENDING`으로 남은 채 영원히 안 닫힌다.

`trace_events(events, *, context, known_run_ids=())`로 이 run_id를 미리
채워 넣을 수 있게 했다 — `_resume_deep_agent()`가
`trace_events(raw_events, context=context, known_run_ids=(run_id,) if
run_id else ())`로 호출한다.

## 4. 검증

### 4.1 구조 검증 스크립트 (`_hitl_structural_check.py`)

기존에 있던 스크립트다 — 결정론적 가짜 모델로 `task_register`를 무조건
호출하게 만들고, `graph.invoke()` → interrupt 확인 → `Command(resume=...)`
→ handler 호출 여부를 직접 확인한다.

Postgres를 재시작한 뒤 처음 돌렸을 때 `interrupted_before_execution: False`로
**실패했다.** 원인을 진단해 보니, 이 스크립트가 매 실행마다 같은 결정론적
`thread_id`(`f"hitl-struct-{decision}"`)를 재사용하고 있어서, 이전 실행들이
남긴 **오래된 체크포인트**가 Postgres에 그대로 쌓여 있었다(`checkpoints`
테이블에서 `hitl-struct-approve`/`hitl-struct-reject` 두 thread_id에 각각
27개, 25개 행 확인). 새로 `graph.invoke()`를 부르면 그 오래된(이미 완료된)
체크포인트 상태에서 이어지므로, 가짜 모델이 "이미 `task_register`가
불렸다"고 보고 interrupt 없이 바로 답만 냈다 — 내 코드가 아니라 **테스트
스크립트 자체의 상태 오염**이었다. 별도로 새 `thread_id`("dbg-1")로 같은
그래프 조립 로직을 직접 재현했더니 `has interrupt: True`로 정상 동작함을
먼저 확인해 이 가설을 뒷받침했다.

`checkpoints`/`checkpoint_blobs`/`checkpoint_writes`에서 그 두 thread_id의
행을 지우고 다시 돌리니 정상 통과했다:

```
=== decision=approve ===
승인 대기 상태로 멈췄는가(먼저 실행 안 됐는가): True
승인 요청 시점까지 실제 handler 호출 횟수: 0
재개(resume) 이후 실제 handler 호출 횟수: 1

=== decision=reject ===
승인 대기 상태로 멈췄는가(먼저 실행 안 됐는가): True
승인 요청 시점까지 실제 handler 호출 횟수: 0
재개(resume) 이후 실제 handler 호출 횟수: 0

=== PASS ===
```

이 스크립트는 `graph.invoke()`/`Command(resume=...)`을 직접 부른다 —
내가 이번에 짠 `events.py`/`stream_adapter.py`/`executor.py` 코드를
거치지 않는다. 즉 이 결과는 "LangGraph의 interrupt 메커니즘 자체가
살아 있다"는 걸 확인해 줄 뿐, "내 새 코드가 그 이벤트를 올바르게
집어 들어 화면까지 전달하는가"는 별도로 확인해야 한다 — §4.2가 그것이다.

**교훈**: 이 스크립트는 결정론적 thread_id를 재사용하는 한, 두 번째
실행부터는 항상 이렇게 실패할 수 있다. 스크립트 자체를 매번 새
thread_id를 쓰게 고치는 건 이번 범위 밖이라 손대지 않았다 — 다시 돌릴
일이 있으면 위 DELETE로 그 thread_id의 체크포인트를 지우고 돌리거나,
스크립트를 실행마다 다른 thread_id를 쓰게 바꿔야 한다는 걸 여기 남겨
둔다.

## 5. 한계 (정직하게 기록)

- **자기 승인만.** 팀원 요청 → 팀장 승인 흐름은 없다.
- **approve/reject만.** edit/respond 미지원.
- **턴 전체에 같은 결정.** 한 턴에 side_effect tool_call이 여러 개면(드묾)
  전부 같은 결정이 적용된다 — 레거시 확인 카드의 항목별 부분 승인
  (`selected`)에 대응하는 기능이 새 엔진에는 아직 없다. 필요해지면
  `decision`을 화면에서 리스트로 받게 넓히면 된다 — 프레임워크
  (`HumanInTheLoopMiddleware`) 쪽 제약은 이미 없다(애초에 `decisions`가
  리스트다).
- **`_hitl_structural_check.py`는 결정론적 thread_id를 재사용한다.** 두
  번째 실행부터 오래된 체크포인트로 오탐 실패할 수 있다(§4.1). 스크립트
  자체를 고치는 건 이번 범위 밖으로 남겨 뒀다.
