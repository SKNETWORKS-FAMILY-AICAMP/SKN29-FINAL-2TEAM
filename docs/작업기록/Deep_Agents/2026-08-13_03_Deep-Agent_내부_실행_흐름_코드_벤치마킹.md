# Agent Harness 내부 흐름 — Deep Agents 오픈소스 코드 벤치마킹

이 문서는 실제 코드를 짤 때 참고하기 위한 함수 호출 흐름 정리입니다. 코드 전체를 옮겨 적지 않고, 어떤 함수가 무엇을 호출하고 다음에 어디로 넘어가는지, 예외가 나면 어디로 가는지, 재시도는 몇 번인지만 정리했습니다. 모든 항목에 실제 GitHub 출처를 남겼습니다.

## 표기 규칙

**근거 표시**
- [확인됨] — 아래 고정 커밋의 실제 소스를 fetch해서 코드로 직접 확인
- [부재확정] — 아래 고정 커밋의 해당 조립 경로 소스를 직접 읽고 이 메커니즘이 없다는 걸 확인. **"이 프로젝트 전체에 없다"가 아니라 "이 조립 경로에는 없다"는 뜻**이며, 범위를 항상 같이 적음
- [확인불가] — 이번 조사 범위 밖이라 못 찾아본 것. 없다는 뜻이 아니라 안 봤다는 뜻
- [OpenCode참고] — Deep Agents 계열엔 없지만 OpenCode에 실제 구현이 있어 벤치마킹 가능
- [제안] — 오픈소스 사실이 아니라 우리 팀이 판단해서 정하는 값/설계

**층 구분** (모든 절 제목에 표시)
- [기본] — `create_deep_agent()`를 인자 없이 호출해도 자동으로 켜져 있음
- [선택] — LangChain/Deep Agents가 제공하지만 `middleware=[...]`에 우리가 명시적으로 추가해야 켜짐
- [우리구현] — 프레임워크 어디에도 없어서 새로 설계해야 함

## 1. 전체 조립 구조 — `create_deep_agent()`

`create_deep_agent()`는 자체 그래프를 만들지 않습니다. 미들웨어 스택을 조립한 뒤 `langchain.agents.create_agent()`를 그대로 호출해서 컴파일된 LangGraph를 받아옵니다(langgraph의 구식 `create_react_agent`가 아니라 langchain v1의 신규 미들웨어 기반 factory).

**실제 미들웨어 조립 순서**(`deepagent_middleware` 리스트가 채워지는 순서, `graph.py` 그대로):

```
1. Skills(선택)              — skills 인자가 있을 때만
2. Filesystem                — 항상
3. SubAgent(해당 시)          — inline_subagents가 있을 때만
4. create_summarization_middleware(model, backend)  — 항상, 인자 없어도 자동
5. PatchToolCalls             — 항상
6. AsyncSubAgent(해당 시)     — async_subagents가 있을 때만
   ── 여기까지가 "core" 구간, 아래 _apply_custom_middleware()가 이 core 리스트 바로 뒤에
      사용자 middleware를 스플라이스함 ──
7. 사용자가 넘긴 middleware=[...] (커스텀)
8. harness profile의 extra_middleware
9. provider별 prompt-caching 미들웨어(Anthropic 항상, Bedrock/Fireworks는 해당 패키지 설치 시)
10. Memory(해당 시)           — memory 인자가 있을 때만
11. HumanInTheLoopMiddleware(해당 시) — interrupt_on 인자가 있거나, permissions에 mode="interrupt" 규칙이 있을 때
12. ToolExclusion(해당 시)    — harness profile이 excluded_tools를 지정했을 때, 항상 맨 마지막
```

```python
create_deep_agent(model, tools, system_prompt, middleware, subagents, permissions, memory, skills,
                   interrupt_on, backend, response_format, context_schema, checkpointer, store, ...)
  └─ return create_agent(
         model, system_prompt=final_system_prompt, tools=_tools,
         middleware=deepagent_middleware,   # 위 1~12 순서로 조립된 리스트
         response_format=..., context_schema=..., checkpointer=checkpointer, store=store, ...,
         state_schema=state_schema or DeepAgentState,
     ).with_config({"recursion_limit": 9_999, "metadata": {...}})
```

`TodoListMiddleware`는 이 조립 목록 어디에도 없습니다 — `graph.py` 전체에서 `TodoListMiddleware`가 등장하는 곳은 주석 1건뿐이고 import·인스턴스화 둘 다 없습니다. 이건 "v0.7부터 기본이 아니게 됐다"는 버전 연혁 주장이 아니라, **위 고정 커밋(`217b9eb3`)의 `create_deep_agent()` 조립 경로에는 없다**는 사실만 확인된 것입니다. `langchain.agents.create_agent()`가 내부적으로 이걸 추가하는지는 [확인불가](이번 조사 범위 밖).

## 2. 그래프 구조

핵심 실행 노드는 `"model"`과 `"tools"` 두 개뿐입니다. 하지만 활성화된 미들웨어가 `before_agent`/`before_model`/`after_model`/`after_agent` 훅을 구현하면, **그 훅마다 별도의 그래프 노드가 추가**됩니다(예: `TodoListMiddleware.after_model`을 구현하면 `"TodoListMiddleware.after_model"`이라는 독립 노드가 생김). 즉 "그래프는 model/tools 두 노드뿐"이라는 말은 실행 흐름의 핵심 경로를 가리키는 것이지, 실제 컴파일된 그래프의 노드 개수와는 다릅니다.

```python
# factory.py — 핵심 두 노드
graph.add_node("model", RunnableCallable(model_node, amodel_node))
if tool_node is not None:
    graph.add_node("tools", tool_node)

# after_model 훅을 구현한 미들웨어마다 별도 노드 추가
if (m.__class__.after_model is not AgentMiddleware.after_model
    or m.__class__.aafter_model is not AgentMiddleware.aafter_model):
    graph.add_node(f"{m.name}.after_model", RunnableCallable(sync_after, async_after))
```

`loop_exit_node`(한 iteration의 끝)는 `after_model` 훅이 있으면 그 마지막 노드, 없으면 `"model"` 자신입니다. "tools"로의 조건부 라우팅은 항상 이 `loop_exit_node`에서 평가되므로, **"model" 노드가 끝나고 활성 `after_model` 노드들이 전부 실행된 뒤에야 "tools" 노드로 갈지가 결정**됩니다.

출처: [factory.py](https://github.com/langchain-ai/langchain/blob/c5b2f95b5e26169548398d5d8ec6b9d963af9cc8/libs/langchain_v1/langchain/agents/factory.py)

## 3. 종료·라우팅 조건 (`_make_model_to_tools_edge`)

"tools" 노드로 갈지, 종료할지, 모델로 되돌아갈지는 아래 함수 하나가 전부 결정합니다.

```python
# factory.py _make_model_to_tools_edge 내부, 실제 순서 그대로
def model_to_tools(state):
    # 1. state에 jump_to가 있으면(미들웨어가 강제 지정, 예: ToolCallLimitMiddleware의 exit_behavior="end") 최우선으로 따름
    if jump_to := state.get("jump_to"):
        return _resolve_jump(...)

    last_ai_message, tool_messages = _fetch_last_ai_and_tool_messages(state["messages"])

    # 2. AIMessage 자체가 없으면(예: messages가 지워진 경우) 종료
    if last_ai_message is None:
        return end_destination

    # 3. tool_calls가 하나도 없으면 종료 — 가장 흔한 "직접 답변" 경로
    if len(last_ai_message.tool_calls) == 0:
        return end_destination

    # 4. 아직 응답(ToolMessage)이 안 붙은 tool_call만 골라 "tools" 노드로
    pending_tool_calls = [c for c in last_ai_message.tool_calls
                           if c["id"] not in tool_message_ids and c["name"] not in structured_output_tools]
    if pending_tool_calls:
        return [Send("tools", [tool_call]) for tool_call in pending_tool_calls]

    # 5. pending은 없는데 이번 호출에서 structured_response가 새로 생성됐으면 종료
    if state.get("structured_response") is not None:
        return end_destination

    # 6. tool_calls는 있지만 pending은 없다(=이미 ToolMessage가 채워짐, 인위적 주입 포함) → 모델로 되돌아감
    return model_destination
```

정리하면 다섯 갈래입니다.

```
tool_calls 없음                      → 종료 (일반적인 직접 응답)
미들웨어 jump_to="end"                → 종료 (강제)
structured_response 생성 완료         → 종료
AIMessage 자체가 없음                 → 종료
미처리(pending) tool_call 있음        → "tools" 노드로
tool_call은 있으나 pending 없음       → 모델로 재호출 (인위적 ToolMessage 주입된 경우 포함)
```

"pending_tool_calls가 없다"는 조건은 종료와 동일하지 않습니다 — pending이 없어도 tool_call 자체가 남아있고 structured_response도 없으면 6번 분기로 모델에 되돌아갑니다(Todo 병렬 호출 차단이 바로 이 경로, 4장 참고). Todo가 전부 done인지 여부는 이 라우팅 로직 어디에도 없고, 오직 LLM이 스스로 "더 부를 tool이 없다"고 판단해야만 1번 조건으로 종료됩니다.

`return_direct=True`로 지정된 tool이 있는 경우, "tools" 노드 이후의 라우팅은 별도 함수 `route_tool_responses`가 담당합니다: 마지막으로 실행된 tool이 `return_direct` tool이면 곧바로 종료, 아니면 모델로 되돌아갑니다.

## 4. Checkpointer / Super-step

체크포인트 저장은 노드 단위가 아니라 super-step 단위입니다. 한 super-step에서 병렬로 실행된 모든 task가 끝나면 `PregelLoop.after_tick()`이 `_put_checkpoint({"source": "loop"})`를 정확히 1회 호출합니다.

```
PregelLoop.tick()          # 이번 super-step의 task들 실행 (병렬 가능)
    ↓ (모든 task 완료)
PregelLoop.after_tick()
    ↓
PregelLoop._put_checkpoint({"source": "loop"})
    ↓
checkpointer.put() / aput()
```

`durability`는 컴파일된 그래프의 `.invoke()`/`.stream()` 호출 시점 파라미터입니다(`create_deep_agent()`의 파라미터 아님). `Literal["sync","async","exit"]`, 기본값 `"async"`.

```
sync  → 각 super-step의 checkpoint를 다음 step 시작 전에 동기적으로 persist
async → 각 super-step의 checkpoint를 다음 step과 동시에 비동기로 persist (기본값)
exit  → 중간 super-step에서는 persist하지 않고, 그래프(invoke 1회) 실행이 끝날 때만 persist
```

`durability="exit"`에서 중간에 죽으면 "대화 전체를 처음부터"가 아니라, **그 이전에 이미 저장된 마지막 checkpoint 시점**부터 재개됩니다(이전 turn들의 checkpoint는 그대로 남아있음. 다만 durability="exit"로 실행 중이던 그 turn 내부의 중간 super-step들은 저장 안 됐으므로 그 turn만 처음부터 다시 실행됨).

checkpoint는 실행 상태의 전부가 아니라 다섯 층으로 구분해야 합니다.

| 구분 | 의미 |
|---|---|
| State snapshot checkpoint | `_put_checkpoint()`가 만드는 전체 state의 시점별 스냅샷 |
| Super-step 중간의 pending writes | 한 super-step 안에서 병렬 노드 중 일부만 성공하면, 성공한 노드의 결과가 보존되어 재개 시 재실행 안 될 수 있음 |
| Interrupt 상태 | `interrupt()`로 정지된 지점 — resume 시 해당 노드 처음부터 재실행(6장) |
| Subgraph checkpoint namespace | Sub-agent(`task`) 실행 시 서브그래프가 부모와 네임스페이스를 어떻게 공유/분리하는지 — [확인불가], 7장 참고 |
| Tool의 외부 side effect | checkpoint와 같은 트랜잭션이 아님 — Tool이 외부 시스템(Jira 등)에 성공적으로 쓰기를 한 직후 checkpoint 저장이 실패하면, 재실행 시 같은 tool_call이 중복 실행될 수 있음 |

마지막 항목 때문에, "Write Tool은 자동 재시도 금지"만으로는 안전하지 않습니다. 다음은 [우리구현]이 필요합니다.
- 외부 Write Tool마다 idempotency key
- 재실행 시 이미 성공했는지 조회해서 중복 실행을 막는 방식
- side effect 성공 후 checkpoint 실패 시 처리 정책
- 승인(HITL) 후 재개 시 동일 tool_call을 그대로 재실행하는지, 이미 실행된 것으로 간주하는지

출처: [_loop.py — `PregelLoop`, `after_tick`, `_put_checkpoint`](https://github.com/langchain-ai/langgraph/blob/644815f9e5bc52ad8f7a5227a456227e9c3e639b/libs/langgraph/langgraph/pregel/_loop.py), [main.py — `durability` 파라미터](https://github.com/langchain-ai/langgraph/blob/644815f9e5bc52ad8f7a5227a456227e9c3e639b/libs/langgraph/langgraph/pregel/main.py), [LangGraph Persistence 공식 문서](https://docs.langchain.com/oss/python/langgraph/persistence) — pending writes 보존 동작

## 5. 예외 처리와 재시도

### 5-1. 그래프 노드 레벨 기본 재시도 [기본, 단 기본값이 꺼짐]

`RetryPolicy`가 LangGraph에 있지만 완전 opt-in입니다. `add_node(..., retry_policy=...)`의 기본값은 `None`이고, `create_deep_agent`/`create_agent`/`create_react_agent` 어디도 이 값을 넘기지 않습니다. **아무 설정을 안 하면 노드 레벨 자동 재시도는 0번입니다.**

```python
class RetryPolicy(NamedTuple):
    initial_interval: float = 0.5
    backoff_factor: float = 2.0
    max_interval: float = 128.0
    max_attempts: int = 3
    jitter: bool = True
    retry_on: ... = default_retry_on
    # ValueError/TypeError/ArithmeticError/ImportError/LookupError/NameError/
    # SyntaxError/RuntimeError/ReferenceError/StopIteration/OSError는 재시도 안 함(프로그래밍 오류로 간주)
```

출처: [types.py — `RetryPolicy`](https://github.com/langchain-ai/langgraph/blob/644815f9e5bc52ad8f7a5227a456227e9c3e639b/libs/langgraph/langgraph/types.py), [_retry.py — `default_retry_on`](https://github.com/langchain-ai/langgraph/blob/644815f9e5bc52ad8f7a5227a456227e9c3e639b/libs/langgraph/langgraph/_internal/_retry.py)

### 5-2. Tool 실행 중 예외 — 미들웨어 없이 기본 ToolNode만 쓸 때 [기본]

```
tool 함수 실행
  ├─ 인자 검증 실패(Pydantic ValidationError) → ToolInvocationError로 wrap
  │    └─ ToolMessage(status="error", content=e.message) 반환 (그래프 안 죽음)
  └─ tool 함수 본체가 던진 일반 Exception
       └─ isinstance 체크 실패 → raise e 그대로 재전파 → 그래프 크래시(미들웨어 없으면 여기서 끝)
```

### 5-3. ToolRetryMiddleware [선택 — `create_deep_agent()` 기본 스택엔 없음]

- `max_retries` 기본값 = 2(최초 시도 제외, 최대 총 3번 시도)
- 백오프: `delay = min(1.0 * 2.0 ** attempt, 60.0)`, jitter 기본 활성화(±25%)
- `retry_on` 기본값 = `(Exception,)`, `on_failure` 기본값 = `"continue"`(소진 시 `ToolMessage(status="error")`로 변환, `"error"`면 raise)
- `GraphBubbleUp`(interrupt 등 제어신호)은 재시도 대상에서 항상 제외

```
wrap_tool_call(request, handler):
  for attempt in range(max_retries + 1):
      try: return handler(request)
      except GraphBubbleUp: raise
      except retry_on 매칭 예외:
          마지막 시도면 → on_failure 처리
          아니면 → backoff 후 재시도
```

**재시도 횟수의 범위를 구분해야 합니다.** 위 수치는 미들웨어 내부의 물리적 재시도만을 의미하며, 시스템 전체 재시도와는 다른 층입니다.

```
physical_attempts_per_tool_call = ToolRetryMiddleware.max_retries + 1   # 미들웨어 내부, 기본 3회(추가 시)
semantic_tool_calls_per_run     = 오류 ToolMessage를 본 LLM이 같은 tool을 다시 호출하기로 판단하는 횟수
model_provider_sdk_retries      = 모델 provider SDK 자체의 HTTP 재시도 (Deep Agents 재시도 아님)
run_retries                     = Graph 실행 자체가 실패했을 때 애플리케이션 계층 재실행 여부
```

`semantic_tool_calls_per_run`에 상한이 없으면 LLM이 같은 tool을 계속 다시 부를 수 있습니다. 이를 막는 방법은 하나가 아니라 여럿입니다 — `ToolCallLimitMiddleware`(5-4)가 그중 유력한 선택지 중 하나이고, 그 외에 전체 Run budget, tool별 idempotency/중복 감지, `recursion_limit`, 특정 오류에 대한 재호출 금지, 애플리케이션 계층 timeout도 같은 목적에 쓰일 수 있습니다. 실제로는 이 중 여러 개를 같이 두는 게 일반적입니다.

출처: [tool_retry.py](https://github.com/langchain-ai/langchain/blob/c5b2f95b5e26169548398d5d8ec6b9d963af9cc8/libs/langchain_v1/langchain/agents/middleware/tool_retry.py), [_retry.py](https://github.com/langchain-ai/langchain/blob/c5b2f95b5e26169548398d5d8ec6b9d963af9cc8/libs/langchain_v1/langchain/agents/middleware/_retry.py)

### 5-4. ToolCallLimitMiddleware [선택]

- 파라미터: `tool_name`(None=전체, 카운트 키는 `tool_name or "__all__"`), `thread_limit`, `run_limit`(`run_limit > thread_limit`이면 `ValueError`, 둘 다 `None`이어도 `ValueError`)
- `exit_behavior`(`Literal["continue","error","end"]`, 기본 `"continue"`): `"continue"`=초과분만 error ToolMessage 주입 나머지 통과, `"error"`=`ToolCallLimitExceededError` raise, `"end"`=`jump_to="end"`로 즉시 종료
- 훅: `after_model` — 모델이 tool_calls를 낸 직후, 실제 tool 실행 전에 카운트/차단 결정
- ToolRetryMiddleware의 재시도 횟수는 이 카운터에 전혀 반영되지 않음(한 tool_call은 몇 번 재시도되든 1건으로 집계)

### 5-5. 미들웨어 체이닝 순서

`create_agent(middleware=[A, B, C])` → 리스트 앞쪽이 바깥쪽(outer), 뒤쪽이 안쪽(inner). 요청은 A→B→C→tool, 응답은 tool→C→B→A. 재시도(`ToolRetryMiddleware`)와 최종 에러 캐치(`ToolErrorMiddleware`, 선택)를 같이 쓸 때: `ToolErrorMiddleware`를 outer, `ToolRetryMiddleware(on_failure="error")`를 inner에 둬야 재시도 소진 후 예외가 outer까지 전파됨.

## 6. Todo Flow [기본 아님 — `create_deep_agent()`엔 없음. LangChain의 `TodoListMiddleware`를 우리가 직접 추가해야 함]

### 6-1. 클래스/훅

`TodoListMiddleware`는 정확히 4개 훅을 구현: `wrap_model_call`/`awrap_model_call`(시스템 프롬프트에 `WRITE_TODOS_SYSTEM_PROMPT` 주입), `after_model`/`aafter_model`(병렬 write_todos 호출 검증). `after_model`은 `"model"` 노드와 `"tools"` 노드 사이에 위치하는 **별도의 그래프 노드**입니다(2장).

### 6-2. write_todos 툴

- 스키마: `WriteTodosInput{todos: list[Todo]}`, `Todo = TypedDict{content: str, status: Literal["pending","in_progress","completed"]}`
- 반환: `Command(update={"todos": todos, "messages": [ToolMessage(...)]})` — state의 `todos` 키를 전체 교체(diff 아님), 순수 CRUD, LLM 호출 없음
- 함수 내부에 malformed status 등에 대한 커스텀 validation 없음(pydantic 타입 체크에만 의존)
- "동시에 여러 개 in_progress 허용"이 프롬프트에 명시됨 — 관련 없고 병렬 가능한 task라면 여러 개 in_progress 가능

### 6-3. 병렬 write_todos 차단 — 정확한 순서와 메커니즘

LLM이 write_todos를 2개 이상 병렬 호출한 경우, 실행 순서는 다음과 같습니다.

```
"model" 노드: LLM이 write_todos 2개 이상 병렬 호출
  ↓ (동기적으로, "tools" 노드 진입 전에)
"TodoListMiddleware.after_model" 노드:
  write_todos 호출이 2개 이상인가? → 예
  → 각 write_todos tool_call_id에 매칭되는 error ToolMessage를 state.messages에 추가
    (AIMessage.tool_calls 리스트 자체는 건드리지 않고 그대로 둠)
  ↓
조건부 edge(3장의 model_to_tools):
  pending_tool_calls = [tool_call_id가 아직 ToolMessage 없는 것들만]
  → write_todos 2개는 방금 error ToolMessage가 붙었으므로 pending에서 자동 제외됨
  → 다른 정상 tool_call이 있으면 그것만 "tools" 노드로 Send
  → 없으면 model 노드로 되돌아감("tools" 노드는 거치지 않음)
```

`_write_todos` 함수 본문은 이 경우 실행되지 않고, `state["todos"]`도 갱신되지 않습니다. `jump_to`를 쓰는 게 아니라, "이미 응답(에러)이 달린 tool_call은 pending에서 제외된다"는 3장의 라우팅 필터링만으로 실행이 차단됩니다. 거부되는 Todo가 먼저 저장되는 일은 없습니다.

출처: [todo.py — `TodoListMiddleware.after_model`](https://github.com/langchain-ai/langchain/blob/c5b2f95b5e26169548398d5d8ec6b9d963af9cc8/libs/langchain_v1/langchain/agents/middleware/todo.py)

[확인불가]: `ContextEditingMiddleware`/`SummarizationMiddleware`가 `todos` state를 실제로 읽거나 건드리는지.

## 7. HITL 승인 흐름

### 7-1. HumanInTheLoopMiddleware [선택 — `interrupt_on`을 직접 넘기거나, `permissions`에 `mode="interrupt"` 규칙이 있을 때만 자동 설치됨]

```python
HumanInTheLoopMiddleware(
    interrupt_on: dict[str, bool | InterruptOnConfig],
    description_prefix: str = "Tool execution requires approval",
)
```

`interrupt_on`은 tool 이름 정확히 일치(exact key)로만 등록 — wildcard/glob 패턴 매칭 미지원(`interrupt_on.get(tool_call["name"])` 단순 dict 조회). `InterruptOnConfig` 필드: `allowed_decisions`(필수), `description`, `args_schema`(미사용, 주석에 "미래 작업"), `when`(인자 값 기반 조건부 콜백).

### 7-2. 훅과 정지 메커니즘

```
after_model(state):
  마지막 AIMessage.tool_calls 순회
  interrupt_on에 등록된 tool만 골라서:
    decisions = interrupt(hitl_request)["decisions"]   # GraphInterrupt 예외 raise, 그래프 정지
    (재개 시 이 노드 처음부터 다시 실행됨)
  각 decision 처리:
    approve → tool_call 그대로, 정상 실행
    edit    → tool_call.args를 edited_action으로 교체(id 유지), 정상 실행
    reject  → 실행 안 함, status="error" ToolMessage 합성 주입
    respond → 실행 안 함, status="success" ToolMessage(사람이 대신 답변) 합성 주입
```

`interrupt()`는 checkpointer 필수 — 없으면 `Command(resume=...)` 시점에 `RuntimeError`가 명시적으로 raise됩니다. 재개는 `Command(resume={"decisions":[...]})`로 동일 `thread_id`에.

## 8. Sub-agent 위임 흐름 (task tool)

### 8-1. 등록 [기본 — subagents를 하나도 안 넘겨도 general-purpose 서브에이전트가 자동 추가되어 사실상 항상 존재]

`SubAgentMiddleware.__init__`은 `subagents`가 비어있으면 `ValueError`, 있으면 `self.tools = [task_tool]`을 생성자에서 고정 등록(훅이 아님). `create_deep_agent`는 기본적으로 "general-purpose" 서브에이전트를 자동 추가하므로, 사용자가 명시적으로 끄지 않는 한 `task` 툴은 항상 존재합니다.

스키마: `TaskToolSchema{description: str(필수), subagent_type: str(필수)}` — 이 두 필드만 모델에 노출.

### 8-2. 서브에이전트 상태 초기화

```python
subagent_state = {
    k: v for k, v in parent_state.items()
    if k not in _EXCLUDED_STATE_KEYS and k not in private_state_keys
}
subagent_state["messages"] = [HumanMessage(content=description)]
```

완전 격리가 아닙니다 — `messages`/`todos`/`structured_response`만 제외하고, 부모 state의 나머지(공유 파일시스템 backend 상태 등)는 그대로 넘어갑니다. system_prompt는 서브에이전트 자체 spec 값 사용(독립). tools는 spec에 명시되면 그것, 없으면 부모 tools를 그대로 상속. permissions는 spec에 명시되면 **완전 대체(REPLACE)**, 없으면 부모 상속.

```python
subagent_permissions = spec.get("permissions", permissions)  # 교집합 아님, dict.get(key, default)
```

→ 부모보다 넓은 권한을 가질 수 있는 구조입니다. `graph.py` 자체 주석: "permissions field, which replaces the parent's rules entirely."

### 8-3. 실행과 결과 반환

```
task 호출 (description, subagent_type)
  → subagent_type 없는 타입이면 → 예외 아님, 에러 문자열을 모델에 그대로 반환
  → subagent_state 구성(8-2)
  → subagent.invoke(subagent_state, subagent_config)  # 예외 시 별도 try/except 없이 그대로 전파
  → 결과 패키징: structured_response 있으면 json 직렬화, 없으면 마지막 non-empty AIMessage.text
  → Command(update={**state_update(공유 backend 상태만), "messages":[ToolMessage(...)]})
  → 부모 LLM 재호출
```

서브에이전트의 중간 tool_call/tool_result는 부모 대화 컨텍스트에 전혀 안 남음(context quarantine). 공유 backend 상태(파일 등)는 부모에게 병합되어 넘어감. LangSmith에는 `ls_agent_type="subagent"` 태그로 별도 run 기록이 남음(observability 계층에는 남되 conversational context엔 없음).

### 8-4. Depth 제한 [부재확정: `subagents.py`에 없음]

재귀 깊이 카운터가 전혀 없습니다. 기본 구성에서는 서브에이전트 자신에게 `SubAgentMiddleware`가 안 붙어서 구조적으로 재귀가 막히는 것뿐, 명시적 depth guard 코드는 없습니다. 사용자가 직접 서브에이전트 spec의 `middleware`에 `SubAgentMiddleware`를 넣으면 무한 재귀가 이론상 가능합니다. 유일한 안전장치는 `recursion_limit`(deepagents 기본 9,999 — 그래프 스텝 수 제한이지 서브에이전트 중첩 깊이 전용 카운터가 아님).

[OpenCode참고]: depth=1을 강제하려면 아래 패턴을 벤치마킹할 수 있습니다.

```typescript
// packages/opencode/src/tool/task.ts
let current = parent
let depth = 0
while (current.parentID) {
  depth++
  current = sessions.get(current.parentID)
}
if (depth >= (cfg.subagent_depth ?? 1)) {
  return Effect.fail(new Error(`Subagent depth limit reached (${cfg.subagent_depth ?? 1})`))
}
```

매 `task` 호출마다 세션의 부모 체인을 실시간으로 거슬러 올라가며 깊이를 세고, 설정된 한도(기본 1) 초과 시 도구 호출 자체를 에러 처리합니다. OpenCode는 서브에이전트 ruleset에 `task` 권한이 명시적으로 없으면 기본 `task: deny`를 주입하는 이중 방어도 갖고 있습니다.

- `operations` 분류는 `Literal["read", "write"]` 두 종류뿐(7-3 참고), edit은 write에 포함

### 9-2. MemoryMiddleware [선택 — `memory` 인자를 넘겨야 스택에 들어감]

LangGraph Store/namespace 기반이 아닙니다. `AGENTS.md` 같은 파일을 backend에서 읽어 시스템 프롬프트에 주입하는 구조이며, Store 개념 자체가 이 코드에 없습니다.

- 훅: `before_agent`, `wrap_model_call`(시스템 프롬프트에 주입)
- **로드 조건은 "세션당 1회"가 아니라 정확히 이 코드입니다**:
  ```python
  def before_agent(self, state, runtime, config):
      if "memory_contents" in state:
          return None
      ...
  ```
  즉 state에 `memory_contents` 키가 이미 있으면 스킵하고, 없으면 로드합니다. 시간이나 세션 개념이 아니라 state/checkpointer 생명주기에 종속됩니다 — checkpointer가 state를 계속 이어받으면 재로드 안 되고, state가 초기화되면 다시 로드됩니다.
- 쓰기: `MemoryMiddleware` 자체는 쓰기를 수행하지 않음 — 프롬프트로 "새 지식은 `edit_file`을 호출해 저장하라"고 지시할 뿐. 실제 쓰기는 `FilesystemMiddleware`의 `edit_file` 툴이 수행
- 충돌 처리: 락/버전 체크/병합 로직 전혀 없음, `os.O_TRUNC`로 단순 덮어쓰기 — "last-write-wins가 의도적으로 구현됨"이 아니라 "동시성 제어가 아예 없어서 결과적으로 그렇게 보이는 것"

출처: [memory.py — `before_agent`](https://github.com/langchain-ai/deepagents/blob/217b9eb372fa51b0439434f31abc3ac22e6cd7f2/libs/deepagents/deepagents/middleware/memory.py), [backends/filesystem.py](https://github.com/langchain-ai/deepagents/blob/217b9eb372fa51b0439434f31abc3ac22e6cd7f2/libs/deepagents/deepagents/backends/filesystem.py)

[확인불가]: Agent/User/Org-scoped 다중 네임스페이스 Memory는 LangGraph `Store`/`BaseStore` API 자체를 봐야 함 — 이번 조사는 deepagents의 MemoryMiddleware(파일 기반)만 다룸.

### 9-3. SkillsMiddleware [선택 — `skills` 인자를 넘겨야 스택에 들어감]

- 훅: `before_agent`(SKILL.md frontmatter만 파싱해 name/description/path 메타데이터만 저장, 본문 미로드, 같은 이름이면 뒤 source가 덮어씀), `wrap_model_call`(스킬 목록을 시스템 프롬프트에 주입)

## 10. Summarization

세 가지를 구분해야 합니다: (A) LangChain 원본 클래스 자체의 동작, (B) Deep Agents가 그걸 감싼 자체 래퍼의 동작, (C) `create_deep_agent()`가 실제로 무엇을 기본 결선하는지. 이 셋이 서로 다릅니다.

### 10-1. (A) LangChain 원본 `SummarizationMiddleware`

- 훅: `before_model`
- `RemoveMessage(id=REMOVE_ALL_MESSAGES)`로 `state["messages"]`를 전체 삭제한 뒤 `[요약 HumanMessage, ...최근 유지 메시지]`로 재구성 — **state를 직접 mutate**
- 기본값: `trigger=None`(직접 인스턴스화해서 아무 설정도 안 하면 절대 발동 안 함), `keep=("messages", 20)`
- 요약 모델: 생성자 필수 파라미터, `.with_retry()`로 자체 최대 3회 재시도

이 (A)는 `deepagents` 패키지가 아니라 `langchain` 패키지에 있는 클래스이며, **`create_deep_agent()`는 이 클래스를 직접 스택에 넣지 않습니다.**

출처: [summarization.py](https://github.com/langchain-ai/langchain/blob/c5b2f95b5e26169548398d5d8ec6b9d963af9cc8/libs/langchain_v1/langchain/agents/middleware/summarization.py)

### 10-2. (B) Deep Agents 자체 래퍼(`_DeepAgentsSummarizationMiddleware`)

`create_deep_agent()`가 실제로 스택에 넣는 건 이 클래스입니다. (A)와 훅부터 다릅니다.

- 훅: `wrap_model_call`/`awrap_model_call`만 구현 — `before_model`은 구현하지 않음
- 내부에 (A)의 인스턴스를 `self._lc_helper`로 보유하고, 요약 판단(`_should_summarize`)·생성 로직만 위임(컴포지션)
- **`state["messages"]`를 직접 건드리지 않습니다.** 대신 `_summarization_event`라는 private state 필드에 요약 결과를 기록하고, 그 모델 호출 하나에 한해 `request.override(messages=...)`로 압축된 메시지를 넘김:
  ```python
  update: dict[str, Any] = {"_summarization_event": new_event}
  if new_state_tail:
      update["messages"] = list(new_state_tail)
  return ExtendedModelResponse(model_response=response, command=Command(update=update))
  ```
- 밀려난 원본 대화는 삭제되지 않고 backend에 markdown으로 오프로드됨: `/conversation_history/{thread_id}.md`
- 클래스 자체 docstring이 (A)와의 차이를 명시: "Unlike the legacy `before_model` approach, this does NOT modify the LangGraph state. Instead, it tracks summarization events in middleware state... LangChain rewrites it with `RemoveMessage(id=REMOVE_ALL_MESSAGES)` from `before_model`."

출처: [middleware/summarization.py — `_DeepAgentsSummarizationMiddleware`, `wrap_model_call`, `SummarizationState._summarization_event`](https://github.com/langchain-ai/deepagents/blob/217b9eb372fa51b0439434f31abc3ac22e6cd7f2/libs/deepagents/deepagents/middleware/summarization.py)

### 10-3. (C) `create_deep_agent()`의 실제 기본 결선 [기본]

개발자가 summarization 관련 인자를 하나도 안 넘겨도, `create_deep_agent()`는 내부적으로 항상 `create_summarization_middleware(model, backend)`를 호출해서 (B)를 스택에 넣습니다.

```python
# graph.py — 인자 없이도 무조건 호출됨
deepagent_middleware.extend([create_summarization_middleware(model, backend), PatchToolCallsMiddleware()])
```

`compute_summarization_defaults(model)`의 정확한 기본값:

```python
if has_profile:   # model.profile에 max_input_tokens가 정수로 존재
    trigger = ("fraction", 0.85)
    keep    = ("fraction", 0.10)    # 컨텍스트의 정확히 10% — 메시지 개수 아님
else:              # profile 정보 없음 — 보수적 고정값
    trigger = ("tokens", 170_000)
    keep    = ("messages", 6)
```

즉 실전에서 `create_deep_agent()`를 쓰면 요약은 (A)의 `trigger=None`(꺼짐)이 아니라 위 값으로 기본 켜져 있고, 훅도 `before_model`이 아니라 `wrap_model_call`이며, state를 직접 지우는 게 아니라 `_summarization_event`로 관리됩니다.

출처: [graph.py](https://github.com/langchain-ai/deepagents/blob/217b9eb372fa51b0439434f31abc3ac22e6cd7f2/libs/deepagents/deepagents/graph.py), [middleware/summarization.py — `create_summarization_middleware`, `compute_summarization_defaults`](https://github.com/langchain-ai/deepagents/blob/217b9eb372fa51b0439434f31abc3ac22e6cd7f2/libs/deepagents/deepagents/middleware/summarization.py)

### 10-4. 미들웨어 조립 순서의 라벨 정정

"Harness Profile Middleware"/"Provider Prompt Caching Middleware"는 실재하는 단일 클래스명이 아닙니다.
- `HarnessProfile`은 미들웨어가 아니라 `base_system_prompt`/`excluded_tools`/`excluded_middleware`/`extra_middleware` 등을 담은 데이터클래스이고, 그 안의 `extra_middleware`가 실제로 append됨
- "Provider Prompt Caching"은 단일 클래스가 아니라 `append_prompt_caching_middleware()` 함수가 provider별로 `AnthropicPromptCachingMiddleware`(무조건)/`BedrockPromptCachingMiddleware`(langchain-aws 설치 시)/`FireworksPromptCachingMiddleware`(langchain-fireworks 설치 시) 중 해당하는 걸 골라 append
- 커스텀 미들웨어(`middleware=[...]`)는 core 구간(1장 1~6번) 바로 뒤, harness-profile 파생 미들웨어/prompt-caching/Memory/HITL보다 앞에 스플라이스됨
- `_ToolExclusionMiddleware`(실제 클래스명, private)만 정확히 맨 마지막에 append됨

출처: [graph.py](https://github.com/langchain-ai/deepagents/blob/217b9eb372fa51b0439434f31abc3ac22e6cd7f2/libs/deepagents/deepagents/graph.py), [profiles/harness/harness_profiles.py](https://github.com/langchain-ai/deepagents/blob/217b9eb372fa51b0439434f31abc3ac22e6cd7f2/libs/deepagents/deepagents/profiles/harness/harness_profiles.py)

## 13. Run Snapshot — 이건 프레임워크 사실이 아니라 우리 제안입니다

`Checkpointer thread state에 agent_version/model/toolset/permission을 별도 필드로 pin`하는 아이디어는 [제안]이며, 검증된 권장 방식이 아닙니다. 다음 이유로 checkpoint state와 완전히 분리된 별도 audit record로 관리하는 방안도 함께 비교해야 합니다.

- checkpoint 정리·삭제 정책과 audit 보존 정책이 다를 수 있음(checkpoint는 오래되면 지워도, 감사 기록은 남겨야 할 수 있음)
- 하나의 thread에 여러 Run이 생길 수 있음(Run 경계와 checkpoint 경계가 다를 수 있음)
- Run마다 model/toolset/permission 버전이 다를 수 있음(Agent가 대화 중간에 재배포되는 경우)
- snapshot은 실행 중 변경되면 안 되는 immutable record에 가까운데, checkpoint state는 매 super-step 갱신되는 mutable 구조라 성격이 다름

두 방안(checkpoint state에 필드로 pin vs 별도 audit 테이블)을 실제 요구사항(재현성, 삭제 정책, 조회 패턴) 기준으로 비교한 뒤 결정해야 합니다.

## 14. 전체 함수 호출 그래프

```
create_deep_agent()
  └─ create_agent()  [langchain.agents.factory]
       └─ StateGraph{ "model", "tools", (활성 미들웨어별 before_agent/before_model/after_model/after_agent 노드) }

            "model" 노드 (model_node / amodel_node)
              ↓
            활성 after_model 노드들 순차 실행 (예: TodoListMiddleware.after_model)
              ↓
            model_to_tools 라우팅(3장):
              jump_to 있음        → 강제 종료/이동
              AIMessage 없음      → 종료
              tool_calls 없음     → 종료 (직접 답변)
              pending_tool_calls  → "tools" 노드로 Send
              structured_response 생성됨(pending 없음) → 종료
              그 외(pending 없음) → "model" 노드로 재호출

            "tools" 노드 (ToolNode, wrap_tool_call 체인 — 아래는 ToolRetryMiddleware를 추가했을 때의 예시. 기본 스택엔 없음)
              각 tool_call에 대해:
                ToolRetryMiddleware.wrap_tool_call:
                  for attempt in range(max_retries+1 = 3):
                    try: 실제 tool 함수 실행
                    except GraphBubbleUp: raise (재시도 대상 아님)
                    except retry_on 매칭 예외:
                      마지막 시도면 → on_failure 처리
                      아니면 → backoff 후 재시도
              실행 끝나면(return_direct 없으면) "model" 노드로 loop-back

       durability(sync/async는 매 super-step마다 persist, exit는 실행 종료 시점에만 persist) — PregelLoop.after_tick
```

## 15. 확인불가 종합 목록 (추후 재조사 대상)

- checkpointer.put()/aput()의 concrete DB(SQLite/Postgres) 구현 세부
- `durability="sync"`의 정확한 블로킹 지점
- Sub-agent 서브그래프가 부모와 checkpoint 네임스페이스를 어떻게 공유/분리하는지
- `ContextEditingMiddleware`/`SummarizationMiddleware`가 `todos` state를 실제로 건드리는지
- `AsyncSubAgentMiddleware`(원격/LangSmith 배포 서브에이전트) 내부 구현
- `FilesystemPermission` 규칙의 정확한 매칭/우선순위 평가 알고리즘
- LangGraph `Store`/`BaseStore` API 자체(Agent/User/Org 다중 네임스페이스 Memory 설계에 필요)
- MCP 서버 연결 → tools 목록 매핑 어댑터 계층
- `langchain.agents.create_agent()`가 `TodoListMiddleware`를 내부적으로 추가하는지

## 16. 이 문서만으로는 부족한 운영·보안 설계 항목 (전부 [우리구현])

- Run/thread/user-turn의 정확한 생명주기(하나의 Run이 여러 turn을 걸치는지, thread_id와 run_id 관계)
