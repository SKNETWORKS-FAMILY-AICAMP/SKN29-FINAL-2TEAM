# 2026-08-21_04 — MCP 동시 쓰기: 직렬화 대신 경고

## 1. 이 문서의 결론

`2026-08-20_02_에이전트_병렬실행_설계.md` §5.2가 제안한 "같은 MCP 서버
호출을 advisory lock으로 직렬화"를 **폐기하고**, 대신 "동시 실행 중인
호출이 있으면 승인 카드에 경고를 띄우고 판단은 사람에게 맡긴다"로
바꾼다.

1. MCP 서버가 동시 접속을 못 받는 게 아니다 — 이건 기술적 제약이 아니라
   "동시 요청이 안전한지 우리가 모른다"는 정보 부족 문제다. 정보 부족은
   기다리게 한다고 해결되지 않는다.
2. 그래서 직렬화(기다리게 하기) 대신, 아는 사실("지금 같은 서버에 다른
   실행이 진행 중이다")만 정직하게 보여주고 진행 여부는 승인하는 사람이
   정하게 한다.
3. 이 방식은 아무도 기다리지 않으므로, `2026-08-21_01`이 걱정했던
   "advisory lock을 쥔 채 최대 8분간 DB 커넥션을 붙잡는 문제"가 애초에
   생기지 않는다.
4. 부수 효과로, "MCP는 read/write를 몰라서 전부 다 줄 세운다"는 문제도
   같이 없어진다 — 이제 아무것도 줄을 서지 않으므로 조회 도구가
   불필요하게 느려질 이유가 없다.
5. 내장 side-effect Tool과 개인 메모리 쓰기는 기존 advisory lock 방식을
   그대로 유지한다 — 그건 우리가 코드를 아는 로컬 도구라 lock을 오래
   쥘 일이 없다. 바뀌는 건 MCP뿐이다.
6. **(2026-08-21 정정)** 실제 `HumanInTheLoopMiddleware` 소스를 확인한
   결과, DB 표시판(§3.1)만으로는 "같은 배치(한 AIMessage)에 함께
   요청된 MCP 쓰기끼리 부딪히는 경우"를 못 잡는다 — 승인 전이라 아직
   아무것도 "활성"으로 기록되지 않기 때문이다. §3.2에서 `state`를 직접
   훑어 같은 배치 내 충돌도 추가로 잡는다.
7. **(2026-08-21 정정)** 표시판 삽입/삭제는 raw MCP handler가 아니라
   `factory.py`의 `_run()` wrapping 레이어(A-3의 idempotency 기록과
   같은 자리)에서 한다 — raw handler에는 `run_id`/`tool_call_id`가
   넘어가지 않는다(§3.1).

## 2. 원래 제안이 왜 다시 검토됐나

`2026-08-20_02` §5.2는 "MCP 서버가 동시 쓰기를 안전하게 처리하는지 모르니
안전한 쪽으로 통째로 줄 세운다"고 결정했었다. 이 결정 자체를 사용자가
다시 물었다 — "접속을 줄 세워야만 하는 이유가 뭔가, 문제는 쓰기·수정
같은 특정 동작 아닌가, 그럼 다른 사용자가 이미 하고 있다는 걸 HITL로
알려주고 승인받으면 안 되나."

이 질문에 답하려고 원래 전제부터 다시 짚었다.

- MCP 서버는 보통 HTTP 기반이고, 동시 접속을 여러 개 받는 게 정상이다.
  "연결 하나만 허용"은 프로토콜 제약이 아니다.
- 진짜 모르는 건 "그 서버가 노출하는 특정 동작(예: 같은 문서에 동시에
  쓰기)이 경합에 안전한가"다. 이건 `tools/list` 응답만으로는 절대 알 수
  없다(`2026-08-20_01` §3, `2026-08-20_02` §3.2와 동일한 결론).
- "모르니까 기다리게 한다"는 안전해 보이지만, 사실 기다린다고 이 정보
  부족이 해결되는 게 아니다 — 그냥 위험을 미루는 것뿐이다. 반면
  `2026-08-21_02`/`2026-08-21_03`에서 이미 두 번 택한 방향("숨기지 않고
  알려주고, 판단은 사람에게 둔다")을 여기도 적용하면, 위험을 미루지
  않고 그 자리에서 사람이 정보를 갖고 판단하게 만들 수 있다.

## 3. 새 설계 — 활성 호출 표시판

### 3.1 무엇을 기록하나

새 테이블(가칭 `mcp_active_calls`)에 "지금 이 MCP 서버에 진행 중인 호출"
목록만 짧게 적었다 지운다.

```text
mcp_server_id   -- 어떤 MCP 서버 연결인지
run_id          -- 어느 실행인지
tool_call_id    -- 어느 tool_call인지
started_at      -- 시작 시각
```

핸들러가 시작할 때 한 행을 넣고(수 ms), 끝나면(성공·실패·timeout 모두)
그 행을 지운다(수 ms). `tool_call_idempotency`(`2026-08-21_03` §2)와 같은
성격 — DB 연결을 여는 즉시 쓰고 바로 닫으며, 절대 그 호출이 끝날 때까지
연결을 붙잡지 않는다.

**중요**: 이 행을 지우는 코드는 우리 timeout 미들웨어가 아니라 **`_run()`
wrapping 레이어**(`services/agent_runtime/factory.py`의
`_IdempotencyAwareTool._run()` — A-3의 idempotency `record_result()`가
이미 이 자리에서 돈다, `2026-08-21_03` §2)가 실제 handler 호출을
감싸는 형태로 가져야 한다(2026-08-21 정정 — 원래 "handler 자신"이라고
썼던 건 raw MCP handler로 오해될 수 있어 정정한다. raw handler에는
`run_id`/`tool_call_id`가 넘어가지 않는다). `2026-08-21_01` §6에서 이미
확인했듯 timeout이 나도 백그라운드 스레드는 계속 돈다 — `_run()`은 우리
timeout 미들웨어와 별개로 그 스레드 안에서 끝까지 실행되므로, 실제로
끝날 때 자기 행을 지워야 우리가 포기한 뒤에도 표시판이 정확하게
유지된다.

### 3.2 같은 배치 안에서 동시에 요청된 것도 잡는다(2026-08-21 추가)

§3.1의 표시판은 **이미 실행이 시작된** 호출만 기록한다. 그런데 Root가
한 턴에 같은 MCP 서버를 쓰는 side-effect 호출을 2개 이상 함께 요청하면,
`HumanInTheLoopMiddleware.after_model()`이 그 tool_call들의 승인 카드를
전부 같은 시점에 만든다 — 이 시점엔 어느 쪽도 아직 승인 전이라 실행을
시작하지 않았으므로, §3.1의 DB 조회만으로는 서로를 못 잡는다.

```text
Root가 같은 턴에 MCP 쓰기 2개 요청 (같은 MCP 서버)
  → 카드 A 생성: 표시판 조회 → 아직 아무도 "활성" 아님 → 경고 없음
  → 카드 B 생성: 표시판 조회 → A도 아직 "활성" 아님(승인 전) → 경고 없음
  → 사용자가 둘 다 승인 → 그제서야 동시 실행 시작 (경고 없이)
```

이건 실제로 실측한 `HumanInTheLoopMiddleware.after_model()`(설치된
`langchain` 소스)로 확인했다 — `InterruptOnConfig`의 `description`
콜백은 `(tool_call, state, runtime)`을 받는데, `state["messages"]`에
지금 처리 중인 AIMessage의 `tool_calls`가 전부 들어 있다. 그러므로 DB
조회 없이, 이 콜백 안에서 `state`의 같은 AIMessage 안 다른 tool_call들의
MCP 서버 ID를 직접 훑어 "지금 같이 승인 요청된 것 중에도 같은 서버가
있는지"를 추가로 확인한다 — §3.1(DB 표시판, 다른 run·이미 시작된 호출용)
과 이 체크(같은 배치, state 안에서 직접 비교) 둘 다 있어야 §3.4가 말하는
범위를 다 덮는다.

### 3.3 언제 조회하나

HITL 승인 카드를 만들 때, 이 tool_call이 쓰려는 `mcp_server_id`로
①§3.1의 활성 호출 표시판과 ②§3.2의 같은 배치 내 다른 tool_call을 모두
확인한다. 자기 자신의 tool_call_id는 제외하고, 둘 중 하나라도 있으면
카드에 경고를 붙인다.

```text
[승인 대기] jira_create_issues(...)
⚠ 다른 실행이 지금 같은 MCP 서버에 쓰기 작업을 진행 중입니다.
   그래도 진행하시겠습니까?
```

### 3.4 오래된 행 처리

프로세스가 죽는 등으로 지우기 코드가 못 도는 경우를 대비해, 조회할 때
`started_at`이 너무 오래된 행은 무시한다. 기준은 `2026-08-21_01`이 이미
정한 gunicorn 절대 한도(600초)를 그대로 쓴다 — 그보다 오래 "활성"인
행은 실제로는 이미 죽은 실행이 남긴 찌꺼기로 본다. 별도 정리(cleanup)
작업 없이 조회 시점에 필터링만 하면 된다.

```sql
WHERE started_at > now() - interval '600 seconds'
```

### 3.5 범위 — 같은 run 안의 병렬 Child도 포함

다른 사용자·다른 run뿐 아니라, **같은 Root가 두 Child를 병렬로 띄워서
같은 MCP 서버에 동시에 쓰는 경우**도 같은 경고를 띄운다. 위험의 성격이
같기 때문이다(둘 다 "내가 모르는 동시 쓰기가 같은 대상에 일어난다").
`run_id`가 같은지 다른지는 조회 조건에서 구분하지 않는다 — `mcp_server_
id`가 같으면 무조건 검사한다. §3.2(같은 배치)의 "같은 AIMessage 안"과
§3.1(표시판)의 "이미 시작된 다른 run" 둘 다 이 범위에 포함된다.

## 6. 이 설계가 풀지 않는 것

- 여러 side-effect 도구가 섞여 병렬 승인됐다가 일부만 성공하는 경우의
  뒷정리(롤백/보정) — 이건 이 표시판과 무관한 별개 문제로 남아 있다.
- 표시판 자체의 정확성 — "활성"이라고 표시돼도 실제로 그 handler가
  여전히 유효한 작업을 하고 있는지(예: 이미 응답만 못 받았을 뿐 실제
  작업은 끝났을 수도 있음)까지는 알려주지 않는다. 정직하게 "동시에
  뭔가 진행 중이었다"는 사실만 보여준다.
