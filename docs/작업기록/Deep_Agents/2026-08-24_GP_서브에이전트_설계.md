# 웹/문서 검색 반복 문제 — 재설계 (측정 우선, 단계적 도입)

## 이 문서의 위치

`2026-08-24_03_서브에이전트_분리_실험설계_및_구현설계.md`(이하 "기존 설계")를 대체한다. 기존 설계가 세운 문제의식(§0의 "긴 반복이 컨텍스트를 채운다")은 유효하지만, 그 문제의식을 뒷받침한다고 인용한 근거 일부가 실측과 어긋났고, 검증 안 된 가설 위에 상당히 무거운 구조(카탈로그, exclusive 바인딩, 로그 매핑)를 곧바로 확정한 순서도 재검토가 필요했다. 이 문서는 같은 문제를 다시 정의하고, 실측 가능한 가장 싼 단계부터 순서대로 쌓는 방식으로 다시 설계한다.

## 0. 기존 설계에서 다시 확인한 사실들

착수 전에 코드와 외부 근거를 다시 맞춰봤다. 결과는 이렇다.

- **`web_search`에 재검색을 강제하는 코드 루프는 없다.** `services/harness/registry.py`의 `_web_search(*, query: str)`는 Tavily에 HTTP POST 한 번(`services/websearch/client.py`)을 보내고 끝난다. 결과가 부족하다고 판단해서 다시 부를지는 전적으로 그 도구를 호출한 에이전트(LLM)의 판단이다. `document_search`도 같은 구조다.
- **"100번까지 갈 수 있다"는 위기감의 근거는 web_search 전용 카운터가 아니었다.** `runtime_policy.py`의 `general_purpose_max_tool_calls=100`은 GP가 그 실행에서 부르는 **모든** 도구 호출을 합친 상한이다. web_search만 반복해서 이 상한에 닿는 시나리오는 가능하지만, 그게 일반적이라는 근거는 없다.
- **Tavily 응답은 이미 작게 잘려 있다.** `MAX_RESULTS=5`, `SNIPPET_CHARS=700` — 결과 하나가 문서 한 건을 통째로 읽는 것과는 크기 자체가 다르다.
- **Anthropic 자신의 web_search 서버 도구도 별도 에이전트가 아니라 평범한 도구다.** `tools`에 하나 넣어두면 모델이 한 턴 안에서 판단해 여러 번(단순 질의 1~3회, 비교·다중 개체 리서치는 10회 이상) 부르고, 상한은 `max_uses`라는 단순 카운터 하나로만 건다. ([Web search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool))
- **deepagents 자체 가이드도 "간단하고 단일 단계인 작업, 오버헤드가 이득보다 클 때는 서브에이전트를 쓰지 말라"고 명시한다.** 서브에이전트로 격리할 근거는 "중간 결과가 커서 부모 컨텍스트를 채우는가"다. ([Subagents — deepagents docs](https://docs.langchain.com/oss/python/deepagents/subagents))
- **실제 호출 횟수 분포는 지금 아무 데이터도 없다.** `_web_search`/`_document_search` 어디에도 호출 횟수를 세거나 로그로 남기는 코드가 없다. 기존 설계 §6도 이 데이터가 필요하다고 스스로 인정했지만, 그 데이터를 만드는 단계 없이 §3에서 exclusive 서브에이전트 구현을 먼저 제시했다.

결론: "긴 반복이 GP 컨텍스트를 위협할 수 있다"는 문제의식 자체는 기각할 근거가 없다. 다만 "그러니 지금 바로 전담 서브에이전트로 격리해야 한다"는 결론으로 건너뛸 근거는 부족하다. 사이에 있는, 훨씬 싸고 검증 가능한 단계들을 먼저 밟는다.

## 1. 설계 원칙

1. **측정 없이 구조를 바꾸지 않는다.** 구조 변경은 실측 데이터가 그 필요를 보여준 다음에만 한다.
2. **가장 싼 해법부터 시도한다.** 같은 위험을 인프라 없이 막을 수 있으면 인프라를 만들지 않는다.
3. **단순 질의의 비용을 늘리지 않는다.** 검색 한 번으로 끝나는 요청이 위임이라는 추가 왕복을 매번 지불하게 만들지 않는다.
4. **되돌릴 수 있는 순서로 쌓는다.** 각 단계는 이전 단계를 깨지 않고, 다음 단계로 갈지는 그 단계의 데이터를 보고 다시 정한다.

## 2. 단계 1 — 호출 횟수 계측 (구조 변경 없음)

가장 먼저, 그리고 유일하게 지금 바로 해도 안전한 작업이다. `web_search`/`document_search`가 한 실행(run) 안에서 몇 번 불리는지부터 센다.

### 구현

`services/agent_runtime/tools/loader.py`가 이미 `run_id`를 도구 핸들러에 주입할 수 있다(`CONTEXT_PARAM` 테이블의 `"run_id": lambda context: context.run_id`). `_web_search`/`_document_search` 시그니처에 `run_id: str | None = None` 키워드 인자를 추가하기만 하면 별도 배선 없이 값이 들어온다.

```python
# services/harness/registry.py

def _web_search(*, query: str, run_id: str | None = None):
    logger.info(
        "web_search 호출 — run_id=%s, query=%r",
        run_id, query,
    )
    ...
```

`document_list`처럼 이미 반복이 아닌 걸로 판단해 카탈로그에서 뺀 도구는 계측 대상에서 제외한다 — 이 단계의 목적은 "반복이 의심되는 두 도구가 실제로 얼마나 반복되는가"이지 전체 도구 사용량 집계가 아니다.

이 로그(또는 `agent_run` 관련 테이블에 도구별 카운트를 남기는 얕은 집계)를 1~2주 실사용으로 쌓는다. 확인할 것:

- 한 run 안에서 `web_search`가 평균/중앙값/최댓값 몇 번 불리는가.
- `document_search`도 같은 지표.
- 상한(100)에 근접하거나 닿은 run이 실제로 있는가, 있다면 그 run에서 web_search/document_search가 전체 도구 호출의 몇 %를 차지했는가.

**이 단계는 구조를 하나도 바꾸지 않는다.** 로그 한 줄 추가가 전부라 배포 리스크가 없고, 이후 모든 판단의 근거가 된다.

## 3. 단계 2 — 도구 자체에 상한 (Anthropic `max_uses` 방식)

단계 1의 로그가 쌓이기 전이라도, "재검색이 끝없이 이어질까"라는 걱정 자체는 서브에이전트 없이 먼저 해소할 수 있다. Anthropic이 web_search에 쓰는 것과 같은 방식이다 — 도구 자체에 같은 run 안에서의 호출 횟수 상한을 건다.

### 구현 방향

`_web_search`가 이미 `run_id`를 받게 됐으니(단계 1), 같은 `run_id`로 이 도구가 이번 실행에서 몇 번째 호출인지 확인하고, 임계값(예: 5~8회 — Anthropic 문서가 보여준 "복잡한 리서치도 10회 안팎" 범위를 참고해 결정)을 넘으면 결과 대신 사유를 반환한다.

```python
def _web_search(*, query: str, run_id: str | None = None):
    if run_id and _exceeds_call_cap("web_search", run_id):
        return {
            "query": query,
            "results": [],
            "note": (
                "이번 요청에서 웹 검색을 이미 여러 번 시도했습니다. "
                "지금까지 찾은 내용으로 답하거나, 사용자에게 검색 범위를 더 "
                "좁혀 달라고 요청하세요."
            ),
        }
    ...
```

카운터 저장 위치는 기존 idempotency 기록(`ToolCallIdempotencyRepository`, `factory.py`의 `_to_langchain_tool`)이 이미 `(run_id, tool_ref)` 단위로 상태를 다루고 있으므로 같은 계열에 얹는 것이 자연스럽다 — 이 문서는 방향만 정하고 정확한 저장소는 구현 시점에 기존 코드와 맞춰 정한다.

**이 단계도 서브에이전트나 카탈로그가 전혀 필요 없다.** "100번까지 컨텍스트가 불어난다"는 최악의 시나리오를 원천적으로 차단하면서, 카탈로그가 요구했던 이름 충돌 규칙, exclusive/shared 트레이드오프, 로그 매핑(`CATALOG_SUBAGENT_IDENTITIES`) 같은 부가 복잡도를 하나도 지지 않는다.

## 4. 단계 3 — 그래도 필요하면: shared 서브에이전트 (exclusive 아님)

단계 1의 데이터가 "특정 유형의 요청에서 web_search/document_search가 반복적으로 여러 번(예: 평균 5회 이상) 불린다"를 실제로 보여줄 때만 이 단계로 간다. 이때도 기존 설계의 exclusive 바인딩을 기본값으로 삼지 않는다.

### 무엇이 다른가

기존 설계 §3은 카탈로그가 가져간 도구(`web_search`, `document_search`)를 Root/GP의 도구 목록에서 **완전히 제거**하고, 그래서 `description`을 "단순 질의도 포함"하도록 넓게 쓰라고 요구했다. 이게 단순 질의에도 위임 왕복을 강제하는 원인이었다.

이 재설계에서는 반대로 **공유(shared)를 기본값으로 삼는다.** `services/agent_runtime/factory.py`의 `build()`를 보면 Root의 도구 목록(`langchain_tools`)과 서브에이전트 목록(`subagents=[gp_spec, *compiled_children]`)은 독립적으로 조립된다 — 카탈로그 서브에이전트를 이 리스트에 추가하는 것과, `web_search`를 `langchain_tools`/`gp_read_only_tools`에서 빼는 것은 원래도 별개의 작업이었다. 지금 설계는 후자를 하지 않는다.

```python
# factory.py — build() 안, 기존 gp_spec 조립 이후

catalog_specs = [
    build_general_purpose_spec(
        middleware=self.middleware_factory.build_for_general_purpose(),
        system_prompt=WEB_RESEARCH_SYSTEM_PROMPT,
        description=WEB_RESEARCH_DESCRIPTION,  # "여러 라운드가 필요할 것 같은 리서치용" — 좁게 써도 된다
        tools=[t for t in langchain_tools if tool_ref_of(t) == "web_search"],
        name="web-research",
    ),
]

# root_tools/gp_read_only_tools에서 web_search를 빼지 않는다 — 그대로 둔다.
create_root_graph(
    ...,
    tools=langchain_tools,                          # web_search 그대로 포함
    subagents=[gp_spec, *catalog_specs, *compiled_children],
    ...,
)
```

이렇게 하면:

- 검색 한두 번으로 끝나는 단순 질의는 지금처럼 Root/GP가 `web_search`를 직접 불러 바로 끝낸다. 위임 왕복이 강제되지 않는다.
- Root가 스스로 "이 요청은 여러 라운드짜리 리서치가 될 것 같다"고 판단할 때만 `web-research`에 위임한다. 이 판단 자체가 이미 Root가 하는 일(어느 서브에이전트에 맡길지 고르는 것)의 연장선이라 새로운 종류의 판단이 추가되는 게 아니다.
- `description`을 기존 설계처럼 "모든 경우 포함"으로 넓힐 필요가 없다 — 도구가 Root/GP 손에 그대로 남아 있으므로, description이 좁아서 생기는 사각지대(§0에서 우려했던 "위임도 안 되고 직접 호출 경로도 없는" 상태)가 원천적으로 발생하지 않는다.

`document-research`도 같은 방식으로 필요하면 추가한다.

### 이 단계에서도 지키는 것

- 이름 충돌 시 팀이 명시적으로 등록한 Child가 우선한다는 규칙(기존 설계 §3)은 그대로 유지한다.
- 실행 기록에서 이 서브에이전트를 구분해야 한다는 문제의식(기존 설계 §4)도 유효하다 — `events.py`의 `_classify_parent_tool_calls()`가 `definition.subagents`(Child)를 alias로 찾는 구조를 그대로 재사용해 카탈로그 이름을 위한 매핑을 추가하는 방향은 그대로 가져간다.

## 5. 단계 4 — exclusive 전환은 별도 결정으로 미룬다

shared로 운영하다가, 실사용 로그에서 "Root가 직접 `web_search`를 부르고도 스스로 판단 없이 5번, 10번씩 반복하며 길을 잃는" 패턴이 실제로 관찰되면 그때 `web_search`를 Root/GP 목록에서 빼는 exclusive 전환을 검토한다. 이건 별도 관찰 항목으로 두고, 지금 이 설계 문서에서 미리 코드를 짜두지 않는다 — 필요가 확인되지 않은 코드를 미리 만드는 것이 애초에 재검토의 이유였다.

## 6. 무엇을 하지 않는가 (기존 설계 대비)

- **exclusive 바인딩을 기본값으로 두지 않는다.** shared로 시작한다.
- **description을 "모든 경우 포함"으로 넓게 쓰라고 강제하지 않는다.** 도구가 Root/GP에 남아 있으므로 좁게 써도 사각지대가 안 생긴다.
- **`task_extraction`/`task_register` 등 단발성 도구 묶음화는 검토하지 않는다** — 기존 설계가 이미 기각한 결론이고, 이번 재검토에서도 근거가 다르지 않다.
- **측정 데이터 없이 §4(exclusive 전환)를 실행하지 않는다.**

## 7. 실행 순서 요약

1. `run_id`를 `_web_search`/`_document_search`에 주입해 호출 횟수를 로그로 남긴다. (구조 변경 없음, 즉시 가능)
2. 로그가 쌓이기를 기다리는 동안, 또는 그와 별개로, 두 도구에 `max_uses`류 상한을 건다. (구조 변경 없음, Anthropic 방식 그대로)
3. 1의 데이터가 "반복이 실제로 잦다"를 보여주면, `web-research`/`document-research`를 shared 서브에이전트로 추가한다. Root/GP의 직접 호출 경로는 남긴다.
4. 3 이후에도 Root가 직접 호출 경로에서 길을 잃는 패턴이 로그로 확인되면, 그때 exclusive 전환을 별도로 재검토한다.

## 8. 참고 근거

- [Web search tool — Claude Platform Docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool) — `max_uses` 상한, 서버 도구로서의 반복 호출 패턴(단순 질의 1~3회, 복합 리서치 10회 이상).
- [Subagents — deepagents docs](https://docs.langchain.com/oss/python/deepagents/subagents) — 서브에이전트 사용/비사용 기준("간단하고 단일 단계인 작업, 오버헤드가 이득보다 클 때는 쓰지 않는다").
- `services/harness/registry.py`(`_web_search`, `_document_search`), `services/websearch/client.py`(`MAX_RESULTS`, `SNIPPET_CHARS`) — 지금 도구의 실제 크기와 반복 로직 부재.
- `services/agent_runtime/runtime_policy.py` — `general_purpose_max_tool_calls=100`이 도구 전용이 아니라 GP 전체 상한이라는 사실.
- `services/agent_runtime/factory.py`(`build()`) — Root의 `tools`(직접 호출 목록)와 `subagents`(위임 목록)가 독립적으로 조립되어, "서브에이전트를 추가하는 것"과 "직접 호출 경로를 빼는 것"이 원래 별개의 결정이라는 근거.
- `services/agent_runtime/tools/loader.py`(`CONTEXT_PARAM`) — `run_id` 등 컨텍스트 값을 도구 핸들러에 주입하는 기존 메커니즘, 단계 1의 계측이 새 배선 없이 가능한 이유.
