# 도구 묶음 서브에이전트 — 설계

## 왜 이렇게 만드는가

**GP가 Root의 모든 도구를 받아 길을 잃는 문제를 해결하기 위해, Root 도구를 묶은 기본 Subagent 카탈로그를 자동 생성한다.**

- 무거운 도구(웹 검색·문서 검색)는 검색→평가→재검색을 반복해야 해서 GP 컨텍스트를 계속 채운다. 반복 스텝이 길어질수록 "다음에 뭘 해야 하는지"를 잊는 위험이 커진다(METR: 4분짜리 작업은 거의 100% 성공, 4시간짜리는 10% 미만 — 원인은 지식 부족이 아니라 "긴 액션 시퀀스를 이어 붙이는 것 자체의 어려움").
- 이 도구들을 전용 프롬프트를 가진 별도 컨텍스트로 감싸면, 반복은 그 안에서만 일어나고 GP/Root는 압축된 결과만 받는다 — Anthropic 자체 멀티에이전트 리서치 시스템이 이 구조로 단일 에이전트 대비 90.2% 더 나은 성능을 냈다.
- **묶는 단위는 "도메인"이 아니라 "도구 하나하나"다.** 어떤 도구가 진짜로 반복 판단(검색어 refinement, 몇 번 더 부를지 결정)이 필요하면 그 도구만 독점적으로 묶는다. 관련 있어 보이는 옆 도구라도 그 자체로 판단이 단순한 단발성 호출이면 묶지 않고 Root/GP가 직접 쓰게 둔다 — 안 그러면 그 도구 하나만 필요한 질의도 불필요하게 에이전트를 거쳐야 한다.
- 이 기준을 통과하지 못하는 조합은 넣지 않는다 — §2 참고.
- **도구를 하나만 묶어도 끝이 아니다.** 그 도구가 카탈로그로 넘어가면 Root 손에서 완전히 사라지므로, 서브에이전트의 `description`이 그 도구가 커버하는 범위 전체(단발성 조회부터 반복 검색까지)를 담지 않으면 사각지대가 생긴다 — "복잡한 리서치가 필요할 때만 위임"처럼 좁게 쓰면, "어떤 문서 있는지 조회해줘" 같은 단순 질의를 Root가 "이건 위임 대상이 아니다"라고 잘못 판단할 수 있고, 그 도구를 쓸 다른 경로가 없으므로 질의 자체가 처리 불가능해진다. 도구를 여러 개 묶었을 때의 문제(불필요한 우회 한 단계)보다 이쪽이 더 심각하다 — 그건 비효율이고 이건 기능 손실이다. 그래서 `description`은 항상 "이 도구가 필요한 모든 경우"로 넓게 쓴다 — §2 각 항목에 반영.
- **"필요한 도구"와 "Root에서 뺄 도구"는 다른 개념이다.** 카탈로그 항목이 요구하는 도구(`required_tool_refs`)를 전부 Root/GP에서 뺄 필요는 없다 — 그 도구 자체가 반복 판단 없는 단발성 호출이면 Root/GP도 그대로 쓰게 둔다. 지금 카탈로그는 이미 이 원칙을 지키고 있다(`document-research`가 `document_search`만 요구·독점하고 `document_list`는 그대로 둔 것). 항목이 늘어나 도구를 여러 개 요구하게 되면, 그중 정말 반복 판단이 필요한 도구만 골라 독점시키고 나머지는 공유로 남겨야 한다 — "카탈로그가 요구하는 도구니까 전부 뺀다"는 식으로 일괄 처리하지 않는다.
- **독점(exclusive)과 공유(shared)는 트레이드오프다, 정답이 아니다.** `document_search`처럼 반복 판단이 실제로 필요한 도구를 독점시키면, 검색 한 번으로 끝나는 단순 질의도 위임 한 단계를 거쳐야 한다(비용). 반대로 Root도 직접 부를 수 있게 공유하면 단순 질의는 빨라지지만, Root가 그 도구로 스스로 검색을 반복하다 길을 잃는 경로가 다시 열린다(§0의 원래 문제로 회귀). 지금은 후자의 위험이 더 크다고 보고 독점을 기본값으로 둔다 — 다만 이건 추론만으로 확정할 문제가 아니라, 배포 후 실제 호출 로그로 "이 도구가 평균 몇 번 만에 끝나는지" 확인하고 재판단해야 한다(§6에 확인 항목 추가).

## 1. 복합 질의로 보는 설계 동작

> "웹 검색해서 문서 찾고 액션 아이템 추출해줘." (등록 요청은 없음)

Root의 판단은 아래 세 단계뿐이다.

1. Root → `web-research`: 웹 검색 반복은 그 안에서 끝나고 Root는 요약만 받는다.
2. Root → `document-research`: `document_search` 반복도 마찬가지로 요약만 받는다. (`document_list`는 이 질의에 필요 없으면 Root가 직접 부르지 않아도 그만이다 — 애초에 카탈로그가 가져가지 않은 도구다.)
3. Root가 직접 `task_extraction`을 호출해 액션 아이템을 추출한다. **등록 요청이 없으므로 `task_register`는 부르지 않는다** — 이 질의에 등록 관련 판단(순서, `required_role` 규칙)은 필요 없고, `task_extraction` 자체가 반복 판단이 없는 단발성 호출이라 애초에 카탈로그로 안 감쌌기 때문에 Root가 그냥 직접 부르면 된다.

만약 "회의록 붙여넣었으니 액션 아이템 추출하고 등록까지 해줘"였다면 3번 단계에서 Root가 `task_extraction` 다음에 사용자 확인을 받고 `task_register`까지 직접 호출한다 — 두 도구 다 Root 손에 그대로 있으므로 추가 위임 없이 이어진다. 승인 카드는 `HumanInTheLoopMiddleware`가 `side_effect` 플래그로 걸기 때문에 지금과 동일하게 뜬다.

**GP가 문서와 프로젝트 도구를 동시에 요구하는 질의는 어떻게 되는가**: "문서를 검토하고 프로젝트 업무량과 비교해서 일정 위험을 분석해줘" 같은 질의도 GP 혼자 끝까지 처리하는 게 아니다 — GP는 `document_search`가 없어도 상관없다. Root가 먼저 `document-research`에 위임해 문서 요약을 받고, 그다음 프로젝트 관련 조회(GP 위임 또는 Root 직접 호출)로 나머지를 처리한 뒤 Root가 두 결과를 종합한다. "GP 하나가 모든 도구를 갖고 한 번에 풀어야 한다"는 전제 자체가 이 설계와 안 맞는다 — Root가 여러 서브에이전트를 순서대로 부르고 종합하는 구조를 쓰는 이유가 바로 이거다. 그래서 "요청마다 GP에 필요한 도구만 동적으로 다시 구성해 준다" 같은 방안은 불필요하다 — `factory.py`는 그래프를 세션(Agent Version)당 한 번만 조립하지 매 질의마다 다시 만들지 않으므로, 이런 동적 재구성은 지금 아키텍처와 맞지 않는 큰 변경이 된다.

## 2. 카탈로그 — 무엇을 넣는가

근거가 뚜렷한 것만, 도구 단위로 넣는다.

### 2.1 웹 리서치 에이전트 (`web-research`)

- **도구**: 웹 검색 도구 하나만. **구현 전 필수 확인**: `BUILTIN_TOOLS`(`services/harness/registry.py`)에 실제로 등록돼 있는지부터 확인한다. 없으면 이 항목은 뺀다.
- **근거**: 검색어 refinement를 몇 번이고 반복해야 하는, 스텝 수가 가변적이고 긴 도구다. §0의 "길을 잃는" 위험이 가장 뚜렷하게 성립하는 케이스.
- **`description`**: "복잡한 웹 검색"이 아니라 "웹에서 뭔가 찾아야 하는 모든 요청"으로 넓게 쓴다 — 검색 한 번으로 끝나는 단순 질의도 포함한다고 명시한다. 이 도구는 Root에 안 남아 있으므로, 설명이 좁으면 단순 질의를 처리할 방법이 아예 없어진다(§0).
- **프롬프트에 넣을 것**: 검색어를 좁혀 가는 절차, 출처 인용 형식, 다음 단계로 넘길 수 있게 검색 과정 나열 없이 결론만 압축 반환.

### 2.2 문서 검색 에이전트 (`document-research`)

- **도구**: `document_search` 하나만. `document_list`는 목록 조회일 뿐 반복 판단이 없어 묶지 않는다 — Root/GP가 필요할 때 직접 부른다.
- **근거**: 검색어를 다듬어 여러 번 불러야 하고 결과가 길다. `web-research`와 같은 성격의 반복 작업.
- **`description`**: "이 팀 문서에서 뭔가 찾아야 하는 모든 요청에 위임"으로 넓게 쓴다 — "복잡한 다단계 리서치"로 좁혀 쓰지 않는다. "어떤 문서 있는지 조회해줘" 같은 단순 질의도 이 서브에이전트가 처리해야 하는 범위라고 명시한다. `document_search`도 Root에 안 남아 있으므로 같은 이유다.
- **프롬프트에 넣을 것**: `not_indexed`를 "문서 없음"으로 오해하지 않기, 결과 없으면 없다고 바로 말하기, 다음 단계로 넘길 수 있게 핵심 주장 위주로 압축 반환.

### 카탈로그에 넣지 않는 항목과 이유

- `document_list`, `task_extraction`, `task_register`, `people_list`, `project_list`, `task_list`, `workload_report`, `absence_list`, `get_current_datetime`, `skill_register`, `jira_get_issues` — 전부 한 번 부르면 끝나는 단발성 호출이거나(목록 조회, 추출, 등록), 여러 소스를 하나의 판단으로 종합해야 하는 도구다. 둘 다 "반복 판단이 필요해서 별도 컨텍스트로 격리해야 한다"는 근거에 해당하지 않는다.
- `task_extraction`+`task_register`를 하나의 "액션 아이템 추출·등록 에이전트"로 묶는 안도 검토했으나 뺐다 — 이렇게 묶으면 추출만 필요한 질의(§1 예시)까지 등록 전용 에이전트를 거쳐야 해서, 필요하지도 않은 위임 한 단계가 항상 끼어든다. `required_role` 규칙은 이미 도구 자체의 스키마/설명에 있어 누가 부르든 동일하게 적용되고, 승인 카드도 `side_effect` 플래그 기준이라 Root가 직접 불러도 지금과 똑같이 뜬다 — 전용 에이전트가 없어도 안전장치는 그대로 작동한다.
- `project-status-briefing`, `workload-matching`, `onboarding-briefing`류의 다중 소스 종합안도 검토했으나 뺐다 — 도구 3~4개를 한 번씩만 부르고 끝나는 낮은 복잡도라 "긴 반복" 근거가 성립하지 않고, 오히려 여러 소스를 쪼개면 Anthropic이 경고한 "공유 컨텍스트가 필요한 작업을 멀티에이전트로 나눴을 때의 손실"이 생길 수 있다.

## 3. Root/GP 도구 목록에서 어떻게 빼는가

`AgentRuntimeFactory.build()`(`services/agent_runtime/factory.py`)의 도구 조립 지점에 아래 순서로 추가한다. 순서가 중요하다 — 뒤바뀌면 우회 경로가 남는다.

```python
# services/agent_runtime/subagents/catalog.py (신규)

DEFAULT_SUBAGENT_CATALOG = [
    {
        "name": "web-research",
        "description": "...",   # action-oriented하게 작성 — Root 위임 판단 기준
        "system_prompt": "...",
        "required_tool_refs": frozenset({"web_search"}),  # 실제 tool ref로 확인 후 수정
    },
    {
        "name": "document-research",
        "description": "...",
        "system_prompt": "...",
        "required_tool_refs": frozenset({"document_search"}),  # document_list는 포함하지 않는다
    },
]
```

```python
# factory.py — build() 안, langchain_tools를 다 만든 직후

def _attach_default_subagents(langchain_tools, definition):
    tool_refs_available = {tool_ref_of(t) for t in langchain_tools}
    child_aliases = {sub.alias for sub in definition.subagents}  # DB에 등록된 Child 이름

    attached = []
    claimed_tool_refs = set()
    for entry in DEFAULT_SUBAGENT_CATALOG:
        if not entry["required_tool_refs"].issubset(tool_refs_available):
            continue  # 이 팀 도구로는 못 만든다 — 조용히 스킵, 에러 아님
        if entry["name"] in child_aliases:
            # 팀이 같은 이름으로 이미 전용 Child를 등록해 뒀다면
            # 팀의 명시적 선택이 카탈로그 자동 항목보다 우선한다 — 스킵.
            continue
        attached.append(entry)
        claimed_tool_refs |= entry["required_tool_refs"]

    root_tools = [t for t in langchain_tools if tool_ref_of(t) not in claimed_tool_refs]

    catalog_specs = [
        build_general_purpose_spec(   # 기존 GP 조립 함수를 그대로 재사용
            middleware=self.middleware_factory.build_for_general_purpose(),
            system_prompt=entry["system_prompt"],
            description=entry["description"],
            tools=[t for t in langchain_tools if tool_ref_of(t) in entry["required_tool_refs"]],
            name=entry["name"],
        )
        for entry in attached
    ]
    return root_tools, catalog_specs, claimed_tool_refs
```

```python
# factory.py — gp_spec 조립부, 기존 side_effect 필터 뒤에 이어서

gp_tools = [
    t for t in langchain_tools
    if not BUILTIN_TOOLS.get(tool_ref_of(t), _NO_SIDE_EFFECT).side_effect
    and tool_ref_of(t) not in claimed_tool_refs   # 추가 — 카탈로그가 가져간 도구는 GP도 못 쓴다
]
```

```python
# factory.py — subagents 조립부

subagents=[gp_spec, *catalog_specs, *compiled_children]
# 이름이 겹치면 나중 것이 이긴다(deepagents 자체 규칙).
# compiled_children을 맨 뒤에 두는 이유: 팀이 명시적으로 등록한 Child가
# 이름이 같은 카탈로그 항목보다 항상 이기게 하기 위함이다.
```

**바로 실행해도 깨지지 않는 이유**:
- `required_tool_refs`가 팀 도구 목록과 안 맞으면 그 항목은 그냥 안 붙는다 — 새 에러 타입이 생기지 않는다.
- 카탈로그 전체가 하나도 안 맞으면(`attached == []`) 지금과 완전히 동일하게 동작한다.
- 팀이 같은 이름으로 Child를 이미 등록해 뒀으면 카탈로그 항목은 자동으로 양보한다.
- `document_list`처럼 카탈로그가 가져가지 않은 도구는 `claimed_tool_refs`에 없으므로 `root_tools`/`gp_tools`에 그대로 남는다 — Root/GP가 이 도구는 지금처럼 직접 부른다.

## 4. 실행 기록에서 이 서브에이전트가 보이는가 — 지금은 안 보인다, 그리고 이렇게 고친다

**지금 상황**: GP가 실제로 일을 해도 실행 기록(Run 로그)에는 Root가 한 일인지 구분이 안 된다. 로그가 "누가 했는지" 찾을 때 보는 명부(`definition.subagents`)에 GP는 원래 올라가 있지 않기 때문이다 — DB에 정식 등록된 에이전트가 아니라 코드에서 그때그때 만들어지는 존재라서다. `subagent_name` 칸이 비고, `agent_id`/`agent_version_id`도 Root 것 그대로 찍힌다. 카탈로그 2개도 같은 이유로 로그에서 서로 구분이 안 된다.

**해결 방법**: Child를 찾을 때 이미 쓰는 방식을 그대로 재사용한다. `services/agent_runtime/events.py`의 `_classify_parent_tool_calls()`가 alias로 `definition.subagents`를 찾는 코드가 이미 있다. 여기에 **카탈로그 이름을 위한 고정 매핑 하나**를 더한다.

```python
# events.py, 또는 catalog.py에서 함께 정의

CATALOG_SUBAGENT_IDENTITIES = {
    entry["name"]: {"subagent_name": entry["name"], "agent_id": None, "agent_version_id": None}
    for entry in DEFAULT_SUBAGENT_CATALOG
}
```

`_classify_parent_tool_calls()`가 alias를 찾을 때 먼저 `definition.subagents`(Child)를 보고, 없으면 `CATALOG_SUBAGENT_IDENTITIES`를 본다. 여기서도 못 찾으면(GP처럼) 지금처럼 Root 값으로 폴백한다 — 순서만 하나 늘어나는 것뿐이라 기존 동작을 안 깬다.

`agent_id`/`agent_version_id`는 여전히 비지만(DB에 등록된 진짜 에이전트가 아니므로 당연), **`subagent_name` 칸에 `"web-research"` 같은 이름이 정확히 남는다** — 로그에서 어느 항목이 실행됐는지 필터링할 수 있다. `resolved_provider`가 Root와 같은 값인 건 고칠 문제가 아니다 — 실제로 Root와 같은 모델 객체를 쓰기 때문에 정확한 값이다. 프롬프트 버전 추적은 이미 있는 `agent_run.runtime_profile_version`(배포 커밋 해시 기반)으로 충분하다.

## 5. Builder 노출 여부

사용자에게는 지금 GP처럼 안 보인다. Builder 화면에도 노출하지 않는다 — 팀이 고르는 게 아니라 Root가 고른 도구 조합에 따라 자동으로 결정되는 내부 최적화이기 때문이다.

## 6. 구현 후 확인할 것

- 카탈로그 항목이 요구하는 도구가 팀 목록에 없으면 그 항목만 조용히 빠지고 나머지는 영향받지 않는지.
- Root/GP의 최종 도구 목록에서 카탈로그가 가져간 도구(`web_search`, `document_search`)만 정확히 빠지고, `document_list`는 그대로 남아 있는지.
- 팀이 같은 이름으로 Child를 이미 등록해 뒀을 때 그 Child가 실제로 우선하는지.
- 카탈로그가 다 빠졌을 때 Root가 지금과 완전히 동일하게 동작하는지.
- `subagent_name`에 카탈로그 이름이 정확히 찍히는지.
- §1처럼 추출만 필요한 질의에서 `task_register`가 불리지 않고, 등록까지 필요한 질의에서는 Root가 직접 `task_extraction`→`task_register` 순서로 부르며 승인 카드가 정상적으로 뜨는지.
- §1의 복합 질의를 실제로 넣어보고, Root가 원시 검색 결과를 옮겨 적지 않고 요약만으로 다음 단계를 진행하는지.
- **"어떤 문서 있는지 조회해줘"처럼 단순한 단발성 질의를 넣어보고, Root가 "복잡한 작업이 아니니 위임 안 해도 된다"고 잘못 판단해 건너뛰지 않고 실제로 `document-research`에 위임하는지.** `web-research`도 같은 방식으로 단순 검색 질의 하나로 확인한다 — 이 확인이 빠지면 도구가 Root에 없는데 위임도 안 되는 사각지대를 놓칠 수 있다.
- **`document-research`/`web-research` 위임이 실제로 평균 몇 번의 도구 호출로 끝나는지 로그로 확인한다.** 대부분 한 번으로 끝난다면 독점(exclusive) 대신 Root도 직접 부를 수 있게 공유(shared)로 바꾸는 게 이득일 수 있다 — 이건 배포 전에 추론만으로 정할 수 없고, 실제 데이터가 쌓인 뒤 재판단할 항목이다.

## 7. 되돌리는 방법

`DEFAULT_SUBAGENT_CATALOG`를 빈 리스트로 두면 §3의 로직이 아무것도 안 걸러내므로 지금 구조로 즉시 되돌아간다. DB 마이그레이션이나 별도 롤백 절차가 없다.
