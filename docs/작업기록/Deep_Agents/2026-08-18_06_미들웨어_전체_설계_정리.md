## 2. 프로젝트 메모리 파일은 project_id로 격리된다

`/memories/projects/{project_id}.md`는 팀·에이전트가 공유하는 메모리
namespace(`/memories/AGENTS.md`와 같은 자리) 안의 파일명일 뿐이라, 아무 제약이
없으면 같은 팀·같은 에이전트로 대화 중인 세션은 지금 프로젝트가 무엇이든 다른
프로젝트의 메모리 파일도 읽고 쓸 수 있다. `middleware/permissions.py`가 이걸
막는다.

Root 그래프를 만들 때(장기 메모리가 붙어 있는 경우에 한해) 아래 두 규칙을 항상
같이 건다.

1. 지금 대화의 `project_id`에 해당하는 파일(`/memories/projects/{project_id}.md`)만
   읽기·쓰기 허용
2. 그 외 `/memories/projects/` 아래 전부 차단

`project_id`가 없는 세션(프로젝트 문맥 없이 시작한 대화)이거나 `project_id`
값이 영숫자가 아닌 경우에는 1번 규칙 없이 2번만 걸려서, 프로젝트 메모리 전체가
막힌다 — 애매하면 차단하는 쪽으로 정했다. `/memories/AGENTS.md`(팀 공유 규칙)와
`/memories/users/preferences.md`(개인 메모리)는 이 규칙과 무관한 별도 경로라
영향받지 않는다.

이 격리는 general-purpose 서브 에이전트에도 자동으로 함께 적용된다 — Root와
같은 그래프 조립 과정에서 같은 규칙을 물려받기 때문이다. Child(위임받은
서브 에이전트)는 애초에 장기 메모리 backend 자체가 없어서 `/memories/...` 경로를
불러도 항상 비어 있는 휘발성 공간만 보므로, 이 규칙을 따로 걸 필요가 없다.

**한계**: 이 규칙은 "다른 프로젝트 파일에 접근하는 것"만 막는다. "같은 파일을
`edit_file`(부분 수정) 대신 `write_file`(전체 덮어쓰기)로 건드리는 것"은 막지
못한다 — 프레임워크가 이 두 도구를 같은 권한 범주로 묶어놔서 구분할 수단이 없다.
메모리를 부분 수정으로만 갱신하라는 지침은 여전히 프롬프트 안내로만 존재한다.

검증: 실제 Postgres·Django 환경에서 새 규칙의 판정 결과, `FilesystemMiddleware`
치환 후에도 규칙이 살아있는지, `factory.py`가 `context.project_id`를 실제로
반영하는지까지 포함해 관련 테스트 109개를 돌려 전부 통과했다.

## 3. `ls`/`delete`/`write_file` 같은 파일시스템 도구는 실제로 어디까지 닿나

이 프로젝트는 실제 OS 디스크나 샌드박스에 쓰는 backend(`FilesystemBackend`,
`SandboxBackend` 등)를 어디에서도 만들지 않는다(`services/`·`apps/` 전수
grep으로 확인 — 0건). 즉 `ls`·`read_file`·`write_file`·`edit_file`·`delete`·
`glob`·`grep` 전부 **진짜 서버 디스크나 다른 팀의 실제 DB 테이블을 자유롭게
건드리는 게 아니라, 이 두 가상 backend 안에서만 동작한다.**

- **`StateBackend`** — `/memories/`로 시작하지 않는 나머지 모든 경로(기본
  backend)의 실체. LangGraph 그래프 상태의 `files` 채널 안 딕셔너리일 뿐,
  디스크도 DB 테이블도 아니다. **다른 스레드·다른 사용자의 state와는 구조적으로
  분리**되어 있어서(deepagents 자체 docstring: "persist within a conversation
  thread but not across threads"), 다른 세션·다른 사용자의 스크래치 파일은
  애초에 같은 state가 아니라서 안 보인다 — 이건 그대로 유효하다.
  다만 **"이번 대화 스레드 안에서만 존재한다"를 "대화가 끝나면 사라진다"는
  뜻으로 읽으면 부정확하다**(2026-08-19 수정): 이 프로젝트는 checkpointer
  (`PostgresSaver`)가 `memory_provider`와 항상 같이 켜져 있어서, `StateBackend`의
  `files` 채널도 매 스텝 뒤 체크포인트로 Postgres에 실제 저장된다(`StateBackend`
  자체 docstring: "State is automatically checkpointed after each agent
  step"). 즉 같은 스레드(`thread_id`=`session_id`)를 나중에 다시 이어가면 그
  데이터가 다시 보인다 — "대화 종료 시 완전 삭제"가 아니라 "장기 메모리 Store에
  영속화되지 않는다"(다른 스레드에서는 안 보이고, 매 턴 시스템 프롬프트에
  자동 주입되지도 않는다)는 뜻으로 읽어야 한다. 자세한 근거는
  `services/agent_runtime/memory/backend.py` 모듈 docstring 참고.
- **`StoreBackend`** — `/memories/`(팀 공유)와 `/memories/users/`(개인) 두
  route의 실체. Postgres `store` 테이블의 어댑터인데, 이 프로젝트는 backend를
  만들 때 namespace를 클로저로 고정한다(`build_memory_backend()`) — 공유는
  `(team_id, agent_id)`, 개인은 `(team_id, agent_id, account_id)`. 이 값은
  요청마다 서버가 인증된 세션에서 채우는 것이지 모델이 넘기는 인자가 아니라서,
  이 backend를 통해 다른 팀·다른 에이전트·다른 계정의 행에 닿을 방법이
  구조적으로 없다.

**`ls`의 범위**(`CompositeBackend.ls`, 실제 소스 확인): 경로가 route와 정확히
일치하면 그 backend 하나만 조회한다. `path="/"`로 부르면 default(`StateBackend`)
루트 항목 + route 이름들(`/memories/`, `/memories/users/`)을 "디렉터리
있다"는 표시로만 보여줄 뿐, 그 안의 실제 파일 목록까지 한 번에 펼쳐 주지
않는다 — 안을 보려면 `ls("/memories/")`처럼 그 route를 직접 불러야 하고,
그 호출도 결국 그 요청의 고정된 namespace로만 라우팅된다. 즉 `ls` 한 번으로
다른 팀·계정의 메모리나 다른 세션의 임시 파일이 우연히 섞여 나올 방법이
없다.

**`delete`의 범위**(`CompositeBackend.delete`/`StateBackend.delete`, 실제
소스 확인): 한 번의 호출은 넘긴 `file_path` 정확히 그 경로 + 그 아래 중첩
경로(그 경로가 디렉터리처럼 쓰였을 때)만 지운다 — "전부 지우기"나 다른
route·namespace로 번지는 동작은 없다. 그리고 이 프로젝트는 이 도구 자체를
모델에게 아예 안 보여준다 — `runtime_policy.DEFAULT_EXCLUDED_BUILTIN_TOOLS =
{"delete"}`가 두 곳에서 이중으로 걸린다: `_ToolExclusionMiddleware`(role 필터
경로)와 `create_root_graph`/`create_child_graph`의 `fs_excluded_tools`(그래프
조립 시 `FilesystemMiddleware`의 `tools=` 허용목록에서 아예 뺌, Phase 6). 한쪽
설정이 빠지거나 틀려도 다른 쪽이 남는 이중 방어라, 지금은 `delete`가 위험하지
않게 다듬어진 게 아니라 **모델의 도구 목록에 존재 자체를 안 준다.**

**Root/general-purpose vs Child의 차이**: Root와 general-purpose 서브 에이전트는
같은 그래프 조립 과정에서 같은 backend 인스턴스(메모리 Store 포함)와 같은
`FilesystemPermission` 규칙을 그대로 물려받는다(1번 표, 2장). 반면 Child(위임된
서브 에이전트)는 `create_child_graph`가 애초에 backend를 안 넘기고 deepagents
기본값인 **새 `StateBackend()`**만 받는다(`compat/deepagents_v075.py` 주석:
"치환 시에도 backend를 안 넘긴다") — 이 Child 전용 인스턴스는 Root/
general-purpose가 쓰는 backend와 아예 다른 객체라, `/memories/...` 경로에 뭘
해도 그 Child 실행 안에서는 항상 빈 파일 취급이고, 다른 세션이나 계정의
메모리에 닿을 방법 자체가 없다(위 `StateBackend` 설명과 마찬가지로 "빈
휘발성 공간"이라는 표현은 checkpoint에 남을 수 있다는 점에서 정확하지 않다 —
다만 Child의 격리 자체는 여전히 유효하다: 이 새 인스턴스가 Root의 namespace나
Store에 애초에 연결되어 있지 않기 때문이다).
