### 1-1. 없으면 뭐가 문제고, 왜 쓰는가

| 미들웨어 | 없으면 생기는 문제 | 왜 이걸 쓰는가 |
|---|---|---|
| `ModelCallLimitMiddleware` | 모델이 답을 못 찾고 자기 자신을 계속 불러 비용만 나가고 응답은 안 옴 | 모델 호출 하나하나가 곧 돈이다. 이 실행에 쓸 수 있는 "예산"을 정해 두고, 다 쓰면 조용히 멈추는 대신 에러로 확실히 끊어서 왜 멈췄는지가 로그에 남는다 |
| `ToolCallLimitMiddleware` | 같은 조회 도구를 계속 반복 호출해 비용만 쌓임 | 모델 호출과 도구 호출은 서로 다른 자원이다 — 모델 호출은 LLM 추론 비용, 도구 호출은 외부 API·DB에 실제로 요청을 보내는 부수효과다. 그래서 예산도 따로 잡는다 |
| `TodoListMiddleware` | 여러 단계 작업 중 순서를 잊거나 이미 한 일을 또 함 | 모델 스스로 진행 상황을 적어 두게 해서, 복잡한 다단계 작업에서 중간을 놓치지 않게 한다 |
| `MemoryMiddleware` | 사용자가 매번 같은 선호·규칙을 다시 설명해야 함 | 저장해 둔 개인 메모를 매 턴 자동으로 시스템 프롬프트에 넣어 준다 |
| `FilesystemMiddleware`(`tools=` 허용목록) | 모델이 파일을 지우는 도구까지 고를 수 있게 됨 | 읽기·쓰기는 필요해도 지우는 동작만은 선택지에서 아예 뺀다 |
| `FilesystemMiddleware`(`_permissions=`) | (지금은 비활성이라 해당 없음 — 아래 1-2 참고) | (지금은 안 씀 — 아래 1-2 참고) |
| `HumanInTheLoopMiddleware` | 모델이 잘못 판단해도 사람이 거를 기회 없이 바로 실행됨 | 업무 등록·Jira 이슈 생성처럼 외부에 실제 영향을 주는 도구는 실행 전에 확인을 받는다. 예를 들어 "이슈 5개 등록해줘"라고 하면 모델이 곧바로 만들지 않고, 확인 카드를 먼저 띄운다 |
| `PatchToolCallsMiddleware` | 모델이 만든 도구 호출 형식이 살짝 어긋나도 그대로 흘러가 실패로 이어짐 | deepagents가 이미 검증해 둔 보정 로직이라, 직접 다시 만들 이유가 없다 |
| `SummarizationMiddleware`(deepagents 자체 버전) | 대화가 길어질수록 컨텍스트가 계속 불어나 비용·지연이 커짐 | deepagents 자체 요약 로직을 그대로 믿고 쓴다 |
| `SubAgentMiddleware` | Root가 general-purpose·Child에 위임하는 구조 자체가 안 돌아감 | 위임 구조의 핵심 배선이라, 여기서 따로 만들면 오히려 더 위험하다 |
| Prompt Caching | 같은 프롬프트를 매번 새로 계산해 비용·응답 속도 둘 다 손해 | deepagents가 기본으로 주는 기능을 그대로 쓴다 |
| `_ToolExclusionMiddleware` | `tools=` 허용목록 설정이 실수로 빠지면 `delete`가 다시 보이게 됨 | 같은 걸 두 곳에서 막아 둔다. 한쪽이 실수로 빠져도 다른 쪽이 남는 이중 방어다 |
| 역할 기반 Tool 노출/재검사(RBAC) | 권한 없는 계정이 업무 등록 같은 도구를 실행하거나, 왜 실행이 안 되는지 몰라 헷갈림 | 도구가 "있느냐"와 "지금 실행해도 되느냐"는 다른 문제다. 목록에는 항상 보여 주고, 실행 직전에 권한만 한 번 더 확인한다 |
| Sub-agent 위임 깊이 제한 | 서브 에이전트가 서브 에이전트를 계속 불러 누가 뭘 했는지 추적 불가·무한 루프 위험 | 위임을 한 단계로 묶어 구조를 단순하고 추적 가능하게 유지한다 |
| `SkillsMiddleware` | 사내 업무 절차를 매번 새로 설명해야 함(재사용 불가) | (미사용 — 별도 설계 중, `2026-08-20_16_Skill_Middleware_설계.md`) |
| `PIIMiddleware` | 사용자가 채팅에 그대로 붙여 넣은 카드번호·IP·MAC 주소가 마스킹 없이 모델 컨텍스트로 들어감 | 채팅 입력 단계 마스킹(`mask_sensitive()`)과는 별개로, LangChain 표준 미들웨어로 한 번 더 걸러 낸다. 도구 결과 쪽(`apply_to_tool_results`)은 이번 범위 밖 — 필요해지면 그때 켠다 |
| `ContextEditingMiddleware` | 대화가 길어지면 컨텍스트가 무거워짐 | (미사용 — deepagents 자체 Summarization이 이미 비슷한 역할을 함) |
| `LLMToolSelectorMiddleware` | 도구가 많아지면 모델이 관련 없는 도구까지 다 보게 됨 | (미사용 — 지금은 에이전트당 도구 수가 적어 문제가 안 됨) |

### 1-2. 우리 프로젝트에 맞게 무엇을 바꿨고, 왜 그렇게 바꿨는가

프레임워크 기본값을 그대로 쓰는 것도 있고(위 표에서 "정한 값"이 `—`인
것들 다수), 값이나 문구를 직접 고른 것도 있다. 후자만 적는다.

| 미들웨어 | 무엇을 바꿨는가 | 왜 |
|---|---|---|
| `ModelCallLimitMiddleware` | Root/Child는 에이전트별 설정값(빌더에서 정하는 `max_iterations`)을 그대로 쓰고, general-purpose만 고정값 50을 직접 정했다. 아무리 크게 설정해도 50을 못 넘도록 방어선도 따로 뒀다 | general-purpose는 Root/Child와 달리 에이전트별 설정 항목 자체가 없다. 그래서 이 고정값이 곧 실제 실행 상한이다 |
| `ToolCallLimitMiddleware` | Root/Child·general-purpose 모두 100으로 고정값을 직접 정했다 | Root/Child도 도구 호출 상한만큼은 에이전트별 설정 항목이 없다. 방어선 값 자체를 상한으로 쓴다 |
| `TodoListMiddleware` | LangChain 기본 도구 설명에 우리 프로젝트 전용 문단을 추가했다 — "이건 네 혼자 쓰는 체크리스트지, 팀원에게 보이는 진짜 업무 등록(`task_register`/`task_update`)이 아니다"라는 구분 안내 | `write_todos`는 이 세션에만 있는 개인 계획이고, `task_register`/`task_update`는 DB에 남아 팀 전체가 보는 공식 기록이다. 이름·개념이 비슷해서 모델이 둘을 헷갈릴 여지가 있었다 |
| `MemoryMiddleware` | `MemoryMiddleware` 자체는 Root에만 붙인다. Child·general-purpose는 이 미들웨어가 없다 | 다만 general-purpose는 Root와 같은 조립 과정에서 backend 자체(Store 기반 메모리 경로 포함)를 그대로 물려받으므로, 메모리에 아예 접근하지 못하는 건 아니다. 없는 건 "시스템 프롬프트에 메모리를 자동으로 넣어 주는 미들웨어"뿐이다. Child는 위임받아 도는 일회성 작업이라 개인 배경지식까지 자동 주입할 필요가 약하다고 판단했다 |
| `FilesystemMiddleware`(`tools=` 허용목록) | deepagents 기본은 `delete`까지 다 열려 있는데, 허용목록에서 `delete`만 빼도록 직접 좁혔다 | 파일을 지우는 동작은 되돌리기 어려운 부수효과다. "지우지 말라"는 프롬프트 안내보다 도구 자체를 안 주는 쪽이 확실하다 |
| `FilesystemMiddleware`(`_permissions=`) | 원래는 다른 프로젝트의 공유 메모 파일을 못 읽고 못 쓰게 막는 규칙을 직접 만들어 붙였었다. 지금은 배선을 끊어 비활성 상태다 | 팀·프로젝트가 함께 보는 공유 메모리 자체를 없애고 계정 개인 메모리만 남기기로 하면서, 이 규칙이 막아야 했던 "다른 프로젝트 메모 열람" 상황 자체가 사라졌다. 규칙을 고쳐서 안 쓰는 게 아니라, 막을 대상이 없어져서 안 쓰는 것이다 |
| `HumanInTheLoopMiddleware` | 개별 도구를 하나하나 지정하지 않고, 도구 정의의 `side_effect=True` 플래그를 기준으로 자동 설치되게 배선했다. 승인도 "팀장이 팀원 요청을 대신 승인"하는 구조가 아니라, 요청한 사람 본인이 승인하는 구조로 썼다(팀장·팀원 동일) | 도구를 새로 추가할 때마다 승인 대상 목록을 손으로 관리하지 않아도 된다. 자기 요청 자기 승인 구조로 둔 이유는 따로 있다 — 팀장이 대신 승인하게 하면, 승인 카드를 띄운 그 사람이 본인 요청을 스스로 눌러 승인해 버릴 수 있는 허점이 생긴다 |
| `_ToolExclusionMiddleware` | 제외 도구 값을 `{"delete"}`로 직접 정해 배선했다 | `FilesystemMiddleware`의 허용목록 설정과 같은 걸 한 번 더 막는다. 한쪽 설정이 실수로 빠지거나 틀려도 다른 쪽이 남는다 |
| 역할 기반 Tool 노출/재검사(RBAC) | 부수효과 있는 도구를 목록에서 아예 숨기던 방식에서, 목록엔 항상 보이게 하고 실행 직전에만 권한을 재검사하는 방식으로 바꿨다. 실행 허용 역할도 `leader`만이 아니라 `leader`/`member` 둘 다로 정했다 | 도구를 숨기면 모델이 "그런 기능이 없다"고 잘못 답하는 문제가 있었다. 역할 범위를 넓힌 건 팀원도 자기 업무는 스스로 등록할 수 있어야 한다고 판단해서다 — 실행은 항상 요청한 본인이 승인해야 하므로(위 HITL), 범위를 넓혀도 방어선 자체가 없어지는 건 아니다 |
| Sub-agent 위임 깊이 제한 | 위임 횟수를 세는 카운터가 아니라, "서브 에이전트가 이미 서브 에이전트를 갖고 있으면 에러"라는 구조적 규칙으로 만들었다 | 지금 단계에서는 위임이 한 단계로 충분하고, 구조로 막는 쪽이 숫자 상한보다 예외 없이 확실하다 |
| `PIIMiddleware` | LangChain 기본 5종(`email`/`credit_card`/`ip`/`mac_address`/`url`) 중 `credit_card`/`ip`/`mac_address` 3종만 켰다. `pii_type`은 인스턴스 하나당 하나만 받아서(langchain 실측), 3개를 각각 별도 인스턴스로 만들어 리스트로 붙였다. Root/Child의 `MiddlewareFactory.build()`에만 넣고 `build_for_general_purpose()`에는 안 넣었다 | `email`/`url`은 이 프로젝트 채팅에서 담당자 메일 주소·문서 링크로 정상적으로 자주 오가 켜면 업무에 방해가 됐다. GP는 사용자 원문을 직접 받는 경로가 없어 지금은 붙일 이유가 없다 |
