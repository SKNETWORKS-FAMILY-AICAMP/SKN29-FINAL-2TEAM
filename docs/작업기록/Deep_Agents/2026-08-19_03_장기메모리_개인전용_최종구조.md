# 2026-08-19_03 — 장기 메모리를 개인 전용으로 단순화

결정: 팀 공유 메모리(`/memories/AGENTS.md`)와 프로젝트 공유 메모리
(`/memories/projects/{project_id}.md`)를 없애고, 장기 메모리는
개인(`/memories/users/preferences.md`) 하나만 쓴다. 이 문서는 그 결정에
맞춰 지금까지의 설계를 다시 정리한 최종 구조다 — 공유 메모리를 전제로 했던
이전 설계(`2026-08-19_02` §1·§3·§4, `2026-08-18_06` §2·§3의 project 격리
부분)는 이 문서로 대체된다.

## 1. 메모리 구조

**바뀌기 전** (`services/agent_runtime/memory/backend.py`):

```python
def build_memory_backend(*, team_id, agent_id, account_id):
    return CompositeBackend(
        default=StateBackend(),
        routes={
            MEMORY_USERS_PATH_PREFIX: StoreBackend(namespace=_personal_namespace),  # (team, agent, account)
            MEMORY_PATH_PREFIX: StoreBackend(namespace=_shared_namespace),          # (team, agent)
        },
    )

def memory_paths() -> list[str]:
    return [MEMORY_FILE]  # "/memories/AGENTS.md" — 매 턴 자동 주입
```

**바뀐 후**:

```python
def build_memory_backend(*, team_id, agent_id, account_id):
    return CompositeBackend(
        default=StateBackend(),
        routes={
            MEMORY_USERS_PATH_PREFIX: StoreBackend(namespace=_personal_namespace),
        },
    )

def memory_paths() -> list[str]:
    return [MEMORY_USERS_FILE]  # "/memories/users/preferences.md" — 매 턴 자동 주입
```

`MEMORY_PATH_PREFIX`(`"/memories/"`) route를 아예 지운다 — 그 route가
없어지면 `/memories/AGENTS.md`든 `/memories/projects/{project_id}.md`든
`/memories/users/`가 아닌 나머지는 전부 `default`(`StateBackend`, 이번
대화 스레드 안에서만 존재하는 휘발성 공간)로 자연스럽게 떨어진다 —
경로별로 따로 분기하거나 새 예외를 만들 필요가 없다. 지난 세션에서
모델이 실수로 그 경로에 뭘 써도(예: `_MEMORY_ROUTING_PROMPT`가 아직
안 고쳐진 상태에서 습관적으로) 그 대화가 끝나면 그냥 사라진다.

**자동 주입 대상도 바꾼다.** 원래 `AGENTS.md`를 매 턴 자동 주입했던 이유는
"항상 알아야 할 배경지식이라 매번 다시 안 물어봐도 되게" 하려는 것이었다 —
이제 그 배경지식의 자리는 개인 선호(`preferences.md`)가 대신한다. 같은
이유로 이 파일도 짧게 유지해야 한다(매 턴 시스템 프롬프트에 실리므로).

## 2. `is_default_chat` 기반 공유 제외 설계는 필요 없어졌다

`2026-08-19_02` §1에서 다뤘던 문제 — "기본 챗 에이전트는 팀원 전체가 같이
쓰는 `agent_id`라서, 공유 메모리를 쓰면 한 팀원의 말이 다른 팀원에게
동의 없이 끼어든다" — 는 애초에 공유 메모리가 없으면 존재할 수 없는
문제다. `AgentDefinition.is_default_chat` 필드, `AgentVersionRepository`의
`a.is_default_chat` SELECT 추가, `include_shared` 파라미터를
`build_memory_backend()`/`memory_paths()`/`memory_system_prompt()`에
스레딩하는 작업 — 전부 취소한다. 새 DB 컬럼도, 새 로더 필드도 필요 없다.

## 3. 메모리 쓰기 내용 방어(`write_guard`)는 그대로 유지 — 오히려 유일한 방어선이 된다

`2026-08-19_02` §2에서 설계한 내용은 그대로 유효하다: `write_file`/
`edit_file`을 감싸는 `wrap_tool_call` 미들웨어(`memory/write_guard.py`)가
`/memories/`로 시작하는 경로에 API 키·비밀번호·주민등록번호·카드번호
패턴(정규식, 신뢰성 있음)과 욕설·보안 민감 문구(단어 목록, 한계 있음— 이
문서에서도 그대로 인정)를 실행 전에 검사한다. 개인 메모리라고 비밀번호를
저장해도 되는 건 아니므로 적용 범위는 그대로다.

**바뀌는 건 "누가 쓸 수 있는가" 레이어가 통째로 사라진다는 점이다.**
`2026-08-19_02` §3에서 설계했던 role 게이트(leader만 공유 경로에 쓸 수
있음)와 `FilesystemPermission(mode="interrupt")`로 leader 본인의 쓰기를
매번 확인받게 하는 설계 — 둘 다 이제 필요 없다. 이제 각자 자기 개인
메모리만 쓰므로 "이 쓰기를 다른 누가 승인해야 하나"라는 질문 자체가
성립하지 않는다. `2026-08-19_01` §2에서 확인한 "새 엔진용 HITL resume
API가 아직 없다"는 공백도, 적어도 메모리 쓰기 확인 목적으로는 더 이상
막힐 이유가 없어진다 — 애초에 그 확인이 필요 없어졌기 때문이다.

## 4. `middleware/permissions.py`(프로젝트 메모리 격리)는 이제 죽은 코드다 — 삭제 권장

이번 세션에서 실제로 구현하고 테스트까지 통과시킨 기능이지만, 전제 자체가
사라졌다. 그 기능은 "`/memories/projects/{project_id}.md`가 Postgres
Store에 영구 저장되는데, 아무 제약이 없으면 같은 팀·에이전트의 다른
프로젝트 대화에서도 그 파일에 접근할 수 있다"는 문제를 막으려는 것이었다.
이제 `/memories/projects/...` 경로는 애초에 영구 저장(Store)에 안
가고 `StateBackend`(이번 대화 스레드 한정)로 떨어지므로, 새 대화로 넘어가는
순간 아무것도 안 남는다 — 격리할 대상 자체가 없어진다.

구체적으로 다음이 정리 후보다: `services/agent_runtime/middleware/
permissions.py`(`build_filesystem_permissions`), `factory.py`의
`root_kwargs["permissions"] = build_filesystem_permissions(...)` 배선,
`compat/deepagents_v075.py`의 `permissions`/`fs_kwargs["_permissions"]`
이중 배선(이 배선 코드 자체는 다른 목적의 `permissions`가 생기면 재사용
가능하니 완전히 지울지는 별개 판단이지만, 지금 유일하게 이 값을 채우던
호출부는 사라진다), `tests/test_middleware_permissions.py`와
`tests/test_deepagents_compat.py`/`tests/test_factory.py`에 추가했던
관련 테스트들. **이 문서 작성만으로는 코드를 건드리지 않았다** — 실제
삭제는 별도로 요청하면 진행한다.

## 5. `_MEMORY_ROUTING_PROMPT`도 다시 써야 한다

지금 프롬프트는 "SHARED냐 PERSONAL이냐 먼저 분류하고, SHARED면 AGENTS.md
(핵심)냐 projects/*.md(상세)냐 고르고, 정책·팀정보·프로젝트정보·도구조회
결과 사이 우선순위를 판단하라"는 상당히 복잡한 지침이다
(`2026-08-18_21_장기메모리_충돌우선순위_설계.md`가 그 근거). 이제 파일이
하나뿐이라 이 전부가 "기억할 가치가 있으면 `/memories/users/
preferences.md`에 적어라, 부분 수정은 `edit_file`로"까지 단순해진다.

**남기는 것**: "저장된 메모리 vs 지금 도구 조회 결과가 다르면 지금 조회
결과를 따른다"는 판단 기준은 그대로 남긴다 — 이건 공유냐 개인이냐와
무관하게, 오래된 개인 메모리와 지금 확인한 사실이 부딪히는 경우에도
똑같이 필요하다. **없애는 것**: 정책 vs 팀정보 vs 프로젝트정보 우선순위
표 전체 — 그 축을 나누던 파일들이 다 사라졌으니 표 자체가 무의미하다.
side_effect 도구 실행 전 HITL은 메모리 파일 구조와 별개 메커니즘이라
전혀 안 바뀐다(`2026-08-18_21` §5에서 이미 확인한 대로 — "실제로 코드가
강제하는 건 HITL 하나뿐").

## 6. 잃는 것 — 기록만 해 둔다

이전에 공유 메모리를 유지하자고 주장했던 근거(Builder 공유 에이전트가 팀
컨벤션을 자동으로 알려주는 것, 프로젝트에 새로 합류한 사람이 이전 맥락을
자동으로 아는 것)는 이 결정으로 실제로 사라진다 — 결정을 뒤집자는 게
아니라, 나중에 "왜 이렇게 됐는지" 알 수 있게 남겨 둔다. 팀원들은 이제
같은 팀 컨벤션을 각자 개인 메모리에 따로 넣어야 하거나, 그때그때 다시
말해야 한다.

**문서화된 내용은 여전히 팀 전체가 본다** — `document_search`/
`document_list`/`project_list`/`task_list` 같은 기존 조회 도구는 이번
결정과 무관하게 그대로 남아 있고, 이건 애초에 메모리가 아니라 DB를 매번
다시 조회하는 별개 경로다(`2026-08-19_02` §5에서 이미 확인한 구분). 이번
결정으로 없어지는 건 정확히 "문서화되지 않은, 대화에서만 나온 것을 팀
전체에 자동으로 남기는 기능" 하나뿐이다.

## 7. 완료 — 코드 반영

2026-08-19, 이 설계를 실제 코드에 반영했다. 진행하면서 확정한 두 가지 판단:

- **`middleware/permissions.py`(프로젝트 메모리 격리)는 코드와 테스트를
  남기고 배선만 끊었다.** `factory.py`에서 `build_filesystem_permissions()`
  호출과 `permissions=...` 배선만 뺐다 — 함수 자체와
  `tests/test_middleware_permissions.py`는 그대로 둬서, 나중에 다른 경로별
  권한 제어가 필요해지면 재사용할 수 있게 남겨뒀다.
- **개인 메모리(`preferences.md`)를 매 턴 자동 주입하기로 했다** — 팀 공유
  메모리(`AGENTS.md`)가 갖던 "항상 알아야 할 배경지식을 매번 안 물어봐도
  되게" 자동 주입 자리를 개인 선호가 대신한다.

**바뀐 파일**: `services/agent_runtime/memory/backend.py`(공유 route 제거,
`MEMORY_USERS_FILE` 자동 주입, `_MEMORY_ROUTING_PROMPT` 단순화),
`services/agent_runtime/factory.py`(`permissions` 배선 제거),
`tests/test_memory_backend.py`·`tests/test_memory_provider.py`·
`tests/test_factory.py`(새 구조에 맞게 재작성).

**검증**: 바뀐 파일 관련 테스트(`test_memory_backend`, `test_memory_provider`,
`test_factory`, `test_middleware_permissions`, `test_deepagents_compat`) 109개
전부 통과. 전체 스위트(870개) 기준 실패 25건·에러 6건은 전부 이번 변경과
무관한 기존 실패(`test_accounts`·`test_document_download`·`test_harness`·
`test_hr_tenant`·`test_projects`의 503 관련, `test_document_pipeline` import
에러)로, 이번에 건드린 파일에는 없다.

**아직 안 한 것**: 메모리 쓰기 내용 방어(`memory/write_guard.py`, §2~3에서
설계만 한 부분)는 이번에 코드로 반영하지 않았다 — 별도로 요청하면 진행한다.
