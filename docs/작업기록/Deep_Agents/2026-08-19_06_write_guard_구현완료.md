# write_guard 코드 반영 완료 (2026-08-19, §1순위)

> 설계는 `2026-08-19_04_write_guard_구현설계.md`에 이미 끝나 있었다. 이
> 문서는 그 설계를 그대로 코드로 옮기고 검증한 기록이다 — 설계 문서의
> 내용을 다시 옮겨 적지 않는다.

## 구현 내역

| 파일 | 변경 |
|---|---|
| `services/agent_runtime/memory/write_guard.py`(신규) | `MemoryWriteGuardMiddleware`, `build_memory_write_guard()`. 설계 문서 §3의 코드를 그대로 반영 — credential/PII/authority 세 카테고리 패턴, `validate_path()`로 정규화한 경로 기준 prefix 비교, 매칭 원문을 오류 메시지에 안 옮기는 구성. |
| `services/agent_runtime/factory.py` | Root 분기에 `root_middleware` 변수를 새로 두고, `memory_provider is not None`일 때만 `[*custom_middleware, build_memory_write_guard()]`로 write_guard를 더한다. `create_root_graph(middleware=...)`가 `custom_middleware` 대신 이 값을 받도록 바꿨다. Child 분기(`create_child_graph`)는 그대로 `custom_middleware`만 쓴다 — 손대지 않았다. |

설계 문서 §3의 예시 코드와 실제 반영본의 차이는 하나뿐이다 — `validate_path`
import를 함수 안이 아니라 모듈 상단으로 뒀다. `factory.py`가 이미
`compat/deepagents_v075.py`를 거쳐 모듈 최상단에서 `deepagents`를 불러오고
있어서(확인함), `apps/chat/api_views.py`가 `build_default_executor`를
지연 import하는 것과 같은 "Django URL 설정 로딩 시점에 deepagents 없이도
부팅돼야 한다"는 이유가 이 파일에는 적용되지 않는다.

## 검증

### 단위 테스트 — `tests/test_memory_write_guard.py`(신규, 21개)

설계 문서 §5의 테스트 계획을 전부 코드로 옮겼다. `ToolCallRequest`는 실제
`langchain.agents.middleware.types` 클래스를 그대로 쓴다(mock 아님) —
`wrap_tool_call()`이 실제로 읽는 `.tool_call` 속성만 있으면 되므로.

대상 도구 아니면 통과, `/memories/users/` 밖 경로면 내용 무관 통과,
정규화하면 같은 파일로 떨어지는 경로 표기(`"memories/users/..."`,
`"/memories//users/..."`)도 잡히는지(§2 문제의 회귀 테스트), `validate_path`가
`ValueError`를 내는 경로는 관여하지 않는지, 세 카테고리(credential/PII/
authority) 각각이 막히는지, `edit_file`은 `new_string`만 보고 `old_string`은
안 보는지, 정상 문장은 통과하는지, 거부 메시지에 매칭된 원문(API 키·
주민번호 값 자체)이 안 남는지, `guarded_prefix`를 바꾸면 그 기준으로 도는지
— 전부 통과.

### 배선 테스트 — `tests/test_factory.py`(`BuildMemoryWiringTests`에 5개 추가)

`memory_provider`가 있으면 `create_root_graph`로 가는 `middleware`에
`MemoryWriteGuardMiddleware`가 정확히 하나 포함되는지, 없으면 안 들어가는지,
Child(`create_child_graph`)에는 `memory_provider` 유무와 무관하게 절대
안 들어가는지, 기존 `custom_middleware`(예: `ModelCallLimitMiddleware`)를
갈아 끼우지 않고 그대로 유지하며 더해지는지 — 전부 통과.

### 실제 그래프 통합 확인 (mock 없이, 실제 Postgres Store까지)

결정론적 가짜 모델로 `AgentRuntimeFactory`가 조립한 실제 컴파일 그래프를
직접 `graph.invoke()`했다(`_hitl_structural_check.py`와 같은 방식) — 두
경우를 비교했다:

1. **모델이 `/memories/users/preferences.md`에 `"api_key:
   sk-abcdefghijklmnopqrstuvwx"`를 쓰려는 경우**: `write_file` 도구
   메시지가 `status="error"`로 돌아왔고, 실제 Postgres Store를 그
   namespace(`(team_id, agent_id, account_id)`)로 직접 조회하니 **행이
   0개** — 실제로 저장되지 않았음을 DB 레벨에서 확인.
2. **같은 경로에 `"한국어로 답해줘"`(정상 내용)를 쓰는 경우**: 도구
   메시지가 `status="success"`로 돌아왔고, Store를 조회하니 그 내용이
   담긴 행이 **1개** — 정상 케이스는 그대로 저장됨을 확인(과차단이 아님을
   함께 확인).

이 확인은 `wrap_tool_call()`이 실제 컴파일된 `AgentRuntimeFactory` 그래프
안에서, 실제 `FilesystemMiddleware`/`ToolNode`/`StoreBackend`와 함께 있을
때도 설계대로 동작한다는 것을 단위 테스트(구성 요소 하나만 격리해서 확인)
와는 다른 층위에서 보여준다.

## 한계 (설계 문서 §4 그대로 유효, 재확인만)

- 여러 번의 `edit_file`에 걸쳐 쪼개서 넣으면 각 호출은 통과할 수 있다.
- 전화번호 패턴은 오탐 가능성이 있다.
- 권한/보안 키워드는 문맥 없이 문자열 포함 여부만 본다.
- 모델이 추론한 사실·프로젝트 한정 사실은 이 미들웨어의 대상이 아니다
  (`_MEMORY_ROUTING_PROMPT`의 몫).
- **(이번에 실측으로 재확인한 것)** 거부 메시지 자체에는 원문이 안
  남지만, 모델이 제안한 `tool_call`의 `args`는 이미 대화 상태(메시지
  히스토리)에 있다 — write_guard가 개입하기 **전에** 모델이 이미 그
  값을 생성해 낸 상태이므로, 장기 저장은 막아도 그 턴의 대화 기록에서
  완전히 지우지는 못한다. 이건 write_guard의 버그가 아니라 tool-calling
  프로토콜 자체의 구조 — 어떤 `wrap_tool_call` 기반 방어로도 피할 수
  없다(모델이 이미 만든 값을 사후에 지울 수는 있지만 그건 별개의 문제다).
