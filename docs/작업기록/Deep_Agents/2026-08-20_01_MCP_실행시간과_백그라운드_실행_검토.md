# 2026-08-20_01 — 자유 연결 MCP의 실행시간과 백그라운드 실행 검토

## 1. 이 문서의 결론

이 프로젝트는 운영자가 정해 둔 MCP만 제공하는 서비스가 아니다. 사용자가 자신이 쓰는
MCP 서버를 자유롭게 연결하고, 그 도구를 조합해 에이전트를 만드는 Agent Platform이다.
따라서 플랫폼은 처음 보는 MCP 도구의 실제 실행시간, 부작용 여부, 취소 가능 여부를
사전에 확실하게 알 수 없다.

이번 검토에서는 다음을 결정했다.

1. MCP 도구의 실행시간을 사전에 정확히 분류할 수 있다고 가정하지 않는다.
2. 과거 실행시간은 관측·최적화 자료일 뿐, 안전성 판단의 확정 근거로 쓰지 않는다.
3. 지금의 `CompiledSubAgent` + `task` 구조와 Deep Agents의
   `AsyncSubAgentMiddleware`는 서로 다른 문제를 푼다.
4. `AsyncSubAgentMiddleware`는 일반 MCP 도구나 현재 로컬 Child를 자동으로
   백그라운드화하는 기능이 아니다.
5. 현재는 `AsyncSubAgentMiddleware` 도입을 보류한다.
6. 우선순위는 알 수 없는 MCP 실행을 견디는 타임아웃, 동시 실행 제한, HITL,
   실행 추적과 멱등성이다.
7. 사용자 요청과 수명이 분리된 장시간 작업이 실제 제품 요구가 되면, 플랫폼 자체의
   작업 레코드와 별도 실행 프로세스(Worker)를 설계한다.

이 문서는 설계 판단만 기록한다. 코드와 DB에는 아직 반영하지 않았다.

## 2. 현재 실행 구조

현재 채팅 실행은 하나의 요청 안에서 이어진다.

```text
브라우저
  → Django Chat API
  → AgentExecutor
  → Root Deep Agent
  → Child 또는 MCP Tool
  → 최종 결과
  → 같은 HTTP 스트림으로 브라우저에 전달
```

Root가 한 AIMessage에 여러 `task` tool call을 만들면 LangGraph ToolNode가 그
호출들을 동시에 실행할 수 있다. 하지만 이것은 **동기 병렬 실행**이다. Root는 가장
느린 Child까지 모두 끝나야 결과를 종합할 수 있고, 채팅 요청도 그때까지 살아 있어야
한다.

```text
Root
  ├─ task(A): 3초  ─┐
  ├─ task(B): 8초  ─┼─ Root는 약 20초 뒤 다시 실행
  └─ task(C): 20초 ─┘
```

병렬 여부는 현재 애플리케이션 스케줄러가 정하지 않는다. Root LLM이 독립 작업들을
한 응답의 복수 `task` 호출로 만들면 병렬이고, 한 Child의 결과를 받은 뒤 다음
`task`를 만들면 직렬이다.

## 3. 자유 연결 MCP에서는 실행시간을 미리 알 수 없다

MCP 도구 목록에서 일반적으로 얻는 정보는 이름, 설명, 입력 스키마다. 이것만으로는
다음을 확정할 수 없다.

- 조회인지 쓰기인지
- 2초짜리 호출인지 5분짜리 호출인지
- 취소가 가능한지
- 실패 후 다시 실행해도 안전한지
- 같은 도구라도 입력 크기에 따라 얼마나 달라지는지

같은 도구도 외부 서버 상태와 입력에 따라 실행시간이 크게 달라질 수 있다.

```text
search("한 건")        → 2초
search("전체 문서")    → 40초
search("전체 문서")    → 외부 서버 장애로 타임아웃
```

그러므로 다음 방식은 안전한 기본 설계가 될 수 없다.

```text
도구 설명을 LLM이 읽음
  → 짧은지 긴지 추측
  → 동기 또는 백그라운드 선택
```

LLM의 판단은 실행 계획을 돕는 힌트로는 쓸 수 있지만, 서버 자원·권한·타임아웃을
결정하는 보안 및 운영 정책으로 쓰면 안 된다.

## 4. 알 수 없는 MCP에 적용할 현실적인 기본 정책

도구별 추가 메타데이터를 필수로 요구하지 않는다는 제품 전제를 유지한다. 대신 모든
MCP 호출에 플랫폼 공통 방어를 적용한다.

1. 실행 hard timeout
2. 팀·계정·실행별 동시 호출 수 제한
3. 입력 및 출력 크기 제한
4. 실행시간, 성공·실패, timeout 관측
5. side effect 가능성이 있는 도구의 승인 정책
6. 재시도 시 중복 실행을 막는 idempotency 정책
7. 연결 해제·자격증명 변경 시 실행 권한 재검증

과거 실행시간은 다음 키로 분리해 기록할 수 있다.

```text
(team_id, mcp_server_id, tool_name)
```

이 통계는 사용자에게 예상 시간을 보여주거나 timeout 기본값을 개선하는 데 사용할 수
있다. 하지만 다음 호출도 같은 시간 안에 끝난다는 보장은 없으므로, hard timeout과
동시성 제한을 대체하지 않는다.

## 5. Background와 Worker의 의미

Background는 사용자의 HTTP 요청이 끝나도 작업을 계속 살려 두는 실행 방식이다.
Worker는 그 작업을 실제로 실행하는 별도 프로세스다. Worker 자체는 LLM이나
서브에이전트가 아니다.

```text
현재
브라우저 → Django가 직접 Deep Agent 실행 → 결과 응답

Background 구조
브라우저 → Django가 작업표 저장 → 즉시 접수 응답
                         ↓
                    Worker가 작업표를 가져감
                         ↓
                    Deep Agent 실행·결과 저장
```

여기서 필요한 핵심은 `agent_job`과 같은 영속 작업 레코드다.

```text
QUEUED → RUNNING → SUCCEEDED
                 ├→ WAITING_APPROVAL → RUNNING
                 ├→ FAILED
                 └→ CANCELLED
```

이 구조를 도입하면 실행시간을 미리 맞힐 필요는 줄어든다. 모든 실행을 Worker에 맡기고
웹 계층은 잠깐 결과를 기다릴 수 있다. 빨리 끝나면 기존 채팅처럼 바로 보여주고,
아직 실행 중이면 작업 카드로 전환한다. 이미 시작한 동기 함수나 MCP 호출을 실행
도중 다른 프로세스로 옮길 수는 없으므로, 이 방식을 쓰려면 실행 시작부터 Worker가
소유해야 한다.

다만 Worker 도입은 현재 채팅 스트리밍, LangGraph checkpoint, HITL resume,
`agent_run`/`tool_call` 추적, 취소 및 장애 복구를 함께 바꾸는 큰 작업이다. 장시간
작업을 요청과 분리해야 한다는 제품 요구가 확인되기 전에는 구현하지 않는다.

## 6. AsyncSubAgent와 AsyncSubAgentMiddleware의 정확한 역할

설치된 `deepagents==0.7.5`에서 `AsyncSubAgent`는 원격 Agent Protocol 서버에
배포된 에이전트의 접속 명세다.

```python
{
    "name": "remote-researcher",
    "description": "장시간 조사를 수행한다",
    "graph_id": "research-agent",
    "url": "https://agent-server.example.com",
}
```

`create_deep_agent()`는 `subagents` 항목에 `graph_id`가 있으면 이를 일반
`SubAgent`/`CompiledSubAgent`와 분리하고 `AsyncSubAgentMiddleware`를 자동으로
붙인다. 이 미들웨어가 Root에 제공하는 기능은 다음과 같다.

- `start_async_task`: 원격 실행을 시작하고 task ID를 즉시 받음
- `check_async_task`: 상태와 결과 확인
- `update_async_task`: 실행 중인 원격 작업에 추가 지시
- `cancel_async_task`: 원격 작업 취소
- `list_async_tasks`: 추적 중인 작업 목록 조회

따라서 이 기능은 단순한 Python `async/await`나 로컬 병렬 실행 스위치가 아니다.

```text
AsyncSubAgent       = 원격 에이전트 주소와 graph ID
AsyncSubAgentMiddleware = 원격 작업을 시작·조회·수정·취소하는 연결 계층
```

MCP 서버는 Tool Protocol 서버이고, AsyncSubAgent가 요구하는 것은 Agent Protocol
서버다. 사용자가 MCP 서버를 연결했다고 해서 그 서버를 AsyncSubAgent로 실행할 수
있는 것은 아니다.

## 7. 현재 프로젝트에 AsyncSubAgentMiddleware를 바로 넣지 않는 이유

현재 사용자 제작 Child는 `subagents/builder.py`에서 `CompiledSubAgent`로 만들어져
같은 애플리케이션 런타임 안에서 실행된다. 원격 Agent Protocol에 배포된 사용자
에이전트를 등록하는 제품 기능은 아직 없다.

`AsyncSubAgentMiddleware`만 추가해도 다음 문제는 해결되지 않는다.

- 자유 연결 MCP의 실행시간 예측
- 로컬 Child의 요청 수명 분리
- Django worker 점유
- 플랫폼 작업 목록과 완료 알림
- 로컬 작업의 장애 복구와 재시도
- 백그라운드 HITL 승인

원격 Agent Protocol 에이전트를 연결하는 기능이 제품 범위에 들어올 때 이 미들웨어를
어댑터로 추가한다. 플랫폼 자체의 장시간 실행 요구는 별도의 job/Worker 설계로 다룬다.

## 8. 다음 설계 주제: 에이전트 병렬 실행

백그라운드 실행과 병렬 실행은 별개의 축이다.

```text
동기 + 직렬: task(A) 완료 후 task(B)
동기 + 병렬: task(A), task(B)를 같은 모델 응답에서 호출하고 모두 기다림
비동기 + 단일: 원격 작업 A를 시작하고 기다리지 않음
비동기 + 병렬: 원격 작업 A, B를 각각 시작하고 기다리지 않음
```

다음 설계에서는 현재 동기 `task` 병렬 실행을 기준으로 아래 질문을 다룬다.

1. 병렬화 결정을 Root LLM에만 맡길 것인가.
2. 독립 작업과 의존 작업을 어떻게 표현할 것인가.
3. 동시 실행 수를 어디에서 제한할 것인가.
4. 같은 도구·MCP·파일·메모리에 대한 동시 접근을 어떻게 보호할 것인가.
5. 병렬 Child의 결과와 이벤트를 어떤 ID로 정확히 연결할 것인가.
6. 하나만 실패했을 때 전체 실행을 실패시킬지 부분 결과를 허용할지.
7. side-effect 도구와 HITL이 병렬 호출에 섞이면 어떻게 처리할 것인가.
8. 팀별 자원 공정성과 비용 상한을 어떻게 둘 것인가.

이 후속 설계에서도 `AsyncSubAgentMiddleware`를 병렬 실행의 필수 전제로 두지 않는다.
현재 `task` 도구의 동기 병렬 실행을 먼저 안정화하고, 백그라운드·원격 실행은 독립된
확장으로 유지한다.
