# 2026-08-19 — 도구 실행 안정화와 권한 정책

> 도구 호출 실패 하나가 대화 전체를 끊던 버그에서 시작해, 같은 종류의
> "숨겨진 실패"를 여섯 군데 더 찾아 고쳤다. 그 사이 main과 두 번
> 동기화했고, 화면 쪽은 진행 카드와 생각 과정 카드를 하나로 묶었다.
> 마지막으로 레거시(`agent`)·신규(`agents`) 스키마 공존 위험 4건을 점검해
> 실제 버그 3개를 더 찾아 고쳤다.

## 1. 도구 호출 실패가 대화 전체를 끊던 버그

**증상**: Jira 프로젝트가 연결 안 된 채로 `jira_get_issues`를 부르면
"요청을 끝내지 못했습니다"만 뜨고 대화가 끊김.

**원인**: 설치된 langgraph 버전의 기본 에러 핸들러(`_default_handle_tool_errors`)가
langgraph 자체 예외(`ToolInvocationError`)만 잡고 우리 코드의 `ToolInputError`는
그대로 다시 던져서, 도구 하나 실패가 실행 전체를 크래시로 만들었다.

**수정**(`services/agent_runtime/factory.py`): 도구 실행 예외를
`langchain_core.tools.ToolException`으로 바꿔 던지고 `handle_tool_error=True`를
켜서 `BaseTool.run()` 선에서 잡히게 했다 — `tool_completed`는 여전히 FAILED로
뜨고 사유도 그대로 보이면서, 대화는 안 끊긴다.

**main과의 정책 조율**: 팀원이 같은 버그를 먼저 고쳐 뒀는데(`73bc79c`)
"말할 수 있는 예외만 봐주고 그 밖은 크래시" 정책이었다. 그 판단(원인 모를
장애는 숨기지 않는다)은 그대로 가져오고, "봐주는" 방식만 상태 마스킹 없는
쪽으로 유지했다 — `services.harness.runner.SPEAKABLE_ERRORS` 공개 상수를
같이 쓴다.

## 5. 서브 에이전트 실행 오류 — 저장은 되는데 실행이 안 됨

**증상**: 메인 에이전트에 자신이 만든 DRAFT 서브 에이전트를 붙여 저장까지는
됐는데, 실행하면 `InactiveSubagentError`로 끊김.

**원인**: "본인 소유 DRAFT는 서브 에이전트로 써도 된다"는 완화 규칙이 저장
API(`_build_subagent_refs`)에는 있는데, 실행 시점에 쓰는 조회 함수
(`AgentSubagentRepository.list_for_parent_version`)에는 빠져 있었다 — 저장할
땐 통과하고 실행할 때만 걸림.

**수정**(`backend/db/agent_platform.py`, `services/agent_runtime/loader.py`):
자식의 `owner_account_id`도 같이 조회해서 두 경로가 같은 기준을 쓰게 맞췄다.
Builder "테스트 실행" 경로(`_resolve_draft_subagent`)에도 같은 문제가 있어
함께 고쳤다.

## 7. Jira 자격증명 — 팀장 계정으로 통일

**수정**(`backend/db/repositories.py`, `services/harness/registry.py`,
`apps/projects/api_views.py`): `TeamRepository.leader_account_id()` 추가.
프로젝트 갱신(`ProjectTaskSyncAPIView`/`TeamTaskSyncAPIView`)과 챗의
`jira_get_issues`/`jira_create_issues`가 이제 팀장 계정의 Jira 자격증명을
쓴다 — 프로젝트·권한 확인은 여전히 요청자 자신의 계정 기준.

실제 팀원 계정으로 검증: 자격증명 조회가 정확히 팀장 계정으로 넘어가는 것,
그리고 실제 Jira 소스가 붙은 프로젝트로 갱신 버튼을 눌러 확인. (검증 중
팀장의 실제 Jira 토큰 갱신을 잘못 건드려 `EXPIRED`로 바뀐 것은 이 코드
수정과 무관한 별개 사고 — 재연결 필요.)

## 8. 승인 필요 도구가 "존재하지 않는다"고 판단하던 버그

**증상**: `side_effect=True`(승인 필요) 도구가 붙은 에이전트를 팀원 계정으로
쓰면, 모델이 그 도구가 아예 없는 것처럼 답함.

**원인**: `runtime_policy.filter_tools_for_role()`이 그래프를 짓기 전에
`member` 역할에서 승인 필요 도구(내장 도구 + MCP 도구 전부)를 통째로
지워서, 모델이 그 도구를 받은 적이 없었다 — 사실이었다. Builder 화면의
"승인 필요" 표시는 "승인하면 쓸 수 있다"로 읽히는데 실제로는 "팀원에겐
안 보임"이었다.

**정책 결정**(지훈 확인): 노출은 막지 않고, 실행하려 하면 이유를 말해
준다 — 이미 있던 실행 시점 재검사(`_run()`)를 유일한 방어선으로 삼는다.

**수정**:
- `runtime_policy.py` — 노출 필터(`filter_tools_for_role`) 삭제, 실행 허용
  판단(`is_tool_allowed_for_role`)만 남김
- `factory.py` — `build()`가 역할과 무관하게 전부 노출. 승인 대기
  (`interrupt_on`)는 여전히 역할별로 걸러서, 팀원이 부르면 승인 카드 없이
  곧바로 거부됨(승인 카드를 띄우면 부른 사람 본인이 눌러 승인해 버릴 수
  있어서). 권한 거부는 `ToolPermissionError`(크래시)에서 `ToolException`
  (대화 유지)으로 변경
- `exceptions.py` — 안 쓰게 된 `ToolPermissionError` 삭제
- 테스트 갱신, 실제 팀원 계정으로 검증(도구를 실제로 시도하고 권한 없음
  사유를 정상적으로 전달받음)

## 10. 레거시(`agent:*`)·신규(`agents`) 스키마 공존 위험 4건 점검

팀원이 정리해 전달한 위험 목록을 하나씩 코드로 확인했다.

| 항목 | 결론 |
|---|---|
| 옛 대화를 다시 열면 새 엔진이 `agent:*` 위임을 못 알아들어 깨질 수 있음 | **재현 안 됨** — `_history()`가 애초에 도구 호출 구조 자체를 복원하지 않는다(평문 텍스트만 다시 넣음). DB에도 그런 흔적을 가진 대화가 0건 |
| `agent`/`agents` 테이블 ID 채번이 반대 방향으로 충돌할 수 있음 | **실제 버그** — 이미 한 번 발생(`AG001`이 두 테이블에 각각 다른 에이전트로 존재), 다음 채번도 실제 기본 챗 에이전트 ID(`AG004`)와 겹칠 상황이었음 |
| `agent_versions.model`이 NULL이면 실행이 깨질 수 있음 | **실제 버그**(코드에 자체 인지 주석 있음) — 지금 ACTIVE 에이전트 중엔 안 걸림 |
| `_check_tool_refs`가 일부 옛 엔드포인트에서 예외 처리 없이 불림 | 팀원이 지목한 함수(`agent_platform.py`)는 안전함. 근데 **동명이인 함수**(`apps/agents/api_views.py`)가 진짜로 3곳에서 안 잡히고 있었음 |

## 11. 위 4건 중 실제 버그 3개 수정

**ID 역방향 충돌** — `_next_agents_id()`를 `_next_shared_agent_id()`로 넓혀서
옛 `agent` 테이블에 새로 만들 때도(`AgentCrudRepository.create()`) 두 테이블
MAX를 같이 본다. 검증: 다음 발급 ID가 `AG004`(충돌)가 아니라 `AG049`로 나옴.

**`model` NULL 방어** — `ModelConfigResolver.resolve()` 맨 앞에서 빈 값이면
`ModelUnavailableError`로 먼저 막는다. 덤으로 `apps/chat/api_views.py`의
`_relay()`가 이런 우리 쪽 예외(`AgentRuntimeError`)를 잡을 때 **클래스
이름만 보여주고 실제 메시지는 버리고 있던 것**도 같이 고쳤다 — 그 밖의
예상 못 한 예외는 여전히 클래스 이름만 남긴다(문자열에 원문·토큰이 섞일
수 있어서). 검증: 실제로 "AttributeError" 대신 "이 에이전트에는 아직
모델이 설정되지 않았습니다"가 사용자에게 뜸.

**`_check_tool_refs`(api_views.py 쪽) 예외 미처리** — `POST /api/agents/`·
`PUT /api/agents/<id>/`·`POST /api/agents/<id>/activate/` 세 곳 다
try/except로 감쌌다. 검증: 팀 없는 계정으로 직접 호출 테스트 → 500 대신
403("팀에 속하지 않은 계정입니다")으로 정상 응답.
