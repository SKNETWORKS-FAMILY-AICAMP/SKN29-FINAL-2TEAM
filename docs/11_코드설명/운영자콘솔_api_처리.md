## 0. 공통 구조

- 앱 위치: `apps/ops/`(Django, ORM 미사용 — `DB/schema.sql` 테이블을 Repository가 raw SQL로 직접 조회).
- 라우트 prefix: `/api/ops/`.
- 인증: `Authorization: Bearer <토큰>` 헤더. 토큰 유효기간은 2시간이며, 일반 로그인 토큰과는 서명 salt가 달라 서로 바꿔 쓸 수 없다.
- **관리자 인증이 필요한 API**(`/auth/me/`, `/auth/logout/`, `/overview/`, `/organizations/`, `/accounts/...`, `/invites/...`, `/connectors/`, `/audit/...`, `/policies/...`)는 토큰 서명·만료 확인에 더해 **요청마다 DB를 다시 조회**해서 계정이 여전히 관리자(`is_admin = true`)이고 상태가 `ACTIVE`인지 재확인한다. 로그인 이후 관리자 권한이 회수되거나 계정이 잠기면, 유효기간이 남은 토큰이라도 다음 요청부터 즉시 차단된다.
- 관리자 권한 부여·회수는 API로 할 수 없다. 별도 스크립트를 호스트에서 직접 실행해야만 바뀐다.
- DB 조회·연결 실패는 인증 단계에서 발생하든 요청 처리 중 발생하든 관계없이 전부 `{"detail": "데이터베이스 요청을 처리할 수 없습니다."}` + `503`으로 통일해서 응답한다.
- 정의되지 않은 HTTP 메서드로 호출하면(예: 조회 전용 API에 `POST`) `405`와 `{"detail": "메서드 \"POST\"는 허용되지 않습니다."}`를 반환한다. 정의되지 않은 쿼리 파라미터는 조용히 무시된다.

## 1. 섹션 1 — 관리자 로그인

### 1.1 `POST /api/ops/auth/login/`

요청 바디: `{"email": string, "password": string}`

| # | 입력·상황 | HTTP | 응답 `detail` | 비고 |
|---|---|---|---|---|
| 1 | `email` 필드 누락 | 400 | `{"email": ["이 필드는 필수 항목입니다."]}` | |
| 2 | `password` 필드 누락 | 400 | `{"password": ["이 필드는 필수 항목입니다."]}` | |
| 3 | 이메일 형식이 아님 | 400 | `{"email": ["유효한 이메일 주소를 입력하세요."]}` | |
| 4 | 빈 JSON(`{}`) | 400 | 두 필드 오류를 함께 반환 | |
| 5 | JSON 자체가 깨짐 | 400 | `{"detail": "JSON parse error - ..."}` | 파서가 만드는 진단 메시지라 영어로 나온다 |
| 6 | 가입되지 않은 이메일 | 401 | `이메일 또는 비밀번호가 올바르지 않습니다.` | 계정 존재 여부를 노출하지 않으려고 비밀번호 오류와 문구를 통일 |
| 7 | 비밀번호 불일치 | 401 | `이메일 또는 비밀번호가 올바르지 않습니다.` | |

## 2. 섹션 2 — 운영 현황

### 2.1 `GET /api/ops/overview/`

읽기 전용, 입력값 없음. 인증 실패 응답은 1.2절과 동일하다.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰 | 200 | 아래 2.2절 응답 구조 |
| 10 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

### 2.2 응답 구조

```json
{
  "org_count": 9,
  "accounts": { "total": 2, "locked": 0, "duplicate_mapping": 0, "needs_review": 0 },
  "connectors": { "total": 0, "connected": 0, "expired": 0, "error": 0 },
  "invites": { "pending": 0, "expiring_today": 0 },
  "recent_activity": [
    { "audit_id": "AL012", "action": "OPS_LOGIN", "target_type": null, "target_id": null,
      "occurred_at": "2026-07-30T06:13:13.577244Z", "actor_display_name": "관리자", "actor_email": "rhksflwk@halil.com" }
  ]
}
```

각 필드의 산출 방식:

| 필드 | 산출 방식 |
|---|---|
| `org_count` | 활성 상태(`status='ACTIVE'`)인 조직 수 |
| `accounts.total` | 전체 계정 수 |
| `accounts.locked` | 그중 상태가 `LOCKED`인 계정 수 |
| `accounts.duplicate_mapping` | 유효한(`VERIFIED`) 직원 연결이 2개 이상인 계정 수(계정 1개가 여러 직원에 연결되는 것을 스키마가 막지 않음) |
| `accounts.needs_review` | `locked`이거나 `duplicate_mapping`인 계정의 합(중복 집계 없이) |
| `connectors.*` | 연결 서비스 상태(`CONNECTED`/`EXPIRED`/`ERROR`)별 건수 |
| `invites.pending` | 아직 만료되지 않은 대기 중 초대 수 |
| `invites.expiring_today` | 그중 오늘 만료 예정인 수 |
| `recent_activity` | 최근 감사 로그 5건(수행자 이름·이메일 포함) |

"오늘 확인할 일" 카드는 `accounts.needs_review`, `connectors.expired + connectors.error`, `invites.expiring_today` 값이 각각 0보다 클 때만 하나씩 생성되고, 셋 다 0이면 "확인이 필요한 항목이 없습니다."를 표시한다. 카드에는 건수와 이동 링크만 있고 조직명·직원 ID 같은 세부 항목은 포함하지 않는다.

계정·연결 서비스 총합이 0일 때는 비율 계산에서 0으로 나누지 않도록 처리해 그래프가 항상 0%로 표시되며, `accounts.total`/`connectors.total`이 0이면 막대그래프 대신 "등록된 계정이 없습니다."/"연결된 서비스가 없습니다." 문구를 보여준다.

## 3. 섹션 3 — 연결 조직 현황

### 3.1 `GET /api/ops/organizations/`

읽기 전용, 입력값 없음. 인증 실패 응답은 1.2절과 동일하다.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰, 조직이 1개 이상 존재 | 200 | 아래 3.2절 응답 구조 |
| 10 | 정상 토큰, 활성 조직이 0개 | 200 | 빈 배열(`[]`) — 오류가 아니라 정상적인 빈 목록으로 처리 |
| 11 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

### 3.2 응답 구조

```json
[
  {
    "org_id": "A002", "up_org_id": "A001", "mgr_id": "PX002", "name": "개발팀",
    "org_type": "DEPARTMENT", "status": "ACTIVE",
    "member_count": 1, "total_member_count": 18, "mapped_count": 0, "issue_count": 0
  }
]
```

각 필드의 산출 방식:

| 필드 | 산출 방식 |
|---|---|
| `org_id`/`up_org_id`/`mgr_id`/`name`/`org_type`/`status` | 조직 원본 정보. `status='ACTIVE'`인 조직만 포함 |
| `member_count` | 그 조직에 **직속**된 직원 중 재직 상태(`emp_status='ACTIVE'`)인 인원 수 |
| `total_member_count` | 그 조직 자신 + 모든 하위 조직에 직속된 인원까지 합친 전체 인원 수. 하위 조직이 없으면 `member_count`와 같다 |
| `mapped_count` | `member_count`(직속) 중 플랫폼 계정에 유효하게 연결된 인원 수. `member_count - mapped_count`가 아직 계정이 연결되지 않은 인원 수다 |
| `issue_count` | 직속 직원 중, 연결된 계정이 잠김(`LOCKED`) 상태이거나 중복 연결(2.2절 `duplicate_mapping`과 같은 정의) 상태인 경우의 수 |

`mapped_count`/`issue_count`는 `total_member_count`가 아니라 `member_count`(직속) 기준으로 계산된다. 모든 값은 조회 시점 기준으로 계산되어, 계정 상태가 바뀌면 다음 조회부터 바로 반영된다.

`up_org_id`는 DB 제약으로 참조 무결성이 강제되지 않는 컬럼이라 다음 두 가지 비정상 데이터도 오류 없이 처리한다.

- 가리키는 상위 조직이 존재하지 않는 경우: 조직 하나하나가 독립적으로 조회되므로 깨진 상위 참조가 있어도 그 값을 그대로 반환하고 전체 목록 조회에는 영향이 없다.
- `up_org_id`가 순환 참조를 이루는 경우(예: A의 상위가 B, B의 상위가 다시 A): `total_member_count` 집계 쿼리가 조직마다 정확히 한 번만 방문하도록 처리되어 있어 요청이 멈추거나 오류를 내지 않고 정상 응답한다.

### 3.3 화면 처리

이 화면은 운영자가 People DB 조직도 자체를 열람하는 화면이 아니라, **조직별로 플랫폼 연동이 얼마나 돼 있는지**를 확인하는 화면이다. 그래서 조직을 선택했을 때 하위 조직 목록을 보여주는 대신, 그 조직의 계정 연동 현황(직속 인원, 전체 인원, `계정 연결 M명 / N명`, `확인 필요 건수`)을 보여준다. 확인 필요 건수가 0보다 크면 계정 관리 화면으로 이동하는 버튼만 제공하고, 어떤 계정이 문제인지 목록으로 나열하지는 않는다(그 목록은 계정 관리 화면의 역할).

- 조직 트리는 상위 조직 아래에 하위 조직이 접히고 펼쳐지는 방식으로 표시된다. 하위 조직이 있는 조직에는 펼침·접힘 화살표가 붙고, 접으면 그 아래 하위 조직 전체가 화면에서 숨겨진다(하위 조직이 많은 트리에서 스크롤을 줄이기 위함). 검색 중에는 접기·펼치기 대신 검색어와 일치하는 조직만 평면 목록으로 보여준다.
- 트리에 표시되는 "구성원" 수치는 `total_member_count`(하위 조직 포함 전체 인원)를 쓴다. 하위 조직이 없는 조직은 `member_count`와 같은 값이라 차이가 없다.
- 트리의 들여쓰기는 `up_org_id`를 실제로 따라 올라가며 계산한 깊이를 쓴다. 상위 조직이 없거나(참조가 끊긴 경우) 순환 참조가 있으면 그 지점에서 계산을 멈춰 무한 루프에 빠지지 않는다. 화면에는 2단계까지만 들여쓰기가 있어 그보다 깊은 조직은 2단계로 표시한다.
- `org_type` 값은 `COMPANY`(회사), `DEPARTMENT`(본부), `SUPERVISORY`(팀), `COST_CENTER`(비용 센터)로 화면에 표시하고, 매핑에 없는 값이 오면 원본 값을 그대로 보여준다.
- 선택한 조직에 소속 직원이 없으면 계정 연결 현황 대신 "소속 직원이 없습니다."를 표시한다.
- 연결된 조직이 하나도 없으면 "연결된 조직이 없습니다."를, 검색 결과만 없으면 "조건에 맞는 연결 조직이 없습니다."(목록)와 "검색 조건을 변경하면 조직 상세를 확인할 수 있습니다."(상세 패널)를 구분해서 보여준다.
- 조회에 실패하면 오류 메시지와 "다시 시도" 버튼을 보여주고, 인증이 만료된 경우(401)에는 관리자 로그인 화면으로 이동시킨다.

| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰 | 200 | 아래 4.4절 응답 구조 |
| 10 | 계정이 0개(이론상 불가하지만) | 200 | 빈 배열(`[]`) |
| 11 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

### 4.2 `POST /api/ops/accounts/{account_id}/lock/`, `POST /api/ops/accounts/{account_id}/unlock/`

본문 없음. URL의 `account_id`만으로 동작한다.

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하지 않는 `account_id` | 404 | `존재하지 않는 계정입니다: {account_id}` |
| 10 | 대상 계정 상태가 `WITHDRAWN` | 400 | `탈퇴한 계정은 상태를 변경할 수 없습니다.` |
| 11 | `lock`을 자기 자신의 계정에 호출 | 403 | `본인 계정은 잠글 수 없습니다.` |
| 12 | 이미 목표 상태와 같음(예: `ACTIVE`인데 `unlock` 호출) | 400 | `이미 처리된 상태입니다.` |
| 13 | 정상 처리 | 200 | `{"account_id": "...", "account_status": "LOCKED"/"ACTIVE"}` — 변경 전/후 상태를 감사 로그(`ACCOUNT_LOCK`/`ACCOUNT_UNLOCK`)에 함께 기록 |
| 14 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

동시에 들어온 잠금/해제 요청이 서로 낡은 상태를 덮어쓰지 않도록, 대상 계정 행을 잠근(`SELECT ... FOR UPDATE`) 상태에서 상태를 확인·변경한다 — 같은 계정에 대한 `lock` 요청 두 개가 동시에 들어와도 하나만 적용되고 나머지는 `이미 처리된 상태입니다`(400)로 정리되며, 감사 로그도 정확히 한 건만 남는다.

관리자 자신의 계정이 잠기면(다른 관리자가 잠갔거나, DB에서 직접 상태를 바꾼 경우) 그 즉시 본인 토큰의 관리자 인증 자체가 실패하므로(0장의 매 요청 재확인 규칙), **본인 계정을 스스로 `unlock`할 방법이 없다** — 다른 관리자가 풀어주거나 DB를 직접 고쳐야 한다.

### 4.3 `POST /api/ops/accounts/{account_id}/unlink-person/`

본문 없음. 해당 계정에 연결된 모든 유효(`VERIFIED`) 직원 연결을 해제(`REVOKED`)한다 — 하나만 있든 중복으로 여러 개 있든 전부 해제한다.

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하지 않는 `account_id` | 404 | `존재하지 않는 계정입니다: {account_id}` |
| 10 | 연결된 직원이 하나도 없는 계정 | 404 | `연결된 직원 정보가 없습니다.` |
| 11 | 링크가 있지만 전부 이미 해제(`REVOKED`) 상태인 계정 | 404 | `연결된 직원 정보가 없습니다.` — 10과 동일하게 취급(다시 해제할 유효 링크가 없음) |
| 12 | 연결된 직원이 1개 이상 있는 계정 | 200 | `{"account_id": "...", "revoked_person_ids": ["PB001", ...]}` — 해제된 직원 ID 전부를 감사 로그(`ACCOUNT_UNLINK_PERSON`)에 함께 기록 |
| 13 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

`account_id` 조건으로 해당 계정의 링크만 골라 해제하므로, 다른 계정에 연결된 직원 정보는 영향받지 않는다.

### 4.4 응답 구조(`GET /api/ops/accounts/`)

```json
[
  {
    "account_id": "UA002", "email": "acct-test@halil.com", "display_name": "테스트대상",
    "account_status": "ACTIVE", "mapping_status": "DUPLICATE", "link_count": 2,
    "person": { "person_id": "PB001", "name": "박승우", "org_id": "A003", "org_name": "백엔드파트" },
    "services": ["GOOGLE_DRIVE", "JIRA"]
  }
]
```

각 필드의 산출 방식:

| 필드 | 산출 방식 |
|---|---|
| `account_id`/`email`/`display_name`/`account_status` | 계정 원본 정보. `WITHDRAWN` 계정도 포함해 전체 계정을 반환 |
| `link_count` | 그 계정에 연결된 유효(`VERIFIED`) 직원 링크 수 |
| `mapping_status` | `link_count`로부터 계산 — 0이면 `UNMAPPED`, 1이면 `LINKED`, 2 이상이면 `DUPLICATE`(2.2절 `duplicate_mapping`과 같은 정의) |
| `person` | 대표로 보여줄 직원 1명(가장 먼저 연결된 링크). 링크가 없으면 `null` |
| `services` | 그 계정의 연결 서비스 중 `auth_status='CONNECTED'`인 것만 유형별로 나열(만료·오류 상태는 제외) |

`person.person_id`는 링크(`user_person_link`) 자체가 있는지로만 결정되고, `person.name`/`person.org_id`/`person.org_name`은 그 직원 레코드를 실제로 찾았는지로 결정된다 — 그래서 링크는 있는데 가리키는 직원 레코드가 없는 경우(참조 무결성이 DB 제약으로 강제되지 않음)에도 `person`이 통째로 `null`이 되지 않고, `person_id`만 채워지고 나머지가 `null`인 상태로 나온다.

### 4.5 `account_id` 처리

URL의 `{account_id}`는 그대로 파라미터 바인딩되어 SQL에 문자열로만 비교되므로, 어떤 값이 들어와도 안전하다.

- 존재하지 않는 값, SQL 구문처럼 보이는 문자열, 컬럼 길이(`VARCHAR(5)`)보다 긴 문자열: 전부 동일하게 `404 존재하지 않는 계정입니다: {입력값}`으로 처리되고 서버 오류가 나지 않는다.
- `/`가 포함된 값(예: URL 인코딩된 `%2F`)은 URL 라우팅 단계에서 아예 그 경로와 일치하는 패턴이 없어 Django 기본 404 페이지로 응답한다 — 이 프로젝트의 다른 모든 API(`invites/{id}`, `projects/{id}` 등)도 동일한 라우팅 규칙을 쓰므로 이 화면만의 특이 동작은 아니고, 실제 `account_id`는 하이픈·슬래시 없는 5자리 코드로만 발급되어 정상 경로에서는 발생하지 않는다.

### 4.6 화면 처리

- 계정 상태 필터는 `전체`/`확인 필요`(매핑이 `LINKED`가 아니거나 상태가 `LOCKED`)/`정상`/`잠김`/`탈퇴` 다섯 가지를 실제 값 기준으로 구분한다.
- 상세 패널의 작업 버튼은 서버가 거부할 게 뻔한 조작을 애초에 보여주지 않는다: 이미 `LOCKED`면 "계정 정지" 대신 "계정 재활성"만, 상태가 `WITHDRAWN`이면 두 버튼 다 감추고 안내 문구만, 본인 계정이면 "계정 정지" 버튼 자체를 감춘다. "직원 연결 해제"는 `mapping_status`가 `DUPLICATE`일 때만 노출한다.
- 작업 확인 모달은 처리 중에는 버튼을 비활성화해 중복 제출을 막고, 처리 결과와 무관하게 성공하면 최신 목록을 다시 불러온다.
- 계정이 0개면 "등록된 계정이 없습니다."를, 검색·필터 결과가 없으면 "조건에 맞는 계정이 없습니다."를 표시한다.
- 조회에 실패하면 오류 메시지와 "다시 시도" 버튼을, 조작 중 오류가 나면 서버가 응답한 문구를 그대로 토스트로 보여준다. 인증이 만료된 경우(401)에는 관리자 로그인 화면으로 이동시킨다.

## 5. 섹션 5 — 계정 연결·초대 현황

### 5.1 `GET /api/ops/invites/`

읽기 전용, 입력값 없음. 인증 실패·DB 연결 실패 응답은 1.2절·3.1절과 동일하다.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰 | 200 | 아래 5.4절 응답 구조 |
| 10 | 발급된 초대가 0건 | 200 | 빈 배열(`[]`) |
| 11 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

### 5.2 `POST /api/ops/invites/{invite_id}/discard/`

본문 없음. 대기 중(`PENDING`, 화면에 `만료`로 보이는 것 포함)인 초대만 폐기(`REVOKED`)한다 — 이미 수락됐거나, 이미 취소됐거나, 존재하지 않는 초대는 전부 같은 메시지로 거부한다(어느 쪽인지 구분해서 알려주지 않음).

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하지 않는 `invite_id` | 404 | `폐기할 수 있는 초대가 아닙니다.` |
| 10 | 이미 수락된(`ACCEPTED`) 초대 | 404 | `폐기할 수 있는 초대가 아닙니다.` |
| 11 | 이미 폐기된(`REVOKED`) 초대 | 404 | `폐기할 수 있는 초대가 아닙니다.` |
| 12 | 대기 중이지만 만료 시각이 지난 초대(화면엔 `만료`로 표시) | 200 | 폐기 가능 — DB에는 여전히 `PENDING`으로 남아있는 상태라, 아직 정리되지 않은 만료 건도 폐기할 수 있다 |
| 13 | 만료 전 대기 중인 초대 | 200 | `{"invite_id": "...", "status": "REVOKED"}` — 감사 로그(`INVITE_DISCARD`)에 대상 직원 ID 기록 |
| 14 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

같은 초대에 폐기 요청이 동시에 여러 번 들어와도, `UPDATE ... WHERE status = 'PENDING' ... RETURNING`이 단일 SQL 문으로 원자적으로 처리되어 하나만 적용되고 나머지는 9번 행(404)으로 정리된다 — 감사 로그도 정확히 한 건만 남는다.

### 5.3 `POST /api/ops/invites/{invite_id}/unlink/`

본문 없음. 이 초대의 직원(`person_id`)이 현재 연결된 계정을 찾아, **그 계정에 연결된 직원 링크 전부**를 해제한다(4.3절의 `unlink_all()`을 그대로 재사용 — 계정 1개가 이 초대 말고 다른 초대로도 중복 연결돼 있으면 그것까지 함께 해제된다).

| # | 입력·상황 | HTTP | 응답 `detail` |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하지 않는 `invite_id` | 404 | `존재하지 않는 초대입니다: {invite_id}` |
| 10 | 아직 수락된 적 없는(연결이 생긴 적 없는) 초대 | 404 | `이미 연결이 해제됐거나 연결된 적이 없는 초대입니다.` |
| 11 | 이미 다른 경로로 연결이 해제된 초대 | 404 | 〃 |
| 12 | 연결이 남아있는 초대 | 200 | `{"invite_id": "...", "account_id": "...", "revoked_person_ids": [...]}` — 그 계정에 연결돼 있던 직원 전부의 ID를 포함(1명이든 중복 연결된 여러 명이든), 감사 로그(`ACCOUNT_UNLINK_PERSON`)에 기록 |
| 13 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

한 계정에 중복 연결된 두 직원을 서로 다른 초대로 각각 연결 해제 요청해도(둘 다 같은 계정을 가리키므로), 먼저 처리된 요청이 그 계정의 링크를 전부 해제하고 나중 요청은 10번 행(404)으로 정리된다 — 계정 링크를 두 번 해제하거나 감사 로그가 중복 기록되지 않는다.

`team_org_id`/`invited_by`가 가리키는 조직·계정이 존재하지 않거나(참조 무결성이 DB 제약으로 강제되지 않음), `person_id`가 가리키는 직원 레코드가 없어도 오류 없이 처리된다 — 해당하는 `org_name`/`inviter_email`/`person_name`/`person_email`이 `null`로 나올 뿐, 조회·폐기·연결 해제 자체는 정상 동작한다.

### 5.4 응답 구조(`GET /api/ops/invites/`)

```json
[
  {
    "invite_id": "MI003", "person_id": "PB005", "person_name": "서지호", "person_email": "user007@halil.com",
    "org_id": "A003", "org_name": "백엔드파트", "invited_by": "UA001", "inviter_email": "rhksflwk@halil.com",
    "status": "ACCEPTED", "expires_at": "2026-08-06T07:34:03Z", "accepted_at": null, "created_at": "2026-07-30T07:34:03Z",
    "linked_account_id": "UA002", "linked_account_duplicate": true
  }
]
```

각 필드의 산출 방식:

| 필드 | 산출 방식 |
|---|---|
| `invite_id`/`person_id`/`invited_by`/`expires_at`/`accepted_at`/`created_at` | 초대 원본 정보 |
| `person_name`/`person_email`/`org_id`/`org_name` | 초대 대상 직원과 그 소속 조직 정보 |
| `inviter_email` | 초대자(`invited_by`) 계정의 이메일 |
| `status` | 대기 중(`PENDING`)인데 만료 시각이 지났으면 `EXPIRED`로 바꿔 보여주고, 그 외에는 원본 상태(`PENDING`/`ACCEPTED`/`REVOKED`) 그대로 |
| `linked_account_id` | 이 초대 대상 직원이 현재 유효하게 연결된 계정 ID. 아직 연결이 없으면 `null` |
| `linked_account_duplicate` | 그 계정이 이 직원 말고 다른 직원과도 중복 연결돼 있는지(4.4절 `mapping_status`의 `DUPLICATE`와 같은 정의) |

### 5.5 화면 처리

- 초대 상태 필터(`수락 대기`/`수락 완료`/`만료`/`취소됨`)와 연결 조직 필터는 실제로 조회된 데이터에 있는 값만으로 구성한다 — 특정 팀 이름을 미리 정해두지 않는다.
- "이상 초대 폐기" 버튼은 상태가 `수락 대기` 또는 `만료`일 때만 노출한다(둘 다 대기 중 상태를 뜻하고, 5.2절 규칙대로 실제 폐기가 가능한 상태). "중복 직원 연결 해제" 버튼은 `linked_account_duplicate`가 참일 때만 노출한다 — 계정 관리 화면과 동일하게, 정상적으로 1명만 연결된 초대는 연결 해제 대상으로 노출하지 않는다.
- 연결 해제는 이 초대의 직원 한 명이 아니라 **그 계정에 연결된 모든 직원**을 해제하므로, 같은 계정을 가리키는 다른 초대를 나중에 다시 조회하면 이미 함께 해제되어 대상이 없다는 결과가 나올 수 있다(4.3절과 동일한 재사용 동작).
- 발급된 초대가 하나도 없으면 "발급된 초대 기록이 없습니다."를, 검색·필터 결과가 없으면 "조건에 맞는 초대 기록이 없습니다."를 표시한다.
- 조회에 실패하면 오류 메시지와 "다시 시도" 버튼을, 조작 중 오류가 나면 서버가 응답한 문구를 그대로 토스트로 보여준다. 인증이 만료된 경우(401)에는 관리자 로그인 화면으로 이동시킨다.

## 6. 섹션 6 — 연결 서비스 현황

읽기 전용 화면이다. 실제 재연결은 계정 소유자가 설정 화면에서 하므로, 이 섹션에는 조회 API 하나만 있고 쓰기 작업이 없다.

### 6.1 `GET /api/ops/connectors/`

입력값 없음.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰, 연결이 1건 이상 존재 | 200 | 아래 6.2절 응답 구조 |
| 10 | 정상 토큰, 연결이 0건 | 200 | 빈 배열(`[]`) |
| 11 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

### 6.2 응답 구조

```json
[
  {
    "conn_id": "CN001", "account_id": "UA002", "owner_email": "conn-test@halil.com",
    "connector_type": "GOOGLE_DRIVE", "auth_status": "EXPIRED", "connected_at": "2026-07-29T08:00:27Z",
    "person": { "person_id": "PB002", "name": "윤유진", "org_id": "A003", "org_name": "백엔드파트" },
    "diagnosis": "인증이 만료됐습니다.", "next_action": "계정 소유자가 설정에서 재연결"
  }
]
```

각 필드의 산출 방식:

| 필드 | 산출 방식 |
|---|---|
| `conn_id`/`account_id`/`connector_type`/`auth_status`/`connected_at` | 연결 원본 정보. 모든 연결을 포함(만료·오류 상태도 제외하지 않음) |
| `owner_email` | 그 연결을 소유한 계정의 이메일. 계정 자체가 존재하지 않으면(참조 무결성이 DB 제약으로 강제되지 않음) `null` |
| `person` | 소유 계정에 대표로 연결된 직원 1명(4.4절 `person`과 같은 규칙 — 가장 먼저 연결된 링크). 연결된 직원이 없으면 `null` |
| `diagnosis`/`next_action` | `auth_status` 값으로부터 만드는 안내 문구. `CONNECTED`→"정상"/"조치 없음", `EXPIRED`→"인증이 만료됐습니다."/"계정 소유자가 설정에서 재연결", `ERROR`→"연결 중 오류가 발생했습니다."/"계정 소유자가 설정에서 연결 재시도". 이 세 값 외의 상태가 들어오면(`auth_status`는 DB에 CHECK 제약이 없는 컬럼) "알 수 없는 연결 상태입니다: {값}"과 "계정 소유자에게 연결 상태 확인 요청"으로 대체해 오류 없이 응답한다 |

연결을 소유한 계정 자체가 존재하지 않는 경우(`owner_email`이 `null`인 경우)에도 그 연결 자체는 목록에서 빠지지 않고 그대로 나온다 — 소유자를 알 수 없다는 사실 자체가 운영자가 확인해야 할 정보이기 때문에, 소유 계정 존재 여부로 걸러내지 않는다.

`person`도 4.4절과 같은 규칙으로, 링크는 있지만 그 직원 레코드가 없는 경우 `person_id`만 채워지고 `name`/`org_id`/`org_name`은 `null`로 나온다(통째로 `null`이 되지 않음).

### 6.3 화면 처리

- 유형(`인사 정보`/`구글 드라이브`/`Jira`)과 상태(`연결됨`/`확인 필요`/`오류`) 필터는 알려진 값 기준으로 고정 목록을 쓴다. 요약 카드의 유형별 건수·상태 분포는 전부 조회된 데이터에서 그때그때 집계한다.
- 상세 패널에는 소유 계정 이메일과 연결 조직만 표시하고, 연결된 직원의 실명은 표시하지 않는다 — 운영자가 필요한 건 "무엇이 문제인지"이지 "누구인지"가 아니기 때문이다.
- 연결이 하나도 없으면 "연결된 서비스가 없습니다."를, 검색·필터 결과가 없으면 "조건에 맞는 연결 서비스가 없습니다."를 표시한다.
- 조회에 실패하면 오류 메시지와 "다시 시도" 버튼을 보여주고, 인증이 만료된 경우(401)에는 관리자 로그인 화면으로 이동시킨다.

## 7. 섹션 7 — 감사 로그

전부 읽기 전용, 5개 GET 엔드포인트. 입력값은 없다.

### 7.1 공통 인증·오류 처리

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부(5개 엔드포인트 전부 동일) | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰 | 200 | 아래 7.2~7.3절 응답 구조 |
| 10 | 조회 도중 DB 연결 불가(5개 엔드포인트 전부 동일) | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

### 7.2 `GET /api/ops/audit/operations/` — 운영 활동

`audit_log` 최신 200건(수행자 이름·이메일 조인). 이 콘솔 자체의 조치(관리자 로그인·로그아웃, 계정 잠금/해제,
직원 연결 해제, 초대 폐기 등)가 여기 쌓인다 — 지금 바로 데이터가 있는 유일한 탭이다.

```json
{
  "audit_id": "AL093", "actor_account_id": "UA001", "actor_display_name": "관리자", "actor_email": "rhksflwk@halil.com",
  "action": "ACCOUNT_LOCK", "proj_id": null, "target_type": "ACCOUNT", "target_id": "UA002",
  "payload": { "before": "ACTIVE", "after": "LOCKED" }, "occurred_at": "2026-07-30T08:05:20Z"
}
```

`actor_account_id`가 가리키는 계정이 존재하지 않으면(참조 무결성이 DB 제약으로 강제되지 않음) `actor_display_name`/
`actor_email`만 `null`이 되고, `actor_account_id` 원본 값과 기록 자체는 그대로 남는다.

### 7.3 `GET /api/ops/audit/assignment-runs/`, `/recommendations/`, `/validations/`, `/decisions/` — 분석·결정 기록

배정 실행 → 추천 결과 → 검증 결과 → PM 결정으로 이어지는 파이프라인의 저장 결과를 각각 별도 탭으로 조회한다.

| 엔드포인트 | 조회 테이블 | 함께 보여주는 정보 |
|---|---|---|
| `/assignment-runs/` | `assign_run` | 스냅샷의 `proj_id`(`ana_snapshot` 조인), 요청자 이름·이메일(`user_account` 조인) |
| `/recommendations/` | `reco_result` | 업무명(`task` 조인) |
| `/validations/` | `valid_result` | 근거가 된 추천의 실행 ID·업무 ID(`reco_result` 조인) |
| `/decisions/` | `decision_rec` | 결정자 이름·이메일(`user_account` 조인) |

네 엔드포인트 모두 참조가 끊긴 경우(예: `assign_run.snapshot_id`가 가리키는 `ana_snapshot`이 없거나, `requested_by`가
가리키는 계정이 없는 경우) 원본 ID는 그대로 보여주고 조인으로만 채워지는 필드(`proj_id`, 이름·이메일, 업무명 등)만
`null`로 나온다 — 7.2절과 같은 원칙이다.

**중요 — 지금 실제로 비어 있는 이유**: `reco_result`/`valid_result`/`decision_rec`, 그리고 `assign_run`이 참조하는
`ana_snapshot`/`feat_ready_result`/`task`까지, 이 저장소에는 아직 이 테이블들에 쓰는 추천·검증·배정 파이프라인이
없다. 그래서 `/assignment-runs/`부터 `/decisions/`까지 4개 엔드포인트는 지금 전부 빈 배열(`[]`)을 반환한다. 이는
오류가 아니라 파이프라인이 아직 구현되지 않은 정상 상태이며, 나중에 파이프라인이 이 테이블에 쓰기 시작하면 API
코드 변경 없이 그대로 채워진다.

### 7.4 화면 처리

- "운영 활동"과 "분석·결정 기록"(4개 하위 탭) 중 하나를 선택하는 2단 탭 구조다. 각 탭의 데이터는 처음 열 때만
  불러오고, 이후 탭을 오갈 때는 다시 불러오지 않는다(조회 실패로 "다시 시도"를 누르면 그때 다시 불러온다).
- "운영 활동"의 작업 종류 필터는 실제로 조회된 데이터에 있는 `action` 값만으로 구성한다. 4개 분석 탭의 상태·조치
  필터도 마찬가지로 조회된 데이터 기준이다 — 특정 상태값을 미리 정해두지 않는다(파이프라인이 아직 없어 실제로
  어떤 상태값을 쓰게 될지 확정돼 있지 않기 때문).
- PM 결정의 조치(`pm_action`)만 스키마에 명시된 `APPROVE`/`MODIFY`/`REJECT` 세 값을 한글 라벨(승인/수정/반려)로
  표시하고, 그 외 값은 원본을 그대로 보여준다.
- 분석 탭 4개는 데이터가 없으면(파이프라인 미구현) "아직 실행된 배정이 없습니다" 같은 상황 설명 문구를 보여주고,
  검색·필터 결과만 없는 경우와는 다른 문구를 쓴다(전자는 화면 전체를 대체, 후자는 표 안에 빈 행으로 표시).
- CSV 내보내기(현재 목록만)는 클라이언트에서 직접 만든다 — 서버 API를 추가로 부르지 않는다.
- 조회에 실패하면 오류 메시지와 "다시 시도" 버튼을 보여주고, 인증이 만료된 경우(401)에는 관리자 로그인 화면으로 이동시킨다.

## 8. 섹션 8 — 전역 정책

초대 코드 만료 기간 하나와 시스템 공지 CRUD, 그리고 이 둘의 변경 이력 조회로 구성된다. 변경 이력은 별도
테이블 없이 `audit_log`를 `action` 값으로 필터링해 재사용한다(`POLICY_INVITE_TTL_CHANGE`/`NOTICE_CREATE`/
`NOTICE_UPDATE`/`NOTICE_DELETE`).

### 8.1 `GET/PUT /api/ops/policies/invite-ttl/`

초대 코드 만료 기간(`sys_setting.INVITE_EXPIRE_DAYS`)을 조회·변경한다. 이 값은 `apps/accounts`의
`MemberInviteRepository.create()`가 신규 초대를 발급할 때마다 읽어 만료 시각을 계산하는 데 쓰인다 — 운영자
콘솔 밖에서도 실제로 쓰이는 유일한 설정값이다.

| # | 입력·상황 | HTTP | 응답 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | `GET`, 정상 토큰 | 200 | `{"days": 14}` |
| 10 | 설정 행이 아직 없는 상태에서 `GET`(볼륨을 비우지 않고 수동으로 스키마만 반영한 경우) | 200 | 기본값 `{"days": 14}`로 안전하게 대체 — 이 값이 없으면 신규 초대 발급 전체가 막히므로, 조회 실패 대신 기본값으로 응답한다 |
| 11 | `PUT`, `days`가 정수가 아님(문자열 등) | 400 | `{"days": ["유효한 정수를 입력하세요."]}` |
| 12 | `PUT`, `days` 필드 자체가 없음 | 400 | `{"days": ["이 필드는 필수 항목입니다."]}` |
| 13 | `PUT`, `days`가 0 이하 또는 91 이상 | 400 | `초대 만료 기간은 1일에서 90일 사이로 입력해 주세요.` |
| 14 | `PUT`, `days`가 현재 값과 동일 | 400 | `변경된 초대 정책이 없습니다.` |
| 15 | `PUT`, 1~90 범위의 새로운 값(+ 선택적 `reason`) | 200 | `{"days": 30}` — 감사 로그(`POLICY_INVITE_TTL_CHANGE`)에 `before`/`after`/`reason` 기록 |
| 16 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

같은 값으로 동시에 여러 `PUT` 요청이 들어와도, 설정 행을 잠근(`SELECT ... FOR UPDATE`) 상태에서 현재 값과
비교하므로 하나만 실제로 반영되고 나머지는 14번 행(`변경된 초대 정책이 없습니다.`)으로 정리된다 — 계정
잠금/해제(4.2절)와 같은 방식의 동시성 처리다.

### 8.2 `GET/POST /api/ops/policies/notices/`

시스템 공지 목록 조회와 신규 생성.

| # | 입력·상황 | HTTP | 응답 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | `GET`, 정상 토큰 | 200 | 아래 응답 구조. 등록된 공지가 없으면 빈 배열(`[]`) |
| 10 | `POST`, 제목·내용 중 하나라도 공백 | 400 | `공지 제목과 내용을 입력해 주세요.` |
| 11 | `POST`, 날짜·시간 중 하나라도 누락 | 400 | `공지 날짜와 시간을 선택해 주세요.` |
| 12 | `POST`, `status`가 `PUBLISHED`/`SCHEDULED`/`ENDED` 외의 값 | 400 | `{"status": ["\"...\"은 유효하지 않은 선택입니다."]}` |
| 13 | `POST`, `schedule_mode`가 `FROM`/`UNTIL` 외의 값 | 400 | `{"schedule_mode": ["\"...\"은 유효하지 않은 선택입니다."]}` |
| 14 | `POST`, 필수 조건을 모두 만족(+ 선택적 `reason`) | 200 | 생성된 공지 — 감사 로그(`NOTICE_CREATE`)에 `after`/`reason` 기록 |
| 15 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

`schedule_date`(날짜)와 `schedule_time`(시간)은 요청에서 따로 받아 서버에서 프로젝트 표준시(`Asia/Seoul`)
기준의 타임존 인지 시각으로 합친 뒤 `sys_notice.schedule_at`(TIMESTAMPTZ) 한 컬럼에 저장한다.

### 8.3 `PUT/DELETE /api/ops/policies/notices/{notice_id}/`

기존 공지 수정·삭제. 검증 규칙은 8.2절 생성과 동일하다.

| # | 입력·상황 | HTTP | 응답 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 존재하지 않는 `notice_id`(수정·삭제 공통) | 404 | `존재하지 않는 공지입니다.` |
| 10 | `PUT`, 제목·내용 공백 또는 날짜·시간 누락 | 400 | 8.2절 10~11번 행과 동일 문구 |
| 11 | `PUT`, 필수 조건을 모두 만족(+ 선택적 `reason`) | 200 | 수정된 공지 — 감사 로그(`NOTICE_UPDATE`)에 `before`/`after`/`reason` 기록 |
| 12 | `DELETE`, 존재하는 `notice_id`(+ 선택적 `reason`) | 204 | 본문 없음 — 감사 로그(`NOTICE_DELETE`)에 `before`/`reason` 기록 |
| 13 | 처리 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

같은 `notice_id`에 삭제 요청이 동시에 여러 번 들어와도, 단일 `DELETE ... RETURNING`이 원자적으로 처리되어
하나만 적용되고 나머지는 9번 행(404)으로 정리된다.

### 8.4 응답 구조(`GET /api/ops/policies/notices/`)

```json
[
  {
    "notice_id": "NT001", "title": "점검 안내", "content": "정기 점검 진행중",
    "status": "PUBLISHED", "schedule_at": "2026-08-01T09:00:00Z", "schedule_mode": "UNTIL",
    "created_by": "UA001", "created_by_name": "관리자",
    "created_at": "2026-07-30T09:04:52Z", "updated_at": "2026-07-30T09:05:13Z"
  }
]
```

`created_by`가 가리키는 계정이 존재하지 않으면(참조 무결성이 DB 제약으로 강제되지 않음) `created_by_name`만
`null`이 되고, `created_by` 원본 값과 공지 자체는 그대로 남는다. 생성 직후 응답에서는 `created_by_name`을
다시 조회하지 않고 `null`로 내려준다(목록 조회 시에만 조인해서 채운다).

### 8.5 `GET /api/ops/policies/changes/` — 정책 변경 이력

`audit_log`에서 `action`이 `POLICY_INVITE_TTL_CHANGE`/`NOTICE_CREATE`/`NOTICE_UPDATE`/`NOTICE_DELETE`인
행만 최신순으로 반환한다. 입력값은 없다.

| # | 입력·상황 | HTTP | 비고 |
|---|---|---|---|
| 1~8 | 인증 실패 케이스 전부 | 401 | 1.2절 표와 동일 |
| 9 | 정상 토큰 | 200 | 7.2절과 같은 구조(`actor_display_name`/`actor_email` 조인 포함) + `payload`에 `before`/`after`/`reason` |
| 10 | 정책 변경 이력이 0건 | 200 | 빈 배열(`[]`) |
| 11 | 조회 도중 DB 연결 불가 | 503 | `데이터베이스 요청을 처리할 수 없습니다.` |

`POLICY_INVITE_TTL_CHANGE`는 `sys_setting`이 단일 설정 행이라 `target_id`를 채울 5자 이내의 자연스러운 ID가
없으므로 `target_id`는 항상 `null`이고, `target_type`(`SYS_SETTING`)만으로 구분한다. 공지 관련 세 액션은
`target_id`에 `notice_id`가 그대로 들어간다.

### 8.6 화면 처리

- 초대 정책 저장 버튼은 값이 1~90 범위를 벗어나거나 현재 값과 같으면 서버가 그대로 거부하므로, 화면에서도
  동일한 조건을 먼저 검사해 같은 문구를 보여준 뒤에만 실제 요청을 보낸다.
- 공지 목록은 상태별 배지(`게시 중`/`게시 예정`/`종료`)와 게시 일정(`MM.DD HH:mm 부터`/`까지`)을 함께 보여주고,
  상세 모달에서 수정·삭제로 진입한다. 등록된 공지가 없으면 "등록된 공지가 없습니다."를 표시한다.
- "정책 변경 이력" 목록은 각 행 앞에 변경 유형 배지(초대 정책 변경/공지 생성/공지 수정/공지 삭제, 색으로 구분)를
  붙여 어떤 종류의 변경인지 한눈에 훑어볼 수 있게 하고, 화면에는 최신 5건만 미리 보여주고, 항목을 고르면 하단에
  변경 전/후, 변경 시각, 변경 사유(입력하지 않았으면 "입력된 사유 없음"), 변경자를 보여준다. 이력이 없으면
  "정책 변경 이력이 없습니다."를 표시하고, 이 경우 "전체 보기" 버튼 자체를 숨긴다.
- "전체 보기"를 누르면 전체 이력을 변경 유형(전체/초대 정책 변경/공지 생성/공지 수정/공지 삭제) select와 제목·
  변경자 검색으로 걸러볼 수 있는 목록을 모달로 띄운다. 목록은 세로 스크롤로 제한 높이 안에서 내려 보고,
  필터·검색 조건 둘 다 실제로 조회된 데이터 안에서만 걸러낸다(서버에 별도 요청 없이 클라이언트에서 필터링).
  조건에 맞는 이력이 없으면 "조건에 맞는 정책 변경 이력이 없습니다."를 표시한다. 목록에서 항목을 고르면 모달이
  닫히고 화면 하단의 상세(변경 전/후 등)가 그 항목으로 바뀐다.
- 조회에 실패하면 오류 메시지와 "다시 시도" 버튼을 보여주고, 저장·생성·수정·삭제 중 오류가 나면 서버가 응답한
  문구를 그대로 토스트로 보여준다. 인증이 만료된 경우(401)에는 관리자 로그인 화면으로 이동시킨다.
