# 검색 품질 평가 세트

**파싱·청킹·임베딩이 좋아졌는지를 숫자로 말하기 위한 것이다.** 고도화 전에
기준선을 재 두지 않으면 나중에는 못 잰다.

```
documents/   문서 원본(HTML)과 PDF 생성기
  pdf/       Drive 에 올릴 PDF 8종
golden/
  retrieval.json         질의 37개와 각 정답의 앵커 문장   ← 이 세트의 중심
  tasks.json             부록. 아래 「범위」 참고
  tasks_groupware.json   부록
retrieval_eval.py        측정 하네스
```

## 1. 범위 — 무엇을 재고 무엇을 안 재나

재는 것은 **문서에서 근거를 찾아내는 능력**이다. 그래서 하네스는 에이전트를
거치지 않고 `embed_queries` → `vec_idx` 를 직접 때린다. 대화로 재면 LLM 의
회차별 흔들림과 도구 선택이 섞여 들어와, 숫자가 나빠졌을 때 **청킹이 나빠진
건지 모델이 그날 이상했던 건지 가를 수 없다.** 여기서는 원인이 한 곳이고,
싸고, 몇 번을 돌려도 같은 답이 나온다.

⚠ `golden/tasks.json` · `tasks_groupware.json` 은 **부록이다.** `task_extraction`
도구를 쓰는 prebuilt 「업무 추출 에이전트」 전용이고, 기본 어시스턴트의 도구
21개에는 그 도구가 아예 없다(내장 32개 중 명시적으로 제외된 11개 중 하나).
제품의 기본 기능이 아니므로 이 세트의 중심이 아니다.

## 2. 정답을 적는 방식 — chunk_id 를 쓰지 않는다

재색인하면 `chunk_id`(UUID)가 새로 나온다. 정답을 거기에 걸면 **청킹을 바꾸는
순간 정답지가 무효**가 되는데, 그 전후를 비교하는 것이 이 세트의 목적이므로
목적 자체가 깨진다.

정답은 **문서 파일명 + 원문에 그대로 있는 앵커 문장**이다. 채점은 검색된 청크의
본문이 앵커를 품는지로 한다(공백을 모두 지운 뒤 부분 문자열). `CHUNKING_MAX_TOKENS`
를 바꾸든 제목 밀도 보정을 켜든 **같은 정답지로 잰다.**

두 가지를 조심한다. 둘 다 실제로 밟았다.

- **문서 이름을 부분 문자열로 적지 않는다.** 「과업지시서」라고 적었더니 두
  프로젝트의 파일에 다 걸려 잠식률이 거꾸로 나왔다(자기 문서를 남의 것으로 셌다).
  파일명 전체를 적고, 하네스가 색인에 그 이름이 실재하는지 먼저 본다.
- **앵커는 한 문서에만 있어야 한다.** 여러 문서에 있으면 변별력이 0이다.
  하네스가 preflight 에서 잡아 준다.

## 3. 지표

| 지표 | 뜻 |
|---|---|
| Recall@1 / @5 / @10 | 정답 청크가 상위 k 안에 든 질의 비율 |
| MRR | 정답이 처음 나온 순위의 역수 평균 |
| 잠식률 | 다른 프로젝트 문서가 상위 3 에 든 질의 비율 |
| **앵커 정착률** | 앵커가 지금 색인 안에 **온전히** 남아 있는 비율 |

마지막 것이 이 세트에만 있는 지표다. 앵커를 못 찾으면 검색이 못 찾은 것이
아니라 **청킹이 문장을 두 청크로 잘랐거나 파싱이 흘린 것**이다. 이 둘을 안
가르면 청킹을 바꿀 때마다 검색이 나빠진 것처럼 보인다.

## 4. 실행

컨테이너 안에서 돈다(DB·RunPod 설정이 거기 있다).

```
docker compose -f infra/docker/docker-compose.yml exec -T web \
  python tests/eval/retrieval_eval.py --json /tmp/eval/baseline.json
```

`--json` 으로 남긴 파일끼리 비교하는 것이 고도화 전후 판정이다.

⚠ **질의를 16개씩 나눠 임베딩한다.** 37개를 한 번에 넘기면 워커가 `FAILED` 로
떨어진다(2026-08-28 실측). 제품은 `document_search` 가 질의 하나씩만 부르므로
이 한도에 닿은 적이 없다.

## 5. 기준선 (2026-08-28 · 문서 8종 · 청크 294개)

```
Recall@1    59.5%   (22/37)
Recall@5    94.6%   (35/37)
Recall@10   97.3%   (36/37)
MRR         0.743
잠식률      16.2%   (6/37)
앵커 정착  100.0%   (37/37)
```

읽는 법 —

- **앵커 정착 100%** 는 파싱·청킹이 37개 문장을 하나도 자르거나 흘리지 않았다는
  뜻이다. 지금 청킹(`CHUNKING_MAX_TOKENS=512`, merge_peers)에서는 문장 단위가
  온전하다.
- **Recall@5 94.6% 인데 @1 이 59.5%** 다. 찾기는 찾는데 **1등으로 못 올린다.**
  상위 5 안에 넣는 것과 1등에 놓는 것은 다른 문제이고, `document_search` 의
  기본 `top_k=10` 이면 실사용에는 대부분 걸린다.
- **잠식률 16.2%** 는 문서가 8종뿐인데도 나온 값이다. 같은 발주사의 다른 사업
  문서가 절 제목까지 같아서 그렇다 — 의도한 난이도다. 문서가 100종이 되면 이
  숫자가 어떻게 변하는지가 볼거리다.
- 놓친 1건(Q29)은 「스냅샷으로 레거시를 받는다」가 과업지시서와 회의록 양쪽에
  적혀 있어 엉뚱한 쪽이 올라온 경우다. 문서 사이 근사 중복이 만드는 전형적인
  실패다.

## 6. 문서를 고칠 때

HTML 을 고치고 다시 굽는다. PDF 를 직접 고치지 않는다.

```
.venv/Scripts/python.exe tests/eval/documents/build_pdf.py
```

굽고 나면 **앵커가 그대로인지** 본다. 문장을 고치면 정답지가 조용히 틀려지는데,
`retrieval_eval.py` 의 preflight 가 「앵커를 색인에서 못 찾음」으로 잡아 준다.
