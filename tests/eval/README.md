# 에이전트 평가 세트

업무 추출과 근거 검색이 **얼마나 맞는지 숫자로 말하기 위한** 문서 세트와 정답지다.
사람이 눈으로 보고 「괜찮네」 하는 것으로는 고도화 전후를 비교할 수 없다.

```
documents/   문서 원본(HTML)과 PDF 생성기
  pdf/       Drive 에 올릴 PDF 8종 — build_pdf.py 가 만든다
golden/      정답지
  tasks.json            프로젝트 A 의 기대 업무 8건과 필드별 근거 위치
  tasks_groupware.json  프로젝트 B 의 기대 업무 4건 (격리 시험용)
  retrieval.json        질의 14건과 그 근거가 있어야 할 절
```

## 1. 무엇을 평가하나

| # | 대상 | 어떻게 보나 |
|---|---|---|
| 1 | 업무 추출 재현율 | 기대 업무 8건 중 몇 건을 뽑았나 |
| 2 | 오추출 | 사업관리 절차(보고·검수·보안)를 업무로 뽑지 않았나 |
| 3 | 교차 문서 필드 채우기 | 역할·기술·공수·일정·제약·위험을 **다른 문서**에서 가져왔나 |
| 4 | 모르는 것을 모른다고 하나 | 비어 있는 필드를 `missing_fields` 로 알렸나, 아니면 지어냈나 |
| 5 | 근거 검색 | 질의마다 정답 절이 상위 k 안에 들어왔나 |
| 6 | 프로젝트 격리 | 프로젝트 A 의 근거에 프로젝트 B 의 문서가 섞이지 않았나 |

3번이 이 세트의 설계 의도다. **필드를 일부러 다섯 문서에 갈라 놓았다** — 기준 문서만
읽어서는 어느 업무도 완성되지 않는다. 공수는 WBS 에만, 필수 기술은 인력 운영
계획서에만, 위험은 회의록에만 있다.

## 2. 일부러 심어 둔 것 — 고치지 말 것

읽다가 「빠졌네」 싶은 곳들은 대부분 의도한 것이다.

| 심은 것 | 어디 | 무엇을 보려고 |
|---|---|---|
| 사업관리 절차 한 장 | 과업지시서 9장 | 추출 1단계 지시가 「보고·검수·산출물 제출·보안은 여기서 찾지 않는다」다. 이것을 업무로 뽑으면 오추출 |
| 공수 「미정」 | WBS W-03 | `effort_hours` 를 0 이나 그럴듯한 숫자로 **지어내는지**. 모델은 모르는 값을 0 으로 채운다 |
| 우선순위 공란 | WBS W-06 | 위와 같다. `missing_fields` 에 `priority` 가 나와야 정답 |
| 완료 기준 전건 「미정」 | 요구사항정의서 8장 | 과업 3.7(관측성)에는 완료 기준이 없다. 다른 과업 것을 끌어다 붙이면 오답 |
| 우선순위가 어디에도 없음 | 그룹웨어 문서 전체 | B 의 기대 업무 6건 **전건**에서 `priority` 가 결측으로 나와야 한다 |
| 공수 「미정」 | 그룹웨어 과업지시서 7 (3.6) | A 의 W-03 과 같은 함정을 다른 문서에서 한 번 더 |
| 다른 사업 문서 3종 | 그룹웨어 계열 | 근거 잠식. 특히 「공용 성능시험 환경 1식 예약」이 양쪽 기준 문서에 다 있다 |
| 프로젝트 2개 | A · B | 문서 풀은 팀 소속이라, 프로젝트가 하나면 격리를 볼 수 없다 |

**B 의 기준 문서는 A 의 디스트랙터를 겸한다.** 그래서 일부러 A 의 기준 문서와 같은
무게(8쪽)로 썼다 — 얇으면 근거 경쟁이 안 되어 잠식을 못 잡는다. 「과업 범위」
「산출물 및 검수 기준」 「투입 인력」 「제약사항」 같은 절 제목도 A 와 똑같이 붙여
두었다. 제목만 보고 문서를 고르면 틀리게 만들려는 것이다.

## 3. 실서버에 올리는 절차

### 3.1 초기화

옛 프로젝트와 문서를 걷어낸다. 팀·계정·커넥터는 남으므로 재로그인도 Google 재연결도
필요 없다.

```bash
pg_dump "$DATABASE_URL" > backup_$(date +%Y%m%d_%H%M).sql
psql "$DATABASE_URL" -f DB/reset_eval.sql
```

**그리고 Drive 팀 폴더에서 옛 파일을 치운다.** 3.3 에서 폴더를 다시 저장하면 전체를
훑으므로, 폴더에 남아 있으면 그대로 다시 들어온다. S3 원문도 함께 치운다
(자세한 것은 `DB/reset_eval.sql` 맨 아래).

### 3.2 PDF 올리기

`documents/pdf/` 의 8종을 연결된 Drive 팀 폴더에 올린다. **파일 이름이 곧 화면에
보이는 문서 이름**이므로 바꾸지 않는다 — 정답지가 이 이름으로 문서를 가리킨다.

### 3.3 수집

화면에서 팀 폴더 지정을 다시 저장한다. 전체 수집이 돌아 8종이 등록되고 본문 색인까지
올라간다. 대화 시작 시의 동기화는 **변경분만** 보므로 이미 폴더에 있던 파일을 새로
등록해 주지 않는다.

색인이 끝났는지는 문서 목록에서 본다. 등록만 되고 색인이 안 된 문서는 문장 근거를
내지 못해 평가가 통째로 무의미해진다.

### 3.4 프로젝트 만들기

팀장 계정으로 두 개를 만든다(프로젝트 생성은 팀장만 된다).

| 프로젝트 이름 | 기준 문서 |
|---|---|
| 한빛몰 주문·정산 시스템 고도화 구축 | `한빛몰_주문정산_고도화_과업지시서.pdf` |
| 2027년도 사내 그룹웨어 유지보수 용역 | `한빛리테일_사내그룹웨어_유지보수_과업지시서.pdf` |

새 프로젝트 대화상자에서 이름을 넣고 기준 문서까지 고른다. 나중에 바꾸려면 프로젝트
화면의 「기준 문서 변경」을 쓴다.

## 4. 채점

### 4.1 업무 추출 (`golden/tasks.json` · `golden/tasks_groupware.json`)

두 프로젝트를 각각 추출해 따로 채점한다. A 가 8건, B 가 6건이다.

| 항목 | 계산 | 기준 |
|---|---|---|
| 재현율 | 뽑은 기대 업무 수 / 8 (B 는 / 6) | 1.00 을 목표로 한다. 과업 하나를 둘로 쪼갠 것은 1건으로 센다 |
| 오추출 | `negative_tasks` 와 겹치는 건수 | **0 이어야 한다.** 1건이라도 나오면 재현율과 무관하게 실패로 본다 |
| 필드 정확도 | 맞은 필드 수 / 채워진 필드 수 | 값이 정답지와 다르면 오답. `null` 은 세지 않는다 |
| 결측 인지 | `missing_fields_expected` 재현율 | 지어낸 값(예: 공수 0, 우선순위 「중」)은 **필드 정확도에서도 감점** |
| 근거 정확도 | `evidence_refs` 가 가리킨 청크가 정답 절인가 | 문서만 맞고 절이 다르면 0.5 로 센다 |
| 격리 | 프로젝트 B 문서를 인용한 근거 수 | 0 이어야 한다 |

한 번의 추출로 판정하지 않는다. **같은 조건으로 3회 돌려 평균과 편차를 함께 적는다** —
이 파이프라인은 모델 호출이 5단계라 회차 간 흔들림이 있다.

### 4.2 근거 검색 (`golden/retrieval.json`)

질의 14건을 그대로 던져 상위 10건을 받는다.

- **Recall@10** — 정답 절이 상위 10 안에 있는 질의의 비율
- **MRR** — 정답 절의 첫 등장 순위의 역수 평균
- **잠식률** — `must_not_cite` 에 적힌 문서가 상위 3 안에 든 질의의 비율

Q14(시험 환경)와 Q10(과업 발굴)이 이 세트에서 가장 잘 깨지는 자리다.

## 5. 문서를 고칠 때

HTML 을 고치고 다시 굽는다. PDF 를 직접 고치지 않는다.

```bash
.venv/Scripts/python.exe tests/eval/documents/build_pdf.py
```

Chrome 헤드리스의 `--print-to-pdf` 를 쓴다(새 의존성 없음, 한글 조판이 정확하고
텍스트가 살아 있는 PDF 가 나온다). 굽고 나면 **정답지의 절 번호가 그대로인지** 본다 —
문서를 고치면서 절 번호가 밀리면 정답지가 조용히 틀려진다.

바꾼 문서는 Drive 에서 덮어쓴다. 같은 파일을 고치면 수집이 변경으로 보고 다시 받아
색인한다(등록이 아니라 갱신으로 센다).
